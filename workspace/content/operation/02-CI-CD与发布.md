# OPS-02 CI/CD 与发布

当前 CI 的作业与依赖以 [ci.yml](../../../.github/workflows/ci.yml) 为准；已配置 backend、frontend、images 三项作业。端到端、AI 评测、额外安全扫描、制品推送与远程发布计划按本文准备并接入，已有作业成功不代表完整发布能力已验收。

## 1. 原则

1. 提交到 `main` 须通过适用质量门禁；常规合并通过 PR 检查。生产可部署性须在目标环境另行验证。
2. 准备远程发布时采用同一镜像摘要从 staging 晋升到 production，不重新构建。
3. **生产发布与版本标签须产品负责人明确批准**（AGENTS.md：未经明确要求不发布、不打标签）。
4. 迁移向前兼容一个版本，发布可在 15 分钟内回滚（REQ-02 DEP-03）。
5. 未执行或被跳过的检查在流水线摘要中如实显示，不视为通过。

## 2. 流水线

当前流水线在 PR 与 push 到 `main` 时执行：

```text
backend
  ├─ 格式、vet、lint、Race、govulncheck
  ├─ 空库 Schema、隔离 PostgreSQL / Redis / Kafka / 私有对象 / Temporal 合同
  └─ Wire / Swagger 生成一致、公开路由与在线 Swagger、@umijs/openapi 客户端一致
frontend
  └─ 冻结依赖安装 → lint → format → typecheck → vitest → build
images（依赖 backend 与 frontend 通过）
  └─ 构建 backend 与 frontend 镜像；不推送制品或执行远程部署
```

计划补充文档编号与链接检查、Skill 评测、secret/许可与制品扫描、E2E 冒烟。准备发布流水线时再接入 SBOM、镜像仓库、staging 部署及冒烟；夜间性能、故障注入与多浏览器测试须有独立环境和实际运行证据。

### 2.1 质量门禁汇总

下表定义计划采用的完整门禁；具体已启用步骤见当前工作流。接入新增门禁时须证明其执行、失败阻断与跳过报告有效。

| 门禁                                                                       | 阻断 PR                       | 说明                                         |
| -------------------------------------------------------------------------- | ----------------------------- | -------------------------------------------- |
| 格式与静态检查（Go / 前端）                                                | 是                            | PROJECT.md §9                                |
| 单元、集成、工作流回放、前端组件测试                                       | 是                            | TST-01 §2                                    |
| Race Detector                                                              | 是                            | AGENTS.md                                    |
| 漏洞扫描（高危）                                                           | 是                            | govulncheck、pnpm audit、Trivy               |
| 生成物一致（wire、swag、在线 Swagger、`@umijs/openapi` API）及公开路由覆盖 | 是                            | REQ-02 MNT-03                                |
| 单一 Schema 可初始化空库；既有库增量升级另行验证                           | 是                            | DES-02 §10；空库通过不替代数据保留与升级验收 |
| Secret 扫描                                                                | 是                            | DES-07 §13                                   |
| 文档编号与链接校验                                                         | 是（workspace 变更时）             | PLN-02 §4.2                                  |
| AI 评测门禁                                                                | 是（Skill / 模型变更时）      | TST-03 §6                                    |
| E2E 冒烟                                                                   | 是                            | TST-01 §6                                    |
| 覆盖率                                                                     | 否（核心包 < 80% 时评论提示） | REQ-02 MNT-02                                |

计划的 CI 运行时长目标：PR 全部检查 ≤ 20 分钟（依赖缓存：Go module、pnpm store、Docker layer）。

CI 直接运行格式、静态检查、测试、生成一致性和镜像构建命令，不使用项目脚本或 Makefile。测试数据库隔离，实际外部依赖按工作流提供；通用 Go Race 测试禁用结果缓存，摘要显示通过、失败与跳过数量，跳过不能视为对应集成验收。

### 2.2 失败定位与交付

1. 提交前核对任务文件范围、测试目录、格式、静态检查和受影响测试；按 CI 固定版本使用工具，并核验 ffmpeg/ffprobe 等实际系统依赖。
2. 数据库测试使用隔离临时空库，初始化同一 Schema；故障注入独立建库。记录真实条件与跳过项，不把缺环境时的绿色结果当集成验收。
3. 已获授权推送后，按本次 SHA 等待工作流全部作业结束；失败先查看日志并修复首个可操作错误，针对回归通过后再推送。只有证实外部临时故障才重跑。
4. 交付报告包含 SHA、最终 CI 链接与结论、工作区和未执行门禁。运行中、仅本地通过或必要作业跳过时，不报告 CI 全绿；推送 main 仍需用户明确授权。

## 3. 制品与版本

镜像目前只在 CI 构建；计划发布时准备以下制品标识和存储，推送及晋升须分别验收。

| 制品       | 标识                                                                | 存放                                             |
| ---------- | ------------------------------------------------------------------- | ------------------------------------------------ |
| 容器镜像   | `<仓库>/lanverse/<服务>:<git-sha>`；发布时追加 `:<版本号>`          | 火山引擎镜像仓库（CR）【待核实】                 |
| SBOM       | `sbom-<服务>-<sha>.json`                                            | 随镜像（OCI artifact）                           |
| 数据库结构 | `backend/db/schema.sql`（最终态唯一事实源，与应用固定同一 Git SHA） | Git；部署使用同一 SHA 的文件，当前无自动升级入口 |
| Skill 包   | 实际接入后随 owning Go 镜像发布版本化 Skill 包；未接入时不生成制品  | 镜像内                                           |
| 前端       | Next.js standalone 输出打包进镜像                                   | 镜像内                                           |

**计划版本规则**：语义化版本 `vMAJOR.MINOR.PATCH`；里程碑发布为 MINOR（如 M1 = v0.1.0，MVP = v1.0.0）；修复为 PATCH。版本标签与 GitHub Release 在产品负责人批准后创建，发布说明列出需求编号、迁移、注意事项。

## 4. 部署流程

远程 staging / production 部署尚未接入。准备执行以下流程前，须完成 OPS-01 的认证、资源与备份配置，并演练部署、回滚和运行中工作流兼容。

### 4.1 staging 目标流程

计划接入发布流水线后：拉取新镜像 → 准备数据库结构（新空库初始化 Schema；既有库执行已审阅实例增量）→ 滚动更新（先 worker、relay，再 api、frontend）→ 冒烟（当前身份与项目、实际已接入报价/生成/媒体链；消费者登录与渲染接入后另验）→ 结果通知。

### 4.2 production 目标流程（人工批准）

```text
1. 研发在 GitHub Actions 发起 “deploy-production”，选择已在 staging 验证的镜像 sha
2. 产品负责人在 Environment 审批中批准（GitHub Environments required reviewers）
3. 预检查：staging 冒烟通过；无进行中的 S1 事件；实例增量在 staging/隔离副本已验证；数据库备份 < 24 小时
4. 执行已审阅实例增量（只允许向前兼容的 expand 类升级，见 §5；禁止在既有库重跑 Schema）
5. 滚动更新（每个服务先起新实例、健康后停旧实例；backend-api 2 实例保证不中断）
6. 发布后冒烟 + 观察 30 分钟（错误率、延迟、队列积压、unknown 数；OPS-03 看板）
7. 记录发布：版本、sha、迁移、执行人、结果（GitHub Release 或部署记录）
```

计划发布窗口：工作日 10:00–17:00，避开批量生成高峰；计划停机类变更按 REQ-02 AVL-02 提前 24 小时通知。

## 5. Schema、既有库升级与发布顺序

当前已实现结构唯一来源是 `backend/db/schema.sql`；直接维护最终态表、索引、约束、函数、触发器和授权，不追加 up/down 文件。新空库由独立表所有者按 OPS-01 §7 在一个事务中初始化，管理员预置 `lanverse_app NOLOGIN NOSUPERUSER`。既有库依据实际实例与目标 Schema 审阅增量 SQL，单独记录前置结构、备份、执行内容和数据保留证据；该增量不成为另一套常驻结构事实源。当前 `lanverse` CLI 没有自动迁移命令。

准备增量升级时采用 **expand / contract** 两阶段：

| 变更            | 发布 N（expand）                            | 发布 N+1（contract）   |
| --------------- | ------------------------------------------- | ---------------------- |
| 加列            | 加可空列 / 带默认值；代码兼容新旧           | 回填后加 NOT NULL 约束 |
| 删列            | 代码停止读写该列                            | 删除列                 |
| 改列名          | 加新列 + 双写 + 回填；读新列                | 删旧列                 |
| 加索引          | `CREATE INDEX CONCURRENTLY`（独立审阅执行） | —                      |
| 改枚举（CHECK） | 放宽 CHECK（加新值）                        | 需要时收紧             |

- 增量升级在应用滚动更新**之前**执行；任何增量升级都必须让“上一版本代码”继续正常工作，保证可回滚。
- 大表回填由后台任务分批执行，不放在结构升级事务中。

## 6. 工作流与契约的兼容

| 对象                            | 规则                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Temporal 工作流                 | 修改已发布工作流的逻辑必须用 `workflow.GetVersion` 分支；回放测试通过（DES-04 §14）；删除旧分支前确认无在途执行             |
| Activity 契约                   | 只做向后兼容变更（加可选字段）；破坏性变更新建 Activity 名（`provider.submit.v2`），旧名保留至在途执行结束                  |
| Kafka 事件                      | 加字段不升版；语义变化发布 `.v2` 并双写一个发布周期（DES-03 §6.1）                                                          |
| 公共 API（`/api`，无 URL 版本） | 只做向后兼容变更；删除字段或改语义先标记废弃并保留一个发布周期；后端先于前端发布；对外开放接口（V2）另设带版本的 `/open/v1` |
| 前端与 API                      | 前端先兼容新旧响应；部署顺序为后端先、前端后                                                                                |
| Worker 部署                     | 新旧 Worker 同时存在期间，靠上述版本分支保证兼容；滚动更新后旧 Worker 优雅退出（DES-04 §2）                                 |

## 7. 回滚

接入发布能力时须在目标环境演练以下动作和目标时长；数据库恢复依赖实际可用且经过验证的备份。

| 场景             | 动作                                                                                                           | 目标时长     |
| ---------------- | -------------------------------------------------------------------------------------------------------------- | ------------ |
| 应用缺陷         | 重新部署上一版本镜像 sha（结构升级已保证兼容）                                                                 | ≤ 15 分钟    |
| 结构升级导致问题 | 优先前滚修复；需要撤销时先审阅特定实例的无损逆向调整，不执行历史 down 或重跑 Schema                            | 视情况       |
| 工作流逻辑缺陷   | 回滚 Worker 镜像；已按新逻辑运行的在途执行通过 `GetVersion` 分支保持一致；必要时对受影响执行发送信号或人工处理 | ≤ 30 分钟    |
| 数据损坏         | 按 OPS-04 恢复流程                                                                                             | RTO ≤ 4 小时 |

## 8. 功能开关

计划在能力需要分阶段启用时准备简单开关，优先复用模型注册表的状态与既有部署配置；接入时写审计并验证在途任务的行为。不预建第三方平台或组织级开关表；确需新增持久化结构时，先接受对应设计并更新 Schema。临时开关在功能稳定后移除。

## 9. 依赖更新

- 计划接入 Renovate，准备 Go、npm、Docker 基础镜像和 GitHub Actions 更新分组；每周普通更新、安全更新及时处理，自动创建 PR 的行为在接入时验证。
- 主要框架（Next.js、Gin、GORM、Temporal SDK）大版本升级作为单独任务评估。
- 基础镜像固定摘要；FFmpeg、libvips 版本升级需运行媒体黄金样例测试（TST-01）。

## 10. CI 中的密钥

- 远程发布接入时，通过 Environment secrets 准备镜像仓库推送与 staging / production 部署凭据；production 配置审批，权限限制到对应环境。
- CI 不持有任何模型供应商凭据；需要真实调用的评测由有权限的人手动触发，使用评测专用凭据与预算（TST-03 §7）。
