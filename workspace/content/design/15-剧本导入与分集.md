## 2. 处理流程

```text
选择文件（1..n）→ 前端校验格式与大小 → 上传到对象存储（REQ-30 上传流程）→ 勾选“我确认拥有该剧本的使用权”
→ POST 导入 → ScriptImportWorkflow：
     1. 逐文件抽取文本（docx → 段落文本；txt → 编码识别 UTF-8 / GBK / GB18030）
     2. 规范化（统一换行、全半角标点保留、去除页眉页脚与多余空行）
     3. 多文件按文件名集号排序拼接（插入“第 N 集”标记）
     4. 计算内容指纹；与已有版本相同 → 结束并提示
     5. 保存 script_version（全文写对象存储）
     6. 分集：先按规则（“第 X 集”“EP X”等标记）并保存为候选；规则未命中或结果异常时生成 AI 分集报价，导入结束。用户确认后由 OperationWorkflow（episode_split）执行 split_episodes Skill，新增一套 AI 分集候选；规则候选保留，用户在分集确认页选择以哪一套为基础并可调整
     7. 生成 episode 候选（split_status = candidate）
→ 用户在分集界面查看每集起止原文、字数；合并 / 拆分 / 重命名 / 调整顺序 → 确认 → 写入或调整正式分集（split_source = confirmed，候选集保持不变）
```

## 4. 接口

```http
POST /api/projects/{pid}/script-imports
{ "source_asset_ids": ["…", "…"], "rights_confirmed": true, "order": ["…", "…"] }
202 { "import_id": "…", "workflow_id": "script-import/…", "status": "importing" }

GET /api/projects/{pid}/script-imports/{import_id}
200 { "status": "done", "script_version_id": "…", "files": [ { "asset_id": "…", "file_name": "第1集.docx", "result": "ok", "chars": 5210 },
                                                            { "asset_id": "…", "file_name": "第7集.docx", "result": "failed", "reason": "file_corrupted" } ] }

GET /api/projects/{pid}/episodes?script_version_id=
200 { "items": [ { "id": "…", "split_set_id": "…", "split_source": "rules", "seq_no": 1, "title": "初遇", "span_start": 0, "span_end": 5210, "chars": 5210,
                   "split_status": "candidate", "preview_head": "…", "preview_tail": "…" } ] }

POST /api/projects/{pid}/episodes/split:confirm
{ "script_version_id": "…", "split_set_id": "…", "episodes": [ { "seq_no": 1, "title": "初遇", "span_start": 0, "span_end": 5210 }, … ],
  "expected_revision": 3, "ack_invalidate": false }
200 { "confirmed": 61, "invalidated": 0 }      422 validation_failed（重叠 / 遗漏 / 越界）
409 confirmation_required { "meta": { "affected_episodes": [ { "episode_id": "…", "seq_no": 3, "shots": 42 } ] } }
```

`expected_revision` 使用 `script.script_version.split_revision`：确认分集时在同一事务中比较并递增，只以数据库为准。

候选集与正式分集：同一剧本版本可并存多套分集候选（规则一套、每次 AI 分集一套，按 `split_set_id` 区分，`split_source = rules / ai`）。**候选集是不可变快照**，确认不修改、不迁移候选行，因此任何候选集都可随时再次选作基础。正式分集是独立的一套行（`split_source = confirmed`，`split_set_id = script_version.confirmed_split_set_id`，首次确认时生成）。确认时请求带所选基础候选集 `split_set_id`（记入审计）与提交的边界列表，一个事务（`SELECT script_version FOR UPDATE`，比较并递增 `split_revision`）：

1. **受影响集判定**：对现有正式分集的每一集，若提交的边界列表中存在 `seq_no`、`span_start`、`span_end` 完全相同的一项 → 未受影响；否则受影响。受影响集中 `confirmed_structure_id IS NOT NULL` 者（曾确认过解析，无论当前 `parse_status` 是否因再次编辑变为 `awaiting_review`）列入 `affected`，并据此生成下游过期事件。
2. **二次确认（REQ-12 R9）**：`affected` 非空且请求未带 `"ack_invalidate": true` → `409 confirmation_required`，`meta.affected_episodes[]`（集号、标题、已确认解析、下游镜头数），不做任何修改；前端弹出二次确认后带 `ack_invalidate` 重新提交。
3. **写入（只改正式分集的行）**：未受影响的集保留原行（保留 `id`、已确认解析与下游）；若提交的 `title` 与原行不同，只更新该行 `title` 并递增其 `revision`（标题不影响解析与下游，不列入 `affected`、不标记过期）；受影响的集原行置 `is_delete = true`（其 `parse_status`、`confirmed_structure_id` 随行一并失效，解析历史保留可查，不再出现在集列表，也不再作为下游依据）；提交中未匹配的项插入新行（`split_source = confirmed`、`split_status = confirmed`、`parse_status = not_started`）。候选集行不受影响。
4. **下游**：写 Outbox `script.split_confirmed.v1 {script_version_id, affected_episode_ids, renamed_episode_ids}` 与 `audit.recorded.v1`（记录基础候选集、受影响集、改名集的旧 / 新标题）；lineage 将受影响集的场、镜头、配音等标记过期（原因 `split_changed`，REQ-31），realtime 推送集列表变化（含改名）；新插入的集需重新解析。

首次确认（无原已确认集合）时 `affected` 为空，直接写入。

## 5. 异步与工作流

导入由 `ScriptImportWorkflow`（`script-import/{import_id}`）执行抽取、规范化、去重、保存版本与规则分集，写入规则分集候选；需要 AI 分集时生成 `episode_split` 报价后结束。用户确认后由 `OperationWorkflow`（LLM 分支，`split_episodes` Skill）新增一套 AI 分集候选（与规则候选并存，REQ-25 R5 只新增候选），由用户确认分集时选用。步骤、队列与超时以 DES-04 §3、§10.1 为准。

## 6. 事件与实时

`script.version_imported.v1`；SSE `episode.updated`（分集完成）。

## 7. 界面

- 剧本页：导入按钮 → 多文件拖拽区（显示每个文件的校验结果与顺序）→ 版权确认复选框。
- 分集编辑器：左侧集列表（集号、标题、字数、首尾预览），右侧原文；在原文中点击“在此处拆分”、在列表中“与下一集合并”、编辑标题；顶部“确认分集”。

## 8. 权限与审计

制作者。审计：`script.imported`、`episode.split_confirmed`。

## 9. 非功能要求

PERF-05（60 集约 60 万字导入与分集 ≤ 5 分钟）；AIQ（分集准确率：P0 样例 100% 正确，否则规则优先）。

## 10. 测试设计

- 单元：编码识别（UTF-8、GBK、GB18030、带 BOM）；集号识别正则；边界校验（重叠、遗漏）。
- 评测：10 部样例剧本的分集准确率（TST-03）。
- 集成：导入工作流中断续跑；重复导入。

## 11. 待确认

| 编号      | 问题                                         | 拟采用方案                                                                                                                | 确认时机                    |
| --------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| DES-15-Q1 | docx 解析用什么库？                          | 自研轻量解析：读取 `word/document.xml` 的段落文本，不引入商业许可库；表格与文本框按段落顺序展开。                         | M2 开始前                   |
| DES-15-Q2 | 规则分集何时判定为“结果异常”，改用 AI 分集？ | 满足任一条件即视为异常：识别出的集数少于 2、单集字数少于 300 或超过 5 万、集号不连续。                                    | M2 实施中（用样例剧本校准） |
| DES-15-Q3 | txt 编码识别用什么方法？                     | 先检测 BOM，再依次尝试 UTF-8、GB18030 严格解码（GBK 是 GB18030 子集），均失败则判为 `file_corrupted` 并提示另存为 UTF-8。 | M2 开始前                   |

需求层面的待确认问题见 [REQ-12](../requirement/12-剧本导入与分集.md) 的“待确认”。

完整章节/富文本与文件来源实施以 [工作台设计 §15](工作台设计.md) 为准。稳定 lineage 与不可变 source/version 保留原 HTML、格式变化及重排历史；空章节保留但无零宽正式 episode。文件导入为持久 202/job，不采用同步 200 作为未知提交的唯一事实；1..200 文件逐文件失败与 1..2500 章节原子请求独立。正文与 rich 同内容索引不替代有序来源 manifest 唯一性，原件 media_asset_id 对手工/legacy 输入可空。分集/结构确认与既有确认保护继续沿本设计及 DES16；未装配的必要下游 owner 取证失败明确拒绝。

文件批次成功来源按冻结顺序一次发布新 draft；成功与失败并存为明确 partial，全部失败不发布版本。原 job 重试只处理失败文件并保留已成功 lineage/结果；以本 job 最近发布 revision 和完整映射进行 CAS，正文被其他操作改动时保留审阅结果并报告冲突。取消不撤销已经发布的成功版本。详细未知对象、执行取消和恢复边界沿 工作台设计 §15.7。

## 故障约束与专项验证

- 专项验证：用 60 集 docx、重复文本、三文件中一损坏、无集标记和未确认版权数据执行 TC-12-01～05；注入导入中断、AI 分集失败与改动已解析集，核验边界、去重、逐文件结果及 PERF-05（REQ-12 §3；DES-15 §10；TST-02/TST-03）。

- 编码或文件损坏可能造成缺集：逐文件报告失败，仅对成功文件生成候选，用户修复后重导。
- 规则与 AI 都无法分集：保留原文并以单集候选供手工拆分；旧已确认分集不被失败候选覆盖。
