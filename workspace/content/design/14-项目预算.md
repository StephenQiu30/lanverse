## 2. 数据

| 表                     | 关键字段                                                                             | 为什么需要         |
| ---------------------- | ------------------------------------------------------------------------------------ | ------------------ |
| `billing.budget`       | `limit_micros`、`reserved_micros`、`settled_micros`、`revision`；`ck_budget_balance` | 余额计算与并发保护 |
| `billing.ledger_entry` | `entry_type = budget_change`                                                         | 预算调整留痕       |

`budget_change.amount_micros` 记录新预算上限减旧预算上限；调高为正、调低为负。它只记录额度变化，不计入项目已结算费用。预算更新、分录、审计与 Outbox 必须在同一事务提交。

`ck_budget_balance` 为 `reserved_micros + settled_micros <= limit_micros OR is_overrun`；`is_overrun` 默认为 false，超支必须显式标记（DES-02）。

## 3. 接口

```http
GET /api/projects/{pid}/budget
200 { "limit_micros": 500000000, "reserved_micros": 12000000, "settled_micros": 180000000,
      "available_micros": 308000000, "available_display": "¥308.00", "is_overrun": false, "revision": 4 }

PUT /api/projects/{pid}/budget
{ "limit_micros": 800000000, "expected_revision": 4 }
200 { … }     422 validation_failed { "errors": [{ "field": "limit_micros", "code": "below_committed", "message": "最低可设 ¥192.00" }] }
```

报价与确认中的预算错误：`422 budget_insufficient { "meta": { "shortfall_micros": 30000000 } }`。

## 4. 异步与工作流

无；预留与结算在 `flow` 队列 Activity 的数据库事务中执行（DES-04）。

## 5. 事件与实时

`billing.budget_changed.v1`（realtime 投影为项目 SSE `budget.updated`，只携带 `available_micros`；审计经 `audit.recorded.v1`）、`billing.settled.v1`（realtime 从结算后的余额投影同一 SSE）、`billing.budget_low.v1`（notify）、`billing.budget_overrun.v1`（notify，结算导致超支时由 DES-04 §7 发出）。

预算调整时，只有可用额从不低于上限 20% 变为严格低于 20%，才在同一事务写 `billing.budget_low.v1` Outbox；默认上限 0 不判为低余额。事件按每次跨越记录事实，同一项目同一自然日的通知去重由 E-33 消费者负责。结算导致的跨越与超支由 DES-04 §7 的结算事务按相同阈值规则处理。

## 6. 界面

设置页预算卡片（上限、已结算、已预留、可用、使用率进度条）；报价对话框显示剩余预算与差额；顶部低余额横幅。

## 7. 权限与审计

管理员与制作者均可设置（MVP 内部使用）；审计 `budget.changed`（前后值）。

## 8. 非功能要求

REL-08（任何时刻预算 ≥ 已结算 + 已预留，超支需显式标记；每日对账）。

## 9. 测试设计

并发确认测试（race）；结算超支路径；阈值通知去重。

## 10. 待确认

| 编号      | 问题                                                        | 拟采用方案                                                                                                                        | 确认时机  |
| --------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------- |
| DES-14-Q1 | 结算超支（`is_overrun = true`）后，是否阻止该项目的新确认？ | 阻止：所有新确认返回 `budget_insufficient`，直到上限调高到覆盖已结算加已预留。                                                    | M1 开始前 |
| DES-14-Q2 | 低余额通知的去重窗口？                                      | 按 REQ-11 与 REQ-33：可用余额跨越上限 20% 时通知，同一项目每个自然日（Asia/Shanghai）最多一次，去重键 `budget:{pid}:low:{日期}`。 | M1 实施中 |
| DES-14-Q3 | 每日对账发现账本不平时，是否自动修正？                      | 不自动修正：发告警与 `billing.reconciliation_diff.v1`，由管理员用 `ledger:adjust` 处理并写审计。                                  | M1 开始前 |

需求层面的待确认问题见 [REQ-11](../requirement/11-项目预算.md) 的“待确认”。

## 故障约束与专项验证

- 专项验证：用余额 50/报价 80、已结算 300/预留 50、双浏览器并发和 25%→15% 阈值执行 TC-11-01～04；验证超支记事实、阻止新确认及同项目同阈值同自然日去重（REQ-11 §3；DES-14 §9；TST-02）。
- 数据作用域按 DES-02 D10 的四类原则与 DDL 表级定义核对；本 Epic 的 `billing.budget`、`billing.ledger_entry` 均为项目级表，查询强制带 `project_id`，结算超支不得绕过 `ck_budget_balance`（DES-02 §5.10）。

- 并发预留可能突破预算：数据库事务拒绝后确认方，刷新报价与余额后再试。
- 实际结算超出预留：仍按事实记账、标记超支并拦截新确认；对账差异只告警，管理员核对后做审计留痕的调整。
