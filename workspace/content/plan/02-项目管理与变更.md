## 3. 任务管理

### 3.1 工具与结构

- 使用仓库根目录的 [`BACKLOG.md`](../../../BACKLOG.md) 作为唯一的进度与任务清单（只维护当前任务、状态与未决项；执行证据随CI或交付）：
  - **Epic** = MVP 功能 `E-<REQ 号>`（需求 REQ-06～REQ-33、REQ-35～REQ-39 与对应功能设计 DES-09～DES-41）；
  - **Task** = 可在 1–3 天内完成并独立提交的工作 `E-<REQ 号>-<序号>`，写明怎么做（设计章节链接）、涉及文件与验收用例；基础任务为 `P0-nn`、`M1-nn`；
  - **Bug**、**Tech Debt**、**Spike**（调研）单独标签。
- 看板状态统一为 `待办` → `就绪` → `进行中` → `评审中` → `待验收` → `完成`；执行阶段可进入 `阻塞`，解除后回到符合条件的状态，评审不通过回到 `进行中`。真实验收条件尚未满足时保留 `待验收`，不能因技术门禁通过关闭完整任务。
- 活跃任务的小节与唯一状态行放在同一 BACKLOG，通过稳定任务 ID 关联；小节记录范围、合同、授权、依赖、验证与下一步，不重复维护状态。模板见 [知识库使用手册](../KNOWLEDGE.md)。Nextra 与 Obsidian 只派生视图，外部 Issues/Projects 只用于讨论或证据引用，默认不双写任务状态。

### 3.2 就绪定义（DoR）

任务进入“就绪”须满足：

1. 关联功能基线已接受，或用户明确授权当前合同且范围/日期已记录；任务引用具体需求与验收，不从草案默认推断授权。
2. 涉及的表、接口、工作流已在 DES-02 / DES-03 / DES-04 中定义；需要新增的已先修改设计文档。
3. 依赖写到具体任务或已验证合同，并列所需状态；不得把整个 Epic 的后续联调、跨阶段模板或真实供应商验收当作本阶段实现的前置。合同模拟可并行，必须保留其真实验收缺口。
4. 验证方式明确（哪些测试、哪些手工步骤）。
5. 规模 ≤ 3 天；超过则拆分。

### 3.3 完成定义（DoD）

1. 代码满足 PROJECT.md 与 AGENTS.md（Go 规范、分层、命名）。
2. 核心逻辑按 Red → Green → Refactor；测试覆盖功能设计“测试设计”一节中与本任务相关的条目。
3. 质量门禁全部通过（格式、静态检查、单元与集成测试、Race、漏洞扫描、契约一致性），未执行项如实说明。
4. 当前任务的验收标准可以演示通过（端到端或手工）；Epic 与里程碑的全部功能标准另行聚合验收。限定切片完成只标该切片，不把依赖模拟、单机或固定素材证据外推成完整产品通过。
5. 文档同步：设计变化已更新 DES 文档；接口已更新swag注解/DTO并重生在线Swagger；当前已实现结构更新唯一Schema，概念规划同步DES-02。
6. 提交信息符合 `type(scope): 中文说明`；工作区无无关文件。
7. TST-02 的稳定标准与实际验证相符，任务状态/未决项更新BACKLOG，证据随交付保存。

## 4. 需求基线与变更控制

### 4.1 基线

- 文档评审通过后更新正式事实源与未决边界，即成为**基线**；基线版本以 Git 标签标记：`baseline-req-v<N>`（需求：PRD-01、REQ 文档、功能文件）、`baseline-design-v<N>`（DES 文档）。标签的创建与推送须产品负责人明确要求（AGENTS.md）。
- 实施以已接受合同或用户明确授权范围为依据，授权范围与未决边界明确可查；候选默认方案不能自动视为已接受。产品/架构变化先更新正式事实源并评审，任务状态与未决项只在 BACKLOG 维护。

### 4.2 文档评审检查清单

| 类别   | 检查项                                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------------------------- |
| 需求   | 每条需求有编号、优先级、用户故事、业务规则、验收标准；验收标准可测试；无实现细节混入需求                              |
| 一致性 | 引用的需求、非功能、用例、功能编号都存在（直接校对链接、编号和任务计数）；术语符合 REQ-04；不新增项目脚本或 Makefile  |
| 完整性 | 每个 MVP 功能需求都有对应的功能设计（DES-09～DES-41），覆盖数据、接口、工作流、事件、界面、权限、非功能要求与测试设计 |
| 设计   | 已实现结构按唯一Schema验证；概念设计与未实现接口不预建，已实现接口以在线Swagger核对；失败路径与重试明确               |
| 风险   | 待确认项有默认处理与计划                                                                                              |

### 4.3 变更流程

```text
提出变更（任何人）→ 在 BACKLOG 关联任务的小节记录变更（填 §4.4 模板；外部 Issue 可作为讨论链接）
→ 影响分析（研发）：受影响的需求、功能文件、设计、已实现代码、测试、成本、里程碑
→ 决策（产品负责人）：接受 / 拒绝 / 延后；重大变更记为新的产品决策 P<n>（PRD-01 §9）
→ 先改文档（需求 → 设计 → 计划）并评审 → 更新基线标签（按需）
→ 再改代码与测试 → BACKLOG 保留验证摘要与证据链接，完整结果随 CI 或交付附件保存
```

变更分级：

| 级别 | 例子                                                   | 审批                          |
| ---- | ------------------------------------------------------ | ----------------------------- |
| 小   | 文案、界面细节、不影响接口与数据的规则澄清             | 研发自行修改文档并知会        |
| 中   | 新增或修改验收标准、字段、接口；非功能目标调整         | 产品负责人批准                |
| 大   | 范围增减、优先级跨版本移动、技术选型变化、成本模型变化 | 产品负责人批准并记录为 P 决策 |

### 4.4 变更请求模板

```markdown
## 变更内容

## 影响分析

- 需求：（编号）
- 功能文件：（REQ-xx / DES-xx）
- 设计：（DES-02 / DES-03 / DES-04 …）
- 已实现代码与实例增量升级：
- 测试与验收：
- 成本与进度：

## 方案与替代方案

## 决策（产品负责人填写）：接受 / 拒绝 / 延后，日期
```

## 6. 代码与评审流程

- **主干开发**：`main` 始终可构建、可部署。
- **分支与 PR**：研发按需使用短分支（≤ 3 天）+ PR 合并；AI 助手只在产品负责人明确要求时创建分支、PR、标签或合并（AGENTS.md）。
- **评审**：PR 至少一人评审（1 人团队时由产品负责人抽查 + AI 代码审查）；评审关注：需求符合度、分层与依赖方向、错误处理、并发与幂等、测试充分性、安全与日志脱敏。
- **提交**：每个提交只做一件事，标题 `type(scope): 中文说明`，正文说明原因与影响。
- **结构与契约**：Schema/既有库增量、OpenAPI、Activity schema 的变更必须在 PR 描述中单独说明。

## 7. 缺陷管理

| 级别    | 定义                                     | 例子                   | 响应                       | 修复目标            |
| ------- | ---------------------------------------- | ---------------------- | -------------------------- | ------------------- |
| S1 致命 | 数据丢失、重复扣费、安全漏洞、服务不可用 | 账本不平、凭据泄露     | 立即（工作时段 30 分钟内） | 24 小时内修复或止损 |
| S2 严重 | 核心流程阻断且无替代方案                 | 无法渲染、无法确认报价 | 4 小时内                   | 3 天内              |
| S3 一般 | 功能错误但有替代方案                     | 批量结果计数错误       | 1 个工作日内               | 当前里程碑内        |
| S4 轻微 | 界面、文案、体验问题                     | 对齐、错别字           | 排期                       | 按优先级            |

- 缺陷记录：复现步骤、期望与实际、环境、日志 / 追踪 ID、影响范围。
- S1 / S2 修复后补回归测试，并按 OPS-04 写事后复盘。

## 8. 风险管理

- 风险登记在 BACKLOG 相关任务的未决边界，字段：描述、概率（高 / 中 / 低）、影响（高 / 中 / 低）、已明确的负责人、应对措施、触发信号；任务状态仍只维护在唯一任务行。GitHub Issues（标签 `risk`）可作外部讨论链接，不是默认风险或任务状态源。
- 初始风险来自 PLN-01 §6 与 PRD-01 §14；每周复盘时更新；高概率 × 高影响的风险在周报中单列。

## 9. 度量与汇报

### 9.1 周报模板

```markdown
# 第 N 周（日期）

- 里程碑：M? 进度（验收标准通过数 / 总数）
- 本周完成：（任务、需求编号）
- 演示：（链接或截图）
- 风险与阻塞：
- 成本：本周模型费用、单分钟成本（P0 后）

```

### 9.2 度量

| 度量           | 口径                                   | 用途       |
| -------------- | -------------------------------------- | ---------- |
| 验收标准通过率 | BACKLOG 所链接有效执行证据中的已通过用例 / TST-02 中当前里程碑应执行用例总数 | 里程碑进度 |

| 构建健康       | CI 通过率、平均时长                    | 工程效率   |
| 产品指标       | PRD-01 §10 的成功指标                  | 产品效果   |
