# 历史参考 · PLN-01 实施路线与交付计划

> 历史参考：本文件保留旧范围和当时的方案，不再构成当前页面的必做需求或实施授权。当前基线见[页面总览](../../content/requirement/浮光页面/index.md)；实际已实现接口和结构仍以Handler/DTO与Schema为准。


- 依赖：[PRD-01](../../content/prd/01-产品需求文档.md)、[REQ-01](../../content/requirement/01-功能需求总表.md)、[REQ-02](../requirement/02-非功能需求规格.md)、[工作台设计](../design/工作台设计.md)、[PRD-02 产品能力与架构原则](../prd/02-产品能力与架构原则.md)、[DES-01](../design/01-系统架构设计.md)、[DES-08](../design/08-技术选型决策.md)
- 范围：阶段划分、每阶段交付与验收、人力安排、现有代码处置、风险
- 文档用途：本篇定义准备实施的顺序、交付目标与验收条件，任务和进度统一由 [`BACKLOG.md`](../../../BACKLOG.md) 维护。
- 约定：**以业务流程功能完整为准，时间不作硬约束**（PRD-01 P13）。下文周数按 1–2 名研发（含 AI 辅助编码）估算，只作排序与规模参考；里程碑以验收通过为完成标志

## 1. 结论

1. **先验证、再打底、后纵向切片**：P0 验证全能参考与成本 → M1 工程底座与顶层抽象 → M2–M4 沿工作流纵向打通，M5 结束即 MVP。
2. **M1 准备最小工程合同**：计划接入命令层、Operation、模型注册表、Temporal、Outbox 事件链与媒体来源属性；Go Harness 和实时链路按实际消费者逐项接入，不预建无消费者的抽象。
3. **每个里程碑以“浏览器里能完成什么”验收**，不以“模块写完”验收。
4. **P0 的全能参考结果是项目的关键决策点**：找不到在写实与风格化下都可用的模型，就需要调整方案或时间，而不是降级（PRD-01 §12、§14）。
5. **范围优先于时间**：周数只是估算；任何里程碑都以验收通过为完成标志，不因时间压缩业务流程。

### 2.1 执行优先级与完整生产目标

计划优先准备整项目验证和正式入口 Demo，完整生产验收按 P0、M1～M5 与 PRD-01 九场景执行。

1. 计划按工作台设计接入完整页面与正式项目/画布/媒体/实体合同，保持UUID/revision/永久幂等/Outbox和数据保留。
2. 计划按生成执行设计接入供应商纵向闭环：本机Codex imagegen优先，随后火山Seedream/Seedance，再由OpenRouter扩模型；执行、媒体/审核/费用、未知恢复与当前入口逐项验收。模型支持后扩参考图/蒙版，视频/音频/文本各自推进，全面页面完善后置。
3. 同步适用质量门禁、真实依赖和浏览器证据；目标设备、跨设备、真实账号/产物/费用缺条件时保持未验收，不默认免费或无声回退付费HTTP。
4. 计划按模块需求接入 script/bible/storyboard/audio/Agent、生成参考与正式选定；消费者注册与支付按 V2 规划。当前单工作区不恢复消费者登录；管理与人工费用核验的实际管理员授权独立明确。

任务和状态只在 [BACKLOG](../../../BACKLOG.md) 维护。实施前须列明具体依赖合同：审计先支撑业务命令，依赖传播按剧本与真实镜头分别验收，画布命令可独立于 AI 助手实施；模拟验证保留真实产品验收缺口。

## 3. 各阶段交付与验收

### P0 技术验证（估算 3 周）

**目标：** 在平台开发深入之前回答“全能参考能不能用、要花多少钱”。

| 交付             | 内容                                                                                                                                                                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全能参考评测     | 候选：火山方舟 Seedance、MiniMax 海螺 H3、经 OpenRouter 的海外版 Seedance（PRD-01 P18）；按写实、日系动漫、国风 / 仙侠、3D 卡通、韩漫 / 条漫 5 种风格，分别测单角色、双角色同框、动作参考、运镜参考、音频参考五类镜头；记录一致性、失败率、耗时、单镜成本 |
| 其他能力评测     | 带参考生图（Seedream、GPT Image）、TTS（MiniMax Speech、豆包语音）、剧本解析 LLM（豆包等，原文位置准确率）                                                                                                                                                |
| 样片             | 5 种风格各 1 条 30–60 秒样片，直接调用供应商 API 并人工串联完成                                                                                                                                                                                           |
| 成本模型         | 单镜成本（图生视频 vs 全能参考）、单分钟成片成本、平均重拍次数                                                                                                                                                                                            |
| 一致性评估方法   | 5 种风格分别的自动指标 + 人工抽检标准                                                                                                                                                                                                                     |
| 注册表初始配置   | 选定模型的 ModelProfile（模式、输入上限、参数 schema、价格）                                                                                                                                                                                              |
| 境外调用合规记录 | OpenRouter 调用的数据发送范围与留存条款，供对外发布前法务确认（REQ-02 CMP-06）                                                                                                                                                                            |

**退出标准：** 全能参考在写实与 4 种风格化下各有至少一家模型达到可用；主供应商确定；成本数据齐全。**未达标则暂停 M3 之后的工作，重新评估方案或时间。**

### M1 工程底座与顶层抽象（估算 4 周）

| 交付                 | 内容                                                                                                                                                                                                                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 工程                 | Go与前端目录、锁文件、CI（lint、format、typecheck、test、race、vuln、契约一致性、镜像构建）；本地默认 Compose 热更新运行 Go 与前端，也支持直接启动进程，读取根目录 `.env` 并连接本机已启动的 PostgreSQL、Redis、Kafka、MinIO、Temporal，含健康检查与隔离的备份恢复演练，不重建本机依赖；`docker-compose.yml`、`docker-compose-env.yml`、`docker-compose-prod.yml` 分别定义本机应用、依赖环境与生产应用；开发与检查直接运行工具命令，不设项目脚本或 Makefile |
| 契约链               | Gin Handler 注解 + DTO → swag 自动生成 Swagger → 后端在线 `/swagger/doc.json` → `@umijs/openapi` 生成前端 API；Axios `src/lib/request.ts` 作为普通 HTTP 唯一入口；Activity 类型由 Go owning 模块维护并以持久样例测试校验                                                                                                                                    |
| 全局异常与响应契约   | `backend-api` 的公共 `/api` 统一映射参数校验、鉴权、业务冲突、依赖故障、未匹配路由与未预期错误；panic 恢复也返回 DES-03 §2.4 的 RFC 9457 `application/problem+json`，保留 HTTP 状态、稳定 `code` 和 `request_id`，不泄露内部错误。成功响应使用端点 DTO（列表遵循 DES-03 §2.3），不额外套通用响应外壳                                                        |
| 命令层               | 当前工作区授权；未来消费者会话单独接入、幂等键、`expected_revision`、审计、Outbox 的统一中间层                                                                                                                                                                                                                                                              |
| 工作流与事件         | Temporal Worker（flow / media 队列）与 OperationWorkflow 骨架；Outbox relay → Kafka → realtime 消费者 → Redis Pub/Sub → SSE                                                                                                                                                                                                                                 |
| Go执行端             | owning Activity 与 Harness 的 Skill、校验、预算、Trace 合同；模拟供应商只用于技术验证，真实执行另验                                                                                                                                                                                                                                                         |
| Operation 骨架       | Operation 状态机、输入角色、报价、预留、`input_hash` 复用；经受控模拟适配器跑通 submit → poll → ingest                                                                                                                                                                                                                                                      |
| 模型注册表           | ModelProfile、参数 schema、价格规则；管理员维护界面（可先用表单 + JSON）                                                                                                                                                                                                                                                                                    |
| identity / workspace | 当前单工作区身份、项目（画幅、风格类型、风格预设）、预算                                                                                                                                                                                                                                                                                                    |
| media                | 计划按 DES-33 接入上传、探测、缩略图及来源与合规属性；预签名直传按对应上传合同单独实施                                                                                                                                                                                                                                                                      |
| 前端骨架             | 当前项目列表、按 `param_schema` 渲染参数表单的通用组件、SSE 订阅；应用级 TanStack Query Provider 管理服务端状态与查询失效，编辑器按功能使用 Zustand + Immer 管理局部状态；`request.ts` 统一解析错误，页面提供错误边界与可恢复反馈                                                                                                                           |

**基础能力验收：** 公共 API 契约测试覆盖参数错误、未登录、业务冲突、404、依赖故障与未预期错误，核对 HTTP 状态、`application/problem+json`、稳定 `code`、`request_id` 和敏感信息脱敏；成功响应按端点 DTO 与在线文档校验。前端测试覆盖请求错误解析、共享查询失效与局部编辑状态，浏览器验证页面错误后的恢复路径；Agent 内部路由增加时验证其错误契约。执行契约实现前按 PLN-02 就绪定义完成 DES-03 评审。

**验收：** 浏览器在当前工作区授权下建项目 → 上传图片看到缩略图；消费者登录接入后单独验证 REQ-06；用假供应商创建一个 Operation：报价 → 确认 → 完成 → 候选出现；在 submit 后杀掉 worker 再重启，任务恢复且账本只记一次；模拟响应丢失进入 `unknown` 并对账成功；CI 全绿。

## 5. 研发流程

1. 每个里程碑开始前，按 [TST-02 需求追踪矩阵](../../content/test/02-需求追踪矩阵.md) 中该里程碑的功能与验收用例拆分任务（就绪与完成定义见 [PLN-02](02-项目管理与变更.md) §3）；设计以 DES-01～DES-08 与对应功能设计（DES-09～DES-41）为准。
2. 核心业务逻辑 Red → Green → Refactor；每个任务独立提交，提交信息遵循 `AGENTS.md`。
3. 稳定验收标准留在 TST，BACKLOG 只维护状态/未决项；真实命令、日志、截图、未通过项与风险随 CI 或交付附件保存。
4. 需求或设计变化先改 PRD、REQ、DES 文档并评审，再改代码。

## 6. 主要风险

| 风险                       | 表现                                                    | 应对                                                                                                                                  |
| -------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 全能参考在某种画风下不可用 | 双角色同框换脸、参考音频不生效                          | P0 第一优先级验证；至少 2 家候选；不达标即重新评估，不静默降级                                                                        |
