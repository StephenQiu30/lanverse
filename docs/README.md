# 文档导航

结论：`docs/` 同时保存最新目标、当前已实现切片和可执行验收，但三者必须用状态区分。目标设计说明“最终要成为什么”，代码与测试说明“现在已经是什么”，迁移计划说明“两者怎样安全收敛”。

## 状态词

| 状态 | 含义 |
|---|---|
| 已接受目标 | 已确认的目标架构或产品契约，不等于代码已完成 |
| 已实现 | 已在当前代码和自动化验证中成立 |
| 部分实现 | 只有列出的能力已有代码证据，其余仍是目标 |
| 迁移中 | 当前实现与目标并存于迁移周期，但每个资源只有一个写入所有者 |
| 待决策 | 缺少会实质改变范围或边界的决定，不能自行写成事实 |
| 已取代 | 仅保留历史追溯，不再作为实现依据 |

## 事实优先级

1. 用户明确接受的最新 PRD、Architecture、Design 与 ADR 决定目标。
2. 当前代码、契约和测试决定实际落地状态；未验证能力不得写成已实现。
3. Plan 只描述顺序和门禁，不自动改变目标或完成状态。
4. Acceptance 必须记录真实命令、输入、结果和缺失条件。
5. 发生架构变化时，先更新 ADR 和受影响设计，再修改代码；不得只在代码中形成隐式架构。

## 文档维护规则

- Markdown 文件直接使用中文业务主题和文档用途命名，不添加项目名或版本前缀；只有去除后会改变含义的技术专有名词可以保留。文件名必须直接说明是架构、设计、需求、计划还是验收记录。
- 新能力只创建完成当前问题所需的文档，不批量建立空目录或占位文件。
- 当前仓库沿用已存在的 `designs/`、`plans/`、`requirements/`、`acceptance/` 目录，避免再建立 `design/`、`plan/` 形成双重事实来源；设计基线中的目录树视为目标分类摘要，具体目录调整需单独 ADR。
- 设计文档保留稳定边界、状态和失败路径；易变进度放入 Plan 或 Acceptance。
- 目标目录树是实施终态，不是要求一次性创建空项目。
- 文档内提到的服务、表、Topic、API 或状态，在落地前必须标明目标或部分实现。
- 当前与目标发生冲突时不得双写；由迁移计划指定唯一所有者和切换门禁。
