# Lanverse 文档中心

2026-09-25 起，Lanverse 从零重新设计。此前的 133 份历史文档已移除，需要追溯时查阅 Git 历史（移除前最后一个版本为 `c99a5528`）。旧文档、旧验收记录和现有代码都**不作为新设计的依据**，只在实施阶段作为“可复用候选”接受审计。

## 文档规则

1. **先需求，后设计，再实施。** 0101、02xx 被接受后再细化 03xx；03xx 被接受后才按 0401 领取实施任务。
2. **需求不写实现，设计不改需求。** 02xx 只描述“系统必须做什么、做到什么程度”；技术方案写在 03xx。设计发现需求有问题时，先改需求并评审。
3. **需求可验证。** 功能需求必须有 Given/When/Then 验收标准；非功能需求必须有目标值与验证方法。
4. **区分三类信息。** 公开事实（附来源）、合理推断、待确认事项分开写；时效性信息（模型能力、价格、法规）实施前重新核实。
5. **状态词只有四个：** 草案（待评审）→ 已接受 → 已实施（附验收证据）→ 已取代（写明被谁取代）。“已接受”不等于“已实现”。
6. **同一事实只在一处维护。** 决策在 0101 §9，功能需求正文在 features/，非功能需求在 0202，术语在 0204，状态在 0203 §6，表结构在 0302，接口签名在 0303；其他文档链接过去。
7. **一个功能一个文件。** 功能文件必须写清需求、需求分析，以及实现它背后需要的数据、接口、工作流、事件、界面、权限与非功能要求（模板见 features/README.md）。

## 编号规则

**文档文件**：`TTNN-中文主题.md`，`TT` 是生命周期阶段，`NN` 是阶段内序号。编号一经分配不复用；被取代的文档保留原编号并标注“已取代”。

| 段号 | 目录 | 阶段 |
| --- | --- | --- |
| 01xx | `prd/` | 产品需求（PRD、竞品调研） |
| 02xx | `requirement/` | 需求规格（功能、非功能、流程与用例、术语、界面） |
| 03xx | `design/` | 设计（架构、数据、接口、工作流、Agent、画布、安全、选型） |
| 04xx | `plan/` | 计划（实施路线、项目管理与变更） |
| 05xx | `test/` | 测试（策略、追踪矩阵、AI 评测） |
| 06xx | `operation/` | 运维（环境、CI/CD、监控、备份与故障响应） |
| — | `acceptance/` | 验收记录：`M<里程碑>-验收记录.md` |

**条目编号**（跨文档引用时写“文档号 + 条目号”，如 `0201 VID-04`）：

| 条目 | 格式 | 维护位置 |
| --- | --- | --- |
| 产品决策 | `P<n>` | 0101 §9 |
| 功能需求 | `模块-两位序号`，如 `VID-04` | 0201 |
| 非功能需求 | `类别-两位序号`，如 `PERF-03`、`CMP-01` | 0202 |
| 用例 | `UC-两位序号` | 0203 |
| 业务规则 | `BR-两位序号` | 0203 §7 |

需求被删除时保留空号并注明“已删除”，不把后面的编号前移；只有在整份文档统一评审时才整体重排，并同步所有引用。
