## 文档规则

1. **先 Design，后实施。** 0101–0301 被接受前不编码新功能；0401 被接受后才按阶段领取任务。
2. **文档按需产生，不套模板。** 只有当某个模块复杂到 0201 放不下时，才新建专项设计（如画布、生成任务）；每个阶段只维护一份验收记录。
3. **区分三类信息。** 公开事实（附来源）、合理推断、待确认事项分开写；时效性信息（模型能力、价格、法规）实施前重新核实。
4. **状态词只有四个：** 草案（待评审）→ 已接受 → 已实施（附验收证据）→ 已取代（写明被谁取代）。“已接受”不等于“已实现”。
5. **设计变化先改文档再改代码。** 同一决策只在一份文档里维护，其他地方链接过去。

## 编号规则

**文档文件**：`TTNN-中文主题.md`，`TT` 是文档类型，`NN` 是该类型内的序号。编号一经分配不复用；被取代的文档保留原编号并标注“已取代”。

| 段号 | 类型 | 示例 |
| --- | --- | --- |
| 01xx | 产品需求 | 0101 产品定义与需求分析；以后的模块详细需求依次为 0102、0103… |
| 02xx | 架构设计 | 0201 系统架构设计；画布、生成任务等专项设计依次为 0202、0203… |
| 03xx | 技术选型 | 0301 技术选型决策；模型评测报告等依次为 0302… |
| 04xx | 实施计划 | 0401 实施路线与交付计划 |

**需求条目**：`模块-两位序号`（如 `VID-04`），在 0101 中维护。每个模块内先按优先级排列（MVP → V1 → V2 → 待定），再连续编号。需求被删除时保留空号并注明“已删除”，不把后面的编号前移，以免引用失效；只有在整份文档统一评审时才整体重排，并同步所有引用。

**验收记录**：`docs/acceptance/M<里程碑>-验收记录.md`，如 `M1-验收记录.md`。
