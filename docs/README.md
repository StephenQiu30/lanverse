# Lanverse 文档中心

2026-09-25 起，Lanverse 从零重新设计。此前的 133 份历史文档已移除，需要追溯时查阅 Git 历史（移除前最后一个版本为 `c99a5528`）。旧文档、旧验收记录和现有代码都**不作为新设计的依据**。

## 文档规则

1. **先需求，后设计，再实施。** 需求被接受后再细化设计；设计被接受后才按 PLN-01 领取实施任务。
2. **需求不写实现，设计不改需求。** 设计发现需求有问题时，先改需求并评审。
3. **需求可验证。** 功能需求必须有 Given/When/Then 验收标准；非功能需求必须有目标值与验证方法。
4. **只为当前版本做需求与设计。** 需求规格（REQ-01～REQ-33、REQ-35～REQ-39）与设计文档（DES）只写首个版本（MVP）的内容，不出现 V2 描述；V2 与待定内容全部集中在 REQ-34，V2 规划时再拆出功能文件与设计。
5. **区分三类信息。** 公开事实（附来源）、合理推断、待确认事项分开写；时效性信息实施前重新核实。
6. **状态词只有四个**：草案（待评审）→ 已接受 → 已实施（附验收证据）→ 已取代（写明被谁取代）。
7. **同一事实只在一处维护。** 决策在 PRD-01 §9，功能需求在功能需求文件，功能的实现组合在功能设计（DES-09 起），非功能需求在 REQ-02，术语在 REQ-04，状态在 REQ-03 §6，表结构在 DES-02，接口签名在 DES-03；其他文档链接过去。

## 编号规则

**文件名**：`NN-中文主题.md`，每个目录内部从 `01` 开始连续编号；编号一经分配不复用，被取代的文档保留原编号并标注“已取代”。

**文档编号**：跨文档引用时写“目录代号-编号”，避免不同目录的 `01` 混淆。

| 代号 | 目录 | 内容 |
| --- | --- | --- |
| PRD | `prd/` | 产品需求（PRD、竞品调研） |
| REQ | `requirement/` | 需求规格：01 总表、02 非功能、03 流程与用例、04 术语、05 界面；06 起为功能文件（一个功能一个文件，编号按创建顺序、不复用；34 为 V2 需求池） |
| DES | `design/` | 设计：01–08 为全局设计（架构、数据、接口、工作流、Agent、画布、安全、选型）；09 起为功能设计，与功能需求文件一一对应（编号按创建顺序、不复用） |
| PLN | `plan/` | 计划（实施路线、项目管理与变更） |
| TST | `test/` | 测试（策略、追踪矩阵、AI 评测） |
| OPS | `operation/` | 运维（环境、CI/CD、监控、备份与故障响应） |
| — | `acceptance/` | 验收记录：`M<里程碑>-验收记录.md`（实施开始后创建） |

**条目编号**（引用时写“文档编号 + 条目号”，如 `REQ-28 VID-04`；需求编号本身全局唯一，也可单独引用）：

| 条目 | 格式 | 维护位置 |
| --- | --- | --- |
| 产品决策 | `P<n>` | PRD-01 §9 |
| 功能需求 | `模块-两位序号`，如 `VID-04` | 功能文件；总表 REQ-01 |
| 非功能需求 | `类别-两位序号`，如 `PERF-03`、`CMP-01` | REQ-02 |
| 用例 | `UC-两位序号` | REQ-03 |
| 业务规则 | `BR-两位序号` | REQ-03 §7 |
| 测试用例 | `TC-<功能文件号>-<序号>`，如 `TC-21-03` | TST-02 |

需求被删除时保留空号并注明“已删除”，不把后面的编号前移。

## 与根目录文件的关系

- `AGENTS.md`：协作与 Git 规则，长期有效。
- `BACKLOG.md`：项目进度与待执行任务清单（P0、M1～M5 的基础任务与功能 Epic），由本目录的需求与设计拆解而来，维护规则见 PLN-02 §3。
- `PROJECT.md`：工程规范（目录、技术栈、质量门禁），与设计文档一同评审。
- `README.md`、`agent/README.md`、`frontend/README.md`：按新设计重写；旧实现说明通过 `git show c99a5528:<路径>` 查看。
- `DESIGN.md`：视觉规范，保留沿用；界面与交互需求见 REQ-05。
- 新设计与旧代码的主要差异见 [DES-08 第 11 节](design/08-技术选型决策.md#11-与旧实现的差异)。
