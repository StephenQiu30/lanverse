# NFR-001 跨模块非功能质量需求规格说明书

## 1. 目的与适用范围

本规格定义全部功能模块共同遵守的可用性、性能、可靠性、安全、隐私、可追溯性、可运维性、兼容性和可退出性要求。

本规格不指定数据库、消息系统、云平台或具体技术实现。所有数值均为首发评审基线，在文档进入 `accepted` 前须以真实工作负载和样片验证。

## 2. 服务等级与性能

| 编号 | 规范性需求 | 优先级 |
| --- | --- | --- |
| NFR-001-001 | 系统应使账户、项目、生产控制、审核、成本和交付等核心控制面月度可用性不低于 99.9%，经批准的计划维护除外。 | P0 |
| NFR-001-002 | 系统应在基线负载下使不触发媒体处理或外部 AI 的普通交互请求达到 P95 不高于 2 秒。 | P0 |
| NFR-001-003 | 系统应在基线负载下使异步生产请求达到 P95 不高于 3 秒完成受理并返回可追踪任务标识。 | P0 |
| NFR-001-004 | 系统应在已知外部供应状态后 30 秒内向用户反映相应任务状态，达成率不低于 99%。 | P0 |
| NFR-001-005 | 系统应在首发基线峰值的 3 倍请求量持续 30 分钟时维持受控排队，不丢失已受理任务。 | P0 |
| NFR-001-006 | 系统应对上传、导出和长列表在受理后 2 秒内提供可见状态；除已标明原因、下一次检查时间和取消方式的外部等待外，运行中状态更新间隔不得超过 30 秒。 | P0 |

## 3. 可靠性、恢复与数据一致性

| 编号 | 规范性需求 | 优先级 |
| --- | --- | --- |
| NFR-001-007 | 系统应使平台控制面任务可靠完成率不低于 98%，外部供应商失败应单独统计。 | P0 |
| NFR-001-008 | 系统应保证任务提交、任务回调、额度预占、成本结算和交付创建具备幂等性。 | P0 |
| NFR-001-009 | 系统应保证同一有效计费事件的重复扣费数量为零。 | P0 |
| NFR-001-010 | 系统应使正式业务数据的恢复点目标不超过 5 分钟，恢复时间目标不超过 60 分钟。 | P0 |
| NFR-001-011 | 系统应在单个外部 AI 供应能力故障时隔离影响并保留任务、输入和恢复依据。 | P0 |
| NFR-001-012 | 系统应通过可重复恢复演练验证备份可用性，验证频率不低于每季度一次。 | P0 |
| NFR-001-013 | 系统应在跨模块更新部分失败时保留可判断状态，并支持继续、补偿或人工处置。 | P0 |

### 3.1 NFR-001-001～010 统一测量契约

`基线负载 B` 必须由 QA 与 SRE 在适用 Plan 中冻结请求/任务组合、数据规模、并发用户、唯一请求到达率、媒体规格、供应商桩行为和运行环境；首发无生产数据时使用获产品、架构和 QA 接受的容量假设，产生生产数据后按最近 28 个代表性自然日中 5 分钟峰值窗口的 P95 校准。统计使用服务端权威时间与去重后的逻辑标识；样本不足只能记为 `insufficient/观察`，不得判定通过。

| 编号 | 纳入范围与起止点 | 窗口、样本与负载 | 排除、分母、事实源与通过规则 |
| --- | --- | --- | --- |
| NFR-001-001 | 账户、项目、生产控制、审核、成本和交付公开控制面；每个 1 分钟桶从首个合成探针发出至响应校验结束。 | UTC 自然月；每区域每分钟至少 1 个探针，并以真实请求错误率交叉校验。 | 提前 72 小时批准并公告的维护分钟可排除；客户端 4xx 不计故障，平台 5xx、超时及依赖故障计不可用；分母为符合条件分钟桶，事实源为探针与入口遥测，`可用桶/符合条件桶 ≥ 99.9%` 才通过。 |
| NFR-001-002 | 不触发媒体/外部 AI 的公开普通交互白名单；从入口收到完整请求至最后响应字节。 | 每次发布在 B 下稳定 30 分钟且至少 1,000 个逻辑请求；生产按滚动 24 小时观察。 | 健康检查、静态文件和压测预热排除；幂等网络重放按一个逻辑请求，超时/平台错误按超过阈值计入；事实源为入口 trace，P95≤2 秒且样本达标才通过。 |
| NFR-001-003 | 异步生成、渲染和导出提交；从入口收到完整命令至任务已持久化且响应含可追踪任务标识。 | 每次发布在 B 下稳定 30 分钟且至少 500 个逻辑请求；生产按滚动 24 小时观察。 | 鉴权/校验拒绝排除并单列；同一幂等键的重放按一个逻辑请求，平台超时和错误计入；事实源为入口 trace 与任务库，P95≤3 秒才通过。 |
| NFR-001-004 | 供应商回调或轮询得到的可验证状态变化；从平台接收有效回调或成功轮询时刻至新权威状态可查询。 | UTC 自然日；纳入全部有效状态变化，少于 100 个时为观察。 | 无效签名、重复和已判定过期事件不进分母但须进入去重审计；事实源为回调证据、任务版本和 API trace，`≤30 秒事件数/有效事件数 ≥99%` 才通过。 |
| NFR-001-005 | B 中完整业务组合以 `3 × B` 唯一到达率持续 30 分钟；从命令被受理至形成持久任务/拒绝原因。 | 每次容量基线或关键架构变化执行一次固定 30 分钟测试；至少覆盖 B 定义的全部 P0 类型。 | 预热请求排除；合法限流拒绝单列，已受理任务全部进入分母；事实源为入口、队列和任务库对账，零任务丢失且队列有界、可恢复才通过。 |
| NFR-001-006 | 上传、导出和预计超过 2 秒的长列表；从操作受理至终态，逐次测首状态和相邻状态间隔。 | 每次发布覆盖各类型至少 30 个样本，生产按 UTC 自然月全量观察。 | 用户取消后区间排除并单列；已声明外部等待仅在具有原因、下次检查和取消方式时排除 30 秒间隔；事实源为任务事件与 UI E2E，全部样本满足 2 秒首状态及间隔规则才通过。 |
| NFR-001-007 | 已受理且已到声明截止时间的控制面逻辑任务；从任务持久化至成功终态或平台不可恢复失败。 | 滚动 30 日成熟队列，至少 500 个逻辑任务；发布前故障注入另行验证。 | 用户取消、业务拒绝和确认的外部供应失败不进入平台分母但分别报告；平台重试合并到原逻辑任务，事实源为 Task/Attempt，`成功逻辑任务/平台归因成熟任务 ≥98%` 才通过。 |
| NFR-001-008 | 任务提交/回调、额度预占/结算和交付创建的重复及并发输入；从首次请求至所有重放副作用稳定。 | 每次发布每种操作至少 100 组重复/乱序样本；生产按月审计所有检测到的重放。 | 不排除超时后重试；分母为注入或观察到的重复逻辑操作组，事实源为幂等记录及权威表；100% 返回同一业务结果且只产生一次副作用才通过。 |
| NFR-001-009 | 全部已生效计费事件；从预占至结算、释放、退款或冲正完成。 | UTC 自然月全量，发布前覆盖并发回调和对账导入。 | 无排除；分母为稳定计费事件键去重后的合法事件，事实源为追加账本与余额重算；重复扣费笔数必须为 0，任一例即失败。 |
| NFR-001-010 | PostgreSQL 正式事实、Outbox、审计和对象元数据；RPO 从故障点回溯至最新可恢复提交，RTO 从事故/演练宣布至核心控制面通过一致性校验。 | 每季度至少一次覆盖数据库不可用和区域级恢复的演练，所有场景均计样本。 | 可重建缓存、搜索和分析投影不计 RPO，但须在 RTO 结束前呈现明确重建状态；事实源为备份清单、事务位点和演练记录，全部场景 RPO≤5 分钟且 RTO≤60 分钟才通过。 |

## 4. 安全与租户隔离

| 编号 | 规范性需求 | 优先级 |
| --- | --- | --- |
| NFR-001-014 | 系统应在每次受保护操作中同时校验主体、工作空间、项目、对象和动作。 | P0 |
| NFR-001-015 | 系统应确保不同工作空间的数据在存储、查询、缓存、日志、检索、导出和分析中保持隔离。 | P0 |
| NFR-001-016 | 系统应默认拒绝无法确定归属、权限或策略结果的访问请求。 | P0 |
| NFR-001-017 | 系统应对账户凭据、访问令牌、个人数据、未发布内容和供应商密钥实施与风险相匹配的传输及静态保护。 | P0 |
| NFR-001-018 | 系统应阻止日志、错误信息和用户可见结果暴露凭据、完整令牌或无必要的敏感内容。 | P0 |
| NFR-001-019 | 系统应使高风险操作具备明确授权、二次确认或等效保护，并记录操作审计。 | P0 |
| NFR-001-020 | 系统应使运营临时访问遵循最小权限、明确目的、自动到期和全程留痕。 | P0 |

## 5. 隐私、保留与可审计性

| --- | --- | --- |
| NFR-001-021 | 系统应仅为明确业务目的处理必要的个人数据，并记录处理目的和适用保留策略。 | P0 |
| NFR-001-022 | 系统应支持对个人数据请求执行身份核验、范围识别、导出、删除、保留例外和完成验证。 | P0 |
| NFR-001-023 | 系统应为内容基线、资产版本、任务尝试、审核决定、成本记录、合规结论和正式交付建立端到端追溯链。 | P0 |
| NFR-001-024 | 系统应使安全、权限、费用、合规和交付审计记录在普通业务权限下不可修改或删除。 | P0 |
| NFR-001-025 | 系统应为审计记录保存主体、动作、对象、上下文、结果、时间和关联请求标识。 | P0 |
| NFR-001-026 | 系统应依据数据类别执行可配置保留与删除策略，并记录实际执行结果。 | P0 |

| NFR-001-029 | 系统应为达到配置阈值的关键异常生成可行动告警，并包含影响范围和关联对象。 | P0 |

| NFR-001-040 | 系统应为 180 秒代表性项目的编辑器定义并验证首次可操作时间、播放启动、拖动响应、丢帧、内存峰值和长任务预算。 | P0 |
| NFR-001-041 | 系统应在客户端断线、休眠或事件流重连后，从权威状态恢复且不静默覆盖未保存修改或服务端新版本。 | P0 |
| NFR-001-042 | 系统应在退出登录、切换账户、切换工作空间或权限撤销后清除客户端敏感缓存和媒体访问凭据。 | P0 |
| NFR-001-043 | 系统应按已接受版本矩阵使前后端、事件和运行中工作流在兼容窗口内向前兼容，并为破坏性变更执行有责任人、期限、使用证据、迁移和回滚的弃用流程。 | P0 |

| NFR-001-045 | 系统应使每次生产发布可追溯到源提交、锁定依赖、构建制品、数据库迁移、配置版本和审批记录。 | P0 |
| NFR-001-046 | 系统应在交付前执行依赖漏洞、许可证、密钥泄漏和容器制品检查，并阻止未经接受的严重风险进入生产。 | P0 |

### 8.1 发布兼容契约

| 项目 | 规范性要求 |
| --- | --- |
| 版本矩阵与责任 | Architecture 为矩阵 owner，Backend、Frontend、QA 和 Operations 共同签署；每个发布 Plan/Acceptance 必须冻结后端/API、当前与前一前端制品、事件 schema、Temporal Workflow Build ID、数据库扩展/收缩阶段和浏览器精确版本。缺项不得发布。 |
| 兼容窗口 | 新后端至少兼容当前及前一个生产前端制品、事件 schema 和全部未终结 Workflow；窗口取 30 日或两个完整发布列车中的较长者，并覆盖发布、回滚和 CDN/浏览器缓存旧 HTML/静态资源的最长存活期。 |
| 弃用规则 | 破坏性契约须至少提前 90 日或两个发布列车公告（取较长者），指定迁移 owner；只有旧版本调用量持续一个窗口为零、运行中 Workflow 完成/迁移且回滚演练通过后才可移除。紧急安全停用须有风险批准和兼容替代路径。 |
| 验证门禁 | 每次发布必须执行新旧 API/事件契约测试、Temporal replay、滚动升级/回滚，以及旧客户端加缓存旧资源访问新后端的关键 E2E；任一业务事实不可判断或写入不兼容即失败。 |

## 9. 首发容量基线假设

以下不是已确认需求，而是验证前必须由业务、架构和测试共同确认的容量输入：

| ASM-NFR-003 | 单个媒体文件最大容量、单项目媒体总量及月新增存储量。 |

## 10. 验收要求

- AC-NFR-001：通过负载测试验证普通交互、异步受理和峰值排队指标。
- AC-NFR-002：通过重复请求、重复回调和并发结算测试验证幂等与零重复扣费。
- AC-NFR-003：通过跨工作空间访问、缓存、搜索、导出和日志测试验证租户隔离。
- AC-NFR-004：通过备份恢复演练验证恢复点和恢复时间目标。
- AC-NFR-005：从任一正式交付抽样还原内容、资产、任务、成本、审核和合规追溯链。
- AC-NFR-006：通过媒体样本验证编码、字符、字幕、音画同步和文件完整性要求。
- AC-NFR-007：通过真实用户指标和实验室测试验证普通页面及代表性编辑器性能，记录设备、网络、浏览器和数据规模。
- AC-NFR-008：通过断线、旧前端制品、新旧 API、滚动发布和迁移回滚测试验证兼容与恢复。
- AC-NFR-009：通过自动扫描、全键盘操作和至少一种屏幕阅读器人工测试验证核心流程无障碍。
