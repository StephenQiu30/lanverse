# TCR-001 平台技术栈与总体架构约束需求规格说明书

## 1. 目的与边界

本规格把首发平台必须采用的技术族、架构风格和治理规则固定为可评审的技术约束。其目的不是定义页面、接口字段、数据库表或云资源拓扑；这些实现细节必须在 Design 阶段形成设计文档和 ADR。

当前前后端仓库均无可运行应用或既有技术栈，以下内容是新系统的首发技术基线，不代表对历史试验代码的继承。

## 2. 架构决策摘要

| 决策项 | 首发基线 | 本阶段不固定的内容 |
| --- | --- | --- |
| 总体形态 | API-first 的 Web 平台；业务控制面采用模块化单体，耗时任务采用独立 Worker | 云厂商、区域拓扑、容器编排产品 |
| 主开发语言 | TypeScript 严格模式 | 补丁版本和代码目录细节 |
| JavaScript 运行时 | Node.js 24 LTS；后续仅升级到官方支持的 LTS | 运行时镜像补丁版本 |
| 包管理与锁定 | pnpm；前后端各自提交锁文件并执行冻结安装 | 工作区拆分方式 |
| Web 前端 | React、Next.js App Router、Tailwind CSS、shadcn/ui | 页面结构、组件清单和视觉方案 |
| 前端数据与表单 | TanStack Query、Zustand、React Hook Form、Zod | Store 数量和 Query Key 结构 |
| 后端控制面 | NestJS、Prisma ORM、PostgreSQL | 模块内部类、表、索引和 SQL 细节 |
| API 契约 | REST/JSON、OpenAPI 3.1；任务进度使用 SSE | URL、字段和分组设计 |
| 身份认证 | OpenID Connect；授权码流程与 PKCE；浏览器使用安全会话 | 身份提供商产品和企业单点登录范围 |
| 长任务编排 | Temporal Workflow 与 Worker | Workflow/Activity 的具体拆分 |
| 领域事件 | PostgreSQL 事务发件箱与受控投递；首发不引入 Kafka/RabbitMQ | 达到独立吞吐或隔离门槛后的消息产品 |
| 缓存与临时协调 | Redis；不得作为正式业务事实唯一来源 | Key 结构、分片和托管产品 |
| 媒体存储 | S3 兼容对象存储；授权直传、分片上传和校验 | Bucket、生命周期和 CDN 产品 |
| 媒体处理 | FFmpeg、ffprobe；正式渲染在服务端 Worker 完成 | 编码参数和资源规格 |
| AI 接入 | 供应能力适配器；业务域不得直接绑定厂商 SDK | 首发供应商、模型和路由算法 |
| 可观测性 | OpenTelemetry 统一关联日志、指标和追踪 | 可观测性后端产品 |
| 测试 | Vitest、Testing Library、Playwright；后端增加集成与契约测试 | 用例目录和覆盖率工具 |
| 交付运行 | OCI 容器、GitHub Actions、基础设施即代码 | Kubernetes、Serverless 或具体 IaC 产品 |

## 3. 总体架构约束

| 编号 | 规范性约束 | 验证方式 |
| --- | --- | --- |
| TCR-001-001 | 实现方案必须以 [SRS-001](SRS-001-AI短剧制作平台总体需求规格说明书.md)、FR、[NFR-001](NFR-001-跨模块非功能质量需求规格说明书.md) 和本组 TCR 为共同基线。 | 需求追踪评审 |
| TCR-001-002 | 首发业务控制面必须采用模块化单体，模块以业务事实所有权划分；未经容量或故障隔离证据不得拆分为微服务。 | 架构评审、ADR |
| TCR-001-003 | API 进程、工作流 Worker、AI 适配 Worker 和媒体 Worker 必须能够独立部署与扩缩容。 | 部署设计、伸缩测试 |
| TCR-001-004 | 正式业务事实必须由平台控制的数据存储维护，外部 AI 供应商、浏览器缓存、Redis 和任务引擎不得成为唯一事实源。 | 数据所有权评审 |
| TCR-001-005 | 业务域之间必须通过公开应用契约协作，禁止跨域直接修改他域所有的表、对象或内部状态。 | 依赖扫描、设计评审 |
| TCR-001-006 | 高耗时、可重试或依赖外部供应商的操作必须异步执行，并具备持久状态、幂等、超时、取消和人工恢复能力。 | 故障与恢复测试 |
| TCR-001-007 | AI 供应能力必须通过统一适配层接入；供应商 SDK、密钥、回调和错误语义不得泄漏到业务域或浏览器。 | 代码与安全评审 |
| TCR-001-008 | 原始媒体、代理、候选和母版必须使用对象存储及稳定媒体标识传递，禁止把大体积二进制写入业务数据库或工作流事件历史。 | 数据与工作流评审 |
| TCR-001-009 | 所有运行单元必须使用统一关联标识输出日志、指标和追踪，并能贯穿请求、任务、供应调用、用量和结果。 | 可观测性验收 |
| TCR-001-010 | 浏览器不得持有供应商密钥、长期访问令牌或正式业务事实的唯一副本。 | 构建制品与安全测试 |
| TCR-001-011 | 正式渲染、转码、混音、质检和交付包生成必须在服务端可重复执行，浏览器预览不得改变交付结果。 | 跨设备一致性测试 |
| TCR-001-012 | 所有环境必须由版本化配置和自动化流程重建，生产变更必须可追溯到提交、构建制品和审批记录。 | 发布审计、恢复演练 |

## 4. 语言与运行时边界

| 编号 | 规范性约束 | 优先级 |
| --- | --- | --- |
| TCR-001-013 | 前端、BFF、后端控制面和默认 Worker 必须使用 TypeScript 严格模式，禁止在未说明原因时关闭类型安全检查。 | P0 |
| TCR-001-014 | 生产 Node.js 必须处于官方 Active LTS 或 Maintenance LTS；首发基线为 Node.js 24 LTS。 | P0 |
| TCR-001-015 | Python 仅可用于必须依赖 Python 生态的自托管推理或媒体算法 Worker，并必须通过版本化契约接入，不得直接拥有业务数据库事实。 | P0 |
| TCR-001-016 | 前后端必须独立构建、测试和发布，同时通过同一 OpenAPI 契约及兼容性门禁协同演进。 | P0 |

## 5. 数据与基础设施边界

| 编号 | 规范性约束 | 优先级 |
| --- | --- | --- |
| TCR-001-017 | PostgreSQL 必须作为账户、项目、内容、版本、任务索引、审核、成本、合规和交付记录的权威关系数据存储。 | P0 |
| TCR-001-018 | Redis 仅可用于缓存、限流、短期锁、会话辅助和易失协调；缓存丢失不得导致正式业务事实或已受理任务丢失。 | P0 |
| TCR-001-019 | Temporal 必须管理跨分钟、跨小时或含人工等待的持久工作流；业务数据库仍负责对用户可查询的任务事实和最终业务决定。 | P0 |
| TCR-001-020 | 媒体文件必须存于 S3 兼容对象存储，并具备校验和、来源、版本、保留状态和授权访问记录。 | P0 |
| TCR-001-021 | 部署设计必须把无状态控制面、CPU 密集媒体处理、外部 AI 等待和可选 GPU 推理划分为不同资源池。 | P0 |
| TCR-001-022 | 精确云服务、区域、网络和伸缩参数必须通过容量、数据驻留、恢复目标和成本测算后在 Design 中确定。 | P0 |

## 6. 版本、许可与变更治理

| 编号 | 规范性约束 | 优先级 |
| --- | --- | --- |
| TCR-001-023 | 直接依赖必须锁定可复现版本，自动升级不得绕过类型、测试、安全和契约门禁。 | P0 |
| TCR-001-024 | 运行时、框架、数据库和工作流引擎必须使用仍受官方支持的版本，并在停止支持前完成升级或形成接受风险。 | P0 |
| TCR-001-025 | 引入依赖、模型、编解码器和字体前必须记录许可证、商用范围、安全状态、维护状态和退出路径。 | P0 |
| TCR-001-026 | 替换本规格中的技术族、改变事实所有权、跨服务事务或部署边界，必须建立 ADR，包含候选比较、迁移、回滚、成本和验证证据。 | P0 |
| TCR-001-027 | 仅补丁升级且不改变公开契约、数据格式和运行边界时，可按常规依赖升级流程处理。 | P1 |

## 7. 验收标准

- AC-TCR-001：架构规格逐项映射本文件的 27 条技术约束，并对任何例外给出 ADR。
- AC-TCR-002：概念验证证明 API、Worker、PostgreSQL、Redis、Temporal、对象存储和可观测性链路能够共同完成一个镜头的生成、恢复和追溯闭环。
- AC-TCR-003：冻结安装、类型检查、单元测试、契约测试、构建和端到端测试可在干净环境重复执行。
- AC-TCR-004：依赖与容器扫描不存在未经接受的严重安全问题或许可证冲突。
