# REQ-009 生产模块需求

- 状态：待确认
- 输入：`001-平台总体需求概述.md`、`004-媒体模块需求.md`、`005-审核治理模块需求.md`、`007-资产模块需求.md`、`008-分镜模块需求.md`
- 输出：模型能力、生成请求、任务恢复、候选选择和成本需求
- 下游：REQ-010

## 1. 需求概述

生产模块必须把固定 ShotSpecVersion 转换为可追踪的图片、视频、语音和音效候选。所有长任务以服务端 Task 为事实源，支持幂等提交、取消、恢复、供应商对账、候选择优和成本解释。

用户提交的是业务生成命令，不是任意供应商请求。供应商协议、状态和参数必须通过 ModelCapability 与适配器转换，不能渗透到分镜和前端业务模型。

## 2. 业务实体需求

| 编号 | 实体 | 需求 |
| --- | --- | --- |
| PROD-ENT-001 | ModelCapability | 必须描述能力类别、输入类型、参数范围、限制、计费单位和当前可用状态。 |
| PROD-ENT-002 | GenerationRequest | 必须不可变，保存 ShotSpecVersion、资产版本、能力/模型、参数快照、input hash、幂等键和请求人。 |
| PROD-ENT-003 | Task | 必须表示一次业务工作，保存主状态、进度摘要、阻塞/错误、下一动作和关联请求。 |
| PROD-ENT-004 | Attempt | 必须表示一次实际执行尝试，保存 provider_request_key、供应商任务 ID、状态、时间和错误/对账信息。 |
| PROD-ENT-005 | Candidate | 必须保存生成输出 MediaVersion、来源 Attempt、质量/用户标记和是否被选用；输出不可覆盖。 |
| PROD-ENT-006 | Reservation/CostEntry | 必须表达费用预占、结算、释放或调整，关联 GenerationRequest/Attempt 和供应商账单信息。 |

Task 不等同 RabbitMQ 消息，Attempt 不等同客户端轮询；消息可以重复，业务事实必须唯一且可恢复。

## 3. 功能性需求

| 编号 | 需求 |
| --- | --- |
| PROD-FR-001 | 用户必须能查询当前可用的文本、图像、视频、语音和音效能力及真实参数限制。 |
| PROD-FR-002 | 提交前系统必须预检 ShotSpecVersion、资产授权、媒体、模型参数和可用额度，并返回预计消耗。 |
| PROD-FR-003 | editor/owner 必须能为单 Shot 或选定 Shot 集合提交生成；高成本操作必须经过明确确认。 |
| PROD-FR-004 | 创建生成请求时必须同事务保存 GenerationRequest、Task、费用预占和待投递事实，并快速返回 Task。 |
| PROD-FR-005 | 用户必须能在任务中心按项目、Episode、Shot、类型和状态查询 Task、进度、错误和下一动作。 |
| PROD-FR-006 | 用户必须能请求取消可取消 Task；系统必须区分已接受取消、无法取消和结果已完成。 |
| PROD-FR-007 | 对失败或未知 Task，系统必须先判断是否已被供应商受理；仅在安全条件下重试或创建新 Attempt。 |
| PROD-FR-008 | 用户必须能查看、对比、标记和选择 Candidate；选择必须验证当前 ShotSpecVersion 未过期。 |
| PROD-FR-009 | 单镜头失败不得使同批其他镜头失去可用结果；批量操作是可独立恢复 Task 的集合。 |
| PROD-FR-010 | 用户必须能查看预计、预占、结算和释放的逐任务成本；失败/取消后未使用金额必须释放。 |

## 5. 任务状态与业务语义

Task 主状态：`queued → running → waiting_provider → succeeded | failed | cancelled | unknown`。

- `failed`：已确认本次尝试失败且没有成功副作用，可按规则决定重试。
- `unknown`：无法确认供应商是否受理或完成，必须查询/对账或人工处理，禁止盲目重发。
- `cancelled`：业务不再等待结果；若供应商最终仍返回结果和费用，必须记录而不能伪装不存在。
- 进度只表示可验证阶段，不得伪造连续百分比；下一动作必须来自服务端规则。

## 6. 非功能性需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| PROD-NFR-001 | 幂等 | 稳定幂等键和 provider_request_key 必须防止刷新、超时、重复消息和重复回调产生双重外部副作用。 |
| PROD-NFR-002 | 可靠性 | 数据库事实与待投递事件必须原子保存；消息至少一次投递时消费者按 Task/Attempt 幂等。 |
| PROD-NFR-003 | 恢复 | API/Worker 重启后必须从持久化事实继续；客户端本地状态不能决定是否重发。 |
| PROD-NFR-004 | 成本一致性 | 终态必须满足有效结算与释放可解释地覆盖预占，任何调整保留追加记录。 |
| PROD-NFR-005 | 隔离 | 不同 Workspace 的任务、候选、成本和供应商上下文不得互相可见或引用。 |
| PROD-NFR-006 | 资源控制 | 在途 I/O 与媒体任务必须有界，单用户/Workspace 并发和全局容量在 PRD 量化。 |
| PROD-NFR-007 | 可观测 | Task、Attempt、消息、provider_request_key、MediaVersion、费用和 trace 必须关联查询。 |
| PROD-NFR-008 | 性能 | 提交接口不得等待生成完成；任务状态可见时限、对账时限和失败收敛目标在 PRD 量化。 |
| PROD-NFR-009 | 安全 | 供应商密钥和原始敏感响应不得返回前端或进入普通日志；提示与参考输入遵守 Workspace 权限。 |

## 7. 失败路径与成本规则

- 预检失败不创建费用预占和供应商副作用。
- 发布消息失败保留未发布事实并可重放，不创建第二 GenerationRequest。
- Worker 在写入 Candidate/Media/费用和 Task 结果后才确认消息；重复投递读取既有结果。
- 供应商返回成功但媒体下载失败时保留 Attempt 与供应商结果，安全重试下载而非重新生成。
- Candidate 选择不删除其他候选；取消选择或重选保留历史并通知 editing 当前生产版本变化。

## 8. 非目标与待确认

- 不实现通用低代码工作流、Temporal、第二消息系统、自托管 GPU 调度或模型训练平台。
- 不允许前端直接调用供应商、自由构造未知参数、修改 Task 终态或计算余额。
- 待确认默认供应商、模型参数、计费精度、单镜头候选数、并发限制、取消能力、对账周期和人工处理流程。
