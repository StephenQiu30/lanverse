# Requirement

本目录是 Lanverse AI 短剧生成平台的统一需求分析入口。需求不按前端、后端或模型拆分，而围绕用户完成短剧生产时承担的业务责任组织。

当前目录表达的是现阶段对业务模块的认识，不是永久固定的文件结构。随着访谈、样片和运营证据增加，模块可以合并、拆分、重命名或调整边界。

## 需求层级

1. **L0 总体需求**：说明平台定位、服务范围、主流程、模块地图和模块间业务交接。
2. **L1 模块需求**：按模块自身特点定义完整功能、业务规则、权限和协作关系。
3. **L2 跨模块约束**：定义性能、可靠性、安全、数据、集成、成本等共同要求。

层级用于保持从整体到局部的推导关系，不要求所有文档使用相同章节。

## 编写原则

1. 从用户任务和业务结果出发，不按页面、接口、微服务、模型或供应商组织需求。
2. 不设统一正文模板。权限模块可以使用角色矩阵，资产模块可以使用分类与生命周期，制作模块可以使用任务流，交付模块可以使用审核门禁。
3. 一个关键业务事实只能有一个归属模块；其他模块只能引用，不能建立另一套结论。
4. 模块之间先定义业务输入、责任和结果，后续 Design 再决定接口、事件或数据交换方式。
5. 功能是否进入 MVP 取决于是否阻断主流程、是否显著影响作品质量与返工、是否存在可接受的人工替代，以及是否有真实证据。
6. 明确区分观察事实、待验证假设和产品判断，避免把竞品功能或实现方式直接写成平台需求。

## 功能定义的完整性

模块可以自由选择表达方式，但核心功能应能被评审者回答清楚：

- 为谁解决什么问题，何时触发。
- 需要哪些业务输入或前置条件。
- 平台承担什么业务行为，用户得到什么结果。
- 结果和关键状态由哪个模块负责维护。
- 会向哪些模块提供信息，又依赖哪些模块。
- 哪些角色可以执行，受哪些成本、权利或安全规则约束。
- 属于 MVP、后续候选还是非目标，依据和待验证点是什么。

这些内容不必机械地成为八个章节，也不要求每个小功能单独建立文件。

## 适合不同模块的表达方式

| 模块特征 | 更适合的需求表达 |
| --- | --- |
| 用户与权限 | 身份关系、成员生命周期、角色与操作矩阵、敏感权限规则 |
| 项目与内容 | 内容层级、创作流程、内容基线、变更影响与完成条件 |
| 创作资产 | 资产分类、版本与引用、来源权利、复用和变更影响 |
| AI 制作 | 制作准备、任务与尝试、候选、进度、批量操作和失败恢复 |
| 审核与交付 | 审核轮次、决定、返工、采用、单集组成与交付门禁 |
| 平台保障 | 额度用量、预算、权利、安全、AI 标识和运营处置规则 |
| 跨模块约束 | 可测量目标、约束编号、异常原则和技术方案评价证据 |

## 需求与设计边界

需求阶段可以定义业务对象、功能、业务状态、规则、权限、业务输入输出和质量目标，但不决定：

- 前端页面、组件、交互和视觉方案。
- 后端服务、接口、数据表、消息或状态机实现。
- 编程语言、框架、数据库、队列、云厂商和模型供应商。
- 工作流节点、提示词、模型参数、部署拓扑和研发计划。

技术栈选择应在需求达到 `accepted` 后进入 Design，并以[跨模块非功能与技术约束需求](008-跨模块非功能与技术约束需求分析.md)为评价输入。

## 文档状态

- `draft`：仍在分析，边界或优先级可能变化。
- `review`：功能和边界已形成一致结论，等待业务确认。
- `accepted`：可作为 Design 和 PRD 的正式输入。
- `archived`：已被新结论取代，仅保留历史依据。

## 演进规则

- 发现模块职责重叠或缺失时，先更新总体模块地图和唯一事实归属，再调整模块文件。
- 功能增长不等于必须拆文件；只有出现独立业务责任、不同生命周期或不同评审人时才拆分。
- Front matter 的 `inputs` 与 `downstream` 表示无环的文档推导顺序；运行中的模块协作可以双向，在正文中定义。
- 当前只维护 Requirement；顺序为 `Requirement accepted → Design → PRD → Plan → Acceptance`。
