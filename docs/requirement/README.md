## 1. 本目录的效力

旧编号需求、arrived 历史需求、旧能力基线和旧需求工程总纲已经移除，不再归档。它们基于历史代码、旧 MVP 或剪辑成片范围，不得继续参与当前产品评审、模块划分或工期估算。

本目录是当前核心产品唯一的需求事实源，用于答复“用户要完成什么、系统必须满足什么、如何验收”。需求按业务模块分文档管理，不再把所有当前需求堆入一份总文档，也不再增加 `current/` 等状态型目录层级。

全部需求从用户价值流重新建立，不继承历史代码、旧需求状态或旧 Acceptance 结论。现有实现只在需求接受后的迁移 Design 中评估复用、替换和兼容成本，不能成为产品需求来源。

## 3. 模块需求的强制结构

每份模块需求必须包含：

1. 文档元数据、模块定位、价值和可量化目标；
2. 范围、非范围、前置依赖和下游交接；
3. 角色、权限、用户场景和用户语言；
4. 全量 FR 清单，且每条 FR 有稳定全局 ID；
5. 逐 FR 的前置条件、主流程、备选流程、失败流程、业务规则、输入、输出和 UI/交互要求；
6. 领域概念、关系、状态机和不变式；
7. 用户可观察的接口、事件或文件交接需求；
8. 可测量 NFR、异常分类、恢复和数据、权限、合规约束；
9. 与 FR 直接关联的 Given/When/Then 验收条件；
10. 开放问题、已决策事项、术语和变更历史。

文档不得用数据库表、代码目录、技术框架或某个供应商实现代替需求分析。这些选择只能出现在下游 Design/ADR。

## 4. 编号与追踪

- 功能需求：CUR-MODULE-FR-###；
- 用户场景：CUR-MODULE-US-###；
- 领域概念：CUR-MODULE-ENT-###；
- 交接需求：CUR-MODULE-IF-###；
- 非功能需求：CUR-MODULE-NFR-###；
- 验收条件：AC-CUR-MODULE-###，同一 FR 需要多个场景时可追加稳定 `-A/-B/...` 后缀；
- 开放问题：CUR-MODULE-OQ-###。

文件序号表示推荐评审顺序，稳定模块 ID 表示需求身份。重新排序文件时不得改变已被下游引用的需求 ID。

下游必须建立 `Requirement（含 AC）→ Design → Test → Acceptance Evidence → Release` 追踪。AC 是实现前的验收条件；Acceptance Evidence 是实现后执行真实验证产生的证据，两者不得混用。一个需求只有在成功、失败、边界、权限和恢复证据均完成后才能进入 verified。

## 5. 双轨状态

需求生命周期与交付状态必须分开：

| 维度 | 合法状态 |
| --- | --- |
| 需求 | `proposed → in_review → accepted → changed | deprecated` |
| 交付 | `not_started → planned → in_progress → verified → released | replaced` |

accepted 只表示需求已被产品评审，不表示已实现；verified 必须有真实验收证据，不能由文档自证。

## 6. 当前硬边界

当前不建设 Timeline、多轨剪辑、镜头裁切或拼接、转场、调色、字幕或音频后期、整集渲染、单一成片 MP4、发布分发、匿名公开分享、套餐支付、账单和营销运营。CUR-CAN 以及其可视化画布不进入当前 MVP；后续若实施，必须是同一领域事实的生产视图，不是 Timeline、任意技术节点编排器或第二套工作流事实源。

“内部成本可见”只用于创作者在生成前做决策、在失败后理解消耗，不等于商业计费、支付或财务对账模块。

## 7. 进入下游的门禁

只有模块的范围、非范围、FR、失败路径、NFR、AC 和开放问题均完成评审后，才能生成对应 Design，并拆分 Plan 与开发周期；实现完成并执行真实验证后，才能新增 Acceptance。

新模块化分析继续产生的 Design、Plan、周期表与验收设计必须保留，并在索引中按新序号登记；清理只针对无法回链 CUR ID 的历史内容。
