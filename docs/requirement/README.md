## 1. 文档粒度规则

Requirement 按“一个权威功能模块一份详细需求”组织。M01—M15 每个模块只有一份当前 Requirement；一个文件不得同时拥有两个模块的业务规则，跨模块流程通过上游/下游链接和稳定 Requirement ID 表达。

模块是一组拥有同一业务事实和规则的功能，不等于微服务、进程或代码目录。模块内子功能继续使用稳定 `FR/NFR/AC` ID，不为每个按钮或字段拆成孤立文件。

## 3. 推荐评审顺序

先阅读架构、领域数据和产品模块，再评审全局 Requirement。详细 Requirement 按真实生产依赖分组评审：

1. 基础边界：M01、M02；
2. 内容与知识：M03、M04；
3. 生产规划：M05、M06、M07；
4. 外部执行与结果：M08、M09、M11；
5. 质量与闭环：M10、M12、M13；
6. 横切治理与扩展：M14、M15。

该顺序表示依赖和评审先后，不表示建设十五个服务，也不取代纵向切片 A—F。

## 5. 需求与设计边界

Requirement 定义用户结果、范围、业务规则、失败、权限、恢复、非功能要求和验收，不指定 FastAPI、PostgreSQL、RabbitMQ、LangGraph、表名、队列或代码目录。Design 决定实现；若 Design 暴露新的用户风险，必须先补充对应 Requirement 和验收。

详细 Design 可以跨模块解释一个纵向流程，但必须分别链接每个模块的 Requirement，不得借跨模块 Design 重新合并需求所有权。

## 6. 文档边界

本目录只保存当前有效 Requirement。外部研究、评审意见和历史版本不建立独立项目目录；其中被接受的结论必须进入对应 Requirement 或 Design，未进入当前事实源的内容不参与实现或验收。

## 7. 状态与变更流程

- `proposed`：内容尚在编写或存在未闭合审计问题；
- `reviewed / ready_for_design`：专业审计已完成，内部冲突已修正，可以形成 Design/PRD/Plan，但尚不代表产品负责人签认；
- `accepted`：业务、设计和验收责任人已经评审通过；
- `verified`：真实执行证据满足全部强制验收；
- 文档、Mock、字段或代码存在不能证明 verified。

变更顺序为：Requirement → 影响评审 → Design/接口/数据 → Plan/Test → Acceptance Evidence。任何模块进入实施前，必须签认其 P0 范围、失败恢复、权限、并发、指标口径和待确认项。

## 8. 优先级与切片 Gate

- `P0` 表示该能力是对应验收切片的强制范围；不满足时不能把该切片或模块声明为 verified。
- `P1` 表示目标系统需要但不阻断当前对应切片的后续能力；PRD 可以经评审把具体 P1 提升为某一切片 P0，但不能静默降级 P0。
- P0 不等于“全部在切片 A 建设”。每条需求按模块表和 A—F PRD 的最早切片进入验收，例如 M13 正式装配属于 E、M15 属于 F。
- 依赖 Provider、输出预设、外部审片、企业身份或未签认产品配置的能力必须同时满足对应 Gate；Gate 未签认时保留为目标 P0，但不得进入当前切片完成声明。
- Fixture、Mock 和关闭的 feature flag 只能验证契约或降级路径，不能证明真实 Provider、外部通知、企业身份或正式交付能力已通过。
