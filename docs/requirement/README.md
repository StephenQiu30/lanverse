# Requirement

本目录是 Lanverse AI 短剧生成平台的统一需求分析入口，保存进入产品设计和技术设计之前形成的研究、判断与需求基线。

需求不按 `frontend` 和 `backend` 拆分。平台先形成一份共同的业务与产品需求，再由后续设计分别回答如何实现。

## 当前阶段

当前处于需求发现阶段，重点回答：

1. 平台服务谁，以及用户需要完成什么工作。
2. 平台覆盖从内容输入到短剧交付的哪些环节。
3. 用户使用平台时的主要生产流程是什么。
4. 平台应具备哪些顶层功能域。
5. MVP 需要验证哪些核心价值和风险。

## 文档边界

本目录可以包含：

- 市场、竞品、开源项目和用户工作流观察。
- 平台定位、目标用户、核心问题和服务边界。
- 顶层业务对象、主要工作流程和功能域。
- MVP 候选范围、优先级依据和待验证假设。
- 需求调研记录、结论变化和决策依据。

本目录不包含：

- 前端页面、组件、交互和视觉设计。
- 后端服务拆分、接口、数据表和状态机设计。
- 模型选型、工作流节点、提示词和参数配置。
- 部署、运维、研发计划和代码实现。
- 未经验证却被当作既定需求的功能清单。

## 文档状态

- `draft`：正在观察和分析，结论尚未确认。
- `review`：已形成明确判断，等待业务或产品确认。
- `accepted`：需求边界已确认，可以作为后续 Design 和 PRD 的输入。
- `archived`：已被新结论替代，仅保留研究历史。

需求文档应区分三种信息：

- **观察事实**：来自用户、公开产品、样片实验或可信资料。
- **待验证假设**：目前合理，但仍需访谈或任务验证。
- **产品判断**：基于事实作出的范围或优先级建议。

## 与现有文档的关系

当前 `lanverse-frontend/docs/design/` 和 `lanverse-backend/docs/design/` 中的 AI 短剧文档均为早期未采纳草案，不能反向定义本目录中的需求。

正确顺序是：

`Requirement accepted → Design → PRD → Plan → Acceptance`

只有需求被确认后，才进入前后端仓库的正式设计流程。
