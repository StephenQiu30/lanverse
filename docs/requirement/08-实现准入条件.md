# 实现准入条件

## 1. 结论格式

每次门禁记录必须保存为 Git 跟踪的 `docs/gates/GATE-<gate_scope>-<UTC时间>.yaml`，格式与责任见 [`docs/gates/README.md`](../gates/README.md)。记录必须包含 `gate_scope/result/input_versions/owner/reviewers/decided_at/gaps/evidence/next_stage`；Owner 在评审完成后创建，Reporter 复核输入提交并提交记录，列名 Reviewer 通过 PR/提交审阅确认。`result` 只允许：

- `passed`：全部适用 P0 已满足，可以进入下一阶段。
- `conditional`：不涉及安全、数据完整性或重复付费风险，且每个缺口都有 owner、日期、影响和关闭证据。
- `failed`：不得进入下一阶段。

## 2. Requirement readiness

`gate_scope: requirement_readiness` 通过条件：

1. REQ-01～REQ-08 均为 `accepted`。
2. 单操作者本地边界、输入/镜头/时长/媒体基线与活动编号契约一致，且没有未编号能力混入下游。
3. 文本、图片、视频、TTS 的真实 Provider 决策字段、凭据责任人、测试额度和 T-011 前关闭点已明确；Requirement 接受不等于批准真实调用。
4. 每条 P0 都有唯一 ID、可观察结果和下游 Design 位置。

## 3. Design entry

`gate_scope: design_entry` 通过条件：

1. DESIGN-01～DESIGN-06 均为 `accepted`。
2. 六模块事实所有权、两个后端入口、目录、数据、HTTP、Task/Attempt、OutboxEvent/Temporal、Provider、媒体和失败恢复没有冲突。
3. OpenAPI 设计样例覆盖异步受理、Task 查询、幂等冲突、版本冲突和安全错误；DESIGN-06 为每个机器可读契约定义唯一 Test ID 与证据位置。
4. 固定六镜头夹具覆盖重复请求、部分失败、Worker 重启、Provider unknown、TTS 失败和渲染失败。
5. 每个 Design AC 能追踪到 Requirement、PRD、Plan、Test 和 Evidence。

## 4. Implementation start

`gate_scope: implementation_start` 通过条件：

1. 适用 Requirement、Design、PRODUCT-01 和 PLAN-01 全部为 `accepted`，版本与 DESIGN-06 一致。
2. PLAN-01 已明确技术族、资源上限、FFmpeg 规格、T-001 精确版本引导步骤，以及真实 Provider 决策与凭据的最迟阻断点；不存在阻断 T-001 的未决 P0。
3. 每项任务都有预期 Red、最小 Green、目标路径、命令、Test ID、Evidence ID、迁移和回滚；T-001 在创建应用源码前提交精确依赖、唯一 lockfile 与不可变镜像 digest。
4. 真实 Provider/模型、保留边界和额度未关闭时只允许执行 T-001～010 的 Mock 路径，必须在 T-011 前失败关闭；未创建 ACCEPTANCE-01。

## 5. Implementation release

`gate_scope: implementation_release` 仅在实现和 ACCEPTANCE-01 完成后执行：

1. Mock 完整 E2E 连续 3 次通过，真实 Provider 完整样片至少 1 次通过。
2. 重复提交、Worker 重启、unknown 对账、局部重试、TTS 和渲染恢复证据通过。
3. ffprobe、SHA-256、Manifest、secret 扫描、类型、lint、测试和构建均通过。
4. 所有 P0 Acceptance 结果为 `passed`；否则不得发布。

## 6. 强制失败条件

- 活动 Requirement 未编号的能力进入目录、API、数据库、依赖或测试范围。
- Task/Attempt、候选采用或 Delivery 缺少唯一事实源。
- 真实 Provider 可能因重复提交产生未受控副作用或重复费用。
- 密钥进入前端、数据库业务载荷、日志或 Workflow 历史。
- Plan 缺少可执行命令、恢复测试或回滚。
- 任一上游仍为 `review/draft` 却开始创建应用目录、依赖、代码或 Acceptance。

## 7. 当前状态

当前 Requirement 为 `review`，下游 Design、PRD 与 Plan 为顺序待审草案，因此 `requirement_readiness`、`design_entry` 和 `implementation_start` 当前均为 `failed`，且 `docs/gates/` 中尚无通过记录。完成逐级评审并把对应输入转为 `accepted` 后，必须生成独立门禁记录再进入下一阶段；不得仅修改状态字段绕过评审。

## 8. 验收标准

- AC-ADG-001：任一门禁结论可由输入版本、检查项和证据复现。
- AC-ADG-002：`conditional` 不用于放行安全、数据完整性、重复费用或缺失上游文档。
- AC-ADG-003：门禁只评审活动 Requirement 中明确编号的契约；未编号能力不得作为实现前置条件或交付对象。
