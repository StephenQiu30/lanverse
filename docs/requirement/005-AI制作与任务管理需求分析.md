# AI 制作与任务管理需求分析

## 1. 制作域的业务责任

本模块承接已经确认的内容和资产，把“需要制作什么”组织为可追踪的生产活动，直到形成可提交审核的候选。它保存以下唯一事实：

- 制作目标、责任、优先级、准备程度和任务关系。
- 每次实际制作使用的输入基线、形成的尝试、候选、失败、取消和部分结果。
- 单项及批量工作的进度、阻塞原因、恢复行动和下一步。
- 局部返工与原问题、影响范围、新尝试之间的关系。
- 任务、尝试及候选与 REQ-007 维护的预计和实际用量记录之间的业务关联。

REQ-003 决定内容基线，REQ-004 决定资产身份、版本和来源，REQ-007 决定额度、计费、权利与安全规则，REQ-006 决定正式审核、采用和交付。本模块消费或关联这些事实，不替代它们作决定。

本文不定义页面、接口、数据表、队列、执行编排、工作流节点、提示词、模型参数、模型或供应商选型；业务进展也不预设技术状态机。

## 2. 一条可追溯的制作链

制作事实应保持“制作目标 → 制作任务 → 输入基线 → 一次或多次制作尝试 → 零个或多个候选”的关系。

审核退回会形成明确返工要求，再回到原任务或受控的新任务；成本和异常始终关联到实际尝试，不悬空记在项目总账上。

| 业务概念 | 需要表达的事实 |
| --- | --- |
| 制作目标 | 为哪个资产或镜头形成什么结果，以及服务哪个内容目的 |
| 制作任务 | 围绕一个清晰目标组织的工作单元，具有责任、优先级、依赖和进展 |
| 输入基线 | 某次尝试实际使用的内容、资产、参考和业务限制版本集合 |
| 制作尝试 | 为任务实际发起的一次生产活动；重试、补做和返工产生新尝试 |
| 候选 | 某次尝试形成、尚待用户判断或提交 REQ-006 审核的结果 |
| 制作问题 | 导致不能开始、无法继续、结果不完整或需要人工处置的情况 |
| 返工要求 | 针对明确候选或审核问题提出的修改目标和范围 |
| 用量引用 | 任务、尝试、结果和异常如何关联 REQ-007 维护的预计、实际、调整与补偿记录 |

## 3. 核心功能地图

| 核心功能 | 触发与输入 | 业务行为和结果 | 依赖或输出 | 阶段 |
| --- | --- | --- | --- | --- |
| 制作准备 | REQ-003 内容目标、REQ-004 资产版本、责任和 REQ-007 限制已知 | 判断可开始或受阻，列出缺失、失效和需人工确认事项，不把阻塞伪装为失败 | 向创作者反馈内容或资产缺口，向 REQ-007 查询限制 | MVP；P1 复用准备规范 |
| 匹配可用制作能力 | 目标结果、媒体要求、输入条件和保障限制明确 | 判断当前是否存在可执行能力，说明不支持项和对质量、时效、成本有意义的差异；MVP 可只有一条默认路径 | 接收 REQ-003/004/007 约束，结果进入制作准备 | MVP 默认能力；P1 多能力选择 |
| 建立单项任务 | 用户确认一个资产或镜头制作目标 | 固化目标、责任、优先级、依赖和预期结果，形成可独立取消与追踪的任务 | 接收 REQ-003/004，向 REQ-006 输出候选上下文 | MVP |
| 基础批量制作 | 多个同类目标都已准备，用户确认批量范围 | 一次组织多个任务，但每项仍保留独立输入、进度、结果、异常和处置 | 向项目和单集汇总进度 | MVP 基础；P1 分组、依赖与动态优先级 |
| 记录输入基线 | 尝试即将开始，或返工准备重新制作 | 记录实际使用版本；上游后来变化只标识影响，不静默替换输入 | 关联 REQ-003 内容、REQ-004 资产和 REQ-007 限制 | MVP；P1 辅助影响判断 |
| 确认并启动制作 | 准备和消费门禁通过，用户确认单项或批量范围 | 固定本次输入基线并形成制作尝试；受理、拒绝、取消和后续重试都指向明确任务与尝试 | REQ-002 判断操作权限，REQ-004 提供版本，REQ-007 确认消费门禁 | MVP |
| 尝试与候选管理 | 任务被执行、重试、补做或收到部分结果 | 每次活动形成独立尝试；候选关联目标、输入、来源、问题和 REQ-007 用量记录，旧结果不被覆盖 | 媒体与来源交给 REQ-004，明确候选提交 REQ-006 | MVP；P1 候选连续性与完整性检查 |
| 进度与阻塞汇总 | 任务或尝试发生变化，用户查看项目生产情况 | 分开展示准备、执行、结果、阻塞和审核关系，并给出下一责任方和行动 | 输出到 REQ-003 项目上下文及运营观察 | MVP；P1 瓶颈和趋势分析 |
| 异常恢复 | 失败、无结果、部分结果、长期无进展、重复或取消后迟到 | 保留已知事实，允许按情况重试、补做、取消、等待或人工补入，不重复计算结果 | REQ-007 处理平台补偿或限制，REQ-004 接收有效媒体 | MVP 常见恢复；P1 批量恢复与策略辅助 |
| 局部返工 | 创作者判断偏差，或 REQ-006 退回明确候选 | 保留原候选和意见，只重做被指出范围，新尝试关联原问题并重新提交 | 输入来自 REQ-006，输出新候选及返工结果 | MVP；P1 跨镜头影响与返工分析 |
| 成本关联 | 启动前需了解预计用量，尝试结束或异常后需解释实际用量 | 向 REQ-007 提供任务、尝试、结果与异常上下文，并关联其用量记录；本模块不维护数值或调整结论 | REQ-007 唯一维护估算、实际、调整和补偿 | MVP 基础关联；P1 预测和结构分析 |

## 4. 制作准备与输入基线

任务可以先建立，但正常启动至少需要：

1. 明确的资产或镜头目标、预期结果和所属项目。
2. 可供生产使用的内容基线，以及实际选择的资产与参考版本。
3. 有权启动的责任人和可判断的任务依赖。
4. 当前存在满足必要结果约束的可用制作能力；不支持或暂不可用时必须显式阻断。
5. 权利、安全、额度或预算没有形成阻断；无法判断时必须显式等待确认。
6. 用户在高成本活动前能够理解预计用量或估算不确定性。

准备结果必须是“可以开始”或带具体原因的“尚不可开始”。原因需要指向内容、资产、权限、权利、安全、额度、预算或人工决定，并说明应由谁处理。自动检查只能辅助，不得代替创作判断或合规例外决定。

输入基线按每次尝试保留。内容、资产或限制后续发生变化时，平台应指出可能受影响的进行中任务和已有候选，由用户决定继续、取消、重做或重新审核；不得自动换入新输入，也不得默认旧候选继续有效。

## 5. 单项、批量、尝试与候选

1. 一个任务围绕一个可判断的资产或镜头结果目标；一个任务可以有多次尝试和多个候选。
2. 批量只是任务的组织方式，不把多个目标合并成无法单独追踪的“大任务”。
3. 批量中的任一项都能单独取消、重试、补做、提交审核和说明关联用量。
4. 每次真实制作、重试、返工或人工补入外部结果，都要形成来源明确的独立尝试。
5. 失败、无结果、部分结果和创作质量不合格是不同事实，不能统一写成“失败”。
6. 候选必须关联任务、尝试、输入基线、结果范围和 REQ-007 用量记录；重新制作不能覆盖旧候选。
7. 取消后到达的结果和重复返回的结果必须单独识别，未经人工判断不得进入正常候选范围。
8. REQ-004 登记候选媒体的资产身份和来源，但候选事实仍由本模块维护。
9. 只有被明确提交的候选进入 REQ-006；审核通过、采用或交付不回写为本模块的候选状态。

## 6. 进度与下一步

制作进展要分别回答五个问题：是否具备开始条件、是否正在生产、是否形成结果、为何不能继续、是否已经进入审核。任何一个“完成”标记都不能同时代表这五类事实。

- 单项任务需要展示当前责任、已知进展、已有候选、问题、关联用量和下一行动。
- 批量需要汇总未开始、进行中、有候选、异常和已取消数量，同时保留进入每个单项事实的能力。
- 项目、单集、场次、镜头和资产均应能汇总与其相关的任务，但同一任务不得被重复计算。
- 长期没有新进展时，应表达“进展未知或需处理”，不能假装仍在正常推进。
- 等待用户、等待上游内容或资产、等待平台处置和正常制作中必须可区分。

## 7. 异常恢复和局部返工

| 情况 | 允许的业务处置 |
| --- | --- |
| 输入缺失、停用或无权访问 | 保持任务受阻，指出对象并返回相应责任模块 |
| 权利、安全、额度或预算不足 | 等待 REQ-007 的解除、调整或人工例外，不作为普通运行失败 |
| 无结果、部分结果或长期无进展 | 保留已有内容，可等待、取消、重试或只补做缺失部分 |
| 重复结果或取消后迟到 | 标明来源和异常关系，由用户决定保留为候选或忽略 |
| 外部完成结果需要补入 | 关联明确任务、输入说明和来源，不能伪装成平台内成功尝试 |
| 创作质量不合格 | 转为候选选择或返工问题，不混入平台故障统计 |

局部返工必须对应原候选、具体意见和修改范围。返工形成新尝试，保留原结果、原用量记录和未受影响内容；若上游基线已变化，应先重新完成准备判断。批量返工仍以单项影响为准，不能因一个镜头问题默认重做整批。

## 8. 成本事实与责任权限

REQ-007 唯一维护预计用量、实际数值、费用调整和补偿结论。本模块只提供任务、尝试、结果及异常上下文，并保存对相应用量记录的引用；批量汇总仍须能够定位到单项任务和尝试。

- 项目创作者可以在获授权范围内创建、启动、取消任务，整理并提交候选。
- 项目审核者可以查看制作上下文并经 REQ-006 提出退回；若要创建任务或整理候选，还需兼任项目创作者。
- 项目负责人、制片、资产管理者和制作成员按 REQ-002 映射到实际项目角色，职责名称本身不增加权限。
- 只读成员只能查看获授权进度；平台运营只能处理明确异常、补偿或限制，不替用户发起制作和选择候选。

## 9. MVP 闭环与 P1 扩展

MVP 通过标准是：用户能从已确认镜头或资产建立单项和基础批量任务；在启动前看见准备问题和 REQ-007 提供的预计用量；明确确认后形成制作尝试；追踪候选、进度、阻塞并关联实际用量；处理失败、取消、部分结果和迟到结果；把明确候选提交审核，并根据意见只返工受影响部分。

P1 扩展多集任务计划、复杂依赖与优先级协调、更丰富的批量处置、变化影响辅助判断、候选连续性检查、瓶颈与返工分析、成本预测和可复用制作规范。

不在本模块建设节点式工作流、开放模型市场、模型训练、专业媒体后期、通用项目管理系统或无需人工判断的全自动成片，也不在需求阶段确定排队、执行、重试、存储和分发方案。

## 10. 进入评审前仍需验证

- 首发任务以资产、镜头还是更小结果为主要粒度。
- 哪些准备条件必须阻止启动，哪些只需提醒。
- 用户需要理解多少次尝试历史，以及多大批量仍能有效处理异常。
- 不同失败、取消、部分结果和外部补入应如何解释消耗。
- 哪些上游变化必须重做或重新审核，哪些可以继续使用旧候选。
- 真实样片能否走通“准备—单项/批量制作—候选—审核退回—局部返工—成本解释”。
