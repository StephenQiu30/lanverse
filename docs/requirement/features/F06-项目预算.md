# F06 项目预算

| 项 | 内容 |
| --- | --- |
| 需求 | PRJ-03 项目预算 |
| 优先级 | MVP |
| 用例 | UC-19 |
| 页面 | 项目设置 · 预算；成本页；报价确认对话框 |
| 依赖功能 | F05、F16、F30 |
| 状态 | 草案（2026-09-25） |

## 1. 需求说明

### 1.1 背景与目标

商业模式为按量计费 + 项目预算（P4），成本上限尚未确定（P15），因此必须在生成前拦截超支，而不是事后发现。

### 1.2 用户故事

- 作为**管理员或制作者**，我希望为项目设置预算上限，以便生成前自动拦截超支，并在余额不足时得到提醒。

### 1.3 范围

- 包含：设置 / 调整预算、可用余额计算、报价拦截、余额不足提醒。
- 不包含：充值与支付（V2）、组织级总预算、按月预算。

## 2. 需求分析

### 2.1 业务流程

```text
设置预算上限 → 报价时比较报价金额与可用余额 → 确认时预留 → 终态结算并释放差额（F16）
可用余额 = 上限 − 已结算 − 已预留
可用余额 < 上限 × 20% → 通知（F31），每跨越一次阈值通知一次
```

### 2.2 业务规则

| # | 规则 | 理由 |
| --- | --- | --- |
| R1 | 新项目预算默认 0；0 时所有付费报价不可确认，提示先设置预算 | 防止未规划的支出 |
| R2 | 调低预算不得低于“已结算 + 已预留” | 保持账本平衡（REL-08） |
| R3 | 预算变更写账本（`budget_change`）与审计 | 可追溯 |
| R4 | 报价金额 > 可用余额时确认按钮不可用，并显示差额 | PRJ-03 |
| R5 | 批量报价按整体比较；用户可剔除部分项直到不超额 | 批量可操作 |
| R6 | 并发确认以数据库行锁 + `ck_budget_balance` 保证不超支 | 两个浏览器同时确认 |

### 2.3 状态

无独立状态；余额阈值状态 `normal` / `low` 存 Redis 用于通知去重。

### 2.4 异常与边界

- 实际结算 > 预留（供应商按实际计费超出报价）：允许结算使 `settled` 超过预期，但 `ck_budget_balance` 要求不超上限——若会超上限，结算仍记账（事实不可拒绝），预算自动标记“已超支”并通知，后续报价全部拦截。为此约束改为在结算路径上使用“允许超支”的专用函数，并记录 `adjust` 分录。
- 同时确认两笔各占 60% 余额的报价：第二笔因约束失败，返回 `budget_insufficient`。

### 2.5 前置与依赖

F16 的预留与结算实现。

## 3. 实现所需

### 3.1 数据

| 表 | 关键字段 | 为什么需要 |
| --- | --- | --- |
| `billing.budget` | `limit_micros`、`reserved_micros`、`settled_micros`、`revision`；`ck_budget_balance` | 余额计算与并发保护 |
| `billing.ledger_entry` | `entry_type = budget_change` | 预算调整留痕 |

说明：由于上述“结算超支”边界，`ck_budget_balance` 调整为 `reserved_micros + settled_micros <= limit_micros OR is_overrun`，并增加 `is_overrun boolean NOT NULL DEFAULT false` 列（0302 同步修改）。

### 3.2 接口

```http
GET /api/v1/projects/{pid}/budget
200 { "limit_micros": 500000000, "reserved_micros": 12000000, "settled_micros": 180000000,
      "available_micros": 308000000, "available_display": "¥308.00", "is_overrun": false, "revision": 4 }

PUT /api/v1/projects/{pid}/budget
{ "limit_micros": 800000000, "expected_revision": 4 }
200 { … }     422 validation_failed { "errors": [{ "field": "limit_micros", "code": "below_committed", "message": "最低可设 ¥192.00" }] }
```

报价与确认中的预算错误：`422 budget_insufficient { "meta": { "shortfall_micros": 30000000 } }`。

### 3.3 异步与工作流

无；预留与结算在 `flow` 队列 Activity 的数据库事务中执行（0304）。

### 3.4 事件与实时

`billing.budget_changed.v1`（audit）、`billing.budget_low.v1`（notify）；SSE `budget.updated`。

### 3.5 界面

设置页预算卡片（上限、已结算、已预留、可用、使用率进度条）；报价对话框显示剩余预算与差额；顶部低余额横幅。

### 3.6 权限与审计

管理员与制作者均可设置（MVP 内部使用）；审计 `budget.changed`（前后值）。

### 3.7 非功能要求

REL-08（任何时刻预算 ≥ 已结算 + 已预留，超支需显式标记；每日对账）。

## 4. 验收标准

- Given 可用余额 50 元，When 某批量生成报价 80 元，Then 确认按钮不可用，提示差额 30 元。
- Given 已结算 300 元、已预留 50 元，When 将预算调为 320 元，Then 被拒绝并提示最低可设 350 元。
- Given 两个浏览器同时确认各 60 元的报价、可用余额 100 元，When 两个请求并发到达，Then 只有一个成功，另一个返回预算不足。
- Given 可用余额从 25% 降到 15%，When 结算完成，Then 收到一次“预算余额不足”通知。

## 5. 测试要点

并发确认测试（race）；结算超支路径；阈值通知去重。
