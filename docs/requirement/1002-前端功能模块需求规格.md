## 结论

本规格把 10 个前端 Feature、共享旅程和高影响动作转换为稳定 Requirement ID。它规定用户可观察的输入、结果、失败、权限和验收方式，不重复组件树、状态库或 Backend 内部设计。

Requirement 只描述目标功能契约与验收方式。0→1 交付顺序与唯一 Checklist 见 [前端应用与功能交付实施计划](../plan/1001-前端应用与功能交付实施计划.md)。

## 1. Account Access (`account-access`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-ACC-001` | 用户必须能够完成邮箱验证、注册、登录、会话恢复和退出；各失败类型显示可区分原因。 | Unit + 注册登录 E2E。 |
| `FE-ACC-002` | Access Token 不得持久化到 Web Storage；Refresh 失败或退出后受保护页面必须停止显示业务内容。 | Session 单测、刷新/退出 E2E。 |
| `FE-ACC-003` | 登录成功后只能返回安全站内目标；恶意或外部 Return URL 必须回退到默认 Workspace/Project 入口。 | Return URL 安全单测/E2E。 |
| `FE-ACC-004` | `/account/security` 必须承载密码、活动 Session、全局撤销和账户停用，不与 Workspace 设置混合。 | 路由组件测试和 E2E。 |
| `FE-ACC-005` | 退出、密码变更、账户停用或撤权后，相关 Query、流和协作连接必须失效。 | 多连接 E2E。 |

## 2. Workspace Shell (`workspace-shell`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-WKS-001` | 用户必须看到真实 Membership 对应的 Workspace，并能选择可访问 Workspace。 | Query 组件测试和 E2E。 |
| `FE-WKS-002` | 已验证账户在具有账户级创建资格时可原子创建 Workspace 与 Owner Membership；拒绝必须解释平台策略原因。 | Backend 合同 + 创建 E2E。 |
| `FE-WKS-003` | `/w/:workspaceId/projects` 必须展示该 Workspace 的 Project，并区分真正空列表、筛选无结果、403、404 和已归档。 | 深链、空态和错误态组件/E2E。 |
| `FE-WKS-004` | 切换 Workspace 必须隔离旧 Workspace 的 Query、SSE、上传和协作连接，不得泄漏旧上下文。 | 双 Workspace 缓存/连接 E2E。 |
| `FE-WKS-005` | Viewer 可浏览允许内容，但不得看到无权高影响动作；直接调用仍由 Backend 拒绝。 | 角色组件测试和直接调用 E2E。 |

## 3. Project Shell (`project-shell`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-PRJ-001` | 用户必须能够创建、打开、搜索、更新、归档和恢复 Project，并从 Backend 重新读取结果。 | Unit + Project 生命周期 E2E。 |
| `FE-PRJ-002` | Project Shell 必须恢复 Workspace、Project、Episode、Preset、成本和生产状态摘要，不自行推进业务状态机。 | 深链刷新 E2E和网络断言。 |
| `FE-PRJ-003` | Project 不存在、已归档、无权和依赖降级必须分别展示，不得伪装成空数据。 | 状态组件测试/E2E。 |
| `FE-PRJ-004` | 任一 Project/Episode 子模块深链刷新后必须保持正确上下文和返回点。 | 路由 E2E。 |

## 4. Guided Production (`guided-production`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-GUI-001` | Guided 必须按 Script→Bible→Character/Scene→Storyboard→Shot→Sound→Review→Export 展示步骤、前置条件和下一动作。 | 组件测试、真实剧本 E2E。 |
| `FE-GUI-002` | 用户必须能导入完整剧本、预览、确认不可变修订、审阅分集计划并批量创建 Episode。 | 单元、合同与真实浏览器端到端验收。 |
| `FE-GUI-003` | Guided 编辑必须写入统一 Authoring Draft，发布必须生成不可变 Revision；运行不得直接消费可变 Draft。 | Authoring 合同测试和 E2E 数据核对。 |
| `FE-GUI-004` | Provider Unknown、候选过期、Revision 冲突、失败 Shot、预算不足和上游未确认必须显示不同阻塞与恢复动作。 | 故障注入组件/E2E。 |
| `FE-GUI-005` | 用户必须能只重跑失败 Shot/Node，刷新和服务重启后从 Backend 恢复同一 Run。 | Temporal/Run E2E 和重启演练。 |
| `FE-GUI-006` | `stage=review` 只显示审核摘要和 Review Workbench 深链，不得建立第二套 Claim/Decision 流。 | 路由和命令网络断言。 |
| `FE-GUI-007` | Guided 无法编辑的高级节点必须保留并显示只读摘要，不得从 Draft 静默删除。 | Guided/Canvas 同 Draft E2E。 |
| `FE-GUI-008` | Guided MVP 必须真实完成图片、动态镜头、配音、字幕、QC、审核、Render 和 Export。 | 真实输入端到端验收。 |

## 5. Authoring Canvas (`authoring-canvas`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-CAN-001` | Canvas 必须从 Backend Node Catalog 渲染节点、端口和配置；新增定义不得要求新增前端执行分支。 | Catalog fixture 与动态节点测试。 |
| `FE-CAN-002` | 活动 Graph/Layout 必须由 Yjs 唯一持有，工具、hover 和瞬时选择才可进入本地 Store。 | 状态所有权架构测试。 |
| `FE-CAN-003` | 用户必须能够编辑、Validate、Commit Snapshot、Publish Revision、Estimate 并发起 Node/Branch/Dirty/All 运行。 | Canvas 集成和 E2E。 |
| `FE-CAN-004` | Base Version/Epoch 冲突必须进入可解释 Rebase；旧 Epoch 不得覆盖新 Draft。 | 双客户端冲突 E2E。 |
| `FE-CAN-005` | 纯 Layout 变化不得改变执行 Hash；执行语义变化必须正确传播 Dirty。 | Hash/Dirty 合同测试。 |
| `FE-CAN-006` | 两个客户端最终收敛，断线和服务重启可恢复；未同步状态必须明确显示。 | Collaboration 集成与重启演练。 |

## 6. Review Workbench (`review-workbench`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-REV-001` | Review 队列必须区分 Human Task 生命周期和 Review Decision 类型，不得混用机器状态。 | Schema 合同和组件测试。 |
| `FE-REV-002` | 审核者必须能够打开 WAITING Task、Claim、比较候选/来源/QC/成本、提交唯一决议并读取新 Run 状态。 | Review/Human Gate E2E。 |
| `FE-REV-003` | Artifact 不可预览、Task 被他人领取、对象版本变化或 Decision 已存在时必须阻止默认批准和静默覆盖。 | 冲突和不可用组件/E2E。 |
| `FE-REV-004` | 决议重复提交必须幂等；关闭浏览器不得丢失 Human Gate。 | 幂等合同和重启 E2E。 |

## 7. Asset Library (`asset-library`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-AST-001` | UI 必须区分可复用 Asset 身份、Asset Version 和不可变 Artifact，并展示来源与使用影响。 | 组件测试和 API 数据核对。 |
| `FE-AST-002` | 上传必须走 Create Session→Presigned Direct Upload→Complete→Validation；幂等重试不得产生重复 Artifact。 | 网络断言和上传 E2E。 |
| `FE-AST-003` | `PENDING_VALIDATION` 不得 Preview/Publish/Render；只有 `READY` 可成为 Candidate 或生产输入。 | Readiness 组件/合同测试。 |
| `FE-AST-004` | `QUARANTINED`、`UNAVAILABLE` 和 `TOMBSTONED` 必须有不同动作与说明；恢复必须等待新的完整性 Receipt。 | 状态矩阵组件/E2E。 |
| `FE-AST-005` | 历史 Revision 永远引用原固定版本和 Artifact，切换活动版本不得改写历史。 | 版本/影响合同测试。 |

## 8. Run Observability (`run-observability`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-RUN-001` | Run 详情必须关联 Workflow、Node、输入输出、Provider Job、Artifact、Cost、Human Wait 和 Trace。 | Snapshot 合同和详情 E2E。 |
| `FE-RUN-002` | SSE 必须按 Last-Event-ID 去重重连，终态与重新读取 Snapshot 一致。 | 断线、重复和乱序 E2E。 |
| `FE-RUN-003` | `UNKNOWN` 不得归为 FAILED；Trace 缺失必须显示诊断不完整。 | 故障注入组件测试。 |
| `FE-RUN-004` | Retry Failed 不得误跑成功分支，Cancel/Retry/Reconcile 必须由服务端确认后更新。 | 局部执行 E2E。 |
| `FE-RUN-005` | 成本必须可追溯到 Run、Node、Provider 和 Artifact，并区分估算、预留与结算。 | Cost 合同和对账 E2E。 |

## 9. AI Copilot (`ai-copilot`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-COP-001` | Copilot 必须使用所选 Project/Episode/Draft 上下文，并展示结构化 Reasoning、ToolCall 和 Artifact 建议。 | 流式 reducer、组件和端到端验收。 |
| `FE-COP-002` | 未完成响应只存在流式 Controller；断线按 Event ID 去重，客户端不得伪造终态。 | SSE 断线/恢复测试。 |
| `FE-COP-003` | GraphPatch 必须 Validate→Preview→Confirm→Apply Intent/Grant→Receipt；只有持久 `APPLIED` 才显示成功。 | 故障注入和双客户端 E2E。 |
| `FE-COP-004` | 应用 Tool 必须同时具备 `copilot:apply_tool` 与 `authoring:edit`；任一拒绝不得自动重试。 | Capability 合同和越权 E2E。 |

## 10. Workspace Governance (`workspace-governance`)

| Requirement ID | 必须成立的功能契约 | 验收方式 |
|---|---|---|
| `FE-GOV-001` | Owner 必须能查看和管理允许的成员、角色、Consent、Workspace 设置、Budget/Quota 和审计。 | 角色组件和治理 E2E。 |
| `FE-GOV-002` | Consent 必须按固定 Subject Version 登记、修订和撤销，历史记录不可覆盖。 | Unit + Consent E2E。 |
| `FE-GOV-003` | 最后 Owner、自身降权、并发 Revision 冲突必须由 Backend 阻止并显示明确恢复动作。 | 并发权限 E2E。 |
| `FE-GOV-004` | 无审计事件是合法空态；依赖降级不得显示虚假零用量；无完整审计能力不得泄漏 Subject 是否存在。 | 状态组件和权限 E2E。 |
| `FE-GOV-005` | 权限撤销后 Query、Collaboration 和 Command 能力必须及时失效，所有高影响变更可审计。 | 撤权多连接 E2E 和审计对账。 |

## 11. 跨模块旅程

| Requirement ID | 必须成立的端到端结果 | 验收方式 |
|---|---|---|
| `FE-JNY-001` | 注册→Workspace→Project→刷新恢复→退出后的受保护路由必须形成闭环。 | 真实浏览器端到端验收。 |
| `FE-JNY-002` | 完整剧本上传→预览→固定修订→确定性分集→创建 Episode→发布单集剧本必须形成闭环。 | 真实剧本端到端验收。 |
| `FE-JNY-003` | Guided 发布 Revision→启动 Run→Human Gate→Review Decision→恢复→Export 必须形成闭环。 | 真实剧本 E2E 和服务重启演练。 |
| `FE-JNY-004` | Canvas 双客户端→编辑收敛→发布 Revision→局部运行→刷新恢复必须形成闭环。 | Collaboration/Canvas E2E。 |
| `FE-JNY-005` | Presigned 上传→Readiness→Asset Version→生产引用→历史影响必须形成闭环。 | 上传/资产 E2E。 |
| `FE-JNY-006` | Viewer/Editor/Owner 的页面、动作和直接 API 拒绝必须与 Backend Capability 一致。 | 角色矩阵 E2E。 |

## 12. 高影响动作通用契约

| Requirement ID | 必须成立的契约 | 验收方式 |
|---|---|---|
| `FE-ACT-001` | 发布 Revision、启动/重试/取消 Run、Review Decision、Asset 发布/隔离/删除、成员/策略变更和 Copilot Tool 必须展示目标、影响和所需能力。 | 组件测试和操作 E2E。 |
| `FE-ACT-002` | loading 只表示请求进行中；只有持久结果确认后才能显示完成。 | 延迟/错误注入组件测试。 |
| `FE-ACT-003` | 403 必须失效相关 Capability 查询，但不得自动重发高影响命令。 | request/Query 集成测试。 |
| `FE-ACT-004` | 409、STALE 和 outcome unknown 必须保留可安全保留的用户输入，并通过刷新、Diff、Rebase 或同一 ID 对账。 | 冲突和未知结果 E2E。 |

## 13. 非目标

本规格不定义：

- package、状态库、通信实现和 Canvas 内核选型，详见 [前端应用架构需求规格](1001-前端应用架构需求规格.md)；
- Backend 领域模型、权限算法、Workflow 编译或 Provider 执行；
- 易变视觉布局、营销文案和无验收依据的数值承诺；
- 以局部 Feature 验收替代 Guided MVP 或 Platform Complete 的完整发布门；
- 为尚未开始的功能预建空 Feature、兼容层或占位页面。
