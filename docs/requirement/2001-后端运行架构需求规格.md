## 结论

本规格从空项目出发，定义 Backend 的运行程序、契约源、数据、事件、Agent、存储、安全和可观测性边界。全部条款都是尚待实施和独立验收的目标契约。

## 范围与非目标

本规格覆盖 Go Backend 五 Binary、公共与内部契约、Schema Migration、PostgreSQL/Redis/Kafka/Temporal/ObjectStore/Elasticsearch、Python Agent Runtime 边界、Telemetry 和运行安全。领域事实与生产闭环见[后端领域服务与生产闭环需求规格](2002-后端领域服务与生产闭环需求规格.md)。

本规格不设定 Provider 商业选型、生产 Secret、易变排期或未经测量的 SLA。

## 运行程序与网络边界

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-RUN-001` | Backend 必须使用单一 Go Module，不使用 `go.work`，不包含 Python 运行代码。 | 语言边界与 Module 架构测试。 |
| `BE-RUN-002` | 必须构建 `lanverse-api`、`workflow-worker`、`model-gateway`、`media-worker`、`event-worker` 五个独立 Binary，每个 Binary 只装配所需模块。 | 五 Binary 构建、启动和依赖装配测试。 |
| `BE-RUN-003` | Browser 必须通过 `lanverse-api` 使用 REST/JSON 与 SSE；Backend Binary 间使用 gRPC/Protobuf；业务事件使用 Kafka；长任务和等待使用 Temporal。 | 网络拓扑、协议边界和禁止跨界调用测试。 |
| `BE-RUN-004` | 每个 Binary 必须提供明确的 Liveness、Readiness、BuildInfo 和 Metrics；Liveness 不访问外部依赖，Readiness 反映完成该 Binary 职责所必需的依赖。 | 端点 Contract Test 与单依赖故障注入。 |
| `BE-RUN-005` | SIGTERM 必须使 Binary 停止接收新工作、Drain 已领取工作、在有界超时内关闭连接并暴露停机结果。 | 五 Binary 优雅停机、超时和重启恢复测试。 |

## 分层与依赖

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-ARC-001` | 组合根可以依赖装配所需的模块和 Adapter，但不得包含业务规则。 | 组合根 AST/Import 测试与业务逻辑扫描。 |
| `BE-ARC-002` | Inbound Adapter 只处理认证、协议校验、转换、Context 传播和错误映射，不得直接读写 Repository。 | Handler 依赖方向与禁止 SQL/SDK 测试。 |
| `BE-ARC-003` | Application 层拥有用例、授权、事务、幂等、乐观锁和 Outbox，只依赖 Domain、本模块 Port 和公开模块 Interface。 | Import Direction 和事务边界测试。 |
| `BE-ARC-004` | Domain 不得依赖 HTTP/gRPC 框架、数据库、Redis、Kafka、Temporal、ObjectStore、Provider SDK 或其他模块 Adapter/Repository。 | Go Import/AST 架构测试。 |
| `BE-ARC-005` | Port 由使用它的业务模块拥有，Repository Port 以聚合为单位，不暴露通用 CRUD 或跨模块 Join。 | Port API 审计、聚合持久化和跨模块引用测试。 |

## 契约源与错误

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-CON-001` | 公共 REST/SSE、Backend RPC、Kafka Event 和 Agent RPC 必须分别有唯一 OpenAPI、Proto 或 Event Schema 契约源，生成代码不得手改。 | 契约生成后仓库无漂移；契约源唯一性检查。 |
| `BE-CON-002` | 契约变更顺序必须为 Design → Source Schema → Compatibility Test → Generate → Implement → E2E。 | CI 阶段顺序和不兼容变更负向测试。 |
| `BE-CON-003` | REST 必须使用统一错误包络、游标分页、幂等键和版本冲突响应；SSE 必须支持 `Last-Event-ID`；gRPC 必须声明 deadline、可重试码和幂等语义。 | 协议 Contract Test、错误矩阵和断线重连测试。 |
| `BE-CON-004` | Event Envelope 必须包含事件、Schema、聚合、Workspace、分区、时间、Trace、Correlation、Causation 和 JSON Payload，并拒绝未知字段。 | JSON Schema 与多语言 Decoder 正反 Contract Test。 |

## 数据、事件与运行状态

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-DAT-001` | PostgreSQL 是业务事实源；Temporal 是 Workflow History/Timer/Retry/Signal 事实源；ObjectStore 是字节事实源；Redis 和 Elasticsearch 只保存可重建状态。 | 资源所有权架构测试和重建演练。 |
| `BE-DAT-002` | 生产 Schema 只能由版本化 Migration 修改；Migration 必须连续、有 Checksum、受 Advisory Lock 保护并在事务内记录 Receipt。 | 空库、幂等、并发、Checksum 漂移、中途失败和回滚测试。 |
| `BE-DAT-003` | 业务 Command 必须在一个 PostgreSQL 事务中修改 Owner 事实并写 Outbox；不得在数据库提交后另行发 Kafka 形成双写。 | 事务提交/回滚与 Outbox 发布一致性测试。 |
| `BE-DAT-004` | Kafka Consumer 必须以 Event ID 幂等、按聚合分区保序，支持 DLQ、Replay 和 Projection Checkpoint。 | 重复、乱序、Poison Message、DLQ Redrive 与 Replay/实时竞态测试。 |
| `BE-DAT-005` | Workflow Start/Control/Signal 必须使用持久 Intent/Receipt 和稳定 Temporal Workflow ID；PostgreSQL 投影不得反向驱动 Temporal。 | 远程结果未知、Already Started、重复 Signal、Replay 和投影重建测试。 |

## Agent、存储、安全与可观测性

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-AGT-001` | Python Agent Runtime 只能执行 Structured、ToolLoop 和受限 LangGraph Executor，通过 gRPC 接收绑定 Run/Node/Tool/模型能力/预算/时限的 Execution Grant。 | Grant 作用域、执行上限和 Executor 选择测试。 |
| `BE-AGT-002` | Agent 不得连接 PostgreSQL、ObjectStore、Yjs、任意 Shell 或任意网络；模型调用只能经 Model Gateway，Tool 只能经 Backend Allowlist API。 | 依赖扫描、网络阻断、Tool Allowlist 和绕过 Gateway 负向测试。 |
| `BE-STO-001` | 所有 Bucket 必须私有；Browser 使用短期 Presigned URL 直传/下载；内部操作地址与 Browser 签名地址必须分离。 | 存储 Port Contract、预签名端到端和私有 Bucket 访问测试。 |
| `BE-SEC-001` | 所有资源必须检查 Workspace RBAC；Callback、gRPC 和 Yjs WebSocket 必须认证并绑定最小作用域；高成本操作和关键依赖默认 fail closed。 | 权限矩阵、跨租户、重放、依赖故障和高成本绕过测试。 |
| `BE-SEC-002` | 每个 Binary 只能获得最小凭据；Secret 不得进入命令行、日志、Metric Label、Trace、Event 或公开 API。 | 凭据矩阵、Secret 扫描和各信道泄漏负向测试。 |
| `BE-OBS-001` | Trace 必须跨 HTTP、gRPC、Temporal、Agent、Generation、Media 和 Kafka 传播；日志使用 JSON 且脱敏；Metric 只使用有界标签。 | 全链 Trace 断言、日志脱敏和 Metric 基数测试。 |

## 基础设施闭环

| ID | 目标契约 | 验收方式 |
|---|---|---|
| `BE-INF-001` | 目标部署必须包含 PostgreSQL、Redis、ObjectStore、Kafka、Temporal、Kafka Connect/Debezium、Elasticsearch/Kibana、OTel Collector、Prometheus/Grafana。 | 干净环境完整启动与服务拓扑检查。 |
| `BE-INF-002` | 所有有状态依赖必须有持久化、Health、资源限额、私有网络和生产 Override；业务进程不得私自替代缺失的基础设施。 | 已有 Volume 重启、依赖故障、资源限额和生产配置验收。 |
