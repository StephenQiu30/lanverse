# REQ-011 消息队列与异步投递需求

- 状态：部分 accepted（现有 Outbox/Inbox、消息传播、Attempt 预持久化/无 Provider 失败收敛、generation 协议毒消息终止收敛及 backlog/inflight/prefetch 增量；其余范围待后续验收）
- 输入：`001-平台总体需求概述.md`、`004-媒体模块需求.md`、`009-生产模块需求.md`、`010-剪辑交付模块需求.md`
- 输出：RabbitMQ 投递、消费、重试、恢复和运维需求
- 下游：REQ-013、消息队列详细设计、异步任务实施 Plan

## 1. 需求概述

消息队列必须解耦 HTTP 请求与模型调用、媒体探测、下载、转码和渲染等长操作。RabbitMQ 只承载可重复的工作通知，PostgreSQL 中的业务请求、Task、Attempt、费用和结果始终是事实来源。

MVP 固定 RabbitMQ + aio-pika，不引入 Temporal、Kafka、Celery 或第二套任务状态。消息丢失、重复、乱序、消费者重启和 RabbitMQ 短时不可用均不得破坏已确认业务事实。

## 2. 事实与契约需求

| 编号 | 事实/契约 | 需求 |
| --- | --- | --- |
| MQ-ENT-001 | OutboxEvent | 必须与触发它的业务事实同事务保存，记录事件类型、版本、聚合、Workspace、payload、可发布时间和发布状态。 |
| MQ-ENT-002 | MessageEnvelope | 必须包含唯一 event_id、event_type、schema_version、aggregate_id、workspace_id、occurred_at、trace_id、可选 causation_event_id 和类型化 payload。 |
| MQ-ENT-003 | InboxDelivery | 必须按 event_id 与 consumer 标识一次消费结果，用于重复消息识别、失败定位和安全确认。 |
| MQ-ENT-004 | DeliveryAttempt | 必须保留发布/消费尝试次数、最近错误、下次可执行时间和最终处置，不把 RabbitMQ redelivery 次数当作业务重试事实。 |

消息 payload 只能携带稳定 ID、版本、hash 和执行所需的小型参数；不得携带媒体字节、访问令牌、供应商密钥、完整剧本或不可控大对象。

## 3. 功能性需求

| 编号 | 需求 |
| --- | --- |
| MQ-FR-001 | 创建异步业务时必须原子保存业务事实、Task/请求和 OutboxEvent；RabbitMQ 不可用不得导致业务事实回滚或丢失。 |
| MQ-FR-002 | Publisher 必须领取到期未发布事件、发送持久消息、等待 publisher confirm，并在确认后标记已发布。 |
| MQ-FR-003 | Consumer 必须先验证 envelope 和业务事实，再幂等执行；数据库结果提交后才能 manual ack。 |
| MQ-FR-004 | 重复投递、重复回调和 Worker 重启必须返回既有结果或继续未完成阶段，不重复调用供应商、生成 Candidate 或记账。 |
| MQ-FR-005 | 可重试失败必须由 PostgreSQL 保存 retryable、attempt、available_at 和 next_action；到期后重新投递，不依赖进程内定时器。 |
| MQ-FR-006 | 未知 schema、非法 payload、达到重试上限或不可重试错误必须持久化为 rejected/manual_attention 后确认消息，避免毒消息无限循环。 |
| MQ-FR-007 | Task 取消、暂停新任务和 Workspace 归档必须通过数据库状态控制；删除 RabbitMQ 消息不得伪装业务取消成功。 |
| MQ-FR-008 | 运维人员必须能查询 Outbox、Inbox、Task 和最近错误的关联状态，并安全重放可重放事件。 |
| MQ-FR-009 | RabbitMQ 或 Worker 恢复后，系统必须自动继续未发布 Outbox 和到期工作；客户端无需重新提交原业务命令。 |

## 4. 接口需求

| 编号 | 交接面 | 输入 | 输出/错误 |
| --- | --- | --- | --- |
| MQ-IF-001 | 业务事务写入 | event_type、aggregate、payload、trace、available_at | OutboxEvent；与业务提交共同成功或失败 |
| MQ-IF-002 | Publisher → RabbitMQ | MessageEnvelope、routing_key | broker confirm 或可重试发布错误 |
| MQ-IF-003 | RabbitMQ → Consumer | Envelope、delivery metadata | ack/nack 决策与 InboxDelivery；业务错误写 Task |
| MQ-IF-004 | 运维查询/重放 | event/task ID、状态、时间范围、原因 | 脱敏状态与重放结果；无权访问必须拒绝 |
| MQ-IF-005 | 健康检查 | 当前运行角色、连接、channel、confirm、积压与消费者状态 | 逐依赖 critical/status/reason；API 在 MQ 不可用但 PostgreSQL/Outbox 可写时为 degraded 而非整体 unavailable；依赖异常不得谎报 ready |

MVP 只允许 `lanverse.io` 与 `lanverse.media` 两类主队列。任务类别到 routing key 的映射必须受控，未知 routing key 不得被静默丢弃。

## 5. 非功能性需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| MQ-NFR-001 | 可靠性 | 投递语义为至少一次；必须通过 Outbox、Inbox 和业务幂等实现可观察的一次业务效果。 |
| MQ-NFR-002 | 一致性 | 数据库提交与消息发布不得使用无法恢复的双写；消费者不得在结果提交前 ack。 |
| MQ-NFR-003 | 顺序 | 不依赖 RabbitMQ 全局顺序；同聚合消息通过 revision、状态机和 expected version 拒绝过期操作。 |
| MQ-NFR-004 | 资源 | prefetch、连接数、ThreadPoolExecutor 和 FFmpeg 子进程必须有界；具体容量在 PRD/压测中量化。 |
| MQ-NFR-005 | 安全 | RabbitMQ 使用独立最小权限账户、TLS/受控网络和非默认凭据；消息与日志不得泄露敏感输入。 |
| MQ-NFR-006 | 可观测 | 发布、消费、重试、拒绝和积压必须关联 event_id、task_id、trace_id，并提供低基数指标。 |
| MQ-NFR-007 | 可恢复 | Broker/Publisher/Consumer 重启不得丢失持久事实；连接恢复后不得形成重复外部副作用。 |
| MQ-NFR-008 | 可维护 | schema_version 与 handler 显式注册；禁止反射导入任意函数、pickle 或通用任务执行器。 |
| MQ-NFR-009 | 性能 | 入队接口不等待长任务；发布可见时限、队列积压阈值和恢复时限在 PRD 中量化。 |

## 6. 失败路径与非目标

- publish confirm 超时：Outbox 保持待确认/可重试；重复发布使用相同 event_id。
- Consumer 进程在提交前退出：消息重新投递，Inbox/业务唯一约束保证安全重做。
- Consumer 提交后 ack 前退出：重复消息读取已完成 Inbox/Task 后直接 ack。
- RabbitMQ 长期不可用：API 可创建持久 Task/Outbox，进程 readiness 返回 200 + degraded 并显示排队阻塞；超过积压容量后拒绝新的高成本提交，普通读写仍可用。以 RabbitMQ 为硬依赖的 Scheduler/Worker readiness 可返回 503，但不得用重启代替持久恢复。
- 不以 DLQ、TTL 重试队列或延迟插件建立第二套状态机；毒消息处置和计划重试以 PostgreSQL 为事实。
- 不保证 exactly-once broker 投递，也不把 RabbitMQ 管理页面作为业务任务中心。

## 7. 当前积压与执行容量增量边界

1. PostgreSQL 是 Outbox backlog 的事实源。Publisher 每批结束后按 `routing_key/status` 读取 `pending/claimed/manual_attention` 数量及最老 `created_at`，再归一为 `lanverse.io/lanverse.media/unregistered`；RabbitMQ 队列深度不替代该事实。
2. Prometheus 精确新增 `lanverse_outbox_events(queue,state)`、`lanverse_outbox_oldest_age_seconds(queue,state)`、`lanverse_worker_inflight(queue)` 与 `lanverse_worker_capacity(queue)`。queue/state 只能来自固定集合，event/task/workspace ID、routing key 原值、last_error 和消息正文不得成为 label。
3. Worker 从收到消息到 ack/nack 决策完成均计入 inflight，并在异常/取消路径通过 `finally` 归零。I/O capacity 固定沿用当前 4、Media capacity 固定沿用当前 2；同一常量必须同时驱动 RabbitMQ `prefetch_count` 和 capacity 指标，不能出现“指标容量”和实际 broker 容量两套配置。
4. 真实 RabbitMQ 验收必须投递 `capacity + 1` 条消息并阻塞前 `capacity` 条，证明第 `capacity + 1` 条保持 ready，释放后再消费；只检查常量或 mock channel 不能替代该证据。
5. Outbox 指标刷新失败或 Prometheus 写入失败不得改变 publish confirm、PostgreSQL 状态或 Worker ack/nack。最老年龄使用 `created_at`，不得用未来 `available_at` 隐藏已存在的重试/人工处置积压。
6. D-007 尚未量化 pending 数/年龄的容量门槛，因此本增量不臆造 API 拒绝阈值，不接受积压降级、RabbitMQ ready/unacked、独立 Worker scrape/readiness、告警或 PT-MQ-004/PT-OBS-002 整体。

上述增量已按边界 accepted，真实证据见[Outbox 积压与 Worker 执行容量验收](../acceptance/024-Outbox积压与Worker执行容量验收.md)。

## 8. 当前 generation consumer 增量边界

1. `generation.requested` 固定由 `lanverse.io.generation.v1` 处理，只接受 schema v1、`payload={task_id}` 和 `image_generation|video_generation` Task；它与剧本提取 consumer 共享 Inbox 原语，但不能误用同一 consumer identity。
2. 合法首投必须先提交 processing Inbox、prepared Attempt 与 `running/validating` Task，再进入后续阶段；当前没有经 D-004 验证的 Provider，因此后续阶段只能确认零外部副作用并失败释放，不能尝试 submit。
3. 失败事务后 nack/requeue；同 event redelivery 递增 Inbox delivery attempt_count、复用同一 prepared Attempt 并完成失败释放。成功提交后才 manual ack；ack 后重复消息只回读 completed Inbox，不新增 Attempt、费用或审计。
4. 该增量当时不接受未知 schema/manual_attention、业务重试计划、Provider unknown/query/cancel 或新的 Attempt sequence；其中已知 generation Task 的 schema/payload 协议错误由下述独立增量收敛，其余仍属于 PT-MQ-003 后续真实故障场景。

上述 generation consumer 增量已按边界 accepted，真实证据见[生成 Attempt 预持久化与无 Provider 失败收敛验收](../acceptance/025-生成Attempt预持久化与无Provider失败收敛验收.md)。

## 9. 当前 generation 协议毒消息终止收敛边界

1. 已知 `generation.requested` 且能通过 `aggregate_id/workspace_id` 锁定 queued generation Task 时，不支持的 schema 或与 Task ID 不一致的 payload 是不可重试协议错误；不得创建 Attempt、调用 Provider 或保持预占悬挂。
2. 同一 PostgreSQL 事务必须把 Inbox 置为 `manual_attention`，Task 置为 `failed/manual_attention`，保存稳定 `unsupported_message_schema|invalid_message_payload`、`retryable=false`和 `next_action=contact_support`，释放 active Reservation，追加 `attempt_id=null` 的全额 release CostEntry 与 `task.failed` 审计，提交后才 ack。
3. 同 event redelivery 只递增 Inbox attempt_count 并回读既有结果；不新增 release、Audit 或 Attempt。事务提交失败时必须 nack/requeue，不得在无持久化事实时 ack。
4. Task 已在 running/waiting_provider 或终态时，协议错误消息不得覆盖已有执行事实或二次释放；无法解析 Envelope、未知 event type、业务重试上限、Provider unknown/reconcile 和告警/运维查询仍不由本增量接受。

上述增量已以真实 PostgreSQL 约束与真实 RabbitMQ manual ack/redelivery 通过验收，证据见[generation 协议毒消息终止收敛验收](../acceptance/026-generation协议毒消息终止收敛验收.md)。该接受不扩展到无法解析 body、未知 event type、计划重试/上限、Provider unknown 或运维重放，PT-MQ-003 整体仍为 `in_progress`。
