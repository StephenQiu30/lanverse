## 结论

本规格把平台产品基线转换为跨 Frontend、Backend 与 Agent 的可测试发布契约。各服务 Requirement 可以收紧实现约束，但不得降低本规格的端到端结果、唯一事实源、可恢复性、安全和可追踪要求。

本文件记录原 0→1 目标契约。既有代码、目录、测试和运行结果可以作为当前事实与缺口输入，但不能自动证明任何新 Requirement 或 Acceptance 已完成；StoryGraph 重叠契约必须等待新链路重新派生。

## 范围与角色

本规格覆盖普通创作者、高级创作者、审核者和 Workspace 治理角色从项目创建到成片导出的生产旅程，以及支撑该旅程的运行、资产、成本、安全与审计契约。

不覆盖通用 AI 视频平台、专业时间线、复杂 3D、直播、市场化插件、任意代码执行、多地域多活或超大型企业权限系统。

## 功能需求

| ID | 强制需求 | 验证方式 |
|---|---|---|
| `PLT-FR-001` | 用户必须能够创建或进入 Workspace 与 Project，导入并固定剧本版本，然后从可分享入口恢复当前项目和分集上下文。 | 真实浏览器 E2E；刷新、重新登录和深链恢复测试。 |
| `PLT-FR-002` | Guided Studio 必须覆盖 Script → Production Bible → Character/Scene → Storyboard/Shot → Image/Video → Voice/Subtitle → Render → QC/Review → Export 的完整生产闭环。 | 使用真实剧本执行端到端验收；逐阶段核对业务事实、Artifact 和最终导出物。 |
| `PLT-FR-003` | Guided 与 Canvas 必须编辑同一种 `AuthoringDraft`，发布同一种不可变 `AuthoringRevision`，并由唯一 Compiler 生成同一种 `WorkflowDefinitionVersion`；任一入口不得绕过 Revision 直接启动运行。 | 对等输入的 Definition 差异测试；绕过 Revision 的负向 API 测试。 |
| `PLT-FR-004` | 每次运行必须冻结 Script、Bible、Authoring、Policy、Skill、Prompt、模型选择和输入 Artifact 的精确版本；后续编辑不得静默改变历史运行。 | 运行前后修改源数据，核对绑定版本、Hash、结果和审计记录。 |
| `PLT-FR-005` | 模型和 Agent 输出必须先成为 Candidate；输出字节通过完整性、安全与可用性校验并进入 `READY` 后，才可参与 QC、Review 或 Selection。正式生产事实只能由 Backend 在授权且版本匹配时写入。 | Candidate/Artifact 状态机测试；未就绪、越权和版本冲突负向测试。 |
| `PLT-FR-006` | 审核必须区分 Human Task、Review Decision 与生产 Apply；领取、决议、Signal 和 Apply 分别幂等，重复提交不得产生第二个最终结果。 | 并发领取、重复决议、重复 Signal/Apply 与崩溃恢复测试。 |
| `PLT-FR-007` | 用户必须能看到等待、失败、预算不足、结果未知和需要人工处理的明确状态及下一动作；系统不得把请求已接收或结果未知显示为成功。 | UI 状态矩阵；Provider 超时、网络中断、409/422/429/依赖不可用故障注入。 |
| `PLT-FR-008` | 失败运行必须支持服务重启恢复、失败节点或单 Shot 局部重跑、Human Gate 暂停/继续和显式取消；恢复不得重复收费、Candidate、Artifact 或生产效果。 | Temporal 恢复、重复投递、Heartbeat、Fencing 和取消 E2E。 |
| `PLT-FR-009` | 所有可复用身份及其业务状态必须进入 Asset/AssetState/Version；所有不可变生产输出必须登记为 Artifact，并保留来源、版本、权利与使用影响。 | 资产身份唯一性、版本不可变性、Lineage、Rights、影响分析与删除/替换测试。 |
| `PLT-FR-010` | 图片、视频、音频、字幕、文档和导出字节必须保存在私有 ObjectStore；浏览器使用短期 Presigned URL 直传或读取，大文件不得经 Public API 中转。 | 真实浏览器上传/下载、过期签名、错误 Content-Type/Hash 和私有 Bucket 访问测试。 |

## 运行与数据需求

| ID | 强制需求 | 验证方式 |
|---|---|---|
| `PLT-RUN-001` | PostgreSQL 是业务事实源，Temporal 是 Workflow History/Timer/Retry/Signal 的事实源，ObjectStore 是对象字节事实源；Redis、Kafka、Elasticsearch 和协作日志不得冒充业务事实。 | 架构测试；删除并重建投影；服务重启和数据对账。 |
| `PLT-RUN-002` | 任一业务资源、表、Endpoint、Topic、Workflow Type、索引或 Bucket Prefix 只能有一个写入所有者；Snapshot 与 Projection 只读，业务双写禁止。 | [资源所有权与交付台账](../plan/0008-资源所有权与交付台账.md)、Writer 静态门禁与重复写入负向测试。 |
| `PLT-RUN-003` | 业务事务必须原子修改 Owner 事实并写 Outbox；Consumer 必须以 Inbox/Checkpoint 幂等处理重复、乱序和重放，投影失败不得回滚已提交业务事实。 | 事务中断、重复/乱序投递、DLQ Replay、Reindex 和对账测试。 |
| `PLT-RUN-004` | Temporal 管理跨步骤生命周期；LangGraph 只允许存在于单个 Agent 的有限推理内部；Kafka 不得承担 Timer、Retry、Human Wait 或 LLM Token Stream。 | 架构依赖测试、Workflow Replay、超时/取消和消息用途审计。 |
| `PLT-RUN-005` | 高成本操作必须执行 Estimate → Cost/Quota Reservation → 在线 Claim/Authorization → Execute → Receipt → Settle/Consume/Reconcile；已领取后结果未知不得释放并盲目重提。 | Provider 故障注入；重复回调、迟到 Receipt、未知结果和账目对账测试。 |
| `PLT-RUN-006` | HTTP、gRPC、Temporal、Agent、Provider、Kafka 与 Artifact 必须传播同一关联链路；Prompt、Skill、Policy、模型、费用、Tool 权限、审核和生产结果必须可审计。 | Trace 连贯性查询；审计字段完整性、日志脱敏和 Artifact 反向追踪。 |

## 安全与质量需求

| ID | 强制需求 | 验证方式 |
|---|---|---|
| `PLT-NFR-001` | Browser、Canvas、Agent 与 Provider 均不得直接写业务数据库；Agent 不得持有 PostgreSQL、ObjectStore、任意 Shell 或任意网络权限，只能使用 Run-scoped Grant 调用允许的 Tool/Model。 | 依赖扫描、凭据扫描、Tool Allowlist 与越权负向测试。 |
| `PLT-NFR-002` | 认证、Workspace 能力、对象签名、Callback、幂等键和高影响命令默认 fail closed；Token、Secret、原始 Prompt 私密输入和签名 URL 不得进入 URL 历史、持久前端存储或非脱敏日志。 | 安全 E2E、日志扫描、撤权传播、过期/伪造 Token 与签名测试。 |
| `PLT-NFR-003` | API、事件、RPC、数据库 Migration、Workflow 和生成 Schema 必须版本化；兼容性、生成漂移、回放和回滚必须在发布前通过。 | Contract/Schema compatibility、generated drift、Migration checksum 与 Workflow replay 门禁。 |
| `PLT-NFR-004` | 每个用户可见异步动作必须可通过稳定 ID 查询；重试、刷新、断线重连和服务重启后必须收敛到同一终态。 | 重复请求、断网重连、进程重启、旧 Token Fencing 与终态 Hash 对账。 |

## 发布门

### `Guided MVP`

以下条件必须同时满足：

- `PLT-FR-001`、`PLT-FR-002`、`PLT-FR-004` 至 `PLT-FR-010` 通过真实剧本验收；
- `PLT-RUN-001` 至 `PLT-RUN-006` 对 Guided 主链成立；
- `PLT-NFR-001` 至 `PLT-NFR-004` 的安全、恢复与契约门禁通过；
- 角色/场景一致性、候选选择、错误 Shot 局部修复、成本追踪和最终成片均有 Acceptance 证据。

### `Platform Complete`

在 `Guided MVP` 之上，还必须满足：

- `PLT-FR-003` 的 Guided/Canvas 同源发布与执行等价性；
- Canvas Node Catalog、Graph Validation、局部执行、Dirty/Cache、Yjs 协作与 Copilot GraphPatch 完整闭环；
- 完整 Search、Cost/Quota、Observability、事件投影、Replay/Reindex 与治理能力；
- 双客户端协作、断线恢复、撤权、容量与性能基准有真实 Acceptance 证据。

## Acceptance 证据要求

本规格初始不声明任何条款已实现或已验收。每个发布门的 Acceptance 必须至少记录：

- 从空环境创建的版本化部署与配置，不复用未声明的本地状态；
- 真实用户、Workspace、Project、剧本、Provider 和对象输入的稳定标识与 Hash；
- 实际执行的命令、浏览器旅程、故障注入、结果、指标和失败样本；
- Requirement ID → 测试 → Artifact/Receipt/Trace/Audit 的追踪关系；
- 未运行项、外部条件、人工判断、残余风险和回滚结果。

## 追踪规则

1. 服务 Requirement 必须通过 ID 映射到本规格，不复制系统级发布门。
2. [平台 0→1 交付计划](../plan/0007-平台0到1交付计划.md)拥有跨服务顺序；服务 Plan 只拥有本服务 Checklist。
3. Checklist 初始全部为 `[ ]`；只有对应 Acceptance 完成后才可标记完成。
4. 只有 Acceptance 记录真实输入、环境、命令、结果与残余风险后，才可声明对应范围已验收。
