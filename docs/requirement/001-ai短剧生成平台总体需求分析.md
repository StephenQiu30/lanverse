# AI 短剧生成平台总体需求与模块总览

## 1. 平台需要完成的事情

单个图片或视频能够生成，不代表一集短剧能够完成。创作者真正需要的是：把故事持续转化为内容结构、可复用资产、可审核镜头和可交付单集，并能在生成不确定时定位问题、控制成本和局部返工。

Lanverse 的核心服务定义为：

> 在一个项目上下文中组织短剧的内容、资产、AI 制作、审核和交付，让每一步都有明确输入、业务结果、责任和历史依据。

当前 MVP 基线优先服务已有故事或剧本的个人创作者，完成一集短剧生产闭环。小团队协作、多集生产和跨项目复用仍是待验证扩展。

## 2. 服务边界

| 平台承担 | 当前不承担 |
| --- | --- |
| 组织项目、剧本、场次、镜头和生产进度 | 替代专业编剧、剪辑、调色、混音和发行系统 |
| 统一管理角色、场景、道具、风格、声音及生成媒体 | 承诺一句话生成无需人工判断的商业短剧 |
| 组织图片、视频、声音等制作任务及候选结果 | 把开放模型、节点工作流或素材市场作为首发中心 |
| 支持审核、采用、局部返工、单集组织和交付 | 在需求阶段决定模型、供应商和技术实现 |
| 管理用量成本、内容权利、安全和 AI 标识 | 同时满足所有题材、团队规模和发行渠道 |

## 3. 端到端生产主流程

```mermaid
flowchart LR
  A["建立项目与目标"] --> B["整理剧本与镜头"]
  B --> C["准备创作资产"]
  C --> D["检查制作条件"]
  D --> E["执行制作并收集候选"]
  E --> F["审核、采用或局部返工"]
  F --> G["组织单集并完成交付"]
  G --> H["沉淀资产与生产记录"]
```

流程遵循三项业务原则：先确认低成本内容再开始高成本制作；人工负责内容和审美决定；修改只影响真正依赖它的内容。

## 4. 模块功能地图

| 模块 | 负责的核心功能 | 形成的业务结果 |
| --- | --- | --- |
| [用户、组织与权限](002-用户组织与权限需求分析.md) | 账户与工作空间归属、成员关系、业务角色、访问和操作授权 | 当前身份、项目参与范围、允许或拒绝的操作决定 |
| [项目与内容创作](003-项目与内容创作需求分析.md) | 建立项目；导入或创作故事；组织单集、场次、分镜和镜头；确认内容基线；识别内容变化 | 可供资产准备和制作使用的内容结构、镜头意图和变更影响 |
| [创作资产管理](004-创作资产管理需求分析.md) | 创建或导入资产；分类；维护身份、版本、来源和权利关联；建立镜头引用；复用并识别变更影响 | 可定位、可引用、可追溯的资产版本与使用关系 |
| [AI 制作与任务管理](005-AI制作与任务管理需求分析.md) | 检查制作条件并匹配可用能力；建立单项或批量任务；记录输入基线、尝试、进度、候选、失败和返工执行 | 可审核的候选结果，以及可恢复、可核对的制作记录 |
| [审核、成片与交付](006-审核成片与交付需求分析.md) | 提交审核；定位意见；通过或退回；形成返工要求；决定采用；组织单集；执行交付门禁 | 正式审核决定、采用关系、单集版本和交付版本 |
| [平台保障与运营](007-平台保障与运营需求分析.md) | 管理额度与用量、成本预算、素材权利、内容安全、AI 标识、异常和运营处置 | 消费记录、保障门禁、风险状态、通知和运营决定 |
| [非功能与技术约束](008-跨模块非功能与技术约束需求分析.md) | 约束性能、可靠性、安全、隐私、追溯、兼容、扩展、运维和总成本 | 后续技术方案必须满足的质量目标与评价证据 |

## 5. 唯一事实归属

同一事实不得由多个模块分别维护：

- REQ-002 负责身份、成员关系、角色和授权决定。
- REQ-003 负责内容结构、叙事关系和当前内容基线。
- REQ-004 负责资产身份、版本、来源和业务引用，不决定候选是否通过。
- REQ-005 负责任务、制作尝试、候选、失败和返工执行，不决定正式采用。
- REQ-006 负责正式审核、采用、单集组成和交付事实。
- REQ-007 负责额度用量、权利安全状态和平台运营处置。

## 6. 模块间业务交接

以下定义业务责任，不预设未来使用接口、事件还是文件交换：

| 交接 | 提供方需要给出 | 接收方需要完成 | 业务结果 |
| --- | --- | --- | --- |
| 身份授权 | REQ-002 给出用户、工作空间、项目角色和操作范围 | 各模块在业务动作前判断是否允许 | 未授权操作不能改变项目事实或产生消费 |
| 内容进入资产准备 | REQ-003 给出已确认内容基线和资产需求 | REQ-004 建立或关联所需资产 | 每个镜头需求能定位到资产准备情况 |
| 内容与资产进入制作 | REQ-003 给出镜头目标；REQ-004 给出引用版本；REQ-007 给出保障状态 | REQ-005 检查条件并建立任务输入基线 | 用户知道能否开始、缺少什么以及预计影响 |
| 候选进入审核 | REQ-005 给出候选、来源、输入和消耗 | REQ-006 建立审核轮次并给出正式决定 | 候选与审核结论不会混淆 |
| 审核退回制作 | REQ-006 给出问题、范围和预期 | REQ-005 建立局部返工；REQ-004 登记新资产版本 | 原结果保留，只重做受影响内容 |
| 采用进入单集 | REQ-006 给出采用关系；REQ-003 给出内容顺序；REQ-004 给出媒体引用 | REQ-006 形成可审单集并复核变化 | 能说明单集实际使用了哪些版本 |
| 单集进入交付 | REQ-006 给出明确单集版本；REQ-007 给出权利、安全和标识状态 | REQ-006 执行交付决定并记录结果 | 交付内容、条件、责任和历史均可追溯 |
| 上游发生变化 | REQ-003 或 REQ-004 给出变化对象和新基线 | REQ-005/006 标识受影响任务、候选、采用和交付 | 用户决定保留、复核或返工，不静默覆盖 |

## 7. MVP 功能闭环

MVP 必须能完成：个人建立项目并输入剧本；整理单集、场次和镜头；准备角色、场景和风格等基础资产；检查条件后进行单镜头和基础批量制作；查看候选、失败、成本与进度；审核并局部返工；组织可完整观看的单集；通过基础权利、安全和 AI 标识检查后，形成用户可获取的单集可审视频交付物。MVP 不承诺该交付物无需外部后期即可直接发行。

暂不作为首轮闭环前提：团队成员生命周期、多集排程、跨项目资产库、开放工作流或模型市场、模型训练、专业后期、外部客户审片和发行运营。

## 8. 判断依据与仍需确认的事项

公开产品与项目呈现出三类稳定事实：[即梦](https://jimeng.jianying.com/)、[RunningHub](https://www.runninghub.cn/)和 [LiblibAI](https://www.liblib.art/)证明单项生成与能力生态有价值；[Jellyfish](https://github.com/Forget-C/Jellyfish)和 [LumenX](https://github.com/alibaba/lumenx)表明短剧需要项目、内容、资产、镜头和任务上下文；[Kitsu](https://github.com/cgwire/kitsu)等影视生产系统表明版本审核、采用和交付关系比单个工具功能更稳定。

进入 `review` 前仍需确认：首发内容形态；用户主要输入是小说、剧本还是创意；单集可审视频的第一种规格及是否需要升级为可发布成片；团队协作是否为首发门槛；角色连续性、时间、成本和工具复杂度中哪个问题最影响付费；外部工具保留在哪些环节。
