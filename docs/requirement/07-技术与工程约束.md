# 技术与工程约束

## 1. 技术基线

| 编号 | P0 约束 |
| --- | --- |
| TCR-001-001 | 仓库必须使用 TypeScript strict、Node.js 24 LTS 和 pnpm workspace，并提交唯一 lockfile。 |
| TCR-001-002 | 应用根目录只允许 `backend/`、`frontend/`、`deploy/`；API、Workflow 和 Worker 均位于 `backend/`。 |
| TCR-001-003 | 前端必须使用 React、Next.js App Router、Tailwind CSS、shadcn/ui、TanStack Query；Zustand 只保存未提交编辑会话。 |
| TCR-001-004 | 后端必须使用 NestJS 模块化单体、Prisma 和 PostgreSQL；PostgreSQL 是业务状态唯一事实源。 |
| TCR-001-005 | 长任务必须使用 Temporal TypeScript SDK；API 与单一 `backend-worker` 独立入口，Workflow 不直接执行 I/O。 |
| TCR-001-006 | API 在同一 PostgreSQL 事务写入 SubmissionSnapshot、ProductionTask、初始 ProductionAttempt、TaskEvent 和 OutboxEvent；Worker 至少一次派发并以 `task/{task_id}` 启动唯一 Workflow。 |
| TCR-001-007 | 媒体必须进入私有 S3 兼容存储，local 使用 MinIO；元数据、哈希、谱系和采用关系保存在 PostgreSQL。 |
| TCR-001-008 | 合成与探测必须由服务端 FFmpeg/ffprobe 完成，使用参数数组而非拼接 Shell；浏览器不是正式渲染器。 |
| TCR-001-009 | HTTP 契约源必须是 OpenAPI 3.1，并生成 `frontend/src/services/generated/`；前端不得手写服务端 DTO。 |
| TCR-001-010 | 任务状态同步通道只有 `GET /v1/tasks/{task_id}` 的 2 秒权威轮询。 |
| TCR-001-011 | Text、Image、Video、TTS 每类能力只能绑定一个服务端静态批准 Adapter，并同时提供确定性 Mock Adapter；Task 受理后能力配置不可变。 |
| TCR-001-012 | Provider 密钥必须来自服务端秘密配置；Workflow、OutboxEvent、数据库业务字段和日志只能保存不可反解引用或脱敏摘要。 |
| TCR-001-013 | 后端模块只允许 `project-catalog/story-development/generation/production-jobs/media-library/delivery`，并统一采用 `domain/application/infrastructure/transport/public`。 |
| TCR-001-014 | 跨模块只能导入 `public/index.ts`；Domain 不得依赖 NestJS、Prisma、Temporal、Provider SDK、S3 或 FFmpeg。 |
| TCR-001-015 | 本地部署必须使用版本化 Compose，服务键集合恰为 `frontend/backend-api/backend-worker/postgres/temporal/minio`；每个服务定义容器内 healthcheck，API/Worker 复用各自唯一 main 入口的 `--healthcheck` 模式，不新增 HTTP Operation。只有 frontend、backend-api、minio 可发布宿主端口且必须显式绑定 `127.0.0.1`，其余服务不得发布宿主端口。 |
| TCR-001-016 | 测试必须使用 Vitest、数据库/Temporal/MinIO 集成测试、Testing Library 和 Playwright；完整 Mock E2E 必须可在 CI 重复执行。 |

## 2. 任务与数据约束

- BR-TCR-001：所有高成本命令要求 `Idempotency-Key`；版本编辑要求 ETag/`If-Match`。
- BR-TCR-002：Task、Attempt、Candidate、Adoption、Delivery 分别建模；不得用一个状态字段代替。
- BR-TCR-003：Provider 提交超时且无法证明未受理时进入 `unknown` 并对账，不得盲目重发。
- BR-TCR-004：Task 终态不可回退；自动重试新建 Attempt，用户重试新建 Task 并引用原 Task。
- BR-TCR-005：媒体对象与版本不可原位覆盖；Provider URL 不得作为永久事实。
- BR-TCR-006：同一 PostgreSQL 服务固定使用隔离数据库 `lanverse`、`temporal` 与 `temporal_visibility`；Prisma 只连接 `lanverse`。初始迁移只在 `lanverse` 增加本文件与 REQ-02～REQ-05 明确要求的业务表/唯一约束及 Prisma 自有 `_prisma_migrations` 元数据；业务模型 allowlist 检查排除该元数据且不得扫描两个 Temporal 数据库。回滚不得执行破坏性 down migration。

## 3. 技术实现边界

技术实现只包含 TCR-001-001～016 与 BR-TCR-001～006 明确要求的运行单元、目录、模块和基础设施。未被活动 Requirement 编号要求的技术对象不得预建。

## 4. 验收标准

- AC-TCR-001：ADR/ARCH/Plan 中的技术、目录、模块和运行单元与 TCR-001-001～016 完全一致。
- AC-TCR-002：架构测试自动检查根目录、模块与 Compose 服务/端口/healthcheck allowlist、public-only、无环依赖和 Workflow 确定性；渲染后的 Compose 配置不存在非 loopback 宿主绑定。
- AC-TCR-003：Plan 必须明确技术族、资源上限、FFmpeg、统一命令，以及“基础精确依赖在 T-001 创建应用源码前锁定、真实 Provider/模型/凭据和必需 SDK 在 T-011 前锁定”的可执行门禁。
