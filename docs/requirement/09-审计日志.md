## 1. 需求说明

### 1.1 背景与目标

平台涉及付费确认、预算、价格、凭据、正式版本选定等关键操作，出现费用争议或结果错误时必须能回答“谁在何时做了什么、改之前是什么”。

### 1.2 用户故事

- 作为**管理员**，我希望按时间、操作人、对象、项目、动作查询审计记录，以便追溯问题与费用。

### 1.3 范围

- 包含：审计写入约定、查询、导出 CSV。
- 不包含：审计告警规则（运维监控负责）、用户行为分析。

## 2. 需求分析

### 2.1 业务流程

```text
业务操作完成 → 系统自动生成审计记录（同一操作只记一次）
管理员 → 审计页面按操作人、对象、动作、时间筛选 → 查看前后值摘要 → 跳转到对象
```

### 2.2 业务规则

| # | 规则 | 理由 |
| --- | --- | --- |
| R1 | 必须审计的动作：登录与账号变更、凭据、注册表与价格、预算、报价确认、取消、人工核对处理、所有选定 / 锁定 / 确认、删除与恢复、成片渲染与下载 | REQ-01 G6 |
| R2 | 审计记录只追加，应用账号无删除与修改内容的权限 | SEC-10 |
| R3 | `before` / `after` 只存摘要（变更字段），不存剧本全文、凭据、预签名 URL | PRV-02 |
| R4 | 记录 `actor_kind`：`user` / `agent` / `system`；Agent 提案由用户确认执行时，actor 为用户，并在 `after` 中记录 `via_agent_proposal_id` | 分清责任 |
| R5 | 保留 3 年 | DAT-03 |

### 2.3 状态

无。

### 2.4 异常与边界

- 消息通道暂不可用：审计延迟写入，但不丢失（REL-07）。
- 登录失败等不改变业务数据的动作同样必须留下审计记录。

### 2.5 前置与依赖

所有业务操作都通过统一的事件机制记录（DES-01 事件与实时）。

## 3. 验收标准

- Given 制作者选定了镜头 3 的视频候选，When 管理员按项目与“选定”操作筛选审计日志，Then 能看到该记录，包含操作人、时间、镜头与候选标识。
- Given 任意一次报价确认，When 查询审计，Then 存在 `operation.confirmed` 记录，包含金额与确认人。
- Given 应用数据库账号，When 尝试 `UPDATE audit.audit_log SET after = …`，Then 被数据库拒绝。
