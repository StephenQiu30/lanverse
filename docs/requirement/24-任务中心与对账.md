## 1. 需求说明

### 1.1 背景与目标

生成是异步、付费、依赖外部供应商的。网络超时时，“请求到底有没有被受理”是未知的——盲目重试可能重复扣费。必须有一个地方看清所有任务的状态、原因与费用；对“结果未知”先查询真实状态；无法查询时交给人工核对。

### 1.2 用户故事

- 作为**制作者**，我希望在一个地方看到所有生成任务的状态，筛选失败与异常任务，并取消不需要的任务。
- 作为**制作者**，我不希望因为网络问题被重复扣费。
- 作为**管理员**，我希望处理无法自动对账的任务，并据此正确结算。

### 1.3 范围

包含：任务列表与详情、实时状态、取消、结果未知对账、待人工核对处理、卡死任务检测。不包含：执行细节（DES-04）。

## 2. 需求分析

### 2.1 业务流程

```text
提交供应商：
  明确受理 → submitted → 轮询 → 成功 / 失败
  明确拒绝（4xx 参数错误等）→ failed（可重试标记按错误码）
  超时 / 连接中断 / 5xx 且无法确定 → unknown → 对账：
      supports_query：按 provider_request_key 查询 → 查到 → 按真实状态继续；确认不存在 → failed(retryable, 未扣费)
      不支持查询 → manual → 通知管理员 → 管理员在供应商控制台核实 → resolve-manual（已成功附任务 ID / 未执行）
取消：
  quoted / confirmed（未提交）→ cancelled，全额释放
  submitted 且 supports_cancel → 调用取消 → cancelled，按供应商实际计费结算
  submitted 且不支持取消 → 标记“取消请求中”，结果仍会到达并入库为候选（已付费），状态显示“已完成（取消未生效）”
```

### 2.2 业务规则

| # | 规则 | 理由 |
| --- | --- | --- |
| R1 | 状态：排队中、进行中、成功、失败（附原因）、结果未知、待人工核对、已取消（REQ-03 §6.5） | GEN-04 |
| R2 | 付费请求只在“确定未提交”时自动重试；结果未知永不自动重新提交 | GEN-06、REL-02 |
| R3 | 每次对供应商的调用（提交、查询、取消、回调）记录到 `provider_call` | OBS-05 |
| R4 | 进行中超过模型 `expected_max_ms × 2` 进入对账；`manual` 超过 24 小时告警 | REL-10 |
| R5 | 失败原因使用平台错误码 + 中文说明 + 是否可重试；原始供应商错误只给管理员看 | USE-02 |
| R6 | 人工核对只能由管理员处理，必须填写依据（供应商任务 ID 或说明），写审计 | 费用争议可追溯 |
| R7 | 列表可按项目、集、能力、模型、状态、来源、时间筛选；默认显示当前项目 | GEN-04 |

### 2.3 状态

对用户展示状态与内部状态映射见 [DES-02 §7](../design/02-领域与数据模型.md#7-状态字段与-req-03-状态模型的映射)。

### 2.4 异常与边界

- 服务重启：工作流恢复，前端 SSE 重连后补齐（AVL-04）。
- 供应商回调与轮询同时到达：以工作流内的单线程处理顺序为准，结果幂等写入。
- 供应商返回结果链接已过期：重新查询获取新链接；仍失败则 `failed(final)` 并按供应商计费结算（需人工申诉，记录说明）。

## 3. 实现所需

### 3.1 数据

| 表 | 关键字段 | 为什么需要 |
| --- | --- | --- |
| `operation.operation` | `status`、`failure_code/message`、`retryable`、`started_at`、`finished_at`、`provider_request_key`、`workflow_id` | 状态与对账键 |
| `operation.provider_call` | `action`、`attempt`、`outcome`、`provider_task_id`、`http_status`、`usage`、`cost_micros`、`latency_ms` | 调用明细、对账依据 |
| 索引 `ix_operation_inflight` | 进行中扫描 | 卡死检测 |

新增 `operation.operation_event`（状态变更历史：`from_status`、`to_status`、`reason`、`create_time`），用于详情页时间线（DES-02 同步）。

### 3.2 接口

```http
GET /api/projects/{pid}/operations?status=failed&status=unknown&capability=video.generate&episode_id=…&limit=50
200 { "items": [ { "id": "…", "target_label": "第1集 3-12 片段", "capability": "video.generate", "model_key": "…",
                   "status": "failed", "status_label": "失败", "failure": { "code": "provider_content_rejected", "message": "供应商内容审核未通过", "retryable": false },
                   "quote_micros": 20000000, "settled_micros": 0, "origin": "batch", "batch_id": "…",
                   "create_time": "…", "elapsed_ms": 81234 } ], "next_cursor": "…" }

GET  /api/operations/{id}         → 输入、参数、提示词、状态时间线、provider_calls（普通用户脱敏）、输出、费用
POST /api/operations/{id}:cancel  → 200 { "status": "cancelling" | "cancelled" }
POST /api/operations/{id}:retry   → 新报价（REQ-21）
POST /api/operations/{id}:resolve-manual   （管理员）
{ "outcome": "succeeded", "provider_task_id": "cgt-2026…", "note": "控制台已确认成功" }
→ 工作流收到信号：succeeded 则查询并接管结果；not_executed 则 failed 并全额释放
```

### 3.3 异步与工作流

OperationWorkflow 的提交、轮询、对账、取消、人工核对分支见 DES-04；`InflightWatchdogSchedule`（每 5 分钟）检测 R4 并向工作流发送 `reconcile` 信号。

### 3.4 事件与实时

`operation.status_changed.v1`（realtime、storyboard-progress）；`operation.manual.v1`（notify 管理员）；SSE `operation.updated`。

### 3.5 界面

任务中心表格（筛选栏、状态徽标、进度、费用、耗时、操作：取消 / 重试 / 查看）；详情抽屉（时间线、输入缩略图、调用明细、费用）；管理员“待人工核对”视图与处理表单。

### 3.6 权限与审计

制作者可查看、取消、重试；管理员另可处理人工核对。审计：`operation.cancelled`、`operation.manual_resolved`。

### 3.7 非功能要求

REL-01、REL-02、REL-10；AVL-04；OBS-05；PERF-03。

## 4. 验收标准

- Given 任务进行中时服务重启，When 服务恢复后刷新任务中心，Then 任务状态正确并继续推进。
- Given 模拟供应商提交超时但实际已受理，When 对账完成，Then 任务状态与供应商一致，账本只记录一次费用。
- Given 排队中的任务，When 取消，Then 状态为已取消，预留全部释放。
- Given 不支持查询的供应商提交超时，When 查看任务，Then 状态为“待人工核对”，管理员收到通知；处理为“未执行”后预留全部释放。

## 5. 测试要点

模拟供应商（REQ-02 DEP-06）注入：超时但已受理、超时且未受理、重复回调、结果链接过期、查询接口 5xx；每种场景断言状态与账本。
