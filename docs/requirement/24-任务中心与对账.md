## 1. 需求说明

### 1.1 背景与目标

生成是异步、付费、依赖外部供应商的。网络超时时，“请求到底有没有被受理”是未知的——盲目重试可能重复扣费。必须有一个地方看清所有任务的状态、原因与费用；对“结果未知”先查询真实状态；无法查询时交给人工核对。

### 1.2 用户故事

- 作为**制作者**，我希望在一个地方看到所有生成任务的状态，筛选失败与异常任务，并取消不需要的任务。
- 作为**制作者**，我不希望因为网络问题被重复扣费。
- 作为**管理员**，我希望处理无法自动对账的任务，并据此正确结算。

### 1.3 范围

包含：任务列表与详情、实时状态、取消、结果未知对账、待人工核对处理、卡死任务检测。不包含：执行细节（DES-04）。

## 2. 需求分析

### 2.1 业务流程

```text
提交供应商：
  明确受理 → submitted → 轮询 → 成功 / 失败
  明确拒绝（4xx 参数错误等）→ failed（可重试标记按错误码）
  超时 / 连接中断 / 5xx 且无法确定 → unknown → 对账：
      supports_query：按 provider_request_key 查询 → 查到 → 按真实状态继续；确认不存在 → failed(retryable, 未扣费)
      不支持查询 → manual → 通知管理员 → 管理员在供应商控制台核实 → resolve-manual（已成功附任务 ID / 未执行）
取消：
  quoted / confirmed（未提交）→ cancelled，全额释放
  submitted 且 supports_cancel → 调用取消 → cancelled，按供应商实际计费结算
  submitted 且不支持取消 → 标记“取消请求中”，结果仍会到达并入库为候选（已付费），状态显示“已完成（取消未生效）”
```

### 2.2 业务规则

| # | 规则 | 理由 |
| --- | --- | --- |
| R1 | 状态：排队中、进行中、成功、失败（附原因）、结果未知、待人工核对、已取消（REQ-03 §6.5） | GEN-04 |
| R2 | 付费请求只在“确定未提交”时自动重试；结果未知永不自动重新提交 | GEN-06、REL-02 |
| R3 | 每次对供应商的调用（提交、查询、取消、回调）记录到 `provider_call` | OBS-05 |
| R4 | 进行中超过模型 `expected_max_ms × 2` 进入对账；`manual` 超过 24 小时告警 | REL-10 |
| R5 | 失败原因使用平台错误码 + 中文说明 + 是否可重试；原始供应商错误只给管理员看 | USE-02 |
| R6 | 人工核对只能由管理员处理，必须填写依据（供应商任务 ID 或说明），写审计 | 费用争议可追溯 |
| R7 | 列表可按项目、集、能力、模型、状态、来源、时间筛选；默认显示当前项目 | GEN-04 |

### 2.3 状态

对用户展示状态与内部状态映射见 [DES-02 §7](../design/02-领域与数据模型.md#7-状态字段与-req-03-状态模型的映射)。

### 2.4 异常与边界

- 服务重启：工作流恢复，前端 SSE 重连后补齐（AVL-04）。
- 供应商回调与轮询同时到达：以工作流内的单线程处理顺序为准，结果幂等写入。
- 供应商返回结果链接已过期：重新查询获取新链接；仍失败则 `failed(final)` 并按供应商计费结算（需人工申诉，记录说明）。

## 3. 验收标准

- Given 任务进行中时服务重启，When 服务恢复后刷新任务中心，Then 任务状态正确并继续推进。
- Given 模拟供应商提交超时但实际已受理，When 对账完成，Then 任务状态与供应商一致，账本只记录一次费用。
- Given 排队中的任务，When 取消，Then 状态为已取消，预留全部释放。
- Given 不支持查询的供应商提交超时，When 查看任务，Then 状态为“待人工核对”，管理员收到通知；处理为“未执行”后预留全部释放。
