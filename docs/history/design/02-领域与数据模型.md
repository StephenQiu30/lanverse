## 1. 设计决策

| #   | 决策                                                                                                                                                                                                                                                                                                                                       | 理由                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| D1  | 一个业务库，**按限界上下文分 schema**（`identity`、`workspace`、`script` …）                                                                                                                                                                                                                                                               | 模块化单体：边界清晰、可单独迁移与授权；将来拆服务时按 schema 拆库                                            |
| D2  | 主键使用 **UUIDv7**，由应用生成                                                                                                                                                                                                                                                                                                            | 时间有序，索引局部性好；前端、工作流、幂等键可提前拿到 ID                                                     |
| D3  | 枚举用 `text + CHECK`，不用 PostgreSQL `ENUM`                                                                                                                                                                                                                                                                                              | 增加取值只需迁移 CHECK，不锁表、可回滚                                                                        |
| D4  | 时间统一 `timestamptz`（存 UTC）；时长统一 `integer` 毫秒（`*_ms`）                                                                                                                                                                                                                                                                        | 与 REQ-02 I18N-02 一致；避免浮点误差                                                                          |
| D5  | 金额统一 `bigint` **微元**（1 元 = 1,000,000，`*_micros`），界面显示到分                                                                                                                                                                                                                                                                   | LLM 按 token 计费的单次金额常低于 1 分；整数避免浮点误差                                                      |
| D6  | **“头 + 版本”模式**：可变身份放头表（含 `revision` 乐观锁），不可变内容放版本表                                                                                                                                                                                                                                                            | 满足 REQ-02 REL-05 版本不可变、REL-06 并发修改                                                                |
| D7  | 选定与锁定是**头表上的指针**，同时写一条只追加的历史记录                                                                                                                                                                                                                                                                                   | 查询当前选定只需一次读取；历史可审计                                                                          |
| D8  | 跨上下文只存对方 ID，**不建跨 schema 外键**；同一 schema 内建外键                                                                                                                                                                                                                                                                          | 保持上下文可拆分；一致性由命令层与事件保证                                                                    |
| D9  | 结构不稳定、只整体读写的数据用 `jsonb`（模型参数、参数表单定义、质检结果），并在应用层按 schema 校验                                                                                                                                                                                                                                       | 模型参数随供应商变化；避免频繁迁移                                                                            |
| D10 | 表的作用域分四类，以 `backend/db/schema.sql` 为已实施表级依据：① 项目级表带 `project_id NOT NULL`，仓储查询强制带项目；② `project_id` 可空的表（如通知、审计、风格预设）按用户与组织授权，带项目时再按项目过滤；③ 子表不带 `project_id`，经父对象外键继承项目范围；④ 组织 / 平台级表（账号、目录、基础设施）按管理员权限。MVP 固定一个组织 | DES-01 §3.3                                                                                                   |
| D11 | **所有表统一带 `is_delete` 逻辑删除标志**；项目与媒体另有 `delete_time`、`purge_after` 支持 30 天回收；版本内容仍靠“新版本”表达修改，不靠删除                                                                                                                                                                                              | REQ-01 PRJ-06、MED-03                                                                                         |
| D12 | 高增长的只追加表（审计、Outbox、调用明细）按月**分区**                                                                                                                                                                                                                                                                                     | 审计等按整月保留期删除分区（REQ-02 DAT-03）；短于一个月的 Outbox 保留期按行清理，未投递事件不能因分区过期丢失 |

## 2. 通用约定

### 2.1 命名

- schema、表、列使用 `snake_case`；表名单数（`shot`、`shot_version`）。
- 外键列 `<对象>_id`；指向版本的列 `<对象>_version_id`；布尔列 `is_*` / `has_*`。
- 索引 `ix_<表>_<列>`，唯一约束 `uq_<表>_<列>`，检查约束 `ck_<表>_<含义>`。

### 2.2 必备列与通用列

**目标通用列**（供后续设计使用；已实施表的实际列与例外以 Schema 为准）：

| 列            | 类型                                 | 说明                                                           |
| ------------- | ------------------------------------ | -------------------------------------------------------------- |
| `id`          | `uuid PRIMARY KEY`                   | UUIDv7，应用生成；按月分区表为 `PRIMARY KEY (id, create_time)` |
| `create_time` | `timestamptz NOT NULL DEFAULT now()` | 创建时间                                                       |
| `update_time` | `timestamptz NOT NULL DEFAULT now()` | 最后修改时间；每次 `UPDATE` 由仓储统一设置（并有触发器兜底）   |
| `is_delete`   | `boolean NOT NULL DEFAULT false`     | 逻辑删除标志                                                   |

**通用列（按需出现）**：

| 列                        | 类型                         | 出现在                                          |
| ------------------------- | ---------------------------- | ----------------------------------------------- |
| `project_id`              | `uuid NOT NULL`              | 所有项目级表                                    |
| `org_id`                  | `uuid NOT NULL`              | 组织级表                                        |
| `create_by` / `update_by` | `uuid`                       | 由用户操作产生或修改的表（系统产生时为空）      |
| `revision`                | `integer NOT NULL DEFAULT 1` | 头表；每次修改 +1；命令携带 `expected_revision` |

**`is_delete` 使用规则**：

1. 仓储查询显式携带当前作用域与 `is_delete = false` 条件；不使用 GORM 的 `DeletedAt` 自动处理业务逻辑删除。
2. 业务唯一约束、常用索引一律写成部分索引 `… WHERE NOT is_delete`，保证删除后可以重建同名对象。
3. 版本表、只追加表（`*_version`、`reference_version`、`dialogue_audio`、`ledger_entry`、`audit_log`、`outbox` 等）的内容列不允许更新；`is_delete` 只在项目彻底清理时由清理任务置位，`update_time` 同步更新。
4. 删除头表对象（如镜头）时，只置位头表的 `is_delete`；其版本行保留，供历史与审计查询。
5. 物理删除只发生在：项目回收期满清理、分区表过期分区删除、已投递 `outbox` 行及 `processed_event` / `idempotency_record` 过期清理（§9）。

### 2.3 通用枚举

| 名称                     | 取值                                                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 审阅状态 `review_status` | `candidate`（待确认）· `confirmed`（已确认）                                                                                |
| 任务状态（界面）         | 见 REQ-03 §6.5；数据库使用 §7 的 Operation 内部状态                                                                         |
| 服务区域 `region`        | `domestic` · `overseas`                                                                                                     |
| 输入用途 `input_role`    | `prompt` · `first_frame` · `last_frame` · `subject` · `scene` · `prop` · `style` · `motion` · `camera` · `audio` · `source` |
| 引用类型 `ref_type`      | `reference_version` · `media_asset` · `dialogue_audio` · `operation_output` · `style_preset` · `text`                       |

## 4. 版本、选定与依赖模式

### 4.1 头 + 版本

```text
shot（头）                     shot_version（版本，只插入）
  id, revision                   id, shot_id, version_no, 内容字段…
  current_version_no ──────────→ (shot_id, version_no) 唯一
  selected_take_output_id        create_time, create_by
```

**修改流程**（一个事务）：

1. `SELECT … FROM shot WHERE id = $1 FOR UPDATE`；`revision` 不等于 `expected_revision` → 返回冲突。
2. 插入 `shot_version(version_no = current_version_no + 1)` 及其子表（`shot_line`、`reference_item`）。
3. 更新头表 `current_version_no`、`revision = revision + 1`、`update_time`。
4. 写 `lineage.dependency`（新版本的上游）与 `infra.outbox`（`storyboard.shot_version_created`）。

使用此模式的对象：`script_version`（无头，天然不可变）、`episode_structure`、`reference_version`、`shot_version`、`model_profile_version`、`price_rule_version`。

### 4.2 选定与锁定

- 选定指针在头表：`shot.selected_frame_output_id`、`shot.selected_take_output_id`、`reference_slot.current_version_id`、`line_audio_selection.dialogue_audio_id`。
- 选定命令携带 `expected_revision`，更新指针与 `revision`，同时插入历史（`shot_selection_log`、`reference_version` 本身即锁定历史）。
- 被选定的 `operation_output` 必须 `moderation_status = 'passed'`，且其 Operation 状态为 `completed`。

### 4.3 稳定键（跨版本的同一对象）

剧本结构每次修改都产生新的 `episode_structure` 版本和新的行，但分镜需要引用“同一句台词”。因此：

- `scene.scene_key`、`dialogue_line.line_key` 为稳定 UUID：新版本中未改变身份的场与台词沿用原键，新增的生成新键，拆分时一方沿用、另一方新键。
- `dialogue_line.content_hash` = hash(说话人, 文本, 情绪)。新版本中同一 `line_key` 的 `content_hash` 变化即视为该台词被修改。
- `shot_line` 引用 `line_key`（而不是行 ID），配音选定 `line_audio_selection` 也以 `(episode_id, line_key)` 为键。

### 4.4 依赖与过期

```text
lineage.dependency
  downstream_type  shot_version | reference_version | dialogue_audio | operation_output
  downstream_id    下游版本 ID
  upstream_type    dialogue_line | reference_version | shot_version | dialogue_audio | operation_output | voice_profile
  upstream_key     上游稳定键（line_key / reference_slot_id / shot_id / (episode_id,line_key) …）
  upstream_version 下游创建时所依赖的上游版本号或 content_hash
```

- **登记**：下游版本创建时，把它读取的每个上游（稳定键 + 当时的版本）写入 `dependency`。
- **传播**：上游产生新版本或新选定时发出事件；`lineage` 消费者查询 `upstream_key = 该键 AND upstream_version <> 新版本` 的下游，为其**当前生效的对象**写入 `stale_mark`，再沿依赖递归（递归 CTE，深度上限 6）。
- **清除**：下游重新产生新版本（依赖已是最新）时，旧对象的 `stale_mark.cleared_at` 置位。
- 过期只是标记，不修改任何业务数据（REQ-01 LIN-01）。

## 5. 模块数据职责与目标规划

当前实现统一写入 `backend/db/schema.sql`。本节定义当前模块职责与计划实施的业务约束；实施业务时同步更新 Schema，不根据规划预建表。

### 5.1 identity

账号数据承载组织范围、账号状态与会话纪元；当前账号表的字段、唯一性和目录索引以 Schema 为准。

会话存 Redis（`sess:{token_hash}` → user_id、session_epoch、过期时间），不落库；校验时比较 `session_epoch`（REQ-01 ACC-03）。

### 5.2 workspace

组织、项目与风格预设构成项目聚合；当前目录分类、主图、生命周期命令与完整复制的永久回执同属 workspace 边界，具体对象与权限以 Schema 为准。

画幅、风格类型的不可修改由命令层保证，并由触发器兜底（§12）。项目选择预设时，命令层还须校验预设与项目属于同一组织，且预设是组织级或属于当前项目；单列外键只保证预设存在，不能代替这项授权。项目级预设与项目相互引用，彻底清理时先解除项目的预设指针，再删除项目级预设和项目。`resolution` 在数据库层固定为 `1080p`（REQ-10 R3），项目常用索引按 §2.2 排除逻辑删除行。

### 5.3 catalog

供应商、封装凭据、能力字典、模型头及模型/价格版本构成目录与报价输入；实际字段、版本保护和单活凭据约束以 Schema 为准。

模型与价格版本的目标业务约束：`model_profile.current_version_id` 只能引用同一模型的版本；模型和价格版本号必须为正，`limits` 与 `rule` 必须为 JSON 对象，`param_schema` 必须为 JSON 数组；非人民币价格必须记录正的 `fx_rate_to_cny`。供应商模型数量按未逻辑删除的 `model_profile` 计数，并为 `provider_id` 建索引。版本表的只追加规则仍由写入命令执行。

### 5.4 script

剧本业务合同以 [工作台剧本设计](工作台设计.md) 为准：script_source 为不可变来源快照、稳定 lineage/previous source/revision，原件与 rich/text 私有对象分别存证；project_state 持有 draft/adopted 头和 CAS。正文/rich 哈希各自索引，不能按纯文本唯一抹掉格式或来源变化。已实现结构由 Schema 描述；下游和 AI 能力按各自业务设计实施与验收。

来源快照、版本/分集、结构解析、导入和复制回执由 script 模块持有。当前已实施对象以 Schema 为准；本文不维护另一份表结构。

### 5.5 bible

人物、场景、道具、造型、参考与音色保留对象身份和不可变版本，确认、拆分、合并与复制的永久事实由 bible 模块持有。实际表与边界以 Schema 为准。

### 5.6 storyboard

计划实现：场分镜、镜头头/版本、台词分配、参考组合、模板与选定历史。尚未实施的对象须在业务设计与实现一同通过后进入 Schema。

“一集中每句台词只分配一次”（REQ-01 SB-01）在确认场分镜时由应用校验：该场所有镜头当前版本的 `shot_line.line_key` 无重复，且覆盖该场全部 `line_key`。

### 5.7 operation

批次、操作、冻结输入、报价/确认回执、候选结果、状态历史与供应商调用支撑生成状态机。当前发送证据与工作流保护以 Schema 和对应生成设计为准。

`dispatch_started_at` 与 `receipt` 保存可空的发送证据，结构由 Schema 描述；空值不能证明未发送，不回填未经确认的执行事实。`request_summary.dispatch_contract=v1` 标识采用发送门禁的调用；分区表通过 Operation 行锁与唯一调用行校验串行登记。receipt 的封闭字段、身份、4 KiB/单图/32 MiB 限制及成本 NULL 语义以 [生成执行设计 §5.1](生成执行设计.md#51-同步调用证据与发送门禁) 为准。未核定费用或待恢复的付费证据不得因普通分区保留期删除；清理能力须按此保护条件实现与验收。

`input_hash` = sha256(canonical_json(version=1, capability, mode, model_profile_version_id, provider_model_id, output_count, 规范化 params, 按 seq 排序的 (role, ref_type, ref_id, ref_version, 直接媒体与遮罩的素材 ID、媒体 sha256（含遮罩）、冻结文本), 最终提示词))。直接素材输入即使内容摘要相同，素材身份不同也不能误判为同一输入。

### 5.8 media

正式 document 原件业务合同限定为真实 TXT/DOCX，1..20 MiB、完整 SHA256、扩展名/MIME/codec 相符且无 AV 属性，实际约束以 Schema 为准；所有 owning 读和完整复制均验证这些事实，既有数据须在升级时验证与保留。原件存私有 bucket，经 durable upload 的版权与审核接管，下载实际核验字节。

正式原件、衍生物、上传、素材库、传输/清理/打包与媒体工具回执由 media 模块持有；未实施的授权记录等目标不可预建。当前类型约束、scope、触发器和权限以 Schema 为准。

引用保护（REQ-01 MED-03）：删除前查询所有引用（`reference_version`、`reference_item` 当前版本、`shot` 选定、`line_audio_selection`）；由 `media` 模块的 `ReferenceChecker` 端口聚合各上下文实现。

### 5.9 audio

计划实现台词音频候选、逐句 TTS 参数覆盖与当前选定指针；对应业务实施时再更新 Schema。

### 5.10 billing

预算、预留与只追加账本持有费用事实；成本汇总与对账运行属于后续规划，当前字段、余额保护和写入权限以 Schema 为准。

预留与结算在同一事务中更新 `budget`（行锁）、`reservation`、`ledger_entry`；`ck_budget_balance` 保证未标记超支时不超上限（超支只能由结算事实触发，DES-04 §7）。

### 5.11 lineage、notify、audit、infra

Outbox、消费去重与幂等回执支撑可靠命令/事件，审计持有只追加操作事实；依赖传播和站内通知按各自业务设计继续实施。实际表、分区与最小权限以 Schema 为准。

### 5.12 canvas

文档、节点、边与命令日志保存正式画布状态；工具/复制的永久快照与回执按 owning 模块边界持有。当前对象由 Schema 描述，后续快照等规划不得自动建表。

### 5.13 agent

计划实现会话、运行、消息与提案，Go 内的 Agent 模块边界以专项设计为准；对应业务实施时再更新 Schema。

## 10. Schema 事实源、初始化与升级

1. 结构变更直接更新 `backend/db/schema.sql` 的最终态定义，同时更新 owning 仓储/类型和有风险的结构合同测试；不追加 up/down 文件，不维护 Markdown、GORM 模型或测试夹具中的第二份建表实现。
2. Schema 只描述当前已实现对象；未实施设计继续留在本文及专项设计，不预建未来表、列或权限。生产禁止 GORM AutoMigrate（REQ-02 MNT-04）。
3. 新空业务库由表所有者执行 `psql "$LV_SCHEMA_DB_DSN" -X --single-transaction -v ON_ERROR_STOP=1 -f backend/db/schema.sql`；`LV_SCHEMA_DB_DSN` 由受控部署环境提供，不复用应用账号。由调用方统一保证事务；文件不包含顶层 `BEGIN/COMMIT`；失败须整体回滚，重复执行或对既有业务结构执行须拒绝。执行前由管理员预置集群级 `lanverse_app NOLOGIN NOSUPERUSER`，Schema 只授予所需权限，不创建登录账号或写入凭据。
4. 既有业务库先确认实例、已有结构、备份与未收敛工作，再比较部署版本 Schema 和当前实例；形成精确、可审阅的增量升级 SQL，验证后显式执行。增量是特定发布/实例的执行证据，目标结构仍只由 Schema 定义，不形成另一套常驻迁移事实源。不得重跑 Schema、down/up、清空或重建库升级。
5. 升级须**向前兼容一个版本**（REQ-02 DEP-03）：加列先可空 → 回填 → 加约束；删列先停用，再明确批准删除；大表索引和回填使用适合实例的独立步骤，例如 `CREATE INDEX CONCURRENTLY` 不能放入初始化事务。
6. Outbox、审计与供应商调用初始化分区以执行时 UTC 当前月为基准创建当前及未来三个月；后续 Outbox/审计仍由现有维护命令按月预备；计划补充供应商调用的周期分区维护与自动维护 Schedule，并验证后续月份的分区准备；初始化窗口不代表持续维护已启用。不得把固定日期分区写成永久事实。
7. CI 与普通真实 PostgreSQL 合同库只执行 Schema 初始化，`psql -X --single-transaction -v ON_ERROR_STOP=1` 或 Go 外层事务保证原子性；结构、不可变/只追加保护与实际受限角色行为须验证。既有库的升级演练单独记录实例前置状态、增量内容、执行与保留证据，空库初始化成功不替代升级或产品验收。历史脚本与历史验收从 Git 检索，不在当前目录保留迁移实现。

## 11. 仓储实现约定

- GORM 模型只在 `adapter/postgres` 中定义；领域对象与 GORM 模型显式转换（DES-01 §3.3）。
- 头表更新统一使用 `UPDATE … SET revision = revision + 1 WHERE id = ? AND revision = ?`，影响行数为 0 即冲突。
- 命令事务边界在应用层用例：业务写入 + `lineage.dependency` + `infra.outbox` + `audit`（经 Outbox）同一事务。
- 列表查询一律 keyset 分页；禁止 `OFFSET` 深分页。
- 递归查询、报表使用 Raw SQL，并有集成测试（testcontainers）。

## 12. 数据库层保护目标

下表描述业务保护目标，当前实际函数、触发器、约束与授权统一查阅 Schema；未实施表的保护目标不表示已接线。

| 保护                   | 实现                                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 版本表内容不可改       | 应用账号对 `*_version`、`reference_version`、`dialogue_audio`、`ledger_entry` 只授予 `INSERT, SELECT` 与 `UPDATE (is_delete, update_time)` 列级权限；迁移账号另设 |
| 审计日志只追加         | 非表所有者的应用账号对 `audit.audit_log` 仅有 `INSERT, SELECT`，不得持有 `UPDATE, DELETE, TRUNCATE` 或表所有权；分区维护与归档使用独立高权限账号                  |
| `update_time` 自动维护 | 每张表 `BEFORE UPDATE` 触发器 `set_update_time()` 兜底                                                                                                            |
| 项目画幅与风格不可改   | `BEFORE UPDATE` 触发器：`aspect_ratio`、`style_type` 变化即报错                                                                                                   |
| 预算不超支             | `ck_budget_balance`                                                                                                                                               |
| 每个活跃凭据唯一       | `uq_provider_credential_active`                                                                                                                                   |
| 连接                   | 应用使用 PgBouncer（事务模式）；Temporal 使用独立库与账号                                                                                                         |
