> Review ID：REV-REQ-001

## 1. 审核结论

M01—M15 已具备进入详细设计和实施拆解的条件。模块体系覆盖从来源、知识、镜头、外部生成、媒体、质量、审阅到交付的完整生产闭环，没有发现需要推翻整体产品结构的阻断性缺陷。

本轮发现 8 项跨模块语义问题，均已在 Requirement 和上游 Design 中修正。剩余事项是可配置试点参数、真实 Provider 证据和产品负责人签认，不属于继续写文档即可消除的需求缺陷。

## 2. 审核方法

每个模块按以下 Gate 检查：

1. 用户结果是否明确，是否与商业计划、技术实现和非目标分离；
2. 模块是否只有一个权威事实所有者，跨模块对象是否通过稳定 ID/版本引用；
3. 正常流程、状态、并发、幂等、失败、取消、恢复和人工接管是否闭合；
4. AI 提案、人工事实、外部执行、候选选择、风险决定和交付快照是否分离；
5. P0 功能是否有可观察验收，NFR 是否可形成测试或容量 Gate；
6. 权限、数据外发、资源上限、敏感信息、保留和审计是否覆盖所有入口；
7. 上游变化是否说明影响、过期和最小重算，而不是静默级联；
8. 是否能落入 A—F 纵向切片，而不是要求先建设 15 个完整服务。

## 5. 非缺陷但必须签认的事项

以下事项不会阻止 Design/PRD/Plan，但会阻止相应切片进入 `accepted` 或真实上线：

1. 首批用户、试点规模和正式交付预设；
2. 首批 Provider 的幂等、查询、取消、数据保留和计量证据；
3. 真人肖像、品牌、未公开 IP、地域和模型训练限制；
4. 默认批准矩阵、双人批准动作和外部审片下载权限；
5. 容量目标、对象/媒体上限、RPO/RTO 和 Python 性能基线；
6. PDF/OCR、完整画布、SSO/SCIM、私有模型、公开 API 和 NLE 交换格式的启用 Gate。

这些项必须进入 PRD 的假设与 Gate，不得隐藏在代码默认值中。

## 6. 下游拆分决策

- Requirement 按 M01—M15 保持“一个功能模块一份”，继续作为用户结果和验收事实源；
- Design 按 M01—M15 一一拆分，负责对象、命令、状态、接口、故障和测试设计；
- PRD 不重复抄写 15 份 Requirement，而按 A—F 纵向可交付切片组织用户旅程、范围、页面和发布 Gate；
- Plan 与 PRD 一一对应，按可验证工作包和依赖执行，不按模块建设 15 个服务；
- 追踪矩阵必须能从每个 Requirement ID 找到 Module Design、Slice PRD、Plan 和验收证据位置。

## 7. 审核签认

当前结论仅代表专业产品/架构审计完成：内部冲突已消除，可进入设计。产品负责人接受首轮试点基线后，Requirement 才能从 `reviewed` 进入 `accepted`；真实验收证据完成后才进入 `verified`。
