# DES-000 项目顶层结构与工程规范

- 状态：proposed
- 版本：v1.1
- 日期：2026-08-19
- 设计范围：目标仓库结构、依赖方向、契约、配置、测试和交付门禁
- 上游：[CUR 当前需求集](../requirement/README.md)、[DES-001 目标技术架构与选型](./001-目标技术架构与选型.md)
- 下游：DES-002～DES-015、后续 Plan、Acceptance

## 1. 问题与设计结论

当前需要为一款 AI 短剧制作平台建立可长期维护的工程边界。工程结构必须支持剧本、资产、分镜、关键帧、逐镜视频和素材包导出，又不能因 Provider、长任务和大媒体复杂度过早拆成微服务。设计必须以当前真实运行栈为约束，同时保留后续演进空间。

本设计提出：

1. 采用一个 Git 仓库，目标源码与文档只设 `frontend/`、`backend/`、`docs/` 三个主要项目目录；部署清单只有在真实部署入口确定后才按需增加。
2. 后端是一个 Python 模块化单体代码库，当前使用 FastAPI、SQLAlchemy、Pydantic 和 Python Worker；API、Production Harness、LangGraph Skill 与异步 Worker 通过公开领域端口交接。
3. 前端是 TypeScript React/Next.js 工作台，通过 OpenAPI 生成的客户端调用 API；服务端任务状态通过 SSE 获取，轮询作为降级。
4. 领域模块按事实所有权组织，禁止以 Controller、Service、Model 等技术分层作为仓库顶层边界。
5. 目录图是目标约束，不是一次性创建空目录、兼容层或未来服务的授权。

该结论仍需随 [DES-001](./001-目标技术架构与选型.md) 中的 ADR 与故障 PoC 一并评审，在 accepted 前不得被表述为已完成生产验证的事实。

## 2. 范围与非目标

### 2.1 范围

- 源码、测试、生成代码与文档的目录职责；
- API/Worker 的依赖方向和组合入口；
- Plain Data Contract、OpenAPI、事件和数据库迁移规则；
- 配置、Secret、媒体样本和生成物治理；
- 质量、架构、集成、安全和交付门禁；
- 与 DES-002～DES-015 的事实源关系。

### 2.2 非目标

- 不定义剪辑、时间线、Clip、Render、成片、字幕或音频后期模块；
- 不定义订阅、支付、客户账单、营销或商业运营模块；
- 不为未来微服务、Kubernetes、模型市场、实时多人协作预建目录；
- 不固定未经 ADR/PoC 接受的框架小版本、云厂商和 Provider；
- 不把当前仓库已有页面实现自动认定为产品需求；但当前 Python 运行栈、已存在的任务事实和 LangGraph Harness 是架构兼容约束，除非另行批准后端重写。

## 3. 目标仓库结构

```text
Lanverse/
├── .github/                     # CI 与仓库规则相关配置
├── backend/                     # Python FastAPI API + Worker 模块化单体
├── frontend/                    # TypeScript React/Next.js 工作台
├── docs/                        # Research、Requirement、Design、Plan、Acceptance
├── .editorconfig
├── .env.example                # 仅公开配置名和安全占位
├── .gitignore
├── AGENTS.md                   # 长期协作规则，不承载业务事实
├── LICENSE
```

只有出现已接受的部署用例后才允许新增语义明确的 `deploy/`；不得先放空 Helm、Terraform 或环境副本。根目录不得存储本地数据库、对象存储数据、媒体、Prompt 样本、日志、报表或 Secret。

### 4.1 模块内部最小规则

模块从最少文件开始，只有出现真实独立职责时再拆分：

```text
modules/<module>/
├── __init__.py                 # 唯一公开出口
├── domain/                     # 实体、值对象、状态迁移、纯规则
├── application/                # Command、Query、事务和端口
├── persistence/                # 本模块表映射和查询
└── transport/                  # HTTP/事件映射；不得拥有业务规则
```

- 模块只能写自己拥有的表；跨模块不得导入对方 persistence、ORM 映射或内部 application 实现。
- 跨模块同步调用只能使用目标模块 `__init__.py` 暴露的 Command、Query、Snapshot 和 Port。
- 异步交接只携带稳定 ID、版本、幂等标识和最小路由字段，不传完整剧本、Prompt、媒体字节或对象快照。
- `platform` 拥有 Capability、WorkTask、ExecutionAttempt、MediaArtifact、Lineage 和 Cost 的通用事实，但不得拥有剧本、镜头或主选业务语义。
- `governance` 拥有 RightsDecision、ContentDecision、DataProcessingProfile、Retention/Deletion、SecurityCase 和 AuditRecord；其他模块只消费门禁结果，不复制决定。
- `integrations` 只实现端口，不创建业务事实；Provider Adapter 不能直接修改候选或主选表。
- 禁止全局 `common/`、`utils/`、`helpers/`、`managers/` 成为业务垃圾桶。

### 4.2 运行角色

后端同一构建产物至少支持：

| 角色 | 职责 | 禁止作为事实源 |
| --- | --- | --- |
| API | 同步命令、查询、权限、预检、快照冻结、SSE | 浏览器本地任务状态 |
| provider worker | Provider 提交、轮询、回调对账 | Worker/队列内部状态 |
| media worker | 受控下载、hash、探测、缩略图 | Provider 临时 URL |
| export worker | 只按 ExportSnapshot 构建 PackageBuild | 当前主选或当前镜头顺序 |

角色可从同一 `worker.py` 以队列/任务类型参数启动，也可在容量证据出现后分别扩缩容；不为每个角色复制领域代码或建立独立仓库。

## 5. 前端目标结构

```text
frontend/
├── src/
│   ├── app/                     # Next.js 路由与页面组合
│   ├── features/                # 按用户任务组织的页面级能力
│   ├── components/
│   │   └── ui/                  # 无业务语义基础组件
│   ├── api/                     # OpenAPI 生成，禁止手改
│   ├── state/                   # 未提交草稿、选择和布局；不复制服务端事实
│   └── telemetry/
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── accessibility/
│   └── e2e/
└── package.json
```

- 路由和 feature 以项目、剧本、资产、分镜、关键帧、视频候选、检查导出等用户任务命名。
- 服务端实体、任务、主选和 ProductionRun 快照由查询缓存持有；本地状态只保存未提交草稿和 UI 选择。CanvasLayoutRevision 属于 post-MVP，不进入当前目录。
- OpenAPI 是前后端 HTTP 契约事实源；禁止手写同构 DTO、复制状态枚举或维护第二套 URL。
- SSE 只传任务/摘要变化通知，断线后按事件游标恢复；不可恢复时重新查询服务端。轮询降级不得产生写入副作用。
- 当前完整创作面向桌面；小屏只读能力按 Requirement，不为移动端创建平行页面体系。

## 6. Plain Data Contract

跨边界数据对象只表达数据和局部确定性校验：

- 写入使用 `...Command`；查询使用 `...Query`；固定事实使用 `...Snapshot`；用例返回使用 `...Result`；事件使用过去式 `...Event`。
- Command、Snapshot、Result 和 Event 默认不可变并拒绝未知字段。
- 不得持有数据库连接、ORM 实体、HTTP Client、Provider SDK、对象存储 Client、Logger 或 Service Locator。
- 不得含 `save`、`publish`、`submitProvider`、`download`、`commit` 等 I/O 方法。
- 名称必须表达业务含义，禁止以 `DTO`、`Data`、`Info`、`Object`、`Bean` 代替语义。
- HTTP、事件和 Provider 响应是三种边界契约；不得让 Provider 原响应直接成为业务 Candidate。

## 7. 数据库与迁移规则

1. PostgreSQL 是结构化业务事实源；Redis、工作流历史、对象存储元数据和前端缓存均不能替代它。
2. 每张租户业务表显式保存 `workspace_id`；跨空间查询必须在仓储和数据库防御层同时受限。
3. 可变聚合使用 `revision` 乐观并发；历史版本、决定、任务尝试、消耗和审计采用追加式记录。
4. 不可变版本不得通过普通 UPDATE 替换正文、输入摘要或媒体 hash。
5. 同一 Shot/用途唯一 current Selection、同一 Slot 唯一 current Selection 等不变式应尽可能用唯一索引或约束证明。
6. 事务 Outbox 与业务事实同事务写入；消费者使用 Inbox/业务幂等键处理重复事件。
7. SQLAlchemy `Base.metadata` 是最终结构的唯一代码事实源；本项目不保留冗余的 Alembic 版本链，也不允许应用启动时静默改表。
8. 本地/一次性环境可以从最终结构重建；含重要数据的环境必须使用显式、可审计、可回滚或可前滚的一次性升级脚本，并在升级前备份。禁止以猜测式兼容逻辑替代数据转换，也禁止把“最终结构唯一”误解为“生产数据库可以直接覆盖”。
9. 不为未接受需求预建 Timeline、Render、Payment、Subscription 或 Provider 市场表。

## 8. 文件、Secret 与生成物

- `.env.example` 只列配置名、安全示例和说明；真实 `.env`、凭据、签名 URL 和本地数据不得提交。
- 浏览器公开变量不得含 Provider、数据库、对象存储写凭据或内部 Endpoint。
- Provider Secret 由部署环境的 Secret Manager/KMS 注入；数据库只保存 secret reference 和脱敏状态。
- 原始上传、生成媒体、缩略图、隔离对象和导出包均在对象存储，源码仓库只保留最小无敏感 fixture。
- OpenAPI 客户端、Schema 或 Capability Catalog 生成物只有在构建可复现且 CI 检查漂移时才提交。
- 日志、coverage、测试报告、临时 ZIP、对象存储目录、数据库卷和 Provider 原响应不得提交。

## 9. 测试结构与门禁

| 门禁 | 必须证明 |
| --- | --- |
| architecture | 只保留会影响业务正确性、安全或可替换性的可执行模块边界，不检查文档、文件清单、文件名或目录外观 |
| unit | 状态迁移、版本不变式、readiness、覆盖、幂等和错误映射 |
| integration | PostgreSQL 事务/约束、对象存储、工作流、SSE、ffprobe |
| contract | OpenAPI、事件 Schema、Capability Catalog、真实 Provider 录制/沙箱契约 |
| fault | 重复提交、工作进程退出、回调乱序、Provider unknown、媒体/打包中断 |
| security | 跨 Workspace、直接 ID、短期 URL、Webhook 重放、日志脱敏 |
| e2e | 从剧本到逐镜唯一主选，再到原始视频素材包的当前范围闭环 |
| hygiene | 无 Secret、缓存、日志、媒体、无关生成物或手改生成代码 |

涉及外部 Provider 消耗的测试必须显式启用并设额度；默认 CI 使用契约 fixture 和可控假 Provider，真实 Gate 另行记录账号、地域、能力和消耗证据。

pytest 不承担文档链接、Markdown 格式、文件名长度、固定目录清单或源码字符串快照检查；这些变化不能证明用户功能成功，也不应阻塞业务回归。确有必要的仓库卫生由轻量 lint/评审处理，CI 的主要通过条件必须来自单元、集成、契约、故障、安全和端到端功能证据。

## 10. CI 与交付约束

- PR 与 main 必须运行后端质量、前端质量、架构、OpenAPI 漂移、数据库迁移、集成、安全和当前范围 E2E。
- 任一检查被跳过、超时或缺少外部条件时不得报告为通过。
- API 与 Worker 使用同一后端镜像，不同启动命令；前端单独镜像。
- 生产迁移和应用发布分离并可审计；失败不得由应用启动时静默修复。
- 每次纵向切片只创建当前真实需要的目录、表、队列和配置。
- 部署拓扑、备份和恢复以 [DES-014](./014-非功能服务目标容量观测备份与灾备设计.md) 为准。

## 11. 命名与文档治理

- Design 文件使用三位序号和中文主题；代码、表、字段、事件和 API 标识使用英文语义名。
- 稳定业务 ID 不使用显示名称、镜号、顺序或 Provider Model ID 充当主键。
- 事件使用过去式，如 `ScriptVersionPublished`；命令使用动词，如 `PublishScriptVersion`。
- 错误使用稳定错误码、用户摘要、是否可重试和 next action，不暴露 Provider 原错误。
- Requirement 是“要什么”的事实源；Design 是“如何满足”的事实源；Plan 不得反向改写两者。
- [DES-015](./015-Requirement到Design追踪矩阵.md) 是 Requirement→Design 覆盖索引，不复制完整需求正文。

## 12. 验证与待决策

### 12.1 Design 验证

- 目录和导入架构测试能拒绝跨模块持久化访问；
- OpenAPI 可生成并检查无漂移；
- API/Worker 同一构建产物可分别启动；
- 空库迁移、升级迁移和回滚/前滚策略可执行；
- Secret/媒体/日志仓库扫描为零；
- 当前完整 E2E 不依赖剪辑、成片、字幕、音频或商业运营。
