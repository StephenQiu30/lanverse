# 后端服务架构

- 目标状态：已接受
- 落地状态：迁移中；Go 已接管公共入口，业务写入仍由 Agent 目录中的 Python 兼容运行时承担
- 来源：[完整设计基线](../designs/AI短剧制作平台完整设计基线.md) · [ADR-0001](../adr/0001-采用目标平台架构.md) · [ADR-0002](../adr/0002-采用中文语义化文档与模块命名.md) · [迁移期后端语言切换策略](../adr/迁移期后端语言切换策略.md)

## 结论

目标 Backend 是一个 Go Module、多个垂直领域模块和五个独立运行程序。它是同一套业务代码按部署职责组合出的多个 Binary，不是五套微服务仓库。Python 只保留为独立 Agent Runtime；Temporal 是跨服务长任务的唯一编排者；PostgreSQL 是业务事实源。

当前已落地的迁移切片是：`backend/` 已成为 Go Module，`cmd/api` 自行提供 `/healthz`、`/readyz`、`/metrics` 与 `/version`，并把尚未迁移的业务路由转发到内部 `agent-api`；原 FastAPI、SQLAlchemy、Scheduler 和 Worker 已物理迁入 `agent/`。`backend/api/event/event-envelope-v2.schema.json` 已成为 Event Envelope v2 的首个契约源，Go 侧严格解码拒绝未知字段和 v1 消息；Python 旧 Outbox Publisher 已通过 Topic allowlist 限定为 IO/Media v1。上述能力仍未创建 Audit Topic、Consumer、Projection 或任何 Go 业务 Writer。`agent-api` 是有明确退出门禁的兼容运行时，不是 Agent 终态。

```text
lanverse-api
     │ Commands / Queries
     ▼
PostgreSQL ── Outbox ── Debezium ── Kafka ── event-worker
     │
     ├── workflow-worker ── Temporal
     │          ├── gRPC ── agent-runtime
     │          ├── gRPC ── model-gateway ── Providers
     │          └── gRPC ── media-worker ── MinIO
     │
     └── Redis / Elasticsearch projections
```

## Binary 职责

| Binary | 唯一职责 | 不得负责 |
|---|---|---|
| `lanverse-api` | Access、Production、Authoring、Preset、Asset/Rights、Review、Cost、Quota、Generation Submission Intent ingress、Eventing Outbox/Audit Query、Search 查询；命令入口；Provider Callback 公网入口 | 执行长任务、直接调用 Provider、写 Generation Request/Provider Job、转码大媒体 |
| `workflow-worker` | Temporal Workflow/Activity、Episode/Shot Workflow、Human Gate、重试/恢复/取消、Node Cache | 保存活动 Authoring 编辑态、成为第二个业务事实源 |
| `model-gateway` | 按持久 Submission Intent 创建 Generation Request/Receipt，管理 Provider/Generation Capability Registry、路由、Fallback、限流、Provider Job、定价和回调状态转换 | 写 Submission Intent、持有剧集业务流程、绕过 Cost/Quota |
| `media-worker` | ffprobe、FFmpeg、OpenCV、缩略图、转码、字幕、混音、Motion、Render、Export | 决定业务候选、直接发布领域状态 |
| `event-worker` | Kafka 消费、Search/Cost Analytics/Audit 等下游投影、通知、DLQ、Replay、Reindex | 处理 Workflow Control/Signal、修改 Cost Ledger、承担 Human Gate 等待 |

同一 Binary 内模块通过 Go Interface 调用。只有真实部署边界才使用 gRPC；目录边界不能自动演变成网络跳转。

## 领域模块

Production 聚合层级固定为：

```text
Workspace → Project → Episode → Scene → Shot
```

规范模块职责如下：

- `access`：身份、Session、Workspace Membership、Role/Access Capability 与 Actor Context。
- `production`：Workspace、Project、Episode、Scene、Shot、Script/Bible/Profile Version 等生产事实。
- `preset`：版本化组合 Style、Skill、Model/QC/Motion/Render Policy，并解析 Effective Snapshot。
- `authoring`：Guided/Canvas 共用 Draft/Revision、Node Catalog、Graph Validation、GraphPatch 与发布。
- `workflow`：Workflow Compiler、Definition、Run/Node 状态、Temporal 适配器和 Execution Cache。
- `review`：Human Task、Review Decision、Claim Lease 到期与解决；通过持久事件对接 Temporal Signal。
- `generation`：Generation Capability、Generation Request、Provider Job、Candidate、Callback、Routing 与 Pricing Report。
- `agent`：Backend 侧 Agent Invocation、Execution Grant、Run Context、Tool Policy 与预算；不包含 Python Runtime 实现。
- `asset`：可复用 Asset 身份/版本、不可变 Artifact、上传会话、Lineage、Storage Profile、Location 与 Rights/Consent。
- `media`：媒体探测、Derivative、处理请求、Render Manifest 与 Export Receipt。
- `cost`：Price、Estimate、Reservation、Ledger 与 Budget，负责金额事实。
- `quota`：Quota Policy、Usage Window、Counter 与 Decision，负责使用限额事实。
- `eventing`：Outbox/Inbox、Event Envelope、DLQ、Replay、Projection Checkpoint 与 Audit Projection。
- `search`：Elasticsearch Business Projection、查询与 Reindex。
- `bootstrap/config/database/cache/telemetry`：Binary 装配和基础设施 Adapter，不拥有业务事实。

跨模块只依赖对方公开 Application Interface、不可变值对象或领域事件；不得导入对方 Repository、数据库模型或 Adapter。逐模块用例、状态、事件、失败路径和验收见 [后端领域模块功能设计](../designs/后端领域模块功能设计.md)。

## Asset 与 Artifact

本节是对原设计中命名空白的细化：

- `Asset` 是可复用的创作身份，例如角色、地点、道具、服装或声音身份。`AssetState` 表达剧情阶段，`AssetVersion` 表达已发布版本。
- `Artifact` 是某次 Workflow/Node/Generation 产生的不可变输出，例如 Prompt、图片、视频、音频、字幕、预览或最终 MP4。
- `AssetVersion` 可以引用一个或多个 Artifact；Artifact 不能反向承担角色身份或跨剧情状态。
- 业务记录只保存 Artifact ID 和版本关系，不在 Shot 上直接保存孤立的 `image_url` 或 `video_url`。
- Artifact 内容身份不可变，独立的 `ArtifactReadiness` 表达 `PENDING_VALIDATION / READY / QUARANTINED / UNAVAILABLE / TOMBSTONED`；只有 `READY` 可进入候选选择、版本发布或 Render 输入。
- Media 的 `RenderManifestVersion` 固定合成输入与输出规格，`MediaDerivativeReceipt` 记录处理结果；持久血缘仍以 Asset 的 `ArtifactLineage` 为唯一事实。

所有 Artifact 至少冻结：内容哈希、Storage Profile、Bucket/Object Key、来源 Workflow/Node/Agent/Generation Run、Prompt/Skill/Model/Policy/Preset/Style 版本以及创建时间。

## Authoring 与 Workflow

Guided 与 Canvas 都生成 `AuthoringDraft`。发布操作通过乐观锁产生不可变 `AuthoringRevision`，再由 Workflow Compiler 生成不可变 `WorkflowDefinitionVersion`。每个 Workflow Run 必须绑定一组固定版本，运行中不可漂移。

```text
AuthoringRevision
  + PresetVersion
  + EffectivePolicySnapshot
        ↓ compile
WorkflowDefinitionVersion
        ↓ start
Temporal Workflow Run
```

Compiler 必须验证类型与端口、权限、成本上限、Human Gate、Subflow 版本和有界 Loop。一般有向环不允许发布；Loop 只能编译为声明了最大迭代次数与预算的受控结构。

旧 Workflow Run 不跨引擎迁移。切换时以 Workflow Definition 版本为界，新版本进入 Temporal，旧版本由旧执行链完成或显式终止。

## Agent 与 Model Gateway

本节细化原文未明确的 Agent 模型调用路径：

1. `workflow-worker` 创建 Agent Activity，并签发只对当前 Run/Node、Tool、模型能力和时限有效的 `ExecutionGrant`；它不签发 Cost/Quota `ExecutionAuthorization`。
2. Agent Runtime 通过 gRPC 接收固定上下文；需要模型时携带 ExecutionGrant 调用 `model-gateway`，Gateway 仍须按对应 Intent 向 `lanverse-api` 在线领取 Execution Claim/Authorization，Agent 不得直连 Provider。
3. Agent Tool 只能调用 Backend Tool API Allowlist，不得连接 PostgreSQL、Yjs 持久层、MinIO 或任意 Shell/网络。
4. Agent 返回结构化结果或明确失败；领域写入仍由 Backend Application 层完成。

`StructuredExecutor` 用于解析和简单 QC，`ToolLoopExecutor` 只允许 2–5 次有限工具调用，`LangGraphExecutor` 只用于确需 Plan/Execute/Check/Repair 的 Agent。每次调用都有 step、model/tool call、token、cost 和 deadline 上限；长达数小时的 Episode 生命周期由 Temporal 续接多个有限 Activity，而不是给单次 Agent 无限执行时间。

## Generation 提交与执行 Claim

- `lanverse-api` 在业务事务中创建 Generation Submission Intent、Cost/Quota Reservation 与 Outbox；Event 只带稳定引用和请求 Hash。
- `model-gateway-submission.v1` Consumer Group 从 `lanverse.generation.v1` 取得 Intent 后，立即通过 internal gRPC 调用 API `AcquireExecutionClaim`。API 原子锁定 Intent/两类 Reservation、写 Claim Version 并返回短时签名 Authorization；Gateway 不读取 Cost/Quota 表。
- Gateway 以 Intent ID + Claim Version 作为 Provider Request Key，写 Generation Request/Receipt 与 Receipt Outbox。`generation-submission-intent-updater.v1` Group 在 `lanverse-api` 内消费 Receipt，按 Claim 栅栏推进 Intent 与 Reservation；旧 Claim 或迟到结果进入隔离。
- Claim 前取消可原子释放；Claim 后只记录取消请求，直到 Provider Receipt 明确才能结算或释放。Gateway 崩溃后先按原 Provider Request Key 对账；不能证明未调用时进入 Unknown/Reconciliation，禁止创建新 Intent。
- 两个 Group 都使用 Event Inbox 幂等，Topic/Consumer 先于 Producer 启用；短时 Authorization 不进入 Kafka，所以提交后崩溃与队列延迟都由 Intent/Outbox 恢复。

## Provider Callback

本节细化 API 与 Model Gateway 的共同职责：

- `lanverse-api` 是唯一公网 Callback 入口，负责 TLS、Provider 身份识别、原始签名校验、Body 大小限制、重放窗口和请求审计。
- 验证后的回调被规范化为内部命令，通过 gRPC 交给 `model-gateway`。
- `model-gateway` 以 Provider Job ID + Provider Event ID 幂等地推进 Job/Candidate 状态，并写 Outbox。
- API 不直接决定候选选择，Gateway 不暴露公共业务 API；未知或过期回调进入隔离队列并可人工对账。

## Human Gate 与 Review

本次将任务状态和业务决策拆开：

- `HumanTask` 状态：`WAITING / CLAIMED / RESOLVED / CANCELLED / STALE`。
- `ReviewDecision`：`APPROVE / REJECT / SELECT / REGENERATE / EDIT / SKIP`。
- 决策是不可变记录，包含 Actor、权限、对象版本、原因和幂等键。
- 普通 Human Gate 由 `review` 在同一事务写决策与 Outbox，`workflow-worker` 按 Decision ID 发 Temporal Signal。
- Bible/Storyboard 等会修改 Production 的决策由 `lanverse-api` Coordinator 在同一 Unit of Work 写 Review Decision 与 Production Apply Receipt；`workflow-worker` 只消费 `production.*.applied` Event 后发 Signal，不直接用原 Decision 重复应用。

## 数据与基础设施所有权

| 数据 | 权威系统 | 约束 |
|---|---|---|
| Workspace、Project、Episode、Asset、Revision、Review、Cost | PostgreSQL | 唯一业务事实源，Migration 管理 Schema |
| Workflow 历史、Timer、Retry、Signal | Temporal | 不复制为 Kafka 编排状态；PostgreSQL 只存业务投影 |
| 缓存、限流、Ephemeral Lock | Redis | 可丢失、可重建，不保存永久业务事实 |
| 对象字节 | MinIO/ObjectStore | 私有 Bucket，业务只依赖 ObjectStore Port |
| 领域事件 | Kafka | 不承担 Timer、Human Wait、Token Stream |
| Search/日志投影 | Elasticsearch | 可从 PostgreSQL/Kafka 重建，不反向写业务 |

大文件使用 `Create Upload Session → Presigned URL → Browser 直传 → Complete → Validate → Artifact`，不得经过 API 进程中转。切换 TOS/S3/OSS/COS 只替换 Storage Adapter/Profile；历史迁移通过独立 Workflow、Checksum、Dual Read、切主和旧位置退役完成。

## 事务、事件与契约

业务事务同时写业务数据与 `outbox_event`。Debezium/Kafka Connect 捕获已提交 Outbox 并发布 Kafka；不得使用数据库提交后再直接 `Producer.Send` 的双写方式。

Event Envelope 至少包含 `event_id`、`event_type`、`schema_version`、`aggregate_type/id/version`、`workspace_id`、`partition_key`、`occurred_at`、`traceparent`、`causation_id`、`correlation_id` 与 payload。Consumer 以 event ID 幂等，按聚合分区保证顺序；破坏性 Schema 变化发布新事件版本。

契约位置固定：

```text
backend/api/openapi   Browser REST/SSE
backend/api/proto     Backend 进程间 gRPC
backend/api/event     Kafka Event Schema
backend/api/gen       生成代码
agent/api/proto       Agent 服务契约
```

REST 统一 `/api/v1`、错误包络、游标分页、幂等键和版本冲突响应。命令默认要求 `Idempotency-Key`；更新不可变 Revision 的源 Draft 使用 expected revision/ETag。SSE 支持 Last-Event-ID 重连；gRPC 声明 deadline、可重试码和幂等语义。

## 安全与观测

本节为本次细化：Web 采用短期 Access JWT + 旋转的 HttpOnly Refresh Session，所有资源检查 Workspace RBAC。模型密钥只存在于 Model Gateway；对象存储只使用最小权限服务身份和短期 Presigned URL；Callback、gRPC 和 Yjs WebSocket 都必须认证并绑定 Workspace/Run 范围。

所有服务传播 `trace_id`、workspace/project/episode/scene/shot、revision、workflow/node、agent、generation/provider job 与 artifact 标识。日志使用 JSON 与字段脱敏；OTel Collector 汇聚 Trace/Log，Prometheus 抓取指标，Grafana/Kibana 提供视图。

## 失败与恢复原则

- Provider timeout 或 callback 丢失：Model Gateway 对账，状态保持 `WAITING_PROVIDER` 或 `UNKNOWN`，不伪报成功。
- Agent 结构错误：有限次结构修正；仍失败则 Activity 失败，由 Temporal Policy 决定重试。
- Human Gate：Temporal 等待 Signal，不占用 Worker；对象版本变化使旧任务 `STALE`。
- Kafka Consumer：幂等处理，可进入 DLQ 并 Replay；投影失败不回滚业务事实。
- Media：中间对象使用临时 key，完成校验后原子登记 Artifact；取消与失败清理可重试。
- Cache miss 或 Redis 故障：回源事实系统；高成本命令按 Policy fail closed。
