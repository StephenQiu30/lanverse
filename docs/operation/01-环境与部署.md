当前支持本机 Next.js 与 Go 进程连接已有中间件；应用与依赖 Compose 文件供后续容器化部署准备。本文的 staging、production、托管服务、远程网络和扩容配置均为计划，接入前须验证消费者认证、部署产物、容量和恢复能力。云产品价格、地域可用性与版本在部署准备时核对官方文档。

## 1. 环境

| 环境            | 用途                                             | 部署形态                                                               | 数据                  | 供应商                                         |
| --------------- | ------------------------------------------------ | ---------------------------------------------------------------------- | --------------------- | ---------------------------------------------- |
| local           | 开发                                             | Next.js 与 Go 角色直接启动，连接本机已运行的中间件；根目录 `.env` 配置 | 种子数据              | 模拟供应商；可选真实（个人测试凭据，严格预算） |
| ci              | 自动化测试                                       | GitHub Actions + testcontainers / Compose                              | 每次重建              | 模拟供应商                                     |
| staging（预发） | 集成、端到端、性能、故障注入、验收预演、迁移演练 | 单台云服务器 Docker Compose（中间件自建容器）                          | 脱敏样例 + 合成大项目 | 模拟为主；真实供应商冒烟（每日 ¥20 上限）      |
| production      | 内部生产使用                                     | 云服务器 + Docker Compose；数据库、Redis、Kafka、对象存储使用托管服务  | 真实                  | 真实                                           |

接入环境时须隔离数据、凭据、密钥和存储桶（REQ-02 DEP-02）；staging 不允许读取生产数据。

## 2. 生产拓扑

准备远程部署时按以下目标拓扑评估资源；API 当前仅允许 local 回环访问，须先完成消费者部署与认证合同，才能开放远程入口。

```text
                       Internet
                           │ HTTPS（lanverse.<域名>）
                    ┌──────▼──────┐
                    │ CLB 负载均衡 │  TLS 终止、WAF 基础规则
                    └──┬───────┬──┘
          /api、SSE    │       │  /（页面）
┌──────────────────────▼───────▼──────────────── VPC（私有子网）──────────────────────────┐
│ app-1（8C16G）                           media-1（8C16G，按需扩 media-2）                 │
│   frontend（Next.js standalone）×1         backend-worker --queues=media ×1（FFmpeg）     │
│   backend-api ×2                                                                        │
│   backend-worker --queues=flow ×1        ops-1（4C8G）                                   │
│   backend-relay ×1                         OTel Collector、Prometheus、Grafana、Loki、Tempo │
│                                           Temporal UI、Kafka UI（仅内网 / VPN）           │
│   temporal（frontend / history / matching / worker 服务）                                │
│                                                                                         │
│ 托管服务：云数据库 PostgreSQL（业务库 + Temporal 库，主备）· 缓存 Redis（主备）              │
│          消息队列 Kafka（3 broker）· 对象存储 TOS（私有桶）+ CDN · KMS                     │
│ NAT 网关 / 出口：Go 执行 Worker 访问模型供应商（境内出口 + 境外独立出口，白名单）               │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- 计划以 5 名并发用户为初始容量目标，实测满足 REQ-02 §4 后使用单套部署；准备关键组件双实例并验证滚动发布（AVL-04）。
- 计划自建 Temporal（官方镜像），为持久化与可见性准备独立 PostgreSQL 数据库与账号（DES-08 §5）。

### 2.1 规格估算（初始）

| 资源       | 规格                                            | 依据                                                                  |
| ---------- | ----------------------------------------------- | --------------------------------------------------------------------- |
| app-1      | 8 vCPU / 16 GB / 100 GB 云盘                    | API、Worker、Temporal 以 I/O 为主；媒体原生任务另受资源预算           |

| TOS        | 标准存储 + 低频存储（未选定候选 90 天后转低频） | 单部 80 集剧约 250 GB（CAP-04）                                       |

## 3. 组件部署

下表为计划部署规格；实例数与资源限制须经过目标环境验证。已有角色、端口与探针可用于准备部署，不能证明生产拓扑已启用。

| 组件                    | 镜像                                           | 实例 | 资源限制     | 健康检查                                                                    | 端口（内网）   |
| ----------------------- | ---------------------------------------------- | ---- | ------------ | --------------------------------------------------------------------------- | -------------- |
| frontend                | `lanverse/frontend`                            | 1    | 1C / 1G      | `GET /healthz`                                                              | 3000           |
| backend-api             | `lanverse/backend --role=api`                  | 2    | 1C / 1G      | `GET /healthz`（存活）、`/readyz`（PG、Redis、Temporal 命名空间、对象存储） | 8080           |
| backend-worker（flow）  | `lanverse/backend --role=worker --queues=flow` | 1    | 1C / 1G      | Temporal Worker 心跳 + `/healthz`                                           | 8081           |
| backend-worker（media） | 同上 `--queues=media`                          | 1    | 6C / 12G     | 同上                                                                        | 8081           |
| backend-relay           | `lanverse/backend --role=relay`                | 1    | 0.5C / 512M  | Outbox 积压 + `/healthz`                                                    | 8082           |
| temporal                | `temporalio/server`（固定版本）                | 1    | 2C / 4G      | 自带                                                                        | 7233           |
| temporal-ui             | `temporalio/ui`                                | 1    | 0.25C / 256M | —                                                                           | 8233（仅 VPN） |

- Worker、Relay 的 `GET /healthz` 是进程存活探针；监听地址分别由 `LV_WORKER_HEALTH_ADDR`、`LV_RELAY_HEALTH_ADDR` 指定，默认 `:8081`、`:8082`。任务处理能力另看 Temporal Worker 心跳与 Outbox 积压。`media` 队列已接入；部署时须配置供应商结果来源白名单并挂载可写 `/work` 临时卷。
- 容器部署须使用非 root 用户；media Worker 的 Compose 已配置只读根文件系统与 `/work` 临时卷，其余角色的只读部署在接入时验证（DES-07 §9）。
- 本地 Next.js 与 Go 角色直接运行，连接本机已运行的服务，不通过 Docker 启动环境。后续容器化部署保留两份独立 Compose 文件：`docker-compose.yml` 定义应用服务，`docker-compose-env.yml` 定义依赖服务；本机进程只读取根目录 `.env`。
- `docker-compose-env.yml` 完整描述 PostgreSQL、Redis、Kafka、MinIO、Temporal 及管理界面，供后续容器化部署使用；本地开发不执行该 Compose 文件。部署应用时单独执行 `docker compose up -d --build`。

## 4. 网络与域名

远程网络按下表准备；SSE、浏览器直传和消费者认证接入后分别验证路由、来源限制与超时。

| 项       | 设计                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| 域名     | `lanverse.<公司域名>`（生产）、`staging.lanverse.<公司域名>`；ICP 备案【对外发布前】                              |
| 证书     | CLB 托管证书，自动续期；HSTS                                                                                      |
| 路由     | `/api/*` 与 SSE → backend-api；其余 → frontend；SSE 连接空闲超时 ≥ 35 分钟（DES-03 §5.1 连接 30 分钟主动关闭）    |
| 安全组   | 公网只开放 CLB 443；实例间按端口最小开放；托管服务仅允许 VPC 内访问                                               |
| 出口     | NAT 网关；Go 执行 Worker 出站白名单为供应商域名；OpenRouter 走独立出口（可单独关闭，CMP-06）                      |
| 管理访问 | 运维通过 VPN / 堡垒机访问 ops-1、Temporal UI、Kafka UI、Grafana（DES-07 §9，SC-Q2）                               |
| 对象存储 | 当前上传经 Next.js 和 Go 写入私有对象存储；计划接入的浏览器直传与授权下载须限制预签名权限，桶 CORS 只允许本站域名 |

本机 HTTP 开发按 DES-03 §2.2：Next.js 同源 `/api` rewrite 到 `LV_API_BASE_URL` 的本机 Go 地址，浏览器使用 `LV_PUBLIC_ORIGIN`，后端按该配置校验写命令 Origin。当前工作区不使用登录/会话/CSRF，API 仅允许 `LV_ENV=local` 和回环监听/浏览器 Origin；消费者部署与认证计划按正式设计接入，不从代理 Host 猜源。MVP 不注册供应商 callback/webhook，也不纳入公共 API 文档，先走轮询和对账。

Next.js 的 rewrite 目标在构建时写入产物。后续应用 Compose 部署通过 frontend build arg `LV_API_BASE_URL` 指定容器可访问的 Go 地址（默认 `http://backend-api:8080`），修改后需要重建前端镜像；仅修改运行时环境不会改写既有产物。本机 `.env` 仍填写本机 Go 地址。standalone 镜像显式包含 `public`，确保媒体示例与第三方许可文本可访问。

## 5. 配置与密钥

- **配置**：环境变量（12-factor）；本地进程由根目录 `.env` 提供，示例键见 `.env.example`，文件不得提交。Go 使用 Viper；启动时集中校验当前角色必需项，缺失即退出。应用 Compose 配置在 `docker-compose.yml`，依赖环境 Compose 配置在 `docker-compose-env.yml`，所需密钥通过 shell 或受控环境文件注入。
- **配置清单**（各能力接入时逐项启用）：

| 变量                                                                                                                                                      | 服务                 | 说明                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `LV_DB_DSN`                                                                                                                                               | backend              | API 启动必需；本地指向本机业务库，部署时可经 PgBouncer                                                                            |
| `LV_PARTITION_MAINTENANCE_DB_DSN`                                                                                                                         | backend 分区维护命令 | `lanverse partitions ensure` 必需；指向同一业务库中拥有 Outbox 和审计父表的独立账号，普通进程不使用                               |

| `LV_API_BASE_URL`                                                                                                                                         | frontend 服务端      | 本机 Go API 根地址，仅供 Next.js `/api` rewrite，不公开给浏览器                                                                   |
| `LV_PUBLIC_ORIGIN`                                                                                                                                        | backend-api          | 精确本机前端源，写命令 Origin 校验；当前仅支持 local 回环工作区                                                                   |
| `LV_KAFKA_BROKERS`                                                                                                                                        | backend-relay        | franz-go 已用于 Outbox 投递与实时事件消费；准备托管 Kafka 部署时接入并验证 SASL 认证配置                                          |

- **密钥**：生产部署计划通过 KMS 或权限为 0400 的受控文件注入，接入前验证密钥轮换与恢复；密钥不写入镜像、Compose 文件与仓库。`.env` 仅本地使用且在 `.gitignore` 中（DES-07 §5）。

### 5.1 审计表数据库权限

应用以非表所有者的数据库登录角色连接，Schema 初始化、实例增量升级与分区维护使用另外的高权限角色。部署数据库管理员先创建集群级 `lanverse_app` 非登录、非超级用户权限角色（`CREATE ROLE lanverse_app NOLOGIN NOSUPERUSER`），再创建独立的 `LOGIN INHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE` 应用账号并执行 `GRANT lanverse_app TO <应用账号>`；然后由表所有者按 §7 初始化空库或执行已审阅的实例升级。Schema 中的审计权限只向 `lanverse_app` 授予 `audit` schema 的 `USAGE` 和父表 `audit.audit_log` 的 `INSERT, SELECT`；Schema 按当前仓储所需操作逐表授予其他业务表，新增已实施业务对象须在同一文件中补充必要授权。应用读写审计一律经父表，未来分区由维护角色创建。应用登录角色不能是审计表所有者，也不能继承其他可修改、删除或截断审计表的角色；部署前需实测这些操作被数据库拒绝。权限调整须按具体实例审阅；撤销只涉及明确授权项，不删除可供其他数据库复用的集群角色。

管理员审计读取使用 `identity."user" ... FOR SHARE` 锁定账号行；按 PostgreSQL 的权限规则，应用登录角色还需在该表拥有查询列的 `SELECT` 和至少一列的 `UPDATE` 权限，当前授权统一由 Schema 描述。不能为了满足这项锁权限而向 `lanverse_app` 授予审计表的 `UPDATE`。接入受限账号时，本机根目录 `.env` 的 `LV_DB_DSN` 应指向应用登录角色，部署结构管理凭据由受控环境单独提供。

## 6. 本地开发环境

本机先启动 PostgreSQL、Redis、Kafka、MinIO 和 Temporal，再检查根目录 `.env` 中对应地址与本机服务一致。Go API 启动时会连接 `LV_DB_DSN` 指向的数据库；若缺失或不可达则退出。`LV_REDIS_URL`、`LV_TEMPORAL_ADDR`、`LV_TEMPORAL_NAMESPACE` 或必需的 `LV_OBJECT_STORAGE_*` 缺失或格式错误时，API 启动失败；Redis、Temporal 或对象存储暂不可达时 API 继续运行，`/readyz` 返回 503，`/healthz` 保持存活状态。对象存储的私有桶须提前创建并授予后端凭据访问权限；健康检查只验证桶存在且可访问，不创建桶或写对象。`LV_OTEL_ENDPOINT` 使用 OTLP/HTTP 根地址，Go 进程向其 `/v1/traces` 发送追踪；本机未启动 Collector 时留空禁用导出，仍传播工作流与 Activity 的追踪上下文，API 的就绪状态不依赖追踪服务。`.env` 已存在时保留原文件，不用示例覆盖；本机进程从该文件读取配置。已有本地配置若仍使用 `LV_S3_*`，需改为 `LV_OBJECT_STORAGE_*`。两份 Compose 文件供后续容器化部署使用，不作为本地开发启动命令，也不作为覆盖文件叠加。容器化部署的 `LV_OBJECT_STORAGE_ENDPOINT` 与 `LV_OTEL_ENDPOINT` 须填写后端容器可访问的地址，不能沿用指向容器自身的 `127.0.0.1` 示例地址。

```bash
pg_isready -h 127.0.0.1 -p 5432
redis-cli -h 127.0.0.1 ping
kafka-broker-api-versions --bootstrap-server 127.0.0.1:9092
curl -fsS http://127.0.0.1:9000/minio/health/live
temporal operator cluster health --address 127.0.0.1:7233
temporal operator namespace describe --address 127.0.0.1:7233 --namespace lanverse-local
```

MinIO 的 HTTP 存活探针不验证桶权限；从仓库根目录执行 `cd backend && LV_TEST_OBJECT_STORAGE=1 LV_ENV_FILE="$(pwd)/../.env" go test ./tests/objectstorage -run '^TestPingWithHostObjectStorage$' -count=1 -v`，只读验证 `.env` 中凭据对目标私有桶的访问。`go test` 在测试包目录运行，因此此处将 `LV_ENV_FILE` 展开为绝对路径。

首次使用且 `lanverse-local` 命名空间不存在时，在本机已运行的 Temporal 中执行 `temporal operator namespace create --address 127.0.0.1:7233 --namespace lanverse-local --retention 72h`。新环境按上述命令明确创建，不能由历史环境推定当前存在。命名空间名称应与根目录 `.env` 的 `LV_TEMPORAL_NAMESPACE` 一致。

数据库结构按目标 Schema 准备完成且 Go `flow` Worker 已部署后，本机直启环境在仓库根目录执行 `cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse temporal setup`，向现有 Temporal 命名空间安装 `outbox-cleanup`、`processed-event-cleanup` 和五分钟一次的 `quote-expiry`。后续容器化部署须先独立确认结构准备完成、`flow` Worker 就绪且容器内 `LV_TEMPORAL_ADDR` 可达，再显式执行 `docker compose --profile maintenance-setup run --rm backend-temporal-setup`；该一次性服务不随普通 `up` 自动启动，也不会代为启动 Worker，退出码 0 才表示安装成功。之后由 Temporal 按 UTC 每日触发清理，并每五分钟扫描过期报价。重复执行只接受定义一致的 Schedule，并保留已有暂停状态；定义漂移时报错。`partition-maintain` 尚未安装。隔离验证可加 `--prefix=验证前缀-`，验证后须删除带此前缀的测试 Schedule。

业务结构准备完成、`LV_DB_DSN` 已使用真实的受限登录账号（不能以超级用户登录后切换角色）且 `LV_PARTITION_MAINTENANCE_DB_DSN` 已使用同库独立表所有者账号后，在仓库根目录手动执行 `cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse partitions ensure`。命令在同一事务内准备 Outbox 和审计当前 UTC 月及未来三个月的分区，任一方失败会整体回滚；执行时独占锁可能短暂阻塞写入，应在低流量窗口运行。该命令不做三年审计冷归档或历史分区删除，也不安装 `partition-maintain` Schedule；这两项边界完成前须由运维人员按月手动预备。

Kafka CLI 如由 Homebrew 安装但未加入 `PATH`，可用 `$(brew --prefix kafka)/bin/kafka-broker-api-versions`。该命令核验 Broker 协议；接入 Kafka 的任务仍需做生产与消费验证。确认服务可用后，分别在独立终端直接运行：

```bash
cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse --role=api
cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse --role=worker --queues=flow,media
cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse --role=relay
cd frontend && node --env-file=../.env "$(command -v corepack)" pnpm exec next dev
```

本机也可用 `cd backend && LV_ENV_FILE=../.env go run ./cmd/lanverse --role=all` 合并运行 API、`flow` 与 `media` Worker 和 Relay；此时不要再单独启动这三个 Go 角色。任一角色失败时会停止并等待其余角色退出。

每条命令从仓库根目录起始、在独立终端执行。根目录 `.env` 供本机进程读取；不用项目脚本或 Makefile。Go Worker 的 `flow` 队列执行工作流与基础设施维护任务，`media` 队列执行媒体接管与审核 Activity；同一 Worker 进程监听两条队列，共用 `LV_WORKER_HEALTH_ADDR`，无需占用第二个健康端口。Go Relay 与账号命令要求当前 Schema 的 Outbox、消费标记、审计和账号结构已经准备完成。Kafka 禁止自动建主题；部署方须在启动 Relay 前预建当前 Outbox 生产或消费的 `lanverse.audit.recorded.v1`、`lanverse.identity.user_changed.v1`、`lanverse.catalog.credential_changed.v1`、`lanverse.catalog.provider_changed.v1`、`lanverse.workspace.project_changed.v1`、`lanverse.billing.budget_changed.v1`、`lanverse.billing.budget_low.v1`、`lanverse.billing.budget_overrun.v1`、`lanverse.billing.settled.v1`、`lanverse.operation.confirmed.v1`、`lanverse.batch.confirmed.v1`、`lanverse.batch.finished.v1`、`lanverse.operation.status_changed.v1`、`lanverse.operation.completed.v1`、`lanverse.operation.failed.v1`、`lanverse.operation.manual.v1`、`lanverse.canvas.document_changed.v1`、`lanverse.catalog.credential_test.v1`、`lanverse.mediatool.command.v1`、`lanverse.mediatool.transcription_command.v1`、`lanverse.mediatool.depth_command.v1`、`lanverse.workspace.project_copy_requested.v1`、`lanverse.workspace.project_copy_changed.v1`、`lanverse.workflow.control.v1`。私有媒体接管、正式音视频导出和本机字幕转写由 Go Worker 执行；真实生成计划按正式设计完成实际供应商验收；Skill 和实体消费者计划按 BACKLOG 接入并验收。中间件的启动、停止和数据保留由本机服务管理器负责。隔离的 PostgreSQL 逻辑备份恢复演练使用新建的临时数据库，不读取或覆盖业务库。目标：新人 30 分钟内连接完整本地环境（REQ-02 MNT-05）。

### 6.1 本机字幕转写服务

字幕任务仍由现有 Go `flow`、`media` Worker 和 Outbox/Relay 执行。可选 `LV_WHISPER_ENDPOINT` 只接受带端口的 HTTP 回环 IP 根地址，例如 `http://127.0.0.1:19282`；消费方自行添加 `/inference`，禁止代理和重定向。留空时，新建及重试明确返回服务不可用，已存在任务仍可查询和取消。

字幕服务采用受控 whisper.cpp 原生进程与明确模型文件，固定来源、模型摘要和 MIT 许可见 [NOTICE](../../THIRD_PARTY_NOTICES.md)。模型、构建与临时音频放仓库外；安装与启动必须核验对应文件摘要。以下命令给出当前受支持的原生配置，不证明目标设备、语言准确率或跨设备已验收。

安装 CMake 4.4.3 与系统 C++ 编译器后，在仓库外准备固定原生服务：

```bash
speechRuntimeDir="${HOME}/.local/share/lanverse-whisper"
mkdir -p "$speechRuntimeDir"
git clone --branch v1.9.4 --depth 1 https://github.com/ggml-org/whisper.cpp.git "$speechRuntimeDir/source"
test "$(git -C "$speechRuntimeDir/source" rev-parse HEAD)" = 927cfce34f31707e17f2bff35c349632fb9e2c3a
curl --fail --location --output "$speechRuntimeDir/ggml-base.bin" https://huggingface.co/ggerganov/whisper.cpp/resolve/5359861c739e955e79d9a303bcbc70fb988958b1/ggml-base.bin
printf '%s  %s\n' 60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe "$speechRuntimeDir/ggml-base.bin" | shasum -a 256 -c
cmake -S "$speechRuntimeDir/source" -B "$speechRuntimeDir/build" -DCMAKE_BUILD_TYPE=Release -DGGML_METAL=OFF -DGGML_OPENMP=OFF -DWHISPER_BUILD_SERVER=ON -DWHISPER_BUILD_TESTS=OFF
cmake --build "$speechRuntimeDir/build" --target whisper-server -j 4
"$speechRuntimeDir/build/bin/whisper-server" -m "$speechRuntimeDir/ggml-base.bin" --host 127.0.0.1 --port 19282 --threads 4 --processors 1 --no-gpu --language auto --no-language-probabilities
```

在 API 与 Worker 的启动环境设置 `LV_WHISPER_ENDPOINT=http://127.0.0.1:19282`，并按目标 Schema 准备字幕任务结构、预建 `lanverse.mediatool.transcription_command.v1`。API 只接收已保存正式音视频节点及画布 revision；Worker 从私有原件生成实际 16kHz/mono PCM 后提交识别，将结构化结果私有存储并核对摘要。时间线采用必须先复核文字、时间和对应原件；原识别 SRT 与用户修订后的时间线分别保存。

取消已提交识别时保留连接，等待原生请求实际结束；网络或进程中断后不能证明已停止的任务保留 `awaiting_reconciliation`，不把客户端取消报告为远端停止，不重复提交识别。单任务原件准备最多 5 分钟、识别最多 20 分钟、最终登记最多 1 分钟，Activity 为 30 分钟。语言准确率、目标设备和真实剧集文本须独立验收，小模型或合成样本不能作为准确率保证。

### 6.2 完整项目内容复制

项目复制沿既有 API、Go Worker 的 flow/media 队列、Relay、PostgreSQL 与私有对象存储。部署前按目标 Schema 准备复制结构，预建 `lanverse.workspace.project_copy_requested.v1` 与 `lanverse.workspace.project_copy_changed.v1`，并让 API/Worker/Relay 运行同一组已验证代码；不能只更新页面或 Relay 就声称执行可用。当前 Schema 描述不可变冻结清单、命令与内容回执，以及 Worker 所有的阶段/对象意图字段；既有库只执行已核验、已审阅的实例增量，不通过重建库应用。

副本在 copying 阶段不进入普通项目、画布或媒体查询；只有全部原件/衍生物、画布、参考和回执核验完成，才原子发布 active/succeeded。源项目可继续编辑，复制只使用受理时冻结内容；复制期间的来源 pin 和工作事实阻止生命周期变更，不清理源对象。副本使用新 UUID/私有键与零预算，不复制源 Operation、费用或执行事实。当前实现内容范围与源 units/chat 等未决项以 [Design §12](../design/工作台设计.md) 为准。

复制详情和列表支持刷新恢复。未知创建/控制响应保留原 UUID 幂等键、原正文与修订，仅人工同键核验；不能以客户端超时判断没有副作用。普通失败按 retryable 恢复原清单；needs_reconciliation 的失败使用显式核验，保持旧 attempt/对象键/摘要。execution_unconfirmed 表示原 Worker 的实际退出未确认，此时禁止核验重启。已开始写入但目标不存在不证明原写入停止，仍保留 object_absence_unknown，不重写。取消只登记意图，Worker 核对自己未发布目标的对象归属并清理后才 cancelled；实际完成的项目不能通过取消撤销。

### 6.3 离线视频深度处理

视频深度沿同一 Go API/Worker/Relay、私有媒体、PostgreSQL、Kafka 和 Temporal 执行。先按目标 Schema 准备深度任务结构，预建 `lanverse.mediatool.depth_command.v1`，再同步更新三个进程。当前 Schema 保存永久来源/命令/对象意图，只开放任务状态及实际写入、删除回执的必要列更新。不得通过重建库或重新运行旧迁移覆盖业务数据。

当前正式 profile 仅接受已真实验证的 Apple Silicon `mps`。原生依赖为 Python 3.11.15、PyTorch 2.14.0；全部固定包版本见 `backend/internal/mediatool/adapter/videodepth/requirements.txt`。在仓库外创建独占 Python 3.11 venv 并安装该文件。安装与模型下载只能在部署阶段进行，执行任务不会联网安装、更新或回退设备。CPU/CUDA/Linux/Windows 尚未完成该 profile 的实际验收，当前生产配置拒绝 CPU。

模型代码固定为 Video Depth Anything `4f5ae23172ba60fd7bc11ef671cca678842c7072`。部署时先在仓库外检出该 commit，再按 `backend/internal/mediatool/adapter/videodepth/source_manifest.json` 的 `files` 清单复制并逐文件核对 SHA-256，形成只含 18 个清单文件的只读运行目录；完整上游 checkout 不能直接作为运行目录。清单包含 Apache-2.0 LICENSE 及模型实际 import closure，排除未使用的 CLI、Gradio、streaming 与 `utils/dc_utils.py`。运行目录聚合 SHA-256 为 `275d52984b0f60536f53e778c8d38b082a8ff945b174f49d449e6860d1ee0342`，Runner 再次严格验证全部文件、符号链接和额外内容。

Small 权重使用官方仓库固定 revision `256875362cff76724b920335dfb4b29dd611f66e` 下的 `video_depth_anything_vits.pth`，116440756 字节，SHA-256 `13379300b739e659f076a59d52e9801bd8d38c541a7e71f73bbca4dcfb013609`。只部署 Small，不替换为 Base/Large；完整许可和来源说明见 [Small 许可记录](../licenses/video-depth-anything-small.md)。

三个进程的启动环境必须同时提供四项配置（全留空表示关闭新建/重试，保留现有任务查询、取消和核验）：

```bash
LV_VIDEO_DEPTH_PYTHON_PATH=/absolute/runtime/venv/bin/python
LV_VIDEO_DEPTH_SOURCE_DIR=/absolute/runtime/vda-runtime
LV_VIDEO_DEPTH_MODEL_PATH=/absolute/runtime/video_depth_anything_vits.pth
LV_VIDEO_DEPTH_DEVICE=mps
```

这些路径属于部署配置，不接受 HTTP 或画布参数。Worker 内仅有一个原生 Runner，所有 Depth Activity 共用 concurrency=1；同一设备不能启动多份 Worker 绕过该限制。Go/FFmpeg 按最多 500MiB、15100ms、453 帧、推理最大边 960、原生进程组采样 RSS 8GiB 的合同验证真实字节。RSS 是有采样间隔的监控边界，不等于操作系统硬隔离。

结果经过独立完整解码、SHA、帧数和时长核验，保存三个私有对象并进入待审核状态。用户须预览并明确确认该 job revision 与 SHA，才会得到正式 ready/passed 视频和下载入口。取消先记录意图，实际进程组停止及未审核目标清理后才完成；未知执行不能被重试或核验绕过，未知对象写入只核验原 attempt，不重复推理或盲写。源视频保持完整。只有实际设备、固定模型与私有存储的运行证据能证明推理链可用；通用 Linux CI 的模型测试跳过不算运行验收。

### 6.4 项目库目录与复制分类

按目标 Schema 准备目录分类结构，同步更新 API/Worker/Relay。目录复用既有数据库、项目生命周期 guard、媒体授权和审计主题，没有新服务、运行参数或 Kafka 主题。当前 Schema 保存 actor/org 绑定的扁平目录、个人项目分类及永久命令；只开放名称、封面身份、分类及修订等必要列更新，不允许修改 actor/org 或永久请求回执。

项目根列表明确使用 `folder_id=root`，目录列表使用实际 UUID；旧未指定分类的客户端继续返回可访问项目全集。回收站不按目录过滤。移动只改变个人 placement revision，不改变项目内容 revision；目录重名合法，以 UUID 区分。封面只保存正式项目/image 身份，浏览器按短期授权预览，不保存 URL 或本机路径。

复制在同一受理事务冻结源分类并挂载尚未发布目标，不通过第二个页面请求移动副本。原键重放仍返回首次回执，后来的目录改名或源项目移动不改变冻结副本；真实 worker 发布先核对目标分类。取消确认全部私有目标清理后将未发布 copying 目标退休，其墓碑不可通过正式项目 Restore 恢复，目录版本及其他成员保持。整目录回收依次锁个人项目库、目录、排序后的全部成员，并在同事务核对当前六类工作；任一未知/活动工作阻挡整个回收，禁止循环单删造成部分成功。项目恢复位于根目录，目录本身不恢复。

完整命令、scope、CAS、永久回执和物理锁合同见 [Design §14](../design/工作台设计.md)。当前结构只由 Schema 定义；既有库只执行经审阅的精确实例增量，不能用 down/up 清理业务数据。普通测试库直接初始化Schema，空库验证不能代替既有库升级。

### 6.5 项目主图、永久生命周期回执与文档原件

按目标 Schema 准备文档与主图结构，API/Worker/Relay 必须使用相同版本。既有库增量升级保留旧行，按实际约束验证；当前结构以 Schema 为准，升级时既有行不自动回填或删除；原件 owning 读、下载、上传和完整 Copy 仍对不满足真实 TXT/DOCX 事实的旧行拒绝，不把 legacy PDF 当已支持格式。TXT/DOCX 限20 MiB，DOCX 解包、CRC、XML 深度与节点数量单独限界；不执行宏、外部关系或远程获取。文档上传沿现有版权确认、审核与 durable private Put；无 AV rendition。正式 attachment 下载实际读取并核完整 SHA/size，响应 private/no-store/nosniff，不向前端交付对象键。

当前 Schema 为项目保存可空正式 image asset 主图和永久 `workspace.project_change_command`。遗漏 cover 字段保持主图，明确 null 清除绑定；上传的正式图片仍保留在媒体库。设置、归档、取消归档、删除、恢复和无变化命令共享永久 actor/key 回执，受理与变更、审计及 Outbox 同事务。旧仍存在的兼容 infra 200 回执原样促进永久 owner；已经被删除或覆盖的旧24小时历史无法追溯重建。应用角色只可 SELECT/INSERT 永久命令，UPDATE/DELETE 被 ACL 与不可变触发器阻止；create/defaults 的既有24小时合同没有在此阶段升级。

主图完整 Copy 在 admission 永久冻结独立目标 UUID，未发布 target 数据库绑定先 null；实际 media Register 后同事务取证并绑定，保持正式 FK，publication 重读并核对当前 target 的正式私有图片。主图与文档不新建服务、bucket、namespace、topic 或凭据。部署前核验原数据库身份、已有目录/媒体结构及所有拥有的未终态工作；暂停自有 API/Worker/Relay 后执行经审阅的实例增量，核对数据行保留再以同一验证产物重启，不能重置业务库。

### 6.6 复制取消清理的必要列授权

当前 Schema 包含媒体 Copy `FinishCleanup` 所需的精确授权，只授 `media.media_asset` 的 `is_delete/delete_time/purge_after` 三列 UPDATE。保留既有 revision/SHA 权限，不授物理 DELETE、全表 UPDATE、project_id 或 object_key 改写。既有库若缺失这项权限，增量只改变必要授权并保留所有对象和业务行；变更前核验实例、原权限、未收敛 Copy/上传/Operation 及冻结 SQL SHA，应用后复核精确权限和保留计数。不能用数据库 owner 测试成功替代实际 lanverse_app 取消链的验证。

媒体历史冻结只允许 owning Copy 协调器传入明确同项目文档引用，来源仍需具备完整可核验原件。普通下载、素材引用和导入不开放回收原件；没有完整 owning 历史引用不得扩大冻结范围或从任意 JSON 猜测资产。剧本及素材库结构与真实业务须独立验收，精确列授权验证不证明其他模块已升级或完成验收。

## 7. 初始化与种子数据

[`backend/db/schema.sql`](../../backend/db/schema.sql) 是当前已实现业务结构的唯一事实源，事务由调用方提供；文件不包含顶层 `BEGIN/COMMIT`。以下初始化命令只能用于新空业务库，由受控环境提供独立表所有者 `LV_SCHEMA_DB_DSN`；管理员先预置 `lanverse_app NOLOGIN NOSUPERUSER`，再按 §5.1 创建/绑定应用登录账号。执行失败须整体回滚，不能改为忽略错误继续执行。Schema 按执行时 UTC 当前月创建 Outbox、审计与供应商调用当前及未来三个月分区；既有维护命令仅继续预备 Outbox/审计后续分区，供应商调用的周期维护计划另行接入，不把初始化窗口视为持续维护已完成。

既有业务库不得执行初始化文件或重建覆盖。先核验实例、备份、实际结构与未收敛工作，对照部署版本 Schema 形成增量 SQL，审阅并在隔离副本验证后显式执行，保留结构与数据验证记录。该增量是发布/实例的执行证据，目标结构仍以 Schema 为准。当前 CLI 不提供自动迁移或自动差异应用命令。

## 8. 扩展路径

准备远程部署后按实际负载评估以下扩容动作；自动扩缩容计划在需求达到阈值时接入。

| 触发                         | 动作                                                                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
