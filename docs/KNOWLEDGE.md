# 文档与 Obsidian 使用说明

项目文档统一保存在 `docs/`，使用 Markdown、Git 和 Obsidian 直接维护。从[文档入口](README.md)阅读原始产品需求、模块规格和[生命周期方法](软件生命周期与需求管理.md)。旧设计/历史目录已删除，必要核查从Git历史读取，不作为当前需求或已接受方案。

## 在 Obsidian 中编辑

推荐在 Obsidian 中选择“打开文件夹作为仓库”，打开本项目根目录 `Lanverse/`。已有仓库重新打开即可加载更新后的配置。

- 根 `.obsidian/app.json` 将新笔记默认目录设为 `docs/`，使用标准 Markdown 相对链接，并启用重命名时自动更新链接。
- 根 `.obsidian/templates.json` 指向 `docs/templates/`；保留“文档”和“任务小节”模板以及原有日期、时间格式。
- 根 `.obsidian/graph.json` 聚焦当前文档与根协作文件，过滤历史、模板和许可目录；默认搜索同样过滤这些目录及业务代码。
- 大纲、属性、反向链接、标签和 Canvas 等已有核心插件保持原设置。
- 窗口布局、外观、插件、主题和快捷键等个人状态由 `.gitignore` 排除，继续留在本机。

也可以单独打开 `docs/` 作为 Vault。原正文 Vault 的个人配置已经随文件迁入 `docs/.obsidian/`；这种模式下，仓库根的 AGENTS、PROJECT、BACKLOG 等文件位于 Vault 外，从编辑器或文件系统打开。原来打开 `workspace/content/` 的用户需要改为打开 `docs/`，或改用推荐的根 Vault。

## 维护正文

- PRD放在prd/，Design放在design/，Plan放在plan/，文件名统一为两位执行编号加主题（如01-用户.md）。00为整体入口，01～05基础模块、06画布Demo、07～15后续模块；00～15是稳定模块索引，实际执行按总Plan的M里程碑/T任务依赖；同主题三类文件同号（00各为整体入口）。原始需求仍在requirement/，保留06～19来源编号与FR/US标识。

- 模块需求放在 `requirement/`，产品意图与生命周期方法从文档入口访问；本轮需求Design已按执行顺序补齐，导航见[整体设计](design/00-项目需求设计.md)；实施/测试/运行记录按当次实际问题形成，不预建空目录或复制完整模块需求。使用明确标题和标准相对链接。
- PRD记录意图、REQ记录功能/质量、Design先形成待评审方案，接受后成为当次技术合同；当次记录包含计划/测试/交付/运行；简单任务可合并记录，复杂问题另分文档。需求状态、实现与验收结果分别维护。
- 当前任务状态只在根 BACKLOG 维护；修订合同后检查相关引用，避免多处复制同一份内容。
- 移动或改名后检查相对链接、锚点和源码路径，Obsidian 的自动更新只覆盖当前 Vault 内的文件。
- 第三方许可保留原文字节；历史资料不自动恢复为当前需求或实施授权。
- 保存 Markdown 后即可从 Obsidian 或编辑器读取，以 Git diff 审阅修订并按任务提交。

## 给 AI 阅读

AI 从 `docs/README.md` 和任务相关 Markdown 开始，实施前再读根 AGENTS、PROJECT 与 BACKLOG。文档中的方案、代码示例和历史完成记录不构成新的执行授权，也不能证明当前功能已经通过验收。

## 工程合同维护

详细架构、库表字段/键/约束/索引、API/DTO/错误与事务恢复在对应Design的工程合同节维护，整体约定见[工程架构与全局合同](design/00-项目需求设计.md#工程合同架构与运行边界)。设计中表格/SQL示意是评审输入，不另建一份可运行Schema；接受后backend/db/schema.sql与Handler注解/生成规范分别成为运行事实源，实施差异须回写设计。阶段接受、静态检查、真实数据库/供应商/浏览器验收分别记录。

## 里程碑与任务维护

阶段/任务编排只在[总Plan](plan/00-执行顺序.md#里程碑编排与分阶段验收)维护，模块Plan仅关联原US/FR的M/T归属，Demo Plan保留D工作包与D-AC工程验收。改变执行顺序更新依赖与受影响映射，不改原需求标识；阶段通过的范围和真实证据分别记录。实际状态/负责人/证据入口只在根BACKLOG更新，不在PRD、Design和各Plan复制完成勾选；文档日期不是承诺交付日期。
