# PRD 00：浮光原始产品需求

设计入口：[Design 00](../design/00-项目需求设计.md)。当前是待评审方案，接受后再按本次闭环细化技术工作项；原始需求与验收标识不变。

## 1. 概述

浮光帮助制作者在同一项目中从剧本组织分集、设定、镜头、生成候选与素材，并通过故事板和画布完成内容组织。当前前端已展示这些页面，真实认证、持久化、供应商及费用尚未逐项验收；本PRD与模块规格是待评审的原始需求整理稿。

## 2. 参与者与决策职责

| 角色            | 决策与责任                                        | 当前情况                                  |
| --------------- | ------------------------------------------------- | ----------------------------------------- |
| 产品负责人      | 确认用户价值、范围、业务规则、需求基线及用户验收  | 用户提出原始需求；正式负责人/联系人待落实 |
| 制作者代表      | 验证创作链、批量操作、参考/选定及失败提示是否可用 | 当前无独立访谈或真实生产使用证据          |
| 工程负责人      | 评审模块方案、接口/数据、外部依赖与可行性         | 人员待落实；复用已接受的工程工具          |
| 测试负责人      | 评审可测性、执行功能/质量验证并记录缺陷           | 人员待落实；当前仅有文档和既有页面证据    |
| 管理/运行负责人 | 账号/凭据/模型管理、运行风险、发布与恢复          | 人员及实际部署条件待落实                  |

职责用于明确谁决定问题，不要求增加组织层级；同一人可承担多个角色。

## 3. 背景与问题

用户明确指出“页面已经实现，但功能没有跟上”，要求先整理完整原始需求，再按推荐顺序分别实现业务模块。此前规格侧重页面控件和设计参考，缺少统一功能/质量表述、具体验收和生命周期管理，还混入了未接受的表结构与样例值。

本轮以已有需求、现有源码和用户反馈为输入，保留原有字段/动作并记录差异；不把已实现界面当成已实现业务，也不凭旧架构裁掉现有需要。市场规模、竞争优势、付费意愿和真实使用规模尚无证据，不在本文臆造。

## 4. 产品目标与成功标准

| 目标                 | 可验证结果                                                                                                 | 当前证据/限制                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 原始需求可审阅       | 每个业务模块都有角色/价值、范围、功能、质量、数据约束、验收与缺口；来源内容有去向                          | 本轮整理，不等于基线获接受                                |
| 建立真实创作链       | 指定用户可注册/登录，创建有持久身份的项目，导入支持格式，确认设定/镜头，生成并人工采用真实候选，刷新可恢复 | 需真实认证/存储/媒体/供应商验收，首次镜头形成等规则待确认 |
| 失败可恢复且不误收费 | 权限拒绝、并发冲突、失败与未知状态可辨；未知结果先核对，重复请求不重复产生任务或费用                       | 费用确认/核对机制及供应商条件待确认                       |
| 质量与运行可测       | 按各业务文件内的非功能要求测安全、可靠、数据真实性、性能/容量、可访问和恢复；每项有实际证据                | 无实测依据的阈值保持待确认，不承诺SLA或容量               |

以上是本项目的目标提案。首轮接受范围、时间窗口、用户样本和质量阈值尚未确定，不能编造SMART数字、上线日期或商业KPI。每轮实施前用接受的范围及完成条件补上时间与责任人。

## 5. 使用者与场景

- **访客/待改密用户**：建立或恢复可用身份，清楚错误和联系管理员的途径。
- **制作者**：把剧本和素材组织为同一项目，管理设定和镜头版本，生成、比较并采用候选，查看真实进度和待处理。
- **管理员**：管理账号、供应商和模型，查看脱敏审计、健康和需要核对的风险。

当前角色只有制作者与管理员；组织、邀请、复杂协作角色、订阅/支付产品均没有本轮原始需求依据。是否将文件/剧本发送供应商、运行于本机或远端的边界需在数据流与部署需求确认。

## 6. 用户价值

制作者获得一致项目上下文、可复用且版本明确的参考、可比较的真实候选和刷新后仍存在的内容；减少重复录入、选错版本、失去草稿与不确定情况下重复付费。管理员获得安全配置、可追踪责任和真实运行风险，避免用固定成功提示判断系统正常。

这些是需求推导的预期价值，尚未通过真实用户研究或对比实验验证；不宣称比竞品更强。

## 7. 需求与范围

### 用户流程与界面依据

[业务流程与用例模型](../requirement/03-业务流程与用例模型.md)描述端到端及失败路径；[界面与交互](../requirement/05-界面与交互需求.md)规定共享交互。模块文档保留源码/Figma定位，视觉依据不能代替业务合同。

### 功能性与非功能性需求

功能以[总表中的06～19模块](../requirement/01-需求总览.md#建议执行顺序)为唯一规格：用户、项目、素材、供应商、模型、剧本、设定、镜头、生成、故事板、画布、分析、审计、健康。模块内部列需求和验收，仍是一模块一文档。

功能性需求、非功能性需求与验收条件都直接写在相应业务模块文件；无需另读独立类别规格。数据/业务限制写在需求，实际表、接口、服务和设施选型在需求/Design获接受后决定。工程工具与边界沿用[PROJECT](../../PROJECT.md)和[AGENTS](../../AGENTS.md)，不在PRD预建实现结构。

### 假设、缺口与非目标

[缺口登记](../requirement/01-需求总览.md#需求缺口与确认)保留原7类问题并补充模块细节、源码差异与质量/运行目标。缺少规则的功能仍在范围中，但对应验收保持待定；提案不表示已批准。

旧组织/邀请/支付/协作平台、独立剧本工作台、导演台、时间轴、3D/深度工具、素材包、永久清理及完整报价/对账平台不自动加入本轮。既有数据迁移、清理与真实收费调用需要当次明确条件，不能借文档整理执行。

## 8. 交付与后续

先评审本文、模块需求与缺口，再选择一个模块的最小闭环形成Design并接受，随后细化实施和测试。建议基础身份/项目→素材/供应商/模型→剧本/设定/镜头/生成→故事板/画布/分析→管理查询；权限、审计、幂等和恢复随业务接入。

每一轮以真实用户结果和功能/质量证据界定完成，未实施能力及外部条件单列。当前没有已批准的首发集合、工时或发布日期，不因编号后置而删除需要；未来版本仅在需求变更后确定。完整阶段、评审条件、追踪、发布、运行维护与退役方法见[软件生命周期与需求管理](../软件生命周期与需求管理.md)。
