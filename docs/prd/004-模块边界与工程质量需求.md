# 模块边界与工程质量需求

## 1. 目标

在不拆微服务的前提下，让开发者从一个入口理解和运行后端：业务边界明确、目录只
反映真实能力、数据库按一条可审计历史演进。结构重构不能改变已有会话和 catalog
契约，也不能借机实现后续业务。

## 2. 模块职责

| 模块 | 唯一职责 | 创建时点 |
| --- | --- | --- |
| identity | 用户、邀请、密码、会话、角色 | 已存在 |
| catalog | 来源导入、溯源、模板/示例、分类、搜索 | 已存在 |
| creation | 草稿、生成、额度、对象、本人作品 | S4 开始时 |
| operations | 来源启停、审核、下架、删除、预算和审计 | S6 开始时 |

API、Worker、Scheduler 是运行入口，不是业务模块。PostgreSQL、RabbitMQ、MinIO 和
生成供应商是基础设施，不建立同名业务层。

## 3. 工程规则

| ID | 规则 |
| --- | --- |
| M-BR-01 | 后端业务代码只有 `backend/src` 一个 source root 和 `thief` 一个包 |
| M-BR-02 | 只创建当前实现的模块；禁止空模块、空 schema、空 migration 和占位 Port |
| M-BR-03 | model 只依赖标准库；use case 不导入 FastAPI、Celery、SQLAlchemy、MinIO 或供应商 SDK |
| M-BR-04 | repository 只写所属 schema，跨模块引用使用 UUID，不建立跨 schema ORM/FK |
| M-BR-05 | Alembic 只有一个 `versions/`、一个线性 head；migration 只描述数据库结构变化 |
| M-BR-06 | migration 必须提供可执行 upgrade；可逆变更提供 downgrade，不可逆时写明恢复方式 |
| M-BR-07 | API、Worker、Scheduler 从同一 `thief` 包启动，配置集中且按进程校验 |
| M-BR-08 | 文件按真实职责拆分，长期目标不超过 200 行；不为形式创建目录层级 |
| M-BR-09 | 前端位于 `frontend/`，只通过 HTTP/API 契约使用后端，不导入 Python 实现 |
| M-BR-10 | 只有出现异步重试、外部替换或第二实现时才引入 Event/Port/Adapter 抽象 |

## 4. Migration 用户契约

- `make migrate` 把空数据库升级到唯一最新版本。
- `make migrate-down` 能在本地/CI 将可逆结构回到 base。
- `alembic heads` 必须输出且只输出一个 revision。
- 新 migration 按 `0001_initial → 0002_<capability>` 顺序命名，不按模块建立目录。
- 当前 pre-release 基线允许一次性 squash；保留数据的环境出现后不得修改已发布 migration。
- 本地重建必须是显式命令，不把删库藏在应用启动或普通 migration 中。

## 5. 工程验收标准

| ID | 标准 |
| --- | --- |
| AC-M01 | `backend/src/thief` 是唯一后端包，Make/CI 不拼接多个业务 source root |
| AC-M02 | 仓库不存在未实现模块占位文件、空业务 schema 或空 migration |
| AC-M03 | 架构测试阻止 model/use case 导入外部框架或供应商 SDK |
| AC-M04 | identity/catalog repository 只写自己的 schema，且无跨 schema ORM/FK |
| AC-M05 | `alembic heads` 只有一个 head，空库 `upgrade head` 成功 |
| AC-M06 | `downgrade base → upgrade head` 后表、约束和 revision 与首次升级一致 |
| AC-M07 | Web/API/Worker/Scheduler 构建启动，API/Worker/Scheduler 来自同一 Python 包 |
| AC-M08 | 结构重构前后的 identity 与 catalog 单元/集成/API 契约结果一致 |
| AC-M09 | 自动检查拒绝空模块、多个 source root、超 200 行业务文件和无理由层级 |
| AC-M10 | 新业务模块必须随首个用例、测试和 migration 一起创建，不允许预建模板 |

## 6. 测试要求

Red 先固定目标目录、禁止项、单 migration head 与现有行为；Green 只移动和合并现有
实现。验证必须覆盖空库 migration、完整 downgrade/restore、unit、integration、
architecture、lint、typecheck、build 和四进程 runtime。前端无行为变化时不重复做
浏览器业务验收；结构完成后至少验证 Web 健康页和登录主路径未回归。

## 7. 非目标

本任务不实现 DiffusionDB 导入、目录 API/UI、生成、作品、管理、outbox/inbox、
微服务、动态插件或通用 repository。也不保留旧目录兼容导入；所有调用一次迁移到
新包，深入修正 source root 和 migration 根因。

## 8. 发布门禁

AC-M01 至 AC-M10 全部通过；CI 使用新结构完成空库 migration、测试和四进程运行；
本地与远端 `main` 一致且工作区干净。
