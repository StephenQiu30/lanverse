# 产品范围与验收基线

- 状态：已接受目标
- 来源：[完整设计基线](../design/0001-AI短剧制作平台完整设计基线.md)
- 派生规格：[平台 V1 需求规格](../requirement/0001-平台V1需求规格.md)

## 结论

本平台的产品范围是面向 AI 短剧生产的端到端 AI Native Production Platform。用户输入故事或剧本后，平台通过 AI 与人工审核共同完成剧本结构、Production/Story Bible、角色、场景、分镜、镜头图片、动态视频、声音、字幕、合成、审核与导出，并保证失败恢复、候选选择、局部重生成和全链路追踪。

真人短剧与 AI 漫剧共享同一 Production Core。差异只能由 Preset、`EffectiveStyleSnapshot`、Skill、Model Policy、QC Policy、Motion Strategy 和 Render Policy 表达，不建立两套 Backend、Workflow 或 Agent。

## 用户入口

- Guided Studio 面向普通创作者，以“剧本—角色—场景—分镜—镜头—声音—审核—成片”呈现业务步骤。
- Canvas Studio 面向高级创作者，以 Node、Edge、Subflow、Human Gate、局部执行与协作提供可视化编排。
- 两种入口只改变 Authoring 体验，发布后都生成不可变 Authoring Revision，并编译为同一种 Workflow Definition。

## 端到端闭环

```text
Project → Script → Production / Story Bible
→ Character / Scene → Storyboard → Shot
→ Image Candidate → Motion / Video Candidate
→ Voice → Subtitle → Render
→ QC → Human Review → Export
```

所有模型生成输出先登记为 Candidate Artifact；Artifact 通过完整性、安全性与可用性校验并进入 `READY` 后，才可建立 `GenerationCandidate` 供质量门和人工选择。所有可复用身份及其业务状态进入 Asset，所有不可变生产输出登记为 Artifact。人工可在 Storyboard、Reference、Image Candidate、Video Candidate 和 Final Episode 处审核。

## 产品发布门

为消除“完整平台范围”和“早期业务闭环”混用的歧义，产品采用两个发布门。发布门是能力验收口径，不等同于[平台 0→1 交付计划](../plan/0007-平台0到1交付计划.md)的阶段编号：

- `Guided MVP`：完成从剧本到成片的 Guided Studio 业务闭环，以及恢复、局部重跑、人工审核、基础成本追踪和可审计执行。
- `Platform Complete`：在 Guided MVP 之上完成事件投影、Search、完整成本治理与可观测性，以及 Canvas、多人协作和 Copilot。

两者都属于产品路线；只有达到第二个发布门才可宣称完整平台目标全部完成。

## 非目标

V1 不建设通用 AI 视频平台、Premiere 级时间线、复杂 3D、MV/广告/直播、Workflow/Skill/插件市场、任意代码执行节点、无限循环 Agent、多地域多活或超大型企业权限系统。

## 产品验收

Guided MVP 至少满足：

- 可以创建项目、选择 Preset、导入剧本并完成角色、场景、分镜、图片、动态镜头、配音、字幕、合成、审核和导出。
- 服务重启后任务可恢复；单 Shot 与失败节点可局部重跑；Human Gate 可暂停并继续。
- Human Gate 展示并冻结真实候选；决议必须绑定精确候选与对象版本，调用方不能在继续执行时改写已提交决议。
- 相同 Workspace 与相同冻结执行输入可复用已提交节点输出；输入、定义或运行契约变化必须失效，跨 Workspace、运行中结果或冲突输出不得命中。
- Agent 输出、Prompt、Skill、Model Policy、费用与 Tool 权限可追踪。
- 所有生产结果登记 Artifact，媒体通过私有对象存储与 Presigned URL 访问。
- 角色、场景和画风达到已定义的基本一致性；用户可选择候选并只修复错误镜头。

Platform Complete 还必须通过 Canvas 模式的 `AuthoringDraft/AuthoringRevision`、Node Registry、Workflow Compiler、局部执行、Dirty/Cache、Yjs 协作与 Canvas Agent GraphPatch 的端到端验收。量化质量、成本、并发和恢复目标需在各阶段 Acceptance 中按真实基准补齐，不能在本基线中虚构通过值。

## Shot 媒体链路的首个增量验收边界

在接入真实图片 Provider 与单 Shot Workflow 前，系统必须先完成可独立验收的图片 Artifact Readiness：真实图片先进入私有 Staging Object，经 Backend Asset Owner 核对完整字节、SHA-256、大小、媒体类型和图片可解码性后才能成为 `READY`。损坏、伪报或不可解码对象必须进入 `QUARANTINED`；对象存储暂时不可用不得被误报为损坏或就绪。

同一个 Provider/Worker Source Output 或同一个幂等命令无论重复到达、并发到达或在回执前重试，都只能形成一个 Artifact、一个当前 Location 和一个对应命令回执。下游 Generation Candidate、候选选择、Production Binding 与 Workflow Node 在 Artifact 非 `READY` 时必须 fail closed。本增量不包含 Provider 调用、费用、QC、候选选择、图片审核 UI 或 Shot Workflow，不得据此宣称已经完成图片生成或单 Shot 媒体重跑。

## 图片 Candidate 与确定性 QC 增量验收边界

图片 Artifact 进入 `READY` 后，Generation Owner 才能为同一个 Provider Source Output 建立唯一 Candidate，并冻结 Artifact Revision/Hash、图片元数据和确定性 QC Policy Snapshot。首版确定性 QC 必须真实判断允许的媒体类型、最小宽高和最大像素数，形成不可变 QC Report；通过与失败必须使用不同状态和稳定失败码，不能把“可解码”直接等同于“质量通过”。

重复或并发登记不得产生重复 Candidate、QC Report 或相同命令的不同回执；Pending、Quarantined、非 Provider Job 来源、Artifact 绑定漂移和 Policy 输入漂移必须 fail closed。该增量只交付 Candidate/QC Owner 边界，不包含真实 Provider Submission/Callback、语义 QC、人工选择、Production Binding、图片审核页面或单 Shot Workflow。

## 图片 CandidateSelection 增量验收边界

人工选择只能从 Review HumanTask 已冻结、且不可变 `selected` ReviewDecision 明确选中的 Candidate 产生。Generation 必须从 Review Owner 重读 Task/Decision，并重新验证冻结集合内全部 Candidate 的确定性 QC 与当前 Artifact READY；客户端不得在应用阶段替换候选、Reviewer、Subject Revision 或选中值。

同一 HumanTask 和 ReviewDecision 最多形成一个 CandidateSelection；重复或并发应用只能返回同一 Selection，候选事实、决议事实或幂等输入漂移必须拒绝。Selection 是后续 Production/Workflow 可以引用的唯一选择事实，但本增量不包含 CandidateSet Workflow 输入展开、图片审核页面、Production Binding、Temporal Signal 或单 Shot Workflow。

## 图片生成日配额增量验收边界

在发起真实图片 Provider 调用前，Workspace Owner 必须能为 Project 设置 `generation.image` 的 UTC 日单位上限；任何预留都由 Backend 根据当前 Policy 和服务端时间确定窗口，客户端不能自报剩余额度。并发预留不得突破上限，同一 Source 或同一幂等命令不得重复占用。

已预留额度只能通过明确的消费或释放命令结束；结果未知时保持占用，不能先释放再盲目重提。重复消费/释放不得产生第二次数量变化，已消费额度不能释放，所有 Counter 必须非负且可从 PostgreSQL Reservation 事实对账。本增量只交付 Quota Owner 生命周期，不包含价格、预算、Cost Ledger、Generation Intent、Execution Authorization、真实 Provider 或前端管理页面。

## Project Budget 唯一事实增量验收边界

Project 的金额预算只能由 Cost Owner 保存和修改，Production Project 不得继续返回或写入第二份 `BudgetLimit/Currency`。Workspace Owner 可以为 Project 创建或按明确 Revision 更新当前 BudgetPolicy，其他当前成员只能读取；金额必须使用精确 Decimal 与单一 Currency，重复命令不得产生第二次更新。

未设置 BudgetPolicy 必须明确返回未设置，不能隐式采用零金额或 Project 默认币种。旧 Production Budget 路由直接移除，调用方必须使用新的 Cost 契约，不建立兼容转发或双写。本增量不包含 Price、Estimate、Cost Reservation、Ledger、Provider 调用或前端预算管理页面。

## 图片价格与费用估算增量验收边界

Workspace Owner 必须能在 Project Budget 已设置后为 `generation.image` 追加精确 PriceQuote；报价币种必须与 Budget 一致，历史 Quote 不得被原地修改，已有 Quote 后 Budget 也不得切换币种。Editor/Owner 发起图片生成前，Cost 必须根据服务端当前 Quote 和正整数 Units 创建不可变 Estimate，并冻结当时的 Budget 与 Quote Revision。

Estimate 调用方不能自报单价、币种、总额或 Quote Revision。同一 Generation Intent Source 的并发或重试只能产生一个 Estimate；修改 Source 对应的 Metric/Units、复用幂等键提交不同输入或篡改已保存金额必须失败关闭。本增量不包含预算预留、Ledger、Provider/Model 路由、汇率、前端价格管理页面或 GenerationIntent Coordinator。

## 费用预留与追加式账本增量验收边界

Editor/Owner 只能从 Cost 已冻结的 Estimate 创建费用 Reservation；并发预留不得使 Project 当前 Reserved + Settled 超过 Budget，同一 Estimate 不得重复占用。Budget 下调不能低于已经预留和结算的总额，系统不能用 Redis、客户端余额或第二份 Counter 作为金额正确性来源。

结算只能提交稳定 Usage Receipt ID 与实际 Units，实际金额必须由 Cost 按 Estimate Unit Amount 计算且不能超过预留；释放只归还未结算 Reservation。每次预留、结算、释放都必须追加不可变 Ledger Entry 并与 Reservation/CommandReceipt 原子提交；重复、竞态、币种或事实漂移不得产生第二笔金额变化。结果未知时保持 Reserved，不自动释放。本增量不包含公开 REST、Execution Claim/Authorization、Provider Receipt 校验、自动 Reconcile、Outbox 或前端账本页面。

## Generation 高成本准备与执行授权增量验收边界

Workflow 外部 AI Node 必须以冻结的 WorkflowRun/NodeRun/Input Hash 和正整数 Units 创建唯一 GenerationIntent；首次或新幂等键准备必须校验真实 Workflow Run/Node 归属、执行态、Runtime Claim、发起人与 canonical `node-input-v1` Hash，伪造或已不可执行的来源不得产生占用。Generation 必须在一个 PostgreSQL/GORM 外层事务中调用 Cost/Quota Owner，同时提交 Intent、Estimate、两类 Reservation、Cost Ledger、Quota Counter 和全部 Receipt。Cost、Quota 或 Generation 任一步失败时不得留下部分 Intent、金额占用、Quota 占用或孤立 Receipt；GORM 嵌套事务能力被关闭时必须直接拒绝，不得退化为多事务兼容流程。

Execution Claim 与取消必须锁定同一 Intent 并互斥；Claim 派生的短时 Authorization 必须绑定 Input Hash、Fencing Version 与 Cost/Quota Reservation。授权到期、发起人撤权、Claim 或 Owner Reservation 漂移必须失败关闭，不能自动重新 Claim 或释放未知结果。本增量不执行 Provider、不创建 Provider Job/Callback、不伪造 Usage Receipt，也不提前实现 Outbox、Settle/Consume 或 Reconcile。

## Generation Provider 提交与结果对账增量验收边界

Project Owner 发布的图片 Provider Binding 必须追加版本且只保存非敏感 Adapter/Model/Credential Reference；Generation Request 创建时冻结当前 Binding。已 Claim Intent 只能在重新验证短时 Authorization、当前发起人权限以及仍为 Reserved 的 Cost/Quota 后创建唯一 Request/ProviderJob，并在事务提交后用稳定 Request Key 执行远程调用。同一 Intent 并发或崩溃重投不得产生第二次 Submit、第二个 Job 或新 Request Key。

Provider accepted、known failed、succeeded 与 outcome unknown 必须分开处理。未知结果保持费用与配额预留并只允许按原 Request Key Query；迟到 terminal Outcome 可完成对账，旧 accepted/unknown 不得覆盖 terminal。成功结果必须用稳定 Provider Event ID、实际 Units 和 Staging Output References 创建唯一 Provider Result Receipt，并与 Cost Settle、Quota Consume、Job/Intent 终态原子提交；明确失败则与双 Release 原子提交。任一 Owner 失败不得留下部分终态。本增量不包含真实云 Provider SDK、Callback 公网验签、自动 Staging、Candidate 自动登记、Fallback 或 Workflow 图片节点。

## Provider 成功输出物化增量验收边界

只有 Backend 重新核验为成功、Cost 已结算且 Quota 已消费的 Provider Job 才能物化输出；调用方不能自报或替换 Receipt Output。Provider Submission 必须冻结 Workspace、Project 和 Provider Job ID，Staging Object Key 必须属于 `staging/{workspace_id}/{provider_job_id}/...` 私有路径。每个输出必须真实经过 Asset `PENDING_VALIDATION → READY/QUARANTINED`，实际读取结果的 Hash、大小、媒体类型与解码宽高必须和 Provider Receipt 一致，只有完全一致的 READY Artifact 才能登记 Candidate 和确定性 QC。

Provider Receipt ID + Output Key 必须派生稳定的 Asset 登记、Readiness 校验和 Candidate 登记幂等命令。重复、并发、进程重启和部分完成不得产生重复 Artifact、Location、Candidate 或 QC Report；对象存储不可用保留待验证事实，隔离对象和元数据漂移失败关闭。本增量不新增物化状态表或补偿删除，不包含真实云 Provider、Callback、公网接口、Workflow 图片节点、CandidateSet、Human Gate 或 Production Binding。

## Generation CandidateSet 与 Workflow Human Gate 增量验收边界

已成功物化的 Provider Job 必须能够由 Generation 重新构造唯一 CandidateSet：只包含仍通过确定性 QC 且 Artifact 仍 READY 的 Candidate，成员按稳定顺序冻结，Content Hash 必须与后续 CandidateSelection 使用的 CandidateSet Hash 相同。调用方不能提交 Candidate ID 或 Set Hash；任一 Provider Receipt、Output、Candidate、QC、Artifact、权限或成员完整性漂移都不得打开人工任务。CandidateSet 不新增持久表，Provider Job、不可变 Receipt 与既有 Candidate/QC 是唯一重建依据。

Workflow Generation Human Gate 必须从冻结的 `generation_candidate_set` 输入通过 Generation Application Interface 展开真实候选，再由 Review Owner 冻结 HumanTask；`selected` 决议只能通过 Generation `ApplySelection` 产生唯一 CandidateSelection 和 `generation.candidate.select` Owner Receipt。重复/并发 Signal、Owner 已提交但 Temporal 结果未知以及服务重启只能重放同一 Selection、Apply Receipt 与 Signal Intent，不能重复选择或接受客户端替换候选。该 Generation CandidateSet 增量不包含真实 Provider Adapter、图片生成 Executor、Production Shot Binding、图片审核页面、ShotWorkflow 或单 Shot 重跑。

## Production Shot 图片绑定增量验收边界

只有 Generation Owner 当前仍可验证的 CandidateSelection 才能绑定到正式 Storyboard Shot。调用方只指定 Shot、冻结的 Shot Revision/Content Hash、Selection、Expected Current Binding Revision 与幂等键；Candidate、Artifact、Selection Hash 和 Selection Revision 必须由 Backend Owner 重读。绑定按 Shot 追加不可变版本，首绑从 Revision `1` 开始；并发替换、重复命令、跨 Workspace/Project、归档 Shot、撤权、Shot/Selection/QC/Artifact 漂移或 Expected Revision 不匹配必须失败关闭，不能覆盖既有版本或产生第二个当前结果。

本增量只交付 Production Owner 的图片绑定事实与 Generation Application Port，不包含真实云 Provider、图片生成 Executor、正式 Shot System Catalog、Temporal ShotWorkflow、Render、公开绑定 API 或图片审核页面；因此不能将“绑定可持久化”报告为单 Shot 生成或重跑已完成。

## 正式 Shot Workflow 后半程增量验收边界

已成功物化 CandidateSet 的单个 active Shot 必须能编译并启动独立 `lanverse.shot-production` Temporal Workflow，不能继续用 Episode Workflow 名称或测试 Catalog 代替。正式 Shot Catalog 必须从 Backend Owner 重读 Shot 与 CandidateSet，打开真实 HumanTask，由用户选择 Candidate，并在同一 Run 内产生 CandidateSelection、Owner Receipt、Signal Receipt、ShotImageBindingVersion 与成功 Node/Run Projection。重复 Start/Decision/Signal/Activity 不得产生第二选择或绑定；Shot/CandidateSet 跨 Workspace/Project、撤权、归档或 Hash/Revision 漂移必须失败关闭。

该增量不负责产生 CandidateSet，不选定或伪造图片 Provider，不实现 Episode 自动扇出、Motion/Video/Render、已绑定 Shot 替换图片或单 Shot 局部重跑。本地 Codex CLI 继续只用于 Agent 服务的文本/结构化 AI 调用，不作为图片产物来源。

## Shot 绑定目标与单 Shot 局部重跑增量验收边界

已成功首绑的 Shot 必须能从原 Shot Workflow 派生新 Run，在不重跑整集的前提下重新打开候选审核，选择另一个已物化候选并追加新的 Shot 图片绑定版本。新 Run 必须保持原 Definition/Snapshot，使用新 Run/Temporal 身份，并记录 Source Run 与 Rerun Root；重复重跑命令只得返回同一派生 Run。

绑定节点不得依赖发布时写死的当前 Revision。Shot 源节点必须冻结运行开始时的 Shot 与当前 Binding Target，最终 Production Owner 必须在事务中重新校验 Target Revision/Hash。两个并发重跑针对同一 Target 时只能一个追加成功，过期 Target、归档 Shot、撤权、候选/选择漂移和重放输入漂移都必须失败关闭。

本增量只对已成功物化的同一 CandidateSet 重新审核和绑定，不调用或伪造图片 Provider，不生成新 CandidateSet，不实现 Episode 动态扇出、前端局部修复界面、Motion/Video/Render 或最终成片。
