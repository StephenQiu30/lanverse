# PRD 文档

本目录存放产品需求类文档。

PRD 的核心目的不是堆叠描述，而是让需求更清楚，让代码更可验证，让错误更早暴露，让重构更安全。

PRD 只能在引用的全局 Design 与切片 Design 均为 `accepted` 后创建。每个纵向切片对应一份主 PRD，编号与范围以 [`ARCH-008`](../design/ARCH-008-交付切片文档链与工程结构设计.md) 为准；跨切片约束通过 Requirement/Design 引用复用，不复制成互相漂移的需求。

## 适合放入

1. 产品需求说明。
2. 用户故事与使用场景。
3. 功能范围与不做事项。
4. MVP 边界与阶段目标。

## 不适合放入

1. 详细技术实现方案。
2. 测试报告或验收记录。
3. 发布流程或 Git/PR 操作说明。
4. 临时需求讨论、执行 todo 或一次性过程记录。

## 命名建议

使用 `PRD-xxx-主题产品需求.md`，例如 `PRD-001-可信项目入口产品需求.md`。

## 推荐结构

PRD 建议按以下结构扩展：

1. `背景`：说明产品问题、用户价值、当前风险和为什么需要该需求。
2. `产品目标`：使用 SMART 和 BDD 场景描述目标，关键目标可写成 Gherkin。
3. `非目标`：明确首版不做什么。
4. `核心用户故事`：按用户类型、使用场景和验收标准展开。
5. `用户体验原则`：说明交互、反馈、状态可见性和边界提示。
6. `数据与权限边界`：说明默认收集、默认不收集、存储、删除和权限规则。
7. `状态模型`：列出核心状态、含义和流转约束。
8. `技术方案`：只写影响产品边界和验收的技术方案，不替代 design 文档。
9. `首版验收门禁`：列出必须满足的可验证验收项。
10. `待确认问题`：列出需要产品、研发、QA 或运营继续确认的问题。

## 强制可执行字段

1. frontmatter：`layer/doc_no/status/version/owner/inputs/outputs/downstream` 等 [`docs` 必要信息](../README.md#必要信息)。
2. 每条用户故事：用户、触发场景、目标价值、前置条件、主流程、失败/恢复和非目标。
3. 每条 `AC-PRD-*`：可观察行为、量化阈值、事实源、样本/环境、排除规则和最迟验证门禁。
4. 追踪：精确引用 Requirement 条款、Design 章节与 Design AC，并预留后续 Plan/Acceptance 编号。
5. 状态：存在未关闭 P0 产品决策、无法测量的目标或未追踪范围时不得转为 `accepted`。
