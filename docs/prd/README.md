# AI 视频生产平台 PRD 索引

> 文档职责：PRD 只定义用户价值、交付范围、业务规则、成功指标和可验收结果；稳定能力合同由 [Requirement](../requirement/README.md) 定义，系统边界由 [Design](../design/README.md) 定义，实施顺序由 [Plan](../plan/README.md) 定义，执行证据归档到 [Acceptance](../acceptance/README.md)。

## 2. PRD 状态

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `proposed` | 范围可审阅，但尚未形成交付承诺 | 评审范围、补齐前置决策 |
| `accepted` | 产品负责人接受范围、非目标和验收条件 | 按对应 Plan 开始实施 |
| `in_progress` | 已满足入口门禁并正在实施 | 持续记录测试与决策证据 |
| `verified` | 全部 P0 验收条件已有可复现证据 | 决定是否发布或进入下一切片 |
| `superseded` | 已由明确的新事实来源取代 | 保留历史引用，不继续实施 |

只有产品负责人可以把 PRD 从 `proposed` 调整为 `accepted`。实现完成不等于 `verified`；必须以验收目录中的证据为准。

## 3. 专业 PRD 的固定内容

每份切片 PRD 至少包含以下信息：

1. 产品决策、目标用户和用户结果；
2. P0 范围、用户主旅程、业务规则与失败路径；
3. 明确的非目标和需要前置确认的门禁；
4. 可计算或可观察的成功指标，不使用“体验良好”等模糊表述；
5. 使用 Given / When / Then 表达的验收条件；
6. Requirement、Design、Plan 与证据的双向追溯入口。

PRD 不重复数据库表、包结构、消息主题、类名或部署拓扑。需要改变这些实现边界时，先更新 Design，再同步 PRD 中受影响的用户合同。

## 4. 标识符规则

| 标识符 | 用途 | 示例 |
| --- | --- | --- |
| `PRD-<切片>-O-<序号>` | 用户或业务结果 | `PRD-A-O-001` |
| `PRD-<切片>-FR-<序号>` | 本次交付的产品功能 | `PRD-A-FR-001` |
| `PRD-<切片>-BR-<序号>` | 跨功能业务规则 | `PRD-000-BR-001` |
| `PRD-<切片>-M-<序号>` | 成功指标 | `PRD-C-M-001` |
| `PRD-<切片>-AC-<序号>` | 可执行验收条件 | `PRD-E-AC-001` |

标识符一经用于 Plan、测试或验收证据，不因文字润色而复用或重新编号。删除的合同保留编号并标记 `retired`；不得让同一编号表达另一项含义。

## 5. 追溯与变更规则

标准链路为：

`Requirement → Design → PRD 功能/验收条件 → Plan 工作包 → 自动化测试或人工步骤 → Acceptance 证据`

- 每项 P0 产品功能必须映射到至少一条 Requirement；若没有对应稳定合同，先修改 Requirement。
- 每条 `PRD-*-AC-*` 必须在对应 Plan 中指定工作包和预期证据包。
- 验收证据记录执行时的提交、环境、数据集、命令或步骤、预期结果、实际结果和结论。
- PRD 范围变化时，同时检查 Plan 和尚未执行的验收矩阵；已执行的旧证据不得自动沿用。
- 公开接口只表达当前合同，不在路径中加入 `v1` 等版本段，也不建立兼容层；任何相反需求必须先解决 Requirement 与已接受 Design 的冲突。

## 6. 进入实施的统一条件

PRD 只有同时满足以下条件才可进入 `in_progress`：

- 上游 Requirement 和 Design 没有影响本切片的未决冲突；
- 前置切片的退出证据全部通过；
- 外部 Provider、样本数据、版权和安全条件真实可用；
- 对应 Plan 已覆盖全部 P0 验收条件和失败注入；
- 产品、研发和验收责任人对非目标及停止条件达成一致。
