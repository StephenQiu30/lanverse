# PRD 文档

本目录存放产品需求类文档。

PRD 的核心目的不是堆叠描述，而是让需求更清楚，让代码更可验证，让错误更早暴露，让重构更安全。

当前 MVP 只有一个纵向闭环，下游产品草案为 [AI短剧端到端产品需求](01-AI短剧端到端产品需求.md)。它在 Requirement 与 Design 均 `accepted` 前保持 `draft` 且不参与门禁；上游接受并通过 `design_entry` 后，PRD 才进入正式评审，转为 `accepted` 后才能进入 Plan。跨文档约束通过精确引用复用，不复制成互相漂移的需求。

## 适合放入

1. 产品需求说明。
2. 用户故事与使用场景。
3. 穷尽式 MVP 产品清单。
4. MVP 边界与阶段目标。

## 不适合放入

1. 详细技术实现方案。
2. 测试报告或验收记录。
3. 发布流程或 Git/PR 操作说明。
4. 临时需求讨论、执行 todo 或一次性过程记录。

## 命名建议

使用 `NN-语义名称.md`，按阅读顺序编号；当前 MVP 使用 `01-AI短剧端到端产品需求.md`，文档级编号为 `PRODUCT-01`。条款级 `AC-PRD-*` 保持稳定，只用于追踪，不写入文件名。

## 推荐结构

PRD 建议按以下结构扩展：

1. `背景`：说明产品问题、用户价值、当前风险和为什么需要该需求。
2. `产品目标`：使用 SMART 和 BDD 场景描述目标，关键目标可写成 Gherkin。
3. `唯一 MVP 产品清单`：以正向、穷尽的能力清单确定唯一实现输入。
4. `核心用户故事`：按用户类型、使用场景和完成定义展开。
5. `用户体验原则`：说明交互、反馈、状态可见性和边界提示。
6. `数据与权限边界`：说明收集、存储、删除和权限规则。
7. `状态模型`：列出核心状态、含义和流转约束。
8. `SMART 验收标准`：列出每项能力必须满足的可执行验收项。
9. `双向追踪与门禁`：连接 Requirement、Design、Plan 和 Acceptance。

## 强制可执行字段

1. frontmatter：`layer/doc_no/status/version/owner/inputs/outputs/downstream` 等 [`docs` 文档规则](../README.md#文档规则)。
2. 每条用户故事：用户、触发场景、目标价值、前置条件、主流程、失败/恢复和完成定义。
3. 每条 `AC-PRD-*`：可观察行为、量化阈值、事实源、样本/环境、排除规则和最迟验证门禁。
4. 追踪：精确引用 Requirement 条款、Design 章节与 Design AC，并映射 Plan/Acceptance 编号。
5. 状态：存在未关闭 P0 产品决策、无法测量的目标或未追踪范围时不得转为 `accepted`。

产品范围必须由正向清单穷尽；清单和验收标准未定义的能力不得作为代码输入，也不得以额外清单、空接口、Feature Flag 或占位代码写入 PRD。
