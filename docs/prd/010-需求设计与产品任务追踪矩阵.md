## 1. 使用规则

1. Requirement 是需求事实源，Design 解释边界与实现约束，PT 是 MVP 可排期单元，切片/里程碑组合多个 PT；本矩阵不重复定义业务事实。
2. `001–005` 表示同一完整前缀下的连续叶子编号，例如 `PRJ-FR-001–005`；每个范围均可机械展开，不使用“各模块 ENT”或“相关 NFR”这类模糊表达。
3. 表内的“覆盖 PT”表示该需求必须成为所列 PT 的交付边界或验收条件，不表示为每个实体、接口或 NFR 单独创建任务。
4. 整体需求、Design 与 PT 状态仍为 `proposed`；D-001 只局部接受 S0 工程基线，且不改变任何 PT 状态。本矩阵只证明追踪完整，不代表后续切片已被产品负责人接受。

## 6. 验收和变更门禁

- 纵向实施时，当前 PT 的 Plan 必须从本表取回对应 ENT/FR/IF/NFR，并把其成功、权限、失败、并发和恢复条件转成可执行测试或人工验收步骤。
- Acceptance 只能记录已执行的证据；编号出现在本表、Design 或 PT 中不等于该需求已通过。
- 新增或修改需求时，先改 Requirement，再同步 Design、PT/切片和本矩阵；任一叶子编号无 Design 或无验收归属时，PRD 不得进入 accepted。
- `IDN-FR-005` 与 `IDN-IF-006` 是唯一明确的 P1 需求，不得混入 PT-IDN-003；PT-STO-002 是生产 OSS 被选定后的条件性发布门禁，不阻塞 MinIO MVP。
