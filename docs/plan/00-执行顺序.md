# Plan 00：浮光执行顺序与需求拆解入口

设计入口：[Design 00](../design/00-项目需求设计.md)。当前是待评审方案，接受后再按本次闭环细化技术工作项；原始需求与验收标识不变。

## 目录与编号

PRD集中在docs/prd/，Design集中在docs/design/，Plan集中在docs/plan/。00为整体产品/执行入口，01～05为基础模块，06为画布生图生视频Demo，07～15为后续业务模块；同主题PRD、Design与Plan编号相同。文件号表示本次执行顺序，原始requirement/06～19和FR/US编号不变。

## 本次结论

首轮优先完成**画布图片节点→真实生图→明确选图→视频输入边→真实图生视频→播放与持久恢复**。完整业务模块仍按06～19的既有顺序拆解；本次提前抽取14生成与16画布的最小切片，与06～10基础依赖一起形成Demo，不等待剧本/设定/镜头/故事板全部完成。

依据：[本次Demo PRD](../prd/06-画布生图生视频Demo.md)、[原始需求总览](../requirement/01-需求总览.md#建议执行顺序)、[原始产品PRD](../prd/00-浮光.md)。本次用户已明确Demo优先；下述业务切片、节点/费用/外发政策与技术方案仍为待评审，不宣称已获接受。需求文件号表达完整阅读顺序，不能当成“画布必须最后接入”的限制。

本次新增14组模块PRD/Plan及1组跨模块Demo PRD/Plan。本文件是执行导航；不替代模块FR/质量/AC，也不复制生成平台、节点实现或当前任务状态。现有原始需求、用户修改和业务代码保留。

## 首轮先做什么

| 阶段                  | 执行内容                                                                            | 交付判断                                                 |
| --------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------- |
| D0 可行性/决策门      | 核实际生图与单图首帧图生视频能力、参数、费用/外发、核对与环境；接受Demo范围和Design | 条件未确定不承诺实施周期；真实调用须另满足执行条件       |
| 06→07 最小入口        | 真实身份/会话；空白项目与授权画布身份                                               | 不用固定账号/项目；刷新可读回                            |
| 08→09→10 最小生成依赖 | 真实授权媒体；服务端可用凭据；图片/视频发布模型                                     | 不等待素材库和管理页全部动作；不使用占位模型             |
| 16→14 生图子链        | 两类节点结构/草稿保存；统一校验/确认/冻结/任务；图片候选与明确选择                  | 真实图片、真实任务与读回证据；只证明生图阶段             |
| 16＋14 图到视频       | 明确候选版本的输入边；单独提交视频；真实视频播放、恢复及安全失败                    | 输入边不自动收费；改图不改变历史；整链反例通过才验收Demo |
| Demo后模块补齐        | 从06起补未覆盖范围，依次进入07～19，已验14/16切片复用                               | 局部Demo通过不等于完整模块/产品通过                      |

逐项依赖、D0～D12工作包、验收命令和证据要求以[Demo Plan](06-画布生图生视频Demo.md)为准。该Plan是当前最细的实施准备；其他模块Plan主要细化用户结果、依赖和验收切片，数据库/架构/API合同已补在对应Design工程节，接受后补精确代码与迁移执行清单。

## 可开工条件与完成尺度

- 产品接受当前闭环的范围、图片输入方式、费用与外发政策，并记录接受者/基线；未知只阻塞对应工作。
- 工程接受Design与真实外部可行性，实际责任人/产能和迭代窗口明确后再估算；当前不能编造日期、故事点或已承诺Sprint。
- 核心业务逻辑按Red→Green→Refactor；对应真实存储、权限、故障与浏览器验证同时规划，供应商样本单列。
- 自动化、真实供应商、持久恢复、浏览器与用户验收分别留证，未执行/阻塞如实记录；原质量阈值未确认部分不报达标。
- 必要权限、审计事件、幂等、费用与恢复随所属写入落地；18/19查询页面后置不代表记录和诊断可省略。
- Demo通过后，补齐14个模块的剩余FR/质量/AC，再判断完整创作链；没有剧本与镜头验收时不能报告完整制作流程完成。

1. 先读[Demo PRD](../prd/06-画布生图生视频Demo.md)，审阅首轮节点/边、费用、媒体可用、恢复与D-AC。
2. 再读[Demo Design](../design/06-画布生图生视频Demo.md)，核节点/输入边、冻结事务、故障与D0决定；之后读[Demo Plan](06-画布生图生视频Demo.md)，核D0条件与D1～D12依赖；当前先收敛D0受影响政策。
3. 按上表01～15执行编号阅读模块PRD/Plan，确认首轮基础子集与后续保留范围；来源需求号仍为06～19。
4. 将接受的决定写回对应事实来源，接受[Demo及模块Design](../design/00-项目需求设计.md)后，再落实技术工作项与实际迭代容量。
