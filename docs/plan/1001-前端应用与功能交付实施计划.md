## 结论

本计划从空项目开始建立 Lanverse 前端应用、共享能力、Guided Studio、Canvas Studio、Review、AI Copilot 与 Collaboration Runtime。实施按 P0–P6 顺序推进，每一阶段必须同时交付真实能力、正式契约、自动化验证和失败恢复；不得用空目录、占位页面或模拟成功跨过阶段门禁。

本文件是前端主题唯一执行 Checklist。Design 负责方案边界，Requirement 负责可测试契约，Acceptance 负责记录真实执行证据。Checklist 全部从未开始状态建立；完成某项后必须由实施任务依据真实证据单独更新。

## 1. 执行规则

- `[ ]` 表示尚未由实施任务提交并验收。
- 每个阶段的 Checklist 必须覆盖下方追踪表中的 Requirement；单项完成记录还必须引用其直接满足的 Requirement ID。
- 核心业务逻辑遵循 Red → Green → Refactor；无法先写测试时必须记录原因和替代验收。
- 每个 package、Feature、路由和运行进程必须随首个真实用例、消费者和测试建立。
- 同一服务端资源、表单、导航状态、协作 Graph 和 AI 流分别只有一个状态 Owner。
- Browser 不直接调用 Temporal、Provider、Agent Runtime、PostgreSQL 或私有对象存储地址。
- 发布、运行、审核、删除、权限、资产状态与 Copilot Tool 等高影响动作必须先固定失败路径和幂等契约。
- 阶段完成只表示该阶段验收通过，不自动代表 `Guided MVP` 或 `Platform Complete`。

## 3. P0：应用与工程基础

建立唯一 TypeScript 工作区、浏览器应用、协作应用边界、共享包边界、契约生成和质量门禁，为后续业务能力提供可审阅基础。

### Checklist

- [ ] `FE-P0-001` 建立单一 pnpm Workspace、唯一 lockfile 和 Turborepo 任务图，覆盖开发、检查、构建和测试。
- [ ] `FE-P0-002` 建立 `apps/web` 的 Next.js App Router、根布局、公共/认证/Workspace Route Group 和统一错误边界。
- [ ] `FE-P0-003` 定义 `apps/collab` 的进程入口与职责边界，但只在 P6 首个协作用例实现时创建运行代码。
- [ ] `FE-P0-004` 建立 `packages/ui`，交付 Token、Theme、Keyboard、Focus、ARIA 和首批真实 Primitive。
- [ ] `FE-P0-005` 建立 package/import boundary，禁止 app 反向依赖、循环依赖、Feature 私有导入和 `ui` 访问业务能力。
- [ ] `FE-P0-006` 建立 OpenAPI 生成流水线、生成代码/手写适配分区和 clean-diff 契约门禁。
- [ ] `FE-P0-007` 建立 lint、typecheck、unit、component、contract、E2E、visual 和 performance 的任务入口。
- [ ] `FE-P0-008` 建立安全配置注入和 Bundle Secret Scan，确保浏览器不包含服务端凭据。
- [ ] `FE-P0-009` 建立路由级 loading、empty、error、forbidden、not-found 和 conflict 展示基元。
- [ ] `FE-P0-010` 建立可重复的常规页面性能基准和 Accessibility 基准。

### 完成门

## 4. P1：SDK、Auth 与状态基础

### 目标

建立 REST、SSE、上传、认证、服务端缓存、表单和错误恢复的唯一基础能力，并固定一份事实一个 Owner。

### Checklist

- [ ] `FE-P1-001` 建立 `@lanverse/sdk` 的 REST Client、资源 Query Key/Base Options、统一错误、Trace 和 Idempotency 适配。
- [ ] `FE-P1-002` 建立结构化 SSE 协议、Event ID 去重、恢复游标、终态对账和连接状态模型。
- [ ] `FE-P1-003` 建立 Presigned Upload Controller，覆盖初始化、直传、完成确认、签名过期和幂等重试。
- [ ] `FE-P1-004` 建立 `@lanverse/auth` 的内存 Access Token、HttpOnly Refresh Session、并发刷新合并和安全 Return URL。
- [ ] `FE-P1-005` 建立身份恢复、退出、账户撤销、路由守卫和 Access Capability Reader。
- [ ] `FE-P1-006` 建立 TanStack Query Provider、按资源唯一 Query Key、失效策略和 Workspace 隔离。
- [ ] `FE-P1-007` 建立 React Hook Form + Zod 表单基线，并将服务端 Field Error 映射回输入。
- [ ] `FE-P1-008` 建立 feature-scoped Zustand 约束，只允许跨组件瞬时 UI 状态。
- [ ] `FE-P1-009` 建立 401、403、404、409、422、429、依赖不可用和 outcome unknown 的可判别错误模型。
- [ ] `FE-P1-010` 建立状态所有权架构测试，禁止服务端实体、Token、表单和未来 Yjs Graph 被重复保存。

### 完成门

- [ ] `FE-P1-G01` 登录恢复、并发 401、退出和安全 Return URL 合同测试通过。
- [ ] `FE-P1-G02` REST、SSE、上传和错误协议合同测试通过。
- [ ] `FE-P1-G03` Query、Form、URL、Zustand 与 React local state Owner 不重叠。

## 10. 每阶段交付记录

每项 Checklist 完成时必须在对应提交或 Acceptance 中记录：

1. 覆盖的 Requirement ID；
2. 新增或改变的模块边界、接口和状态 Owner；
3. Red、Green 与 Refactor 的真实命令和结果；
4. 正常、失败、冲突、权限、幂等和恢复输入；
5. 构建、合同、E2E、视觉、性能和安全验证结果；
6. 未执行项、缺失外部条件和残余风险；
7. 回滚点、数据兼容性和后续责任。

## 11. 非目标

本计划不授权：

- 为完整目录树创建没有用例、消费者和测试的空模块；
- 在 Frontend 复制 Backend 的权限、Workflow、节点、成本或业务事实；
- 让两套状态 Owner 同时管理同一实体、表单、Graph 或 AI 终态；
- 使用本地常量宣称 Node、Model、Capability 或高影响动作可用；
- 以连接结束、请求接受或客户端推测替代持久成功结果；
- 在 Requirement 未接受或关键失败路径未设计时直接进入功能开发；
- 以 Checklist 勾选替代 Acceptance 证据。
