# 切片 F：团队、画布与组织扩展实施计划

> Plan ID：`PLAN-F`
> 上游：[PRD-F](../prd/006-切片F团队画布与组织扩展PRD.md)、M01/M06/M12/M14/M15 Design
> 验收：[Acceptance 规范](../acceptance/README.md)
> 状态：`proposed`；每项能力独立进入、独立退出

## 1. 执行结论

F 不是一个必须同时上线的大版本。项目角色/临时 Grant、外部审片、完整画布、模板、API/Webhook、私有能力、SSO/SCIM 分别建立 Gate、工作包和证据；未满足采用、安全或运维条件的能力不创建空服务、空目录或兼容入口。所有入口复用 A—E 的同一 Command/Query、权限、expected revision、资源和治理判断。

## 2. 共通入口 Gate

- A—E 核心事实所有权和命令合同稳定，切片 E 为 `verified`；
- 每项扩展分别有真实用户/消费者、采用指标、数据与权限范围、故障模式、回退方式和责任人；
- 当前 API 规则与已接受 Design 一致：唯一 `/api` 当前合同、无 `v1` 路径、无兼容层；
- Requirement 中 `INT-NFR-001` 的“版本化/弃用窗口”若仍与当前合同冲突，必须先修正事实来源；冲突解决前 API/Webhook 工作包保持 `blocked`，不得暗自实现双合同；
- 扩展不得直写业务库、复制领域关系、绕过 M07/M08/M11/M14 或把 Python Agent 暴露为公共服务。

## 4. 单项执行方法

每项能力独立遵循以下步骤：

1. 记录真实用户问题、当前流程基线和成功指标；
2. 接受相关 PRD 范围并满足单项 Gate；
3. 复用当前 OpenAPI、Command/Query 和权限服务，不建立第二套业务 API；
4. 先写跨租户、撤销、重复、并发和故障 Red 测试；
5. 完成最小纵向能力并运行真实消费者/用户 E2E；
6. 保存采用、安全、故障和回退证据，仅将该能力标为 `verified`。

完整画布、SSO/SCIM、API/Webhook、私有能力和模板可以任意顺序进入，不互为前置；F0 是需要高级授权能力的共通前置，F1 依赖 E 的冻结 ReviewPackage。

## 6. 安全、故障与采用验证

所有已准入能力都必须覆盖跨 Workspace 已知 ID、成员/客户端/链接/连接撤销、重复请求和依赖中断。各能力另需覆盖：模板缺依赖和迁移冲突；Webhook 伪造/重放/dead-letter；画布损坏布局和无障碍键盘路径；私有能力不健康或越权；SSO/SCIM 同步冲突和紧急访问到期。

单项上线后记录真实采用、任务完成率、权限拒绝、重试/dead-letter、回退次数和支持工单。没有用户使用不等于技术通过失败，但会阻止继续扩大该能力范围。

## 7. 退出、停止与回退

每项能力只在对应 PRD-F 验收条件和自身 E2E/运行证据为 `passed` 后独立标为 `verified`。若扩展要求数据库直写、画布保存第二套业务关系、模板复制草稿、双 API 合同、或私有能力绕过 M07/M08/M11/M14，立即停止该项并回到 Requirement/Design。

回退以撤销 Grant/Client/Connection、停用 Feature/Capability/TemplateRelease 或停止新路由为主；历史事件、决定、投递日志和审计保留。单项失败不应中断 A—E 核心流程或其他已验证能力。
