## 1. 执行规则

切片严格按 `S0 → S1 → S2 → S3 → S4 → S5 → S6` 接受。一个时间点只允许一个主切片处于 `in_progress`；后续切片可以做调研或外部契约验证，但不得提前建立空模块、宣告完成或绕过前序事实。

每个切片都按同一闭环执行：关闭准入 → 选取 PT → 先写失败验收 → 后端事实与接口 → 生成 API client → 前端用户动作 → 故障/权限路径 → 真实依赖验证 → 产品接受。

## 3. 单切片执行清单

1. 准入：当前切片对应的 Requirement/Design/PRD 范围已在确定 commit 上形成接受记录；全局文档的未来切片可保持 proposed；只关闭本切片实际需要的 D-001～D-007；依赖 PT 已 accepted。
2. Red：为成功、失败、权限、并发和恢复路径建立可失败的测试或明确人工步骤。
3. Green：只实现本切片实际使用的表、模块、接口、页面和基础设施能力。
4. Contract：更新 OpenAPI，并从运行中 URL 生成 `frontend/src/api/`；禁止手写平行 DTO/URL。
5. Full-stack：页面写入 `frontend/src/app/`，复用组件写入 `frontend/src/components/`，场景状态按既定 feature/ViewModel 规则组织；测试独立放入测试目录。
6. Reality：PostgreSQL 以及本切片使用的 RabbitMQ、Redis、MinIO、FFmpeg、Provider 必须走真实契约；fake 仅作为确定性测试替身。
7. Evidence：保存真实命令、环境、结果和未验证项；中断或缺少依赖不得记录为通过。
8. Exit：对应 PT 和本切片退出条件同时 accepted，才能将下一切片置为 ready。

- 新能力必须先定位到一个明确切片，给出用户结果、事实所有者、依赖和自动化退出证据；否则不进入实施。
- PT 的细粒度执行以 PLAN-007～PLAN-009 为准；本计划只决定 PT 在哪个纵向结果中被接受。
- 切片通过后创建对应 Acceptance 证据；证据必须链接 PT、测试输出、外部限制和残余风险。
