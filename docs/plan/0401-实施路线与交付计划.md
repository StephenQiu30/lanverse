## 1. 结论

1. **先验证、再打底、后纵向切片**：P0 验证全能参考与成本 → M1 工程底座与顶层抽象 → M2–M4 沿工作流纵向打通，M4 结束即 MVP。
2. **顶层抽象在 M1 一次定型**：命令层、Operation、模型注册表、Temporal 工作流骨架、Outbox → Kafka → Redis → SSE 事件链路、Agent Harness 骨架、媒体来源与合规属性，从第一个功能开始就按它们实现，避免 MVP 之后返工。
3. **每个里程碑以“浏览器里能完成什么”验收**，不以“模块写完”验收。
4. **P0 的全能参考结果是项目的关键决策点**：找不到在写实与风格化下都可用的模型，就需要调整方案或时间，而不是降级（0101 §12、§14）。
5. **范围优先于时间**：周数只是估算；任何里程碑都以验收通过为完成标志，不因时间压缩业务流程。

## 3. 各阶段交付与验收

### P0 技术验证（估算 3 周）

**目标：** 在平台开发深入之前回答“全能参考能不能用、要花多少钱”。

| 交付 | 内容 |
| --- | --- |
| 全能参考评测 | 候选：火山方舟 Seedance、MiniMax 海螺 H3、经 OpenRouter 的海外版 Seedance（0101 P18）；按写实、日系动漫、国风 / 仙侠、3D 卡通、韩漫 / 条漫 5 种风格，分别测单角色、双角色同框、动作参考、运镜参考、音频参考五类镜头；记录一致性、失败率、耗时、单镜成本 |
| 其他能力评测 | 带参考生图（Seedream、GPT Image）、TTS（MiniMax Speech、豆包语音）、剧本解析 LLM（豆包等，原文位置准确率） |
| 样片 | 5 种风格各 1 条 30–60 秒样片，用脚本 + 人工串联完成 |
| 成本模型 | 单镜成本（图生视频 vs 全能参考）、单分钟成片成本、平均重拍次数 |
| 一致性评估方法 | 5 种风格分别的自动指标 + 人工抽检标准 |
| 注册表初始配置 | 选定模型的 ModelProfile（模式、输入上限、参数 schema、价格） |
| LibTV 实测 | 产品负责人登录实测画布交互、Agent 质量、全能参考效果与成本；按实测清单记录，补入 0102（0102 R2） |
| 境外调用合规记录 | OpenRouter 调用的数据发送范围与留存条款，供对外发布前法务确认（0202 CMP-06） |

**退出标准：** 全能参考在写实与 4 种风格化下各有至少一家模型达到可用；主供应商确定；成本数据齐全。**未达标则暂停 M3 之后的工作，重新评估方案或时间。**

### M1 工程底座与顶层抽象（估算 4 周）

| 交付 | 内容 |
| --- | --- |
| 工程 | 三端目录、锁文件、Makefile、CI（lint、format、typecheck、test、race、vuln、契约一致性、镜像构建）；Docker Compose 一键启动全部组件（PostgreSQL、Redis、Kafka、MinIO、Temporal、Temporal UI、可观测栈），含健康检查与备份恢复演练 |
| 契约链 | Gin + swag 注解 → OpenAPI → 前端 TS 客户端；Activity JSON Schema → Go / Python 类型与样例测试 |
| 命令层 | 鉴权（Redis 会话）、幂等键、`expected_version`、审计、Outbox 的统一中间层 |
| 工作流与事件 | Temporal Worker（flow / media 队列）与 OperationWorkflow 骨架；Outbox relay → Kafka → realtime 消费者 → Redis Pub/Sub → SSE |
| Agent 服务骨架 | FastAPI + Temporal Activity Worker（agent 队列）；Harness 骨架（Skill Registry、执行循环、校验、预算、Trace）与一个假供应商适配器 |
| Operation 骨架 | Operation 状态机、输入角色、报价、预留、`input_hash` 复用；经 Agent 服务的假供应商适配器跑通 submit → poll → ingest |
| 模型注册表 | ModelProfile、参数 schema、价格规则；管理员维护界面（可先用表单 + JSON） |
| identity / workspace | 管理员创建账号、登录、项目（画幅、风格类型、风格预设）、预算 |
| media | 预签名直传、探测、缩略图、来源与合规属性 |
| 前端骨架 | 登录、项目列表、按 `param_schema` 渲染参数表单的通用组件、SSE 订阅 |

**验收：** 浏览器中登录 → 建项目 → 上传图片看到缩略图；用假供应商创建一个 Operation：报价 → 确认 → 完成 → 候选出现；在 submit 后杀掉 worker 再重启，任务恢复且账本只记一次；模拟响应丢失进入 `unknown` 并对账成功；CI 全绿。

### M2 剧本到设定集（估算 3 周）

| 交付 | 内容 |
| --- | --- |
| script | 整部剧导入（docx / txt，单文件或多文件）、分集确认、逐集解析（原文位置校验与修复）、解析审阅与修改 |
| bible | 全剧抽取与别名合并、造型（按集 / 场适用）、场景、道具；确认 |

**验收：** 导入一部 ≥ 10 集的真实剧本，分集与解析可逐条追溯原文；单集失败可单独重试；修改后产生新版本，下游标记过期；0201 SCR-01～05、BIB-01、BIB-02 通过。

## 5. 现有代码的处置（已确认：方案 A）

新设计与现有实现在数据访问、接口契约、前端状态、编排 Owner、生成模型上存在结构性差异（0308 §11），逐步改造成本高于重建。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 同仓库重建（默认）** | 给当前代码打标签（如 `legacy-2026-09`）；新代码在 `backend/`、`agent/`、`frontend/` 按新设计重建；旧实现通过标签查阅，逐模块审计后按需搬运 | 结构干净；Git 历史连续 | 旧代码不可运行期间需保留旧版本镜像用于演示 |
| B. 新仓库 | 新建仓库从零开始，本仓库归档 | 最干净 | 历史不连续，工程配置需重搭 |
| C. 原地改造 | 逐模块改造现有代码 | 始终可运行 | 新旧规范长期并存，成本与认知负担最高 |

**可能值得审计复用的部分**：登录与邮件验证、对象存储上传、供应商 API 细节、shadcn 基础组件与视觉 token（`DESIGN.md`）。M1 开始时逐项评估并记录。

**已确认（2026-09-25）**：采用方案 A（0101 P22）。执行步骤：① 在当前 `main` 上创建并推送标签 `legacy-2026-09`；② M1 开始时在同名目录按新设计重建，旧代码的删除与目录调整作为 M1 的第一个独立提交；③ 可复用部分逐项审计后搬运，记录在 M1 验收记录中。标签的创建、推送与旧代码删除，均在执行前再次向产品负责人确认具体命令。

## 6. 研发流程

1. 每个里程碑开始前，在本文对应小节补充任务清单与验收用例；复杂模块（Operation、画布）按需写专项设计（02xx）。
2. 核心业务逻辑 Red → Green → Refactor；每个任务独立提交，提交信息遵循 `AGENTS.md`。
3. 每个里程碑结束时创建 `docs/acceptance/M<n>-验收记录.md`，记录真实操作、命令、结果、未通过项与残余风险。
4. 需求或设计变化先改 01xx–03xx 并评审，再改代码。

## 7. 主要风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 全能参考在某种画风下不可用 | 双角色同框换脸、参考音频不生效 | P0 第一优先级验证；至少 2 家候选；不达标即重新评估，不静默降级 |
| 人力不足导致超期 | M3 / M4 延期 | 严格按 0101 MVP 边界；每周复盘，优先保证 0101 §8.2 验收场景 |
| 成本过高 | 单分钟成本不可接受 | 锁定输入后再生成；`input_hash` 复用；按镜头选择模式；P0 给出数据后设上限 |
| 供应商不可靠 | 超时、结果丢失、重复扣费 | Operation 状态机与对账；供应商队列限流 |
| 模型变化快 | 接口或价格变化 | 注册表 + 适配器隔离；每季度重跑评测集 |
| 顶层抽象过度设计 | M1 拖长 | M1 只实现抽象的最小可用版本（一个假适配器跑通），功能在后续里程碑填充 |
| 合规 | 标识或审核缺失 | 标识与审核列为 MVP 验收项；对外发布前法务审阅 |
| 画布性能 | 媒体多时卡顿 | M3 并行 PoC；渲染层可替换 |
| 中间件运维负担 | Temporal、Kafka、Redis、MinIO、PostgreSQL 由 1–2 人维护 | M1 完成一键启动、健康检查、统一看板与告警、备份恢复演练；生产优先使用托管 PostgreSQL；每个组件的职责边界按 0308 §6 执行，不扩大用途 |
