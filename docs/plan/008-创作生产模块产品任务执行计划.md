## 1. PT 接受顺序

PT 按 S2 的 scripts/assets → S3 的 storyboards → S4 的 production 顺序接受，不单独领取或估算；工程实现只领取 PLAN-000 当前切片的 `DEV-*`。S2/S3 已于 2026-08-04 通过真实联合契约 accepted：DeepSeek confirmed 结构经人工决议和 current 切换后，使用本机 MinIO、真实媒体探测、三类 ready 资产与真实 Scene/Dialogue 完成 Ready 分镜 1/1。S2 仍只拥有文本提取所需的最小 Task/Outbox/Worker；完整 Attempt、unknown、费用和镜头生成必须等 S4 的真实用例，不预建第二套任务框架。

S3 同步完成 PT-PRJ-003 的 Project/Episode 删除影响汇总：一次批量查询统计所属 active/archived Shot 及全部 ShotSpecVersion，预检逐项显示两类数量，Episode DELETE 在锁内复查。并发建镜/删除 PostgreSQL 用例与真实 Project 页面浏览器用例是该持续门禁的必须证据。

S2/S3 资产增量同步完成 Project 级资产删除影响汇总：批量统计 active/archived Asset 和全部 AssetVersion，预检显示两类数量，Project DELETE 在行锁内复查。PostgreSQL 必须同时固定有版本/归档事实不可删与首个 Asset/项目删除的两种安全竞争结果；真实 Project 页面不复制计数规则。

PT-AST-001 的 Asset 自身删除门禁还必须统计 scripts 中 `downstream_type=ASSET` 的 CandidateDecision，以及全部 Prop/Costume 历史 AssetVersion 中的 holder/wearer 引用。assets 只依赖自有 Protocol 获取 scripts 计数，关联版本由本模块查询不可变 JSONB；预检返回结构化 `decision_count`/`related_version_count`。所有 Asset 写命令按 Project → Asset 锁定并强制刷新锁定重读，追加关联版本再锁目标 Character；`link_existing` 与 DELETE 共享目标 Asset 锁。PostgreSQL 固定“无版本但已有决议不能硬删”“被道具/服装历史版本引用时同样只能归档”及两类并发 winner，真实资产页显示两种“只能归档”且不提供确认删除动作。

PT-SBD-005 的 production 摘要不能停留在单独的 shot-readiness endpoint：storyboards 必须按 Project 下的 Episode 集合批量聚合相同 readiness 规则，并让 ProductionSnapshot 显示 Ready 分镜、blocked/unavailable 数量和阶段动作。依赖故障进入 partial failure；全 ready 只把本地 S3 进度推进到 90%，不得据此创建或暗示 S4 Provider、Task、Candidate 或费用事实。OpenAPI/Next.js 只消费该摘要，12 集及 36/120 镜头查询上限是持续门禁。

DEV-S4-01 已在无 Ark Key 时独立完成：两个内置方舟能力保持 `provider_contract_unverified`，无价格、禁止任意参数且不可提交。Red 使用隔离数据库的已验证 active Capability 事实验证参数白名单、纯读预检、HMAC 过期阻断、高成本确认零写入、五事实同事务和 Decimal 预占；OpenAPI/Next.js 任务中心只展示服务端能力与费用事实。该 fixture 不返回生成结果，不进入 Worker，不能接受 PT-PROD-002～004/008 或 S4；D-004 仍是真实参数、价格、Attempt 与 Provider E2E 的必须前置。工程证据见 [ACC-019](../acceptance/arrived/019-生成预检与费用预占事实层验收.md)。

DEV-S4-02 先执行的空 Ark Key 取消子集已完成：仅 queued 且无 Attempt 的生成 Task 可本地取消，Task 行锁与 Worker 决定唯一赢家；成功时 cancelled Task、released Reservation、全额 release CostEntry 和审计同事务收敛，重复命令不重复释放。证据见 [ACC-021](../acceptance/arrived/021-排队生成取消与预占释放验收.md)；该增量不代表 Provider cancel、retry/reconcile、PT-PROD-006/008 或 S4 accepted。

2026-08-04 当前代码显式复核中，定向浏览器已验证 active Ready 分镜 2/2、单集 90% 和项目汇总 2；完整无密钥 E2E 7/7、MinIO/RabbitMQ/ffprobe/媒体联合栈 2/2、2/2、1/1、1/1，固定性能 profile 1/1。随后真实 DeepSeek confirmed 起点联合契约 1/1 通过，并验证 Ready 分镜 1/1；S2/S3 产品与发布门禁关闭。

## 6. 执行与验收模板

1. 从 PRD-010 取回当前 PT 的需求叶子和 Design，确认版本、权限、幂等、失败和恢复条件。
2. 先写领域、事务、外部契约和 E2E Red；确定性替身只验证内部状态，不可替代真实 AI 服务验收。若真实流程后来引入编排运行时，必须补充恢复不重复付费副作用的测试。
3. 用公开模块契约获取 ScriptVersionRef、AssetVersionRef、ShotSpecRef、RightsGate 与 MediaVersionRef；禁止跨模块 ORM。
4. 更新 OpenAPI 并生成 client，前端显示服务端 readiness、Task、费用和 next_action。
5. 真实 PostgreSQL/RabbitMQ/MinIO 通过；S4 还必须通过默认 Image/Video Provider 契约和端到端调用。
6. 记录成功、局部失败、重复投递、重启、unknown、取消和费用不变量的真实证据，再申请 accepted。
