## 1. 结论

1. **先验证、再打底、后纵向切片**：P0 验证全能参考与成本 → M1 工程底座与顶层抽象 → M2–M4 沿工作流纵向打通，M5 结束即 MVP。
2. **顶层抽象在 M1 一次定型**：命令层、Operation、模型注册表、Temporal 工作流骨架、Outbox → Kafka → Redis → SSE 事件链路、Agent Harness 骨架、媒体来源与合规属性，从第一个功能开始就按它们实现，避免 MVP 之后返工。
3. **每个里程碑以“浏览器里能完成什么”验收**，不以“模块写完”验收。
4. **P0 的全能参考结果是项目的关键决策点**：找不到在写实与风格化下都可用的模型，就需要调整方案或时间，而不是降级（PRD-01 §12、§14）。
5. **范围优先于时间**：周数只是估算；任何里程碑都以验收通过为完成标志，不因时间压缩业务流程。

### M1 工程底座与顶层抽象（估算 4 周）

| 交付 | 内容 |
| --- | --- |
| 工程 | 三端目录、锁文件、CI（lint、format、typecheck、test、race、vuln、契约一致性、镜像构建）；本地三端进程读取根目录 `.env` 并连接本机已启动的 PostgreSQL、Redis、Kafka、MinIO、Temporal，含健康检查与隔离的备份恢复演练，不通过 Docker 启动环境；后续部署的两份 Compose 文件分别定义应用和依赖环境；开发与检查直接运行工具命令，不设项目脚本或 Makefile |
| 契约链 | Gin Handler 注解 + DTO → swag 自动生成 Swagger → 后端在线 `/swagger/doc.json` → `@umijs/openapi` 生成前端 API；Axios `src/lib/request.ts` 作为普通 HTTP 唯一入口；Activity 类型由 Go / Python 各自维护并以样例测试校验 |
| 全局异常与响应契约 | `backend-api` 的公共 `/api` 统一映射参数校验、鉴权、业务冲突、依赖故障、未匹配路由与未预期错误；panic 恢复也返回 DES-03 §2.4 的 RFC 9457 `application/problem+json`，保留 HTTP 状态、稳定 `code` 和 `request_id`，不泄露内部错误。成功响应使用端点 DTO（列表遵循 DES-03 §2.3），不额外套通用响应外壳；`agent-api` 增加内部路由时统一处理其异常并为内部调用方固定错误契约 |
| 命令层 | 鉴权（Redis 会话）、幂等键、`expected_revision`、审计、Outbox 的统一中间层 |
| 工作流与事件 | Temporal Worker（flow / media 队列）与 OperationWorkflow 骨架；Outbox relay → Kafka → realtime 消费者 → Redis Pub/Sub → SSE |
| Agent 服务骨架 | FastAPI + Temporal Activity Worker（agent 队列）；Harness 骨架（Skill Registry、执行循环、校验、预算、Trace）与一个假供应商适配器 |
| Operation 骨架 | Operation 状态机、输入角色、报价、预留、`input_hash` 复用；经 Agent 服务的假供应商适配器跑通 submit → poll → ingest |
| 模型注册表 | ModelProfile、参数 schema、价格规则；管理员维护界面（可先用表单 + JSON） |
| identity / workspace | 管理员创建账号、登录、项目（画幅、风格类型、风格预设）、预算 |
| media | 预签名直传、探测、缩略图、来源与合规属性 |
| 前端骨架 | 登录、项目列表、按 `param_schema` 渲染参数表单的通用组件、SSE 订阅；应用级 TanStack Query Provider 管理服务端状态与查询失效，编辑器按功能使用 Zustand + Immer 管理局部状态；`request.ts` 统一解析错误，页面提供错误边界与可恢复反馈 |

**基础能力验收：** 公共 API 契约测试覆盖参数错误、未登录、业务冲突、404、依赖故障与未预期错误，核对 HTTP 状态、`application/problem+json`、稳定 `code`、`request_id` 和敏感信息脱敏；成功响应按端点 DTO 与在线文档校验。前端测试覆盖请求错误解析、共享查询失效与局部编辑状态，浏览器验证页面错误后的恢复路径；Agent 内部路由增加时验证其错误契约。执行契约实现前按 PLN-02 就绪定义完成 DES-03 评审。

**验收：** 浏览器中登录 → 建项目 → 上传图片看到缩略图；用假供应商创建一个 Operation：报价 → 确认 → 完成 → 候选出现；在 submit 后杀掉 worker 再重启，任务恢复且账本只记一次；模拟响应丢失进入 `unknown` 并对账成功；CI 全绿。

## 5. 现有代码的处置（已确认：方案 A）

新设计与现有实现在数据访问、接口契约、前端状态、编排 Owner、生成模型上存在结构性差异（DES-08 §11），逐步改造成本高于重建。

| 方案 | 做法 | 优点 | 缺点 |

## 6. 研发流程

1. 每个里程碑开始前，按 [TST-02 需求追踪矩阵](../test/02-需求追踪矩阵.md) 中该里程碑的功能与验收用例拆分任务（就绪与完成定义见 [PLN-02](02-项目管理与变更.md) §3）；设计以 DES-01～DES-08 与对应功能设计（DES-09～DES-41）为准。
2. 核心业务逻辑 Red → Green → Refactor；每个任务独立提交，提交信息遵循 `AGENTS.md`。
3. 每个里程碑结束时创建 `docs/acceptance/M<n>-验收记录.md`，记录真实操作、命令、结果、未通过项与残余风险。
4. 需求或设计变化先改 PRD、REQ、DES 文档并评审，再改代码。

## 7. 主要风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 全能参考在某种画风下不可用 | 双角色同框换脸、参考音频不生效 | P0 第一优先级验证；至少 2 家候选；不达标即重新评估，不静默降级 |
| 人力不足导致超期 | M3 / M4 延期 | 严格按 PRD-01 MVP 边界；每周复盘，优先保证 PRD-01 §8.2 验收场景 |
| 成本过高 | 单分钟成本不可接受 | 锁定输入后再生成；`input_hash` 复用；按镜头选择模式；P0 给出数据后设上限 |
| 供应商不可靠 | 超时、结果丢失、重复扣费 | Operation 状态机与对账；供应商队列限流 |
| 模型变化快 | 接口或价格变化 | 注册表 + 适配器隔离；每季度重跑评测集 |
| 顶层抽象过度设计 | M1 拖长 | M1 只实现抽象的最小可用版本（一个假适配器跑通），功能在后续里程碑填充 |
| 合规 | 标识或审核缺失 | 标识与审核列为 MVP 验收项；对外发布前法务审阅 |
| 画布性能 | 媒体多时卡顿 | M3 并行 PoC；渲染层可替换 |
| 中间件运维负担 | Temporal、Kafka、Redis、MinIO、PostgreSQL 由 1–2 人维护 | M1 完成一键启动、健康检查、统一看板与告警、备份恢复演练；生产优先使用托管 PostgreSQL；每个组件的职责边界按 DES-08 §6 执行，不扩大用途 |
