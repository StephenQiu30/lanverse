## 3. 任务管理

### 3.1 工具与结构

- 使用 GitHub Issues + Projects（仓库已托管在 GitHub）：
  - **Epic** = 功能文件（REQ-06～REQ-34），标签 `feature:Fxx`；
  - **Task** = 可在 1–3 天内完成并独立提交的工作，关联需求编号（如 `VID-04`）与里程碑（`M1`–`M4`、`V2`）；
  - **Bug**、**Tech Debt**、**Spike**（调研）单独标签。
- 看板列：`待办` → `就绪` → `进行中` → `评审中` → `完成`。

### 3.2 就绪定义（DoR）

任务进入“就绪”须满足：

1. 关联的功能文件为“已接受”，任务引用具体需求编号与验收标准。
2. 涉及的表、接口、工作流已在 DES-02 / DES-03 / DES-04 中定义；需要新增的已先修改设计文档。
3. 依赖的前置任务已完成或可并行。
4. 验证方式明确（哪些测试、哪些手工步骤）。
5. 规模 ≤ 3 天；超过则拆分。

### 3.3 完成定义（DoD）

1. 代码满足 PROJECT.md 与 AGENTS.md（Go 规范、分层、命名）。
2. 核心逻辑按 Red → Green → Refactor；测试覆盖功能文件“测试要点”中与本任务相关的条目。
3. 质量门禁全部通过（格式、静态检查、单元与集成测试、Race、漏洞扫描、契约一致性），未执行项如实说明。
4. 对应的功能文件验收标准可以演示通过（端到端或手工）。
5. 文档同步：设计变化已更新 DES 文档；新增接口已在 DES-03 与 swag 注解中；新增表已在 DES-02 与迁移脚本中。
6. 提交信息符合 `type(scope): 中文说明`；工作区无无关文件。
7. TST-02 需求追踪矩阵中对应测试用例状态已更新。

## 4. 需求基线与变更控制

### 4.1 基线

- 文档评审通过后状态改为“已接受”，即成为**基线**；基线版本以 Git 标签标记：`baseline-req-v<N>`（需求：PRD-01、REQ 文档、features）、`baseline-design-v<N>`（DES 文档）。标签的创建与推送须产品负责人明确要求（AGENTS.md）。
- 实施只以基线为依据；草案中的内容不得作为实现依据。

### 4.2 文档评审检查清单

| 类别 | 检查项 |
| --- | --- |
| 需求 | 每条需求有编号、优先级、用户故事、业务规则、验收标准；验收标准可测试；无实现细节混入需求 |
| 一致性 | 引用的需求、非功能、用例、功能编号都存在（链接与编号校验脚本通过）；术语符合 REQ-04 |
| 完整性 | 功能文件的“实现所需”覆盖数据、接口、工作流、事件、界面、权限、非功能要求 |
| 设计 | 表结构可执行（DDL 验证）；接口与错误码与功能文件一致；失败路径与重试明确 |
| 风险 | 待确认项有默认处理与计划 |

### 4.3 变更流程

```text
提出变更（任何人）→ 创建 Issue（标签 change-request，填 §4.4 模板）
→ 影响分析（研发）：受影响的需求、功能文件、设计、已实现代码、测试、成本、里程碑
→ 决策（产品负责人）：接受 / 拒绝 / 延后；重大变更记为新的产品决策 P<n>（PRD-01 §9）
→ 先改文档（需求 → 设计 → 计划）并评审 → 更新基线标签（按需）
→ 再改代码与测试 → 在变更 Issue 中记录完成证据
```

变更分级：

| 级别 | 例子 | 审批 |
| --- | --- | --- |
| 小 | 文案、界面细节、不影响接口与数据的规则澄清 | 研发自行修改文档并知会 |
| 中 | 新增或修改验收标准、字段、接口；非功能目标调整 | 产品负责人批准 |
| 大 | 范围增减、优先级跨版本移动、技术选型变化、成本模型变化 | 产品负责人批准并记录为 P 决策 |

### 4.4 变更请求模板

```markdown

## 决策（产品负责人填写）：接受 / 拒绝 / 延后，日期
```

## 6. 代码与评审流程

- **主干开发**：`main` 始终可构建、可部署。
- **分支与 PR**：研发按需使用短分支（≤ 3 天）+ PR 合并；AI 助手只在产品负责人明确要求时创建分支、PR、标签或合并（AGENTS.md）。
- **评审**：PR 至少一人评审（1 人团队时由产品负责人抽查 + AI 代码审查）；评审关注：需求符合度、分层与依赖方向、错误处理、并发与幂等、测试充分性、安全与日志脱敏。
- **提交**：每个提交只做一件事，标题 `type(scope): 中文说明`，正文说明原因与影响。
- **迁移与契约**：数据库迁移、OpenAPI、Activity schema 的变更必须在 PR 描述中单独说明。

## 7. 缺陷管理

| 级别 | 定义 | 例子 | 响应 | 修复目标 |
| --- | --- | --- | --- | --- |
| S1 致命 | 数据丢失、重复扣费、安全漏洞、服务不可用 | 账本不平、凭据泄露 | 立即（工作时段 30 分钟内） | 24 小时内修复或止损 |
| S2 严重 | 核心流程阻断且无替代方案 | 无法渲染、无法确认报价 | 4 小时内 | 3 天内 |
| S3 一般 | 功能错误但有替代方案 | 批量结果计数错误 | 1 个工作日内 | 当前里程碑内 |
| S4 轻微 | 界面、文案、体验问题 | 对齐、错别字 | 排期 | 按优先级 |

- 缺陷记录：复现步骤、期望与实际、环境、日志 / 追踪 ID、影响范围。
- S1 / S2 修复后补回归测试，并按 OPS-04 写事后复盘。

## 8. 风险管理

- 风险登记在 GitHub Issues（标签 `risk`），字段：描述、概率（高 / 中 / 低）、影响（高 / 中 / 低）、负责人、应对措施、触发信号、状态。
- 初始风险来自 PLN-01 §7 与 PRD-01 §14；每周复盘时更新；高概率 × 高影响的风险在周报中单列。

## 9. 度量与汇报

### 9.1 周报模板

```markdown
# 第 N 周（日期）
- 里程碑：M? 进度（验收标准通过数 / 总数）
- 本周完成：（任务、需求编号）
- 演示：（链接或截图）
- 风险与阻塞：
- 成本：本周模型费用、单分钟成本（P0 后）
- 下周计划：
```

### 9.2 度量

| 度量 | 口径 | 用途 |
| --- | --- | --- |
| 验收标准通过率 | TST-02 中当前里程碑已通过的用例 / 总数 | 里程碑进度 |
| 周吞吐 | 完成的任务数与规模 | 估算校准 |
| 缺陷趋势 | 新增 / 关闭 / 遗留（按级别） | 质量 |
| 构建健康 | CI 通过率、平均时长 | 工程效率 |
| 产品指标 | PRD-01 §10 的成功指标 | 产品效果 |
