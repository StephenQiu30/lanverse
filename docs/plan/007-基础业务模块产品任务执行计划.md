## 1. PT 接受顺序

每行是一个产品范围与接受单元，不单独领取或估算。工程负责人领取 PLAN-000 当前切片的 `DEV-*`，在该 DEV 中从 PRD-010 取回对应 PT 的 ENT/FR/IF/NFR，建立成功、权限、失败、并发和恢复中的适用 Red 证据，并交付后端事实、OpenAPI/生成 client、必要前端交互和测试。`IDN-FR-005`/`IDN-IF-006` 的成员管理不属于以下任务。

## 6. 单项执行模板

1. 追踪：在 PRD-010 找到该 PT 覆盖的所有需求叶子，确认 Design 落点和 P0/P1 属性。
2. Red：建立领域、真实 PostgreSQL、当前外部契约和浏览器测试；先证明缺失规则会失败。
3. Backend：只创建当前用例需要的模型、repository、service、schema 和 API；事务/锁/幂等在服务端成立。
4. Contract/UI：生成 TypeScript client；页面只显示服务端事实、阻塞和 next_action，Redux 不保存权威状态。
5. Failure：验证跨空间、权限、冲突、重复命令、依赖不可用和恢复路径。
6. Evidence：记录真实命令、fixture、结果、外部阻塞和残余风险，由产品负责人接受该 PT。

## 7. 完成门禁

- 表中 20 个 PT 必须逐项有 Acceptance 证据；持续任务 PRJ-004/005、GOV-006 到最终接入点前不能提前 accepted。
- OIDC、MinIO/目标 OSS、合规责任等真实依赖缺失时，对应 PT 保持 blocked 或 in_progress。
- 四模块联合场景通过后，PLAN-004 才能完成；单模块 CRUD、页面存在或 API 200 不构成模块验收。
