# 001 AI 短剧平台产品调研与核心能力

- 状态：proposed
- 日期：2026-07-26
- 输入：用户提出的即梦/可灵对标、AI 短剧平台目标与模块化要求
- 输出：产品定位、核心生产链路、能力边界与 MVP 范围
- 下游：`002-architecture-and-technology-selection.md`、后续 MVP PRD

## 1. 结论

Lanverse 不应被设计成“输入提示词后调用一次视频模型”的工具，而应是以项目为单位、以镜头为最小生产单元、以可复用资产保证一致性、以候选与版本支持局部返工的 AI 短剧生产工作台。

平台的核心价值不是拥有某一个模型，而是把剧本、角色/场景资产、分镜、生成任务、审核、成本和成片组织成一个可恢复、可追踪的生产闭环。

## 2. 调研边界

即梦和可灵是闭源商业产品。公开页面只能确认其用户功能和部分 Web 端技术信号，无法证明内部后端语言、数据库、任务系统或模型编排实现。因此：

- 产品能力采用官方页面和官方发布资料作为事实依据。
- 内部架构只做基于业务约束的独立设计，不冒充竞品源码复刻。
- 开源项目用于验证工作流与数据建模，不直接照搬其工程结构。

### 2.1 可验证的实现信号

- 2026-07-26 实测即梦 Web 页含 `__MODERN_SERVER_DATA__`，响应计时含 SSR loader/render 阶段；结合 [Modern.js 官方定位](https://modernjs.dev/)可以确认其 Web 壳属于 React/Modern.js SSR 生态。该证据不能推导其业务后端和模型服务技术栈。
- LumenX 公开采用 FastAPI、Python、Next.js、Qwen/Wanx 和 FFmpeg，验证了 Python API + Web 工作台 + 媒体工具的可行组合，但其本地优先输出目录不等于多用户 SaaS 的持久化方案。
- Jellyfish 实际代码采用 FastAPI、SQLAlchemy、Celery/Redis、MySQL 和 S3 兼容存储，产品实体较完整；同时存在大型横向 service 目录和较重的任务自建逻辑，应借鉴业务模型而非复制目录。
- Huobao 采用 Node.js、SQLite 和本地存储，更适合单机工具参考；不能作为生产级多租户服务的架构依据。

## 3. 对标观察

| 产品/项目 | 已公开的关键能力 | 对 Lanverse 的启示 |
| --- | --- | --- |
| 即梦 AI | 文/图生视频、首尾帧控制、主体保持的图片编辑、智能画布、局部重绘与多图融合 | 单素材生成必须与可编辑画布、参考输入和局部修改结合 |
| 可灵 AI | 多图参考可组合人物、物体、场景、服装和动作，并改善多镜头主体一致性 | 参考资产必须是结构化实体，不能只是散落附件 |
| Runway | Agent 规划、多模态生成、角色表/故事板、审核后生成、时间线编辑 | 生成计划、成本预估、人工确认和时间线是一体化流程 |
| LTX Studio | 从概念/剧本/图像/视频启动，提供 Elements、动态故事板、时间线和团队反馈 | 项目资产、镜头控制、后期和协作共同构成生产工作台 |
| Jellyfish | 剧本拆镜、候选确认、角色/场景/道具/服装资产、统一异步任务 | `候选 → 确认 → ready → 生成` 是可靠的人机协作边界 |
| LumenX | 资产提取、风格定义、角色三视图、分镜图、视频候选和 FFmpeg 合成 | 角色设计资产和逐镜头抽卡/择优是短漫剧的实用 SOP |
| Huobao/Toonflow | 一句话到成片、Agent/节点式生产、供应商配置 | 可借鉴工作流体验，但 SQLite/本地文件或动态脚本不适合作为生产架构模板 |

## 4. 目标用户与产品定位

首要用户是小型短剧制作团队中的编剧、导演/分镜师、AI 生成操作员和审核人。第一版解决“把已有故事稳定做成 1 集可导出的竖屏短剧”，不追求自动经营内容账号。

产品单位如下：

- Workspace：组织、成员、权限与额度边界。
- Project：一部短剧或一个系列，持有全局风格和资产圣经。
- Episode：一集剧本和生产进度。
- Scene：叙事场景，用于组织镜头与场景连续性。
- Shot：最小生产、审核、重做和成本核算单元。
- Asset：角色、场景、道具、服装、风格、声音等可复用参考。
- Media Version：一次输入或生成结果，不覆盖历史版本。

## 5. 核心生产链路

`故事/剧本 → 结构化剧本版本 → 实体候选 → 资产确认 → 分镜/ShotSpec → 关键帧候选 → 镜头视频候选 → 配音/音效/字幕 → 时间线 → 审核 → 渲染与导出`

关键原则：

1. AI 提取结果先成为候选，用户确认后才进入项目事实。
2. ShotSpec 固化景别、构图、角色、动作、镜头运动、台词、时长和参考资产。
3. 每次生成保留输入快照、模型参数、费用、任务和输出版本。
4. 用户在镜头级选择候选或重做，不因一个镜头失败重跑整集。
5. 页面刷新、Worker 重启或供应商超时后，服务端仍能给出真实状态和下一动作。

## 6. 核心业务能力

### 6.1 工作空间与项目

- 项目、剧集、成员和角色权限。
- 项目级画幅、语言、目标时长、视觉风格和默认模型策略。
- 项目进度、异常任务、预算和待审核项总览。

### 6.2 剧本与结构化理解

- 导入或编写故事、小说片段和分集剧本。
- 版本化编辑，AI 拆分场景、镜头、对白和旁白。
- 提取角色、场景、道具、服装候选并人工合并、忽略或确认。
- 剧情连续性与角色设定冲突提示，不自动篡改已确认事实。

### 6.3 资产圣经与一致性

- 角色身份、外观、服装、声音及授权材料。
- 场景、道具、风格参考和多视角参考图。
- 资产版本、使用范围、来源、授权状态与镜头引用关系。
- 生成时自动组装与 ShotSpec 对应的参考资产，但允许用户覆盖。

### 6.4 分镜与镜头准备

- 可编辑 ShotSpec、镜头排序、增删拆合和批量校验。
- 关键帧/首尾帧候选生成、对比、选中与退回。
- readiness 检查：缺少角色、场景、台词或参考时不得误报可生成。
- 支持单镜头和选择性批量生成。

### 6.5 多模态生成

- 文本处理、文/图生图、图/参考生视频、TTS、音效和字幕。
- 供应商/模型能力目录和参数校验；前端只展示模型真实支持的参数。
- 每次生成先展示范围与预计消耗，昂贵操作支持确认。
- 输出多个候选，允许对比、选用、取消和局部重做。

### 6.6 任务、恢复与成本

- 统一任务中心：排队、运行、等待供应商、成功、失败、取消和未知。
- 重试、超时、取消、进度、错误原因和可执行的下一动作。
- 请求幂等、供应商任务对账，禁止因刷新或重试产生不可见的重复扣费。
- 额度预占、实际结算、释放、退款和逐任务成本明细。

### 6.7 后期、审核与交付

- 镜头顺序、裁剪、转场、对白、旁白、音乐、音效和字幕时间线。
- 逐镜头审核、整集预览、问题标记和版本回退。
- FFmpeg 渲染 9:16 成片，输出 MP4、字幕和制作清单。
- 导出时写入 AI 生成显式/隐式标识及可追溯内容编号。

## 7. MVP 范围

MVP 必须包含：项目/剧集、剧本版本、AI 拆镜候选、角色与场景资产、ShotSpec、图片和视频生成、候选选择、统一任务状态、成本明细、基础 TTS/字幕、简单时间线、FFmpeg 导出、审核与 AI 内容标识。

MVP 只接入一个默认文本模型、一个图像模型和一个视频模型，但从第一天通过稳定接口隔离供应商协议。第二供应商只有在故障切换或效果对比被验收为真实需求后进入范围。

## 8. 明确非目标

- 不在 MVP 自训视频基础模型、LoRA 平台或 GPU 调度平台。
- 不做微服务、Kafka、服务网格、Kubernetes 或多地域部署。
- 不做无限画布、专业 NLE 全功能、实时多人 CRDT 或移动端。
- 不承诺“一句话无人审核直接成片”；AI 输出天然需要选择和返工。
- 不做素材交易市场、社交社区、自动投放或平台分发。

## 9. 产品成功标准（进入 PRD 后量化）

- 一集可以从剧本完成到可播放 MP4，所有步骤有服务端状态。
- 单镜头失败或退回不会迫使整集重做。
- 任一成片镜头可追溯到 ShotSpec、参考资产、模型调用、费用和审核记录。
- 同一角色跨镜头具备可审核的一致性检查流程，而不是仅靠提示词宣称一致。
- 任何可计费请求在重试、超时和刷新后不会形成无法解释的重复结算。

## 10. 主要风险

- 模型能力和价格变化快：供应商能力表与业务模型分离，版本显式记录。
- 一致性无法绝对保证：使用资产圣经、参考输入、候选选择和质量检查降低漂移。
- 长任务结果不确定：任务持久化、幂等键、对账和人工处理状态不可缺失。
- 肖像、版权与敏感内容：素材授权、审核、审计和生成标识必须进入主流程。
- 自动化过度：高成本生成和关键资产确认保留人工门禁。
