# M15 模板与集成接口详细设计

> Design ID：DES-M15
> Requirement：[REQ-INT](../../requirement/015-M15-模板与集成接口需求.md)
> 状态：proposed

## 1. 设计结论与范围

M15 提供内部模板发布/实例化、版本化 API、公共 Webhook 投递、私有能力/扩展的**注册工作流**。API、Webhook 和扩展复用与界面相同的应用命令、权限、并发、M11 资源和 M14 治理规则，不获得数据库直写、对象存储通配或第二套执行路径。

M15 **只拥有私有能力注册的申请、审查编排和阶段记录**：M14 拥有准入政策/条款评估，M07 拥有 `CapabilityRevision`、能力资格与路由，M08 拥有 ProviderConnection/Binding、凭据、健康和 Job/Attempt 执行。M15 保存各阶段返回的稳定引用，不生成、启停或执行 Capability；注册工作流 `approved` 也不代表能力当前可路由，实时资格以 M07/M08 状态为准。

所有能力在单体应用内按逻辑模块实现，不拆出模板服务、API 服务或 Webhook 微服务。

### 1.1 范围内

- 从已批准事实生成不可变 TemplateRevision，发布、预览、实例化和显式迁移提案；
- 可撤销客户端身份、明确 Scope、唯一当前契约、幂等和 optimistic concurrency；
- 签名、防重放、筛选、投递日志、重试/死信/人工重放的公共 Webhook；
- 私有模型/LoRA 的注册申请与 M14/M07/M08 审查编排；
- 仅声明并调用白名单领域命令的受控扩展注册。

### 1.2 非目标

- 公共工作流/模型市场、商业分成、任意脚本节点或在核心进程安装第三方代码；
- API 通用 CRUD、数据库/对象桶直连、跨 Workspace 复制未发布事实；
- M15 自建 Capability、路由、Provider 连接、健康检查或执行 Job；
- 模板升级自动改写已运行项目，或把模板中的凭据/任务状态复制到实例。

## 2. 事实所有权与数据模型

| 对象 | 关键字段 | 不变量 |
| --- | --- | --- |
| `TemplateRevision` | type、schema version、source refs/versions、included manifest、defaults、dependencies、capability requirements、rights/sensitivity summary、status/hash | published 后不可改；只包含已批准、可发布事实 |
| `TemplateRelease` | template revision、organization visibility、required capabilities、released/retired by/time | release 不改变 revision；retire 不影响既有实例 |
| `TemplateInstantiation` | release、preview hash、target Workspace/project、status、created object refs、idempotency key | 新对象身份；来源 release/version 永久保留 |
| `TemplateSourceLink` | target object/version、release/source ref、local override metadata | 记录来源，不让模板拥有项目对象 |
| `TemplateMigrationProposal` | instance/current refs、from/to releases、add/remove/conflict/capability gaps/downstream impact、status | proposal 不写项目；逐项接受才调用领域命令 |
| `ApiContractRevision` | version、endpoint/command mapping、schema、deprecation window、status | API 与 UI 映射同一 application port；不暴露内部表 |
| `ApiClientRegistration` | M01 service identity ref、Workspace/project scope、actions、expiry、rate policy、status | 凭据由 M01/密钥设施管理；M15 不保存明文 secret |
| `ApiIdempotencyRecord` | client/workspace/key、request hash、command/version、result ref/status、expiry | 同 key 不同 payload 冲突；业务结果可回读 |
| `WebhookSubscription` | owner scope、event filters、endpoint、secret ref、current contract hash、status | endpoint/secret 变化产生新 revision；Workspace 隔离；不保留旧 payload encoder |
| `WebhookEvent` | domain event ref、public event type/version、minimal payload/hash、occurred_at | 稳定 event ID；不复制完整剧本/Prompt/凭据/媒体 |
| `WebhookDelivery` / `WebhookAttempt` | subscription/event、signature version、attempt/status、response summary、next retry/dead-letter | 重放同 event ID；投递状态不修改领域事实 |
| `PrivateCapabilityRegistration` | applicant、declaration manifest/hash、stage、M14 evaluation ref、M07 capability revision ref、M08 connection/binding readiness refs、decision history | 只保存工作流与外部 refs；不成为 Capability/Connection 真相 |
| `ExtensionRegistration` | manifest/version、requested queries/commands、M14 evaluation、approval/status | 仅白名单端口；不代表可执行任意代码 |

## 3. 私有能力注册工作流边界

### 3.1 工作流步骤

1. M15 `SubmitPrivateCapabilityRegistration` 冻结申请 Manifest：模型/LoRA 版本、media kind、输入输出、参考限制、地域/数据处理/权利、用量单位、健康契约和回滚/撤销声明。
2. M15 调用 M14 `EvaluateCapabilityAdmission`，只保存 `PolicyEvaluation` 引用和阻塞理由；M14 不创建 Capability。
3. 政策通过后，M15 请求 M07 验证/发布 `CapabilityRevision`。M07 自己校验 schema、purpose、限制、估计和资格并返回 revision ref；M15 不写 M07 表。
4. M15 请求/等待 M08 对 ProviderConnection/Adapter/Binding 的执行契约验证。凭据录入、加密、健康检查、提交/回调/unknown/取消/下载测试和 Binding 事实全部由 M08 完成。
5. 三方阶段引用齐全后 M15 将**注册流程**标为 `approved`。M07 仍依据实时治理、资源和 M08 health 决定可路由；M08 仍决定连接是否可提交。
6. 撤销时 M15 记录请求并分别调用 M07 的 capability retirement 端口与 M08 的 binding/connection disable 端口；只有下游确认后工作流进入 `revoked`。M15 不直接改它们的状态。

### 3.2 明确禁止

- `PrivateCapabilityRegistration` 不能被 M07 当作 `CapabilityRevision` 使用；
- `approved` 不能绕过 M07 GenerationPlan/preflight、M11 用量 Gate、M14 外发 Gate 或 M08 durable execution；
- M15 的“健康”页面只查询 M08 只读状态，不自行发心跳或判定 circuit；
- 注册撤销未完成时显示 `revoking/blocked`，不得由 M15 假装已停止执行。

## 5. 模块边界与跨模块契约

### 5.1 所有权矩阵

| 事实 | 所有模块 | M15 的责任 |
| --- | --- | --- |
| 用户/ServiceIdentity、credential issuance/revocation | M01 | 保存身份/密钥引用，编排客户端注册；不存明文凭据 |
| Brief/实体/风格/镜头/质量/交付预设等模板来源对象 | 各业务模块 | 冻结已发布 refs，实例化/迁移时调用其应用命令 |
| 资源政策/预留/实际 | M11 | API/实例化/能力流程调用同一 Gate，不复制配额逻辑 |
| 权利/条款/政策/准入 Evaluation | M14 | 模板发布、扩展/能力注册保存 evaluation ref |
| CapabilityRevision、资格、GenerationPlan、路由 | M07 | 请求并等待 M07 结果；只读展示 ref/status |
| ProviderConnection/Binding、凭据、健康、Job/Attempt/执行 | M08 | 请求/等待执行契约结果；只读展示 ref/status |
| Template/ApiContract/Webhook/Registration workflow | M15 | 唯一事实所有者 |

### 5.2 API 与 UI 共用端口

`ExecutePublicCommand` 只完成协议解析、契约版本、client/scope、rate limit、idempotency 和错误映射，然后调用与 UI 相同的应用命令。例如 API 的“批准计划”与 UI 都调用 M07 `ApproveGenerationPlan`，都触发 M11/M14 Gate；M15 不提供 `UPDATE table` 风格的通用 endpoint。

公开错误至少稳定映射：`unauthenticated`、`forbidden_scope`、`not_found`（防枚举）、`revision_conflict`、`idempotency_conflict`、`usage_blocked`、`policy_blocked`、`dependency_unavailable`、`rate_limited`。内部堆栈、Provider secret 和跨 Workspace 对象存在性不得泄露。

### 5.3 Webhook 契约

- 领域事件经 Outbox 转为最小 `WebhookEvent`；公共 event version 与内部 schema 解耦。
- Payload 只含 `event_id/type/version/occurred_at/workspace-scoped refs/status/trace` 和事件必需摘要。
- 签名覆盖 timestamp + event ID + raw body；接收方可按时间窗和 event ID 防重放。
- 一个 `WebhookEvent` 对一个 subscription 有一个 `WebhookDelivery`，重试/人工重放增加 Attempt，不改 event ID。
- Webhook 成功只表示通知送达，不代表对方业务成功；Webhook 失败永不回滚原领域事实。

### 5.4 注册工作流端口

| 阶段 | M15 发起 | 所有者返回 | M15 可做/不可做 |
| --- | --- | --- | --- |
| policy_review | M14 `EvaluateCapabilityAdmission` | PolicyEvaluation ref/result | 记录结果；不可修改条款/政策 |
| capability_review | M07 capability validation/publication port | CapabilityRevision ref/status | 记录 ref；不可创建/enable/route |
| execution_review | M08 connection/adapter contract port | connection/binding/health test refs | 记录 ref；不可保存凭据、跑健康或 Job |
| revoking | M07 retirement + M08 disable 请求 | 各自确认/失败 | 保持 workflow pending/blocked；不可直接改下游表 |

## 6. 关键状态、并发与幂等

### 6.1 状态机

| 对象 | 合法状态与转换 | 不变量 |
| --- | --- | --- |
| TemplateRevision | `draft → published`；published 可由 Release 状态表现 `retired/superseded` | published 内容不变；新内容新 revision |
| TemplateInstantiation | `previewed → running → succeeded \| partial \| failed`；partial/failed 可 `→ running` | 已创建对象有稳定 step key；恢复不重复创建 |
| MigrationProposal | `draft → ready → applying → applied \| conflicted \| failed \| cancelled` | proposal 生成不写项目；冲突需重新确认/新版本 |
| ApiClientRegistration | `pending → active → revoked \| expired` | revoked/expired 不恢复；新凭据新 registration/revision |
| WebhookSubscription | `pending_verification → active ↔ paused`；任意活动态可 `revoked` | filter/secret/endpoint 变化新 revision |
| WebhookDelivery | `pending → delivering → delivered \| retry_wait \| dead_letter` | Attempt 只追加；领域事实不受影响 |
| PrivateCapabilityRegistration | 主路径 `draft → submitted → policy_review → capability_review → execution_review → approved`；任一审查可 `→ changes_requested`（新修订后重新 submitted）或 `→ rejected`（终态）；仅 approved 可 `→ revoking → revoked`；下游引用失效时可投影为 `blocked` | stage 前进需上一所有者的稳定结果 ref；approved 不是 runtime eligibility；rejected/blocked 不得进入 revoking |
| ExtensionRegistration | `draft → submitted → approved \| rejected`；approved `→ revoked` | allowlist 冻结；新增命令需新 revision/审批 |

### 6.2 并发规则

1. Template head、Release、Subscription 和 Registration stage 均用 `expected_revision/stage` compare-and-swap；并发发布/推进只有一个成功。
2. 实例化 preview 绑定 release、依赖和 target baseline hash；执行前重新解析，stale 则拒绝，不偷偷采用新依赖。
3. Instantiation/Migration 每个领域步骤使用稳定 `workflow_id + step_id` 调用目标模块；partial 恢复回读已完成 step，避免重复对象。
4. API 幂等唯一键 `(client_id, workspace_id, contract_version, idempotency_key)`；同 key 不同 request hash 返回 409。
5. Webhook dispatcher 对 `(subscription_revision_id, event_id)` 唯一；抢占使用 lease，超时可接管，同 attempt token 只能完成一次。
6. 注册 workflow 不锁 M07/M08 长事务；保存请求/返回 ref 后推进。下游状态变化时 registration 只显示 stale/blocked，真实能力状态仍由下游拥有。

### 6.3 幂等键

| 写入 | 幂等键 | 重复结果 |
| --- | --- | --- |
| PublishTemplateRelease | template revision + visibility + request key | 回读同 Release |
| InstantiateTemplate | release + target workspace/project key + request key | 回读 workflow/created refs |
| ApplyMigrationProposal | proposal + accepted item set hash + request key | 回读各 step 结果 |
| ExecutePublicCommand | client + workspace + contract + caller key | 回读原业务 result/error |
| Dispatch/ReplayWebhook | subscription revision + event ID + replay request key | 同 Delivery 新/原 Attempt，不产生新事件 |
| AdvancePrivateCapabilityRegistration | registration revision + expected stage + dependency result ref | 回读当前 stage；不同 ref 冲突 |
| SubmitExtensionRegistration | manifest version/hash + owner scope | 回读原 registration |

| 实例化向导 | 查看包含项/default/能力/覆盖，确认创建 | previewing/ready/blocked/stale/running/partial/failed/succeeded；逐步已创建 refs 可见 |

| Webhook 控制台 | 管理订阅、轮换 secret、看/重放投递 | verifying/active/paused/revoked；delivery pending/retry/dead letter/delivered；response 脱敏 |
| 私有能力注册 | 提交声明、查看 M14/M07/M08 阶段、请求撤销 | draft/missing fields/policy_review/capability_review/execution_review/approved/changes_requested/rejected/revoking/revoked/blocked；能力资格与 M08 health 只读分栏 |

指标：模板发布/实例化成功率和 update conflict、API QPS/latency/rate-limit/idempotency hit/current contract hash、Webhook delivery/retry/dead-letter/replay/current signature policy、注册各 stage 周转/拒绝原因、M07 capability eligibility 与 M08 health 的只读关联、扩展 command 拒绝。第三方限流/投递队列与核心交互 worker 隔离，故障不得拖垮 UI/API 领域事务。

## 8. 失败路径与恢复约定

| 场景 | 用户结果 | 恢复 |
| --- | --- | --- |
| 模板依赖缺失/当前能力不足 | 实例化前列出依赖、能力差距和替换选项 | 安装/选择已批准依赖或新建 preview |
| 模板实例化 partial | 显示已创建/未创建 step，不伪装完成 | 以相同 workflow/step key 恢复；必要时明确取消，已建事实不直接删除 |
| migration target 并发变化 | proposal conflicted，项目不被覆盖 | 基于新 target revision 重新生成/确认 proposal |
| API 重复/同 key 异 payload | 相同 payload 回读；不同 payload 明确冲突 | 客户端使用原结果或新 idempotency key |
| API client/credential 撤销 | 新调用实时拒绝，历史日志保留 | 重新授权新身份/credential；旧 secret 不恢复 |
| Webhook 目标失败/限流 | 原业务成功，投递 retry_wait/dead_letter | 退避重试；修复目标后人工重放同 event ID |
| 注册政策阶段失败 | workflow 停在 changes_requested/rejected，规则原因可见 | 更新声明形成新 registration revision，再请求 M14 评估 |
| Capability/执行阶段失败 | 精确显示 M07 schema/eligibility 或 M08 connection/contract 原因 | 在所有者模块修复并返回新 ref；M15 幂等推进，不代为执行 |
| 能力健康异常/撤销中 | 注册页显示 runtime blocked/revoking；新路由由 M07/M08 停止 | M08 恢复/禁用并由 M07 重算资格；M15 仅同步阶段 |
| 扩展请求未批准命令 | 领域调用拒绝并审计，不执行 fallback SQL/script | 提交新 manifest/审批；不可临时放开通配权限 |

## 9. 逐 ID 验收映射

### 9.1 功能需求

| ID | 设计落点 | 可执行验证 | 切片 |
| --- | --- | --- | --- |
| INT-FR-001 | CreateTemplateRevision/immutable manifest | 从已批准对象创建；发布后更新/源变化不改 revision | F |

## 10. 实施顺序与 Gate

1. 先建立 TemplateRevision/Release/Preview/Instantiation 的已批准事实闭环和 SourceLink。
2. 增加 M01 ServiceIdentity 依赖、API contract/idempotency adapter，证明 UI/API 同端口同结果。
3. 将内部 Outbox 事件映射为最小公共 Webhook，完成签名、防重放、重试/死信/人工重放。
4. 实现 PrivateCapabilityRegistration 工作流，依次接 M14 policy、M07 capability、M08 execution refs；注册页面只读展示下游事实。
5. 最后开放 ExtensionRegistration 白名单，安全测试证明无任意代码/直连/跨 Workspace 路径。

整个切片 F 内，M15 只编排注册；能力与执行始终由 M07/M08 拥有。
