# M09 媒体、候选与选择详细设计

> Design ID：DES-M09
> Requirement：[REQ-MED](../../requirement/009-M09-媒体候选与选择需求.md)
> 状态：proposed

## 1. 设计结论

目标部署固定使用私有、版本化 MinIO 保存字节，PostgreSQL 保存 MediaArtifact 完整性、精确物理 Location、派生血缘、Candidate 和追加式 SelectionDecision。领域/Application Service 只依赖版本感知的 `ObjectStoragePort`，MinIO SDK、错误类型和管理凭据只能出现在基础设施适配器。文件 ready、候选可用和人工采用是三个独立判断。

M09 的媒体检查只回答“字节是否按声明完整、可安全存储并能被基础解析/解码”，不回答“对该镜头、审片或交付用途是否达标”。格式、长度、哈希、MIME/魔数、安全扫描和基础解码属于 M09 传输/存储完整性；目标时长偏差、黑帧、静音、镜头符合性、连续性和用途阻塞属于 M10。Candidate `ready` 因此可以与 M10 `unassessed/blocked` 并存。本模块不执行生成、不关闭质量问题、不批准审片或交付，也不拆为微服务。

## 2. 数据模型

| 对象 | 关键约束 |
| --- | --- |
| MediaObject | 可选稳定媒体身份、kind、current artifact；current 变化不修改历史 |
| UploadSession | workspace/project、purpose、声明 size/type/SHA-256、权利/保留范围、服务端临时 key、上传模式、expiry、idempotency request hash、status |
| MediaArtifact | 不可变字节版本：workspace、nullable MediaObject/version no、hash、size、media type、purpose、rights scope hash、retention、status；不保存“当前对象路径”作为身份 |
| MediaArtifactLocation | Artifact、storage profile、bucket、object key、MinIO object version id、size/SHA-256、ETag、status；物理 tuple 唯一，同 Artifact 至多一个 active location |
| MediaMetadata | probe version、codec、duration/timebase、dimensions、tracks |
| DerivationEdge | source→derived、operation/params hash；禁止环 |
| Candidate | target type/id/revision、job/attempt、artifact、ordinal；不可改目标 |
| CandidateSet | 冻结比较集或查询投影，不是主选 |
| SelectionDecision | target revision、purpose、assembly context、candidate、decision、supersedes |

同 `(target revision, selection purpose, assembly context)` 最多一个 current adopted。storyboard_reference、first_frame、last_frame、video_primary、audio_primary 等 purpose 不互相覆盖。

`MediaArtifact` 是不可变媒体版本；MinIO `object_version_id` 只是该 Artifact 某个物理 Location 的版本，两者不得混用。`MediaLocation` 承担物理位置历史。Artifact 复用必须同时满足同 Workspace、purpose、rights scope、retention class 和内容哈希；相同字节但权利或保留范围不同，保留独立逻辑 Artifact，不能因去重合并治理语义。

### 2.1 MinIO key 与引用规则

每个环境使用独立私有 bucket，key 由服务端生成且不含邮箱、项目名、原文件名、Candidate 或 Selection。规范前缀为：

```text
workspaces/{opaque_workspace_id}/staging/uploads/{upload_session_id}/payload
workspaces/{opaque_workspace_id}/quarantine/{artifact_id}/{ingest_attempt_id}/payload
workspaces/{opaque_workspace_id}/originals/{sha256_prefix}/{artifact_id}
workspaces/{opaque_workspace_id}/derivatives/{derivation_manifest_hash}/{artifact_id}
workspaces/{opaque_workspace_id}/agent-results/{agent_run_id}/{item_key}/{payload_hash}
workspaces/{opaque_workspace_id}/delivery-staging/{delivery_build_id}/{render_run_id}/{purpose}/{output_id}
workspaces/{opaque_workspace_id}/temporary/{operation_id}/{attempt_id}/{opaque_object_id}
```

`derivation_manifest_hash` 由排序后的全部 source Artifact refs/hash、处理引擎版本和规范化参数共同计算，因此单输入代理与 M13 多输入装配/交付输出都能获得合法 final key，不需要任意选择一个 source。Candidate 只引用 Artifact，不建立 `candidates/{candidate_id}` 字节副本。DeliverySnapshot 同样只冻结 Artifact/hash；M13 的 staging 对象通过 M09 验证、发布为 Artifact 后才可进入 Snapshot。ready/committed 引用必须包含 `storage_profile + bucket + object_key + object_version_id + size + SHA-256`；ETag 只用于 MinIO 对账，不能充当平台 hash。Location 迁移或灾难恢复追加新 Location 并再次验证相同 SHA-256，不修改 Artifact、Candidate、Selection 或 Snapshot。

## 3. 摄取流水线

M08 提交结果引用 → 对象下载到 MinIO quarantine 的服务端分配 key → 冻结精确 object version → 大小/类型/流式 SHA-256/恶意内容检查 → ffprobe/解码验证 → 复制到不可覆盖的 Artifact key → 校验目标 object version 与 SHA-256 → 短事务发布 Artifact/Location ready → 生成代理/缩略图/抽帧派生物 → 创建 Candidate → Outbox 发布 `CandidateReady`。

上述 ffprobe/解码只作为存储完整性门禁：验证容器可读、轨道/时基可解析且在安全资源限制内可解码样本；不在此判定时长是否符合 ShotPlan、是否黑帧/静音或语义质量。M10 读取 M09 的 Artifact/Metadata 精确版本后产生独立 QualityEvaluation/Issue。

上传媒体走相同验证，但 Candidate 是否创建由具体用途命令决定。单对象上传优先使用带 `content-length-range`、允许 Content-Type 和固定 key/expiry 的 MinIO POST Policy；需要大文件 multipart 时由 UploadSession 管理 upload id、part 数/大小、每 part capability 和完成清单，禁止把无限制通用 PUT URL 当成“已限制大小”。无论上传方式，完成命令都必须由受信任 Worker 读取精确 version 并流式计算 SHA-256；调用方声明、HEAD 或 multipart ETag 不足以通过。

quarantine→Artifact 是可恢复的 `prepare → copy → verify target → finalize → cleanup source`，不是 MinIO 原子 rename，也不与 PostgreSQL 组成分布式事务。copy 成功但响应丢失时按目标 key/version/hash 对账并回读同一 Artifact；目标 key 已存在但 version/hash 不符时隔离并报警，绝不覆盖。代理失败不改变原件 ready；原件精确 version 缺失不能只靠代理通过正式交付。

## 4. 应用接口

- Commands：`InitiateUpload`、`CompleteUpload`、`ExpireUpload`、`ReconcileArtifactPromotion`、`IngestProviderResult`、`RetryDerivation`、`CreateCandidate`、`RecordSelectionDecision`、`RebindCandidate`、`Quarantine/DeleteArtifact`；
- Queries：UploadSession/摄取 Operation、候选比较、媒体血缘、当前 purpose 主选、当前上下文可用性、删除影响、受限媒体访问；
- Events：`MediaArtifactReady/Quarantined`、`CandidateReady`、`SelectionDecisionRecorded`。

选择命令在 expected revision 下检查 Candidate ready、当前 context 可用、M14 权利和用户能力；预览高亮/收藏使用独立轻量对象。

## 5. 删除、复用与恢复

已被 Selection、ReviewPackage、Assembly 或 Snapshot 引用的 Artifact 禁止普通删除；保留/法定保全由 M14 决定。上游变化只返回 `usable_for_context=false + reasons`；显式 Rebind 重新做规格、质量和权利预检并创建新决定。

删除必须由 M14 DataLifecycleCase 冻结全部 ArtifactLocation 和精确 MinIO object version；M09 存储生命周期执行器只执行 M14 已领取且携带当前 fence token 的 `DeleteObjectVersion/PutObjectLegalHold`，把不可变 receipt 返回 M14，并按 M14 的完成结果推进 Artifact `deletion_pending/deleted` 投影。普通 `DeleteObject` 产生 delete marker、仍存在 non-current version 或只删除 active Location 都不算物理清除完成。处于 `placing/active` LegalHold 的 Location 不可领取删除；需要法定保全的数据类只有在 MinIO Object Lock 对全部 version 生效并由 M14 收齐回执后才显示 active。

存储故障保持 Candidate 历史状态并把 Artifact 标 `missing/verification_pending`，不把生成 Job 改成失败。读取精确 version 失败时不得回退到同 key latest；可从已验证副本/备份恢复相同字节到新 Location，SHA-256 一致后原 Artifact 恢复可用。重复回调按 `(job, output ordinal/hash)` 回读同一 Candidate；删除、copy 或 Hold 返回 unknown 时先 stat/读取精确 version 对账，不盲目重放副作用。

## 6. 性能、安全与验证

列表按需加载代理。工作区内部预览可以在每次授权后签发极短 TTL、仅 GET 精确 object version 的 MinIO URL；已签发 URL 在过期前是 bearer capability，数据库撤销只能阻止新 URL，不能宣称即时失效。要求即时撤销的外部分享、正式交付或显式高风险下载必须使用 M13 鉴权下载网关：SVC-01 逐请求/Range 重查 Grant/M14 并把一次性内部交接结果交给受控反向代理，代理再以最小权限读取精确 version；Python API 不缓冲媒体正文，也不把 MinIO URL 直接交给终端。

MinIO bucket 必须 private，生产强制 TLS 和 versioning；需 LegalHold 的 bucket 还必须启用 Object Lock。应用不得使用 root access key：API 只可创建限定 capability，Import/Media Worker 按 Workspace 前缀和动作最小授权，下载网关只可读取已解析的精确 version，Agent Worker 无通用对象凭据，生命周期身份才可执行受 fence 约束的 `DeleteObjectVersion/PutObjectLegalHold`。任何服务都不得向浏览器开放 ListBucket，日志/Trace 不记录 bucket、key、签名 query 或凭据。

内容哈希去重不跨租户权利边界。验证损坏媒体、重复摄取、并发选择、不同 purpose、越权 key、超大上传、multipart ETag、copy 响应丢失、精确 version 缺失、删除引用、LegalHold 竞争、代理恢复和显式复用。

映射 MED-FR-001—012、MED-NFR-001—005、AC-MED-001—009；A 用 Fixture 候选验证选择，C 接真实媒体。

## 7. 模块边界与跨模块契约

| 模块 | M09 接收 | M09 输出 | 边界规则 |
| --- | --- | --- | --- |
| M01/M02 | actor、workspace/project 权限 | 受限查询/内部短时访问和审计主体 | 对象键不暴露业务命名；服务端从 actor scope 解析 Workspace 前缀，跨租户 hash 不授予引用、签名或网关访问 |
| M07 | 计划 InputRef/参考精确版本 | `GetArtifactAvailability`、Selection ref | M09 不判断计划批准或路由；仅返存储/上下文可用性 |
| M08 | Job/Attempt/output ordinal、受限 provider locator、expected declaration | ingest operation、Artifact/Candidate ref、完整性观测 | M09 执行字节传输/隔离/验证；下载失败不改 Provider Job 为生成失败 |
| M10 | 上下文质量状态和问题摘要读模型 | Artifact/Metadata/Candidate 精确版本、`candidate.ready` | M09 只展示 M10 摘要，不保存或推断质量分/问题终态 |
| M12/M13 | ReviewPackage/Assembly/Snapshot 引用 | 媒体可读性、Selection 和删除影响 | 活动引用阻止普通删除；不自动改选代理或最近 Candidate |
| M14 | rights/retention/legal hold 结论、已领取的 LifecycleCase item/fence command | ArtifactLocation 精确 version、物理删除/Hold receipt 与 Artifact 投影结果 | M14 独占策略、Case、fence 和 LifecycleItemResult；M09 仅经 ObjectStoragePort 执行精确物理动作并回 receipt，不自行决定 retention；保留或法定保全优先 |

`MediaArtifact` 是字节和完整性事实；`Candidate` 是指向历史目标版本的可比较输出；`SelectionDecision` 是追加式人工决定。三者分别建表和版本约束，不在 Artifact 上增加 `selected`，不在 Candidate 上增加 current 主选字段。

## 9. 状态、并发与幂等

### 9.1 状态

| 对象 | 状态 | 关键守卫 |
| --- | --- | --- |
| UploadSession | `initiated → uploading → uploaded → verifying → promoting → completed`；非终态可进 `expired/cancelled/failed` | completed 必须绑定已验证 Artifact/Location；expiry 只触发具名清理，不直接按业务 prefix 删除 |
| MediaArtifact | `pending→verifying`；验证和 promotion 后进入 `ready`、`quarantined` 或 `missing`；恢复后可重回 verifying；允许删除的非终态可进 `deletion_pending→deleted` | ready 需精确 object version、size/SHA-256/type/security/基础解析通过；missing 恢复到新 Location 后重验证；placing/active legal hold 禁止领取删除；全部目标 version receipt 成功后才 deleted |
| MediaArtifactLocation | `staged → verified → active → retiring → retired`，并允许 `quarantined/missing/deletion_pending/deleted` | 同 Artifact 至多一个 active；active 切换先验证相同 SHA-256；物理删除历史不删除 Location 审计行 |
| Candidate | `ingesting` 后进入 `ready`、`quarantined` 或 `failed`；任一非归档态可在满足引用守卫后进 `archived` | ready 只表示历史输出已完整摄取；不因上游新版转 stale；M10 状态独立；隔离解除需 Artifact 新证据 |
| SelectionDecision | 每条追加决定的值为 `adopted`、`alternate`、`rejected` 或 `cleared`，后续决定以 `supersedes` 关联 | 决定不原地修改；current 由未被 supersede 的决定投影；个人高亮/shortlist 不在此状态机 |

### 9.2 幂等与并发

- Upload 唯一：`workspace + Idempotency-Key`；request hash 覆盖 purpose、size/type/SHA-256、rights/retention、upload mode，相同键不同 declaration hash 返回 `idempotency_conflict`。
- Provider ingest 唯一：`generation_job_id + output_ordinal`，再校验 provider output/content hash；同 ordinal 不同结果进隔离/对账。
- Artifact 只可在同 Workspace/同 purpose/同权利与 retention 范围按 content hash 复用，不因 hash 相同跨租户建可见引用；物理 Location 复用不得合并逻辑治理范围。
- 派生唯一：`source_artifact + operation_version + params_hash`；候选唯一：`job + output_ordinal`。
- 选择使用 `selection_context revision`乐观锁和部分唯一约束：`target revision + selection purpose + assembly context` 最多一个 current adopted。
- 对象存储调用不在领域事务内；摄取分 prepare→事务外 transfer/copy/verify→finalize，中断由 Operation、精确 object version 与幂等 Worker 恢复。promotion key/version/hash、Lifecycle fence token 和 attempt receipt 均进入幂等键/对账输入。
