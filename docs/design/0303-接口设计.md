## 2. 公共 API 约定

### 2.1 基本规则

- 基础路径 `/api/v1`；破坏性变更才升级主版本，新增字段不算破坏性变更。
- 资源名用复数名词、`kebab-case`；字段名 `snake_case`；ID 为 UUID 字符串。
- 时间 RFC 3339（UTC，带 `Z`）；时长 `*_ms` 整数；金额 `*_micros` 整数（界面换算到元，0302 D5）。
- 查询：`GET`；创建：`POST /资源`；修改头表字段：`PATCH`；**业务命令**（确认、选定、锁定、取消等）：`POST /资源/{id}/<动作>`，动作名为动词。
- 所有写请求（`POST / PATCH / DELETE`）必须带 `Idempotency-Key`（UUID）；同键同请求体返回首次结果，同键不同请求体返回 `422 idempotency_key_reused`（0201 G1）。
- 修改或选定正式对象时，请求体带 `expected_revision`；不一致返回 `409 revision_conflict`，响应体带当前 `revision`（0201 G2）。

### 2.2 认证与安全

- 登录成功后下发 `lv_session` Cookie：`HttpOnly; Secure; SameSite=Lax; Path=/`。
- CSRF：登录响应同时下发非 HttpOnly 的 `lv_csrf` Cookie，写请求须带 `X-CSRF-Token` 头且与 Cookie 一致。
- 每个请求带或生成 `X-Request-Id`；响应回写 `X-Request-Id` 与 `traceparent`。
- 权限：MVP 两种角色（`admin`、`producer`）；项目级接口校验项目属于用户组织且未删除；管理接口仅 `admin`。

### 2.3 分页、筛选、排序

- 列表统一 keyset 分页：请求 `?limit=50&cursor=<opaque>`，响应 `{ "items": [...], "next_cursor": "..." | null }`；`limit` 上限 200。
- 筛选使用明确字段：`?status=failed&status=unknown&episode_id=…`（同名参数多值为“或”）。
- 排序 `?sort=-create_time`，只允许端点声明的字段。

### 2.4 错误模型

采用 RFC 9457 `application/problem+json`，并增加稳定的 `code`：

```json
{
  "type": "https://lanverse.local/errors/revision_conflict",
  "title": "内容已被修改",
  "status": 409,
  "code": "revision_conflict",
  "detail": "镜头 3-12 已被更新，请刷新后重试",
  "request_id": "…",
  "errors": [{ "field": "duration_ms", "code": "out_of_range", "message": "超出模型允许范围 4–10 秒" }],
  "meta": { "current_revision": 7 }
}
```

## 3. 资源模型要点

- 所有对象返回 `id`、`create_time`、`update_time`；已逻辑删除（`is_delete = true`）的对象默认不返回。
- 头表对象返回 `revision` 与 `current_version`（内嵌当前版本内容）；版本历史用单独的 `/versions` 端点。
- 对象的派生状态在响应中统一为 `status` 结构：

```json
"state": {
  "progress": "awaiting_selection",
  "stale": [{ "cause_type": "reference_version", "cause_label": "造型「日常装」v3", "since": "…" }],
  "missing_refs": [{ "owner_type": "look", "owner_id": "…", "name": "李明 / 战斗受伤" }]
}
```

- 金额字段同时返回 `*_micros` 与 `*_display`（如 `"¥12.30"`）以减少前端换算错误。

### 4.13 上传流程

```text
浏览器 → POST /projects/{pid}/uploads（校验类型与大小，登记 media_asset(status=uploading)）
       ← 预签名 PUT（或分片上传 ID + 每片预签名 URL），限定 object_key、Content-Type、Content-Length
浏览器 → 对象存储 PUT（显示进度）
浏览器 → POST /uploads/{id}:complete
backend → 启动 MediaIngestWorkflow（media 队列：按内容识别类型、ffprobe、缩略图 / 波形、sha256；agent 队列：内容审核）
       → media_asset.status = ready | rejected | failed，推送 media.updated
```

## 5. 实时推送（SSE）

### 5.1 通道

- `GET /api/v1/projects/{pid}/events`（`text/event-stream`）；另有 `GET /api/v1/me/events` 推送通知。
- 每条事件带 `id`（Kafka 事件 ID）；断线重连带 `Last-Event-ID`，服务端从 Redis Stream 中最近 10 分钟的缓冲补发，超出则发送 `resync` 事件，前端全量刷新当前页面（0202 AVL-04）。
- 服务端每 20 秒发送注释行心跳；连接 30 分钟后主动关闭，前端自动重连（便于负载均衡与发布）。

### 5.2 事件

事件只携带“什么变了”，前端据此使相应 TanStack Query 缓存失效，不在事件中携带完整对象。

| event | data | 前端动作 |
| --- | --- | --- |
| `operation.updated` | `{operation_id, batch_id?, target_type, target_id, status, progress?}` | 失效任务中心、目标对象 |
| `batch.updated` | `{batch_id, succeeded, failed, unknown, total}` | 失效批次 |
| `shot.updated` | `{shot_id, episode_id, revision}` | 失效镜头与镜头表 |
| `episode.updated` | `{episode_id, parse_status}` | 失效集列表、结构 |
| `bible.updated` | `{owner_type, owner_id}` | 失效设定集 |
| `reference_slot.locked` | `{slot_id, version_no}` | 失效槽位 |
| `stale.changed` | `{object_type, object_ids[]}` | 失效受影响对象、影响清单 |
| `media.updated` | `{media_asset_id, status}` | 失效媒体库 |
| `edit_plan.updated` / `delivery.updated` | `{episode_id, …}` | 失效剪辑 / 交付 |
| `budget.updated` | `{available_micros}` | 失效预算 |
| `canvas.updated`（V1） | `{document_id, revision}` | 拉取增量 |
| `notification.created` | `{notification_id}`（`/me/events`） | 刷新通知角标 |
| `resync` | `{}` | 全量刷新 |

## 6. 领域事件（Kafka）

### 6.1 信封

```json
{
  "event_id": "uuid",
  "event_type": "lanverse.operation.completed.v1",
  "occurred_at": "2026-09-25T08:00:00Z",
  "org_id": "uuid",
  "project_id": "uuid",
  "actor": { "kind": "user|agent|system", "id": "uuid|null" },
  "aggregate": { "type": "operation", "id": "uuid", "revision": 3 },
  "trace": { "traceparent": "…" },
```

- 主题 = `event_type`；分区键 = `project_id`；消费者按 `event_id` 去重（`infra.processed_event`）。

## 7. 内部契约

### 7.1 Temporal Activity（Go 工作流 ↔ Python agent-worker）

所有 Activity 输入输出在 `contracts/activities/<name>.schema.json` 定义；Go 用代码生成的结构体，Python 用 Pydantic 模型并在 CI 中与 schema 校验一致。

| Activity | 队列 | 输入要点 | 输出要点 |
| --- | --- | --- | --- |
| `llm.run_skill` | `agent` | `skill_key`、`skill_version`、`model_key`、冻结输入（文本片段带偏移、结构化对象）、`budget`、`trace` | `result`（按 Skill 输出 schema）、`trace_steps[]`、`usage`、`cost_micros` |
| `provider.submit` | `agent.<provider>` | `operation_id`、`provider_request_key`、`adapter_key`、`provider_model_id`、`mode`、`params`、`inputs[{role, media_url, media_type, duration_ms, text}]`、`credential{id, key_id, ciphertext}`（密文，0307 §5.2） | `outcome`（`accepted` / `rejected` / `unknown`）、`provider_task_id`、`error{code,retryable,message}` |
| `provider.query` | `agent.<provider>` | `provider_task_id` 或 `provider_request_key` | `state`（`pending` / `running` / `succeeded` / `failed` / `not_found`）、`result_urls[]`、`usage`、`error` |
| `provider.cancel` | `agent.<provider>` | `provider_task_id` | `outcome` |
| `provider.test_credential` | `agent` | `provider_key`、`credential{id, key_id, ciphertext}` | `result` |
| `moderation.check` | `agent` | `media_url` 或 `text`、`kind` | `status`、`labels[]` |
| `prompt.compose` | `agent` | 镜头参数、参考描述、目标模型 | `prompt`、`negative_prompt` |

Go 侧 Activity（`flow` / `media` 队列）不跨语言，契约为 Go 接口，见 0304。

### 7.3 Agent 只读工具的内部端点（V1）

`backend-api` 暴露 `/internal/agent-tools/*`，仅接受 `agent-api` 服务令牌，且必须带由 Go 签发、绑定 `session_id + project_id + user_id` 的短期工具令牌（15 分钟）：

| 端点 | 用途 |
| --- | --- |
| `GET /internal/agent-tools/projects/{pid}/summary` | 项目、集、阶段进度 |
| `GET /internal/agent-tools/episodes/{eid}/structure` | 集结构（可按场裁剪） |
| `GET /internal/agent-tools/episodes/{eid}/shots` | 镜头表 |
| `GET /internal/agent-tools/bible` | 设定集摘要 |
| `GET /internal/agent-tools/models` | 可用模型与限制 |
| `POST /internal/agent-tools/quotes:preview` | 预估费用（不创建 Operation） |

写操作不开放给 Agent：Agent 只输出**提案**（命令列表 + 差异）；用户在界面点击“应用”后，`POST /agent/proposals/{id}:apply` 由服务端以**该用户身份**逐条执行，与用户手动调用等价，付费项进入报价确认（0301 §7.4、F34）。

### 7.4 供应商回调

`POST /api/v1/provider-callbacks/{provider_key}`：按供应商规则验签（HMAC 或公钥）；只作为“唤醒”信号——验签通过后向对应工作流发送 Signal，工作流仍以 `provider.query` 的结果为准，防止伪造与乱序。

### 7.5 AG-UI 代理（V1）

`POST /api/v1/projects/{pid}/agent/sessions/{sid}/runs`（SSE）：Go 校验会话与项目权限、落库用户消息，转发到 `agent-api /internal/agent/runs`，逐条持久化 AG-UI 事件（`agent.message.seq` 递增）后转发给浏览器。`GET …/sessions/{sid}/messages?after_seq=` 用于断线续传。
