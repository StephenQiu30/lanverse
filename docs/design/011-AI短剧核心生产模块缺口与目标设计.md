## 1. 决策结论

Lanverse 当前不是从零开始：单集剧本不可变版本、人工结构提取决议、六类资产及权利门禁、稳定 Shot/ShotSpec/AssetVersion 固定引用都已达到本地纵向闭环。真正的产品缺口位于这些对象之间：**没有整剧入口、没有可审核的分集方案、没有剧情状态化资产、没有剧本内容到镜头的覆盖证明**。

本 Design 建议接受五项核心决定：

1. 在现有单集 `ScriptSource/ScriptVersion` 上方新增项目级 `ScriptDocument → DocumentRevision → EpisodePlan → ImportCommit`，保存整部原稿、分集候选和批量物化血缘；不推翻现有单集版本底座。
2. “这份剧本做多少集”分为确定性与建议性两种答案：合法显式集标记给出精确集数；无标记文本只给带证据、时长区间和置信度的 Top-3 方案，最终由人确认。
3. 新增稳定 `NarrativeUnit/Version`。剧本文本与镜头是多对多覆盖关系，不能强行做段落与镜头 1:1，也不能只靠字符位置或镜号维持血缘。
4. 资产严格分层：`Asset` 是身份、`AssetState` 是剧情状态、`GenerationRun → OutputCandidate` 是待选生成结果，主选候选或手工上传再形成不可变 `AssetVersion`；镜头固定引用 Asset/State/Version，`@图片N/@视频N/@音频N` 只是 Prompt 编译显示别名。
5. AI 生成的是 `EpisodePlan`、资产关联和 `StoryboardDraftBatch` 候选，不直接覆盖 Episode、Asset 或 Shot；每次落入正式对象前都必须经过预检、人工决定、幂等应用和影响记录。

当前 MVP 不再使用完整平台/B2B/公开 GA 口径。建议只看三个内部里程碑：

| 内部里程碑 | 6 人团队 | 4 人团队 | 范围 |
| --- | ---: | ---: | --- |
| MVP-A 制作核心 | **16–18 周** | **24–28 周** | 整剧导入、分集、改写、稳定叙事单元、状态资产、分镜覆盖和分镜包 |
| MVP-B 图片生成验证 | **累计 21–24 周** | **累计 32–36 周** | 再增加一个真实图片 Provider、Candidate/Selection/Lineage 和图片预览 |
| MVP-C 内部动态样片 | **累计 26–30 周** | **累计 39–44 周** | 再增加一个视频 Provider 和极简拼接；仍不含商业化 |

详细工作包和不重复计费口径见 DES-012。本文后续给出的完整对象设计可以被 MVP 分批接受，不要求一次性实现全部目标能力。

## 2. 事实等级与研究边界

- **当前代码事实**：由本仓库模型、API、服务、前端和 E2E 直接证明。

## 4. 目标生产主链

~~~mermaid
flowchart LR
    A["整剧 ScriptDocument"] --> B["不可变 DocumentRevision"]
    B --> C["格式体检与 NarrativeBlock"]
    C --> D["EpisodePlan Top-3 候选"]
    D --> E["人工调整并确认边界"]
    E --> F["批量物化 Episode + 原始 ScriptVersion"]
    F --> G["NarrativeUnit / 修订映射"]
    G --> H["资产候选决议与 AssetState"]
    G --> I["StoryboardDraftBatch"]
    H --> I
    I --> J["人工应用 Shot / ShotSpec"]
    J --> K["CoverageReport + Readiness"]
    K --> L["PromptRevision / GenerationRun"]
    L --> M["OutputCandidate 主选/备选"]
    M --> N["Timeline / Review / Delivery"]
~~~

主链遵守四个阶段边界：

1. **分析不写正式对象**：格式解析、分集、资产和分镜模型输出全部先落候选批次。
2. **确认不等于发布**：用户可先确认方案并物化草稿；发布 current pointer 是独立 CAS 命令。
3. **发布不自动覆盖下游**：新剧本、资产主选或状态只产生影响报告；历史 ShotSpec、Prompt 和输出保持固定。
4. **Ready 是派生门禁**：必须同时满足叙事覆盖、资产状态/权利、镜头规格和供应商输入，不是一个可手工随意修改的布尔字段。

## 5. 模块 A：整部剧本导入与格式体检

### 5.1 P0 范围

P0 支持：

- 粘贴全文；
- UTF-8 `.txt` 和 `.md`；
- 原始文件、原始 hash、规范化正文和 normalizer 版本；
- 编码、BOM、换行、字符数、显式集标记、疑似场景标题、空段和乱码诊断；
- 规则拆集、人工边界编辑、批量物化草稿和批量发布预检。

本估算绑定首期限额：每个 DocumentRevision 最多 200,000 个 Unicode code point、每次计划/物化最多 50 集、每集继续满足当前 20,000 字契约。超过任一上限需要分页/分片任务、对象存储和性能重新估算，不能把本章工期直接外推。

P0 不支持 PDF、扫描件和 DOCX/OCR。它们的版面、表格、批注、隐藏文本和宏安全会显著扩大范围；后续如需标准编剧格式，优先增加纯文本 [Fountain](https://fountain.io/syntax/)。

### 5.2 目标用户流程

1. 用户在 Project 级选择“导入整部剧本”，填写标题、语言、来源和权利声明。
2. 系统保存原始媒体/字节和 `DocumentRevision.raw_text`，再生成带版本的 `normalized_text` 与 normalization map；不覆盖用户原文。
3. 格式体检输出可定位到行列和 Unicode code-point 区间的 `FormatIssue`。
4. 系统识别集标记、场景头、对白、动作、旁白、前言/人物表等 `NarrativeBlock`。
5. 用户选择“按标记”“指定集数”“按目标时长”或“映射已有 Episode”。
6. 系统生成 EpisodePlan，不创建 Episode；用户可移动边界、拆集、合集、锁边界、改标题和排除项目资料。
7. `validate` 返回覆盖、空集、超长、权利、已有镜头和并发影响。
8. `materialize` 同一事务创建/映射 Episode、ScriptSource 和 draft ScriptVersion，但不改变已有 current pointer。
9. 用户再次确认后批量 publish。沿用现有语义：从冻结 draft 正文创建新的 published sibling，再 CAS 切 current；ImportCommit 保存每集 `draft_version_id → published_version_id`。任一集冲突则全部 current pointer 保持不变。

### 5.3 核心模型

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| ScriptDocument | project、title、source_type、source_media_version、language、rights | 项目级来源身份；P0 扩展 Media `document` kind 和安全 text MIME/probe，不假设现有 Media 已支持 |
| DocumentRevision | document、version、raw_text/raw media ref、raw hash、normalized_text/hash、normalizer version、normalization_map | 只追加；任何修正产生新 revision；可在 raw/normalized 坐标间定位 |
| FormatIssue | code、severity、coordinate_space、source span、raw/normalized line/column、evidence、resolution | blocking 问题未决不能物化 |
| NarrativeBlock | revision、position、kind、source span、text hash、metadata | 覆盖规范化正文；不把 UTF-16 offset 当身份 |
| ImportAnalysisRun | revision、parser/model/prompt version、input/result hash、task/status | 重跑新建；不覆盖旧结果 |
| EpisodePlanningRun/PlanSet | revision、analysis/parser/model/prompt/solver/profile/cost、constraints hash、status | 一次运行的输入与 Top-3 生成血缘 |
| EpisodePlan | run、rank、total score、revision、strategy、requested count/target duration、status | 固定一个 DocumentRevision；只管理 draft/review/confirmed/superseded |
| EpisodeProposal | plan、position、start/end block、estimated duration、confidence、lock | 非排除 block 必须恰好落入一集 |
| BoundaryEvidence | boundary、kind、score、source range、reason、decision | 每个 AI 边界必须能回看证据 |
| ImportCommit | plan、mode、idempotency、expected project/episode revisions、expected current IDs、expected order hash、draft/published map、status | 独占 materialize/publish 执行状态；重放不重复建集；发布 all-or-none |
| EpisodeSegmentOrigin | episode、document revision、proposal、source range/hash | 证明单集来自整剧哪个区间 |

所有 NarrativeBlock、EpisodeProposal、EpisodeSegmentOrigin 的持久区间都以 `normalized_text` 的 Unicode code-point 为基准；`normalization_map` 负责回显原始字节/文本位置。浏览器 UTF-16 offset 只能是临时 UI 坐标。

映射已有 Episode 时，计划必须显式选择 `append_new / replace_order / map_existing`，ImportCommit 固定每个目标 Episode 的 expected revision/current script version 和完整 active order hash。插入/替换顺序作为一次全序列 CAS 应用，不能边发布边移动 position。

### 5.4 失败规则

| 情况 | 产品行为 |
| --- | --- |
| 非 UTF-8、伪装 MIME、乱码 | 阻塞并给出转码动作；不得把乱码送入模型 |
| 集号缺失、重复、逆序或空集 | 显示精确行号；不得静默按出现顺序发布 |
| “第 3 集”出现在对白中 | 只有独占一行且满足语法的标记可成为硬边界 |
| 前言、人物表、世界观、后记 | 用户选择作为项目资料、排除或归入某集 |
| 单集超过当前 20,000 字 | 物化前阻塞拆分；不能绕过下游契约 |
| 分析任务超时/结果非法 | 保留规则结果和人工方案；unknown 不盲重试扣费 |
| 原稿在计划后发生变化 | `EPISODE_PLAN_STALE`，只能基于新 revision 生成新计划 |
| 映射到已有且已有镜头的 Episode | 默认只创建候选版本；先给影响预览，禁止覆盖 |

## 6. 模块 B：如何判断一份剧本制作多少集

### 6.1 模式一：显式集标记，给确定答案

VibeReels 公开行为表明其支持独占一行的 `第X集/话/章`、`EP X`、`EPISODE X`，并要求顺序连续；[LocalMiniDrama 固定提交的客户端解析器](https://github.com/xuanyustudio/LocalMiniDrama/blob/05f90fb9ec21dea5753e324b673fc8a96bc6b2e0/frontweb/src/utils/scriptEpisodes.js#L6-L77)也用行首正则做规则拆分。这类输入不需要 LLM。

Lanverse 的规则模式应满足：

- 中文数字、阿拉伯数字、全角数字可识别；
- 标记独占一行；
- 编号连续且区段非空；
- 前后所有正文都有明确去向；
- 结果集数等于合法非空区段数，测试语料准确率必须为 100%。

### 6.2 模式二：用户指定集数，求最合适边界

用户指定 `N` 后，以 NarrativeBlock/NarrativeUnit 边界为最小切分点，通过确定性求解器生成恰好 N 集。硬约束是：

- 不在一句对白或不可拆动作中间切；
- 任何必需内容不 gap、不 overlap；
- 不产生空集；
- 锁定边界不可移动；
- 每集时长不得超出用户批准的范围。

软目标是时长均衡、优先在场景/节拍结束处切、有结尾钩子、不切断因果链和状态转变。LLM 负责给节拍、钩子、因果链和证据候选；动态规划/约束求解器负责满足硬约束。

### 6.3 模式三：按目标时长，给建议范围

无显式标记且用户未指定集数时：

~~~text
D_total = Σ(
  dialogue_chars / configured_dialogue_rate
  + narration_chars / configured_narration_rate
  + action_beat_duration
  + pause_duration
  + transition_duration
)

N0 = max(1, ceil(D_total / target_episode_duration))
~~~

系统在 `N0-2 … N0+2` 中求可行方案，至少返回：

- 均衡时长方案；
- 强钩子/快节奏方案；
- 较少集数/较慢节奏方案。

Huobao 源码中的“500 字/分钟、4.5 字/秒、约 12 秒一生成段落”只能作为初始实验参考，不是行业真值。实际参数必须按题材、选定音色、对白/动作比例和 animatic 实测校准。

边界代价可表达为：

~~~text
boundary_cost =
  duration_deviation
  + split_dialogue_penalty
  + split_scene_penalty
  + weak_hook_penalty
  + unresolved_causal_chain_penalty
  + state_continuity_penalty
~~~

产品必须显示“推荐 8–10 集，主方案 9 集”，而不是把 9 集冒充客观正确答案。用户最终可锁定、移动、拆分或合并边界。

### 6.4 建议质量门槛

在至少 20 部、三种题材、每部 3–20 集的授权黄金样本上，由两名编剧/制片独立标注：

- Top-3 包含人工接受集数的比例 ≥90%；
- 隐式边界在相邻一个 NarrativeBlock 容差内 F1 ≥0.85；
- 每集人工边界调整中位数 ≤2 次；
- 预计时长相对配音/animatic 的 MAPE 内测 ≤25%，试运营前 ≤20%；
- 所有低置信或可能切断对白/因果链的边界都被提示。

这些是建议 Go 门槛，不是当前已达到事实。

## 7. 模块 C：剧本结构、改写与稳定叙事单元

### 7.1 为什么现有 Scene/Dialogue 不够

当前 Scene 有源范围，ShotSpec 可引用 dialogue IDs，但剧本发布新版本后，影响判断只是“Shot 的 source_script_version_id 是否等于 current version”。它能保护历史，却无法回答：

- 这段对白只是改了措辞，旧镜头能否继续使用？
- 一个动作被拆成三个节拍，哪些镜头需新增？
- 一段伏笔被删掉，旧镜头应标 orphan 还是批准省略？
- 两个场景合并后，资产状态和导演标注如何迁移？

### 7.2 目标模型

| 实体 | 关键字段 | 作用 |
| --- | --- | --- |
| ScriptRevision | kind=`original/adapted/formatted`、parent、content/hash、status | 原文、改写和格式化都是不可变修订 |
| NarrativeUnit | stable unit_id、episode、kind、parent_unit_id、required | 叙事事实的稳定逻辑身份；Scene 是容器，只有 leaf unit 参与 required coverage |
| NarrativeUnitVersion | unit、revision、source span、text hash、payload | 某次修订中的具体表达 |
| RevisionMappingEdge | from/to unit version、relation、confidence、evidence、decision | preserved/rewritten/split/merged/added/omitted |
| DirectorMark | formatted revision、base hash、source range、unit ids、label/note | 导演标注绑定内容基线，不绑定易变镜号 |
| ImpactAssessment | from/to revision、affected units/shots/assets/prompts、reason | 局部失效传播与人工决策入口 |

`NarrativeUnit` 至少覆盖 scene、beat、action、dialogue、narration、transition；Scene 只作为容器和空间/时间上下文，不与其子 beat/action/dialogue 重复计数。只有不可再分的 leaf unit 可以标记 `required_for_coverage`。hook/payoff 可先作为标签，不宜首期制造过多实体类型。

### 7.3 改写规则

- AI 改写输出 `AdaptationCandidate`，绝不原地覆盖 original。
- 每个候选固定输入 revision、brief、Skill/Prompt/model 版本、费用和输出 hash。
- 人工可逐单元接受、拒绝、修改；发布后形成新的 adapted/formatted ScriptRevision。
- 任何新增事实、删除关键情节、角色关系或结局变化必须显式标识。
- 映射低置信时允许手工决议；没有映射决议的 required unit 不得进入自动分镜 Ready。

## 8. 模块 D：资产识别、状态、版本与主选治理

### 8.1 四层对象必须分开

~~~mermaid
flowchart LR
    A["Asset 稳定身份<br/>角色小雨"] --> B1["AssetState base/常服"]
    A --> B2["AssetState 婚纱"]
    A --> B3["AssetState 受伤"]
    B3 --> C["GenerationRun"]
    C --> D1["OutputCandidate A 拒绝"]
    C --> D2["OutputCandidate B 主选"]
    C --> D3["OutputCandidate C 备选"]
    D2 --> E["promote 为 AssetVersion v2<br/>冻结规格+固定媒体"]
    B3 --> F["手工上传/录入 AssetVersion v1"]
~~~

- `Asset` 回答“是谁/是什么”；改名不换 ID。
- `AssetState` 回答“剧情此刻是什么状态”；例如常服、婚纱、受伤、雨夜、破损、耳语。
- `AssetVersion` 回答“镜头实际固定哪套规格和媒体”；由手工录入或主选候选提升而来，只追加、不覆盖。Version 本身仍可能是 draft/blocked，是否已审核和可生产由独立 readiness/review 派生。
- `OutputCandidate` 回答“一次或多次模型生成出了哪些待选结果”；主选/备选是只追加决策，主选通过显式 promote 产生新 AssetVersion，不把旧 URL 覆盖掉。

### 8.2 资产提取与决议箱

现有资产提取 candidate 只有 kind/name/description。目标 candidate 增加：

- source NarrativeUnitVersion 和精确证据区间；
- canonical name、alias、kind、state hint、出现集/单元；
- exact/alias/context/semantic 候选及置信理由；
- `required_reason`（例如出镜主体、明确交互、连续性关键、声音必需）和是否进入生产门禁；
- UI 的“新建/修改后新建/关联/合并/忽略”分别映射现有 `accept_new / accept_with_changes / link_existing / merge_into / ignore`，不另造第二套领域命令。

同名角色、双胞胎和跨类型同名必须允许。名称规范化采用 Unicode NFKC、trim、casefold、连续空白折叠；只产生重复警告，不自动合并。语义向量只负责推荐候选。

### 8.3 资产圣经工作台

目标页面按“身份 → 状态 → 版本历史与待选候选 → 权利/审核 → 使用镜头”聚合：

- 角色、场景、道具、服装、视觉风格、声音六类沿用；
- 每个 Asset 自动有保留的 `base` 状态；
- 状态显示出现 Episode/NarrativeUnit 证据；
- 上传/生成候选、审核、主选/备选、历史和费用可追溯；
- Shot 的逻辑绑定显示 `asset_id + state_id + version_id + slot_key`；物理事实仍以 `asset_version_id + slot_key + binding_source` 为主，Asset/State 从 Version 派生，避免三组 ID 独立漂移；
- `@图片N` 等 token 由当前有序 binding 编译，N 不是数据库身份。

### 8.4 影响治理

| 操作 | 必须保留 | 派生影响 | 禁止行为 |
| --- | --- | --- | --- |
| 改名 | asset_id、state/version、Shot 绑定、历史输出 | 使用旧名称快照的 Prompt stale | 按名称级联重写关系 |
| 禁用 Asset | 历史媒体、绑定、输出、审计 | 当前镜头 blocked，新绑定/生成禁止 | 静默删除 Shot 引用 |
| 禁用 State | 其他状态和历史版本 | 使用该状态的镜头 blocked | 自动切回 base |
| 选择新主图 | 旧候选、旧版本、旧审核和旧输出 | 新版本需审核/授权，镜头可选择升级 | 覆盖旧 MediaReference |
| 镜头换状态 | 旧 ShotSpec/Prompt | 新建 ShotSpecVersion/PromptRevision | 原地修改历史绑定 |
| 授权撤销 | 全部证据 | 新生成/交付 blocked；在途结果仅可审计结算 | 删除证据或伪造 ready |

VibeReels 的改名影响预览、状态选择器、审核失效和视频生成资源门禁值得借鉴；Lanverse 应进一步保证禁用不删引用、AI rematch 不覆盖人工绑定、在途昂贵任务不因显示名变化盲目取消或重发。

### 8.5 迁移路径

1. 创建 `ast_asset_states`，为每个现有 Asset 回填一个 base state。
2. 新增 `AssetStateOccurrence`：固定 state、NarrativeUnitVersion/source span、Episode/Scene、origin/confidence/decision；非连续出现保存多条证据，不存可变 episodes 数组。
3. `AssetVersion.asset_state_id` 先 nullable，回填后改非空。
4. `AssetState` 保存 `current_version_id + revision`；current version 必须同时满足相同 workspace、asset_id 和 state_id。`AssetVersion.version_no` 首期继续按整个 Asset 递增并保持现有 `(asset_id, version_no)` 唯一约束，避免迁移中出现两个 v1。
5. 兼容期内 `Asset.current_version_id` 镜像 base state current，随后逐步弃用；list/readiness/usage summaries 增加 state 维度并做双读一致性测试。
6. 当前 `AssetVersion.source_type='candidate'` 指 scripts `ExtractionCandidate`，不能复用来表示生成输出。将来源类型化为 `manual / script_extraction_candidate / generation_output_candidate`，或新增不可变 AssetVersionProvenance；保留既有 source ID 含义和迁移映射。
7. 增加 `AssetNameRevision(name_revision, name_snapshot)`；PromptDependency 固定 `asset_id + name_revision + name_snapshot`，不用全文扫描 Prompt 判断改名 stale。
8. 现有 AssetReference 增加 binding_source；历史 asset/state 由 AssetVersion 派生。如为查询性能冗余 state_id，必须用复合 FK/服务端校验保证 Version、State、Asset 一致。
9. 保留现有 usage、upgrade-preflight 和 CAS，不重写已通过的 S0–S3 闭环。

## 9. 模块 E：分镜规划、安排与一一对应问题

### 9.1 “一一对应”要拆成三种关系

| 关系 | 正确基数 | 设计 |
| --- | --- | --- |
| 整剧文本 → Episode | 显式标记时 1 个区段对应 1 集；智能规划时仍需人工确认 | EpisodeSegmentOrigin 保存来源范围 |
| NarrativeUnitVersion → ShotSpecVersion | **多对多** | ShotNarrativeReference 保存 role/channel/segment/contribution/origin/confidence |
| Prompt token `@图片N` → 当前有序资产 binding | 显示层严格 1:1 | token 编译与重编号，不作为稳定 ID |

不能承诺“每段剧本严格对应一个镜头”。一句对白可用主镜头、正反打和反应镜头覆盖；一个蒙太奇也可覆盖多个叙事单元。真正要保证的是 required 内容全部有去向、所有镜头都有来源、改动后能局部识别 stale/orphan。

### 9.2 分镜草案工作流

1. 固定输入：published ScriptRevision、NarrativeUnitVersion 集合、资产状态方案、风格、画幅、目标时长、模型和 Prompt 版本。
2. 创建 `StoryboardDraftBatch`，模型只产生 DraftShot，不写 Shot。
3. 系统按叙事节拍拆视觉拍点，提出建立镜头、主体镜头、正反打/反应、特写/插入、转场等角色。
4. 每个 DraftShot 显示来源单元、建议时长、景别/角度/运镜、动作节拍、对白、资产状态、生成意图和风险。
5. 用户可接受、修改、拆分、合并、重排、忽略或补镜；人工编辑过的现有 Shot 默认受保护。
6. Apply Preflight 以稳定来源和人工保护标记计算 diff：保留哪些 shot_id、创建哪些、哪些旧镜头变 stale/orphan；不得整集删除重建。
7. Apply 创建/更新不可变 ShotSpecVersion，随后生成 CoverageReport；覆盖或批准省略未满足时不得 Ready。

### 9.3 如何安排镜头数和时长

镜头数是内容和节奏的结果，不是按字数固定除法。算法顺序：

1. 把 NarrativeUnit 分成不可再分的视觉/声音 beat。
2. 对每个 beat 判断镜头角色：建立、主体、反应、插入、转场、蒙太奇。
3. 对白镜头时长下限由实际 TTS/配音时长、表演停顿和反应时间决定；动作由复杂度与供应商可生成时长决定。
4. 按题材节奏配置分配时长，再检查总和是否落入 Episode target tolerance。
5. 不足时提出扩展反应/建立/转场候选；超时时提出压缩、拆集或删减候选；不静默截断对白。

现有 MVP 约束继续作为护栏：每集建议 12–36 镜、硬上限 120；单镜 500–15,000ms。首期建议偏好 2–8 秒，但具体数值必须服从选定视频供应商能力和黄金样片，不写成普遍规律。

`ceil(target_duration / preferred_average_shot_duration)` 只能给数量基线，不能替代内容规划。对话、动作、蒙太奇应分别使用不同节奏 profile。

### 9.4 目标领域模型

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| StoryboardDraftBatch | episode、input revisions/hash、style、model/prompt、status、cost | 重跑新建；不修改正式 Shot |
| DraftShot | batch、proposal key、order、spec、source unit refs、decision | 每项可独立接受/修改/忽略 |
| ShotNarrativeReference | shot spec version、unit version、role、channel、coverage_mode/segment、contribution、origin、confidence | 多对多；固定版本，不绑易变顺序；required 与 supporting 分开 |
| CoverageReport | episode/current revision、accounted/omitted/uncovered/orphan/stale、hash | 派生快照；输入变化即过期 |
| CoverageDecision | unit/shot spec target、approved_omitted/revoke/approved_invented、reason/evidence、actor、expected coverage hash | 只追加；修订或 mapping 变化后旧决定 stale |
| DirectorMark | formatted revision/base hash、range、unit、labels/notes | 映射到 Shot，可一对多/多对一 |
| ShotTransform | 现有 copy/split/merge 来源与结果 | 增加 narrative coverage conservation 证据 |

`ShotNarrativeReference` 的最小表达必须包含：

- `channel = visual | audio | both`；
- `coverage_mode = full | partial`；partial 时保存 unit 内稳定 `segment_key` 或相对区间；
- `contribution = required | supporting`，只有 required contribution 计入覆盖完成；
- `origin = ai | human | migrated`；
- `role = primary | dialogue | reaction | insert | setup | payoff | transition | supporting`。

覆盖守恒的比较键是 `(narrative_unit_version_id, channel, segment_key/range)`，不是只有 unit ID。这样才能表达同一句对白在一个镜头完成 audio、另一个镜头完成 reaction visual，也能识别 partial coverage 和重复 primary coverage。

### 9.5 拆分与合并的 P0 修复门禁

当前前端拆镜默认把全部 dialogue 放在第一段并清空第二段；后端只检查两边 dialogue 是来源子集且互不重叠，未检查并集等于来源。合镜会用 `.slice(0, 8)` 静默截断第 9 个以后的 action beat；跨场景时又仅保留 base 镜头的 dialogue/场景，后端也未验证全部来源内容有去向。这是已存在的静默遗漏/重复风险。

目标不变量：

~~~text
split:
  coverage_keys(target_1) ∪ coverage_keys(target_2)
  = coverage_keys(source) - explicitly_approved_omissions

  primary_required_keys(target_1) ∩ primary_required_keys(target_2)
  必须为空；supporting/reaction 才允许有证据的重叠

merge:
  coverage_keys(target)
  = union(coverage_keys(all_sources)) - explicitly_approved_omissions
~~~

- 前后端都校验；后端为最终事实源。
- Shot/ShotSpec v1 只能固定一个 Scene，因此首期**无条件拒绝跨 Scene merge**。未来若确有 montage/transition 需求，必须先接受 ShotSpec v2 的 `primary_scene_id + source_scene_ids`，并同步迁移 hash、readiness、Provider snapshot 和 UI；仅增加 NarrativeReference 不足以解除现有限制。
- 合并结果超过 8 个 action beat、8 条 dialogue、15 秒或 Provider profile 限制时直接阻塞并建议保持拆分，不允许截断。
- 所有 omission 需要 actor、reason 和 evidence；不能用空数组表达。
- Transform 后立即重算 CoverageReport；不满足则结果保持 draft/not_ready。

在 NarrativeUnit/Reference 上线前，先做不依赖未来模型的兼容修复：

- split 两个目标的 dialogue 并集必须等于来源，交集必须为空；
- 来源 action beats 必须逐项分配，禁止默认双边完整复制；
- merge 的 dialogue/action beat 并集必须全部进入目标；超过 ShotSpec v1 上限直接拒绝；
- copy 的来源 reference 默认标 supporting/duplicate warning，不能提高 primary coverage；
- 真实 downstream evidence（生成、审核、Issue、Timeline 的 ID/计数）启用后必须进入 preflight snapshot 和 impact hash；当前空 evidence 不能解释为“无影响”。

| `POST /asset-states/{id}/generation-preflight` | C5 | 权利、审核、成本和 Provider 能力门禁 |
| `GET /asset-states/{id}/output-candidates` | C5 | 候选、审核、费用和 lineage |

| `POST /shots/{id}/asset-match-preflight` / `asset-match` | C4 | AI 只给绑定 diff；人工确认后新建 ShotSpec |

### 11.3 分镜

| API | 语义 |
| --- | --- |
| `POST /episodes/{id}/storyboard-draft-runs` | 固定输入并生成草案批次 |
| `GET /storyboard-draft-runs/{id}` | 状态、成本、候选和 next actions |
| `POST /storyboard-drafts/{id}/decisions` | accept/modify/ignore/split/merge 决议 |
| `POST /storyboard-drafts/{id}/apply-preflight` | 与当前 Shot/Spec/Order 比较 diff |
| `POST /storyboard-drafts/{id}/apply` | CAS + 幂等创建正式对象 |
| `GET /episodes/{id}/coverage` | 当前 ScriptRevision 的覆盖、遗漏、orphan、stale |
| `POST /narrative-unit-versions/{id}/coverage-decisions` | 只追加批准省略/撤销；固定 expected coverage hash |
| `POST /shots/{id}/narrative-references:decide` | 人工纠正映射时新建 ShotSpecVersion 并 CAS 切 current，禁止原地改引用 |

所有写命令必须携带 `idempotency_key`、`expected_revision`/expected current ID 和需要时的 `preflight_hash`。不新增“万能 PATCH + 任意 JSON”接口。

## 12. 状态机

- ImportAnalysisRun：`queued → running → succeeded | failed | unknown | cancelled`
- EpisodePlan：`draft → review_ready → confirmed`；未使用的旧计划可 `superseded`，不承载执行状态
- ImportCommit：`pending → materializing → materialized → publishing → published`；异常为 `conflict | failed`
- Asset 生命周期：`active ↔ archived`；生产可用性单独 `enabled ↔ disabled`
- AssetVersion readiness：实时派生 `draft | ready | blocked`
- OutputCandidate ingest：`pending_ingest → available | failed | quarantined`；媒体 probe 状态只从固定 MediaVersion 派生
- ReviewDecision：固定不可变 Candidate/Version，投影 `unreviewed | approved | rejected`
- Selection：通过只追加 Decision 投影 `primary | alternate | rejected`
- StoryboardDraftBatch：`queued → running → needs_review → approved → applied`，异常为 `failed | unknown | cancelled`
- Coverage：派生 `fresh | stale`；结果含 `ready | blocked`
- PromptRevision：不可变；`fresh | stale | superseded` 由依赖比较派生

“unknown”不得自动当 failed 重发；涉及供应商计费时必须先 reconcile provider request。

Coverage 必须进入现有 Shot readiness 和 Project ProductionSnapshot，而不是形成旁路页面。新增稳定 blocker：

- `SCRIPT_REVISION_NOT_CURRENT`；
- `NARRATIVE_REFERENCE_INVALID`；
- `COVERAGE_UNACCOUNTED`；
- `SHOT_SOURCE_ORPHAN`；
- `COVERAGE_DEPENDENCY_UNAVAILABLE`。

readiness `evaluation_hash` 至少固定 Episode current ScriptRevision、NarrativeUnitVersion IDs、current CoverageReport hash 和生效的 CoverageDecision IDs。Coverage 依赖不可用时 fail-closed，不得继续把镜头计为 ready。

## 13. 产品界面

### 13.1 项目级整剧导入向导

- 步骤条：来源 → 格式体检 → 分集策略 → 方案审核 → 影响预检 → 物化/发布；

- 卡片显示预计时长、对白字数、场景数、结尾钩子、置信度和风险；
- 同屏比较三种方案，明确“AI 建议”与“确定性标记结果”。

### 13.2 剧本结构与改写工作台

- original/adapted/formatted 三层切换；
- 单元级 diff、保留/改写/拆合/新增/省略关系；
- 文本与受影响镜头双向高亮；
- 导演标注固定 base hash，显示待迁移状态。

### 13.3 资产圣经

- 角色/场景/道具等身份列表；
- 每个身份下按状态矩阵展示出现集、主选、备选、权利和 readiness；

- 同名资产显示类型、短 ID 和区分说明，避免名称即身份。

### 13.4 分镜台

- 左栏 NarrativeUnit 与 coverage；中栏有序 Shot；右栏 ShotSpec、资产状态、候选与 Prompt；

## 14. 研究计划与仍待验证事项

### 14.1 VibeReels 授权黑盒实验

使用一部自有 2–3 集控制剧，逐项记录对象 ID、费用和可恢复性：

1. 导入带合法、缺号、重复和无标记版本，观察集数与错误；
2. 修改原文一个对白、一个动作、一个角色名和一个场景，观察派生层和镜头的失效粒度；
3. 对同一导演标注测试映射 0/1/N 个镜头，并检查置信度和纠错入口；
4. 拆镜、合镜、插镜、删镜后检查导演标注和资产引用是否保留；
5. 角色改名、禁用、换状态/主图时记录当前镜头、历史版本、任务和 Prompt 影响；
6. 重跑整集分镜，确认是 diff apply 还是删除重建；
7. 测试主选/备选、批量下载和是否存在正式整集合成/时间线导出。

### 14.2 Lanverse 黄金样本

首轮至少准备：

- 10 份格式语料：中文/阿拉伯/全角数字、EP、缺号、重复、前言、超长、Emoji/扩展汉字；
- 20 部授权分集语料：三种题材、3–20 集；
- 30–50 个真实剧本的资产标注集：同名、别名、服装/受伤/场景/道具/声音状态；
- 2–3 集分镜黄金剧：对白正反打、反应镜头、蒙太奇、跨场景、动作、伏笔/回收；
- 一部 60–90 秒真实生成控制剧用于时长、资产一致性和成本校准。

### 14.3 待确认问题

- 首期导入上限是 20 万还是更大，是否需要 Fountain；
- 用户主要输入是已分集剧本、长篇网文还是故事大纲；三者分集策略不同；
- target episode duration 的业务默认值和题材 profile 由谁负责；
- 改写是否允许改变结局、人设和集数，还是只压缩节奏；
- AssetState 与 Costume Asset 的边界：独立可复用服装仍是 Asset，角色“穿着该服装”是状态/绑定；
- 导演标注映射的人工质量 owner 与接受阈值；
- Provider 能否满足角色、状态、镜头时长和参考图输入，仍需真实账号 PoC。

## 15. 验收标准

### 15.1 导入与分集

- 合法显式标记语料的集数与边界准确率 100%；
- 所有非法编号 100% 返回行号、错误码和 next action；
- 排除区外 NarrativeBlock accounted=100%，gap=0、overlap=0；
- 幂等重放只产生一组 Episode/Source/Version；
- 任一 publish CAS 冲突时 0 个 current pointer 部分更新；
- 已有 ScriptVersion、Shot 和任务 0 个被静默覆盖或删除。

### 15.2 资产

- 100% required 资产候选有 `accept_new/accept_with_changes/link_existing/merge_into/ignore` 决议，且黄金样本至少包含一条非零 required 候选及 required_reason，禁止空集假通过；
- 100% 当前 Shot binding 由固定 asset_version_id 唯一解析 asset/state，0 个按名称或 token 浮动引用，任何冗余 ID 复合一致；
- 同名资产可共存，AI 自动 merge 数为 0；
- 改名造成 0 个 FK 变化，所有旧名称 Prompt 被影响预检识别；
- disable apply 后删除引用数为 0；
- 同一 OutputCandidate 幂等 promote 只创建一个 AssetVersion；Selection、promote、set state current 分属明确 CAS，未升级镜头继续固定旧版本；
- C4 可在没有 C5 时以手工/上传 AssetVersion 独立通过；所有 OutputCandidate lineage/review 属 C5，C4 只做联合展示与 promotion adapter；
- C4+C5 联合验收时，所有 OutputCandidate 可追溯 run/provider/model/prompt/input media/rights/media/cost/review。

### 15.3 分镜

- required NarrativeUnit 全部 `covered` 或 `approved_omitted`；
- 当前正式镜头 orphan=0、stale=0 才可 Ready；建立/氛围/创作性转场可由人工 `approved_invented` 并给出 reason，但不计入 required coverage；
- split/merge 后 required references 守恒，未批准遗漏=0；
- AI 草案运行对正式 Shot 写入数为 0；
- apply 幂等且保护人工锁定镜头；
- 所有对白音频时长不超过分配镜头/镜头组时长；
- 总镜头时长在目标容差内，否则有用户批准的例外；
- 文本到镜头、镜头到文本可双向追溯。
- current spec 切换、Script current 切换、split/merge 并发冲突均有 E2E；旧 CoverageDecision 在修订/mapping 改变后 100% stale；
- 延续现有性能门禁：36 镜 P95 ≤800ms、120 镜 P95 ≤2s，coverage/readiness 批量查询不得产生按镜 N+1。

## 17. 难点、卡点与可行性

| 能力 | 可行性 | 真正难点/卡点 | 降级策略 |
| --- | --- | --- | --- |
| UTF-8 txt/md 导入与显式拆集 | 高 | 格式边界和批量事务 | 非法输入阻塞，人工改边界 |

## 19. VibeReels 公开事实与借鉴结论

截至 2026-08-12 可从官网和公开客户端构建物确认：

- UTF-8 md/txt 导入、显式集标记拆分、追加剧本和自动流水线入口；
- original/normalized/annotated 三层内容，原文改变使派生层可能过期；
- Project → Episode → 有序 Shot → ShotVersion；
- 导演标注固定格式化文本字符区间、base hash 和 version，再映射到镜头；
- 角色/场景/道具按名称和剧情状态治理，状态含出现集和候选/主选图片；
- 镜头保存有序 AssetRef，Prompt token 与引用序号同步；
- 改名、禁用、换主选有影响提示或审核失效；
