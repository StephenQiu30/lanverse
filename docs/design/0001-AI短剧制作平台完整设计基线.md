## 1.1 当前视觉生产 MVP 覆盖规则

本次只把已接受的视觉生产主链同步到平台基线，不提前定义 StoryGraph Schema、Agent Stage/Wire、GORM Model、API 或 Workflow 恢复合同。本文后续章节与 `0011/0006` 冲突时，以已接受的后者为准；与尚未重新接受的 `0010/3001/3002/3003/2002/2051/2055/1002` 冲突时，相关旧条款暂停实施，等待 `VP-D04`–`VP-D12` 依次裁决。

当前 MVP 只固定：

- Guided Studio 是主产品，用户只面对 Structure & Identity、Bible & Continuity、Visual Foundation & Scope、Reference Selection 和 Storyboard 五个决策 Gate；
- 剧本事实抽取对 Preset/Style 隔离，先完成 `SceneSpanCandidate → SceneFactCandidate → IdentityResolutionCandidate`，再由 Gate 1 Owner Apply 发布 `StructureIdentitySetVersion`；
- 同一人物的多形象是一个 Character Asset 下的多个完整 AssetState；人物拿取、使用或交接道具使用 Interaction/Continuity 与组合 Binding，不创建组合人物形象；
- `preset` 是 Go Backend 内的正式 Owner，对 PresetVersion、EffectiveStyleSnapshot 和 EffectivePolicySnapshot 负责；预设默认不得改写剧本事实或 WorldRule；
- 人物参考先选择基础身份锚点 AssetVersion，再让每个形象变体绑定该锚点且只改变已声明的形象内容；地点板、道具板和人物变体均人工选择并发布后，才能用精确基础版本生成 Scene/Interaction 组合 Binding，最后编译 SceneProductionPacket 交给 Storyboard；
- Vision Reviewer 只给建议，正式 AssetVersion 或 Reference Binding 必须来自用户唯一候选选择；
- Backend 仍是业务事实唯一 Writer，PostgreSQL/GORM 是唯一 SQL 事实源，Temporal 管理跨步骤恢复，Python Harness 只返回 Candidate；
- Kafka、Elasticsearch、ELK、MinIO、Provider 配置/Secret Store 等已接受或已实现的平台事实继续保留，但不抵扣新产品链的完成门。

当前 MVP 的 P0 是不生成图片的 Text Production Bible 真实剧本闭环；P1–P4 才依次加入视觉身份、组合参考、精确分镜交接和完整剧本加固。完整视频、配音、字幕、剪辑、渲染、发布、支付/计费产品、复杂预算和多 Provider 广度属于 Platform Complete 长期能力，不是当前 MVP 发布门。

# 2. 产品定位

平台定位为：

> **面向 AI 短剧生产的端到端 AI 内容制作平台。**

平台 MVP / Platform Complete 长期愿景继续覆盖：

- AI 真人短剧；
- AI 漫剧；
- 写实、半写实、国漫、日漫等不同视觉风格；
- 静态漫画动态化；
- AI 图生视频；
- AI 配音；
- 自动字幕；
- 自动粗剪；
- 人工审核；
- AI QC 与局部修复。

但真人短剧和 AI 漫剧**不是两套产品、两套 Backend 或两套 Workflow**。当前 Visual Production MVP 只取其共同的剧本事实、生产世界、视觉基底、参考资产与分镜交接闭环；动态视频、声音和成片只作为长期下游保留。

统一抽象为：

```text
AI Short Drama Production Core
            │
            ├── Preset
            ├── Style
            ├── Skill
            ├── Model Policy
            ├── QC Policy
            └── Motion Strategy
```

不同内容形态只是不同能力组合。

# 3. MVP 核心产品目标

当前平台最重要的目标不是拥有最多模型、节点或媒体产物，而是：

> 用户输入一份完整剧本，Lanverse 能经过 AI 候选和少量明确的人工决策，形成来源可追溯、身份不重复、人物多形象与道具交互不混淆、风格统一、可局部修改并可直接进入分镜的视觉生产包。

当前北极星指标是 `Production-ready Scene Coverage`：已通过审核且拥有完整事实、身份/状态、连续性、风格快照与必需已选参考版本的场景数，除以已确认场景总数。

核心闭环：

```text
Project + Preset Selection（只冻结选择）
   ↓
DocumentRevision / SourceSpanIndexVersion
   ↓
SceneSpanCandidate / SceneFactCandidate（style-blind）
   ↓
IdentityResolutionCandidate
   ↓
Gate 1 Owner Apply / StructureIdentitySetVersion
   ↓
Specification + AssetState + Scene / Occurrence
ContinuityClaim（含 InteractionClaim）+ WorldRule
   ↓
Gate 2 / Confirmed Production World
   ↓
PresetVersion + typed override
   ↓
EffectiveStyleSnapshot + ApprovedReferencePlanVersion
   ↓
Character identity anchor 候选与人工选择
   ↓
已选 identity anchor AssetVersion
   ↓
绑定该锚点的 Character appearance variant + Location / Prop 基础参考候选与人工选择
   ↓
Published base AssetVersion
   ↓
Scene / Interaction Composition 候选与人工选择
   ↓
SceneReferenceBindingVersion / InteractionReferenceBindingVersion
   ↓
Production-ready Scene + SceneProductionPacket
   ↓
Storyboard
```

StoryGraph 在这条链中只是 Schema 明确列入的已确认 Owner 事实的只读投影，不是 SceneFactCandidate 或生产世界构建的前置输入。具体 Compiler 时点与投影 Schema 留给 `VP-D04/VP-D05` 独立评审。

# 4. 当前 MVP 非目标

当前 Visual Production MVP 不包含：

- 完整视频、配音、字幕、剪辑、渲染、发布和成片管线；
- 支付/计费产品、复杂预算优化和多 Provider 自动比价/路由；
- 多人实时协作 Canvas 或可自由修改正式事实的通用图编辑器；
- 无人值守自动接受 Identity、AssetState、Preset 冲突或媒体候选；
- 动态 Skill 市场、运行时安装外部 Skill 或通用 Agent 平台；
- 服装×伤势×年龄×形态的组合状态规则引擎；
- 复杂多人战斗站位、高级轴线/视线规则、通用表情/动作库、3D Rig 或骨骼姿态系统；
- 为没有剧本使用、用户请求或连续性风险的全库资产预生成参考图；
- 通用 AI 视频平台；
- 专业 Premiere 级时间线；
- 复杂 3D 编辑；
- MV 制作；
- 广告制作；
- 数字人直播；
- 工作流市场；
- Skill 市场；
- 第三方插件市场；
- 任意代码执行节点；
- 完全自主、无限循环 Agent；
- 多地域多活；
- 超大型企业组织权限系统。

这些能力都应建立在 MVP Production Core 成熟之后。

# 5. 当前主产品与长期交互方向

当前 Visual Production MVP 只以 Guided Studio 交付主闭环。Guided Studio 与 Canvas Studio 作为长期平台方向共享相同 Owner 事实和编译边界，但不要求在当前 MVP 同时交付。

## 5.1 Guided Studio

适合普通创作者。

用户看到的是业务流程：

```text
创建项目并选择世界观/视觉基底预设
 ↓
固定剧本原稿
 ↓
Structure & Identity
 ↓
Bible & Continuity
 ↓
Visual Foundation & Scope
 ↓
Reference Selection（先基础资产，后组合参考）
 ↓
Storyboard
```

用户可以在建项时先选预设，但该选择不得进入 Scene Fact 和 Identity Resolution 的输入。Guided Studio 的五个 Gate 只表达用户决策时刻；内部 Stage、HumanTask Subject、Owner Apply 和恢复状态机分别留给后续 Design/Requirement。

不要求用户理解：

```text
DAG
Node
Port
Temporal
Agent Graph
Tool Calling
```

---

## 5.2 Canvas Studio（长期平台方向）

适合高级创作者。

只读 Story Lens 是已保留的平台能力，可用 DAG 展示 `StoryGraphVersion` 中已确认的剧集、场景、节拍、角色、地点、状态、出场和严格 Claim；它不是当前 Visual Production MVP 的完成门：

```text
Story Lens
├── React Flow 只读节点/边
├── Dagre 自动布局
├── 按集/场/角色/地点过滤
├── 节点详情与 Evidence 追溯
└── StoryGraphVersion 切换
```

Authoring Canvas 是后续独立交付的执行编排视图，不与 Story Lens 共用 Graph Record、ID、Schema 或 Writer。多人协作、Subflow、局部运行和画布 Agent 不属于当前 StoryGraph MVP。

后续 Authoring Canvas/Canvas Agent 通过独立 Design 解锁后，工程上仍不增加根目录第四个项目：

> **Canvas 不是根目录第四个项目。**

它分别存在于：

```text
Frontend
→ Canvas UI

Backend
→ Canvas Authoring Domain

Agent
→ Canvas Builder Agent
```

# 6. 产品 Owner、StoryGraph 与执行系统边界

禁止：

```text
Guided Workflow
+
Canvas Workflow
```

形成两套逻辑。

统一的是 Owner 和编译边界，不是一张通用 Graph。Guided Studio 通过 Backend Owner Command 和人工决议生成正式版本，再消费聚合 View 与 StoryGraph 只读投影：

```text
Guided Studio
      ↓ Owner Commands + Human Decisions
Script / Project / Bible / Planning / Preset
Asset / Reference / Storyboard Owners
      ↓ confirmed immutable versions
      ├──▶ production/storygraph
      │       └── Backend Compiler component
      │           （只读取当前 Schema 明确列入的 Owner 事实）
      │                    ↓
      │       StoryGraphVersion + StoryGraphHead ──▶ Story Lens（只读）
      └──▶ Backend typed Query ──▶ Guided Studio

Guided / Authoring Canvas
           ↓
   AuthoringDraft
           ↓
   AuthoringRevision.Graph
           ↓
   Workflow Compiler
           ↓
WorkflowDefinitionVersion
           ↓
        Temporal History
```

StoryGraph Compiler 的触发时点、Node/Edge 与 Schema Version 不在本步定义；`production/reference` 等新 Owner 事实也不因本文命名而自动进入当前 `storygraph-narrative`。这些边界等待 `VP-D04/VP-D05` 独立接受。

四种图事实必须分开：

| 事实 | 回答的问题 | 唯一 Owner / Writer |
|---|---|---|
| `StoryGraphVersion` + `StoryGraphHead` | 故事、角色/地点状态、Scene、Beat、Shot 和资产如何关联，以及 Project 当前发布版本指向 | `production/storygraph`；Backend Compiler 只是该 Owner 的写入组件 |
| `AuthoringRevision.Graph` | 用户准备怎样编排生产节点和端口 | Backend Authoring |
| `WorkflowDefinitionVersion` | 本次运行按什么依赖执行 | Backend Workflow Compiler |
| Temporal History | Activity、Timer、Retry、Signal 实际发生了什么 | Temporal |

Agent 只返回带 Evidence 的 Candidate Revision；Backend 验证、人工门禁和 Owner Apply 后才能生成新的业务版本。

# 7. 核心架构原则

平台固定以下架构原则。

## 7.1 一个 Backend Go Project

Backend 是：

```text
一个 Go Module
+
多个领域模块
+
多个运行程序
```

统一：

```text
backend/go.mod
backend/go.sum
```

不使用多个 Go Module。

不使用：

```text
go.work
```

---

## 7.2 Agent 是独立 Python Project

统一：

```text
agent/pyproject.toml
agent/uv.lock
```

当前正式结构：

```text
agent/app/                 # 受限候选生成运行时
agent/skills/              # 可调用 Skill Bundle
agent/tests/               # 与业务代码分离的测试
```

StoryGraph Bundle 的唯一目标路径是 `agent/skills/build-storygraph/`；不写入 `.agent/skills`，不把 Skill 伪装成 Backend 业务模块。

---

## 7.3 Frontend 是独立 TypeScript Project

当前 MVP 的 Frontend 只包含 Guided Studio 主链所需的：

```text
Web
UI
AI UI
SDK
```

只读 Story Lens 作为既有平台能力继续保留，但不属于本轮 Visual Production MVP 的新增范围或完成门；Authoring Canvas 与 Collaboration 仍需后续独立 Design 接受。

---

## 7.4 Temporal 是唯一全局工作流引擎

Temporal 负责：

```text
可靠执行
暂停
恢复
重试
超时
人工等待
子工作流
长任务状态
```

---

## 7.5 MVP Agent 不引入 LangGraph

当前 StoryGraph Harness 使用确定 Stage/Shard、结构化输出、有界重试和 Checkpoint，不使用 LangGraph。若后续真实复杂 Agent 需要状态图，必须有独立 Design 和可测试的有界执行契约，且只能存在于 Temporal Activity 内部：

```text
Temporal
   ↓
Agent Node
   ↓
Bounded Agent State Graph（延后）
```

---

## 7.6 PostgreSQL/GORM 是唯一 SQL 事实源

```text
PostgreSQL
= Source of Truth
```

Backend 使用一套 GORM Model Catalog 建立和校验 Schema。不创建 Migration 目录/文件，不混用 `sqlc` 或第二 ORM，不用手写 SQL 复制 ORM 已提供的业务读写。Kafka 只运输已提交事实，Elasticsearch 只保存可从 PostgreSQL/Kafka 重建的剧本和 StoryGraph 检索投影，ELK 日志索引不保存业务状态。Redis 只能作为可删除的临时加速。

---

## 7.7 MinIO 是 MVP 默认对象存储

业务不能直接依赖 MinIO。

必须：

```text
ObjectStore Interface
       ↓
Storage Adapter
       ↓
MinIO
```

后续支持：

```text
TOS
S3
OSS
COS
```

# 38. Style 层级覆盖与事实优先级


```text

+

Model Policy
+

+
Motion Strategy
+
Render Policy
```

首批只策展 4–6 个通过 Character/Location/Prop/Scene/Interaction 全用途矩阵验证的预设，产品类别可例如：

```text

都市真人短剧
古装真人短剧
```

# 40. Preset 产品模型与 Owner

| 正式对象 | 产品含义 | 唯一 Owner |

# 48. Agent 模型与媒体 Provider 边界

文本/结构化 Agent 调用继续由 Backend 冻结 Policy 后交给私有 Agent Runtime，本地开发可使用受控 Codex CLI；图片/视频生成则统一由 Backend `generation` 模块拥有的媒体 Provider Registry 执行。二者不共用凭据、配置表、远端幂等语义或结果协议，也不预建独立 `model-gateway` 进程。

浏览器、Agent、Workflow Definition 和 StoryGraph 都不直接连接媒体 Provider。Workflow 只传递精确 GenerationTarget 与冻结 Project Binding；Backend 在远程调用前完成权限、Capability、Cost/Quota 和 ExecutionAuthorization。

上述 Provider 配置、Secret Store、幂等执行与费用事实作为已接受/已实现平台能力保留；当前 Visual Production MVP 只要求一条能够真实验证参考资产闭环的图片执行路径。支付/计费产品、复杂预算和多 Provider 广度不是新 MVP 的完成门。

# 49. 通用媒体 Provider 配置与 Adapter

Backend 提供无 Secret 的内置 `MediaProviderPresetDescriptor Catalog`，Owner 通过 Web 创建跨重启持久的不可变 `ProviderConnectionVersion`、`ProviderCredentialVersion`、`ModelProfileVersion` 和 `ProjectProviderBindingVersion`。该 Catalog 只是媒体连接工厂描述，不是创作 `PresetVersion` Owner。API Key 只写不读，使用 Docker Secret 文件提供的 root key 加密；缺少 root key 时只阻塞凭据创建、轮换和执行，不阻塞零配置启动与非视觉业务。

以下 Adapter/模型属于旧 `SG-D13`–`SG-D21` 已接受、由 `SG-I21` 延续但尚未完成的 Platform Complete 目标，不因 MVP 重排被回滚，但也不抵扣新视觉生产闭环：

```text

google_gemini  → Nano Banana 2 Lite / 2 / Pro / Legacy
```

Media Provider Descriptor 只暴露已注册 Factory 的受控字段、模型和 Host/Region allowlist；不允许浏览器配置任意 URL，不建立动态插件市场，不保留 Runware 兼容入口。`SG-I21` 工作区增量继续暂停，ProviderCall/Receipt 与精确 Adapter 完成门在 `VP-D10` 重新同步前不扩展。

# 50. ModelProfile 与 Capability

每个不可变 ModelProfile 精确冻结外部 Model/Endpoint ID、调用协议、图片/视频能力、尺寸/比例/时长、输入 Artifact 类型、音频/水印参数、PriceQuote 合同和 Provider 限流。Workflow 不根据展示名、`>=` 字符串或通用 `image.fast` 猜测模型；Target Builder 必须解析 Project Purpose 的精确 Binding Version，再按该 Profile 校验完整输入组合。

---

# 51. ProviderCall、费用与恢复

一次 GenerationTarget 先建立稳定 Intent、Cost/Quota Reservation、ProviderJob，再为每个候选建立一个独立 ProviderCall。四候选就是四个 Call，每个 Call 只允许首次 `PENDING → DISPATCHING` 的执行路径发送一次真实远端请求，并最多收敛一个输出。同步 Provider 在发送边界后丢失结果时进入 `outcome_unknown`，不得自动重提；异步 Provider 持久化 remote task id，并由 Temporal 查询同一身份直到终态或明确失败。

所有远程调用和 Staging 下载都在 PostgreSQL 事务外；明确终态按 Call 聚合 Cost，未知结果继续占用预留。Kafka 不调度 Provider Job，日志不保存 Prompt、Secret 或私有 URL。

# 53. Asset 系统

Asset 系统严格区分身份、剧情状态、已发布版本和一次执行产物：

Design 回答：

> 系统和具体模块如何设计。

必须包含问题、范围、非目标、架构或模块边界、决策与取舍、数据与接口、状态和失败路径。架构决策直接作为 Design 保存，并在被取代时记录替代关系。

# 87. Requirement

# 88. Plan

必须记录实施阶段、迁移门禁、资源所有权和回滚点；计划状态不能作为功能已经实现的证据。

# 89. Acceptance

Acceptance 回答：

> 如何判定完成，以及实际验证了什么。

必须区分验收标准与已执行证据，记录真实命令、输入、结果、缺失条件和残余风险。未运行或缺少外部条件的验证不得报告为通过。

# 93. 当前 MVP 的 Design 级成功边界

本节只给 `VP-D13`–`VP-D15` 派生 PRD、Requirement、Plan 和初始全未通过 Acceptance 提供产品锚点；它不是 Acceptance Checklist，也不会因旧测试存在而自动通过。

## Product

用户能够：

```text
创建项目
选择策展 Preset 和 faithful / world adaptation 模式
导入并固定完整剧本 Revision
通过五个稳定决策 Gate
修正场界、别名/同名、多形象、道具状态与交互
选择人物/地点/道具基础参考与必需组合参考
看到 Production-ready Scene Coverage、阻断和影响闭包
将完整、精确版本绑定的 SceneProductionPacket 交给 Storyboard
```

---

## Text Production World

必须保证：

```text
原文/SceneSpan 完整覆盖且可追溯
事实抽取不消费 Preset/Style
同一 Mention 不重复归类，同名不自动合并
同一人物的多形象不创建第二 Identity
人物—道具持有/使用/交接不写入 Character AssetState
无 Evidence 且无用户决定的内容不冒充剧本事实
```

---

## Visual Foundation 与 Reference

必须保证：

```text
Preset 不改写 Script、Identity、Specification、AssetState 或 WorldRule
人物基础三视图保持同一身份与完整 front/profile/back 覆盖
先由人工选择人物基础身份锚点 AssetVersion；每个形象变体必须绑定该精确锚点，只改变已声明的形象内容
地点板与道具板保持拓扑/结构/尺度/状态一致
Scene/Interaction Composition 只消费精确已选基础 AssetVersion
Vision Reviewer 不自动发布，正式版本/绑定来自人工唯一选择
切换 Preset 不覆盖旧版本，只标记精确视觉下游 stale
```

---

## Storyboard 交接与可恢复性

必须保证：

```text
必需 unresolved、stale 或未选参考不得标记 Scene ready
Storyboard 只消费冻结 SceneProductionPacket，不搜索“最新资产”
单 Scene/Identity/State/Interaction/参考失败只阻塞相关下游
人工等待、Worker 重启或 Provider 暂时不可用后可恢复同一执行身份
重放/恢复不创建重复 Owner 事实，不覆盖已发布 Artifact
```

---

## 平台不变量

必须：

```text
四种 Graph 的 Record / ID / Schema / Writer 互不混用
Backend 是业务唯一 Writer
PostgreSQL/GORM 是唯一 SQL 事实源
Python Harness 只返回 Candidate，不写业务事实
Bundle/Invocation/输入身份可追踪且可重放
Kafka Outbox/Inbox 可在重复投递下收敛
剧本/StoryGraph Elasticsearch 索引可从 PostgreSQL 重建
Backend → Logstash → Elasticsearch → Kibana 日志链路可查询
```

# 95. 最终架构定义

平台最终应被定义为：

> **一套以可追溯剧本事实和已确认 Owner 版本构建视觉生产世界的 AI 短剧制作平台。Guided Studio 先将完整剧本收敛为身份不重复、人物多形象与道具交互不混淆、风格与参考版本精确的生产就绪场景，再交给分镜。StoryGraph 只投影 Schema 明确列入的已确认 Owner 事实；Authoring Graph、Workflow Definition 与 Temporal History 保持独立。Go Backend 是业务唯一 Writer，Temporal 负责可恢复的跨步骤执行，Python Agent Runtime/本地 Codex CLI 只生成受限候选，MinIO 管理对象，PostgreSQL/GORM 保存唯一 SQL 事实，Kafka 解耦业务异步消息，Elasticsearch 提供可重建的剧本/StoryGraph 检索，Logstash/Elasticsearch/Kibana 提供集中日志管理。**
