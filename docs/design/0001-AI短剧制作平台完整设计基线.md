## 1.1 StoryGraph MVP 覆盖规则

本次只把已接受的 StoryGraph 设计同步到平台主干，不把“最终平台能力”提前当作 MVP 实施清单。本文后续章节与 `0006/0010/3003` 冲突时，以后者的更精确设计为准。

当前 MVP 只固定：

- 一个 Frontend 应用、一个 Backend Go Module 和一个 Backend 私有 Agent 运行时；
- Backend 是业务事实唯一 Writer，PostgreSQL 是唯一 SQL 事实源，并通过 GORM 的唯一模型目录管理 Schema；
- 不创建 Migration 文件、不引入 `sqlc`/第二 ORM、不手写业务 SQL、不设置第二个业务 Writer；
- Temporal 只管理跨步骤可恢复执行，MinIO 管理对象，Agent 只产生候选；
- Backend 内置可版本化媒体 Provider 预设并拥有 Connection/Credential/ModelProfile/Project Binding；零 Provider 配置不影响非视觉服务，Provider API Key 由 Web 一次写入并以独立密文版本持久化，不使用 `.env` 保存；
- Kafka 承担真实跨模块/跨进程的异步解耦，Elasticsearch 承担可重建的剧本/StoryGraph 检索投影，ELK 承担集中日志检索；
- 本地开发可以通过 Codex CLI 完成 AI 调用，但 Owner Apply 仍由 Backend 执行；
- 测试只放在各项目的独立 `tests/` 目录中，不与业务代码混放。

Kafka 与 ELK/Elasticsearch 是平台必需能力，但 MVP 只实现已定义生产者和消费者的 Topic、Outbox/Inbox、剧本/StoryGraph 索引和日志管道，不建设通用事件平台。Redis 正确性依赖、Yjs/Hocuspocus、Konva 或 Eclipse Layout Kernel（ELK Layout）等额外 Canvas 引擎、多人协作服务、通用 LangGraph Executor、无真实消费者的新运行程序及市场/插件能力仍是延后项。

# 2. 产品定位

平台定位为：

> **面向 AI 短剧生产的端到端 AI 内容制作平台。**

V1 同时需要覆盖：

- AI 真人短剧；
- AI 漫剧；
- 写实、半写实、国漫、日漫等不同视觉风格；
- 静态漫画动态化；
- AI 图生视频；
- AI 配音；
- 自动字幕；
- 自动粗剪；
- 人工审核；
- AI QC 与局部修复。

但真人短剧和 AI 漫剧**不是两套产品、两套 Backend 或两套 Workflow**。

统一抽象为：

```text
AI Short Drama Production Core
            │
            ├── Preset
            ├── Style
            ├── Skill
            ├── Model Policy
            ├── QC Policy
            └── Motion Strategy
```

不同内容形态只是不同能力组合。

## 5.2 Canvas Studio

适合高级创作者。

当前 MVP 首先交付只读 Story Lens，用 DAG 展示 `StoryGraphVersion` 中已确认的剧集、场景、节拍、角色、地点、状态、出场和严格 Claim：

```text

├── React Flow 只读节点/边
├── Dagre 自动布局
├── 按集/场/角色/地点过滤
```

> **Canvas 不是根目录第四个项目。**

它分别存在于：

```text

→ Canvas UI

Backend
→ Canvas Authoring Domain

Agent
→ Canvas Builder Agent
```

# 6. StoryGraph 与执行系统边界

禁止：

```text
Guided Workflow
+
Canvas Workflow
```

形成两套逻辑。

统一的是 Owner 和编译边界，不是一张通用 Graph：

```text
ScriptVersion + ProductionBibleVersion
                  ↓
        Backend StoryGraph Compiler
                  ↓
          StoryGraphVersion
            │           │
            │           └────────▶ Canvas Story Lens（只读）
            └──────────────▶ Guided Studio

Guided / Authoring Canvas
           ↓
   AuthoringDraft
           ↓
   AuthoringRevision.Graph
           ↓
   Workflow Compiler
           ↓
WorkflowDefinitionVersion
           ↓
        Temporal History
```

四种图事实必须分开：

| 事实 | 回答的问题 | 唯一 Owner / Writer |
|---|---|---|
| `StoryGraphVersion` | 故事、角色/地点状态、Scene、Beat、Shot 和资产如何关联 | Backend Production / StoryGraph Compiler |
| `AuthoringRevision.Graph` | 用户准备怎样编排生产节点和端口 | Backend Authoring |
| `WorkflowDefinitionVersion` | 本次运行按什么依赖执行 | Backend Workflow Compiler |
| Temporal History | Activity、Timer、Retry、Signal 实际发生了什么 | Temporal |

Agent 只返回带 Evidence 的 Candidate Revision；Backend 验证、人工门禁和 Owner Apply 后才能生成新的业务版本。

# 7. 核心架构原则

平台固定以下架构原则。

## 7.1 一个 Backend Go Project

Backend 是：

```text
一个 Go Module
+
多个领域模块
+
多个运行程序
```

统一：

```text
backend/go.mod
backend/go.sum
```

不使用多个 Go Module。

不使用：

```text
go.work
```

---

## 7.2 Agent 是独立 Python Project

统一：

```text
agent/pyproject.toml
agent/uv.lock
```

当前正式结构：

```text
agent/app/                 # 受限候选生成运行时
agent/skills/              # 可调用 Skill Bundle
agent/tests/               # 与业务代码分离的测试
```

StoryGraph Bundle 的唯一目标路径是 `agent/skills/build-storygraph/`；不写入 `.agent/skills`，不把 Skill 伪装成 Backend 业务模块。

---

## 7.3 Frontend 是独立 TypeScript Project

当前 MVP 包含：

```text
Web
UI
AI UI
Story Lens
SDK
```

Authoring Canvas 与 Collaboration 只在后续独立 Design 接受后增加。

---

## 7.4 Temporal 是唯一全局工作流引擎

Temporal 负责：

```text
可靠执行
暂停
恢复
重试
超时
人工等待
子工作流
长任务状态
```

---

## 7.5 MVP Agent 不引入 LangGraph

当前 StoryGraph Harness 使用确定 Stage/Shard、结构化输出、有界重试和 Checkpoint，不使用 LangGraph。若后续真实复杂 Agent 需要状态图，必须有独立 Design 和可测试的有界执行契约，且只能存在于 Temporal Activity 内部：

```text
Temporal
   ↓
Agent Node
   ↓
Bounded Agent State Graph（延后）
```

---

## 7.6 PostgreSQL/GORM 是唯一 SQL 事实源

```text
PostgreSQL
= Source of Truth
```

Backend 使用一套 GORM Model Catalog 建立和校验 Schema。不创建 Migration 目录/文件，不混用 `sqlc` 或第二 ORM，不用手写 SQL 复制 ORM 已提供的业务读写。Kafka 只运输已提交事实，Elasticsearch 只保存可从 PostgreSQL/Kafka 重建的剧本和 StoryGraph 检索投影，ELK 日志索引不保存业务状态。Redis 只能作为可删除的临时加速。

---

## 7.7 MinIO 是 V1 默认对象存储

业务不能直接依赖 MinIO。

必须：

```text
ObjectStore Interface
       ↓
Storage Adapter
       ↓
MinIO
```

后续支持：

```text
TOS
S3
OSS
COS
```

# 8. 顶层系统架构

```text
                         Lanverse

┌─────────────────────────────────────────────────────────┐
│                     Frontend                            │
│                                                         │
│ Guided Studio    Story Lens       Review    AI Copilot  │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP / SSE / WS
                         ▼
┌─────────────────────────────────────────────────────────┐
│              Backend Go（唯一业务 Writer）            │
│                                                         │
│ Production   StoryGraph   Authoring      Workflow       │
│ Review       Generation   Agent          Asset          │
│ Preset       Media        Cost           Quota          │
└──────────────┬─────────────┬───────────────┬────────────┘
               │             │               │
               │             ▼               ▼
               │          Temporal       Model Gateway
               │             │               │
               │             │               ├─ LLM
               │             │               ├─ Image
               │             │               ├─ Video
               │             │               └─ Audio
               │             │
               │             ▼
               │        Agent Runtime
               │           Python
               │             │
               │       Candidate Harness
               │
               ▼
          PostgreSQL
               │
               ├── Redis
               ├── MinIO
               ├── Kafka
               └── Elasticsearch
```

`PostgreSQL + GORM` 保存唯一业务事实；Kafka 从交易内 Outbox 可重试地发布已提交事实，用于异步解耦检索索引等真实业务消费者，不承载日志。Elasticsearch 的剧本/StoryGraph 索引是可重建业务 Projection；Logstash 写入的日志索引与业务索引逻辑隔离。Agent 和 Provider 只返回 Candidate/Artifact，不直连 PostgreSQL。

# 48. Agent 模型与媒体 Provider 边界

文本/结构化 Agent 调用继续由 Backend 冻结 Policy 后交给私有 Agent Runtime，本地开发可使用受控 Codex CLI；图片/视频生成则统一由 Backend `generation` 模块拥有的媒体 Provider Registry 执行。二者不共用凭据、配置表、远端幂等语义或结果协议，也不预建独立 `model-gateway` 进程。

浏览器、Agent、Workflow Definition 和 StoryGraph 都不直接连接媒体 Provider。Workflow 只传递精确 GenerationTarget 与冻结 Project Binding；Backend 在远程调用前完成权限、Capability、Cost/Quota 和 ExecutionAuthorization。

---

# 49. 通用媒体 Provider 配置与 Adapter

Backend 提供无 Secret 的内置 Preset Catalog，Owner 通过 Web 创建跨重启持久的不可变 `ProviderConnectionVersion`、`ProviderCredentialVersion`、`ModelProfileVersion` 和 `ProjectProviderBindingVersion`。API Key 只写不读，使用 Docker Secret 文件提供的 root key 加密；缺少 root key 时只阻塞凭据创建、轮换和执行，不阻塞零配置启动与非视觉业务。

当前必须真实接入且不能降级为预留的 Adapter 是：

```text
volcengine_ark → Seedream 5.0 Pro+ / Seedance 2.0+
openai         → GPT Image 2
google_gemini  → Nano Banana 2 Lite / 2 / Pro / Legacy
```

Preset 只暴露已注册 Factory 的受控字段、模型和 Host/Region allowlist；不允许浏览器配置任意 URL，不建立动态插件市场，不保留 Runware 兼容入口。

---

# 50. ModelProfile 与 Capability

每个不可变 ModelProfile 精确冻结外部 Model/Endpoint ID、调用协议、图片/视频能力、尺寸/比例/时长、输入 Artifact 类型、音频/水印参数、PriceQuote 合同和 Provider 限流。Workflow 不根据展示名、`>=` 字符串或通用 `image.fast` 猜测模型；Target Builder 必须解析 Project Purpose 的精确 Binding Version，再按该 Profile 校验完整输入组合。

---

# 51. ProviderCall、费用与恢复

一次 GenerationTarget 先建立稳定 Intent、Cost/Quota Reservation、ProviderJob，再为每个候选建立一个独立 ProviderCall。四候选就是四个 Call，每个 Call 只允许首次 `PENDING → DISPATCHING` 的执行路径发送一次真实远端请求，并最多收敛一个输出。同步 Provider 在发送边界后丢失结果时进入 `outcome_unknown`，不得自动重提；异步 Provider 持久化 remote task id，并由 Temporal 查询同一身份直到终态或明确失败。

所有远程调用和 Staging 下载都在 PostgreSQL 事务外；明确终态按 Call 聚合 Cost，未知结果继续占用预留。Kafka 不调度 Provider Job，日志不保存 Prompt、Secret 或私有 URL。

---

# 52. 生成任务与严格 Target

生成链统一为：

```text
GenerationTarget(reference_asset | shot_frame | shot_video)
  → GenerationSubmissionIntent / ExecutionAuthorization
  → ProviderJob → ProviderCall[] → CallReceipt[]
  → private Staging validate → Artifact + GenerationCandidate[]
  → QC / HumanTask / CandidateSelection
  → AssetVersion | ShotImageBindingVersion | ShotVideoBindingVersion
```

`reference_asset` 只能发布 AssetVersion；`shot_frame` 只能选择图片 Artifact 并发布 ShotImageBindingVersion；`shot_video` 必须消费正式 Shot、精确 ShotImageBindingVersion、ShotProductionBindingVersion 与目标时长，选择通过 Video QC 的视频 Artifact 后发布不可变 ShotVideoBindingVersion。Shot 不保存 `image_url`/`video_url`，Provider URL 不进入正式 Binding。

应用输出统一脱敏结构化日志并保留 stdout，通过失败开放 TCP Writer 直送 Logstash，不直接写 Elasticsearch，也不创建 Kafka 日志 Topic。Logstash 只处理日志解析、二次脱敏、非法记录 Hash-only 路由与日志索引，不消费业务事件。Trace 与 Metrics 继续使用 OpenTelemetry/Prometheus，不经由业务 Topic。

# 85. PRD

---

# 86. Design

Design 回答：

> 系统和具体模块如何设计。

必须包含问题、范围、非目标、架构或模块边界、决策与取舍、数据与接口、状态和失败路径。架构决策直接作为 Design 保存，并在被取代时记录替代关系。

---

# 87. Requirement

Requirement 回答：

> 哪些可测试契约必须成立。

必须把已接受的产品与设计边界细化为明确的功能/非功能需求、输入输出、约束和验收条件。

---

# 88. Plan

Plan 回答：

> 按什么依赖和顺序安全落地。

必须记录实施阶段、迁移门禁、资源所有权和回滚点；计划状态不能作为功能已经实现的证据。

---

# 89. Acceptance

Acceptance 回答：

> 如何判定完成，以及实际验证了什么。

必须区分验收标准与已执行证据，记录真实命令、输入、结果、缺失条件和残余风险。未运行或缺少外部条件的验证不得报告为通过。

# 95. 最终架构定义

平台最终应被定义为：

> **一套以 StoryGraph 组织剧本、生产对象与视觉资产关系的 AI 短剧生产平台。Guided Studio 和只读 Story Lens 消费同一个 StoryGraphVersion，Authoring Graph、Workflow Definition 与 Temporal History 保持独立。Go Backend 是业务唯一 Writer，Temporal 负责可恢复的跨步骤执行，Python Agent Runtime/本地 Codex CLI 只生成受限候选，MinIO 管理对象，PostgreSQL/GORM 保存唯一 SQL 事实，Kafka 解耦业务异步消息，Elasticsearch 提供可重建的剧本/StoryGraph 检索，Logstash/Elasticsearch/Kibana 提供集中日志管理。**

核心关系最终固定为：

```text
                    Lanverse

 ScriptVersion + ProductionBibleVersion
                    ↓
         Backend StoryGraph Compiler
                    ↓
            StoryGraphVersion
              ┌──────┴──────┐
              ▼             ▼
       Guided Studio   Story Lens（只读）

 Guided / Authoring Canvas
              ↓
 AuthoringRevision.Graph
              ↓
 WorkflowDefinitionVersion
              ↓
           Temporal
      ┌──────┼──────┐
      ▼      ▼       ▼
 Candidate  Provider  Media
      └──────┼──────┘
             ▼
       Backend Owner Apply
          ┌──┴──┐
          ▼     ▼
 PostgreSQL/GORM  MinIO
          │
        Outbox
          ↓
 Kafka Business Topics ──▶ Search Indexer ──▶ Elasticsearch Business Indices

 JSON Logs ──▶ fail-open TCP ──▶ Logstash
                                      ↓
                     Elasticsearch Log Indices ──▶ Kibana
```

本文档可以作为当前平台主干基线；专项语义以已接受的编号 Design 为准，实施只从 `docs/README.md` 当前唯一激活步骤领取。
