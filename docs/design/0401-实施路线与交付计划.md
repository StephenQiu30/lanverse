# 0401 实施路线与交付计划

- 状态：草案，待评审
- 日期：2026-09-25
- 依赖：[0101](0101-产品定义与需求分析.md)、[0201](0201-系统架构设计.md)、[0301](0301-技术选型决策.md)
- 范围：阶段划分、每阶段交付与验收、团队、现有代码处置、风险
- 约定：周期按 5–8 人团队估算，是规划参考，不是承诺。每个阶段结束时按实际情况修订本文。

## 1. 结论

1. 按 **“先验证、再打底、后纵向切片”** 推进：P0 用脚本验证一致性与成本 → M1 搭好工程底座 → M2–M4 按工作流顺序纵向打通，M4 结束即 MVP。
2. **每个里程碑都以“用户能在浏览器里完成什么”为验收**，而不是“某个模块写完了”。
3. 画布放在 MVP 之后，但**画布 PoC 与 M3 并行**，提前暴露性能风险。
4. 现有代码不作为新设计的基础。默认**在同一仓库内重建**，旧代码打标签保存，逐模块审计后按需复用（见第 5 节，待确认）。

## 2. 阶段总览

```text
P0 验证 ─→ M1 底座 ─→ M2 剧本到设定集 ─→ M3 视觉与分镜 ─→ M4 成片（= MVP）─→ 内测 ─→ V1 画布与协作 ─→ V2 商业化
 3–4 周      3–4 周        3–4 周              4–5 周            4–5 周          4–6 周      8–10 周
                                          └─ 画布 PoC（并行 2 周）
```

## 3. 各阶段交付与验收

### P0 技术验证（3–4 周）

**目标：** 在写平台代码之前，用脚本 + 人工方式回答“能不能做、要花多少钱”。

| 交付 | 内容 |
| --- | --- |
| 样片 | 3 条 30–60 秒样片（2 个角色、5–10 个镜头），覆盖 0101 Q3 选定的品类 |
| 模型评测报告 | 每种能力 2–4 个候选供应商的质量、一致性、价格、延迟、API 能力（0301 §7 核实清单） |
| 成本模型 | 单分钟成片成本、平均重拍次数、关键帧先行对重拍率的影响 |
| 一致性评估方法 | 自动指标（如人脸相似度）+ 人工抽检标准与阈值 |
| 用户验证 | ≥ 10 家工作室访谈；≥ 3 家看过样片并表达试用意愿 |

**退出标准：** 主 / 备供应商确定；单分钟成本在可接受范围【待确认：目标值由产品负责人定】；至少 3 家种子客户同意内测。未达标则调整品类或产品方向，不进入 M1。

### M1 工程底座（3–4 周）

**目标：** 能登录、建项目、上传文件，一条空的 Temporal 工作流端到端跑通；三端质量门禁上线。

| 交付 | 内容 |
| --- | --- |
| 仓库与工具链 | 三端目录、锁文件、Makefile / 脚本、CI（lint、format、typecheck、test、race、vuln、镜像构建） |
| 契约链 | `openapi.yaml` → Go 服务端代码 + TS 客户端生成；CI 校验生成物与契约一致 |
| identity / workspace | 注册登录、组织、项目、成员；项目设置（画幅、风格预设） |
| media | 预签名直传、探测、缩略图、签名访问 |
| 编排骨架 | Temporal 接入；Go flow-worker、Python ai-worker、Go media-worker 各跑通一个示例 Activity |
| 实时推送 | Outbox → Redis → SSE，前端收到事件后刷新查询 |
| 可观测 | 结构化日志、trace 贯穿 api → 工作流 → Worker |

**验收：** 浏览器中注册 → 建项目 → 上传一张图 → 看到缩略图；触发示例工作流，重启 Worker 后工作流继续完成；CI 全绿。

### M2 剧本到设定集（3–4 周）

**目标：** 0101 工作流阶段 1–3。

| 交付 | 内容 |
| --- | --- |
| script | 导入 txt / docx；ParseScript 工作流；分集分场结果带原文位置；审阅与手工修改；确认门 |
| bible | 资产抽取与别名合并；角色 / 造型 / 场景 / 道具卡片编辑；确认门 |
| lineage | 依赖登记表与过期标记（先覆盖剧本 → 场 → 资产） |
| 评测 | 解析与抽取评测集，纳入 CI 的离线回归（使用录制的模型响应） |

**验收：** 上传 3 份不同格式的真实剧本，解析结果可逐条追溯原文；人工修改后确认；刷新和服务重启后状态不丢失；修改剧本产生新版本，下游被标记过期。

### M3 视觉定稿与分镜（4–5 周）

**目标：** 0101 工作流阶段 4–6，以及通用生成任务能力。

| 交付 | 内容 |
| --- | --- |
| generation | 0201 §5.2 状态机全量：报价、预留、提交、`unknown` 对账、接管、候选、结算、取消；主 / 备供应商各接一家（生图） |
| billing | 价格表、项目预算、预留、账本、按镜头归集 |
| bible | 参考图生成、多候选选定、版本锁定 |
| storyboard | AI 分镜生成、镜头表编辑、镜头引用锁定参考 |
| 关键帧 | 批量生成关键帧（整场），单镜重做 |
| review | 候选对比、选定、打回 |
| 画布 PoC（并行） | 按 0301 §6.3 的压测标准完成性能验证 |

**验收：** 一集完整完成到“每镜都有选定关键帧”；故意制造一次供应商超时，任务进入 `unknown` 并正确对账，无重复扣费；改一个造型后只重做选中的镜头；账本金额与供应商账单核对一致；画布 PoC 给出通过 / 不通过结论。

### M4 视频、声音、剪辑与交付（4–5 周）= MVP

**目标：** 0101 工作流阶段 7–10，完成 0101 §9 的 MVP 完成定义。

| 交付 | 内容 |
| --- | --- |
| 视频 | 图生视频（主 / 备各一家）、批量、选片、实测时长 |
| 声音 | 角色音色、对白 TTS、字幕时码 |
| edit | 自动粗剪、时间线（顺序、入出点、对白轨、字幕） |
| delivery | 渲染前校验、统一转码合成、AIGC 显式与隐式标识、成片质检、版本化交付 |
| 合规 | 输入输出内容审核接入 |

**验收：** 种子用户独立完成一集 1–2 分钟成片并导出；成片在主流播放器从头到尾正常播放，对白完整、字幕正确、带标识；替换一个镜头后重新导出，旧成片保留。

### 内测（4–6 周）

- 3–5 家种子工作室真实生产；每周复盘 0101 §10 指标。
- 只修问题和补体验短板，不加新模块。
- **退出标准：** 周交付成片分钟数持续增长；第 2 集续做率达标【待确认目标值】；无数据丢失与重复扣费事故。

### V1 画布与协作（8–10 周）

| 交付 | 内容 |
| --- | --- |
| 画布 | React Flow 引擎 + 移植界面；CanvasDocument、命令、撤销重做、409 冲突处理；类型化端口；生成节点接入报价执行流程；与流水线视图共享数据 |
| 协作 | 项目角色权限、帧上批注、审阅指派 |
| 生产效率 | 故事板视图、跨集资产复用、BGM / 音效轨、成本报表与预算告警 |

**验收：** 用户在画布上完成一个镜头从参考到选片的全过程，结果在流水线视图中一致可见；两人同时编辑画布时冲突有提示且无数据丢失；0301 §6.3 的性能指标在真实项目数据上复测通过。

### V2 商业化与扩展（持续）

套餐与计费、AI 画布助手（提案 → 确认 → 应用）、多人实时协同、模型自动路由、剪辑工程导出、开放 API、角色 LoRA 训练（视 P0 与内测数据决定）。

## 5. 现有代码的处置【待确认】

新设计与现有实现在数据访问（GORM → sqlc）、接口契约（注解 → 契约先行）、前端状态（RTK Query → TanStack Query）、编排 Owner（Python 编排 → Go 工作流）上存在结构性差异，逐步改造的成本高于重建。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 同仓库重建（默认）** | 给当前代码打标签（如 `legacy-2026-09`）；新代码在 `backend/`、`agent/`、`frontend/` 按新设计重建；旧实现通过标签查阅，逐模块审计后按需搬运 | 结构干净，不受旧约束；Git 历史连续 | 旧代码不可运行期间，现有演示环境需保留旧版本镜像 |
| B. 新仓库 | 新建仓库从零开始，本仓库归档 | 最干净 | 丢失历史连续性，工程配置需重搭 |
| C. 原地改造 | 按新规范逐模块改造现有代码 | 始终可运行 | 新旧规范长期并存，改造成本与认知负担最高 |

**可能值得审计复用的部分：** 登录与邮件验证、对象存储上传、供应商适配器中的 API 细节、前端的 shadcn 基础组件与视觉 token（`DESIGN.md`）。是否复用在 M1 开始时逐项评估并记录。

**执行前提：** 只有在用户确认方案后才对现有代码做任何移动或删除操作。

## 6. 研发流程

1. **每个里程碑开始前**：在本文对应小节补充任务清单与验收用例；复杂模块（如 generation、画布）单独写专项设计。
2. **开发**：核心业务逻辑 Red → Green → Refactor；每个任务独立提交，提交信息遵循 `AGENTS.md`。
3. **每个里程碑结束时**：创建 `docs/acceptance/M<n>-验收记录.md`，记录真实操作步骤、命令、结果、未通过项与残余风险。
4. **变更控制**：需求或设计变化先修改 0101–0301 并评审，再改代码。

## 7. 主要风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 一致性达不到商用 | 角色换脸、种子客户不接受 | P0 前置验证；参考图锁定 + 关键帧先行；保留人工修图上传入口；LoRA 作为 V2 选项 |
| 成本过高 | 单分钟成本超出客户接受范围 | 关键帧确认先于视频；输入 hash 缓存复用；主备供应商比价；预算上限 |
| 模型变化快 | 供应商 API 或价格变动、新模型出现 | 模型网关抽象；每季度重跑评测集 |
| 供应商不可靠 | 超时、结果丢失、重复扣费 | 0201 §5.2 状态机与对账；供应商级限流与熔断 |
| 范围蔓延 | 画布、Agent、协同提前挤入 MVP | 严格按阶段；MVP 不做画布 |
| 合规 | 标识与审核缺失导致下架 | M4 前完成法务审阅；标识与审核列为 MVP 必须项 |
| 画布性能 | 媒体多时卡顿 | M3 并行 PoC；渲染层可替换 |
