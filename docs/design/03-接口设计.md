### 1.1 公共 API 文档与前端请求链

1. **后端为契约事实源**：接口实现时同步维护 Gin Handler 的 swag 注解及请求 / 响应 DTO；构建与 CI 执行 `swag` 生成 Swagger 2.0，`gin-swagger` 在运行中的 `backend-api` 在线提供 `/swagger/doc.json` 和 Swagger UI。前端使用的文档只包含公共 `/api` 端点，不暴露内部服务接口。规范 JSON、YAML、`docs.go` 均是生成物，禁止手写或手改；部署的在线文档须对应同一后端版本。注解变更后必须重新生成并部署，在线端点不会在未重新生成时自行反映源码变化。
2. **前端从在线端点生成**：`@umijs/openapi` 的 `schemaPath` 指向当前后端服务的 `/swagger/doc.json`，`serversPath` 与 `projectName` 指定输出到 `frontend/src/gen/api/`，`requestImportStatement` 固定为从 `@/lib/request` 导入 `request`；不从手工维护的本地规范文件生成，不编辑生成的 API 函数或类型。生成失败、端点不可达、规范无效或生成物与仓库不一致时，开发与 CI 应失败，不能用旧生成物静默继续。
3. **请求入口**：`frontend/src/lib/request.ts` 以 Axios 封装并导出生成函数所需的 `request<T>(url, options)`，负责把生成器的 `params`、`data`、`headers`、`requestType` 等参数转换为 Axios 请求，并统一处理基址、Cookie、CSRF、请求 ID、取消与 RFC 9457 错误。`/api` 只由规范路径提供一次，不在基址重复追加。普通 HTTP 请求（包括业务代码发起的预签名 URL 上传）都经此入口；跨源预签名 URL 请求不发送后端会话、CSRF 头。业务组件不得自行创建 Axios 实例或直接使用 `fetch`。
4. **流式协议边界**：SSE 与 AG-UI 流式连接需要浏览器流式 API，由同一 `request.ts` 对外提供连接入口并复用认证、基址与错误约定；它们不伪装成 Axios 的普通请求 / 响应。生成的 REST API 不承担流式订阅。
5. **漂移检查**：CI 从当前提交构建并启动后端，先重生 Swagger 文档并核对在线 `/swagger/doc.json`，再用 `@umijs/openapi` 从该在线地址重生前端 API，比较生成物；另核对公开 `/api` 路由与文档端点覆盖。任一环节失败阻断合并。

## 2. 公共 API 约定

### 2.1 基本规则

- 基础路径 `/api`，**不带版本号**（产品负责人决定，2026-09-25）：公共 API 只有本项目前端一个调用方，客户端由 OpenAPI 生成并与后端同步发布，URL 版本不带来收益。`/api` 前缀用于负载均衡分流与避免与页面路由冲突。
- 兼容靠发布规则保证（OPS-02 §6）：只做向后兼容变更（新增字段、新增端点）；删除字段或改变语义先标记废弃并保留一个发布周期；后端先于前端发布。
- 资源名用复数名词、`kebab-case`；字段名 `snake_case`；ID 为 UUID 字符串。
- 时间 RFC 3339（UTC，带 `Z`）；时长 `*_ms` 整数；金额 `*_micros` 整数（界面换算到元，DES-02 D5）。
- 查询：`GET`；创建：`POST /资源`；修改头表字段：`PATCH`；**业务命令**（确认、选定、锁定、取消等）：`POST /资源/{id}/<动作>`，动作名为动词。
- 所有写请求（`POST / PATCH / DELETE`）必须带 `Idempotency-Key`（UUID）；同键同请求体返回首次结果，同键不同请求体返回 `422 idempotency_key_reused`（REQ-01 G1）。
- 修改或选定正式对象时，请求体带 `expected_revision`；不一致返回 `409 revision_conflict`，响应体带当前 `revision`（REQ-01 G2）。

### 2.2 认证与安全

- 登录成功后下发 `lv_session` Cookie：`HttpOnly; Secure; SameSite=Lax; Path=/`。
- CSRF：登录成功时下发非 HttpOnly 的 `lv_csrf` Cookie，此后的写请求须带 `X-CSRF-Token` 头且与 Cookie 一致。`POST /api/auth/login` 豁免该校验（登录前没有会话可被冒用），改为校验 `Origin` 必须为本站且请求体为 `application/json`；供应商回调（§7.4）以验签代替。
- 每个请求带或生成 `X-Request-Id`；响应回写 `X-Request-Id` 与 `traceparent`。
- 权限：MVP 两种角色（`admin`、`producer`）；项目级接口校验项目属于用户组织且未删除；管理接口仅 `admin`。

### 2.3 分页、筛选、排序

- 列表统一 keyset 分页：请求 `?limit=50&cursor=<opaque>`，响应 `{ "items": [...], "next_cursor": "..." | null }`；`limit` 上限 200。
- 筛选使用明确字段：`?status=failed&status=unknown&episode_id=…`（同名参数多值为“或”）。
- 排序 `?sort=-create_time`，只允许端点声明的字段。

### 2.4 错误模型

采用 RFC 9457 `application/problem+json`，并增加稳定的 `code`：

```json
{
  "type": "https://lanverse.local/errors/revision_conflict",
  "title": "内容已被修改",
  "status": 409,
  "code": "revision_conflict",
  "detail": "镜头 3-12 已被更新，请刷新后重试",
  "request_id": "…",
  "errors": [{ "field": "duration_ms", "code": "out_of_range", "message": "超出模型允许范围 4–10 秒" }],
  "meta": { "current_revision": 7 }
}
```

## 3. 资源模型要点

- 所有对象返回 `id`、`create_time`、`update_time`；已逻辑删除（`is_delete = true`）的对象默认不返回。
- 头表对象返回 `revision` 与 `current_version`（内嵌当前版本内容）；版本历史用单独的 `/versions` 端点。
- 对象的派生状态在响应中统一为 `state` 结构：

```json
"state": {
  "progress": "awaiting_selection",
  "stale": [{ "cause_type": "reference_version", "cause_label": "造型「日常装」v3", "since": "…" }],
  "missing_refs": [{ "owner_type": "look", "owner_id": "…", "name": "李明 / 战斗受伤" }]
}
```

- 金额字段同时返回 `*_micros` 与 `*_display`（如 `"¥12.30"`）以减少前端换算错误。

## 5. 实时推送（SSE）

### 5.1 通道

- `GET /api/projects/{pid}/events`（`text/event-stream`）；另有 `GET /api/me/events` 推送通知。
- 每条事件带 `id`（Kafka 事件 ID）；断线重连带 `Last-Event-ID`，服务端从 Redis Stream `project:{pid}:events` 中最近 10 分钟、最多 5,000 条的缓冲补发，超出则发送 `resync` 事件，前端全量刷新当前页面（REQ-02 AVL-04）。Stream 条目保存 `id`、`event`、`data`，项目 Pub/Sub 频道为 `project:{pid}`；两者共享相同事件 ID。
- 服务端每 20 秒发送注释行心跳；连接 30 分钟后主动关闭，前端自动重连（便于负载均衡与发布）。

### 5.2 事件

事件只携带“什么变了”，前端据此使相应 TanStack Query 缓存失效，不在事件中携带完整对象。

| event | data | 前端动作 |
| --- | --- | --- |
| `operation.updated` | `{operation_id, batch_id?, target_type, target_id?, status, progress?}` | 失效任务中心、目标对象 |
| `batch.updated` | `{batch_id, succeeded, failed, unknown, total}` | 失效批次 |
| `shot.updated` | `{shot_id, episode_id, revision}` | 失效镜头与镜头表 |
| `episode.updated` | `{episode_id, parse_status}` | 失效集列表、结构 |
| `bible.updated` | `{owner_type, owner_id}` | 失效设定集 |
| `reference_slot.locked` | `{slot_id, version_no}` | 失效槽位 |
| `stale.changed` | `{object_type, object_ids[]}` | 失效受影响对象、影响清单 |
| `media.updated` | `{media_asset_id, status}` | 失效媒体库 |
| `budget.updated` | `{available_micros}` | 失效预算 |
| `canvas.updated` | `{document_id, revision}` | 拉取增量 |
| `notification.created` | `{notification_id}`（`/me/events`） | 刷新通知角标 |
| `resync` | `{}` | 全量刷新 |

## 6. 领域事件（Kafka）

### 6.1 信封

```json
{
  "event_id": "uuid",
  "event_type": "lanverse.operation.completed.v1",
  "occurred_at": "2026-09-25T08:00:00Z",
  "org_id": "uuid",
  "project_id": "uuid",
  "actor": { "kind": "user|agent|system", "id": "uuid|null" },
  "aggregate": { "type": "operation", "id": "uuid", "revision": 3 },
  "trace": { "traceparent": "…" },
  "data": { }
}
```

- 主题 = `event_type`；分区键通常为 `project_id`，无项目范围的 `audit.recorded.v1` 使用 `org_id`；消费者按 `event_id` 去重（`infra.processed_event`）。
- 载荷只放 ID、版本与必要摘要；不放剧本全文、凭据、预签名 URL。
- 版本升级：新增字段不升版；语义变化发布 `.v2` 并双写一个发布周期。
- `operation.status_changed.v1` 的 `aggregate` 为 `{type:"operation", id:<operation_id>}`；`data` 包含 `status`、`target_type`，可包含 `target_id`、`batch_id`、`progress`。`target_id` 与数据模型一致，允许为空；realtime 消费者将其投影为 `operation.updated`，SSE `id` 使用信封 `event_id`。

## 7. 内部契约

### 7.1 Temporal Activity（Go 工作流 ↔ Python agent-worker）

所有 Activity 输入输出在本节表格定义；Go 用手写结构体，Python 用手写 Pydantic 模型，字段与本节保持一致；一致性由两端的契约测试（对同一组示例输入输出分别断言）保证，不引入单独的 schema 文件与代码生成流水线。

| Activity | 队列 | 输入要点 | 输出要点 |
| --- | --- | --- | --- |
| `llm.run_skill` | `agent` | `skill_key`、`skill_version`、`model_key`、`inputs`（冻结输入：文本片段带偏移、结构化对象）、`budget{max_tokens,max_cost_micros,deadline}`、`trace`（可选链路上下文，后续接入） | `result`（按 Skill 输出 schema）、`trace_steps[]`、`trace`（不含原文的摘要）、`usage`、`cost_micros` |
| `provider.submit` | `agent.<provider>` | `operation_id`、`provider_request_key`、`adapter_key`、`provider_model_id`、`capability`、`mode`、`params`、`inputs[{role, media_url, media_type, duration_ms, text}]`、`output_count`、`credential{id, key_id, ciphertext}`（真实供应商必需；模拟供应商省略，DES-07 §5.2） | `outcome`（`accepted` / `rejected` / `not_submitted` / `unknown`）、`provider_task_id`、`error{code,retryable,message}`。`not_submitted` 只在能证明请求未到达供应商时返回：DNS / TCP / TLS 在发送请求体之前失败，或供应商返回 429 等明确“未受理”的响应；其他超时与连接中断一律为 `unknown` |
| `provider.query` | `agent.<provider>` | `provider_task_id` 或 `provider_request_key` | `state`（`pending` / `running` / `succeeded` / `failed` / `not_found`）、`result_urls[]`、`usage`、`error` |
| `provider.cancel` | `agent.<provider>` | `provider_task_id` | `outcome` |
| `provider.test_credential` | `agent` | `provider_id`（UUID）、`provider_key`、`adapter_key`、`credential{id, key_id, ciphertext}`（密文为标准 Base64） | `result`（`ok` / `auth_failed` / `unreachable` / `timeout` / `unsupported`） |

### 7.4 供应商回调

`POST /api/provider-callbacks/{provider_key}`：按供应商规则验签（HMAC 或公钥）；只作为“唤醒”信号——验签通过后向对应工作流发送 Signal，工作流仍以 `provider.query` 的结果为准，防止伪造与乱序。

### 7.5 AG-UI 代理

`POST /api/projects/{pid}/agent/sessions/{sid}/runs`（SSE）：Go 校验会话与项目权限、落库用户消息，转发到 `agent-api /internal/agent/runs`，逐条持久化 AG-UI 事件（`agent.message.seq` 递增）后转发给浏览器。`GET …/sessions/{sid}/messages?after_seq=` 用于断线续传。
