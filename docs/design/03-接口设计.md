### 1.1 公共 API 文档与前端请求链

1. **后端为契约事实源**：接口实现时同步维护 Gin Handler 的 swag 注解及请求 / 响应 DTO；构建与 CI 执行 `swag` 生成 Swagger 2.0，`gin-swagger` 在运行中的 `backend-api` 在线提供 `/swagger/doc.json` 和 Swagger UI。前端使用的文档只包含公共 `/api` 端点，不暴露内部服务接口。规范 JSON、YAML、`docs.go` 均是生成物，禁止手写或手改；部署的在线文档须对应同一后端版本。注解变更后必须重新生成并部署，在线端点不会在未重新生成时自行反映源码变化。
2. **前端从在线端点生成**：`@umijs/openapi` 的 `schemaPath` 指向当前后端服务的 `/swagger/doc.json`，`serversPath` 与 `projectName` 指定输出到 `frontend/src/api/`，`requestImportStatement` 固定为从 `@/lib/request` 导入 `request`；不从手工维护的本地规范文件生成，不编辑生成的 API 函数或类型。生成失败、端点不可达、规范无效或生成物与仓库不一致时，开发与 CI 应失败，不能用旧生成物静默继续。
3. **请求入口**：`frontend/src/lib/request.ts` 使用私有 `axios.create()` 实例，按 Axios 的 TypeScript 类型导出生成函数所需的 `request<T>(url, options): Promise<T>`，返回 Axios `response.data`。`params`、`data`、`headers`、`responseType`、取消和进度配置遵循 Axios 的原生语义，不按路径强制 JSON，不修改调用方请求头；生成模板遗留的 `requestType` 标记在边界移除，实际 FormData 由 Axios 序列化。幂等键通过 `options.headers` 传递，不从 query 推断。`/api` 只由规范路径提供一次，不在基址重复追加；按 Axios 完整 URL/baseURL 识别目标并隔离对象资源凭据。统一解析 RFC 9457 错误，包括有界的 Blob/ArrayBuffer JSON 错误正文；fetch 流式响应按实际状态校验在 Axios 包装前取消错误正文，避免带取消信号的错误流保留连接。上传代理响应元数据处理发生在传输错误捕获之后。业务组件仅调用 `@umijs/openapi` 生成的 API，禁止另建请求；项目不接入 `umi-request` 或 Umi 的请求运行时。
4. **流式协议边界（计划）**：计划随公开 SSE 与 AG-UI 路由接入流式订阅，由同一 `request.ts` 提供连接入口并复用授权、基址与错误约定；实施时按所需流式能力选择传输方式。生成的 REST API 不承担流式订阅。
5. **漂移检查**：CI 从当前提交构建并启动后端，先重生 Swagger 文档并核对在线 `/swagger/doc.json`，再用 `@umijs/openapi` 从该在线地址重生前端 API，比较生成物；另核对公开 `/api` 路由与文档端点覆盖。任一环节失败阻断合并。

## 2. 公共 API 约定

### 2.1 基本规则

- 基础路径 `/api`，**不带版本号**：公共 API 只有本项目前端一个调用方，客户端由 OpenAPI 生成并与后端同步发布，URL 版本不带来收益。`/api` 前缀用于负载均衡分流与避免与页面路由冲突。
- 兼容靠发布规则保证（OPS-02 §6）：只做向后兼容变更（新增字段、新增端点）；删除字段或改变语义先标记废弃并保留一个发布周期；后端先于前端发布。
- 资源名用复数名词、`kebab-case`；字段名 `snake_case`；ID 为 UUID 字符串。
- 时间 RFC 3339（UTC，带 `Z`）；时长 `*_ms` 整数；金额 `*_micros` 整数（界面换算到元，DES-02 D5）。
- 查询：`GET`；创建：`POST /资源`；修改头表字段：`PATCH`；**业务命令**（确认、选定、锁定、取消等）：`POST /资源/{id}/<动作>`，动作名为动词。
- 需要防重复业务效果的用户写命令（`POST / PUT / PATCH / DELETE`）必须带 `Idempotency-Key`（UUID）；同键同请求体返回首次结果，同键不同请求体返回 `422 idempotency_key_reused`（REQ-01 G1、IF4）。登录豁免通用幂等，以限速、锁定和 Origin 校验保护；供应商回调若后续启用以验签/事件标识去重，内部记账沿用 `run_id + call_seq` 等稳定业务键，不把密码或会话 Cookie 存进通用幂等回执。
- 修改或选定正式对象时，请求体带 `expected_revision`；不一致返回 `409 revision_conflict`，响应体带当前 `revision`（REQ-01 G2）。

### 2.2 认证与安全

- 当前业务 API 仅在 `cfg.Env=local` 且监听回环地址时装配；浏览器 Origin 必须匹配配置的本机公开源。Next.js 同源 `/api` 转发到本机 Go 地址，后端不从代理 Host 推断可信来源。
- `Workspace(pgidentity.NewStore)` 中间件取得唯一工作区的当前 actor/org；组织、项目、角色和媒体权限仍由 owning 模块逐次复核。固定 producer 不自动获得管理能力。
- 当前入口不使用登录、会话 Cookie 或 CSRF Cookie。消费者账号、会话与 CSRF 的未来规则见 [DES-09](09-账号与会话.md)，接入前不能按该目标开放远程业务 API。
- 每个请求带或生成 `X-Request-Id`，响应回写；内部错误不泄露凭据或请求原值。项目级查询拒绝越组织、删除或未发布项目，管理命令要求实际管理员身份。

### 2.3 分页、筛选、排序

- 通用列表计划采用 keyset 分页：请求 `?limit=50&cursor=<opaque>`，响应 `{ "items": [...], "next_cursor": "..." | null }`；`limit` 上限 200。已实施的素材库页码、总数和有界 offset 合同见[素材库设计](个人与项目素材库设计.md#32-查询与动作)，不因通用规划改变现有接口。
- 筛选使用明确字段：`?status=failed&status=unknown&episode_id=…`（同名参数多值为“或”）。
- 排序 `?sort=-create_time`，只允许端点声明的字段。

### 2.4 错误模型

采用 RFC 9457 `application/problem+json`，并增加稳定的 `code`：

```json
{
  "type": "https://lanverse.local/errors/revision_conflict",
  "title": "内容已被修改",
  "status": 409,
  "code": "revision_conflict",
  "detail": "镜头 3-12 已被更新，请刷新后重试",
  "request_id": "…",
  "errors": [
    {
      "field": "duration_ms",
      "code": "out_of_range",
      "message": "超出模型允许范围 4–10 秒"
    }
  ],
  "meta": { "current_revision": 7 }
}
```

## 3. 资源模型要点

本节定义计划实施的通用响应模型；已注册接口的字段、可选性与范围以生成的 Swagger 为准。

- 所有对象返回 `id`、`create_time`、`update_time`；已逻辑删除（`is_delete = true`）的对象默认不返回。
- 头表对象返回 `revision` 与 `current_version`（内嵌当前版本内容）；版本历史用单独的 `/versions` 端点。
- 对象的派生状态在响应中统一为 `state` 结构：

```json
"state": {
  "progress": "awaiting_selection",
  "stale": [{ "cause_type": "reference_version", "cause_label": "造型「日常装」v3", "since": "…" }],
  "missing_refs": [{ "owner_type": "look", "owner_id": "…", "name": "李明 / 战斗受伤" }]
}
```

- 金额字段同时返回 `*_micros` 与 `*_display`（如 `"¥12.30"`）以减少前端换算错误。

## 4. 公共 API 文档索引

运行中的 `backend-api` 通过 `/swagger/index.html` 提供 Swagger UI，通过 `/swagger/doc.json` 提供机器规范。实际已注册的公共路由、请求字段、响应 DTO 和错误以 Handler 注解及 DTO 为事实源，生成流程见 §1.1；本设计不重复列端点与字段表。

账号、分镜、付费生成、Agent 等业务接口计划按对应模块 Design 和 REQ 的范围、状态与失败路径实施，完成实际注册后再生成 Swagger。上传的真实内容、私有接管、状态和资源预算见 [DES-33 媒体库](33-媒体库.md)与[工作台设计](工作台设计.md)。

## 5. 实时推送（SSE）

公开 SSE 路由与前端订阅计划按以下合同接入；现有内部推送组件不代表公共接口已装配。

### 5.1 通道

- `GET /api/projects/{pid}/events`（`text/event-stream`）；另有 `GET /api/me/events` 推送通知。
- 每条事件带 `id`（Kafka 事件 ID）；断线重连带 `Last-Event-ID`，服务端从 Redis Stream `project:{pid}:events` 中最近 10 分钟、最多 5,000 条的缓冲补发，超出则发送 `resync` 事件，前端全量刷新当前页面（REQ-02 AVL-04）。Stream 条目保存 `id`、`event`、`data`，项目 Pub/Sub 频道为 `project:{pid}`；两者共享相同事件 ID。
- 服务端每 20 秒发送注释行心跳；连接 30 分钟后主动关闭，前端自动重连（便于负载均衡与发布）。

### 5.2 事件

事件只携带“什么变了”，前端据此使相应 TanStack Query 缓存失效，不在事件中携带完整对象。

| event                   | data                                                                    | 前端动作                                                                                                |
| ----------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `operation.updated`     | `{operation_id, batch_id?, target_type, target_id?, status, progress?}` | 失效任务中心、目标对象                                                                                  |
| `batch.updated`         | `{batch_id, succeeded, failed, unknown, total}`                         | 失效批次                                                                                                |
| `shot.updated`          | `{shot_id, episode_id, revision}`                                       | 失效镜头与镜头表                                                                                        |
| `episode.updated`       | `{episode_id, parse_status}`                                            | 失效集列表、结构                                                                                        |
| `bible.updated`         | `{owner_type, owner_id}`                                                | 失效设定集                                                                                              |
| `reference_slot.locked` | `{slot_id, version_no}`                                                 | 失效槽位                                                                                                |
| `stale.changed`         | `{object_type, object_ids[]}`                                           | 失效受影响对象、影响清单                                                                                |
| `media.updated`         | `{media_asset_id, status}`                                              | 失效媒体库                                                                                              |
| `budget.updated`        | `{available_micros}`                                                    | 失效预算                                                                                                |
| `canvas.updated`        | `{document_id, revision}`                                               | 拉取增量                                                                                                |
| `project.updated`       | `{project_id, revision, change}`                                        | 失效项目详情与列表；`change` 为 `created`、`updated`、`archived`、`unarchived`、`deleted` 或 `restored` |
| `notification.created`  | `{notification_id}`（`/me/events`）                                     | 刷新通知角标                                                                                            |
| `resync`                | `{}`                                                                    | 全量刷新                                                                                                |

## 6. 领域事件（Kafka）

### 6.1 信封

```json
{
  "event_id": "uuid",
  "event_type": "lanverse.operation.completed.v1",
  "occurred_at": "2026-09-25T08:00:00Z",
  "org_id": "uuid",
  "project_id": "uuid",
  "actor": { "kind": "user|agent|system", "id": "uuid|null" },
  "aggregate": { "type": "operation", "id": "uuid", "revision": 3 },
  "trace": { "traceparent": "…" },
  "data": {}
}
```

- 主题 = `event_type`；分区键通常为 `project_id`，无项目范围的 `audit.recorded.v1` 使用 `org_id`；消费者按 `event_id` 去重（`infra.processed_event`）。
- 载荷只放 ID、版本与必要摘要；不放剧本全文、凭据、预签名 URL。
- 版本升级：新增字段不升版；语义变化发布 `.v2` 并双写一个发布周期。
- `operation.status_changed.v1` 的 `aggregate` 为 `{type:"operation", id:<operation_id>}`；`data` 包含 `status`、`target_type`，可包含 `target_id`、`batch_id`、`progress`。`target_id` 与数据模型一致，允许为空；realtime 消费者将其投影为 `operation.updated`，SSE `id` 使用信封 `event_id`。

### 6.2 事件目录

审计只经 `audit.recorded.v1` 写入（DES-12）：其他领域事件不再由 audit 消费者落审计，避免重复记录。

## 7. 内部契约

### 7.1 Temporal Activity（内部工作流载荷）

Activity 协议由 Go owning 类型表达，兼容样例内联在 Go 测试中，验证历史字段往返与未知字段拒绝；不维护独立 Activity schema 或生成流水线。下表是持久协议合同，只有实际注册且完成执行验证的 Activity 才视为可用。真实供应商、Skill/Harness 和对话执行的未接入边界见 BACKLOG。

HTTP 接口规范统一由 §1.1 的 Handler 注解与 DTO 生成 Swagger，在线发布并生成前端 API。Temporal Activity 沿用工作流载荷与队列合同；只有实际注册的公共 HTTP 路由才进入公共 Swagger，不为文档展示新增供应商提交、查询、取消或凭据测试 HTTP 入口。

### 7.2 Agent 运行与逐次记账

计划在 Go owning 运行器中接入调试、评测和对话执行，复用现有进程与模块。逐次 LLM 调用以 `run_id + call_seq` 为稳定业务键：调用前在 run 行锁内登记 unknown 并取得 request_key 与剩余预算，调用后幂等写 usage/cost/outcome。模型版本、预算和原始调用证据不得由重试替换，具体合同见 DES-04 §8.7、DES-05 和 DES-39。

### 7.3 Agent 只读工具

计划通过 Go owning 查询端口提供项目摘要、集结构、镜头、设定集、模型及预估费用等只读工具，实施时强制当前 actor/org/project/session scope；跨进程工具授权须绑定 `session_id + project_id + user_id`，有效期 15 分钟。工具不创建 Operation 或写业务对象。

计划的 Agent 只输出提案（命令列表与差异）。用户明确应用后，以该用户当前身份逐条执行并校验 revision 与白名单；付费项进入报价确认。实施范围见 [DES-39](39-对话式Agent.md)与 BACKLOG。

### 7.4 供应商回调

当前不注册供应商回调路由，也不将其纳入公共 Swagger 或前端生成客户端，任务以轮询/对账查询完成。未来接入前须接受独立 webhook 路径、HMAC/公钥验签与供应商事件标识去重合同；回调只唤醒工作流，`provider.query` 仍是结果事实源。

### 7.5 AG-UI 事件持久化

Go owning 运行器校验当前主体、会话和项目权限，持久化用户消息及 AG-UI 事件后流式传输。`agent.message.seq` 单调递增，断线按 `after_seq` 查询增量；消息、提案和预算事实不依赖浏览器连接存活。该目标合同不表示对话执行已接入，具体范围见 DES-39。
