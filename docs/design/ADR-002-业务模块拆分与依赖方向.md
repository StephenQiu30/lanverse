# ADR-002 业务模块拆分与依赖方向

## 1. 状态

- 状态：`review`；与 [ARCH-007](ARCH-007-业务模块边界与服务协作设计.md) 共同评审。
- 决策日期与决策人：待 Product、Architecture、Backend、Frontend、Security、Data 和 Operations 责任人批准时填写。
- 当前无应用源码和业务数据，本决定不授权提前创建目录、依赖、数据库或部署服务。

## 2. 背景与问题

原总体设计中的 12 个模块把多种变化原因和事实放在一起：项目层级与剧本开发、语义资产与物理媒体、模型目录与生成/执行、合规裁判与交付产物相互耦合；场次、媒体技术状态、内容安全、执行 Attempt 和审计也存在潜在重复所有者。

原任务时序还把 Submission、Task、BudgetHold、Media 和 Ledger 描述为跨模块同事务，违反 TCR-002 的公开接口和禁止他域写入约束。若直接按这 12 个名称实现，模块化单体只剩目录分组，无法独立演进、验证或安全拆分。

## 3. 决定

1. 首发仍采用 ADR-001 的模块化单体，不把模块数量等同于微服务数量。
2. 规范业务目录采用 ARCH-007 定义的 17 个模块；每项业务事实只允许一个写入所有者。
3. 模块只通过 `public/index.ts` 暴露 Facade、Port Token、DTO 和版本化集成契约，不导出 Domain Entity、Repository、Prisma Model 或内部用例。
4. 单模块命令只提交所属模块事实、幂等记录、审计记录和 Outbox；跨模块写流程由有明确业务所有者的 Process Manager 分步调用，每步独立事务。
5. 同步查询必须进入 manifest allow-list 且依赖图无环；状态传播使用 Outbox/Inbox，长时流程由 Temporal 承载，综合页面使用只读投影。
6. 默认禁止跨模块 ORM Relation、外键、级联和共享 Unit of Work；例外必须新建 ADR，说明一致性收益、耦合成本、迁移和回滚。

## 4. 旧设计到规范模块的迁移

| 原模块 | 规范模块 | 拆分理由 |
| --- | --- | --- |
| `identity` | `identity-access` | 明确身份、授权、临时访问和撤销边界 |
| `project-content` | `project-catalog`、`story-development` | 项目层级生命周期与来源/改编/剧本不变式不同 |
| `continuity` | `continuity` | 保留独立故事事实与连续性裁决 |
| `asset-media` | `creative-assets`、`media-library` | 语义资产版本与物理媒体/谱系生命周期不同 |
| `storyboard` | `storyboard` | 只拥有 Shot 与准备；场次/对白仍归 story-development |
| `agent-runtime` | `agent-runtime` | 保留运行、Skill、工具和记忆边界，输出只作提案 |
| `capability-production` | `model-catalog`、`generation`、`production-jobs` | 路由政策、创作意图/候选和供应执行的变化与失败域不同 |
| `postproduction` | `postproduction` | 首发内部按声音/字幕/时间线/渲染分组件，暂不增加分布式成本 |
| `review-governance` | `review-approval` | 名称直接表达审核、决定与采用，不泛化为全部治理 |
| `cost-ledger` | `cost-billing` | 同时覆盖预算、额度、追加账本、支付交易及 P1 套餐/开票请求 |
| `compliance-delivery` | `compliance-governance`、`delivery` | 规则/权利裁决与技术质检/交付产物必须职责分离 |
| `notification-ops` | `operations-support` | 限定为 communications、ops-cases、analytics-projections 支撑组件 |

## 5. 被否决方案

| 方案 | 不采用原因 | 重议条件 |
| --- | --- | --- |
| 保留 12 个宽模块 | 重复事实、跨域事务和变化原因混杂，边界测试无法表达真实所有权 | 不重议；仅可在评审后合并有同一事实与生命周期的模块 |
| 一项 FR 一个模块 | FR 是需求文档边界，不等于有界上下文；会拆散同一不变式 | 多个独立团队/SLO/数据边界形成稳定证据 |
| 17 个模块立即拆成微服务 | 引入网络契约、分布式一致性、部署和运维成本，当前没有负载/组织证据 | 满足第 7 节的拆服务门槛并经新 ADR 接受 |
| 为 17 个模块立即建立空目录/文档套件 | 当前 Design 尚未接受，空骨架不能证明实现边界并增加维护漂移 | 对应交付切片进入已接受 Plan 时按需建立模块 Design 与代码 |

## 6. 后果与风险

正向后果：剧本与项目、资产与媒体、模型与执行、合规与交付可独立演进；任务、费用、媒体和采用不再通过共享事务伪装原子性；未来可按证据拆服务。

成本与风险：模块增多会增加公开契约、流程恢复、投影和测试数量；错误使用公共工具包或 `forwardRef()` 可能重新形成隐式耦合；事件一致性要求用户界面显示等待、失败和人工处置状态。

强制缓解：CI 执行无环、public-only、分层和迁移 owner 检查；契约测试验证版本兼容；故障测试覆盖跨模块每一步；TRACE-001 维护 FR→模块→设计→验证追踪。

## 7. 退出、拆服务与回滚

只有模块同时具备稳定公开契约和独立数据所有权，并出现独立团队/SLO、安全或数据驻留边界、持续差异化扩缩，且收益经容量/事故/交付数据证明时，才候选拆服务。拆分 ADR 必须覆盖历史数据、运行中 Workflow、无双写切换、回滚和可观测性。

本决定尚无代码或数据迁移；评审不通过时回退相关 Design 到最近接受版本并重新解决无主/重复事实，不保留双套模块名称。接受后不得静默改名或合并，必须更新 ARCH-007、TRACE-001、受影响 Design 和新 ADR。

## 8. 验证与接受条件

- ARCH-001～ARCH-007 不再把旧名称声明为当前事实所有者；旧名只保留在本 ADR 的迁移表。
- ARCH-007 为 17 个模块逐项定义职责、非职责、公开契约、允许依赖、权限、失败责任和服务映射。
- 生成/任务/媒体/费用、删除和交付流程均显示单模块事务、部分失败与恢复路径，不存在跨域写表。
- Plan 必须把 ARCH-007 的 AC-ARCH-007-001～006 转换为可执行架构、契约、集成和恢复测试。

全部条件和责任人评审通过前，本 ADR 保持 `review`，不得作为实现授权。
