## 结论

Backend 领域主线是“正式 Owner 事实 → 确定性 StoryGraph Compiler → 不可变 StoryGraphVersion”，不是把 Storyboard 改名，也不是让 Agent、Canvas、Workflow、Kafka 或 Elasticsearch 成为新的业务 Writer。

```text
ScriptRevision
  → Evidence / Bible Candidate
  → Human Gate / Owner Apply
  → Bible + Specification + Asset Identity/State
  → Episode + Scene + Beat + Occurrence + Claim
  → Storyboard Candidate / Human Gate / Owner Apply
  → Shot + ShotProductionBindingVersion
  → StoryGraph Compiler → StoryGraphVersion
  → Kafka Event → Elasticsearch Projection
```

PostgreSQL 与唯一 GORM Model Catalog 仍是所有正式业务事实的唯一 SQL 来源。Temporal 只拥有运行历史；Agent 只产生 Candidate；Kafka 只运输已提交事件；Elasticsearch 只保存可重建检索投影；ELK 日志链不保存业务状态。

## 1. 范围与非目标

本文只固定 StoryGraph MVP 必需的 Backend 领域边界：

- StoryGraph Compiler、Version/Head 与正式 Owner 的关系；
- Candidate、Human Gate、Owner Apply 和正式图发布顺序；
- Asset Identity、Specification、AssetState、AssetVersion 与角色/地点卡的边界；
- `ProductionBinding`、`ShotProductionBindingVersion` 与 `ShotImageBindingVersion` 的唯一 Owner；
- Workflow、Agent、Kafka、Search 和日志链如何消费领域事实；
- 当前代码事实与需要按 `SG-Ixx` 补齐的缺口。

本文不设计通用知识图谱、图数据库、任意 EAV Schema、微服务拆分、通用 Repository、动态 Provider 插件市场、CDC 平台、LangGraph 流程、兼容双写或未来媒体全链。已有 Workflow 细节只有被 StoryGraph MVP 使用时才继续演进，不把历史切片全部重做一遍。

| 能力 | 当前代码事实 | StoryGraph MVP 缺口 |
|---|---|---|
| Script/Bible/Planning/Storyboard | 已有 Script Revision、Production Bible Candidate、Episode Plan/Structure、Storyboard Draft/Shot/Export | 增加 Evidence、Specification/Claim 的正式版本和精确来源引用 |
| Workflow | 已有 Definition/Run/NodeRun、输入输出快照、Cache、Human Gate、Control、Temporal Worker | 增加 StoryGraph 宏观节点、Stage/Shard/Candidate Revision 挂载和新 Owner Apply |
| Review | 已有 HumanTask、Claim/Decision 与 Workflow Apply Receipt | 复用为 Bible、Episode、Scene/Beat/Occurrence/Claim、Shot Intent 的公共 Gate |
| Agent | 已有私有 Candidate Runtime、Grant 与持久 Invocation | 收口到 Backend-owned Stage/Shard/Result/Candidate Revision 和唯一 `build-storygraph` Bundle |
| Asset/Generation | 已有 Artifact/Location/Readiness、Generation Candidate/QC/Selection、Provider Job 与 Shot 图片结果绑定 | 增加 Asset Identity/State/Version、参考资产发布和 Shot 生产输入绑定 |

| Kafka/Search/ELK | 尚无真实客户端、Topic、业务索引或日志管道 | 实现最小 Outbox/Consumer、Script/StoryGraph 检索和独立日志链 |

## 4. Candidate 到正式事实的唯一链路

```text
Workflow NodeRun
  → Backend Stage/Shard Manifest
  → AgentInvocation + signed Grant
  → immutable AgentResult
  → immutable StageCandidateRevision + Candidate Head CAS
  → deterministic schema/evidence/DAG gates
  → HumanTask + ReviewDecision
  → exact Owner Application Command
  → Owner CommandReceipt + formal Owner facts
  → StoryGraph Compiler
  → new StoryGraphVersion
```

规则如下：

1. Python Agent 只执行 Backend 冻结的 Stage、Policy、Bundle、Schema、输入 Hash 和预算，不连接 PostgreSQL，也不调用 Owner Repository。
2. `AgentResult` 证明一次 Invocation 的不可变输出；可聚合、可修复的业务内容使用 Backend-owned `StageCandidateRevision`，两者不混用。
3. Candidate 保留 EvidenceRef、临时 Key、置信/歧义、Review Issue 与完整谱系；它不进入正式 StoryGraphVersion。
4. 确定性 Gate 先于 Human Gate。Schema、证据区间、覆盖率、允许的 Node/Edge/Claim 类型、DAG 或引用失败时，不得交给人工“确认通过”。
5. Review 只拥有 Decision；正向决议必须调用目标 Owner 的精确 Application Command。不存在全局 `ApplyCandidateService` 或通用 JSON Patch。
6. Owner Apply 在单 GORM 事务中写正式事实和 Command Receipt；失败整体回滚，重复命令重放同一 Receipt，同键异参返回冲突。
7. StoryGraph Compiler 只读取已确认 Owner 事实。Agent 成功、Candidate Head 切换或 ReviewDecision 本身都不能发布 StoryGraphVersion。

## 5. StoryGraph Compiler 与持久模型

`production/storygraph` 是关系编译 Owner，但不是上游对象 Writer。它通过显式只读 Snapshot Port 收集当前 Owner Head，执行纯确定性编译，再由 Application Service 发布。

首版只增加两个 GORM Record：

```text
StoryGraphVersion
├── id / workspace_id / project_id / version_no
├── parent_version_id / parent_content_hash
├── source_revision_id / source_revision_hash
├── owner_head_refs JSONB / owner_set_hash
├── schema_version / nodes JSONB / edges JSONB
├── topology_hash / content_hash / status=published
└── created_by / created_at

StoryGraphHead
├── workspace_id / project_id
├── current_version_id / current_content_hash
└── revision
```

发布事务必须：

1. 使用 GORM 开启 PostgreSQL `SERIALIZABLE` 事务并锁定 Project 的 Head；
2. 在同一一致快照内读取完整、排序、去重的 Owner Head Ref；
3. 验证 Workspace/Project、逻辑身份、精确版本、Revision、Hash 与 Evidence；
4. 以严格 Node/Edge 类型矩阵构建节点和边，使用稳定 Kahn 排序拒绝环；
5. 对 Canonical JSON 计算 Owner Set、Topology 与 Content Hash；
6. 插入不可变 Version，并以 expected Head Revision/Hash 线性切换 Head；
7. 同事务写 `StoryGraphVersionPublished` Outbox Event。

序列化、唯一约束或 Head CAS 冲突时整体回滚并从新 Head 重编译，不保留孤立 Version，不产生父链分叉。全部事务、锁、JSONB、索引和约束使用 GORM API/Clause/Tag；不创建 Migration、Raw SQL 图遍历、第二 ORM 或图数据库。

`StoryGraphVersion` 只保存 Owner Ref 和关系所需的严格投影，不复制可编辑的完整业务对象。Canvas 坐标、折叠、颜色和 viewport 不进入 Hash。完整 Node/Edge 类型矩阵、稳定 Key 和 Claim Node 语义以 [0010 设计](0010-StoryGraph内容图与DAG创作画布设计.md)为唯一来源，本文不复制第二份可漂移清单。

## 6. Asset、Specification、State 与角色卡

四个维度必须分离：

| 维度 | 唯一事实 | 例子 |
|---|---|---|
| 稳定身份 | `Asset(kind=character|location|prop)` | 同一个角色、地点或道具 |
| 叙事规格 | `Character/Location/PropSpecificationVersion` | 稳定外貌锚点、空间布局、功能、禁改项与证据 |
| 剧情状态 | `AssetState` | 基础形象、受伤制服、夜景、损坏状态 |
| 具体视觉结果 | `AssetVersion` + READY Artifact Lineage | 某规格、状态、画风下审核发布的参考版本 |

- Specification 由 `production/bible` 拥有，必须不可变、带 Bible Version 和 Evidence；
- Asset Identity、AssetState、AssetVersion、Artifact 与 Lineage 由 `asset` 拥有；
- EffectiveStyleSnapshot 由 `preset` 拥有，不塞进 AssetState；
- “角色卡”“地点卡”“Character Look”都是组合 Query View，不增加第二身份表或第二版本号；
- 同一角色的服装、伤势、伪装或年龄阶段产生不同 AssetState，不能产生第二个角色身份；
- MVP 三视图使用一个 READY composite `reference_sheet` Artifact，其 metadata 必须完整覆盖 `front/profile/back`，一次 CandidateSelection 选择一个 Candidate。

Production Bible `Confirm` 只确认不可变 BibleVersion。Asset/Specification/State 的物化由其后的 Backend Coordinator 在独立命令中完成，并在一个共享 GORM 事务内写各 Owner 事实、`ProductionBinding`、Materialization Receipt 和 Outbox；不让 Agent 或 Workflow 直接写表。

## 7. Occurrence、Shot 与三类 Binding

```text
Asset + Specification + AssetState + Style
  → reference generation → READY Artifact → AssetVersion

Scene / NarrativeBeat + AssetState
  → Occurrence
  → reviewed Shot Intent
  → formal Shot + ShotProductionBindingVersion
  → shot-frame generation → selected Artifact
  → ShotImageBindingVersion
```

| Binding | 语义 | 唯一 Owner |
|---|---|---|
| `ProductionBinding` | Bible Specification/State 与物化 Asset/AssetVersion 的发布关系 | `production/bible` |
| `ShotProductionBindingVersion` | 一个 Shot Revision 使用的完整、不可变生产输入集合 | `production/storyboard` |
| `ShotImageBindingVersion` | Shot 最终选择的生成 frame Artifact 输出绑定 | `production/storyboard` |

`ShotProductionBindingVersion` 按 Shot Revision 追加完整集合，每项冻结 Occurrence、Asset Role、精确 AssetVersion、Lineage Hash 和所需 View Role。发布前必须证明每个已审核视觉需求恰好有一个合法 Entry，且身份、AssetState、画风、Readiness 与来源一致；禁止读取“最新资产”、逐项可变覆盖或借用另外两类 Binding。

Storyboard Candidate/Shot Intent 经 Human Gate 后，Storyboard Owner 才能原子创建正式 Shot 和生产输入 Binding；之后 StoryGraph Compiler 才能把 Shot/Binding 编入新 Version。生成画面选择继续写已有 `ShotImageBindingVersion`，不能回写生产输入 Binding。

## 8. Workflow 与 Agent 的领域关系

StoryGraph 不是执行图。四种 ID、Schema 和 Owner 必须分开：

| 事实 | 作用 |
|---|---|
| StoryGraphVersion | 内容和生产关系 |
| AuthoringRevision.Graph | 用户选择的生产编排 |
| WorkflowDefinitionVersion | Workflow Compiler 产生的可执行 DAG |
| Temporal History | 实际 Activity/Timer/Signal 历史 |

WorkflowDefinition 只放稳定宏观节点与 Human Gate，例如 Evidence 提取、全局分析/归并、Bible 审核、分集、逐集分析/归并、Storyboard Draft、参考资产、Shot Detail 和正式 Apply。每个宏观节点内部的 ShardManifest、Invocation、Candidate Revision 和 Repair 由 Backend 持久化并挂到精确 NodeRun；不能动态伪造 Workflow Node，也不引入 LangGraph 作为第二流程引擎。

Node 只通过 canonical `node-input-v1` / `node-output-v1` 传播精确 Owner Ref 或 Candidate Revision Ref。Temporal Activity 不持有整个 Codex 调用；外部运行处于 `queued/running` 时，Node 投影进入可恢复等待并使用 Temporal Timer 轮询同一稳定 Invocation。`failed`、`unknown`、超时和迟到结果按同一 Invocation/Claim/Receipt 对账，不换身份盲目重提。

## 9. Kafka、Search 与日志事件边界

首个异步切片只为真实消费者发布事件：

- `ScriptVersionPublished`：驱动剧本索引更新；
- `StoryGraphVersionPublished`：驱动 StoryGraph Lens/Search 投影更新。

Owner Command 在同一 GORM 事务中写 Aggregate/Version/Head、Command Receipt 和 Outbox。Publisher 从 PostgreSQL Outbox 读取并至少一次发布到 Kafka；Consumer 用 Event ID/业务键与 Revision Fencing 幂等处理，失败进入 DLQ，可按明确范围 Replay。当前不引入 Debezium/CDC，也不为没有消费者的模块预建 Topic。

Elasticsearch 业务文档必须保存 `workspace_id/project_id/owner_kind/owner_id/owner_version/source_event_id`，所有 Query 强制租户与权限过滤。索引可由 PostgreSQL Owner Snapshot 全量 Reindex，旧乱序事件不能覆盖新 Revision；Search 不可用时返回明确 degraded 状态，不能让投影回写正式事实。

业务事件与日志严格分流：

```text
Domain Outbox → Kafka business topic → Backend Event Runtime → Elasticsearch business index
JSON log → fail-open TCP → Logstash → Elasticsearch log index → Kibana
```

Kafka 只承载业务 Topic；日志使用独立 Schema、Logstash Pipeline 和 Index Template，不经过 Kafka。日志必须脱敏，不包含凭据、完整原稿或生成内容；Logstash 不消费 Domain Event。

## 10. 数据与实现约束

1. Backend 只打开一个 `DATABASE_URL`，所有业务 Writer 使用同一个 PostgreSQL 与 GORM Catalog。
2. 新 Model 只在首个 `SG-Ixx` Red 契约需要时加入 `schema.Catalog()`，由 GORM 空库同步；不创建 Migration 文件、迁移字段/账本、第二 Schema 或第二 DSN。
3. 业务持久化只使用 GORM Model、Transaction、Association、Clause 和 Tag，不写手工 SQL、DDL 或图遍历 SQL。
4. Domain/Compiler/Application/HTTP Handler 不导入 GORM；Adapter 才实现本模块 Port。
5. Owner Transaction 不等待 Codex、Provider、Kafka、Elasticsearch 或对象存储网络调用；先提交 Intent/Outbox，再以稳定身份执行和对账。
6. Kafka 与 Elasticsearch 客户端、Broker/Elastic Stack 版本和装配入口必须在唯一总 Plan 中基于官方资料锁定，并在首个实现提交前进入依赖清单；只允许一套客户端，不建兼容封装。
7. Backend 测试只位于 `backend/tests`，Agent 测试只位于 `agent/tests`；包内业务测试不再新增。

## 12. 状态与失败路径

- Owner Ref/Evidence 漂移：拒绝编译，返回精确 stale 引用；
- Candidate Head 漂移：Repair/下游输出拒绝提交，使用 expected Candidate Hash 重算；
- Head CAS/序列化冲突：整个 StoryGraph 发布事务回滚并从新 Head 重编译；
- 未知身份、AssetState、Scene、Shot 或 Claim：保留 Review Issue，不近似匹配或自动创建；
- 参考资产未 READY、三视图覆盖不全或 Lineage 漂移：不得发布 AssetVersion/Shot Binding；
- Human Gate 正向决议但 Owner Receipt 未确认：Workflow 保持等待并按同一 Receipt 对账；
- Kafka 重复/乱序：Inbox/Revision Fencing 收敛；Poison Message 进入 DLQ；
- Elasticsearch 不可用：业务 Command 继续以 PostgreSQL 为准，查询明确 degraded，恢复后 Reindex；
- Agent/Provider 结果未知：保持原 Intent/Invocation/Job 与预算占用，不盲目创建第二份结果。

## 13. 验证与实施门禁

SG-D10 只接受领域边界，不声明新增能力已经实现。实现必须继续按 [0010 的 `SG-Ixx` 唯一队列](0010-StoryGraph内容图与DAG创作画布设计.md#唯一实施任务队列)推进，每个完整小任务遵循 Red → Green → Refactor、真实 CI、独立 Git 提交。

StoryGraph MVP 的最小闭环是：真实剧本 → Evidence → Bible/Specification/AssetState → Episode/Scene/Beat/Occurrence/Claim → Core StoryGraphVersion，并证明每个节点/边可反查唯一 Owner Ref、版本、Hash 和 Evidence。Storyboard/视觉资产在其后分步进入，不提前用空 Asset、假 Provider、测试 Catalog 或兼容路径证明完成。

Kafka、Elasticsearch 与 ELK 的实现只能由真实 Broker、Index、Pipeline 和故障恢复测试验收；全部代码切片和 CI 通过后，最后才使用 `agent-browser` 执行 Browser → API → PostgreSQL Owner → Kafka/Search → Artifact 的完整旅程。
