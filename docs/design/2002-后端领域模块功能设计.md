## 1. 结论

Backend 仍是一个 Go Backend、一个 PostgreSQL、一个 GORM Model Catalog，但内部必须保留明确 Owner。Guided Studio 的正式事实链固定为：

```text
production/script
  → production/project + production/bible（Gate 1）
  → production/bible + production/planning + asset（Gate 2）
  → preset + production/reference（Gate 3）
  → asset（基础选择）
  → production/reference + asset（组合选择 / Gate 4）
  → SceneProductionPacket typed Query
  → agent Candidate + review
  → production/storyboard（Gate 5）
  → production/storygraph Compiler
```

每个业务 Owner 先提交自己的不可变事实、Head、Command Receipt、Collection Commit Receipt 与 Outbox；StoryGraph 随后把这些事实确定性投影为不可变 Version。Agent、Review、Workflow、Generation、Kafka、Search 和前端都不能越过 Owner 直接写正式业务事实。

本文固定七个关键落地点：

1. 五个 P0 Owner 是 `production/script`、`production/project`、`production/bible`、`production/planning`、`asset`；Preset、Reference、Storyboard 和 StoryGraph 在 P1–P3 按同一规则加入；
2. 正式事实使用具体领域 Version/Fragment/Head Record，不建立万能 Owner JSON 表、EAV 或全局 Repository；
3. 一个协调命令只有一个 `OwnerCommandReceipt`，但按实际 Collection Root 写 `0..n` 个 `OwnerCollectionCommitReceipt`；
4. Gate 2 的 Bible/Planning/Asset 与 Gate 3/4 的多 Owner Apply 在同一数据库事务内协调，但每个 Owner 独立校验并只写自己的 Record；
5. `OwnerCollectionRef` 是同一读事务内重算的 phantom-range 完整性证明，不是第二套业务 Record；
6. `SceneProductionPacket` 与执行物化是 typed Query/Agent Invocation 输入快照，不是 Owner 表或 StoryGraph Node；
7. 所有写事务使用统一锁序、expected Head CAS、精确 ReviewDecision/Skill Release fence 与 Outbox，unknown 不产生第二份业务事实。

| 模块/Owner | 唯一拥有 | 明确不拥有 |
|---|---|---|
| `production/script` | DocumentRevision、SourceSpanIndexVersion、Source acceptance | Scene、Identity、Graph |
| `production/project` | Project、Episode identity/order/lifecycle | Scene 内容、Bible、Candidate |
| `production/bible` | StructureIdentitySetVersion、Evidence、Specification、WorldRule、跨集 Claim、ProductionBinding、ProductionBibleVersion | Asset identity、Scene、Preset |
| `production/planning` | Scene、Dialogue、Beat、Occurrence、Causal/Continuity/Interaction Claim、StructureRebase | AssetVersion、Shot、Graph |
| `asset` | AssetIdentity、AssetState、AssetVersion、Artifact/Rendition、Readiness/Rights/Lineage、Reference selection materialization | Specification、Reference Plan、Generation selection |
| `preset` | PresetVersion、Project binding、EffectiveStyleSnapshot、EffectivePolicySnapshot | 剧情事实、Artifact、Provider secret |
| `production/reference` | ApprovedReferencePlanVersion/Target、SceneReferenceBindingVersion、InteractionReferenceBindingVersion | Generation、AssetVersion、Shot |
| `production/storyboard` | formal Shot set、ShotVersion、ShotProduction/Image/Video BindingVersion | Asset/Generation Candidate、Packet |
| `production/storygraph` | Schema-bound Compiler、StoryGraphVersion、StoryGraphHead | 上游对象、Canvas 布局、Workflow |
| `agent` | Definition/Bundle/Release/Control、Stage/Shard、Invocation/Attempt/Outcome、Candidate Revision/Head/Staleness | 任何正式 Production/Asset/Graph 事实 |
| `review` | HumanTask、claim lease、不可变 ReviewDecision | Subject 内容、Owner Apply 结果 |
| `generation` | Provider 配置/调用、GenerationCandidate、QC、CandidateSelection | Artifact readiness、AssetVersion、Reference/Shot Binding |
| `workflow` | Definition/Run/NodeRun、控制、等待、恢复和 Resume Receipt | 业务内容与 Owner Receipt 语义 |
| `eventing` | Outbox 传输、Kafka Envelope、Inbox/DLQ/Replay | Domain Event 的业务判断 |
| `search` | 可重建索引和 reindex 状态 | 正式事实和命令 |

Domain/Application 只依赖本模块接口和调用方定义的窄 Port；只有 Adapter 可导入 GORM。跨 Owner 协调器位于 Backend Application 层，以一个 GORM transaction handle 调用各 Owner 的 transaction-scoped application port；它不能直接操作对方 Model 或 Repository。

`ProductionBinding` 的业务语义由 `production/bible` 拥有，但 Gate 2 协调事务同时调用 `asset` 取得刚发布的精确 Asset/State refs；`production/bible` 不能自己插入 Asset。`production/reference` 发布 Binding 时同理只引用 `asset` 已发布的 exact versions/artifacts。

## 4. 共用不可变合同

本文伪 Schema 均为 `additionalProperties=false`；除 `?` 或 `| null` 外全部字段必需。所有 hash 使用项目 Canonical JSON、小写 SHA-256 与 contract domain separator，对排除自身 hash 的完整对象计算。所有时间戳只用于审计，不参与业务内容 hash，除非合同明确声明。

### 4.1 Owner Version 与 Node Ref

所有具体 Version/Fragment Record 必须能投影 `0010` 已接受的 `OwnerVersionRef` / `OwnerNodeRef`：

```text
OwnerVersionIdentityV1 {
  workspace_id,
  project_id,
  owner_kind,
  version_family,
  owner_logical_id,
  owner_version_id,
  owner_revision,
  parent_owner_version_id | null,
  parent_owner_content_hash | null,
  owner_content_hash
}
```

Root Version 的 content hash 覆盖其完整有序 fragment/member identity；Fragment 有自己的 `fragment_key/fragment_content_hash`，并由 Root content hash 二次覆盖。Receipt、Workflow、ReviewDecision、Graph ID、数据库自增值和“当前 Head”不进入业务 Version content hash，避免环和时间依赖。

一个逻辑对象只允许一条线性 Version chain。新版本以 expected revision/hash CAS 对应 Owner Head；冲突返回 stale，不建立分支、不覆盖旧版本。Head 只服务写入串行化和显式 `GetCurrent...` UI Query，Agent/Compiler/Owner Command 必须携带 exact refs，不能把 Head lookup 隐藏在业务输入中。

### 4.2 具体 Scope Head 合同

每个 Version Family 由其 Owner 实现一个具体 `*ScopeHeadRecord`，共用逻辑字段：

```text
OwnerScopeHeadContractV1 {
  workspace_id / project_id,
  owner_kind / version_family,
  scope_kind / scope_key,
  scope_revision,
  scope_content_hash,
  member_count,
  members_hash,
  collection_root_hash,
  current_root_version_refs[],
  head_revision,
  head_content_hash
}
```

这只是各模块具体 Head 的实现合同，不建立一张全局 `owner_heads` 表。`current_root_version_refs[]` 是 Head CAS 和快速校验缓存；Owner Collection adapter 必须从具体版本/成员表重算并与缓存全等，不能相信缓存自证完整。

Hash 顺序固定为：`scope_content_hash` 覆盖 owner/family/scope/scope revision 与完整 current root refs，但不含 members/collection/head hash；`members_hash` 只覆盖规范排序的 `OwnerVersionRef[]`；`collection_root_hash` 按 `0010` 覆盖 scope identity/revision/content hash + 完整 members/count/hash；最后 `head_content_hash` 覆盖 Head 除自身外的完整字段。Collection Root 从不包含 `head_revision/head_content_hash`，因此只有 `scope → members → collection → head` 单向依赖。

### 4.3 两层 Receipt，无 Hash 环

```text
OwnerCollectionCommitReceiptV1 {
  collection_receipt_id,
  command_id,
  idempotency_key,
  workspace_id / project_id,
  decision_checkpoint_id,
  owner_kind / version_family,
  scope_kind / scope_key,
  scope_revision / scope_content_hash,
  members[] / member_count / members_hash,
  collection_root_hash,
  covered_scope_keys[],
  committed_owner_version_refs[],
  review_decision_audit_ref | null,
  source_acceptance_audit_ref | null,
  receipt_content_hash,
  committed_at / committed_by
}

OwnerCommandReceiptV1 {
  command_receipt_id,
  command_id,
  command_contract_id,
  command_content_hash,
  idempotency_key,
  workspace_id / project_id,
  coordinator_kind,
  subject_ref,
  ordered_collection_receipt_refs[],
  committed_owner_version_refs[],
  domain_event_descriptors[],
  result_content_hash,
  receipt_content_hash,
  committed_at / committed_by
}
```

每个实际 Collection Root 恰一个 Collection Receipt，唯一键是 `(checkpoint, owner, family, scope_kind, scope_key, collection_root_hash)`。同一协调命令只有一个 Command Receipt，它可引用多个 Collection Receipt。正常空 `planning_structure_rebase_set` 不写 Collection Receipt；尚未闭合的增量基础/组合结果也只写自己的 Command Receipt，不冒充 checkpoint complete。

Hash 方向固定为：

```text
Owner Versions / Fragments
→ OwnerCollectionRef root
→ OwnerCollectionCommitReceipt
→ OwnerCommandReceipt
→ Outbox payload / event envelope
```

Owner Version 不引用 Receipt；Collection Receipt 只保存 `command_id`，不引用 Command Receipt content hash；Command Receipt 再引用 Collection Receipt ref/hash 和待发布的有限 Domain Event Descriptor，但不保存 Outbox row/event id。Outbox payload 在 Receipt 完成后单向引用 Command Receipt id/hash。因此无 Version ↔ Receipt、两类 Receipt或 Receipt ↔ Outbox 的 hash 环。

Collection/Command Receipt 的 content hash 均排除自身 hash 与 `committed_at/committed_by` 审计字段；`result_content_hash` 只覆盖排序后的 Collection Receipt refs、Owner Version refs 和 Event Descriptors，`receipt_content_hash` 再覆盖完整命令身份与 result hash。Outbox Event ID、publish attempt 和 broker offset 永不进入 Receipt hash。

```text
DomainEventDescriptorV1 {
  event_type,
  aggregate_owner_ref,
  aggregate_revision,
  aggregate_content_hash,
  payload_contract_id,
  payload_content_hash
}
```

Descriptor 不含 event id、publish state、broker metadata 或 Command Receipt ref/hash；`payload_content_hash` 只覆盖预先可计算的业务事件 payload。Outbox row 在同一事务中获得 event id，并在 Envelope 外层附加 Descriptor hash 与 Command Receipt ref/hash 作为单向上游引用。

`review_decision_audit_ref` 与 `source_acceptance_audit_ref` 必须恰选一：用户 Gate 使用前者，source acceptance 使用后者。内部增量命令如果尚未完成用户 checkpoint，两者都为 null 且不得写 Collection Receipt。

### 4.4 Command 幂等身份

所有写命令带：

```text
CommandEnvelopeV1 {
  command_id,
  command_contract_id,
  workspace_id / project_id,
  actor_ref,
  idempotency_key,
  subject_ref,
  expected_heads[],
  exact_input_refs[],
  command_payload,
  command_content_hash
}
```

`idempotency_key` 在 command contract + workspace 内唯一。相同 key/hash 重放返回同一 Command Receipt；同 key 不同 hash 返回 `idempotency_payload_conflict`。事务开始时以 GORM 唯一约束创建/锁定 module-scoped command dedup row；失败事务不留下“成功”Receipt。不存在一张可接受任意 payload 的通用 Apply API，Envelope 只作为各具体 Command Schema 的共用前缀。

## 5. P0 五个 Owner 与七个 Family

### 5.1 `production/script` — `script_source_set`

具体 Record：

- `DocumentRevisionRecord`：规范化全文、byte/code-point 长度、document content hash、来源审计；
- `SourceSpanIndexVersionRecord`：DocumentRevision ref、code-point 索引合同、完整 span/index hash；
- `ScriptSourceScopeHeadRecord`：Project scope 的 accepted Document + Index exact refs 与 Collection roots。

`AcceptSourceRevisionCommand` 必须携带 Document/Index exact refs、expected Script head 和 source acceptance audit；事务重算 code-point 索引、全文 hash 与成员集合，更新 Head，写 `source_revision_accepted / script_source_set` Collection Receipt、一个 Command Receipt 和 Outbox。SourceSpanIndex 是 Collection 校验成员但不投影 StoryGraph Node。

### 5.2 `production/project` — `project_episode_set`

具体 Record：

- `EpisodeVersionRecord`：稳定 Episode logical id、生命周期、SequenceKey、source scope 与 parent Project；
- `ProjectEpisodeMembershipRecord`：某 scope revision 的完整 active Episode refs/order；
- `ProjectEpisodeScopeHeadRecord`。

`ConfirmProjectEpisodeLifecycleCommand` 是 Gate 1 决议的第一条 Owner 命令。它绑定精确 Structure/Identity Candidate Revision、ReviewDecision、Script Receipt、预留 episode keys 和 expected Project head；发布完整 active Episode 集并写 `project_episode_lifecycle_confirmed / project_episode_set` Receipt。若后续 Bible Gate 1 Apply 失败，该已提交 Project Receipt 保留，重试只能精确复用，不能重建另一批 Episode ID。

### 5.3 `production/bible` — 两个 Family

具体 Record：

- `StructureIdentitySetVersionRecord` + `StructureIdentityScopeHeadRecord`；
- `SourceEvidenceFragmentVersionRecord`；
- `SpecificationVersionRecord`（Character/Location/Prop 严格联合）；
- `WorldRuleVersionRecord`、跨集 `ClaimVersionRecord`、StoryArc/PlotThread Version；
- `ProductionBindingVersionRecord`；
- `ProductionBibleVersionRecord` + `BibleProductionWorldScopeHeadRecord`。

`ConfirmStructureIdentitySetCommand` 是 Gate 1 第二条命令，只在精确 Project Episode Receipt 已提交后执行。它携带 Candidate/Decision、Scene temporary→reserved logical id、mention→identity key 完整映射、expected Bible structure head 和 Skill Release/Result lineage。事务写 StructureIdentitySetVersion、`gate_1_structure_identity / bible_structure_identity_set` Receipt、Command Receipt 与 Outbox；它不创建 Asset、Specification、Scene 或 StoryGraph。

`ProductionBibleVersionRecord` 是 Gate 2 的 Bible root，内嵌精确 StructureIdentitySetVersion ref，并以 fragments/refs 完整覆盖 Evidence、Specification、ProductionBinding、WorldRule、跨集 Claim、Arc/Thread。Receipt 不进入其 content hash。

### 5.4 `production/planning` — 两个 Family

具体 Record：

- `SceneVersionRecord`、`DialogueVersionRecord`、`NarrativeBeatVersionRecord`；
- `OccurrenceVersionRecord`；
- `PlanningClaimVersionRecord`，其中 Interaction 是 Continuity 的严格 discriminated branch；
- `PlanningEpisodeMembershipRecord` + 每 Episode 一个 `PlanningEpisodeScopeHeadRecord`；
- `StructureRebaseVersionRecord` + `PlanningRebaseScopeHeadRecord`。

每个 Planning fragment 保存 Owner-defined SequenceKey/StoryTimeKey 和 exact Evidence 或 creator decision audit，不能由 Compiler 重排。每个 active Episode 的 `planning_scene_set` 独立重算、独立写 Collection Receipt。StructureRebase 只有 split/merge/delete 时发布旧 scope→新 scope 的完整映射；首次无 rebase 的 Gate 2 创建 revision=1 的 canonical empty `PlanningRebaseScopeHeadRecord`，成员数为 0，但不创建 StructureRebaseVersion 或 Collection Receipt。后续仍为空时 Head 不前进；发生 rebase 时才发布 Version、前进 Head 并写 Receipt。

### 5.5 `asset` — `asset_identity_state_set`

具体 Record：

- `AssetIdentityVersionRecord`：Character/Location/Prop 稳定逻辑身份；首次创建 revision=1，后续只在显式身份审计变化时发布线性新版本，绝不因形象/画风变化新建身份；
- `AssetStateVersionRecord`：一个身份在剧情阶段的完整生产状态、边界和原因；
- `AssetIdentityStateMembershipRecord` + `AssetIdentityStateScopeHeadRecord`。

Gate 2 可按 Gate 1 identity key 创建或精确复用 AssetIdentity；同名、相似图或自由文本不能成为复用依据。AssetState 不包含画风、Provider、Artifact 或 AssetVersion。一个正式身份至少一个完整 State；每个实际 Occurrence 必须通过 ProductionBinding 唯一解析 Identity + Specification + State。

### 5.6 Gate 2 三 Owner 原子协调

`ConfirmProductionWorldCommand` 绑定：

- 当前 StructureIdentitySetVersion、Gate 1 两类 Collection Receipts 与 ReviewDecision；
- normalized Production World Candidate 三 partition Revision/Hash；
- Bible/Planning/Asset expected business key sets、scope closure 与 cross-partition ref table；
- Bible head、每个目标 Planning Episode head、Planning Rebase head、Asset head 的 expected revision/hash；
- Skill Release Control hash/fence、Candidate/Review/Repair lineage；
- actor/idempotency/command content hash。

同一 PostgreSQL/GORM 事务按逻辑顺序：

1. 预验证全部三 partition、Evidence、Identity、State、Occurrence、Interaction、Continuity 和 expected key coverage；
2. `asset` 创建/复用 AssetIdentity 并发布完整 AssetState；
3. `production/bible` 用刚产生的 exact Asset refs 发布 Specification/Binding/Bible roots；
4. `production/planning` 发布 Scene/Dialogue/Beat/Occurrence/Claim 与条件式 Rebase；
5. 三 Owner 分别重算并 CAS 自己的 concrete Scope Heads；
6. 为 `bible_production_world_set`、每个 Episode 的 `planning_scene_set`、非空 rebase 和 `asset_identity_state_set` 各写一个 Collection Receipt；
7. 写一个 `ConfirmProductionWorld` Command Receipt 和一次事务 Outbox。

任一 Owner 校验、Head CAS、Collection root、Receipt 或 Outbox 失败，三 Owner 全部回滚。Coordinator 不能在事务外先写 Asset 再补 Bible/Planning；也不能用一个 Owner 级 Receipt 代替各 Episode/Family proof。

Gate 2 允许对依赖闭合的 Scene/Episode scope 分批提交：每次都会发布新的项目级 Bible/Asset roots，并只更新目标 Episode 的 Planning heads/receipts；未受影响 Episode 的旧 Planning receipt 继续有效。`VisualProductionPackageView` 此时可显示 partial。首次 p0 Graph 编译仍要求当前 active Episode 每个都有非空完整 `planning_scene_set` Receipt，另外六个 P0 family 也满足各自 current root、Receipt 或 canonical empty rebase policy；缺一个 Episode 时 Owner 事实可继续存在，但项目不得声称 p0 complete 或发布不完整 Graph。

## 6. P1/P2/P3 Owner Record

### 6.1 `preset` — `preset_effective_set`

具体 Record：

- `PresetVersionRecord`：发布的世界观/视觉基底策略 refs，不含 Provider secret；
- `ProjectPresetBindingVersionRecord`：Project 选定 PresetVersion 与 typed overrides；
- `EffectiveStyleSnapshotRecord`；
- `EffectivePolicySnapshotRecord`；
- `PresetEffectiveScopeHeadRecord`。

Effective Snapshot 是不可变解析结果，不是运行时 map。Style 只含视觉语言；Policy 绑定 Style、Skill/Prompt/Model/QC/Motion/Render 策略 refs/hash。切换 Preset 发布新 binding/snapshots，使 Gate 3 以后 stale，但不修改 P0 facts。

### 6.2 `production/reference` — Plan 与 Binding

具体 Record：

- `ApprovedReferencePlanVersionRecord`；
- `ReferencePlanTargetVersionRecord`，严格 `character_identity_anchor|character_appearance|location_board|prop_sheet|scene_composition|interaction_composition`；
- `ReferencePlanScopeHeadRecord`；
- `ProjectReferencePlanActivationHeadRecord`：一个 Project 到一个 exact active Plan logical/version ref 的唯一 CAS 指针，不是 Collection member；
- `SceneReferenceBindingVersionRecord`；
- `InteractionReferenceBindingVersionRecord`；
- 每 Scene 一个 `ReferenceBindingSceneScopeHeadRecord`。

一个 Project 在 p1 只能有一个 active ApprovedReferencePlanVersion；Gate 3 必须同时 CAS Project activation head 与 Plan scope head，Compiler/Packet Query 重算两者逐字节指向同一 Plan。Target 保存 exact business key、required/optional/not_generated、coverage scopes、依赖、purpose 和 order key，不保存 Provider、价格、Prompt 或 CandidateSelection。Scene/Interaction Binding 只引用 exact selected base AssetVersion、selected Composition Artifact 和 fulfilled Target；不创建组合 AssetState。

### 6.3 Gate 3 双 Owner 原子协调

`ConfirmVisualFoundationAndReferencePlanCommand` 绑定 Gate 3 ReviewDecision、Visual Foundation/Plan Candidate Revisions、完整 p0 roots、PresetVersion/typed override、Backend expected Target key set，以及 Preset/Reference expected heads。

### 6.4 `asset` — 基础与组合结果 Family

新增具体 Record：

- `AssetVersionRecord`：purpose 严格区分 identity anchor、character appearance、location board、prop sheet；
- `ArtifactRecord` / `RenditionRecord` / `ArtifactReadinessRecord` / Rights/Lineage refs；
- `AssetBaseReferenceMembershipRecord` + `AssetBaseReferenceScopeHeadRecord`（Reference Plan scope）；
- `AssetCompositionMembershipRecord` + 每 Scene 一个 `AssetCompositionSceneScopeHeadRecord`。

### 6.5 Gate 4 渐进结果与 checkpoint

基础选择必须允许身份锚点先完成、Appearance 随后生成，因此拆成结果发布和 checkpoint 完成两个 Command：

- `PublishSelectedBaseReferenceResultCommand`：消费一个 exact CandidateSelection/Target，发布或幂等复用 AssetVersion，更新 base membership/head，只写结果 Command Receipt；
- `CompleteBaseReferenceSelectionCheckpointCommand`：在全部 required 基础 Target 闭合时重算完整 `asset_base_reference_set`，写唯一 `gate_4_base_reference_selection` Collection Receipt 和 Command Receipt。

尚缺 required Target 时第一条命令成功不等于 Gate 完成；optional 未选或 not_generated 按 Plan 显式存在但不伪造 AssetVersion。

组合选择同样分层：

- `PublishSelectedCompositionResultCommand`：在同一事务中由 `asset` 固化 selected READY Composition Artifact membership，由 `production/reference` 发布 Scene/Interaction Binding；
- `CompleteSceneCompositionSelectionCheckpointCommand`：按一个 Scene scope 重算 `reference_binding_set` 与 `asset_composition_artifact_set`，分别写两个 `gate_4_composition_selection` Collection Receipt，再写一个 Command Receipt。

required Composition 未闭合时不得完成该 Scene Gate 4；一个 Scene 成功不要求无关 Scene 同时完成。Identity anchor/Base/Composition 的 CandidateSelection 继续由 `generation` 拥有，Asset/Reference 只消费 exact selection ref/hash，不改 Selection。

## 7. Owner Collection Adapter

`OwnerCollectionRef` 不持久化为万能业务表。每个 Owner 为自己拥有的具体 Family 实现 read adapter：

```text
BuildOwnerCollection(
  workspace_id,
  project_id,
  version_family,
  scope_kind,
  scope_key,
  expected_scope_revision,
  expected_scope_content_hash
) -> OwnerCollectionRef
```

Adapter 必须在调用方提供的同一数据库 read/write transaction 中：

1. 锁定或读取具体 `*ScopeHeadRecord`；
2. 从具体 Version/Membership 表重建完整 member universe；
3. 校验 owner/family/scope、member version/hash、业务基数和空集策略；
4. 按 `0010` tuple 排序去重；
5. 重算 member count/hash、scope content hash 和 collection root；
6. 与 concrete Head 缓存和 expected 值全等；
7. 返回完整前像，不只返回 hash。

调用方不得自行拼 `members[]`，不得跨两个查询时间点合并 roots，不得读取另一个 Owner Repository。Compiler 通过窄 Adapter interface 聚合结果。

Checkpoint/Owner/Family allowlist、Scope 基数、空集策略和 Coverage 累计只以 `0010` Schema Manifest 为事实来源。D09 只固定它们如何落到具体 Record/Adapter/Receipt，不复制另一套可编辑常量。Schema Manifest validator 必须证明 13 个 family 与 concrete adapter registry 一一对应；漏一个、多一个或 owner/family 不等价均 fail closed。

## 8. Agent 持久 Record 与 Release fence

`agent` 模块具体 Record：

- `AgentDefinitionCoreRecord`、`SkillBundleRecord`、`StageReleaseRecord`、`CandidateStageSetRecord`、Eval/Shadow/Build Attestation、`SkillReleaseRecord`、Signature；
- `SkillReleaseControlRecord` 与 `SkillReleaseControlHeadRecord`；
- `ShardManifestRecord`；
- `AgentInvocationRecord`；
- `AgentAttemptRecord`、`AgentAttemptResultRecord`、`AgentInvocationOutcomeRecord`；
- `StageCandidateRevisionRecord`、`StageCandidateHeadRecord`、`StageInstanceStalenessRecord`；
- Review/Repair 的 exact Candidate refs 与 patch application receipts。

Record 必须保留 `3003` 规定的完整 JSON 前像、contract/schema/hash、StageVariantKey、Release roots、control hash/fence、input hash、claim/attempt、producer union 与 parent lineage，不能只存 JSON blob + status。Candidate body 可存严格 JSONB，但列中必须另外保存 contract id/schema hash/content hash，读取时重新验证。

`AgentInvocationRecord` 对 `direct_storyboard` 保存完整 SceneProductionPacket、Execution Materialization 和 Media Attachment Manifest JSON/hash；媒体 bytes 只由 broker 按 exact digest 读取，不进数据库。Packet 没有独立 Head/Table。`PrepareDirectStoryboardInvocationCommand` 使用短 `SERIALIZABLE` 事务：先锁 approved Skill Release Control 与 command dedup，再按统一顺序锁定 Packet 涉及的 P0–P2 Scope Heads、Project Plan Activation Head、ArtifactReadiness rows 和当前 StoryGraph Head；在同一事务内通过 typed Query 构建 Packet/Materialization、重验 Scene readiness，并创建唯一 Stage instance/Invocation。它不调用 Codex 或对象存储网络。dispatch 前再按 exact refs/digests 复验 Release fence、Artifact safety/readiness 和 broker bytes。

Backend 在 Invocation 创建、Attempt dispatch、Outcome 接受、Candidate revision/aggregate/repair、Candidate Apply/reuse 的事务中都先锁 current SkillReleaseControlHead，并以 expected control hash + release fence 作为写谓词。Harness 只验证 DispatchAuthorization，不读数据库。quarantine/revoke 后迟到 Result 只留审计，不能成为 Outcome/Candidate/Owner 事实，也不能 fallback 到相近 Release。

Invocation/Attempt/Outcome 和 Candidate Head 分层：unknown 只结束 Attempt 并让 Invocation 进入 reconciling；成功 Outcome 全局唯一；repair 以 expected Candidate Head hash CAS；stale 保留旧 Revision。不得用 Workflow 状态替代这些 Record。

Gate 5 的 UI typed change 若不对应模型 ReviewIssue，Backend 只能按 `3002` 的 `storyboard-human-change-review-aggregate-v1` 创建 `StageCandidateRevision(origin=aggregate)`：producer 精确绑定 Gate 5 NodeRun、单 issue ShardManifest、ReviewDecision、目标 Candidate 和 allowlist roots；不能伪造 StageVariant 或把自由文本直接提升为 Patch 权限。

### 10.1 持久 Record

```text
StoryGraphVersionRecord {
  version_id,
  workspace_id / project_id / version_no,
  parent_version_id / parent_content_hash,
  schema_id / schema_rank / schema_manifest_hash,
  verified_coverage_proof,
  coverage_phase / coverage_scope_manifest_hash,
  node_key_derivation_id / edge_key_derivation_id,

StoryGraphHeadRecord {
  workspace_id / project_id,
  current_version_id / current_content_hash,

  head_revision / head_content_hash

```

Version 不可变、Head 单线。Version 不复制 Candidate、Decision、Receipt、Packet、Provider/Workflow/Canvas 状态；`exact_owner_collections[]` 和 Coverage Proof 足以重建投影输入。v1→v2 只在线性 Head 上切换一次，v2 后禁止降级。

### 10.2 Prepare 与 Publish

`CompileStoryGraphVersionCommand` 携带 schema identity、scope sets、expected Owner heads/collection roots、expected Graph Head 和 idempotency key。执行分两步但发布条件原子：

1. Prepare 在一个 `REPEATABLE READ` 只读事务中由各 Owner adapter 构建完整 CompilerInputSnapshot，验证 Receipts/Coverage，并在事务外以内存纯函数编译 nodes/edges/hash；
2. Publish 短事务按统一 owner rank 锁全部输入 Scope Heads，最后锁 Graph Head，重算/比较 exact Collection roots 与 Receipts，验证 Compiler output hash；
3. 若任何 Owner 或 Graph Head 漂移，丢弃准备产物并返回 stale；
4. 若全等，插入 Version、CAS Head，并在同一事务写 Command Receipt/Outbox `StoryGraphVersionPublished`。

Publish 使用 PostgreSQL `SERIALIZABLE` 和 GORM `clause.Locking`；不得在事务内等待 Codex、Provider、Kafka、Elasticsearch 或对象存储。唯一/CAS/序列化冲突整体回滚，不留孤立 Version 或分叉。Compiler 不拥有上游事实，不能按 Evidence overlap、名称、当前版本或图像相似度补对象/边。

Owner Apply 先提交，Graph 后编译。Graph 失败只让 Lens/Search 暂时落后并显式显示 stale/degraded，不回滚已提交 Owner 事实，也不阻断 Guided Studio 读取 Owner View。

## 11. 写事务锁序与并发

所有会消费Agent Candidate的事务统一锁序：

1. current `SkillReleaseControlHead`；
2. module/coordinator command dedup row；
3. exact ReviewDecision/Human subject审计行；
4. Owner Scope Heads，按固定owner rank再按 `(version_family, scope_kind, scope_key UTF-8)` 排序：
   `production/script < production/project < production/bible < production/planning < asset < preset < production/reference < production/storyboard < production/storygraph`；
5. Owner内部exact member/ArtifactReadiness行，按主业务key排序；
6. immutable Generation CandidateSelection行（只验exactref/hash，不改写）；
7. Collection Receipt唯一键、Command Receipt；
8. Outbox。

不消费 Agent 的 Source/Provider 管理命令从第 2 步开始。Control 状态转换只锁 Control Head，不反向锁业务 Owner，因此不会与 Apply 形成逆序。Graph Compiler 从 command dedup 后先锁排序后的 Owner Heads，最后锁 StoryGraph Head，不锁 Review/Agent Candidate。

Gate1两个命令是有序独立事务；Gate2/3和Composition选择是同数据库多Owner协调事务；Gate4基础结果可渐进提交；Gate5按Scene单事务。事务不得跨网络边界。

expectedHeads必须覆盖所有将写的Scope Head；漏一个即Schema invalid。读取依赖的exactOwner Version是不可变时无需行锁；ArtifactReadiness、Release Control等可变安全状态必须在写入前锁定并复验。任何late result或并发命令只能通过CAS/unique constraint失败，不能last-write-wins。

## 12. 结构 Rebase 与局部失效

`StructureRebaseVersionRecord`只由已接受的新StructureIdentitySet产生，保存：

- old/new Structure roots；
- old scope→`retained|split|merged|deleted`→new scopes完整映射；
-受影响Episode/Scene、Mention/Identity、Planning members；
-supersededOwner refs与replacementrefs；
-rebasecontract/hash和creator decision audit。

Planning在Gate2同一事务应用rebase，未映射或多义映射整体失败。Rebase Receipt只在非空时存在。旧Owner Version、Packet、Candidate、Decision和Graph永久保留；相关Head前进，下游用exact依赖闭包标stale。

| 变化 | stale闭包 | 不应stale |
|---|---|---|
| Source slice | 相关Span/Fact/Identity/P0及下游 | 未引用slice的历史版本 |
| Scene split/merge | 相关Scene、邻接continuity、Reference/Storyboard | 无共享依赖Episode |
| Identity merge/split | 该Identity所有State/Occurrence/Reference/Shot | 无关Identity |
| State/Interaction | 相关Binding/Packet/Shot | 无关基础Identity |
| Preset/Policy | Gate3后Brief/Reference/Packet/Shot | P0事实 |
| AssetVersion/Selection | 引用它的Binding/Packet/Shot | 未引用版本 |
| CandidateRepair | 当前Review/Decision/下游Candidate | Owner上游事实 |
| 其他Scene Graph更新 | Gate5 scene semantic revalidation | exact语义未变的已批准Scene Candidate |

StalenessRecord 必须保存 cause ref/hash、source revision、affected stage/scope/owner roots、closure contract/hash 和 created_at；它是执行/查询状态，不改旧 Version hash。Owner Head 前进本身不自动让无依赖对象 stale，必须由显式 dependency/impact closure 证明。

## 13. 状态分层与失败语义

| 状态层 | 表达内容 | 禁止冒充 |
|---|---|---|
| WorkflowRun/NodeRun | 编排推进、等待、恢复 | Candidate/Owner readiness |
| Invocation/Attempt/Outcome | 模型执行与结果可确认性 | 业务通过 |
| Candidate Revision/Head | 当前候选与 Repair lineage | 正式事实 |
| HumanTask/ReviewDecision | 人工审核 | Owner Apply 已提交 |
| Owner Version/Head/Receipt | 已提交业务事实 | Workflow 完成 |
| typed View | 查询时 ready/blocked/stale | 新业务 Record |
| StoryGraphVersion/Head | 已发布投影 | 上游 Writer |

稳定失败码至少包括：

| code | 处理 |
|---|---|
| `owner_expected_head_conflict` | 返回当前 exact Head，不覆盖 |
| `owner_collection_incomplete` | 返回缺失 family/scope/member，不写 Receipt |
| `owner_collection_root_mismatch` | Adapter 重算不等，fail closed |
| `owner_checkpoint_not_allowed` | Owner/family/checkpoint 不在 Schema Manifest，拒绝 |
| `idempotency_payload_conflict` | 同 key 异参，拒绝且不返回旧成功为本次结果 |
| `review_subject_stale` | Decision subject/Candidate Head 漂移，旧 Decision 不可 Apply |
| `skill_release_control_blocked` | release 被 quarantine/revoke，拒绝 Outcome/Candidate/Apply |
| `production_world_partition_incomplete` | Gate 2 三 partition/key/ref 不闭合，整体回滚 |
| `scene_scope_identity_mismatch` | Planning Scene 未复用 Gate 1 reserved logical id，拒绝 |
| `reference_target_coverage_invalid` | expected/actual Target key 不全等，Gate 3 回滚 |
| `reference_selection_not_ready` | CandidateSelection/Artifact/Rights/Lineage 不合法，不发布结果 |
| `reference_checkpoint_incomplete` | required Target 未闭合，不写 Gate 4 Receipt |
| `scene_packet_input_stale` | Packet exact roots 不再 current，拒绝创建 Invocation |
| `storyboard_input_stale` | Gate 5 scene semantic root 变化，旧 Decision 不可用 |
| `storyboard_apply_conflict` | Scene baseline/head 争用，全 Scene 回滚 |
| `storygraph_compile_input_stale` | Owner collection 或 Graph Head 漂移，丢弃 prepare 结果重算 |
| `attempt_runtime_unknown` | 保持同 Invocation reconciling，不建第二业务身份 |
| `outbox_commit_failed` | 与 Owner 事务一起回滚，不出现无事件正式事实 |

Owner 命令成功但 Workflow 未收到响应时，Workflow 以同 idempotency key 读取同一 Command Receipt/Collection Receipts 后 Resume；不得重做 Owner Apply。Kafka/Search/Compiler 消费失败不改变 Owner 成功事实。

## 14. GORM 与数据约束

1. 所有业务 Writer 使用同一 `DATABASE_URL`、同一 PostgreSQL 和唯一 GORM Catalog；
2. 实施只在新 Plan 首个 Red 测试需要时增加具体 Model，不为本文表格一次性预建全部表；
3. 具体 Version 表至少有 workspace/project/logical/version/revision/parent/hash 唯一约束，具体 Head 表有 scope 唯一约束和 revision；
4. Command/CollectionReceipt、Candidate revision、SkillRelease root、StoryGraph version/head 均有相应唯一/CAS 约束；
5. JSONB 只用于严格 Version payload、Ref 数组、Schema/Graph/Packet 前像；每份 JSONB 旁必须保存 contract id/schema hash/content hash 并在读写重验；
6. Domain/Compiler/Application/HTTP 不导入 GORM；Adapter 实现 transaction-scoped port；
7. 不写 Raw SQL、DDL、Migration 文件、第二 ORM、第二 Schema/DSN 或业务触发器；锁、唯一、关联和事务使用 GORM API/Clause/Tag；
8. Owner 事务不等待 Codex、Provider、Kafka、Elasticsearch 或对象存储；
9. Secret 不进入 Owner/Packet/Graph/Outbox/log；Generation 凭据边界由 `VP-D10` 同步；
10. Backend 测试只位于 `backend/tests`，Agent 跨语言 Schema/fixture 位于 `agent/tests`。

所有 Command/Query 在 Application 边界先完成 Workspace membership/role authorization，并把 actor/audit identity 写入 Command Hash/Receipt；所有具体 Record、唯一键、关联和查询谓词都带 `workspace_id/project_id`。任何 exact ref 的租户、Project、Owner/family 与目标 scope 不等价都在进入 Repository 写入前以 `cross_scope_reference_forbidden` 拒绝，不能靠数据库全局 UUID 唯一性放行。

若真实 PostgreSQL 约束无法由当前 GORM 策略可靠表达，必须在 `VP-D14`/Plan 中显式调整设计或工具链；不能静默退化为应用层 best effort 并报告通过。

- `StoryboardFormalSetCommitted`；
- `StoryGraphVersionPublished`。

Event envelope 保存 event id、workspace/project、owner kind、aggregate/version/revision/content hash、command receipt ref 和 occurred_at，不复制完整原稿、图片 bytes、Prompt 或 Secret。Publisher 至少一次；Consumer 以 event id + owner revision fencing 幂等。Kafka 不调度 Owner 命令，Temporal 继续拥有 Timer/Retry/Signal。Search 和 Lens 可由 PostgreSQL Owner snapshot 重建，旧乱序事件不能覆盖新 revision。

事件发布/消费不是 Owner 事务成功的前置网络调用：Outbox row 与 Owner 同事务提交，publisher 异步发送。Poison message 进入 DLQ；Search 不可用返回 degraded，不回写 Owner。

## 16. 原子迁移策略

新实现由 `VP-D15` 唯一 Plan 编号；顺序必须形成小闭环：

1. 先建立 OwnerRef/ScopeHead/CommandReceipt/CollectionReceipt/CollectionAdapter 跨语言/数据库合同与拒绝测试；
2. 按 P0 family 逐个建立具体 Record/Head/Adapter 和 Gate 1/2 命令，不一次预建 P1–P3 空表；
3. 接入 StoryGraph v2 Compiler prepare/publish 和 p0 完整旅程；
4. 建立 Preset/Reference Plan、基础/组合结果和 Packet typed Query；
5. 建立 `direct_storyboard` 持久输入、Gate 5 Owner Apply 和 p3 Compiler；
6. 在对应 phase cutover 中让新 Workflow 只写新 Owner 链；
7. 旧 v1/Bible-first/Draft/Detail 记录只读保留并由精确旧 runtime 恢复；引用归零后独立删除旧 caller/schema，不双写、不 fallback。

每个任务 Red → Green → Refactor、定向真实 PostgreSQL 测试、相称全量 CI、Acceptance Evidence 和独立提交。旧 `SG-Ixx` 证据只保留历史，不证明新 Record/Receipt/Query 合同。

## 17. 验收边界

未来 Acceptance 至少证明：

1. 13 个 StoryGraph v2 family 与具体 ScopeHead/CollectionAdapter registry 一一对应，checkpoint/owner/family/scope/empty 策略由 Schema Manifest 机械拒绝非法组合；
2. 五个 P0 Owner 的具体 Version/Fragment/Head 可重建七个 family；正常空 rebase 有 canonical empty Head/Collection，但无 StructureRebaseVersion/Receipt；
3. Gate 1 Project → Bible 有序两事务可恢复；Project 成功/Bible 失败重试只复用同一 Episode refs；
4. Gate 2 Bible/Planning/Asset 同一真实 PostgreSQL 事务原子提交，每 Episode 独立 CollectionReceipt，故障注入不留半份事实；
5. Version → Collection → CollectionReceipt → CommandReceipt → Outbox 单向 Hash 可离线重算，无环、无到达顺序差异；
6. 同 idempotency key/hash 重放同一 Receipt，同 key 异参冲突；并发 expected Head 只有一个成功，无 lost update；
7. Gate 3 Preset/Reference 双 Owner 原子发布，expected Target key 与 p0 机械结果全等；Preset 变化不改 P0；
8. identity anchor 先发布，Appearance 才可消费；基础/组合结果可渐进发布，但 required 未闭合时无 Gate 4 Receipt；
9. Scene/Interaction Binding 和 Asset Composition 两个 family 按 Scene 同事务闭合，selected Artifact/AssetVersion/Rights/Lineage 逐项精确；
10. Packet 和 Execution Materialization 只由 typed Query 构建并完整保存到 Invocation，不存在 Packet 业务表、项目资产搜索或 current/latest 读取；
11. Gate 5 每 Scene 一次事务创建完整 formal Shot set、每 Shot 一个 ProductionBinding、一个 CollectionReceipt 和一个 CommandReceipt；
12. 无关 Scene Graph 更新可通过严格 scene semantic revalidation，本 Scene 任一 exact 输入变化拒绝旧 Decision；
13. Agent Release quarantine/revoke 在 Invocation/dispatch/Outcome/Candidate/Apply 统一 fence，unknown/late result 不产生 Owner 事实；
14. Compiler 输入在发布事务重算 OwnerCollections/Receipts/Coverage，v2 Version/Head/Outbox 原子且无孤立/分叉/降级；
15. 一个完整多集剧本从 source、Identity/State/Interaction、Preset、人物多形象三视图、地点/道具、人物拿道具组合、两个相邻 Scene 分镜到 v2 p3 Graph 全链可反查；
16. 所有 Query View 带 exact ReadSetProof 且可从 Owner 重建，Search/Graph 落后不阻断 Guided Studio Owner View；
17. 实现没有通用 Owner JSON/EAV、全局 ApplyCandidate、Raw SQL、第二 ORM/DB、Agent 写库、Kafka 命令或 Secret 泄露。
