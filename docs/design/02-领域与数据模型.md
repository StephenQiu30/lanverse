## 1. 设计决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 一个业务库，**按限界上下文分 schema**（`identity`、`workspace`、`script` …） | 模块化单体：边界清晰、可单独迁移与授权；将来拆服务时按 schema 拆库 |
| D2 | 主键使用 **UUIDv7**，由应用生成 | 时间有序，索引局部性好；前端、工作流、幂等键可提前拿到 ID |
| D3 | 枚举用 `text + CHECK`，不用 PostgreSQL `ENUM` | 增加取值只需迁移 CHECK，不锁表、可回滚 |
| D4 | 时间统一 `timestamptz`（存 UTC）；时长统一 `integer` 毫秒（`*_ms`） | 与 REQ-02 I18N-02 一致；避免浮点误差 |
| D5 | 金额统一 `bigint` **微元**（1 元 = 1,000,000，`*_micros`），界面显示到分 | LLM 按 token 计费的单次金额常低于 1 分；整数避免浮点误差 |
| D6 | **“头 + 版本”模式**：可变身份放头表（含 `revision` 乐观锁），不可变内容放版本表 | 满足 REQ-02 REL-05 版本不可变、REL-06 并发修改 |
| D7 | 选定与锁定是**头表上的指针**，同时写一条只追加的历史记录 | 查询当前选定只需一次读取；历史可审计 |
| D8 | 跨上下文只存对方 ID，**不建跨 schema 外键**；同一 schema 内建外键 | 保持上下文可拆分；一致性由命令层与事件保证 |
| D9 | 结构不稳定、只整体读写的数据用 `jsonb`（模型参数、参数表单定义、质检结果），并在应用层按 schema 校验 | 模型参数随供应商变化；避免频繁迁移 |
| D10 | 所有业务表带 `project_id`（组织级表带 `org_id`）；MVP 固定一个组织 | DES-01 §3.3 |
| D11 | **所有表统一带 `is_delete` 逻辑删除标志**；项目与媒体另有 `delete_time`、`purge_after` 支持 30 天回收；版本内容仍靠“新版本”表达修改，不靠删除 | 产品负责人要求（2026-09-25）；REQ-01 PRJ-06、MED-03 |
| D12 | 高增长的只追加表（审计、Outbox、调用明细）按月**分区** | 便于按保留期删除分区（REQ-02 DAT-03） |

## 2. 通用约定

### 2.1 命名

- schema、表、列使用 `snake_case`；表名单数（`shot`、`shot_version`）。
- 外键列 `<对象>_id`；指向版本的列 `<对象>_version_id`；布尔列 `is_*` / `has_*`。
- 索引 `ix_<表>_<列>`，唯一约束 `uq_<表>_<列>`，检查约束 `ck_<表>_<含义>`。

### 2.2 必备列与通用列

**必备列（所有表都有，无例外）**：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid PRIMARY KEY` | UUIDv7，应用生成；按月分区表为 `PRIMARY KEY (id, create_time)` |
| `create_time` | `timestamptz NOT NULL DEFAULT now()` | 创建时间 |
| `update_time` | `timestamptz NOT NULL DEFAULT now()` | 最后修改时间；每次 `UPDATE` 由仓储统一设置（并有触发器兜底） |
| `is_delete` | `boolean NOT NULL DEFAULT false` | 逻辑删除标志 |

**通用列（按需出现）**：

| 列 | 类型 | 出现在 |
| --- | --- | --- |
| `project_id` | `uuid NOT NULL` | 所有项目级表 |
| `org_id` | `uuid NOT NULL` | 组织级表 |
| `create_by` / `update_by` | `uuid` | 由用户操作产生或修改的表（系统产生时为空） |
| `revision` | `integer NOT NULL DEFAULT 1` | 头表；每次修改 +1；命令携带 `expected_revision` |

**`is_delete` 使用规则**：

1. 所有查询默认追加 `is_delete = false`（仓储基类统一处理，GORM 使用自定义 Scope，不使用 GORM 自带的 `DeletedAt`）。
2. 业务唯一约束、常用索引一律写成部分索引 `… WHERE NOT is_delete`，保证删除后可以重建同名对象。
3. 版本表、只追加表（`*_version`、`reference_version`、`dialogue_audio`、`ledger_entry`、`audit_log`、`outbox` 等）的内容列不允许更新；`is_delete` 只在项目彻底清理时由清理任务置位，`update_time` 同步更新。
4. 删除头表对象（如镜头）时，只置位头表的 `is_delete`；其版本行保留，供历史与审计查询。
5. 物理删除只发生在：项目回收期满清理、分区表过期分区删除、`processed_event` / `idempotency_record` 过期清理（§9）。

### 2.3 通用枚举

| 名称 | 取值 |
| --- | --- |
| 审阅状态 `review_status` | `candidate`（待确认）· `confirmed`（已确认） |
| 任务状态（界面） | 见 REQ-03 §6.5；数据库使用 §7 的 Operation 内部状态 |
| 服务区域 `region` | `domestic` · `overseas` |
| 输入用途 `input_role` | `prompt` · `first_frame` · `last_frame` · `subject` · `scene` · `prop` · `style` · `motion` · `camera` · `audio` · `source` |
| 引用类型 `ref_type` | `reference_version` · `media_asset` · `dialogue_audio` · `operation_output` · `style_preset` · `text` |

## 4. 版本、选定与依赖模式

### 4.1 头 + 版本

```text
shot（头）                     shot_version（版本，只插入）
  id, revision                   id, shot_id, version_no, 内容字段…
  current_version_no ──────────→ (shot_id, version_no) 唯一
  selected_take_output_id        create_time, create_by
```

**修改流程**（一个事务）：

1. `SELECT … FROM shot WHERE id = $1 FOR UPDATE`；`revision` 不等于 `expected_revision` → 返回冲突。
2. 插入 `shot_version(version_no = current_version_no + 1)` 及其子表（`shot_line`、`reference_item`）。
3. 更新头表 `current_version_no`、`revision = revision + 1`、`update_time`。
4. 写 `lineage.dependency`（新版本的上游）与 `infra.outbox`（`storyboard.shot_version_created`）。

使用此模式的对象：`script_version`（无头，天然不可变）、`episode_structure`、`reference_version`、`shot_version`、`model_profile_version`、`price_rule_version`。

### 4.2 选定与锁定

- 选定指针在头表：`shot.selected_frame_output_id`、`shot.selected_take_output_id`、`reference_slot.current_version_id`、`line_audio_selection.dialogue_audio_id`。
- 选定命令携带 `expected_revision`，更新指针与 `revision`，同时插入历史（`shot_selection_log`、`reference_version` 本身即锁定历史）。
- 被选定的 `operation_output` 必须 `moderation_status = 'passed'`，且其 Operation 状态为 `completed`。

### 4.3 稳定键（跨版本的同一对象）

剧本结构每次修改都产生新的 `episode_structure` 版本和新的行，但分镜需要引用“同一句台词”。因此：

- `scene.scene_key`、`dialogue_line.line_key` 为稳定 UUID：新版本中未改变身份的场与台词沿用原键，新增的生成新键，拆分时一方沿用、另一方新键。
- `dialogue_line.content_hash` = hash(说话人, 文本, 情绪)。新版本中同一 `line_key` 的 `content_hash` 变化即视为该台词被修改。
- `shot_line` 引用 `line_key`（而不是行 ID），配音选定 `line_audio_selection` 也以 `(episode_id, line_key)` 为键。

### 4.4 依赖与过期

```text
lineage.dependency
  downstream_type  shot_version | reference_version | dialogue_audio | operation_output
  downstream_id    下游版本 ID
  upstream_type    dialogue_line | reference_version | shot_version | dialogue_audio | operation_output | voice_profile
  upstream_key     上游稳定键（line_key / reference_slot_id / shot_id / (episode_id,line_key) …）
  upstream_version 下游创建时所依赖的上游版本号或 content_hash
```

- **登记**：下游版本创建时，把它读取的每个上游（稳定键 + 当时的版本）写入 `dependency`。
- **传播**：上游产生新版本或新选定时发出事件；`lineage` 消费者查询 `upstream_key = 该键 AND upstream_version <> 新版本` 的下游，为其**当前生效的对象**写入 `stale_mark`，再沿依赖递归（递归 CTE，深度上限 6）。
- **清除**：下游重新产生新版本（依赖已是最新）时，旧对象的 `stale_mark.cleared_at` 置位。
- 过期只是标记，不修改任何业务数据（REQ-01 LIN-01）。

## 5. 表设计

以下 DDL 为设计稿，迁移脚本以此为准；省略了 §2.2 的通用列时以 `-- 通用列` 注明。

### 5.1 identity

```sql
CREATE TABLE identity."user" (
  id                    uuid PRIMARY KEY,
  org_id                uuid NOT NULL,
  login_name            citext NOT NULL,
  display_name          text NOT NULL CHECK (char_length(display_name) BETWEEN 1 AND 50),
  role                  text NOT NULL CHECK (role IN ('admin','producer')),
  status                text NOT NULL DEFAULT 'active' CHECK (status IN ('active','disabled')),
  password_hash         text NOT NULL,                 -- bcrypt(cost 12)
  must_change_password  boolean NOT NULL DEFAULT true,
  password_changed_at   timestamptz,
  failed_login_count    integer NOT NULL DEFAULT 0,
  locked_until          timestamptz,
  session_epoch         integer NOT NULL DEFAULT 1,    -- 禁用 / 重置 / 改密时 +1，使全部会话失效
  last_login_at         timestamptz,
  create_time      timestamptz NOT NULL DEFAULT now(),
  update_time      timestamptz NOT NULL DEFAULT now(),
  is_delete        boolean NOT NULL DEFAULT false
);
CREATE UNIQUE INDEX uq_user_login_name ON identity."user" (org_id, login_name) WHERE NOT is_delete;
```

会话存 Redis（`sess:{token_hash}` → user_id、session_epoch、过期时间），不落库；校验时比较 `session_epoch`（REQ-01 ACC-03）。

## 8. 数据量估算

以 REQ-02 §0.2 基准（1 项目 100 集 × 150 镜头）估算单项目规模：

| 表 | 行数 | 说明 |

| `reference_item` | 约 30 万 | 每版本约 5 项 |
| `operation` | 约 8 万 | 视频约 4 次 / 镜，关键帧、TTS、LLM 另计 |
| `operation_output` | 约 20 万 | 多候选 |
| `media_asset` | 约 25 万 | 含上传与生成结果 |

## 10. 迁移约定

1. 使用 golang-migrate，文件 `backend/migrations/<yyyymmddhhmm>_<说明>.up.sql / .down.sql`；每个迁移只做一件事。
2. 生产禁止 GORM AutoMigrate（REQ-02 MNT-04）。
3. **向前兼容一个版本**（REQ-02 DEP-03）：加列先可空 → 回填 → 加约束；删列分两次发布（先停用，再删除）；重命名用新增 + 双写 + 切换。
4. 大表加索引使用 `CREATE INDEX CONCURRENTLY`（单独迁移，不在事务中）。
5. 分区表由定时任务提前创建未来 3 个月的分区。
6. CI 在空库与上一发布版本的库上各执行一次全部迁移。

## 11. 仓储实现约定

- GORM 模型只在 `adapter/persistence` 中定义；领域对象与 GORM 模型显式转换（DES-01 §3.3）。
- 头表更新统一使用 `UPDATE … SET revision = revision + 1 WHERE id = ? AND revision = ?`，影响行数为 0 即冲突。
- 命令事务边界在应用层用例：业务写入 + `lineage.dependency` + `infra.outbox` + `audit`（经 Outbox）同一事务。
- 列表查询一律 keyset 分页；禁止 `OFFSET` 深分页。
- 递归查询、报表使用 Raw SQL，并有集成测试（testcontainers）。

## 12. 数据库层保护

| 保护 | 实现 |
| --- | --- |
| 版本表内容不可改 | 应用账号对 `*_version`、`reference_version`、`dialogue_audio`、`ledger_entry`、`audit_log` 只授予 `INSERT, SELECT` 与 `UPDATE (is_delete, update_time)` 列级权限；迁移账号另设 |
| `update_time` 自动维护 | 每张表 `BEFORE UPDATE` 触发器 `set_update_time()` 兜底 |
| 项目画幅与风格不可改 | `BEFORE UPDATE` 触发器：`aspect_ratio`、`style_type` 变化即报错 |
| 预算不超支 | `ck_budget_balance` |
| 每个活跃凭据唯一 | `uq_provider_credential_active` |
| 连接 | 应用使用 PgBouncer（事务模式）；Temporal 使用独立库与账号 |
