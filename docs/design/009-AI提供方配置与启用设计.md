- 状态：accepted（2026-08-12 用户要求继续拆分 PRD、Plan 与验收标准；实现仍须按对应 DEV 门禁执行）
- 日期：2026-08-12
- 覆盖范围：Workspace 级 AI 提供方预设、配置、凭据、连通性检查、模型绑定、启停与运行时快照
- 关联文档：[AI 供应商与合规准入](./005-AI供应商与合规准入设计.md)、[生产模块详细设计](./模块设计/009-生产模块详细设计.md)、[数据库表与数据生命周期详细设计](./模块设计/011-数据库表与数据生命周期详细设计.md)

## 1. 结论与设计决定

Lanverse 建立一个 Workspace 级 Provider 管理控制面，借鉴 CC Switch 的“预设填充、配置数据库事实源、保存与启用分离、模型发现、连通性检查和快速切换”，但不引入它面向本机应用的配置文件代理、协议转换网关或明文凭据存储。

2026-08-12 用户在审阅本设计后要求继续形成 PRD、执行 Plan 与验收标准，视为接受 §12 的六项产品决定。下游需求、产品任务和工程执行分别以 [REQ-014](../requirement/014-AI提供方配置与启用需求.md)、[PRD-011](../prd/011-AI提供方配置与启用PRD.md) 和 [PLAN-011](../plan/011-AI提供方配置与启用执行计划.md) 为准；Design accepted 不代表功能已实现或任何 Provider 已通过真实执行验收。

本设计固定以下边界：

1. ProviderPreset 是随代码发布、无密钥、带版本的静态目录；ProviderConnection、加密 CredentialVersion、ProviderBinding 和 HealthCheck 才是 PostgreSQL 中的 Workspace 事实。
2. “已保存”“凭据有效”“连接健康”“模型契约可用”“已启用”是不同事实。保存 API Key 不会自动激活模型；只有既有 `ModelCapability.status=active`、真实 Provider 契约已验收、健康检查通过时，owner 才能为业务用途启用绑定。
3. 启用对象不是笼统的 Provider 开关，而是 `(workspace_id, usage_type)` 的唯一当前绑定。MVP 的用途固定为 `script_structure`、`image_generation`、`video_generation`，同一用途同时最多一个 active 绑定。
4. API Key 以应用层 AES-256-GCM 信封加密后入库；主密钥只来自部署 Secret/KMS，不进入数据库、日志、响应、备份或前端状态。更新凭据只追加新版本，不覆盖历史版本。
5. 新任务在创建时固定 binding、connection、credential、capability 和 adapter 版本；切换 Provider 或轮换 Key 不改变运行中任务，也不触发隐式重试或重复计费。
6. 当前 DeepSeek 文本适配器可在本设计实施后迁移为首个真实绑定；火山方舟 Seedream/Seedance 仍受 D-004 真实账号契约门禁约束，录入 Key 不能把不可用能力变成 active。
7. MVP 不做自动故障转移。跨 Provider 的价格、提示词语义、输出结构和外部副作用不同，自动切换可能重复计费或改变结果，必须另行设计。

本设计接受后，需要同步修改生产模块中“密钥不入库记录”的旧不变量：新的准确表述应为“Provider 凭据不得明文入库；密文只由受控凭据端口解密，业务实体、API、日志和审计均不得持有明文”。

## 2. 当前事实与 CC Switch 参考边界

### 2.1 Lanverse 当前事实

- `DEEPSEEK_API_KEY` 和 `ARK_API_KEY` 当前从服务端环境配置注入；DeepSeek 文本实现固定连接官方接口，尚无 Workspace 级配置事实。
- `ModelCapability` 已保存 provider、model、kind、配置版本、参数、限制、价格和可用状态；它适合作为可执行模型契约，不应再复制一套“配置了 Key 就可用”的平行能力目录。
- 火山方舟的两条内置图片/视频能力保持 `provider_contract_unverified`。D-004 未关闭前，即使存在 Key 也必须 fail closed。
- 现有 Workspace 角色为 owner、editor、viewer；Provider 配置、凭据、启停和轮换属于 owner 权限。其他成员只通过业务 API 读取脱敏后的能力可用性。
- 当前数据库结构来源是 SQLAlchemy Model，只接受空库初始化，没有存量数据库在线迁移框架。新增表不能被描述为已支持生产存量升级。

### 2.2 可借鉴的公开事实

CC Switch 官方文档公开了以下设计：

- 新增 Provider 时可选择内置预设，自动填充名称和 API 地址，用户补充 API Key；同时支持通用/自定义 Provider。
- SQLite 是 Provider 配置的单一事实源，应用配置由数据库同步生成；Provider、endpoint 和健康状态分表保存。
- Provider 卡片明确区分保存、编辑与启用，并提供多 endpoint、模型列表获取和健康检查。
- v3.8 的数据库升级使用显式 schema version 和事务，而不是把配置文件与数据库同时作为无优先级事实源。

### 2.3 明确不照搬的部分

CC Switch 是本机桌面配置切换器，Lanverse 是多 Workspace 后端，两者的信任边界不同。其官方仓库有公开 issue 报告 API Key/Token 以明文 JSON 出现在 SQLite 与备份中；无论该 issue 后续如何处理，Lanverse 都不能接受明文凭据落库或随备份导出。[公开安全问题 #1108](https://github.com/farion1231/cc-switch/issues/1108)

以下能力不进入本设计：

- 修改 Claude Code、Codex 等本机配置文件；
- 在不同协议之间建立通用代理或请求转换层；
- 复用个人订阅、OAuth 登录态或第三方客户端 Token；
- 自动故障转移、负载均衡、多 endpoint 自动测速选路；
- 从备份导出明文凭据；
- 仅凭 `/models` 返回值就自动创建 active ModelCapability。

## 3. 预设目录

### 3.1 预设不是运行时能力

预设只描述公开且可版本化的接入元数据：

| 字段 | 约束 |
| --- | --- |
| preset_id / catalog_version | 稳定 ASCII ID；任何默认值或认证契约变化必须升级目录版本 |
| display_name / official_docs_url | 展示名与官方文档；不依赖第三方整理页 |
| protocol | `openai_compatible`、`anthropic_native`、`gemini_native`、`ark_native` 中的已实现枚举 |
| credential_schema_id | MVP 只接受受控的 API Key/Bearer Key schema，不接受任意 JSON 或自定义 Header 名 |
| endpoint_templates | 按地域提供经过官方文档复核的 HTTPS 模板；不含用户凭据、query、fragment 或 userinfo |
| model_discovery | 受控的模型列表策略；不支持时明确为 `unsupported` |
| capability_hints | 仅用于 UI 分类，不代表 `ModelCapability` 已通过真实契约验收 |
| verified_at | 官方接入资料复核日期；过期只提示复核，不静默改写已有 Connection |

官方端点和认证方式是时效性数据。实施时必须从各平台官方文档生成固定目录测试；目录升级不会直接修改用户已经保存的 endpoint，owner 必须显式接受升级或继续使用旧版本。

首批目录以当前短剧生产链路和常见接入需求为限，不追求复制 CC Switch 的全部平台：

| --- | --- | --- | --- | --- |
| deepseek | DeepSeek | OpenAI-compatible | 文本、剧本结构化 | 迁移现有适配器并通过真实回归后可用 |
| volcengine_ark | 火山方舟 | Ark native | 文本、图片、视频 | 目录可配置；Seedream/Seedance 继续被 D-004 阻断 |

| google_gemini | Google Gemini | Gemini native | 文本、多模态、图片、视频 | catalog-only，待认证与窄适配器契约 |
| alibaba_bailian | 阿里云百炼 | OpenAI-compatible | 文本、多模态、图片、视频 | catalog-only，endpoint 必须绑定地域 |

`catalog-only` 表示用户可以预先录入并验证凭据，但不得用于生产任务。每个平台只有在出现真实业务用例时才增加一个窄 Adapter、一个受控 ModelCapability 和一组真实账号契约测试，禁止预建万能 Provider SDK 层。

## 4. 事实模型

### 4.1 最小新增实体

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| ProviderConnection | id、workspace_id、preset_id/catalog_version、display_name、protocol、region、base_url、non_secret_config、configuration_status、revision、created_by/updated_by、archived_at | Workspace 隔离；只存非敏感配置；preset 升级不静默覆盖；归档代替物理删除 |
| ProviderCredentialVersion | id、workspace_id、connection_id、version、key_id、nonce、ciphertext、auth_tag、fingerprint_hmac、status、created_by、created_at、retired_at | 明文永不落库；版本只追加；一个 Connection 最多一个 current；fingerprint 不返回客户端 |
| ProviderBinding | id、workspace_id、usage_type、connection_id、credential_version_id、capability_id/config_version、binding_revision、status、activated_by/at、deactivated_by/at | `(workspace_id, usage_type)` 最多一个 active；引用的版本不可变；切换以事务完成 |
| ProviderHealthCheck | id、workspace_id、connection_id、connection_revision、credential_version_id、probe_type、status、latency_ms、safe_error_code、checked_by/at、expires_at | 只追加；不存请求/响应正文；旧配置检查不能证明新 revision 健康 |

ProviderPreset 不建表。它是代码中的受版本控制目录，避免数据库里出现可被普通管理 API 篡改的官方认证规则。`ModelCapability` 继续是模型参数、价格、输入输出和真实可用性的唯一契约；ProviderBinding 只选择某个 Workspace 用哪条 Connection 执行该 Capability。

### 4.2 运行时快照

创建 ExtractionBatch 或 GenerationRequest 时，在同一事务读取 active ProviderBinding，并固定以下非敏感引用：

- provider_binding_id / binding_revision；
- provider_connection_id / connection_revision；
- provider_credential_version_id；
- capability_id / config_version；
- adapter_contract_version；
- 规范化 endpoint/model/region 的 snapshot hash。

Worker 只能根据这些引用经 `ProviderCredentialPort` 临时取得明文凭据，并在外部调用结束后释放内存引用。RabbitMQ、Outbox、Task API、Attempt API 和日志均不得携带明文凭据或完整非公开 Provider 响应。

凭据轮换后，旧版本进入 `retiring`；已有非终态任务仍可解密，所有引用任务终结或达到明确的人工撤销门禁后才能变为 `revoked`。如果 owner 选择立即撤销，受影响任务进入类型化失败/人工处理，不允许自动改用新 Key 重发。

~~~mermaid
flowchart LR
    P["代码内 ProviderPreset"] --> C["Workspace ProviderConnection"]
    C --> K["加密 CredentialVersion"]
    C --> H["HealthCheck"]
    M["已验收 ModelCapability"] --> B["ProviderBinding"]
    K --> B
    H --> B
    B --> R["新请求的不可变运行时快照"]
    R --> A["Provider Adapter / Attempt"]
~~~

## 5. 状态、保存与启用

ProviderConnection 不使用一个含义模糊的 `enabled` 布尔值。管理页组合展示三条正交状态：

- configuration_status：`incomplete | valid | invalid`；
- health_status：由最新未过期检查投影为 `unchecked | healthy | degraded | unreachable`；
- usage bindings：每个 usage_type 显示 `unavailable | inactive | active`。

保存流程只验证字段、加密凭据和写入审计，不执行生产调用。健康检查是显式命令，优先调用无计费的官方模型列表/元数据接口；平台没有安全探针时，必须显示“不支持无副作用检查”，不能发送生成请求冒充连通性检查。

启用事务固定执行：

1. 锁定目标 Connection 与该 Workspace/usage_type 的当前 Binding，校验客户端提交的 expected revision。
2. 校验 Connection 非归档、配置完整、凭据 current、最新健康检查仍有效。
3. 校验 Capability 为 active，provider/protocol/模型/adapter contract version 与 Connection 相容；D-004 等门禁未关闭时直接返回稳定 blocker。
4. 新增 active ProviderBinding，并将旧 active Binding 置为 inactive；数据库部分唯一索引保证同用途只有一个 active。
5. 同事务追加不含密钥、endpoint query 或响应正文的 AuditEvent。

切换只影响事务提交后创建的新请求。旧任务继续按原快照执行；切换不会取消、重试或迁移任务。停用后新请求预检返回 `provider_binding_unavailable`，已进入外部调用的任务继续收敛。

## 6. API 与权限

接口沿用当前 `/api/v1` 与 Workspace 资源风格：

| 用例 | HTTP 形态 | 权限与结果 |
| --- | --- | --- |
| list_provider_presets | GET `/api/v1/provider-presets` | 登录成员可读无密钥目录、官方文档与 catalog-only 状态 |
| list/get_connections | GET `/api/v1/workspaces/{workspace_id}/provider-connections[/{id}]` | 仅 owner；返回脱敏配置、状态、版本和绑定摘要 |
| create/update/archive_connection | POST/PATCH/POST archive | 仅 owner；expected revision；归档前必须无 active binding |
| rotate_credential | POST `.../{id}/credential-versions` | 仅 owner；请求字段 write-only；响应只返回版本和状态 |
| discover_models | POST `.../{id}/model-discovery` | 仅 owner；显式触发、有界超时；结果只是候选，不激活 Capability |
| check_health | POST `.../{id}/health-checks` | 仅 owner；幂等/限流；返回 safe status/error code，不返回上游正文 |
| activate_binding | POST `.../{id}/bindings` | 仅 owner；usage_type、capability_id、expected revisions；事务切换 |
| deactivate_binding | POST `/api/v1/provider-bindings/{id}/deactivate` | 仅 owner；不影响已创建任务 |

editor/viewer 不读取 Connection 的 base_url、region、credential 状态细节或健康错误；它们继续通过 `GET /api/v1/model-capabilities` 和业务 preflight 获得“当前用途是否可用”的最小事实。所有写操作记录 actor、workspace、target、旧/新非敏感版本、结果和 trace，不记录提交 body。

OpenAPI 是前后端契约事实源。接口实现后必须运行仓库既有 `umi-openapi` 生成链更新 `frontend/src/api`，页面不得手写平行 DTO 或直接拼接 Provider 请求。

## 7. 凭据与网络安全

### 7.1 应用层加密

- 使用经过维护的密码库提供 AES-256-GCM；每个 CredentialVersion 使用独立随机 nonce 和认证标签。
- AAD 至少覆盖 `workspace_id + connection_id + credential_version_id + version`，防止密文被跨租户/跨记录替换。
- 数据库只存 `key_id`，主密钥从 `PROVIDER_CREDENTIAL_MASTER_KEY` 或生产 KMS/Secret Manager 注入。主密钥缺失时管理查询仍可返回非敏感配置，但新增/轮换/健康检查/启用/运行全部 fail closed。
- 内部 fingerprint 使用独立密钥的 HMAC-SHA256，只用于拒绝意外重复录入，不在 API、日志或管理 UI 展示 Key 前后缀。
- 主密钥轮换通过独立、可审计、逐条解密再加密命令完成；旧 key_id 在所有密文迁移并验证前保留。不得在普通 Web 请求中批量轮换。

### 7.2 SSRF、错误与日志

- 官方预设默认只允许自身 endpoint template；用户 override 必须满足该预设的受控 host/region 规则。
- `custom_openai_compatible` 只接受 HTTPS，拒绝 userinfo、query、fragment、IP literal、localhost、link-local、私网、云元数据地址和解析到受限网段的域名；连接前后都要校验 DNS 解析并限制重定向。
- 所有 Provider I/O 使用固定 connect/read/total timeout、响应大小上限、TLS 校验、受控重试和并发限额。认证失败、限流、不可达、模型无权限映射为稳定错误码；上游 body 只在内存中做最小解析并丢弃。
- Pydantic/HTTP/ORM 异常、trace、metrics、AuditEvent 和测试快照均须经过字段 allowlist；API Key、Authorization、x-api-key、完整 endpoint query、prompt 和原始响应正文列入强制脱敏测试。
- 备份只能包含密文。MVP 不提供带凭据的导入/导出；非敏感 Connection 导出若后续需要，必须与 CredentialVersion 分离。

## 8. 管理页面

在现有 Workspace 设置下增加 `/workspaces/providers`，复用现有视觉系统，不新建平行管理壳层：

1. owner 看到 Provider 卡片：名称、预设、用途提示、配置状态、健康状态、当前绑定、最近检查时间和 catalog version；任何角色都看不到 Key 内容。
2. “添加提供方”先选预设，再显示预设允许的 region/endpoint/认证字段；“自定义 OpenAI 兼容”放在高级入口并提示网络限制。
3. “保存配置”“检查连接”“启用到用途”是三个分离按钮。配置未完整、检查过期、Capability 未验收时，启用按钮保持禁用并展示服务端 blocker。
4. 切换前明确展示将替换的 usage binding、仅影响新任务、运行中任务不迁移；提交 expected revision 防止两个 owner 相互覆盖。
5. Key 字段写入成功后立即清空；编辑页只显示“已配置/轮换时间”，不提供回显、复制或浏览器持久化。
6. editor/viewer 进入页面时只显示无权限说明；Studio 任务面板继续使用既有不可用原因，不暴露 Provider 管理内部信息。

## 9. 数据切换与兼容策略

### 9.1 新环境

本功能首先只支持按当前数据库设计从空库初始化。新增 Model 必须在 composition root 显式注册，并同步更新数据库详细设计和结构测试；不得创建未来 Provider 表、通用 Secret 表或扫描式插件注册器。

### 9.2 当前 DeepSeek 配置迁移

接受并实现本设计后提供一次性受控命令：

1. 确认数据库表存在、主密钥可用、目标 Workspace 与 owner 明确。
2. 从进程环境读取现有 `DEEPSEEK_API_KEY`，在内存中创建 DeepSeek Connection 和加密 CredentialVersion；命令输出只显示 ID/版本/结果，不打印或记录 Key。
3. 运行真实 DeepSeek 契约检查与既有剧本结构化回归；成功后显式激活 `script_structure` binding。
4. 新请求完全从数据库绑定取配置。确认回滚窗口结束后删除运行环境中的 Provider API Key；保留的只有数据库密文与外部主密钥。

迁移期间不做长期双读。启用数据库 binding 前继续使用旧环境配置；启用后数据库成为该 Workspace 的唯一 Provider 配置事实。双写、静默 fallback 会使轮换和停用不可证明，禁止进入稳定状态。

### 9.3 存量数据库门禁

当前仓库没有在线 schema migration。若目标环境已保存不可丢失的业务数据，不能对其执行 `create_all` 冒充升级，也不能直接运行上述回填命令。必须先提交并接受独立的数据变更方案，至少包含 DDL、备份、演练、锁影响、回滚、密钥轮换和恢复验证；本设计不宣称该门禁已关闭。

## 10. 失败与恢复

| 场景 | 系统行为 |
| --- | --- |
| 主密钥/KMS 不可用 | 配置只读；凭据写入、检查、启用和执行 fail closed，返回 `credential_store_unavailable` |
| 保存成功、健康检查失败 | Connection 保留但不可启用；不删除用户配置，不自动改 endpoint |
| 健康检查过期 | 新启用被阻断；已 active binding 标记 degraded 告警，但不自动切换或重发任务 |
| 并发启用 | expected revision + 行锁 + 部分唯一索引使一个事务成功，另一个返回 VERSION_CONFLICT |
| 凭据轮换 | 新请求使用 current 版本；旧任务继续 retiring 版本；立即撤销必须明确确认影响 |
| Provider 配置在任务创建后变化 | Attempt 仍读取请求快照指向的旧版本；不存在“读取最新配置”的漂移 |
| 模型发现返回未知模型 | 只展示候选；没有 active ModelCapability 就不能启用或提交 |
| Provider 返回未知状态/响应 | Task/Attempt 按现有 unknown/manual_attention 收敛，不自动换 Provider 再提交 |
| 归档 Connection | active binding、retiring 凭据或非终态任务存在时拒绝；历史记录和审计保留 |

## 11. 验收与实施切片

本设计接受后再补 Requirement/PRD/Plan，并按 Red → Green → Refactor 执行以下最小闭环：

1. **配置事实与安全 Red**：固定表约束、tenant FK、owner RBAC、API 响应无 secret、AES-GCM 篡改拒绝、主密钥缺失、SSRF、日志/审计脱敏和归档门禁测试。
2. **DeepSeek 纵向闭环**：实现预设查询、Connection、凭据轮换、健康检查、`script_structure` 唯一 Binding、不可变运行时快照和一次性环境迁移；真实 DeepSeek 结构化提取回归通过。
3. **管理页面与 OpenAPI**：后端契约生成前端 API；完成添加、保存、检查、启用、切换、轮换、停用和并发冲突 UI；浏览器不得保存或回显 Key。
4. **catalog-only 目录**：加入其余首批预设和官方来源契约测试，只证明目录字段和安全校验，不宣称可执行。
5. **逐 Provider 准入**：每次只围绕一个真实业务用途增加 Adapter、ModelCapability、价格/限额/失败语义和真实账号 E2E。Ark 图片/视频仍必须先关闭 D-004。

最小验收证据：

- 单元：预设 schema、状态组合、加解密/AAD、版本轮换、endpoint 安全、激活门禁和快照稳定性。
- PostgreSQL 集成：租户隔离、唯一 active binding、并发切换、凭据只追加、审计原子性、归档/引用保护。
- API：owner 写、editor/viewer 拒绝、所有响应/错误/日志/trace 不含 Key，catalog-only 无法启用。
- 真实 Provider：DeepSeek 健康检查和现有剧本提取链；错误 Key、无权限模型、限流、超时和不可达均返回受控结果。
- 浏览器：预设添加 → 写入 Key → 检查 → 启用 → 创建新剧本任务 → 切换/停用；刷新后状态来自数据库，Key 不在 DOM、localStorage、sessionStorage 或生成客户端中。
- 回归：无 Provider 配置时现有 fail-closed 行为不变；Ark Key 存在时 Seedream/Seedance 仍不可用；任务、费用和媒体链路不因配置页面而产生伪成功。
