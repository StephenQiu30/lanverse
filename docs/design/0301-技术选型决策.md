## 2. 后端（Go）

| 关注点 | 选择 | 理由 | 放弃的方案 |
| --- | --- | --- | --- |
| HTTP | 标准库 `net/http`（Go 1.22+ 路由支持方法与路径参数）+ 少量中间件 | 依赖少、稳定；路由由 OpenAPI 生成代码对接 | Gin / Echo：框架耦合，收益不明显 |
| 接口生成 | `oapi-codegen`（strict server 模式）【待核实当前维护状态】 | 契约先行，Handler 签名由契约生成，编译期保证一致 | 注解生成 Swagger：契约散落在注释里，容易与实现漂移 |
| 数据访问 | `pgx` + `sqlc` | SQL 显式可审阅，类型安全，适合版本表、递归 CTE、分区表等复杂查询 | GORM：隐式行为多，复杂查询最终仍要写 SQL；ent：代码生成重、学习成本高 |
| 迁移 | `goose` 或 Atlas（二选一，实施首周定） | 版本化、可回滚、CI 可校验 | 启动时自动建表：生产不可控 |
| 工作流 | Temporal Go SDK | 见第 4 节 | — |
| 日志 | `log/slog` | 标准库结构化日志 | — |
| 配置 | 环境变量 + 启动时集中校验 | 简单、适合容器 | — |
| 对象存储 | AWS SDK for Go v2（S3 兼容接口） | 同时兼容 OSS / COS / S3 / MinIO | 各云厂商私有 SDK：锁定 |
| 质量 | gofmt、goimports、go vet、golangci-lint、`-race`、govulncheck | 与 AGENTS.md 的质量门禁一致 | — |

## 3. AI 执行层（Python）

| 关注点 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Python 3.12+，uv 管理依赖与锁文件 | 可复现安装 |
| Worker | Temporal Python SDK，监听 `ai` 任务队列 | 与 Go 工作流原生互通，无需自建 HTTP 回调协议 |
| 数据契约 | Pydantic v2 | Activity 输入输出、LLM 结构化输出校验 |
| HTTP 客户端 | httpx（统一超时、重试、连接池） | 供应商调用 |
| LLM 调用 | 各供应商官方 SDK 或 OpenAI 兼容接口，经自建网关统一 | 不绑定单一厂商 |
| 结构化输出 | 供应商原生 JSON Schema / 工具调用 + Pydantic 校验 + 有限次修复 | 可靠性 |
| 提示词管理 | 提示词作为版本化文件放在代码库，发布时记录版本与 hash | 可回溯、可评审、可回归测试 |
| 评测 | 自建小型评测集（解析、分镜、一致性），pytest 驱动 | 换模型或改提示词前先跑回归 |
| 质量 | Ruff（lint + format）、mypy、pytest | — |

**跨语言契约（D16）：** Go 工作流调用 Python Activity 时，输入输出结构定义在 `contracts/activities/*.schema.json`（带版本号）。Python 端生成或手写对应 Pydantic 模型，Go 端生成结构体（生成工具实施首周选定）；每个契约附带样例 JSON，两端测试都用同一批样例校验。契约不兼容变更必须升级版本，旧版本在工作流仍有运行实例时保留。

**明确不做：** 不用 LangChain / LangGraph 等框架编排业务流程（业务流程归 Temporal）；单个 AI 任务内部如果将来需要多步推理，再评估是否引入轻量框架。

## 4. 流程编排：为什么选 Temporal

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Temporal** | 持久执行；人工等待（Signal）、定时器、重试、超时、恢复都是原生能力；Go / Python 多语言 Worker 共用一个工作流 | 需要运维或付费托管；有学习曲线；工作流代码必须确定性 | **选用** |
| PostgreSQL 任务队列（River、pg-boss 等） | 简单、少一个组件 | 人工等待、分步恢复、跨语言协作、对账都要自己实现 | 放弃：本业务的复杂度正好落在这些能力上 |
| Inngest / Hatchet / Restate | 开发体验好 | 多语言与自建部署的成熟度需要评估【待核实】 | 备选 |
| Argo / Airflow | 批处理成熟 | 面向数据流水线，不适合交互式人工等待 | 放弃 |

**使用约束：** 工作流代码不做 I/O；所有数据库、模型、文件操作都在 Activity 中；业务事实以 PostgreSQL 为准，Temporal 历史只用于恢复流程。

### 6.2 关键依据

- **infinite-canvas**（MIT，2026-09-23 提交 `dab19ad`，v0.19.0，已读源码）：界面与交互最接近 LibTV（媒体卡、悬浮工具栏、创建菜单、小地图、分组、裁剪 / 重绘弹窗、视口裁剪、WebP 缩略图）。但它是纯本地单用户应用：数据存 IndexedDB，浏览器携带用户 API Key 直连供应商，页面主组件 3406 行，撤销重做为整体快照，连线无类型化端口，仅 1 个测试文件；作者声明不保证数据兼容，并请求二次开发保留作者信息与页面标识。**它的价值在界面，不在引擎。**
- **React Flow**（`@xyflow/react`，MIT）：与 infinite-canvas 同为 DOM + CSS transform 渲染，因此卡片界面可以移植；提供成熟的视口、端口、连线校验、框选、小地图、节点缩放、视口裁剪。
- **tldraw**：功能最完整，但生产商用需付费授权【待核实价格与条款】，且数据模型为白板形态。
- **Canvas / WebGL 自研**：性能上限最高，但文本输入、视频、选择、无障碍都要重做，工作量约为 C 的 2–3 倍，仅作为性能兜底。

### 6.3 方案 C 的落地约束

1. React Flow 作为依赖使用，不 Fork 源码；卡片与面板参考或移植 infinite-canvas 代码，保留 MIT 版权声明，并按作者请求在“关于”页注明来源（商用署名方式先与作者确认）。
2. 移植时移除 antd、插件系统、本地 Agent、WebDAV、本地代理、浏览器端供应商调用和本地持久化。
3. 节点 `data` 只存 `{ref_type, ref_id}`，业务数据由卡片按 ID 订阅；撤销重做基于命令（见 0201 §6.4）。
4. 媒体性能措施：只渲染视口内节点、按缩放级别切换缩略图尺寸、视频默认只显示封面且全局最多 2–3 个同时播放。
5. **PoC 验收（进入画布开发前必须通过）**：中端笔记本上 500 节点（300 图、40 视频、600 连线），平移缩放 ≥ 50 fps，拖动 20 个选中节点无明显掉帧，内存 < 1.5 GB，缩放至全局不白屏。未通过时只替换渲染层（媒体密集部分改用 Canvas 渲染），文档模型与接口不变。

## 7. AI 模型供应商（D12）

原则：**能力抽象 + 多供应商 + 实测决定**。平台内部按“能力”调用（`llm.structured`、`image.generate_with_reference`、`video.image_to_video`、`tts.synthesize`），网关负责路由到具体供应商与模型。模型每季度都在变化，下表只是 P0 评测的候选清单。

| 能力 | 国内候选【待核实】 | 海外候选【待核实】 | 开源自部署候选 |
| --- | --- | --- | --- |
| 剧本解析、分镜（LLM） | DeepSeek、通义千问、豆包、Kimi、GLM | Claude、GPT、Gemini | Qwen 系列 |
| 带参考生图 | 即梦 / Seedream、可灵图像、通义万相 | GPT-Image、Gemini 图像、FLUX Kontext | FLUX、Qwen-Image |
| 图生视频 | Seedance、可灵、海螺（MiniMax）、Vidu | Veo、Sora、Runway | Wan |
| TTS / 音色 | MiniMax 语音、火山 / 豆包语音、CosyVoice | ElevenLabs | CosyVoice、F5-TTS |
| 内容审核 | 阿里云、网易易盾、数美 | 各云厂商审核服务 | — |

**每个候选接入前必须核实：** 参考图输入方式与数量、时长 / 比例 / 分辨率范围、异步查询与回调、请求幂等或去重方式、结果链接有效期、取消能力、计费口径与用量返回、限流、数据使用与存储条款、所在区域是否满足合规。

**选型输出：** P0 结束时，每种能力确定 1 个主供应商 + 1 个备用供应商，并记录实测的质量、一致性、价格、延迟。

## 8. 基础设施

| 关注点 | MVP 选择 | 以后 |
| --- | --- | --- |
| 部署 | 容器镜像；托管容器服务或少量云主机 + Docker Compose | Kubernetes，Worker 按队列长度自动扩缩 |
| 数据库 | 托管 PostgreSQL | 读写分离、分区 |
| Temporal | 云托管优先；国内合规要求时自建 | — |
| 对象存储 | 国内：阿里云 OSS / 腾讯云 COS；海外：S3 / R2；本地：MinIO | 多区域 |
| 缓存 | 托管 Redis | — |
| 可观测 | OpenTelemetry → 托管 APM 或 Prometheus / Grafana / Loki；LLM 观测用 Langfuse（开源，可自建）【待核实】 | — |
| CI / CD | GitHub Actions：三端质量门禁、契约生成一致性检查、镜像构建 | 预发环境与灰度发布 |
| 密钥 | 云 KMS 或托管密钥服务 | — |

**为什么 MVP 不引入 Kafka / Elasticsearch：** 事件量和检索需求都在 PostgreSQL + Redis 的能力范围内；多一个组件就多一套运维和故障模式。Outbox 表的设计保证以后可以无缝把事件发布到 Kafka。

## 9. 与旧实现的差异

`PROJECT.md` 已于 2026-09-25 按本设计重写。仓库中的旧代码仍按以下旧约定实现，这些差异是 0401 第 5 节选择“重建”而非“原地改造”的主要原因：

| 条款 | 旧实现 | 新设计 |
| --- | --- | --- |
| 数据访问 | GORM | pgx + sqlc + 版本化迁移 |
| 接口契约 | Go 注解生成 Swagger → `@umijs/openapi` | 手写 `openapi.yaml` 为唯一来源 → oapi-codegen + TS 客户端生成 |
| 前端服务端状态 | Redux Toolkit Query | TanStack Query + Zustand |
| 编排 Owner | 创作编排归 Python，Go 保留业务工作流 | 所有工作流由 Go 编写，Python 只提供 Activity |
| 事件与检索 | Outbox + Kafka；Elasticsearch | Outbox + Redis Pub/Sub；PostgreSQL 全文检索 |
| 画布 | 迁入 infinite-canvas 源码为基线 | React Flow 引擎 + 移植 infinite-canvas 界面 |
