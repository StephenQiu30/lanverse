## 1. 结论

当前 MVP 不应以“公开商业平台”作为目标，而应先证明一个可人工审核、可追溯、不会在改稿时静默丢内容的内部制作闭环：

> 导入整部剧本 → 建议并确认分集 → 改写并发布单集剧本 → 建立角色/场景/道具资产 → 生成并人工接受分镜草案 → 检查叙事覆盖 → 导出分镜制作包；随后再接一条真实图片生成链路。

产品模块只保留六个：

1. **项目与分集**：管理整剧、Episode 顺序、目标时长和分集结果；
2. **剧本**：保存原稿、改写版本、稳定叙事单元和变更影响；
3. **资产**：管理角色、场景、道具的身份、剧情状态和可用版本；
4. **分镜**：把叙事单元规划为有序镜头，并证明没有漏拍；
5. **AI 生成与媒体候选**：先接一个图片供应商，生成候选、主选并保留血缘；
6. **最小预览与导出**：输出分镜表、Prompt 包和图片 Animatic，不建设专业剪辑台。

其中前四项是产品核心；第五项证明 AI 生成可用；第六项让内部制作人能拿走结果。认证、对象存储、异步任务、幂等、迁移、日志和基础权限属于共同工程底座，不另包装成面向用户的业务模块。

### 1.1 推荐里程碑

| 内部里程碑 | 必须完成 | 6 人团队基准 | 4 人团队基准 | 可以如何描述 |
| --- | --- | ---: | ---: | --- |
| MVP-A 制作核心 | 共同底座 + 项目/分集 + 剧本 + 资产 + 分镜 + 分镜包导出 | **16–18 周** | **24–28 周** | 可完成从整剧到可审核分镜包；不声称已生成短剧 |
| MVP-B 图片生成验证 | MVP-A + 一个真实图片 Provider + 候选/主选/血缘 + 图片预览 | **累计 21–24 周** | **累计 32–36 周** | 可生成和选择单镜/资产图片；仍不是成片系统 |
| MVP-C 内部动态样片 | MVP-B + 一个视频 Provider + 极简顺序拼接/字幕/下载 | **累计 26–30 周** | **累计 39–44 周** | 可做内部单集样片；不包含商业发布能力 |

**推荐当前冻结 MVP-A，架构兼容 MVP-B，并把真实 Provider 账号验证作为独立 Gate。** 如果管理层把“必须看到 AI 画面”作为 MVP 定义，则直接冻结 MVP-B，排期使用 21–24 周，不把外部供应商等待冒充研发完成。

## 2. MVP 验收样本与边界

### 2.1 黄金样本

- 一部 UTF-8 中文短剧原稿，包含 3–5 集；系统上限先控制为 10 集；
- 选择其中一集做完整验证，目标 60–120 秒、12–24 镜头、主画幅 9:16；
- 核心视觉资产只要求角色、场景、道具三类；现有服装、声音、音乐、特效模型保留兼容，但不扩展工作台；
- 每个 AI 结果都先成为候选，必须由人确认后才改变正式版本；
- 无真实 Provider 时允许手工上传图片走完同一候选、主选和引用链路，但不能报告“真实生成通过”。

### 2.2 当前明确不做

- B2B 套餐、计费、毛利、客户运营、公开 GA；
- 备案申报、发行、投流、平台自动发布；
- 企业审批流、实时多人协作、外链评审、复杂 RBAC；
- 多供应商自动路由、模型市场、LoRA 训练和自建 GPU；
- 专业 NLE、多轨时间线、调色、复杂转场、混音和工程文件导出；
- 无人审核的一键成片；
- PDF/DOCX/OCR 导入、跨项目资产库和语义去重。

权利来源、人物肖像/声音授权、媒体哈希和基础审计仍保留，因为它们是生成安全门禁，不属于商业计划。

## 4. M0 项目与分集

### 4.1 用户问题

用户拿到的是一份整剧原稿，并不一定预先知道应做多少集。当前系统要求先逐集创建 Episode 再粘贴剧本，入口顺序与真实工作流相反。

### 4.2 MVP 必做

- 创建项目时设置画幅、默认单集目标时长和语言；
- 上传或粘贴 `.txt/.md` UTF-8 整剧原稿；
- 有合法集标记时确定性拆分，显示缺号、重复号、空集和非法编码；
- 无集标记时，AI 只返回**一个推荐方案**：建议集数、每集边界、预计时长、边界理由和置信度；
- 用户可增删分界线、调整集序和目标时长，再一次性确认；
- 确认后幂等批量创建 Episode 和各集的原始 ScriptVersion；
- 保存 `DocumentRevision → EpisodePlan → ImportCommit → Episode/ScriptVersion` 血缘。

Top-3 分集方案、50 集长剧、PDF/DOCX/OCR 和自动商业时长优化均推迟。MVP 先用“一个建议 + 人工编辑”降低产品和评测复杂度。

### 4.3 难点与卡点

- 字符边界必须覆盖原稿且不重叠，不能在对白、括号动作或场标题中间断开；
- AI 输出不可靠，必须通过结构化 Schema、范围校验和人工确认；
- 批量物化任何一集失败时必须整批回滚，重复提交不得创建重复 Episode；
- 集数没有唯一“正确答案”，验收应看边界可解释和人工修改成本，而不是追求模型命中一个神秘标准答案。

### 4.4 MVP 验收

- 显式 5 集原稿连续 20 次导入均得到同样 5 集；
- 无标记黄金样本能返回完整覆盖的建议，用户可在一个界面完成修改和确认；
- 所有切片并集等于原文、交集为空，首尾字符无遗漏；
- 重放同一 `idempotency_key` 只产生一份 ImportCommit；
- 任一集创建失败时项目中不存在半批 Episode。

## 5. M1 剧本

### 5.1 用户问题

改写不是覆盖一段文本，而是要保留“原稿是什么、AI 改了什么、用户最终接受了什么”，并让资产和分镜知道自己基于哪一版内容。仅用字符位置或当前 `script_version_id` 无法在改稿后稳定追踪剧情。

### 5.2 MVP 必做

- 保存不可变的原始版本和改写版本，Episode 只持有 `current_script_version_id`；
- 一次只生成一个改写候选，支持约束：目标时长、保留核心情节、节奏快慢、台词口语化；
- 展示原文/候选差异，用户可编辑候选并“发布为当前版本”；
- 把发布版本解析为稳定 `NarrativeUnit`，MVP 类型为 `scene_heading/action/dialogue/narration`；
- 每个单元保存稳定身份、不可变内容版本、顺序、角色/地点引用和来源文本范围；
- 发布新剧本时计算影响：现有资产提取、分镜覆盖和导出进入 `stale`，不得继续显示为 ready；
- MVP 不承诺自动把旧分镜精确迁移到新剧本；允许整集重新映射，并展示待人工确认的影响清单。

VibeReels 公开表面显示原始、改写、格式化三层文本和失效提示，但没有公开证明稳定段落 ID 或严格段落—镜头 1:1。Lanverse 因此把格式化结果建模为叙事单元派生层，不复制三个互相覆盖的富文本编辑器。

### 5.3 难点与卡点

- LLM 改写可能删掉关键剧情、改变人物关系或超出目标时长；
- 字符 offset 会随 Unicode、换行和编辑漂移，不能作为长期主键；
- 旧版与新版单元的自动匹配存在歧义，MVP 必须允许“不确定并要求重审”；
- “发布当前版本”是影响大量下游的命令，需要 expected revision/CAS，不能是普通 PATCH。

### 5.4 MVP 验收

- 原稿永不被 AI 或用户后续编辑覆盖；
- 发布候选前能看到差异和预计时长，取消不会改变 current；
- NarrativeUnit 顺序稳定、文本范围合法，所有必拍单元可被覆盖检查引用；
- current 切换后，引用旧 ScriptVersion 的分镜和导出全部 fail-closed；
- 两个编辑者基于同一旧 revision 发布时只有一个成功，另一方收到可理解的冲突。

## 6. M2 资产

### 6.1 用户问题

角色、场景和道具不是一张图片。一个角色可能在不同集出现常服、受伤、婚礼等状态；镜头必须知道引用的是哪个身份、哪个剧情状态以及哪一个不可变图像版本。

### 6.2 MVP 必做

- 保留稳定 `Asset` 身份，MVP 工作台重点展示 `character/location/prop`；
- 新增 `AssetState`，保存状态名称、描述、适用 Episode/NarrativeUnit 范围和 current version；
- `AssetVersion` 不可变，包含 Prompt、参考图、媒体哈希、来源和权利状态；
- 支持手工创建、AI 提取候选的接受/拒绝、上传版本和切换主版本；
- 镜头固定引用 `asset_id + state_id + version_id`，主版本变化不静默改写历史镜头；
- 改名、禁用、切换主版本前展示受影响 Episode、Shot、Prompt 和在途任务；
- 资产 readiness 至少检查媒体可读、权利/同意、状态存在和版本已选；
- 真实生成的图片先进入 M4 `OutputCandidate`，人工主选后才 promotion 为 AssetVersion。

### 6.3 难点与卡点

- “同一资产的不同状态”和“两个不同资产”需要人工纠错，不能只靠名称；
- 资产改名不应改变稳定 ID，但 Prompt 中若存了裸名称会过期；
- 状态、版本和资产三者必须做复合一致性校验，不能引用另一资产的版本；
- 候选与正式 AssetVersion 的来源类型要避免和现有剧本 ExtractionCandidate 混淆。

### 6.4 MVP 验收

- 同一角色可建立至少两个状态，并在不同镜头固定不同版本；
- 切换角色主图后，历史镜头仍解析到原版本，新镜头使用新版本；
- 禁用资产前能预览影响，确认后受影响镜头变为 blocked/stale；
- 资产名称变化不破坏 Shot 引用；重新编译 Prompt 后显示新名称；
- blocked、无媒体或无权利的版本不能进入生成请求。

## 7. M3 分镜

### 7.1 用户问题

剧本到分镜不是段落严格 1:1：一段动作可拆成多个镜头，多段对白也可能合在一个镜头。真正需要保证的是每个必拍叙事单元有明确镜头覆盖、每个镜头有来源，而且拆镜、合镜和改稿后不会静默丢失。

### 7.2 MVP 必做

- AI 生成 `StoryboardDraftBatch` 候选，不直接覆盖正式 Shot；
- 每个候选镜头包含目的、景别、机位/运动、画面描述、对白、预计时长和资产引用建议；
- 用户可逐镜接受/编辑，也可整批应用；应用需幂等并记录来源批次；
- `ShotSpecVersion ↔ NarrativeUnitVersion` 为多对多引用，保存覆盖类型和人工/AI 来源；
- 生成 `CoverageReport`：必拍已覆盖、用户批准省略、未覆盖、孤儿镜头、过期引用；
- 只有未覆盖必拍项为 0、孤儿为 0、过期为 0 时，Episode 才可进入 ready；
- 保留现有顺序 CAS、插入、复制、删除；修复拆分/合并对白和 action beats 静默丢失；
- 镜头资源引用使用结构化 Asset/State/Version，`@图片N` 仅是编译后的可视别名；加删资源时统一重编号。

导演字符区间标注、语义标签自动映射、复杂镜头模板和多版导演方案均为 P1，不阻塞 MVP。

### 7.3 难点与卡点

- AI 草案的镜头数和节奏受目标时长约束，不能只限制 JSON 数组长度；
- 覆盖是多对多，必须防止“一个镜头挂了全部叙事单元”伪造完成；
- 当前拆镜把对白全部留在第一段、第二段清空，合镜还会截断 action beats；这是正式引入 AI 草案前必须修复的数据完整性问题；
- current Script 切换后旧 NarrativeUnitVersion 引用必须立刻阻断 ready。

### 7.4 MVP 验收

- 12–24 镜头黄金样本能从候选批次人工应用为正式镜头；
- 所有必拍 NarrativeUnit 均有覆盖或明确的批准省略理由；
- 拆镜后两边对白/动作并集等于来源且无重复，跨场景合镜默认禁止；
- 调整顺序时旧 revision 请求失败，不发生最后写入覆盖；
- 修改剧本、资产状态或 ShotSpec 后 Coverage/readiness 在同一事务或可靠事件后失效。

## 8. M4 AI 生成与媒体候选

### 8.1 定位

该模块是 MVP-B，不应和资产模块重复建设候选、主选和血缘。资产/分镜只提交生成目标并读取结果，生成模块独占 `PromptRevision / GenerationRun / OutputCandidate / Selection / MediaLineage / ProviderSnapshot`。

### 8.2 MVP-B 必做

- 只接一个真实图片 Provider；目标类型支持 `asset_state` 和 `shot`；
- Prompt 编译固定输入 ScriptVersion、ShotSpecVersion 和 AssetVersion；
- 提交、轮询、回调、取消、超时、重试和幂等；
- 每次输出成为不可变 Candidate，支持预览、拒绝、星标和唯一主选；
- 记录模型、参数、参考媒体、输入/输出哈希、耗时、失败原因和请求计数；
- 主选资产候选可显式 promotion 为 AssetVersion；镜头候选只成为该镜头的选中媒体，不反写 ShotSpec；
- Provider 未配置、余额/权限未知或真实探针失败时 fail-closed。

视频 Provider、TTS、口型、字幕擦除和多供应商降级放到 MVP-C 或更后。

### 8.3 验收

- 同一幂等键重复提交只产生一个 Run；
- Provider 成功、失败、超时、取消均有终态和可恢复路径；
- 任一图片可以追溯到精确 Prompt、模型参数和固定资产版本；
- 切换主选不删除其他候选，历史导出仍能解析当时主选；
- 真实账号连续完成黄金样本至少 20 次请求后，才能关闭 Provider Gate。

## 9. M5 最小预览与导出

### 9.1 MVP-A 必做

- 导出 Episode 的分镜表：镜号、时长、叙事来源、画面、对白、资产状态、Prompt 和 readiness；
- 导出机器可读 JSON 与制片可读 CSV/HTML 包；
- 导出前重新计算 Coverage 和资产 readiness，失败时给出阻断清单；
- 导出包保存自己的 Manifest，固定 Script/Asset/Shot 版本，后续修改不篡改历史包。

### 9.2 MVP-B 可加

- 浏览器按镜头顺序预览主选图片，可调单镜时长；
- 没有生成结果时允许显示手工上传占位图；
- 可下载图片、Prompt 和 Manifest 打包文件。

低清 MP4、视频 trim、字幕轨和简单拼接属于 MVP-C。MVP-A/B 不建设多轨时间线，也不把“浏览器连续播放图片”称为成片导出。

## 10. 共同工程底座

这些能力不单独形成产品菜单，但缺少任一项都可能让核心模块不可用：

| 能力 | MVP 最低要求 |
| --- | --- |
| 不可变版本与 current 指针 | Script、NarrativeUnit、Asset、Shot、Prompt、Export 均固定版本 |
| 并发与幂等 | 发布、批量建集、应用草案、重排、主选、生成提交使用 expected revision/idempotency key |
| 异步状态机 | queued/running/succeeded/failed/cancelled/expired，失败可重试但不伪造成功 |
| 对象存储与媒体探测 | 本机 MinIO 闭环；哈希、MIME、尺寸和可读性校验 |
| Schema migration | 正式 Alembic 迁移、前滚/回滚演练；不得靠测试建表代替生产迁移 |
| 影响与 readiness | 统一 reason code，所有“可生成/可导出”均由派生检查决定 |
| 基础身份与工作区 | 当前账号/Workspace 隔离即可；不做复杂企业角色 |
| 可观测性 | 请求 ID、任务状态、失败原因、耗时和生成请求计数；不做商业计费系统 |
| 黄金样本 | 3–5 集整剧、单集 12–24 镜头，固定期望边界/覆盖/资产状态和失败样例 |

## 11. 实施顺序与关键依赖

~~~mermaid
flowchart TD
    G0["Gate 0：冻结 MVP 样本与边界"] --> F["共同底座：迁移 / 版本 / 幂等 / 任务"]
    F --> M0["M0 整剧入口与分集"]
    M0 --> M1["M1 改写与 NarrativeUnit"]
    M1 --> M2["M2 AssetState 与版本影响"]
    M1 --> M3["M3 分镜草案与 Coverage"]
    M2 --> M3
    M3 --> O1["Gate 1：MVP-A 分镜包"]
    O1 --> M4["M4 真实图片 Candidate"]
    M4 --> M5["M5 图片预览与导出"]
    M5 --> O2["Gate 2：MVP-B 图片生成验证"]
~~~

可并行关系：M0 前端与共同底座可并行；NarrativeUnit 契约冻结后，M2 和 M3 可并行；M4 Provider adapter 可提前做真实探针，但 Candidate/Selection 公共模型必须由 M4 单点拥有。

不可压缩关系：没有发布的 ScriptVersion 就不能确认 NarrativeUnit；没有 AssetState 和 NarrativeReference 就不能判定分镜 ready；没有正式 Candidate/Lineage 就不能把供应商返回 URL 当作资产版本。

## 12. 剩余工作量与排期

估算包含 Design 收敛、后端、前端、迁移、OpenAPI、单元/集成/E2E、黄金样本和普通缺陷；不包含外部账号等待。已完成的 S0–S3 不重复计价。

| 工作包 | 乐观 | 基准 | 保守 | 主要产出 |
| --- | ---: | ---: | ---: | --- |
| 共同底座补齐 | 3 | 5 | 7 人周 | migration、统一失效、黄金样本、日志 |
| M0 项目/整剧/分集 | 13 | 17 | 21 人周 | Document、Plan、边界编辑、批量物化 |

| M3 分镜草案与覆盖 | 10 | 14 | 19 人周 | DraftBatch、Reference、Coverage、拆合修复 |

| M5 图片预览与导出增量 | 4 | 6 | 8 人周 | 图片 Animatic、打包与历史 Manifest |

## 13. 可行性判断

| 能力 | 可行性 | 判断 |
| --- | --- | --- |
| 整剧导入和显式标记拆分 | 高 | 确定性解析、事务和 UI 问题，可稳定验收 |
| 无标记剧本的建议集数 | 中高 | LLM 可产候选，但必须有人确认，不能承诺唯一正确答案 |
| 原稿/改写/发布版本 | 高 | 现有不可变 ScriptVersion 可扩展，主要难点是产品交互和影响传播 |
| 稳定 NarrativeUnit | 中高 | 技术可做；跨大改稿自动迁移准确率有限，MVP 采用失效重审 |
| AssetState 和版本固定引用 | 高 | 工程型能力，现有 AssetVersion/Shot 引用已提供基础 |
| AI 分镜草案 | 中高 | 结构化输出可做，质量必须靠人工应用和黄金样本评测 |
| 剧本—分镜多对多覆盖 | 高 | 领域建模和校验可控，是避免漏拍的必要底座 |
| 跨镜角色视觉一致性 | 中 | 引用治理可显著改善，但最终画面仍受外部模型能力影响 |
| 单图片真实生成 | 中 | 工程链路可做，账号权限、额度、参数和质量尚未通过真实 Gate |
| 自动高质量整集成片 | 低至中 | 涉及视频、声音、字幕、时间线和质量评测，不应塞进当前 MVP-A/B |

整体判断：**MVP-A 高可行，MVP-B 中高可行，MVP-C 中等可行。** 最大内部风险不是“模型不会写 Prompt”，而是修订、资产状态和分镜覆盖之间没有稳定血缘；最大外部风险是真实图片/视频 Provider 的权限、配额、质量和成本尚未用账号证据验证。

## 14. Gate 与完成定义

### Gate 0：范围冻结

- 黄金样本、上限、必拍规则和改写约束由产品负责人/短剧制作人接受；
- 明确当前选择 MVP-A 还是 MVP-B；
- DES-010 商业/完整平台排期不得混入当前迭代燃尽图。

### Gate 1：MVP-A 完成

- 黄金样本从整剧导入到分镜包导出一次完整通过；
- 分集切片无遗漏/重叠，发布和应用命令可幂等重放；
- 必拍 NarrativeUnit 覆盖率 100%，未批准遗漏为 0；
- stale/blocked 结果不能进入 ready 或导出；
- 拆镜/合镜不丢对白、动作、资产和叙事引用；
- 数据库迁移在干净库和含样本数据的旧库均通过。

### Gate 2：MVP-B 完成

- 真实图片 Provider 账号完成连续请求、失败、取消和重试验证；
- 每个输出可追溯到固定 Prompt/Script/Shot/Asset 版本；
- 候选、主选、promotion 和历史导出均通过 E2E；
- 图片失败不会破坏已接受的剧本、资产或分镜。
