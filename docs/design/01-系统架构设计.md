## 1. 结论

1. **四层结构**：交互入口（Web 流水线、画布、对话式 Agent）→ 命令与查询层 → 领域层（结构化生产对象 + 生成操作）→ 编排与集成层（Temporal、Agent 服务、媒体处理、PostgreSQL、Redis、Kafka、MinIO）。每层只依赖下一层的公开契约。
2. **结构化生产对象是事实源**：剧本、集、场、台词、角色、造型、场景、道具、镜头都是有版本与依赖的一等业务对象，存于 PostgreSQL。这是 Lanverse 相对 LibTV（以画布文档为容器）的核心差异。
3. **所有生成都是 Operation**：能力 + 模式 + 模型 + 参数 + 带用途的输入 → 工作流 → 版本化输出。流水线、画布、批量、Agent 只是创建 Operation 的不同入口。
4. **Temporal 编排全部长流程，工作流只用 Go 编写**：Go Activity 负责写库与媒体处理，Python Activity 负责 AI 调用；一个流程只有一个 Owner。
5. **Agent 服务是受控的 AI 执行单元**：FastAPI + Temporal Activity Worker，内含 Agent Harness（Skill、上下文、模型路由、工具白名单、校验修复、预算、追踪）；不写业务数据库，结果经工作流由 Go 落库。
6. **中间件职责单一**：PostgreSQL 存事实；Redis 做缓存、会话、限流、锁与实时扇出；Kafka 做领域事件总线；MinIO 存媒体；Temporal 管流程。
7. **画布是视图 + 自由工作区**，只拥有布局；模型通过声明式注册表接入，新增同类模型只改配置。

## 2. 顶层原则

| # | 原则 | 含义 |
| --- | --- | --- |
| P1 | 单一事实源 | 每个业务字段只有一个 Owner（Go 领域模块）；Redis、Kafka、Temporal、画布、前端、Agent 服务都不作为业务事实源 |
| P2 | 候选与正式分离 | AI 结果先是候选（Operation 输出），人工选定后才被正式对象引用 |
| P3 | 结果字段归任务，配置字段归人 | 工作流只写结果与状态；人只改配置与选定（REQ-01 GEN-10） |
| P4 | 版本不可变、输入可追溯 | 修改产生新版本；每个 Operation 冻结输入快照与 hash |
| P5 | 只标记不重做 | 上游变化只把下游标为过期；重做必须由人触发 |
| P6 | 同一命令层 | Web、画布、Agent 调用同一套命令（权限、幂等、版本校验统一） |
| P7 | 付费操作可对账 | 报价 → 预留 → 执行 → 结算；结果未知先对账，不重复购买 |
| P8 | 单一流程 Owner | 工作流只用 Go 编写；Agent 服务只执行 Activity，不编排业务流程 |
| P9 | 事件只传已提交事实 | 事务内写 Outbox，提交后投递 Kafka；消费者幂等 |

## 3. 领域模型

### 3.1 限界上下文

| 上下文 | 职责 | 核心对象 |
| --- | --- | --- |
| identity | 账号、登录、会话；管理员创建账号 | User、Session |
| workspace | 组织（MVP 固定一个）、项目、项目设置、风格预设 | Organization、Project、StylePreset |
| script | 剧本导入、分集、结构解析 | ScriptSource、ScriptVersion、Episode、Scene、DialogueLine |
| bible | 设定集、参考资产、角色音色 | Character、Look、Location、Prop、ReferenceSlot、VoiceProfile |
| storyboard | 镜头、生成模式、参考组合 | Shot、ReferenceSet、ReferenceItem |
| operation | 生成操作：创建、报价、执行、输出、选定 | Operation、OperationInput、OperationOutput、ProviderCall |
| catalog | 模型注册表与价格 | Capability、ModelProfile、ParamSchema、PriceRule |
| media | 媒体资产、上传、探测、缩略图、来源与合规属性 | MediaAsset、MediaRendition、ProvenanceRecord |
| audio | 台词音频与选定 | DialogueAudio、LineAudioSelection |
| billing | 预算、预留、账本 | Budget、Reservation、LedgerEntry |
| canvas | 画布布局 | CanvasDocument、CanvasNode、CanvasEdge |
| lineage | 依赖与过期传播（横切） | Dependency、StaleMark |

### 3.2 核心关系

```text
Organization ─< Project(style_type, style_preset, aspect_ratio)
  ├─< ScriptSource ─< ScriptVersion
  ├─< Episode ─< Scene ─┬─< DialogueLine ─< DialogueAudio(TTS 输出 | 上传音轨) ─ selected
  │                     └─< Shot(version, generation_mode, 镜头语言参数)
  │                           ├─ ReferenceSet ─< ReferenceItem(role, ref)
  │                           ├─ selected_frame → OperationOutput
  │                           └─ selected_take  → OperationOutput
  ├─< Character ─< Look ─< ReferenceSlot ─ selected → OperationOutput
  │     └── VoiceProfile
  ├─< Location / Prop ─< ReferenceSlot
  ├─< Operation(target?, capability, mode, model, params, input_hash, workflow_id)
  │     ├─< OperationInput(role, ref)
  │     ├─< ProviderCall
  │     └─< OperationOutput → MediaAsset | 结构化结果
  ├─< MediaAsset(object_key, provenance, compliance)
  ├── Budget ─< Reservation / LedgerEntry
  └── CanvasDocument ─< CanvasNode(ref_type, ref_id) / CanvasEdge
```

### 3.3 建模规则

1. **版本不可变**：剧本、造型、镜头（含参考组合）以“对象 + 版本号”存储；引用指向具体版本。
2. **选定是显式命令**：带 `expected_version`，不匹配返回 409。
3. **依赖显式登记**：新版本产生时写入 `lineage.dependency(downstream, upstream)`；上游变化时标记下游 `stale`。
4. **单组织优先**：表保留 `org_id`、`project_id`；MVP 固定一个组织，但查询仍带项目条件。
5. **持久化模型与领域模型分离**：GORM 模型只存在于仓储适配器；领域对象与 API DTO 各自定义，显式转换。

## 4. 生成操作（Operation）模型

### 4.1 定义

```text
Operation {
  id, project_id
  target?            # 可选：服务的业务槽位，如 Shot v5 的 take、Look v2 的参考图、DialogueLine 的音频；无 target 即“自由生成”
  capability         # text.structured | image.generate | image.edit | video.generate | audio.tts ...
  mode               # 例：video.generate 下的 text2video | image2video | frames2video | omni_reference | video2video
  model_key          # 指向 catalog.ModelProfile
  params             # 按 ParamSchema 校验
  inputs[]           # OperationInput { role, ref_type, ref_id, ref_version }
  input_hash         # 冻结输入摘要（复用与缓存）
  origin             # pipeline | batch | canvas | agent | upload | system
  status, quote, reservation_id, workflow_id, provider_calls[], outputs[]
}
```

- 镜头的参考组合是视频 Operation 的输入模板：创建时从镜头当前版本的 ReferenceSet 展开为 `inputs[]`。
- 画布生成节点运行时创建 Operation；有无 target 取决于节点是否绑定业务槽位。
- 批量运行创建一组 Operation，由父工作流统一调度。
- Agent 通过命令层创建 Operation 草稿，仍需报价与确认。

### 4.2 输入角色

| role | 含义 | 可引用 |
| --- | --- | --- |
| `prompt` | 文本描述 | 文本、结构化字段 |
| `first_frame` / `last_frame` | 首帧 / 尾帧 | 图片 |
| `subject` | 角色主体 | 造型参考图 |
| `scene` / `prop` | 场景 / 道具 | 参考图 |
| `style` | 风格 | 图片、风格预设 |
| `motion` / `camera` | 动作 / 运镜参考 | 视频 |
| `audio` | 表演节奏、情绪、口播 | 音频（上传或台词音频） |
| `source` | 被编辑的源素材 | 图片、视频 |

新增角色在注册表登记，Agent 服务的供应商适配器实现映射即可。

### 4.3 状态机

```text
draft → quoted → confirmed(已预留) → submitting → submitted → succeeded → ingesting → completed
                                    │              │
                                    │              ├→ failed(retryable | final) → 释放 / 结算
                                    └→ unknown ──→ reconciling → submitted | failed | manual
任意非终态 → cancelling → cancelled
```

- **报价**：按 ModelProfile 校验模式、输入角色数量与类型、时长、画幅、参数；计算费用与 `input_hash`；命中已有 `completed` 操作时复用输出，不收费。
- **确认**：命令层在一个事务内预留费用、生成 `provider_request_key`、写 Outbox；随后以 `operation/{id}` 为 Workflow ID 启动工作流（重复启动被 Temporal 拒绝，天然幂等）。
- **输出**：OperationOutput 是候选；目标对象 Owner 通过选定命令引用它。
- **写入权限**：工作流只写 Operation 自身的状态与输出（P3）。

### 4.4 模型注册表（catalog）

```text
Capability { key, output_type, allowed_modes[], input_roles[] }
ModelProfile {
  model_key, provider, adapter_key, capability, modes[]
  limits { per role: max_count, max_seconds, allowed_types }, durations, aspect_ratios, resolutions, max_outputs
  param_schema[] { field, type, component(input|select|slider|switch|voice), enum, default, rules, for_modes[] }
  region(domestic|overseas), pricing_rule_ref, supports_query, supports_cancel, supports_callback, queue, status
}
```

- 管理员维护；PostgreSQL 为事实源，Redis 缓存。
- `region` 标注模型服务区域；项目设置不允许境外模型时，境外模型在报价阶段被拒绝（REQ-02 CMP-06）。
- 前端参数面板按 `param_schema` 渲染；报价按 `limits` 与 `rules` 校验。
- 新供应商需要在 Agent 服务新增适配器（`adapter_key`）；同家新模型只增配置。

### 5.2 部署单元

| 单元 | 职责 | 不负责 |
| --- | --- | --- |
| `backend-api`（Go，Gin） | 公共 REST、命令与查询、启动工作流与发送信号、SSE | 长计算、调用模型 |
| `backend-worker`（Go，Temporal Worker） | 全部工作流定义；`flow` 队列（写库、结算、流程推进）；`media` 队列（下载接管、ffprobe、缩略图、转码、抽帧、裁剪、AIGC 元数据标识） | 对外 HTTP、调用模型 |
| `backend-relay`（Go） | Outbox → Kafka 投递；Kafka 消费者（实时通知、过期传播、成本汇总、审计、调用明细） | 同步业务命令 |
| `agent-worker`（Python，Temporal Activity Worker） | `agent` 队列：Harness 执行 LLM 任务；供应商适配器 submit / query / cancel；内容审核 | 写业务数据库；编排流程；自动重提未知付费请求 |
| `agent-api`（Python，FastAPI） | 健康检查、Harness 调试与评测接口；对话式 Agent（AG-UI） | 对外公开 |
| 前端（Next.js） | 界面、交互、服务端状态缓存 | 业务授权、直连内部服务 |

`backend-api`、`backend-worker`、`backend-relay` 是同一个 Go 二进制的三种角色（`--role`）；`agent-api` 与 `agent-worker` 共享同一 Python 代码库。

## 6. 工作流（Temporal）

### 6.1 约定

- 工作流只用 Go 编写；工作流代码确定性，不做 I/O。
- Workflow ID 使用业务 ID：`operation/{id}`、`script-parse/{script_version_id}`、`batch/{batch_id}`。
- 业务状态以 PostgreSQL 为准：工作流通过 `flow` 队列的 Activity 读写业务表；Temporal 历史只用于恢复流程。
- 人工确认：用户命令先写 PostgreSQL，再向工作流发送 Signal（或 Update）；工作流收到后继续。
- 供应商限流：`agent` 队列可按供应商拆分为 `agent.<provider>`，并配合 Redis 配额。

### 6.2 OperationWorkflow

```text
1. flow  : MarkSubmitting(op)                     # 写状态
2. agent : ProviderSubmit(op_input, request_key)  # Harness / 适配器提交
      ├ 成功 → flow: MarkSubmitted(provider_task_id)
      └ 超时 / 响应丢失 → flow: MarkUnknown → 进入对账
3. 循环（定时器退避）：agent: ProviderQuery → 直到成功 / 失败 / 超时
4. media : Ingest(result_urls) → MinIO 存储、ffprobe 校验、缩略图、登记 MediaAsset（来源、合规）
5. agent : Moderate(output)（按注册表配置）
6. flow  : Complete(op, outputs, usage) → 结算、释放预留、写 Outbox（operation.completed）
取消：收到 cancel 信号 → agent: ProviderCancel（若支持）→ flow: MarkCancelled、按实际结算
对账：agent: ProviderQuery(by request_key) → 不支持查询则 flow: MarkManual，不自动重提
```

LLM 类操作（分集、解析、设定集抽取、分镜）为同步型：第 2 步由 Harness 直接返回校验后的结构化结果，跳过第 3–4 步。

### 6.3 业务工作流

| 工作流 | 步骤 |
| --- | --- |
| ScriptImportWorkflow | 抽取文本 → 规范化与去重 → 保存剧本版本 → 规则分集并写入分集候选；需要 AI 分集时生成报价后结束（确认后由独立的 OperationWorkflow 新增一套 AI 分集候选，与规则候选并存，由用户选用）；逐集解析、设定集抽取为 OperationWorkflow 的 LLM 分支（DES-04 §3） |
| BatchWorkflow | 为选中的每个镜头启动 OperationWorkflow 子工作流；汇总成功 / 失败；失败项可单独重试 |

### 6.4 视频生成的两种模式

| 模式 | 前置条件 | Operation 输入 |
| --- | --- | --- |
| `image2video` | 镜头已选定关键帧 | `first_frame` + `prompt` |
| `omni_reference` | 参考组合非空且全部为锁定版本或 ready 素材 | `subject` / `scene` / `prop` / `motion` / `camera` / `audio` + `prompt` |

`prompt` 由 Go 规则模板根据镜头语言参数与参考组合拼接（免费），用户可改写；AI 优化提示词不在 MVP（REQ-34 VID-07）。

## 7. Agent 服务与 Agent Harness

### 7.1 边界

- Agent 服务**只通过 Temporal Activity 接收任务**（MVP）；输入是冻结的：版本 ID、原文片段、参考描述、媒体预签名 URL、Skill 版本、预算。
- 输出是结构化候选 + Trace + 用量；由 Go 工作流落库。
- 不连接业务数据库；不持有 MinIO 管理凭据；供应商凭据只在本服务环境中。

### 7.2 Harness 组成

| 组件 | 职责 |
| --- | --- |
| Skill Registry | 专业能力包（`SKILL.md` + 参考资料 + 输入输出 schema），按版本与内容 hash 发布；任务记录所用版本 |
| Context Builder | 按冻结输入组装上下文，控制 token 预算；超限明确失败，不静默截断 |
| Model Router | 按模型注册表选择模型与参数，封装各家调用 |
| Tool Registry | 声明式只读工具（查原文、取参考描述、计算时长）；按任务白名单授予；无业务写工具 |
| Execution Loop | 调用 → 校验 → 修复，最多 N 轮；响应取消与截止时间（Temporal heartbeat） |
| Validators | schema、原文位置核对、业务规则（每句台词只分配一次、参考数量不超限等） |
| Budget | token、费用、时长上限；超限终止并说明原因 |
| Trace | 每步提示词版本、输入 hash、模型、用量、耗时、校验结果 |

### 7.3 MVP 内置 Skill

| Skill | 输入 | 输出 |
| --- | --- | --- |
| `split_episodes` | 整部剧文本 | 分集边界（带原文位置） |
| `parse_episode` | 单集文本 | 场次、台词行、动作、情绪、时间地点（带原文位置） |
| `extract_bible` | 各集解析结果 | 角色 / 造型 / 场景 / 道具、别名合并、状态变化 |
| `storyboard` | 场次 + 锁定资产 | 镜头表：镜头语言、台词分配、模式建议、默认参考组合 |

### 7.4 对话式 Agent（与 LibTV 对齐 AG-UI 协议）

依据 PRD-02 §3.7：LibTV 使用 CopilotKit + AG-UI，Agent 通过 `CUSTOM` 事件下发画布补丁、通过服务端工具发起生成。Lanverse 采用同一协议，但保持“命令层是唯一写入口”。

```text
浏览器（CopilotKit）──AG-UI over SSE──→ Go backend-api（鉴权、项目范围、审计、会话持久化）──→ agent-api（FastAPI + ag-ui-protocol）
                                                                                           └ Harness：规划、Skill、只读工具
```

| AG-UI 能力 | Lanverse 用法 |
| --- | --- |
| `TEXT_MESSAGE_*` / `REASONING_MESSAGE_*` | 对话与思考过程流式输出 |
| `STATE_SNAPSHOT` / `STATE_DELTA` | Agent 当前计划与进度（如“正在为第 3 场拆镜头”） |
| 服务端只读工具 | 查询剧本、设定集、镜头、参考组合、模型注册表（经 Go 内部接口，按会话项目范围授权） |
| `CUSTOM: canvas_commands` | 下发**画布命令提案**（布局命令 + 业务命令，如新增镜头、设置参考）；前端展示差异，用户确认后提交 Go 命令层执行；LibTV 的 `canvas_patch` 由前端直接应用，我们不采用这种方式 |
| 人工确认工具（human-in-the-loop） | `create_operation_draft`：Agent 只能创建 Operation 草稿；报价后**必须由用户二次确认**才执行，不提供自动确认（PRD-01 P21、GEN-11） |
| `TOOL_CALL_RESULT` 错误码 | 预算不足、模型不可用、权限不足等以统一错误码返回，前端给出可操作提示 |

- 会话与消息由 Go 持久化，按递增序号支持断线续传与增量查询（参照 PRD-02 §3.5 的 `afterSeq`）。
- 传输使用 SSE，协议为 AG-UI。
- 提供 Agent 调试面板（上下文、事件流、手动注入、本地状态），与 LibTV 的调试抽屉对应，仅对管理员开放。

## 8. 事件、缓存与实时

### 8.1 事件（Kafka）

- 业务事务内写 Outbox；`backend-relay` 投递到 Kafka，主题 `lanverse.<上下文>.<事件>.v<N>`，键为 `project_id`。
- 消费者（均幂等，按事件 ID 去重）：

| 消费者 | 处理 |
| --- | --- |
| realtime | 转发为 Redis Pub/Sub 消息，驱动 SSE |
| lineage | 根据“新版本已选定”事件标记下游过期 |
| billing-report | 汇总成本到项目 / 集 / 镜头报表 |
| audit | 审计记录归档 |
| model-usage | 模型调用明细入库，供成本与质量分析 |

- 将来的检索索引、数据分析、外部通知都作为新的消费者接入。

### 8.2 Redis

| 用途 | 说明 |
| --- | --- |
| 会话 | 登录会话，HttpOnly Cookie 引用 |
| 缓存 | 模型注册表、项目概览等热点查询；以 PostgreSQL 为准，失效后重建 |
| 限流 | API 限流；供应商配额（与 Temporal 队列并发配合） |
| 分布式锁 | 批量提交等需要互斥的操作 |
| 实时扇出 | Pub/Sub 频道 `project:{id}`，各 API 实例的 SSE Hub 订阅 |

### 8.3 实时推送

浏览器订阅 `GET /projects/{id}/events`（SSE）→ API 实例订阅 Redis 频道 → 收到“对象类型、ID、新版本”→ 前端刷新对应查询。断线重连后前端全量刷新当前页面数据。

## 9. 画布

### 9.1 节点分类（与 LibTV 对齐）

采用与 LibTV 相同的“节点类型 × 节点动作”分类（PRD-02 §3.2）：

| 节点类型 | 动作 | 说明 |
| --- | --- | --- |
| 文本 `text` | resource / generate | 文案、提示词、备注；生成走 `text.structured` |
| 图片 `image` | resource / generate / edit | 参考图、关键帧、自由生图 |
| 视频 `video` | resource / generate / edit | 图生视频、全能参考、自由生成 |
| 音频 `audio` | resource / generate | 台词音频、上传音频 |
| 脚本 `script` | resource | 镜头表视图（绑定某场或某集的 Shot 列表） |
| 参考 `reference` | resource | 备注与示意连线 |
| 素材预设 `material_style` / `material_lens` | resource | 风格 / 镜头语言预设，连到生成节点即套用（REQ-01 CNV-08） |
| 分组 `group` | — | 分组框 |

`resource` 节点引用已有对象（MediaAsset、Shot 列表等）；`generate` / `edit` 节点保存生成配置，运行时创建 Operation。以下按数据归属再分三类：


| 类别 | 例子 | 数据归属 |
| --- | --- | --- |
| 业务对象节点 | 镜头表、镜头、角色 / 造型、场景、道具、台词音频 | 业务对象归各 Owner；节点只存 `ref_type + ref_id` 与布局 |
| 素材与生成节点 | 图片、视频、音频、文本素材；生成节点（能力 + 模式 + 模型 + 参数） | 素材是 MediaAsset；生成节点配置归画布，运行时创建 Operation |
| 注释节点 | 便签、分组框、风格 / 镜头语言素材节点 | 画布 |

### 9.2 连线

| 类型 | 语义 |
| --- | --- |
| `input` | 素材 / 资产 → 生成节点的输入角色；等价于 OperationInput |
| `reference` | 素材 / 资产 → 镜头；等价于该镜头 ReferenceSet 的一项（流水线视图同步可见） |
| `promote` | 自由生成的结果 → 业务槽位；等价于选定命令 |
| `annotation` | 纯视觉注释 |

### 9.3 同步

- 布局命令：`AddNodes`、`MoveNodes`、`ResizeNode`、`DeleteNodes`、`Group`、`Ungroup`、`UpdateNodeConfig`、`AddAnnotation`。
- 业务命令（参考、选定、删除镜头）转调业务上下文；画布只记录布局结果。
- 前端乐观应用 + 撤销栈；批量提交带 `expected_revision` 与幂等键；409 时基于最新文档重放。
- 画布文档保留快照，可回到任一快照。

## 11. 数据存储

| 数据 | 存储 | 说明 |
| --- | --- | --- |
| 业务实体、版本、依赖、Operation、注册表、画布、账本、Outbox | PostgreSQL（业务库） | 按上下文分 schema；依赖图用关系表 + 递归 CTE；golang-migrate 版本化迁移 |
| 工作流历史与可见性 | PostgreSQL（Temporal 独立库） | 不作为业务事实源 |
| 会话、缓存、限流计数、锁、Pub/Sub | Redis | 可丢失、可重建 |
| 领域事件 | Kafka | 按保留策略保存；审计与明细由消费者落库 |
| 媒体字节 | S3 协议对象存储：开发 MinIO，生产火山引擎 TOS；前置 CDN | 按项目前缀；数据库存 key、hash、元数据；多尺寸缩略图预生成；临时对象按生命周期规则清理 |

**媒体上传**：前端申请预签名 URL → 直传 MinIO → 通知 API → 启动探测工作流（media 队列）→ MediaAsset `ready`。未 ready 或审核未通过的素材不能被引用。

**媒体属性**：来源（上传 / 哪个 Operation / 哪个供应商调用）、合规状态（审核结果、肖像授权记录、AIGC 标识状态）。

## 12. 失败路径

| 场景 | 行为 |
| --- | --- |
| 供应商提交超时 / 响应丢失 | `unknown` → 对账；不支持查询则 `manual`，不自动重买 |
| 供应商限流 | 队列并发 + Redis 配额排队；Activity 退避重试 |
| 供应商成功但下载失败 | 只重试 Ingest Activity |
| 输入超出模型限制 | 报价阶段拒绝并说明 |
| 输入素材被更新 | 已有输出标记过期，不阻止查看与使用 |
| LLM 输出不合法 / 原文位置不符 | Harness 有限次修复；仍失败则该步骤失败，保留原始输出，可单独重试 |
| Agent 服务不可用 | Activity 重试；超过次数工作流进入失败，可手动重试 |
| Worker 崩溃 | Temporal 从历史恢复；Activity 幂等 |
| Kafka 暂不可用 | Outbox 积压，恢复后继续投递；实时通知延迟，业务不受影响 |
| Redis 暂不可用 | 缓存回源 PostgreSQL；实时推送降级为前端定时刷新；限流按保守默认值 |
| MinIO 暂不可用 | 上传与接管失败并重试；已有数据可浏览（受影响的媒体显示不可用） |
| 人工配置在任务运行中被修改 | 工作流只写结果字段，不覆盖配置 |
| 旧页面选定 | 409，前端刷新 |
| 预算不足 | 报价阶段拒绝 |
| 内容审核不通过 | 输出不可选定 |
| 画布并发冲突 | 409 + 最新文档，前端重放 |

## 13. 安全与可观测

- **鉴权**：管理员创建账号；Redis 会话 + HttpOnly Cookie；命令层统一校验项目权限。
- **内部通信**：Agent 服务不对公网暴露；`agent-api` 校验服务间令牌；Temporal、Kafka、Redis、MinIO 只在内网并启用认证。
- **密钥**：供应商凭据只注入 Agent 服务；MinIO 管理凭据只在 Go；前端与日志不出现明文。
- **媒体**：MinIO 桶私有，短期签名 URL 访问。
- **审计**：选定、确认、预算、价格、凭据、注册表变更写 Outbox，由 audit 消费者归档。
- **可观测**：OpenTelemetry 贯穿 API → 工作流 → Activity → Agent 服务 → 供应商；指标（队列积压、失败率、`unknown` / `manual` 数量、未释放预留、Outbox 积压、Kafka 消费延迟）进入 Prometheus / Grafana；日志进入 Loki；Temporal UI 查看工作流。
