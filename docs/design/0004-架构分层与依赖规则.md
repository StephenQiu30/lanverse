# 架构分层与依赖规则

- 目标状态：已接受
- 适用范围：Frontend、Backend、Agent、运行时契约与数据所有权

## 结论

Lanverse 采用“按业务职责垂直组织、依赖指向内层、部署边界决定网络边界”的分层。Domain 不依赖框架或基础设施；跨模块只通过公开契约；跨进程使用正式 RPC/Event；Frontend、Agent、Workflow、Provider 与投影都不能绕过 Application 层直接修改业务事实。

```text
Inbound Adapter
      ↓
Application / Use Case
      ↓
Domain
      ↑
Port ← Outbound Adapter
```

Port 由使用它的业务模块拥有，Adapter 实现 Port。Application 负责事务、授权、幂等和用例编排；Domain 负责不变量和状态转换。

## Backend 分层

### Composition

`cmd/*` 与 `internal/bootstrap` 是组合根，负责读取配置、构造 Adapter、注入 Port、注册 Telemetry 和启动 Server/Worker。组合根可以依赖所有需要装配的模块，但不得放业务规则。

### Inbound Adapter

REST、SSE、gRPC Handler、Temporal Activity/Signal Handler 和 Kafka Consumer 只负责：

- 认证、协议校验和输入转换；
- 构造 Application Command/Query；
- 把业务错误映射为稳定协议错误；
- 传播 Trace、幂等键、Actor 和 Workspace Context。

Handler 不直接读写 Repository，不包含 Provider/SQL/Temporal 细节，不决定领域状态。

### Application

Application 层拥有用例、事务边界、授权、幂等、乐观锁、跨聚合协调、Outbox 写入与 Port 调用。它可以依赖 Domain 和本模块 Port，但不能依赖具体 pgx、Redis、Kafka、Temporal、MinIO 或 Provider SDK。

跨模块同步调用只能依赖目标模块显式公开的 Application Interface；接口参数使用语义明确的值对象和 ID，不共享数据库模型。

### Domain

Domain 包含 Entity、Value Object、Policy、State Machine、Domain Service 和 Domain Event。它不得依赖：

```text
HTTP / gRPC framework
pgx / sqlc generated query
Redis / Kafka / Temporal
MinIO / ObjectStore SDK
Provider SDK
OpenTelemetry implementation
其他模块的 Adapter 或 Repository
```

### Port 与 Outbound Adapter

Port 描述业务真正需要的最小能力，例如 `ObjectStore`、`GenerationGateway`、`AgentExecutionClient`、`WorkflowRunStarter`、`Clock`、`IDGenerator`。Adapter 位于基础设施侧，负责协议、重试、连接池和外部错误归一化。

Repository Port 以聚合为单位，不暴露通用 CRUD、SQL Builder 或跨模块 Join。查询投影可使用独立 Query Adapter，但不能把投影对象作为 Domain Entity 回写。

## Backend 模块依赖

允许：

```text
cmd/<binary> → bootstrap
bootstrap → adapters + applications
adapter → application command/query + port
application → domain + owned ports + public module interfaces
domain → standard library / local domain types
```

禁止：

```text
domain → adapter/framework
module A repository → module B table/model
module A service → module B internal package
HTTP handler → SQL/provider SDK
event consumer → arbitrary cross-module writes
```

如一个模块只做参数转发且没有授权、事务、策略或协议转换价值，则不创建空 Application/Service 层。

## 运行程序与网络边界

目录不是服务。网络边界由五个 Go Binary、Python Agent 和 Collaboration 服务的实际部署决定：

- 同 Binary：Go Interface，保留同一事务的可能性。
- Backend Binary 之间：gRPC/Protobuf，声明 deadline、重试和幂等语义。
- Backend 与 Agent：gRPC/Protobuf + Run-scoped execution token。
- 业务事实广播：Kafka Event，不用于同步请求响应。
- 长任务与等待：Temporal Task Queue/Signal。
- Browser 查询/命令：REST/JSON；AI 流：SSE；Canvas 协作：Yjs WebSocket。
- 大文件：Presigned URL，Browser 直连 ObjectStore。

不得为了模块解耦强制 gRPC，也不得因为代码同仓库就绕过已部署的进程契约。

## Frontend 分层

下图中 `A → B` 表示 A 可以导入 B；没有箭头即默认禁止跨包导入：

```text
apps/web ─────→ auth, ai, canvas, sdk
apps/collab ──→ sdk（仅协作协议与 Backend client）
canvas ───────→ ai, ui, sdk
ai ───────────→ ui, sdk（类型或注入的 transport）
auth ─────────→ ui, sdk
ui ───────────→ （无 Lanverse package 依赖）
sdk ──────────→ （无 Lanverse package 依赖）
```

更精确的依赖规则：

- `apps/web` 可以依赖所有发布 Package，只负责路由、Layout、Server/Client Boundary 和业务页面组合。
- `apps/collab` 通过 `sdk` 的协作协议和服务端 Backend client 校验短期房间授权，不依赖浏览器侧 `auth` package 或 Web 页面组件。
- `packages/canvas` 可依赖 `ui`、明确的 `ai` 展示组件、`sdk` 类型和协作 Client；不得导入 `apps/web`。
- `packages/ai` 依赖 `ui` 和 SDK 类型，不依赖 Canvas 或具体页面。
- `packages/ui` 是无业务语义的基础组件，不依赖 `ai`、`canvas`、SDK 实例或路由。
- `packages/sdk` 是 OpenAPI/Proto 生成契约和 Transport Adapter，不包含 React 组件或业务状态。
- `packages/auth` 负责会话与权限 Client，不拥有 Workspace 业务页面。

Remote Server State 只由 TanStack Query 管理；URL 管理可分享导航状态；Yjs 管理 Canvas 协作工作副本；Zustand 只管理跨组件短期交互；React Hook Form + Zod 管理表单；局部组件状态留在 React。不得把同一事实复制到多个 Store。

详细页面、状态和 Canvas 边界见 [前端应用架构](1001-前端应用架构.md)。

## Agent 分层

```text
api → runtime → executor → harness
                    ↓
           context / tool / skill / prompt
                    ↓
        client ports → gRPC adapters
```

- `api` 只处理 gRPC 和 Schema 转换。
- `runtime` 管理 Run 生命周期、预算、取消、Telemetry 和 Executor 选择。
- `executor` 提供 Structured、ToolLoop、LangGraph 三种有限执行语义。
- `harness` 组合领域 Agent 阶段、确定性 Gate 与有限 Repair。
- `definitions` 保存版本化 Agent/Skill/Prompt/Rubric/Policy，不直接写代码状态。
- `client` 只能调用 Model Gateway 与 Tool API；不包含数据库、对象存储、任意 Shell 或任意网络 Client。

Agent 输出永远是结构化 Candidate/Decision Proposal。只有 Backend Application 可以在授权、版本与确定性校验后写入正式领域状态。

## 数据所有权

每张表、Topic、索引、Bucket 前缀和 Temporal Workflow 类型都必须有唯一 Owner 模块：

- Owner 定义写入状态机、Migration、事件和恢复方式。
- 其他模块通过接口或投影读取，不能直接写 Owner 的表。
- 跨聚合强一致仅在同一事务/同一 Binary 且有明确 Application 用例时允许。
- 跨服务使用 Saga/Temporal Compensation 或最终一致投影，不使用分布式数据库事务。
- Elasticsearch Index、Redis Key 和 Kafka Consumer State 都不是绕过 Owner 的替代写路径。

实施前必须维护“资源 → 唯一 Owner → 存储 → Command/Query → Event → 验收门”清单，见[资源所有权与交付台账](../plan/0008-资源所有权与交付台账.md)。Snapshot 和 Projection 只读；业务双写禁止。

## 契约所有权

```text
backend/api/openapi  公共 REST/SSE 事实源
backend/api/proto    Backend RPC 事实源
backend/api/event    Kafka Event Schema 事实源
backend/api/gen      生成结果，不手改
agent/api/proto      Agent RPC 事实源
frontend/packages/sdk 生成的 Web Client
```

契约变更顺序为：Design/设计决策 → Source Schema → Compatibility Test → 生成代码 → 实现 → E2E。不能先手改生成 Client 或同时维护两份 DTO/错误体系。

## 横切能力

认证、授权、幂等、Trace、日志脱敏、Cost、Quota 和错误模型是显式契约，不是任意 `utils`：

- Context 从协议入口建立并向内传递，Domain 只接收需要的 Actor/Policy 值。
- Cost 采用 Estimate/Reserve/Settle；失败或取消必须释放或结算 Reservation。
- 高成本命令、权限校验和 Callback 验签默认 fail closed。
- Error Code 稳定、可机器处理；日志不能替代 API 错误或业务审计。
- 统一 Trace 标识跨 HTTP、gRPC、Temporal、Kafka、Agent、Provider 和 Artifact 传播。

## 架构验证

每个项目独立保留架构测试：

- Go：Import Direction、Domain 禁止依赖、跨模块内部导入、SDK/凭据边界、Contract 生成漂移。
- Agent：Tool Allowlist、无 DB/Storage/Shell/任意网络依赖、预算有限、Schema/Prompt/Skill 版本完整。
- Frontend：Package Dependency Graph、生成 SDK 漂移、Route/Feature 依赖、Server/Client Boundary。
- Runtime：OpenAPI/Proto/Event compatibility、Temporal replay、Kafka 幂等/重放、Storage contract、全链 E2E。

上述测试必须从项目建立时即成为交付门禁；测试文件存在不代表门禁通过，只有实际执行结果进入 Acceptance 后才可用于完成判断。
