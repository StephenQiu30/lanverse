# 架构分层与依赖规则

- 目标状态：已接受
- StoryGraph 依赖复核：已接受（`SG-D07`，2026-08-27）
- 适用范围：Frontend、Backend、Agent、Workflow、Kafka/ELK 投影、运行契约与数据 Owner
- 依据：[系统总体架构](0003-系统总体架构.md) · [领域语言与模块命名规范](0006-领域语言与模块命名规范.md) · [StoryGraph 内容图与 DAG 创作画布设计](0010-StoryGraph内容图与DAG创作画布设计.md) · [后端语言与运行边界策略](2003-后端语言与运行边界策略.md)

## 结论

Lanverse 按业务职责垂直组织，依赖只指向语义 Owner 和内层契约。部署边界决定是否需要网络契约，目录不自动成为服务。Frontend、Agent、Temporal、Provider、Kafka Consumer 和 Elasticsearch Projection 都不能绕过 Backend Application 直接修改业务事实。

```text
Inbound Adapter
      ↓ Command / Query
Owner Application / Use Case
      ↓
Owner Domain + Compiler / Policy
      ↑
Owned Port ← Outbound Adapter
```

Port 由使用它的 Owner 模块定义，Adapter 实现 Port。Application 负责授权、事务、幂等、乐观锁、跨聚合协调与 Owner Apply；Domain/Compiler 负责纯业务不变量和确定转换。只有出现首个真实用例时才创建层和文件，不为形式完整预建空 `service/repository/manager/utils`。

## Backend 分层

### Composition Root

`backend/cmd/*` 与 `backend/internal/bootstrap` 只负责读取配置、构造 Adapter、注入 Port、注册 Telemetry 和启动 Server/Worker。组合根可以依赖所有必需实现，但不得放置业务规则或通用业务状态。

### Inbound Adapter

REST/SSE Handler、私有 Agent Handler、Temporal Activity/Signal Handler 和 Kafka Consumer 只负责：

- 认证、协议/Schema 校验和输入转换；
- 构造 Owner Application Command/Query；
- 映射稳定协议错误；
- 传播 Trace、幂等键、Actor、Workspace 和精确版本上下文。

Handler/Consumer 不直接读写 GORM Model/Repository，不调用 Provider SDK，不决定领域状态。Kafka Consumer 必须调用明确 Owner 的幂等 Application 用例，不得成为“可以更新任何模块”的后门。

### Application

Application 层拥有用例、事务边界、授权、幂等、乐观锁、Outbox 写入与 Port 调用。它可以依赖本模块 Domain/Compiler、本模块 Port 和其他模块显式公开的 Application Interface，不得依赖对方 `internal` 实现、GORM Model 或 Repository。

跨聚合强一致只在同一 Go Binary、同一 PostgreSQL 事务且有明确 Owner Application 用例时使用。跨进程长周期协调使用 Temporal，已提交异步通知使用 Outbox/Kafka，不使用分布式数据库事务。

### Domain / Compiler

Domain 包含 Entity、Value Object、Policy、State Machine、Domain Service 和 Domain Event。Compiler 是 Owner 内的确定纯转换组件，接收已校验的不可变输入，返回值或稳定错误，不直接发送网络请求或开启事务。

Domain/Compiler 不依赖：

```text
HTTP / SSE / private transport framework
GORM / database driver / SQL
Redis / Kafka / Temporal
MinIO / ObjectStore SDK
Provider SDK / Codex CLI
Elasticsearch / Logstash / OpenTelemetry implementation
other module adapters / repositories / internal packages
```

### Port 与 Outbound Adapter

Port 只描述当前业务用例真正需要的最小能力，例如 `ObjectStore`、`AgentCandidateClient`、`GenerationProvider`、`WorkflowRunStarter`、`EventPublisher`、`SearchProjectionWriter`、`Clock` 和 `IDGenerator`。Adapter 负责具体协议、超时、重试、连接池和外部错误归一化。

Repository Port 以聚合/版本化事实为单位，不暴露通用 CRUD、SQL Builder、“Save Anything”或跨模块 Join。查询投影可使用独立 Query Adapter，但投影 DTO 不得当作 Domain Entity 回写。

## StoryGraph / Harness / Owner Apply 依赖方向

```text
Temporal Activity / API Command
            ↓
Production Application
            ├──▶ AgentCandidateClient Port ──▶ Private Agent Adapter
            │                                  ↓
            │                           StoryGraphHarness
            │                                  ↓
            │                    Candidate + Evidence + Result Hash
            ▼
Candidate Validation / Human Gate / Owner Apply
            ↓
StoryGraph Compiler / Production Domain
            ↓
GORM Repository + Transactional Outbox
```

方向不得反转：

- `StoryGraphHarness` 不导入 Go Domain、GORM Model、Kafka Schema 或 Owner Repository；
- `StoryGraphCompiler` 不调用 Agent/Provider，只消费已验证的 Candidate/Owner 输入；
- Owner Apply 由 Production/Storyboard/Asset 等精确 Application 用例执行，不创建全局 `ApplyCandidateService`；
- Agent 只返回结构化 Candidate/Patch，不返回可直接执行的业务 Command；
- Backend 分配正式 ID、校验预期版本、CAS 切换 Head、写入业务事实和 Outbox。

`StoryGraphVersion`、`AuthoringRevision.Graph`、`WorkflowDefinitionVersion` 与 Temporal History 只能通过各自 Owner 的 Query/Command 建立关联，不共享 Repository、Schema 或 Compiler。

## 运行程序与网络边界

目录不是服务。当前运行边界只按真实消费者创建：

- 同一 Go Binary：使用显式 Go Interface，保留同一事务的可能性；
- `lanverse Backend ↔ agent-runtime`：当前使用已接受的私有 HTTP/JSON 契约和签名 Run-scoped Grant；
- 长任务与等待：Temporal Task Queue/Signal；
- 已提交业务事实：Kafka Event，不用于同步请求/响应；
- Browser 查询/命令：REST/JSON，流式状态：SSE；
- 大文件：Presigned URL，Browser 直连 ObjectStore。

不为未来 `model-gateway`、`media-worker`、协作 App 预生成 gRPC/Protobuf 或空 Binary。若后续拆进程，必须先有真实故障域/资源/凭据隔离需求和单独 Design。

## Frontend 依赖

当前 Frontend 是单一 Next.js 应用，测试独立位于 `frontend/tests`。不为未来协作、通用 Canvas 或设计系统预建 monorepo package。

```text
src/app            → src/features + src/components + src/api
src/features       → owned components/hooks + shared UI/API types
src/components/ui  → framework/primitives only
src/api            → generated/typed transport only
```

- Route 只组合页面和 Server/Client Boundary，不复制业务状态机；
- Feature 不导入另一 Feature 的内部实现，真实共享契约下沉到有明确所有者的 API/type/UI 边界；
- `Story Lens` 只通过 Backend Query 读取 StoryGraph View，不在前端计算第二份业务图；
- Remote Server State 只在已选定 Query 层中管理，URL 只保存可分享导航状态，局部交互状态留在组件/Feature；
- Yjs/Hocuspocus 和可写 Authoring Canvas 是延后边界。

详细 Frontend 决策在 `SG-D14/SG-D15` 激活时同步，本文不预先固定新 package 或 State Library。

## Agent 依赖

```text
private API
    ↓
agent/app/candidate_runtime
    ↓
StoryGraphHarness
    ├──▶ skill registry → agent/skills/build-storygraph
    └──▶ provider port → controlled Codex CLI adapter
    ↓
strict Pydantic Candidate Result
```

- Candidate Runtime 严格消费 Backend-owned Envelope/Stage/Policy，不维护第二份业务定义；
- Harness 只注入当前 Stage 明确引用的 Bundle Reference，不递归扫描所有 Markdown；
- Provider Adapter 只能使用 Backend 冻结的 Model/Schema/Budget/Deadline，本地 Codex CLI 不读取用户级/项目级 Codex 配置；
- Agent 不导入数据库、ObjectStore、Kafka、Elasticsearch、Temporal 或 Backend 业务 Client；
- 当前不引入 ToolLoop/LangGraph Executor，Temporal 是唯一跨步骤持久 Workflow Engine。

Agent 测试只位于 `agent/tests`，覆盖 Bundle Hash、Stage/Schema/Policy、canonical fixture、工具/网络禁止边界和真实 Codex 合约。

## 数据与投影所有权

每个 PostgreSQL Model/Record、Topic、Consumer Group、Elasticsearch Index/Alias、Bucket Prefix 和 Temporal Workflow Type 必须有唯一 Owner：

- PostgreSQL Schema 只来自 Backend 唯一 GORM Model Catalog，不存在 Migration、Raw SQL 或第二 ORM 事实源；
- 其他模块通过公开 Query/Command/Projection 读取，不直接写 Owner Model；
- Kafka 只传输同一事务内写入 Outbox 的已提交事件，Consumer 使用 Inbox/业务幂等键收敛至少一次投递；
- Elasticsearch 业务索引只由 Search Projection Writer 写入，必须能从 PostgreSQL 重建；
- Backend 脱敏 JSON → fail-open TCP → Logstash → Elasticsearch Log Index；日志不经过 Kafka，并与业务 Event/Index 保持独立 Schema 和 Index；
- Snapshot/Projection 只读，不能作为 Owner Apply 的反向输入。

资源所有权随后续唯一 Plan 的真实任务逐项固定，当前不从旧 `0008` 计划领取 StoryGraph 任务或预建资源。

## 契约所有权

```text
backend/api/openapi                 public REST/SSE source
backend/internal/<owner>            Command/Query/Event semantic owner
backend/internal/agent              Agent Envelope/Stage/Policy owner
backend/internal/eventing           Kafka Envelope/Outbox/Inbox owner
agent/app/candidate_runtime         strict private-contract consumer
agent/skills/build-storygraph       StoryGraph guidance source
backend/tests + agent/tests         canonical wire fixtures and contract checks
frontend/src/api                    generated/typed public client
```

契约变更顺序为 `Design → Red Contract Test/Fixture → Owner Schema → Implement → Cross-language Contract → E2E`。只在已接受传输格式确实需要生成时创建生成目录，不同时维护两份 DTO、状态枚举或错误体。

## 横切能力与架构验证

认证、授权、幂等、Trace、日志脱敏、Cost、Quota 和错误模型是显式契约，不是任意 `utils`。Context 从协议入口建立并向内传递，Domain 只接收必要的 Actor/Policy 值；高成本命令、权限校验和 Callback 验签默认 fail closed。

架构测试按项目独立放置：

- `backend/tests/architecture`：Import Direction、Domain/Compiler 禁止依赖、跨模块 internal 导入、GORM Catalog 唯一性、Agent/Provider/Kafka/Projection 写入边界；
- `agent/tests/architecture`：无 DB/Storage/Kafka/Temporal/任意 Shell/Web/文件写依赖、Bundle 唯一入口、有界预算和严格 Schema；
- `frontend/tests/architecture`：Route/Feature/UI/API 依赖方向、Story Lens 只读与 Server/Client Boundary；
- Runtime/Contract：OpenAPI/private contract、Temporal replay、Kafka 幂等/重放、Elasticsearch Reindex、ELK 日志查询、Storage contract 和完整 E2E。

测试文件存在不代表门禁通过；只有当次 CI/验收真实命令和结果才能形成完成证据。
