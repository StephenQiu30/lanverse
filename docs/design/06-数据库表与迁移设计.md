# 数据库表与迁移设计

## 1. 决策与物理约定

应用只连接 PostgreSQL 数据库 `lanverse`，20 张应用表统一位于既有 `public` schema，不创建第二 schema。运行时代码使用 `asyncpg` 与参数化 SQL，不定义 ORM Model、SQLAlchemy Metadata 或 autogenerate；Alembic 只负责按版本执行已经评审的根 `sql/`，`alembic_version` 不属于应用表。§3 的 exact-set 中 19 张业务事实由 DESIGN-02 的六模块拥有，技术表 `idempotency_records` 由根 `infrastructure/idempotency` 拥有并复用调用方数据库事务，不构成第七业务模块；不增加用户、权限、通用审计、模型配置、Shot、SpeechLine 或授权表。

- 表/列/约束使用 `snake_case`。主键固定 `pk_<table>`，单表 CHECK 固定 `ck_<table>_invariants`，其余 UQ/FK/索引名称以根 SQL 中的显式名称为准；校验器断言全局唯一且不超过 PostgreSQL 63 字节，不再生成哈希命名。主键均为应用生成 UUIDv4，无数据库默认；全部 FK 直接定义在所属表的 `CREATE TABLE` 中，固定为 `MATCH SIMPLE NOT DEFERRABLE INITIALLY IMMEDIATE ON UPDATE RESTRICT ON DELETE RESTRICT`，不级联删除、不使用后置 `ALTER TABLE`。
- 字段记法：`u=uuid`、`t=text`、`v(n)=varchar(n)`、`i=integer`、`b=bigint`、`j=jsonb`、`z=timestamptz`、`h=varchar(64)`；`?` 表示可空，未标记均 `NOT NULL`，`=x` 表示数据库默认。
- 时间统一 UTC；`created_at/updated_at=z=now()`，应用在更新时显式改 `updated_at`；`version=i` 必须大于 0，`resource_version=b=1`。哈希字段满足 `^[0-9a-f]{64}$`。
- 状态使用 `text + CHECK`，不用 PostgreSQL ENUM；JSONB 至少检查 object/array 类型。所有 FK 建 B-tree 索引，若已是某唯一/组合索引的最左前缀则不重复创建。
- 版本/快照/事件/媒体谱系永久保留；MVP 没有 DELETE API、soft delete、TTL 或数据库触发器。不可变性由应用用例、权限与集成测试共同保护。

### 3.2 Partial 与普通索引 exact-set

- current UQ：`uq_source_revisions_current(episode_id) WHERE status='confirmed'`、`uq_script_versions_current(episode_id) WHERE status='confirmed'`、`uq_creative_asset_versions_current(asset_id) WHERE status='confirmed'`、`uq_shot_spec_versions_current(episode_id) WHERE status='confirmed'`、`uq_subtitle_versions_current(episode_id) WHERE status='confirmed'`。
- origin UQ：`uq_script_versions_origin_task(origin_task_id) WHERE origin_task_id IS NOT NULL`、`uq_creative_asset_versions_origin_task_asset(origin_task_id,asset_id) WHERE origin_task_id IS NOT NULL`、`uq_shot_spec_versions_origin_task(origin_task_id) WHERE origin_task_id IS NOT NULL`。
- 执行 UQ：`uq_production_attempts_provider_key(provider_id,provider_request_key) WHERE provider_request_key IS NOT NULL`、`uq_production_attempts_provider_request_id(provider_id,provider_request_id) WHERE provider_request_id IS NOT NULL`、`uq_render_snapshots_initial_task(initial_task_id) WHERE initial_task_id IS NOT NULL`。
- 采用 UQ：`uq_generation_candidates_ready_primary(task_id,usage_type,usage_id,input_version_id,input_hash) WHERE status='ready' AND output_slot='primary'`、`uq_adoptions_active_slot(usage_type,usage_id,input_version_id,input_hash) WHERE status='active'`。
- partial index：`ix_production_tasks_nonterminal(status,updated_at) WHERE status IN ('queued','running','cancelling','unknown')`、`ix_task_jobs_pending(next_attempt_at,created_at) WHERE state='pending'`、`ix_task_jobs_leased(lease_until) WHERE state='leased'`、`ix_media_versions_sha256(sha256) WHERE sha256 IS NOT NULL`。
- query index：`ix_projects_created_at(created_at DESC)`、`ix_production_tasks_episode_created_at(episode_id,created_at DESC)`、`ix_task_events_task_occurred_at(task_id,occurred_at)`、`ix_media_objects_episode_created_at(episode_id,created_at)`、`ix_generation_candidates_slot_created_at(episode_id,usage_type,usage_id,input_version_id,input_hash,created_at DESC)`、`ix_adoptions_episode_slot_created_at(episode_id,usage_type,usage_id,input_version_id,input_hash,created_at DESC)`；版本/Attempt/Delivery 历史使用 full UQ 反向扫描。

每个 §3.1 FK 按本地列顺序建立 B-tree；仅当既有 PK/full UQ/full query index 的最左 N 列完全相同，或 nullable FK 已由同列 partial UQ 覆盖时省略。所需 partial、查询与 FK 支撑索引直接跟随所属表的 `CREATE TABLE` 写在同一逐表文件中；SQL/catalog 测试检查名称唯一、长度、归属和索引 exact-set，不生成隐式索引。

### 3.3 Enum/CHECK exact-set

每表只建立一个 `ck_<table>_invariants`。以下是 SQL helper 的编译时宏，不创建数据库函数：`H(c)=(c ~ '^[0-9a-f]{64}$')`、`HN(c)=(c IS NULL OR H(c))`、`K(c)=(c ~ '^[A-Za-z0-9._:-]{8,128}$')`、`NE(c)=(char_length(btrim(c))>0)`、`IFF(p,q)=((p AND q) OR ((NOT p) AND (NOT q)))`、`VS=(status IN ('draft','confirmed','superseded') AND IFF(status<>'draft',confirmed_at IS NOT NULL))`。生成器按数据字典列序先追加所有非空 `h` 的 `H`、可空 `h?` 的 `HN`、`version/resource_version/task_resource_version>0`，再按 §4 artifact 根类型追加 `jsonb_typeof(c)='object|array'`（可空列外包 `c IS NULL OR ...`），最后追加下列对应表达式；每层保留括号并用 `AND` 连接，标准 SQL 与 catalog 测试使用同一规范化规则比较。

```sql
projects := NE(title) AND char_length(title)<=120 AND status='active' AND aspect_ratio='9:16' AND width=720 AND height=1280 AND fps=24 AND timebase=90000
episodes := target_min_ticks=2700000 AND target_max_ticks=5400000
source_revisions := VS AND codepoint_count=char_length(content) AND codepoint_count BETWEEN 300 AND 3000 AND normalization_version='text-normalization-v1' AND rights_basis IN ('original','licensed') AND (parent_id IS NULL OR parent_id<>id)
script_versions := VS AND NE(schema_version) AND (parent_id IS NULL OR parent_id<>id) AND num_nonnulls(origin_task_id,model_profile_id,provider_id,model_id,prompt_version) IN (0,5) AND (model_profile_id IS NULL OR NE(model_profile_id)) AND (provider_id IS NULL OR NE(provider_id)) AND (model_id IS NULL OR NE(model_id)) AND (prompt_version IS NULL OR NE(prompt_version))
creative_asset_versions := VS AND asset_type IN ('character','scene','visual_style') AND NE(name) AND NE(description) AND (parent_id IS NULL OR parent_id<>id)
shot_spec_versions := VS AND shot_count=jsonb_array_length(shots_json) AND shot_count>=0 AND total_duration_ticks>=0 AND (parent_id IS NULL OR parent_id<>id) AND (status<>'confirmed' OR (shot_count BETWEEN 6 AND 10 AND total_duration_ticks BETWEEN 2700000 AND 5400000))
```

## 4. JSONB 严格契约 exact-set

22 个 JSONB 列均使用 owning module `application/contracts/` 中的 Pydantic v2 严格模型；本节的列到模型映射、§4.1 哈希规则和 §5 应用不变式是实现前唯一规范，不在 `docs/` 中维护重复的 JSON/Python artifact。对象模型固定 `ConfigDict(strict=True, extra='forbid', frozen=True)`，数组使用具名 `RootModel[list[Item]]` 且 Item 同样 forbid extra，禁止裸 `dict[str,Any]`/`list`。行标量 `type/capability/event_type/media_kind` 只作为选择下表 variant 的校验上下文，不在 JSON 复制第二份状态；模型字段必须明确 required/null/default/min/max/enum。保存前统一执行 `model_validate` → `model_dump(mode='json', exclude_none=False, exclude_defaults=False)` → 所有字符串 NFC；持久化值必须等于该完整 dump，因此 §3 不保存裸 `{}` 默认。只有下表标记的不可变 JSON 再对完整 dump 执行 RFC 8785→SHA-256。

| JSONB 列 | Pydantic 契约模型 | 哈希绑定 |
| --- | --- | --- |
| `script_versions.content_json` | `ScriptContent` | `content_hash` |
| `shot_spec_versions.asset_version_refs_json/shots_json` | `AssetVersionRefs` / `ShotSpecList` | 合并 `content_hash` |
| `idempotency_records.response_ref_json` | `IdempotencyResponseRef` | 无 |

PLAN-06～08 必须把表中模型落实为 Pydantic `model_validator` 和可执行测试：`event_type` 必须选择唯一 `TaskEventData` variant，`media_kind` 必须选择唯一 Probe variant；命令输入可使用模型默认值，但数据库只接收展开后的全字段 dump。数组 RootModel 的排序、唯一、连续、跨数组对应、tick 关系与总量由模型测试固定，不依赖无版本的自由 JSON。

### 4.1 哈希输入 exact-set

定义 `HJSON(x)=lowerhex(SHA-256(UTF8(RFC8785(deep_NFC(x)))))`、`HTEXT(x)=lowerhex(SHA-256(UTF8(NFC(x))))`；UUID 字符串一律为小写带连字符形式，完整 dump 保留 required null，数组保持 Schema 规定顺序。除下列业务内容外，不把数据库 ID、版本号、状态、父级、来源 Task/Provider、时间或资源版本隐式混入哈希。

- Source `sha256=HTEXT(content)`；持久化的 SpeechLine JSON 必须含 `text_hash=HTEXT(text)`；Provider/HTTP 写入 DTO 排除该字段，应用先丢弃任何供应方派生值、注入服务端计算值，再验证持久化模型，保存、确认和消费入口继续复算；Script `content_hash=HJSON(content_json)`。
- CreativeAsset `content_hash=HJSON({asset_type,name,description})`；单个 Shot `content_hash=HJSON(ShotSpec 去掉 content_hash 后的完整对象)`；ShotSpecVersion `content_hash=HJSON({asset_version_refs:asset_version_refs_json,shots:shots_json})`。
- Subtitle `content_hash=HJSON({input_refs:input_refs_json,language,cues:cues_json})`；Render `recipe_hash=HJSON(normalization_json)`，`content_hash=HJSON({input_refs:input_refs_json,segments:segments_json,normalization:normalization_json})`。
- Submission `parameters_hash=HJSON(parameters_json)`，`content_hash=HJSON({type,capability,input_refs,prompt,parameters,model_profile_id,provider_id,model_id,route_version,schema_version})`，nullable 字段也保留；IdempotencyRecord 与 RenderSnapshot 的 `request_hash` 使用 DESIGN-04 §4 的 HTTP wrapper；Candidate/Adoption `input_hash` 使用 DESIGN-04 §3.1 的各 usage wrapper。
- MediaVersion `sha256` 只对对象原始字节计算；任何保存/确认/创建快照入口都复算相关哈希并拒绝不一致，数据库只接收服务端派生值。

## 5. 状态、事务与并发

- 版本确认：`SELECT ... FOR UPDATE` 锁 Episode 或 asset 当前版本；旧 confirmed→superseded、新 draft→confirmed，partial UQ 兜底。draft 以 `resource_version` CAS 更新，confirmed/superseded 内容不可改。
- 非 Render 异步受理：一个 asyncpg transaction 写 SubmissionSnapshot、ProductionTask、初始 Attempt、TaskEvent、TaskJob 与 IdempotencyRecord；Task CAS 更新与 TaskEvent 追加也在同一事务。Provider 发送前先以独立短事务提交稳定 request key，提交成功后才允许外部调用。
- 版本分配：Episode 级先锁 `episodes` 行；asset 首版锁 Episode，后续锁该 asset 当前版本。版本只需单调，不承诺无缺口。
- TaskJob：Worker 按 `(next_attempt_at,created_at,id)` 用 `FOR UPDATE SKIP LOCKED` 领取 pending 行、写 `lease_owner/lease_until` 并置 leased；执行期间周期心跳续租。租约过期先按稳定 Provider request key 对账，再原子恢复 pending 或收敛结果；达到上限置 failed，不自动领取。
- Adoption：先 `SELECT episodes ... FOR UPDATE` 锁 Episode，再锁可能存在的 current active Adoption，supersede 后插入新 active；partial UQ 收敛并发双采用，不假设空 slot 有行可锁。
- Render 保持三个明确事务：Tx1（delivery）原子创建/复用 pending IdempotencyRecord 与 RenderSnapshot，回执只指 RenderSnapshot；Tx2（production_jobs）以 `(render-task,render_snapshot_id)` 创建/复用引用它的 `SubmissionSnapshot(type=render_episode)`、Task/Attempt/Event/TaskJob，不创建第二个 IdempotencyRecord；Tx3（delivery）锁 Episode、RenderSnapshot 与 Tx1 IdempotencyRecord，CAS 回填 `initial_task_id`，并把 Tx1 回执 completed 到 Task。Task 的 `snapshot_id` 始终是 SubmissionSnapshot ID；任一步崩溃后重放都按唯一键继续，不伪装跨模块原子事务。DeliveryVersion 只由 Render Job Handler 首次幂等执行时以 `render_task_id` UQ 创建；Task 在 Worker 领取前取消时不创建 Delivery。

`lanverse` 连接显式使用 PostgreSQL `READ COMMITTED`；每个 HTTP Handler、Job Handler、TaskJob 领取批次和以上 Tx1/Tx2/Tx3 各自从 asyncpg pool 获取 connection，并由边界层打开 transaction，Repository 不 commit。锁顺序固定为 Episode → 当前聚合/版本/Adoption（多行按 UUID 升序）→ 新子行；TaskJob 仅用独立短事务领取和续租，外部调用不持有数据库事务。唯一冲突翻译为稳定幂等/版本/采用冲突；deadlock、连接中断只允许在尚无外部副作用的整个事务上最多重试 3 次，Provider/MinIO/FFmpeg 调用后只重放以稳定键收敛的结果登记事务，不重放外部副作用。

普通 FK/CHECK 无法表达的应用不变式只允许以下 10 项，每项必须有事务级集成测试：

1. `INV-APP-01`：Source 确认事务锁定 Episode，将旧 confirmed 版本改为 superseded 后再确认新版本；`uq_source_revisions_current` 保证每个 Episode 最多一个 confirmed，读取当前 Source 直接查询该状态，不保存第二份指针。
2. `INV-APP-02`：同一 `asset_id` 的全部版本属于同 Episode；parent/source/origin Task 的类型与状态符合生成或派生路径。
3. `INV-APP-03`：Idempotency response_ref 按 resource_type 存在并属于 operation scope；pending 时 response_status/completed_at 必为空，response_ref 只能为空，或仅在 `renderEpisode` scope 指向同事务 RenderSnapshot；completed 时 response_status/ref/completed_at 全非空。同 scope/key 同 request_hash 重放，异 hash 冲突。
4. `INV-APP-04`：SubmissionSnapshot.input_refs 全部存在、同 Episode 且状态/hash/usage 合法，并满足 `JOBS-JSON-001` 的 type/capability/VersionRef exact-set；Task 通过复合 FK 引用同 Episode Snapshot，二者 type 一致，Script/Storyboard/Media/Render Scope 的全部目标值必须逐项等于对应 input_refs；render Snapshot 必须引用同 Episode RenderSnapshot。
5. `INV-APP-05`：Task/Attempt/Candidate/Media/Delivery 只按 DESIGN-03 单向转换；draft CAS、confirmed/superseded 内容及 Snapshot/Event/finalized Media 不可变；Task CAS 与同 resource_version Event 同事务。
6. `INV-APP-06`：TaskOutput 按 type 找到真实对象，其 origin/render Task 与 task_id 一致且同 Episode；TaskJob.task_id 与 payload 的 task/snapshot 精确一致，release_version 非空。
7. `INV-APP-07`：Candidate 的 MediaVersion 已由复合 FK 固定同 Attempt/slot；其 MediaObject 还须与 Task 同 Episode 且 kind 匹配 usage；ready 只指 ready Media，extra/迟到结果只 blocked。ready provider image 要求 `image/*`、ImageProbe、正 width/height；video 要求 `video/*`、VideoProbe、正 width/height/duration_ticks/timebase；audio 要求 `audio/*`、AudioProbe、正 duration_ticks/timebase；probe 的值必须与 MediaVersion 标量一致。
8. `INV-APP-08`：Adoption 复合 FK 固定同 Episode/slot Candidate；应用另验证 Candidate ready、输入仍兼容，并在同事务 supersede 旧 active 后插入新 active。
9. `INV-APP-09`：Script/Shot/Subtitle/Render JSON 中 Shot、SpeechLine、asset、Adoption、Media 引用均存在、同 Episode 且版本/状态/hash 合法，确认/快照入口复用同一 contract。
10. `INV-APP-10`：Render initial Task 与 Delivery render Task 均为 `render_episode` 且引用对应 RenderSnapshot；三件交付分别为 `mp4(video,ffmpeg)`、`srt(subtitle,application)`、`manifest(manifest,application)`，同 Episode、来源 final render Attempt，摘要/hash 一致。

## 6. `0001_mvp` 与回滚

根 `sql/` 是物理 Schema 唯一实现源：20 个 `NN_<table>.sql` 按 FK 依赖拓扑编号；每个文件只创建一张表，把该表的列/default/PK/UQ/FK/CHECK 直接写入 `CREATE TABLE`，并在同一文件追加该表所需索引。不设置公共关系/索引文件，不使用 `ALTER TABLE` 补约束。`backend/migrations/versions/0001_mvp.py` 只按数字顺序读取这些仓库 artifact 并由 Alembic connection 执行，不复制 DDL、不使用 autogenerate/Metadata。SQL 文件显式限定 `public.<table>`，不含 `CREATE DATABASE/SCHEMA`、psql 元命令、环境读取、测试数据或删除语句。

验证必须针对现有本地 PostgreSQL 中隔离创建的空 `lanverse` 测试库执行两次 `alembic upgrade head`，并直接比较 `pg_catalog` 与本文及根 SQL 定义的 20 张应用表、列/null/default、FK/UQ/CHECK/索引 exact-set；排除 `alembic_version`。正式回滚仅回退兼容制品并前滚修复 Schema，不执行破坏性 downgrade；任何验证脚本都不得删除或改写用户已有数据库。

## 7. Design 验收标准

- AC-DB-001-001：19 张模块业务事实表与六模块所有权一一对应，另有 1 张 API transport 幂等技术表；合计 20 张应用表 exact-set，无未编号表或缺失事实。
- AC-DB-001-002：根 `sql/` 只有 20 个逐表文件且可按编号直接解析；每列类型、null/default、内联 PK/FK、唯一、CHECK、所属表普通/partial 索引均与本文一致，所有 FK RESTRICT、无级联删除、无后置关系/索引脚本。
- AC-DB-001-003：版本确认、Task/Attempt、TaskJob lease、Adoption 与 Render 的事务/锁可由并发测试复现，唯一约束是最终兜底。
- AC-DB-001-004：22 个 JSONB 列均有具名版本化严格 Pydantic Schema 与明确责任；只有 hash-bearing 不可变 JSON 使用 canonical hash，不把深层引用冒充 FK。
- AC-DB-001-005：空测试库双 `upgrade head` 和 `pg_catalog` exact-set 有 PLAN-03 Test/Evidence；迁移回滚不删除业务事实。
- AC-DB-001-006：DESIGN-06 `accepted` 且 `database_design_ready: passed` 前，根 SQL 只允许静态评审/解析，仓库不存在 backend/frontend 应用脚手架、依赖、migration 或源码，且不得执行 DDL。
