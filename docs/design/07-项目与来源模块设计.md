# 项目与来源模块设计

## 1. 输入、状态与边界

本设计把 REQ-02 转换为 `project_catalog` 的可实现契约，当前随上游 Requirement 保持 `draft`。模块仅负责立项、唯一单集和不可变来源版本；不负责剧本、分镜、Task、媒体字节或交付。技术栈、HTTP 通用约定、物理表字段分别以 DESIGN-01、04、06 为唯一来源。

## 2. 职责与依赖方向

| 层/对象 | 责任 | 禁止 |
| --- | --- | --- |
| `domain` | `ProjectTitle`、`ProductionSpec`、`SourceText`、来源版本状态机 | 依赖 FastAPI、Pydantic 或 asyncpg |
| `application` | 创建/列表/读取项目，创建/确认/查询来源 | 触发 AI 或改写下游版本 |
| `infrastructure` | `projects/episodes/source_revisions` 参数化 SQL、Row Mapper | 通用 BaseRepository 或隐式 commit |
| `transport` | DESIGN-04 已定义 Operation 与 Problem Details 映射 | 自定义第二套 DTO/URL |
| `public.py` | 只导出 Project/Episode/Source 查询与快照 DTO | 暴露 Repository 或 Domain 内部类型 |

下游模块只能通过 `public.py` 读取已确认来源和制作规格，不能直接读表。

## 3. 用例与 HTTP 契约

| 用例 | Operation | 前置/输出 |
| --- | --- | --- |
| 创建项目 | `createProject` | 标题有效；单事务创建 Project+Episode，返回 `201` |
| 项目导航 | `listProjects/getProject/getEpisode` | 返回阶段摘要，不内嵌媒体 URL |
| 保存来源 | `createSourceRevision` | 要求 Idempotency-Key 和权利依据；返回新 draft |
| 确认来源 | `confirmSource` | 锁定 Episode，确认新版本并 supersede 旧版本 |
| 来源回溯 | `listSourceRevisions/getSourceRevision` | 历史完整且内容/哈希可对照 |

Transport 只转换 application contract。幂等记录与目标事实使用同一 asyncpg connection/transaction。

## 4. 领域与数据契约

- `Project` 是聚合根；MVP 创建后只有一个稳定 Episode，不提供新增第二集命令。
- `ProductionSpec` 固定 `9:16/720x1280/24fps/30～60s`，由服务端写入，不接受前端自由扩展。
- `SourceTextV1` 先 NFC、换行与首尾空白规范化，再校验 300～3000 Unicode 代码点、Han 字符和禁用代码点。
- `SourceRevision` 保存 `parent_version_id/status/content/character_count/content_hash/rights_basis/resource_version`；哈希是服务端派生值。
- 状态只允许 `draft → confirmed → superseded`；confirmed/superseded 不可原位修改。

## 5. 不变式、事务与并发

1. `createProject` 的 Project、Episode 和 IdempotencyRecord 一次提交；同 scope/key/hash 重放返回原资源。
2. 同 Project 只能有一个 Episode，由数据库候选键收敛并发创建。
3. 来源确认锁定 Episode，先 supersede 旧 confirmed，再确认新 draft；partial UQ 只作最终防线。
4. 来源变化不发送跨模块修改命令；下游依据固定版本计算 `input_outdated`。
5. 客户端修改请求使用 ETag/`If-Match`；版本冲突返回 `412 VERSION_CONFLICT`。

## 6. 失败、权限、迁移与回滚

| 场景 | 结果 | 恢复 |
| --- | --- | --- |
| 权利未声明/文本非法 | `422` 且不产生版本 | 修正后使用新幂等键提交 |
| 幂等键被不同请求复用 | `409 IDEMPOTENCY_KEY_REUSED` | 客户端修正命令边界 |
| 确认时版本已变 | `412 VERSION_CONFLICT` | 刷新并显式创建新 draft |
| API 重启 | 已提交事实不变 | 从 PostgreSQL 重建查询投影 |

只允许 loopback 边界内的 `internal_operator`。日志只记录 ID、字符数和哈希，不记录来源正文。首次迁移由 DESIGN-06 的逐表 SQL 建立；回滚只切回兼容制品，不删除项目或历史来源。

## 7. Design 验收标准

- AC-MOD-PROJECT-001：并发 20 次重放创建项目只得到一个 Project 和一个 Episode，回执一致。
- AC-MOD-PROJECT-002：299/3001、无 Han、禁用代码点和无权利声明样本不落库，300/3000 边界样本的 NFC/LF/哈希可重算。
- AC-MOD-PROJECT-003：来源确认并发测试中每 Episode 最多一个 confirmed，历史内容不被覆盖。
- AC-MOD-PROJECT-004：重启 API 或清空 Redux 后，项目、当前来源和全部历史从 PostgreSQL 恢复。
- AC-MOD-PROJECT-005：新来源确认后，引用旧来源的下游事实只显示 `input_outdated=true`，内容和状态不变。
- AC-MOD-PROJECT-006：模块代码只写入所属三表，下游只经 `public.py` 读取已确认来源契约。
