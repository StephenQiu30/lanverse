# 文本解析失败诊断与受控恢复设计

2026-09-08。落实 3004 第 8 节与 11.3 的失败恢复要求，处理实际第 4 集 422，不改变原稿、专业发布摘要或人工采纳门。

## 已证实的问题

实际冻结输入能够通过 prepare，上下文为 7344 字节。历史 HTTP 422 的响应体未被可信 Worker 保存，Harness 临时候选已清理，因此不能追溯声称某个具体校验规则导致了旧失败。当前代码把输入拒绝、输出预算和候选校验失败混成 422，再统一转为 unknown；unknown 无受控恢复入口。

## 实施规格与边界

1. Harness 返回绑定 invocation/input/release 的闭合失败合同，区分 preflight、generation、validation；可用候选/结构输出保存在受限失败回执中，诊断不进入 Temporal 日志。未认证请求不提供这些内容。
2. 可信 Worker 校验失败身份、大小及允许的状态/错误组合；确定失败保存为 failed，网络断连、非合同响应继续 unknown，不按任意 HTTP 4xx 自动重试。
3. 追加迁移记录不可变失败回执；旧 attempt 记录和旧迁移 checksum 不改写。失败候选不创建可采纳 Draft、OutputBinding 或正式业务数据。
4. 运维恢复命令只接受精确 command/step/旧 attempt、恢复 ID 与操作原因。先确认原 Temporal 执行 blocked、无待执行 Activity、旧调用已退出、原结果不可恢复；在数据库登记单次授权，再以相同 request ID 执行 Temporal reset。保留同一业务 run/Workflow ID 与全部原历史，不删除或伪造旧成功。
5. reset 从原工作流的第一个已完成 Workflow Task 重放调度；活动复用原草案，只有被授权的失败步骤可创建下一 Attempt。新 Attempt 增加 fence、占用剩余预算；旧 unknown/failed 终态保持不可变。相同恢复请求幂等，响应丢失不能换 ID；成功结果、活跃尝试、输入改变、预算耗尽均拒绝。
6. 此切片是显式运维恢复，不增加随机自动重试或修改专业提示词。现有前端显示确定失败原因，Go 追踪合同接受 failed 状态。人物/闪回问题仍需以实际候选为证据另行修订。

## 用户确认的部署纠正

用户明确要求前端、Go 和全部 Agent 都使用 Docker；基础设施使用本机已经运行的服务。本次恢复 `docker-compose.yml` 为唯一应用启动入口，移除 0019 新增的应用 LaunchAgent 托管，不启动环境 profiles。

容器间使用专属 runtime bridge，通过签名 HTTP 调用；仅显式 `CREATION_DOCKER_NETWORK=true` 允许固定的 `backend:8686`、`agent:8787` 服务地址，以及访问本机 Temporal 的 `host.docker.internal:7233`。默认仍要求 loopback 或 HTTPS，不允许任意远程 HTTP。Agent 私有端口不发布到宿主，外部仅开放原前端/API loopback 端口。非本机部署仍使用 TLS 合同。

Agent 容器仅以只读方式挂载本机 Codex 的登录文件，不挂载整个 Codex 目录、业务数据库或平台凭据；运行缓存使用专属卷。可信 API/Worker 与受限 Harness 虽在同一容器内，仍通过模块边界、子进程环境白名单和签名 HTTP 合同隔离，可信编排不会把 Codex 登录或平台凭据传给模型子进程。Worker 收到容器停止信号先停止轮询，等待当前 Activity 在固定截止时间内完成后退出。原记录未知且不可恢复的尝试仅通过新授权追加，不重写历史。

实际 Docker 验证发现旧 Run 的创建地址为 `127.0.0.1:8788`，Go 容器沿用该地址导致追踪与平台门请求失败。增加显式 `CREATION_AGENT_RELOCATED_FROM`，只将完全匹配的历史 origin 路由到当前 `CREATION_AGENT_URL`；原 Run.Endpoint 与命令/引擎身份不改写，不匹配的历史地址仍使用原路由。迁移目标必须是原 Creation 数据库、Temporal namespace/queue 和签名身份；所有回执仍校验原 command/payload/revision。空值不启用迁移。这是同服务部署地址迁移，不允许静默换引擎。

失败合同补充：结构化 `reasoning_execution_failed_or_unknown` 回执使用 HTTP 502，仍记为 unknown / `harness_response_unknown`，诊断持久化但不进入 Temporal。HTTP 状态必须与绑定失败类型匹配；非合同 502 不据此判定模型结果。

## 本地启动精简规格与 checklist（2026-09-08 追加）

按用户要求，本地只启动应用、连接本机既有环境：根目录仅保留 `docker-compose.yml` 应用入口，CI 依赖编排移至 `deploy/ci/compose.dependencies.yml`，镜像发布覆盖移至 `deploy/compose.production.yml` 且不再声明环境服务。日常 README 只提供应用启动/状态命令。后端环境地址只使用 `DATABASE_URL`、`TEMPORAL_ADDRESS`、`KAFKA_BROKERS`、`ELASTICSEARCH_URL`、`LOGSTASH_ADDRESS`，去除平行的 DOCKER_* 别名及数据库拼接配置。容器经 host.docker.internal 访问本机，应用无需加入特定 ELK 网络。CI 通过 `deploy/ci/compose.application.yml` 显式加入其一次性依赖网络，保留 Linux Runner 内部服务地址，避免依赖仅绑定宿主 loopback 的发布端口。
