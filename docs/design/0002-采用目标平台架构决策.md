# 采用目标平台架构决策

- 原决策编号：ADR-0001
- 状态：已接受
- 日期：2026-08-24
- 范围：仓库、运行时、Frontend、Backend、Agent 与基础设施

## 背景

仓库当前实现是 Python 3.11 FastAPI 模块化单体、进程内 Skill Harness 与单 Next.js 应用；`app.runtime.server` 同进程监督 API、Scheduler、IO Worker 和 Media Worker。现有 CI 也显式约束不出现 Go Backend 和独立 `agent/` 项目。

用户指定的最新完整设计基线重新确定了 AI 短剧生产平台的目标边界。后续实现需要把“当前可运行实现”和“新的长期目标”分开，并定义安全迁移规则。

## 决策

采用以下目标架构：

1. Frontend 是 pnpm + Turborepo TypeScript Monorepo，包含 `apps/web`、`apps/collab` 与 `packages/ui|ai|canvas|sdk|auth`。
2. Backend 是一个 Go Module，按领域组织，并构建 `lanverse-api`、`workflow-worker`、`model-gateway`、`media-worker`、`event-worker` 五个运行程序。
3. Agent 是独立 Python Project，通过 gRPC/Protobuf 与 Backend 通信；Agent 不持有数据库、对象存储或任意 Shell/网络权限。
4. Temporal 是跨服务长任务的唯一全局工作流引擎；LangGraph 只存在于确需复杂修复图的 Agent 内部。
5. PostgreSQL 是业务事实源，Temporal 保存 Workflow 历史，Redis 只保存缓存/限流/临时状态，MinIO 保存对象，Kafka 传递领域事件，Elasticsearch 只保存可重建投影。
6. Guided Studio 与 Canvas Studio 共享 Authoring Revision、Workflow Compiler、Workflow Definition 与执行系统，不复制生产核心。

该决策取代提交 `1a4308c` 所代表的长期“只保留 FastAPI、移除 Go 与独立 Agent”方向，但不授权直接删除或覆盖当前可运行代码。代码替换必须按照迁移计划逐个业务切片完成。

## 迁移约束

- 同一 endpoint、数据库表、Topic 或工作流类型在任一时刻只有一个写入所有者。
- 不迁移正在运行的旧任务；旧运行由旧引擎完成或终止，新运行在切换后进入 Temporal。
- 不建立只为匹配目录树的空包、空服务或转发层。新项目/目录必须随首个可验证切片一起创建。
- Go 与 Python 过渡共存时，公共 OpenAPI、Proto、Event Schema、数据库迁移和验收测试是切换门禁。
- Agent 跨进程前必须先收窄为 Tool Allowlist，并移除数据库、对象存储、任意 Shell 与任意网络凭据。
- Debezium/Kafka Connect 接管 Outbox 前必须停用旧 Publisher，避免重复发布。
- Frontend 状态库按业务切片切换；同一 server state 不长期同时由 RTK Query 和 TanStack Query 管理。

## 结果

优点是目标与最新产品范围一致，服务边界、扩缩容、长任务恢复、多模型与 Canvas 能力得到统一归属。代价是当前实现需要结构性迁移，CI、部署、数据库所有权和运行中任务都必须分阶段切换；在完成验收前不能宣称目标架构已经落地。
