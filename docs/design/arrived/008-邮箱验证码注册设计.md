# DES-008 邮箱验证码注册设计

- 状态：accepted
- 日期：2026-08-11
- 输入：[用户与空间模块需求](../../requirement/arrived/002-用户与空间模块需求.md)、[用户与空间模块详细设计](../模块设计/arrived/002-用户与空间模块详细设计.md)、[前端体验与视觉系统重设计](./007-前端体验与视觉系统重设计.md)
- 输出：注册邮箱验证 API、SMTP 与 Redis 边界、一次性注册票据、前端流程、安全与验收基线

## 1. 结论

Lanverse 注册必须先证明邮箱归属，再创建 `UserAccount`、个人 `Workspace` 和 owner `Membership`。注册流程拆为“发送验证码 → 确认验证码 → 提交资料并消费一次性注册票据”三步；未经确认的邮箱不能调用公开注册接口直接创建账号。

邮件由 Lanverse 后端通过现有 HotKey 项目已经配置的 SMTP 服务发送，验证码与一次性票据只保存在 Lanverse 使用的 Redis 中。SMTP 凭据可从 HotKey 本地配置安全映射到 Lanverse 本地配置，但验证码 HMAC 密钥必须为 Lanverse 单独生成，不能复用 HotKey 或 JWT 密钥。

该能力只约束新账号注册。现有账号、邮箱密码登录和已签发身份不依赖邮件服务；SMTP 或 Redis 不可用时注册失败关闭，但登录仍可用。

## 2. 已核验事实、推断与待确认

### 2.1 已核验事实

- 当前 `POST /api/v1/auth/register` 接受邮箱、密码和显示名称后直接创建账号、个人空间和 owner Membership，没有邮箱验证门禁。
- 当前注册的三个持久事实在 PostgreSQL 事务中原子创建，邮箱规范化后由唯一约束处理并发重复。
- Lanverse 已配置 Redis，可承载短期验证码、冷却、尝试次数和一次性票据；PostgreSQL 继续是账号事实来源。
- HotKey 使用 SMTP 发信，配置包含 enabled、host、port、TLS mode、username、password、from email 和 from name；这些项目在 HotKey 本地配置中均已设置。
- HotKey 的已验证安全参数是 6 位验证码、10 分钟有效期、60 秒重发冷却、最多 5 次错误尝试、HMAC 摘要保存和确认后一次性票据。
- 现有身份需求和模块设计明确写有“identity 不承载邮件业务”；本设计若被接受，将把“注册邮箱所有权验证”作为该边界的唯一例外，不自动扩展到找回密码或通知邮件。

### 2.2 合理推断

- 复用现有 SMTP 提供方比引入第二个邮件供应商更符合当前配置事实和最小闭环原则。
- 验证码属于短期认证挑战，不应写入 PostgreSQL，也不应成为账号或审计事实。
- 注册接口必须改为消费服务端签发的票据；只在前端隐藏邮箱字段不能阻止绕过验证码直接调用 API。

### 2.3 待确认事项

- 真实投递验收需要一个明确授权的测试收件邮箱；不得从截图、用户资料或 SMTP 账号中推断收件人并自动发信。
- 本设计只复用 HotKey 的 SMTP 连接配置，不保证两项目长期共用同一发件身份；若生产环境需要独立域名与发件人，应在部署前完成 DNS、信誉和投递率验收。

## 3. 目标与非目标

### 3.1 目标

- 只有持有目标邮箱验证码的访问者才能获得对应邮箱的一次性注册票据。
- 只有持有有效、未消费且与邮箱绑定的注册票据才能创建账号。
- 验证码、SMTP 凭据、密码和票据不能出现在数据库、日志、API 错误或前端持久存储中。
- 重发、错误尝试、过期、重复确认、重复消费、依赖故障和并发请求均有确定结果。
- 注册完成后保持现有账号、个人空间与 owner Membership 的 PostgreSQL 原子事务。

### 3.2 非目标

- 不实现找回密码、Magic Link、MFA、社交登录、邮箱变更验证或通知邮件。
- 不建立通用邮件微服务、邮件队列、模板平台或第二套用户身份。
- 不要求现有账号补做邮箱验证，也不改变现有登录接口。
- 不把 SMTP 或 Redis 设为登录、读取项目或其他既有能力的启动门禁。

## 4. 注册状态与公开接口

### 4.1 状态流

```text
输入邮箱
  → verification_pending（验证码已发出）
  → email_verified（签发一次性 registration_ticket）
  → account_created（票据已消费，账号事务已提交）
```

过期验证码、达到错误次数、重新发送或确认成功都会使旧验证码失效。注册票据只能消费一次，过期或已消费后必须重新验证邮箱。

### 4.2 发送注册验证码

`POST /api/v1/auth/registration-verifications`

请求：

```json
{
  "email": "creator@example.com"
}
```

成功响应只返回通用接受结果和再次发送的等待时间：

```json
{
  "data": {
    "accepted": true,
    "retry_after_seconds": 60
  }
}
```

服务端规范化邮箱并检查 60 秒冷却，生成密码学安全的 6 位验证码。Redis 只保存与 Lanverse 专用 HMAC 密钥、规范化邮箱和注册用途绑定的摘要、过期时间及剩余尝试次数，不保存明文验证码。

已注册邮箱和未注册邮箱使用相同公开响应，避免通过发信接口枚举账号。已注册邮箱不发送可用于注册的验证码；服务端可以写无邮箱值的安全指标，但不得在响应中暴露账号是否存在。

### 4.3 确认注册验证码

`POST /api/v1/auth/registration-verifications/confirm`

请求：

```json
{
  "email": "creator@example.com",
  "code": "123456"
}
```

成功响应：

```json
{
  "data": {
    "registration_ticket": "opaque-single-use-ticket",
    "expires_in": 600
  }
}
```

确认操作必须在 Redis 中原子比较摘要并递减错误次数。同一验证码并发确认只有一个请求可以成功；成功后删除挑战并签发 32 字节以上密码学随机票据。Redis 保存票据摘要、规范化邮箱与 10 分钟有效期，API 不返回验证码或内部 Redis 键。

### 4.4 创建账号

现有 `POST /api/v1/auth/register` 改为：

```json
{
  "registration_ticket": "opaque-single-use-ticket",
  "password": "at-least-12-characters",
  "display_name": "创作者名称"
}
```

邮箱只从票据解析，不再由注册请求直接提供。服务端先原子消费票据，再沿用现有 PostgreSQL 事务创建 `UserAccount`、个人 `Workspace`、owner `Membership` 和注册审计事实，成功后签发访问令牌。

若票据消费后 PostgreSQL 事务失败，不能恢复或重复使用票据；客户端提示重新验证邮箱。这一取舍避免在 PostgreSQL 保存临时验证码，也避免跨 Redis/PostgreSQL 伪事务。邮箱唯一约束仍是并发注册的最终门禁。

## 5. 模块边界

身份模块新增注册验证子边界，但邮件传输与验证码存储都通过窄接口注入：

| 接口 | 职责 | 禁止事项 |
| --- | --- | --- |
| `RegistrationMailer` | 发送包含验证码、有效期和安全提示的纯文本/HTML 邮件 | 不查询用户、不生成验证码、不记录收件人与正文 |
| `RegistrationVerificationStore` | 创建挑战、冷却、原子确认、签发和消费票据 | 不持久化明文验证码或票据 |
| `RegistrationVerificationService` | 规范化邮箱、处理枚举保护、协调存储和邮件 | 不创建账号事实 |
| 现有 authentication service | 消费验证票据并执行账号事务 | 不接收未经票据绑定的邮箱 |

首版在 FastAPI 模块化单体内实现，不创建新微服务。SMTP 是阻塞 I/O，必须在线程边界内执行并设置连接与操作超时，不能阻塞事件循环。

## 6. 配置与密钥

Lanverse 使用自身命名的配置，不让业务代码读取 HotKey 前缀：

| Lanverse 配置 | 来源或默认值 |
| --- | --- |
| `SMTP_ENABLED` | 从 HotKey 本地 SMTP enabled 安全映射 |
| `SMTP_HOST`、`SMTP_PORT`、`SMTP_TLS_MODE` | 从 HotKey 本地连接配置安全映射 |
| `SMTP_USERNAME`、`SMTP_PASSWORD` | 从 HotKey 本地凭据安全映射，使用 `SecretStr` |
| `SMTP_FROM_EMAIL`、`SMTP_FROM_NAME` | 从 HotKey 本地发件身份安全映射 |
| `EMAIL_VERIFICATION_HMAC_SECRET` | 为 Lanverse 新生成的独立 32 字节以上随机密钥 |
| `EMAIL_VERIFICATION_TTL_SECONDS` | 默认 600 |
| `EMAIL_VERIFICATION_RESEND_SECONDS` | 默认 60 |
| `EMAIL_VERIFICATION_MAX_ATTEMPTS` | 默认 5 |
| `EMAIL_VERIFICATION_TICKET_TTL_SECONDS` | 默认 600 |
| `SMTP_TIMEOUT_SECONDS` | 默认 10，必须有上限 |

TLS mode 只允许 `tls` 或 `starttls`；生产环境启用邮件时必须完整配置主机、端口、发件人、凭据和独立 HMAC 密钥，否则配置校验失败。`.env.example` 只记录键名和非敏感默认值，真实值只写入本地/部署密钥环境，不提交 Git、不输出到终端或日志。

## 7. 安全、限流与隐私

- 验证码使用 CSPRNG 生成，固定为 6 位；比较使用恒定时间摘要比较。
- Redis 键包含 Lanverse、环境和注册用途命名空间，避免与 HotKey 或测试环境碰撞。
- 同一规范化邮箱 60 秒内只能申请一次；连续错误最多 5 次，达到上限立即使挑战失效。
- 请求体中的邮箱只用于当前流程；日志记录请求 ID、结果分类和耗时，不记录完整邮箱、验证码、票据、密码、SMTP 凭据或邮件正文。
- 对外错误使用稳定错误码和中文可执行提示，SMTP 原始响应、主机信息和堆栈只进入受控内部诊断，不能返回前端。
- 前端不得把验证码或注册票据写入 `localStorage`、URL、分析事件或错误上报；只保存在当前注册组件内存中。
- 发信接口仍存在按邮箱冷却之外的滥用风险。实现验收必须增加按客户端来源的短窗口限流，并通过受信代理配置取得来源地址；具体生产阈值在部署验收中用观测数据调整，不写死为产品事实。

## 8. 失败路径与恢复

| 失败 | 对外结果 | 恢复动作 |
| --- | --- | --- |
| 邮箱格式非法 | `INVALID_REQUEST`，422 | 修正邮箱 |
| 冷却中 | `RATE_LIMITED`，429，返回等待秒数 | 倒计时后重发 |
| 验证码错误 | `INVALID_VERIFICATION_CODE`，422，返回剩余尝试语义但不返回内部摘要 | 重试或重发 |
| 验证码/票据过期 | `VERIFICATION_EXPIRED`，410 | 重新发送验证码 |
| 验证码/票据已消费 | `VERIFICATION_EXPIRED`，410 | 重新验证，不暴露并发内部状态 |
| SMTP 或 Redis 不可用 | `DEPENDENCY_UNAVAILABLE`，503 | 保留邮箱输入并允许稍后重试；登录不受影响 |
| 已存在账号 | 发信阶段保持通用接受；注册阶段 `RESOURCE_CONFLICT`，409 | 转到登录 |
| 票据消费后数据库事务失败 | `INTERNAL_ERROR` 或稳定依赖错误 | 重新验证邮箱；不得留下部分账号事实 |

发送顺序采用“先写短期挑战，再发邮件；发信失败时尽力删除挑战”。这样不会发出一个 Redis 从未接受的验证码。若失败清理也失败，挑战仍不可被未知验证码利用，且会按 TTL 自动过期；服务端不得把发信失败误报为成功。

## 9. 前端流程

`/register` 使用同一 `AuthForm` 身份入口和现有 shadcn/ui 组件，按三个阶段呈现：

1. 邮箱：输入邮箱并发送验证码。
2. 验证：输入 6 位验证码，显示 60 秒重发倒计时，允许返回修改邮箱。
3. 账号资料：输入显示名称、密码并同意协议，提交一次性注册票据。

阶段切换不新增卡片、装饰插画或自绘控件。使用现有 `Button`、`Input`、`Label`、`Alert` 等官方组件和 Lucide 图标；验证码输入支持粘贴、数字键盘、清楚的 Label、焦点顺序和屏幕阅读器状态。刷新页面会清空挑战状态并回到邮箱步骤，避免持久化敏感票据。

## 10. 实施顺序

1. 更新用户与空间需求、模块详细设计和验收文档，接受注册邮箱验证这一 identity 例外。
2. 先写配置、验证码摘要、Redis 原子状态和 SMTP 适配器的失败测试。
3. 实现注册验证服务和两个公开验证接口，使测试转绿。
4. 把 `/auth/register` 改为只消费一次性票据，补齐并发与事务失败测试。
5. 重新生成 OpenAPI TypeScript 客户端，更新 RTK Query 与三阶段注册 UI。
6. 使用本地假 SMTP 完成自动化端到端验证，再使用明确授权的真实收件邮箱完成一次真实投递验收。

## 11. 验收

1. 未经邮箱确认直接调用 `/auth/register` 无法创建账号、Workspace 或 Membership。
2. 正确验证码能换取一次性票据；错误、过期、超过次数、重复确认和并发确认符合表中结果。
3. 一张票据只能成功注册一次；注册成功仍原子创建三个事实并能立即登录。
4. 已注册邮箱的发送接口不泄露账号存在性；重复注册最终返回冲突且不产生重复事实。
5. Redis 或 SMTP 不可用时注册失败关闭，现有账号登录仍可用。
6. 自动化测试证明 Redis 和日志中不存在明文验证码、票据、密码或 SMTP 密钥。
7. SMTP TLS 模式、超时、配置缺失和错误净化均有测试；本地假 SMTP 能收到预期主题、验证码和有效期。
8. 获得明确测试收件地址授权后，真实 SMTP 投递成功且验证码可完成注册全链路。
9. 后端单元/集成测试、前端 lint/typecheck/test/build、生成客户端漂移检查和浏览器注册/登录验收全部通过。
