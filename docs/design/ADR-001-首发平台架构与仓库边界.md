# ADR-001 首发平台架构与仓库边界

## 1. 状态与决策日期

- 状态：`review`；尚未授权创建应用骨架或引入依赖。
- 决策日期：待 Design 评审批准时填写；最迟复核点为 S0 Plan 接受前。
- 决策人：产品、架构、前端、后端、安全和运维责任人共同确认。

## 2. 背景与驱动因素

平台需要在浏览器中完成来源理解、结构化剧本、资产与分镜、AI 长任务、媒体处理、审核、费用和交付。首发团队需要共享类型和契约、快速交付单集闭环，同时保证租户隔离、任务恢复、媒体谱系、独立扩缩和未来拆分能力。

当前仓库尚无应用源码和生产数据；因此可以直接建立清晰边界，无需为已删除的历史试验目录保留兼容层。

## 3. 决策

1. 使用单一 Git monorepo；业务实现只在根目录新增 `backend/`、`frontend/`、`deploy/` 及统一 pnpm 配置，保留现有治理/社区文件，不增加顶层 `apps/`、`packages/` 或独立 Worker 仓库。
2. `frontend/` 采用 Next.js/React/TypeScript；公开 HTTP 契约由 OpenAPI 3.1 生成客户端，页面不得维护第二套 DTO。
3. `backend/` 采用 NestJS/TypeScript 模块化单体；模块目录、公开面和服务映射由 [ARCH-007](ARCH-007-业务模块边界与服务协作设计.md) 约束。API 与 Worker Activity/适配器调用同一公开应用用例，Workflow 只依赖纯 Activity 契约类型；各入口构建为独立制品、进程、队列和资源池。
4. PostgreSQL 是业务事实源；对象存储是媒体字节权威；Temporal 只保存编排历史；Redis 只用于可丢失缓存、限流和短期协调。
5. 所有业务写入经 `backend` 应用层：公开命令由 API 调用，异步结果由 Worker Activity 调用。Workflow、事件消费者、回调和运维任务不得绕过应用用例直接写业务表。
6. 长任务使用 Transactional Outbox 启动或通知 Temporal；Workflow 不产生数据库、账本、网络或对象存储副作用，副作用只在可幂等 Activity/受控适配层发生。
7. 不预建 Python 服务；只有经基准证明 TypeScript Worker 无法满足推理、媒体或受控执行需求，并通过新 ADR 后才增加独立服务。

## 4. 选择理由

| 驱动因素 | 本决策的响应 |
| --- | --- |
| 首发交付速度 | 单仓库和模块化单体减少跨仓库版本、网络契约和部署协调 |
| 契约一致性 | OpenAPI 与同语言共享工具链降低前后端漂移，但公开边界仍保持显式 |
| 长任务可靠性 | Temporal 提供持久编排，PostgreSQL Task/Attempt 保留用户可见事实 |
| AI/媒体独立扩缩 | API 与不同 Worker 池独立部署，不要求提前拆微服务 |
| 数据完整性 | 唯一应用写入边界、Outbox、幂等 Activity 和追加式账本避免双写 |
| 可演进性 | 模块事实所有权、契约和事件边界为未来按负载或组织拆分提供接缝 |

## 5. 被否决方案

| 方案 | 暂不采用原因 | 何时重议 |
| --- | --- | --- |
| 顶层 `apps/` + `packages/` 通用骨架 | 当前只有明确的前端与后端边界，额外抽象会扩大目录和发布认知成本 | 出现三个以上真实复用消费者并有独立版本需求 |
| 首发微服务 | 增加分布式事务、部署、观测和契约成本，尚无组织或负载证据 | 单模块达到独立团队、SLO、数据驻留或扩缩隔离阈值 |
| Electron + SQLite 本地应用 | 不满足多租户 Web、中心化审计、协作和持久任务要求 | 产品明确增加离线桌面版并另建同步设计 |
| 数据库轮询/进程内 Promise 长任务 | 进程退出、部署和重复执行下难以恢复及审计 | 不重议；仅允许测试替身或明确的同步短操作 |
| Kafka 作为首发事件总线 | 当前 Outbox、Temporal 与投影规模无需额外平台 | 事件吞吐、保留、多消费者或跨区域需求超过已验证阈值 |
| 预建 Python 推理微服务 | 没有模型运行或性能证据，空服务会形成运维负担 | 出现不能由 Worker/供应商适配解决的实测需求 |

## 6. 后果与约束

正向后果：仓库结构直观，API/Worker 可独立部署，业务规则只有一套，单集闭环可分切片推进，未来拆分有明确模块接缝。

成本与风险：模块化单体需要自动边界检查；共享代码库可能造成 Worker 引入不必要依赖；Temporal Workflow 演进需要确定性约束；PostgreSQL、Temporal 与对象存储仍需对账和恢复演练。

强制护栏：禁止跨模块直接写表、禁止 Workflow 副作用、禁止 Redis/画布/Agent 记忆成为事实源、禁止在生产 API 执行用户代码、禁止未通过 Plan 提前搭建空目录或引入依赖。

## 7. 退出、迁移与回滚

- 模块拆服务必须以事实所有权、公开契约、历史迁移、双写避免、SLO、成本和回滚方案的新 ADR 为前提；不得按目录直接复制数据库表。
- Temporal 产品替换须保留稳定 Task/Attempt/Outbox 事实，并证明运行中任务迁移、取消、幂等和费用对账；Workflow 历史不得成为迁移唯一输入。
- 对象存储、数据库或身份供应商替换采用双读校验/分批迁移/校验和对账；在切换完成前保留可回退副本和审计证据。
- S0 尚无业务数据时，回滚只删除未接受的应用骨架提交；任何产生正式事实后的回滚必须保留任务、账本、媒体和审计记录。

## 8. 验证与接受条件

- Design：ARCH-001～ARCH-007、ADR-002 与 TRACE-001 对本决策无冲突；关键模块均有单一所有者、运行边界和退出条件。
- Plan：S0 明确目录、依赖、边界检查、独立构建、OpenAPI 生成、Outbox/Temporal 故障测试和回滚步骤。
- Implementation：前端、API 和至少一个 Worker 可从同一提交独立构建/部署；边界测试阻止跨模块写入；重复 Outbox/Activity 不重复事实。
- Acceptance：删除 Redis、重建投影、重启 Worker、重放 Outbox 和滚动升级时，Task/Attempt/费用/媒体均保持可判断且可追踪。

在上述 Design 条件满足且责任人签署前，本 ADR 保持 `review`；任何来源项目的实现方式仅作证据，不改变本决策的独立责任。
