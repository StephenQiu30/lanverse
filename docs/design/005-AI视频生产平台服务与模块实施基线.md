## 1. 结论

Lanverse 经评审选定的目标基线是 **`frontend/` 中一套 TypeScript/Next.js 浏览器应用、`backend/` 中 15 个 Python 逻辑业务模块、跨前后端的 Model–View–ViewModel–Controller（MVVC）调用链、6 类按切片启用的安全隔离进程入口、6 项基础设施能力、唯一 MinIO 对象存储实现和少量外部适配能力**。它们不是 15 个微服务，也不是 27 个独立仓库；目录、服务和抽象只随可验收纵向切片创建。

浏览器端不采用 Python；目标态使用严格 TypeScript、React 和 Next.js，并只拥有交互与视图状态。后端目标态采用 Python 模块化单体：一套 Plain Object 领域模型、一套 Application Service、一套 PostgreSQL 权威事实，通过不同进程入口隔离公网请求、调度对账、外部 Provider、Agent 和媒体执行。Python 可以支撑目标规模，前提是长任务不与 API 共进程、CPU/媒体工作隔离、队列有背压、类型与模块边界受 CI 约束并按容量水平扩缩；代码量本身不是引入 Java/Go 的理由。

竞品报告中“Agent + 画布”“批量生成”“多模型”“商业路线”等表述只作为市场证据。目标产品范围包括：统一项目事实、可审阅提案、冻结生成计划、版本化参考与候选、可恢复外调、局部修复、审阅及不可变交付。公共市场、商业计费、一键整季、自动发布、完整 NLE 和按报告月份建设的路线图不进入本设计。

## 2. 统一术语与边界

| 概念 | 回答的问题 | 权威位置 | 目标基线/数量 |
| --- | --- | --- | --- |
| 产品能力 | 用户最终能完成什么 | Requirement、PRD | A—F 纵向切片 |
| 逻辑模块 | 哪个模块拥有事实、规则和写入 | M01—M15 Design | 15 |
| 运行服务/进程角色 | 长短任务在哪个故障边界执行 | 系统架构、本设计 | 6 类 |
| 基础设施能力 | 权威存储、投递、密钥、观测与必需运行态依赖什么 | 系统架构、部署配置 | 6 项 |
| 外部能力 | 通过什么受控适配器调用模型、通知或身份系统 | M07、M08、M14、M15 | 按 Gate 启用 |
| 页面/画布 | 用户从哪里查看和提交相同命令 | 产品设计、模块 Design | 不是事实源 |
| 代码包 | 同一语言代码如何声明所有权和依赖 | `frontend/src/features`、`backend/app/modules` | 不等于部署服务 |
| MVVC | View/ViewModel 如何通过生成 API 调用 Controller，再进入 Service/Model | 前端 `views\|view-models`；后端 `transport/http/controllers` | Controller 不是业务 Service，ViewModel 不是领域 Model |
| Plain Object | 如何表达无框架依赖的命令、值、结果与领域对象 | 模块 `domain/application` | Python 对 POJO 的落实 |
| Application Service | 哪个用例执行鉴权、版本、幂等、短事务和 Outbox | 模块 `application/services` | 不按表建立万能 Service |
| Agent Harness / Skill | 如何恢复并约束一次 AI 推理图 | `backend/app/agent_runtime` | 不是 M02—M04 业务事实源 |

以下规则不可违反：

1. 一个逻辑模块可以被多个进程调用，但同一业务事实只有一个写入所有者。
2. 一个运行进程可以承载多个模块的后台任务，但不得因此接管模块审批、主选或交付决定。
3. 前端、Agent、API、Webhook 和 Worker 必须走相同应用端口、权限、幂等和治理规则。
4. 队列、缓存、LangGraph checkpoint 和对象存储路径都不是业务完成事实。
5. `modules/agents` 拥有 M06 的 Run/Proposal/Decision 业务事实；`agent_runtime` 只实现通用 Harness 和具体 Skill，二者不能合并成一个可直写业务表的 Agent 包。
6. 目录按已实施纵向切片渐进创建，不为未来能力预建空目录、空 Service 或兼容层。
7. 数据库 Schema、`/api`、消息契约和 canonical MinIO key 分别只有一套权威定义；不建立并行契约、转换器、对象双读或回退分支。
8. 新增框架、服务、顶层目录或跨模块抽象前，先按 000 §2.4 核验官方资料和相近开源实现；没有当前用例、owner 和测试则不采用。

| 切片 | 允许首次创建的目标目录 | 明确不创建 |

### 3.1 六类生产进程角色

目标拓扑共有六类安全隔离入口，但按切片启用：A 部署 SVC-01/02/03/06，B 增加 SVC-05，C 增加 SVC-04。部署与队列统一使用表中的 `kebab-case runtime_slug`，Python 入口文件使用对应 `snake_case`。某入口一旦启用，就必须具有独立生产生命周期、队列、身份、网络策略和健康检查。SVC-03 与 SVC-04 可以复用镜像依赖，但 Import 无默认公网/KMS 权限，Provider 仅允许名单外网和按连接读 KMS，二者绝不共用进程身份。

通知、Webhook 投递和邮件/短信适配首期作为 SVC-02 消费 Outbox 的适配器，不单独建设“通知微服务”。只有独立吞吐、合规或供应商故障边界得到证据后再拆分。

### 3.2 Agent Harness 运行边界

Harness 是 SVC-05 内的通用执行内核，不是第七类服务，也不是第十六个业务模块。它统一执行 `run/graph/contract` 版本校验、Tool allowlist、预算/超时、checkpoint、恢复、结构化输出校验和 ResultPort 提交；每个 Skill 只提供 State、Node、Prompt 与 Proposal 合并规则。

首个剧本分析 Skill 以三个连续 Run 完成推理编排：`stage=breakdown` 只基于 SourceRevision 输出承载 M03 `CreateEpisodeBreakdownDraft` 的 M06 AgentProposal；M03 批准 Manifest、M02 物化 ContentUnit/Order 且返回 mapping 后，M03 先创建私有 `NarrativeDraftImport`，`stage=narrative` 再按稳定 ContentUnit 输出承载 M03 `ApplyNarrativeContentUnitDraft` 的 M06 AgentProposalItem，并在全部集成功应用或人工补齐后由 M03 `FinalizeNarrativeDraftImport` 形成可见 draft；M03 批准 NarrativeRevision 后，`stage=knowledge` 才基于 approved Narrative/Order/M04 只读复现快照，通过自包含 M04 Command 提出人物聚类/MentionResolution，以及对 ProductionElementMention/NarrativeScene coverage subject 的正式 Schema 允许类型 ProductionRequirement。Run 快照用于审计和重跑；逐项接受由目标 Service 对实际 read/write set 做细粒度 CAS，不以同批不相交项更新后的全局 set hash 互相判过期。人物出场矩阵、Inventory 和 Readiness 不是 Agent current，而是 M04 接受事实后确定性重建的投影。关闭 SVC-05 后，SVC-01 的手工命令必须仍可完成同一业务闭环。

三个 AgentRun 都挂到同一个 M03 AnalysisRun/root Operation：SVC-05 承载每个 stage 的 child Operation，SVC-01 展示根 Operation 的 `waiting_user` 门禁，SVC-02 负责耐久投递与恢复。AgentRun 完成不等于整本分析完成。

### 3.3 六项基础设施能力

| 基础设施 ID | 能力 | 是否首期必需 | 权威用途 | 不得承担 |
| --- | --- | --- | --- | --- |
| INF-01 | PostgreSQL + 最终 ORM Metadata + RLS | 必需 | 领域事实、Operation/Job/Attempt、Outbox/Inbox、审计、投影、空库初始化和严格 Schema 校验 | 直接存放大媒体；增量 revision 链、数据回填或启动时修改非空结构 |
| INF-02 | 私有 MinIO（唯一对象存储；S3-compatible API 仅为协议） | 必需 | 来源原件、媒体、代理、Agent 大载荷、模型原响应和交付文件 | AWS S3 adapter、多存储 Provider 工厂；以对象路径替代 Candidate、Selection 或 DeliverySnapshot |
| INF-03 | RabbitMQ | 必需 | 至少一次任务投递、背压、死信和消费者隔离 | 充当权威状态或业务审计 |
| INF-04 | Secret/KMS 服务 | 接真实 Provider 前必需 | Provider、Webhook、服务身份的可轮换密钥引用 | 在业务数据库保存可解密凭据材料 |
| INF-05 | OpenTelemetry + 指标/日志/Trace 后端 | 上线前必需 | operation→job→attempt→provider/artifact 的可观测链 | 记录来源正文、Prompt、凭据或跨租户敏感数据 |
| INF-06 | Redis | 切片 A 必需 | M01 刷新会话、注册验证、高成本请求门禁，以及限流/短期缓存/SSE fan-out | 保存项目、任务、批准或交付等权威业务事实；不可用时伪造验证通过 |

Redis 是首期运行依赖，不是权威业务数据库。丢失或不可用时，刷新会话与一次性验证必须要求重新认证或 fail closed。

### 3.4 外部服务启用 Gate

| 外部服务 | 首次切片 | 启用前必须确认 | 降级路径 |
| --- | --- | --- | --- |
| 一个图像 Provider capability | C | 地域、保留/训练条款、输入输出契约、幂等/对账、用量单位、凭据和测试额度 | 阻止真实外调，保留 A 的 Fixture 路径 |
| 一个视频 Provider capability | C | 同上，并增加时长/参考/分辨率限制和异步任务语义 | 保留图像候选和手工占位，不宣称视频闭环通过 |
| Agent 模型 Provider | B | 结构化输出、Tool 白名单、Token 上限、数据外发与删除政策 | 全部手工工作台持续可用 |
| 通知/邮件 Provider | E；外部审片 F | 收件人授权、模板、退订/撤销、投递回执和敏感字段 | 站内待办和可复制受控链接 |
| 企业 OIDC/SSO | F | issuer、claim 映射、会话撤销、break-glass 和审计 | 本地受控身份；不得降低租户隔离 |
| 私有模型/LoRA | F 或明确企业试点 | 注册主体、版本、地域/权利、健康、回滚、用量和 Adapter 验收 | 停止新路由，保留历史计划和任务对账 |

“多模型路由”只有在两个同类能力完成淘汰原因、受控 fallback 和故障演练后才能宣称完成。首个图像能力加首个视频能力只能证明跨媒体能力接入，不能证明同类路由优化。

## 4. 平台级执行契约

以下是跨模块共享的运行语义，不新增 M16；其对象分别由 M01、M08、M11、M14 等权威模块拥有。

| 契约 | 必须明确的字段/规则 | 失败时用户结果 |
| --- | --- | --- |
| `CommandEnvelope` | command ID/version、workspace/project、actor、idempotency key、expected revision、trace | 冲突或重复回读原结果，不产生第二次副作用 |
| `Operation` | 用户意图、目标范围、状态、进度、最后证据、错误码、恢复动作 | 页面刷新/进程重启后仍可继续或接管 |
| `Job / Attempt` | 逻辑工作与单次尝试分离；Attempt 追加式；外部 ID/确定性持久化 | 超时进入 unknown/ReconciliationCase，不盲目重发 |
| `TaskEnvelope` | task/current schema version、contract hash、operation/job/attempt、最小对象引用、deadline、trace | 非当前版本隔离/死信，不加载旧 decoder 或猜测执行 |
| `ResultPort` | 结果哈希、证据引用、expected state、幂等键、生产者身份 | 重复结果被去重，非法状态转移被拒绝 |
| `DomainEvent` | event ID/type/current schema version、aggregate/version、occurred/recorded time、workspace、trace | 当前消费者可幂等重放；非当前字段/枚举 fail closed，不做旧契约转换 |
| `ErrorContract` | 稳定 code、retryable、用户消息、evidence、recovery actions | 用户看到可执行下一步，不暴露厂商原始敏感错误 |

强一致写入必须在单一 PostgreSQL 短事务内完成；事务提交前禁止模型、对象存储、网络、FFmpeg 或文档解析。副作用通过 Outbox 触发，Worker 再通过受限结果端口提交证据。

## 6. 七阶段生产闭环

竞品分析中的七阶段流程校准为以下可验收链路。每一阶段都有明确事实、人工决定和失败恢复，不以页面跳转代替状态完成。

| 阶段 | 主要模块 | 完成事实 | 阻塞/恢复 |
| --- | --- | --- | --- |
| 1. 导入与拆集 | M02/M03/M09/M14 | project-scoped SourceRevision + ParseReport + approved EpisodeBreakdownManifest + stable ContentUnit/OrderRevision | 损坏/无标题/边界冲突/部分物化显示缺口；可局部恢复且不覆盖人工结果或暴露半成品 |
| 2. 结构化剧本与全局清单 | M03/M04 | approved NarrativeRevision + Entity/UnresolvedSubjectRevision + exact MentionResolution coverage + published ProductionCoverageSchemaRevision + ProductionCoverageDecision + immutable ProductionRequirementRevision + complete Inventory（unassessed=0）+ independent Readiness + revision-bound EntityOccurrenceProjection | 歧义/unresolved/incomplete/not_analyzed/failed scopes 保持可见；缺失/重叠人物决议阻止预检；Agent 不可用时有完整手工创建/决议命令；人物矩阵和清单均按固定基线回源并可重建 |
| 3. 设定资产 | M04/M09/M14 | 已发布 Profile/State/Reference 及有效范围；Requirement 与 Media 分离 | 缺引用、范围冲突或权利未知时阻止外发；接受需求不自动生成媒体 |
| 4. 分镜/预演 | M05/M09 | approved ShotPlan/Order + AnimaticRevision | 覆盖缺口可见；预演是 M05 派生只读结果，M13 仅在 E 读取其基线初始化装配 |
| 5. 提示编译与批准 | M07/M11/M14 | approved GenerationPlan + Prompt/Route/Preflight 快照 | 超限、能力不匹配或治理拒绝时 blocked，不静默降级 |
| 6. 批量生成与选择 | M08/M09/M11 | Job/Attempt 证据 + ready Candidate + SelectionDecision | unknown 先对账；部分失败保留成功项；评分不替代人工选择 |
| 7. 质量、审阅与交付 | M10/M12/M13/M14 | 问题决议 + approved ReviewPackage + DeliverySnapshot | `domain_revision` 修复回 M04/M05，`deterministic_media` 回 M09/M13，只有 `provider_regeneration` 才创建新 M07 Plan；任何必需输出/门禁缺失都不创建 Snapshot |

阶段 2 固定支持两条同源路径：切片 A 的手工工作台直接调用 M03/M04 Command；切片 B 的 `script_analysis` Skill 分成 Breakdown、Narrative、Knowledge 三个 Run，并严格经过 `M03 Manifest 批准 → M02 物化/mapping → M03 Narrative 批准` 两个业务门禁。三个 Run 分别只提交面向 M03 Breakdown Command、面向 M03 `NarrativeDraftImport` 每 ContentUnit staging Command、面向 M04 Knowledge Command 的 M06 AgentProposal；人工接受后仍调用完全相同的目标 Command，两条路径必须产生相同领域结果和错误契约。人物出场集数来自带版本基线的 MentionResolution/EntityOccurrence 投影，不能由前端临时拼接，也不能只保存在 Agent checkpoint 或候选 JSON 中。

Agent 和画布横跨阶段 2—6，但只提供提案、解释和操作视图；它们不是第八阶段，也不拥有另一套项目数据。

## 8. 模块 Design 的可实施完成标准

每个模块详细 Design 在进入接受评审前必须至少包含：

1. 模块目标、非目标、拥有对象和写入所有者；
2. 功能分解到类型化 Command/Query、输入、输出、权限和业务规则；
3. 状态迁移的前置条件、参与者、并发控制、副作用、超时与补偿；
4. 同步端口、事件 payload/version、幂等键和稳定错误/恢复动作；
5. 页面/工作台的 loading、empty、blocked、partial、unknown、stale 和 conflict 状态；
6. Requirement FR/NFR/AC 到接口、数据、测试和验收切片的逐项映射；
7. 从入口 Command 到权威事实、跨模块输出、页面状态和恢复动作可端到端追踪；
8. 至少一个成功闭环、一个权限负例、一个并发/重复负例和一个恢复场景。
9. View、ViewModel、生成 API、Controller、Plain Object Command/Result、HTTP/Task/Agent Schema、ORM 和 Adapter 的映射位置清晰，类型不跨越不属于自己的边界；
10. 每个 Controller 只调用一个明确 Service/Query Handler，每个 Service 对应明确用例、事务和端口，未出现万能 `service.py`、全局 `utils` 或只转发调用的空层；
11. 若使用 Agent，明确 Harness、Skill、M06 Run/Proposal 和目标模块 Command 的四段责任，并有关闭 Agent 后的手工验收；
12. 前端 Feature 明确 URL、本地、RTK Query 和可恢复草稿状态所有权，不复制服务器事实。
13. 任何新增框架、服务、顶层目录或跨模块抽象都附 000 §2.4 的最小调研记录，并说明从官方/开源实现中采用与拒绝了什么；没有现实证据的未来能力不得进入结构。
14. 数据库、HTTP、消息、Agent Result 和 MinIO key 分别只有一套目标契约，验收包含拒绝非当前契约的负向用例。

模块 Design 保持 `proposed`，直到产品、设计、研发和验收责任人完成签认。实施状态记录在 Plan，真实执行证据记录在 Acceptance；文件、Mock 或同名类不能替代签认和验收。

## 9. 首次实施 Gate

以下 Gate 必须由对应纵向切片以真实命令和测试证据满足；它们是目标实现的进入条件，不新增业务模块：

1. **Schema Gate**：最终 SQLAlchemy Metadata 可初始化空业务库；非空库严格一致才 ready；RLS policy/session context 和跨租户负向测试通过。
2. **进程隔离 Gate**：API、Operation、Import、Provider、Agent/Evaluation、Media 六类入口按切片独立启动、健康检查和故障隔离；Import 无公网/KMS，Provider 只有 allowlist egress 和按连接 KMS ref。
3. **耐久执行 Gate**：Operation/Job/Attempt/Outbox/Inbox/Reconciliation 具有统一契约、幂等键、稳定错误和恢复动作；重投、超时、unknown、取消均有可执行验收。
4. **短事务 Gate**：对象存储、probe、文档解析、Provider 和 FFmpeg 均在数据库事务之外运行，结果通过受限端口回写。
5. **Provider Gate**：至少一个图像和一个视频 capability 完成真实提交、轮询/回调、下载、unknown 对账和幂等闭环；凭据只保存 Secret/KMS `credential_ref`。
6. **HTTP/MVVC Gate**：公开路径统一 `/api`；工作区上下文、幂等 Header、乐观并发、稳定错误、SSE 和生成客户端与 003 一致；View→ViewModel→生成客户端→Controller→Service 链路可追踪。
7. **Revision Gate**：Brief、ShotOrder、Narrative、Knowledge、Review 和 Delivery 等历史敏感事实使用不可变 Revision + 显式 current pointer；冻结引用不被后续 current 改写。
8. **剧本分析闭环 Gate**：SourceRevision→approved Manifest→stable ContentUnit/Order→approved Narrative→MentionResolution→Requirement/Inventory/人物矩阵完整可追踪；`episode_numbers` 不作为 Candidate JSON 或前端临时状态的权威事实。
9. **Agent 边界 Gate**：M06 AgentRun/Proposal 与 `agent_runtime` Harness/Skill 分离；`agent_worker` 只用只读 Query Tool 和受限 ResultPort；手工与 Agent 接受调用同一 M03/M04 Service。
10. **模块架构 Gate**：M03/M04 Plain Object Command/Result 不依赖 FastAPI、HTTP Pydantic Request 或 SQLAlchemy Session；Controller 只映射并调用一个用例；CI 阻止框架泄漏、越界 ORM/Repository、循环 import 和生成客户端漂移。
11. **MinIO Gate**：唯一 adapter 位于 `infrastructure/object_storage/minio.py`；Server 镜像和 SDK 版本锁定；私有桶、versioning、canonical key、临时 lifecycle、Object Lock/LegalHold、精确 version ref、hash、删除/恢复和最小权限测试通过。
12. **调研 Gate**：每个新增框架、服务、顶层目录或跨模块抽象在实现前完成 000 §2.4 调研记录，并说明采用、拒绝及其对应验收。
