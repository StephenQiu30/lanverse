# 本机既有环境运行设计

> 历史记录：用户随后明确要求全部应用使用 Docker。本文 LaunchAgent 部署已由 [0020](../design/0020-文本解析失败诊断与受控恢复设计.md) 的部署纠正取代；下文只保留当时事实，不作为当前启动指引。

2026-09-08。用户要求先提交 main，再以本机已经运行的环境承载实际业务。本次是部署落实，不改变 0013/3004 的业务所有权或创作流程。

## 范围与实施规格

- PostgreSQL、MinIO、Kafka、Temporal 和现有 `es-local-dev` / `logstash-local-dev` / `kibana-local-dev` 保持原实例、数据和权限；不启动 bundled profiles 或替代验证实例。
- 沿用正在承载项目的业务库、独立 Creation 库、项目 ID、原稿版本、Temporal Workflow 和冻结 SkillRelease。数据库名字不是环境分类依据，不因名字重建或清空数据。
- 本机 Go 与可信 Creation API 继续通过 loopback 通信，符合现有非 loopback 必须 HTTPS 的合同；不放宽鉴权边界来迁就 Docker 地址。
- 应用使用固定 Git 提交的发布副本。Go 编译为正式二进制，前端使用 Next standalone 生产构建；macOS launchd 在当前用户登录域管理前后端、Harness、Creation API 和 Worker，自动重启退出进程。基础设施仍由其现有管理方式负责。
- 发布副本放在用户 `Library/Application Support/Lanverse/releases/<commit>`，日志在 `Library/Logs/Lanverse`；LaunchAgent 配置权限为 0600，仅给各服务所需配置。凭据不写入仓库，不将可信 Creation 数据库凭据注入 Harness。
- 使用 `.env` 中已有效的 ES 业务账号，Go 日志连接现有 Logstash。使用既有 `lanverse reindex --kind script` 从真实数据库重建应用搜索投影，保持应用自己的别名与蓝绿切换机制，不修改业务 Outbox、Inbox 或 Kafka offset。

## 状态与失败处理

迁移前检查真实运行是否有在途模型调用；存在时先完成或按既有协议排空，不通过杀进程清理。已经 blocked/unknown 的任务保持原状态，部署不能重置或伪造成功；恢复必须另按调用结果对账合同处理。

所有应用仅监听 loopback。本机生产构建与自动拉起不等于公网生产验收；当前用户退出登录后 LaunchAgent 不运行，重启机器需用户登录。若需要无人登录运行或公网服务，应另设计运行账号、TLS、备份与服务托管，不能用修改 ENVIRONMENT 标签代替。
