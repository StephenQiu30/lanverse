## 1. 设计结论

Lanverse 使用一个仓库、四类可运行角色：FastAPI API、Scheduler/Outbox Publisher、同代码库 RabbitMQ Worker、Next.js 工作台。仓库顶层只保留 `backend/`、`frontend/`、`docs/` 三个项目目录，以及必要的 Git/Codex/CI 和根 Compose 配置；不增加 `deploy/`、`apps/`、`packages/`、`services/`、顶层 `src/` 或独立 Worker 仓库。

本文件是目录和命名的唯一事实源。当前仍处于 Design 阶段，只维护文档，不按目录图创建空代码；进入已接受的纵向实施切片时，才创建该切片实际使用的文件。

## 3. 根文件职责

| 文件 | 唯一职责 | 禁止内容 |
| --- | --- | --- |
| README.md | 项目入口、架构链接、依赖条件、启动和验证命令 | 重复完整需求、密钥、过期实现细节 |
| AGENTS.local.md | 当前仓库协作边界与设计阶段限制 | 目录/表数量、供应商和业务需求副本 |

仓库不维护 Makefile、根 package.json、task runner 或命令兼容层。README 直接给出本地 Python/npm 与 Docker Compose 命令，CI 也执行同一组底层工具；工具参数变化时只更新实际调用方，不再维护转发目标。本地开发不隐式启动 Docker，只有显式执行 `docker compose up -d --build --wait` 时才启动完整隔离环境；生产入口必须显式提供 `.env.production`。本地应用只连接已由 Homebrew 安装并运行在 `127.0.0.1:9000` 的 MinIO，仓库不负责启动、停止或管理它。完整 Compose 保留六服务一键启动能力，并将容器 MinIO 发布到宿主机 `9100/9101` 以避开本机服务。

`docs/acceptance/` 中已完成切片记录的旧聚合命令属于当时实际验收证据，不是当前启动或验证入口；现行命令只以 README 与 CI 为准。

~~~text

├── Dockerfile                    # API/Worker 共用镜像
├── pyproject.toml                # 依赖、Ruff、Pyright、Pytest 配置
├── requirements.txt              # pip-compile 生成的运行依赖锁
├── requirements-dev.txt          # pip-compile 生成的开发/测试依赖锁
├── test_main.http                # PyCharm HTTP Client 的健康/就绪请求
├── app/
│   ├── main.py                   # FastAPI composition root
│   ├── server.py                 # 容器内 API/Scheduler/两类 Worker 监督入口
│   ├── scheduler.py              # Schedule dispatcher + Outbox Publisher
│   ├── io_worker.py              # RabbitMQ I/O Worker 组合入口
│   ├── media_worker.py           # RabbitMQ Media Worker 组合入口
│   ├── model_registry.py         # 组合根统一注册已实现 SQLAlchemy Model
│   ├── core/                     # 全局技术能力，不含业务规则
│   │   ├── config.py             # Pydantic Settings
│   │   ├── database.py           # engine/session/空库初始化
│   │   ├── auth.py               # 密码摘要、JWT 验证与 ActorContext 装配
│   │   ├── errors.py             # ApiError/TaskError 基础契约
│   │   ├── logging.py            # JSON logging
│   │   └── observability.py      # OpenTelemetry/Prometheus
│   ├── modules/
│   │   └── <module>/             # identity/projects/media/governance/scripts/
│   │       ├── __init__.py       # 显式导出模块公开用例/DTO
│   │       ├── api.py            # 简单模块 Router；复杂模块只组合子 Router
│   │       ├── contracts.py      # 有跨模块调用者时才创建；无 ORM/FastAPI
│   │       ├── models.py         # 本模块 SQLAlchemy Model
│   │       ├── repository.py     # 本模块共享参数化查询/锁
│   │       ├── schemas.py        # 简单模块的 HTTP/Application DTO
│   │       ├── service.py        # 简单模块的用例、权限和事务编排
│   │       └── <capability>/     # 复杂模块按版本、提取、单集等真实能力拆分
│   │           ├── api.py        # 该能力的 Router/HTTP 映射
│   │           ├── schemas.py    # 该能力 DTO
│   │           └── service.py    # 该能力用例与事务编排
│   └── integrations/
│       ├── rabbitmq.py           # topology、publisher/consumer adapter
│       ├── redis.py              # cache/rate-limit adapter
│       ├── minio.py              # 当前 ObjectStoragePort adapter；选定后再增 oss.py
│       ├── ffmpeg.py             # argv 构造、探测和子进程 adapter
└── tests/                        # 与 app 完全分离
    ├── architecture/             # 目录、导入、ORM 和测试边界
    ├── unit/                     # 纯规则，无外部基础设施
    ├── integration/              # PostgreSQL/RabbitMQ/Redis/MinIO/FFmpeg
    ├── contract/                 # OpenAPI、provider、message schema
    └── conftest.py               # 仅跨测试类别确实共享的 fixture
~~~

业务模块名只允许 identity、projects、media、governance、scripts、assets、storyboards、production、editing；平台交付模块允许 messaging。目录按纵向切片逐步出现，不一次创建空文件。简单模块使用扁平文件；只有已经出现两个独立变化职责的模块才创建 `<capability>/`。完整拆分条件、公开 seam 和迁移顺序见 [DES-006 后端模块工程化重构设计](./arrived/006-后端模块工程化重构设计.md)。

API、Scheduler 与 Worker 共用 `backend/app`、Model 和 use case；容器部署由 `app.server` 在同一 `server` 服务中将三个运行角色作为受监督的并行任务启动，任一角色退出时取消其余角色并让容器失败重启。各角色仍保留独立组合函数，支持本地单独调试；不创建独立 scheduler/worker 服务、第二份 pyproject 或额外 backend Dockerfile。

## 5. 后端模块文件规则

- Router 只依赖本能力 schemas/service；service 可依赖本模块 models/repository/policy/contracts 和其他模块公开接口；repository 只访问本模块 Model。
- 禁止跨模块导入 `models.py`、`repository.py`、内部 `service.py`、能力内部包或内部异常；跨模块只从目标模块 `__init__.py`/`contracts.py` 取得公开命令、查询、Protocol 和 DTO，并只传稳定 ID、版本 ID 与必要快照。
- `service.py`、`schemas.py`、`api.py` 等从单文件开始；当存在两个独立资源生命周期、事务边界或调用方时按业务能力拆子包。行数只作为审计信号，不作为机械拆分标准。
- `contracts.py` 只有真实跨模块调用者时才创建，禁止导入 FastAPI、ORM 或 adapter；公开函数必须完成真实业务动作，禁止增加仅转发一次调用的空 Facade。
- `__init__.py` 无启动、注册、数据库和网络副作用；组合只发生在 main.py/server.py/scheduler.py/io_worker.py。
- core 只容纳 config、database、auth、errors、logging、observability、clock、ID 等技术原语；禁止 `common/`、`shared/`、`utils/` 成为业务垃圾桶。
- SQL/SQLAlchemy 查询留在所属 repository；复杂查询可拆语义明确的文件，例如 `snapshot_query.py`，不建立全局 queries 目录。

## 6. 前端结构

~~~text
frontend/
├── Dockerfile                    # Next.js build 与 standalone 运行时
├── package.json
├── package-lock.json             # npm 唯一 lockfile；CI 使用 npm ci
├── components.json              # shadcn/ui，固定 Radix base
├── openapi2ts.config.ts          # OpenAPI URL → src/api
├── next.config.ts                # Next.js 配置（图片域名、rewrite、headers）
├── tsconfig.json
├── vitest.config.ts
├── playwright.config.ts
├── postcss.config.mjs            # Tailwind v4 PostCSS
├── src/
│   ├── app/                      # Next.js App Router：layout、路由、Provider
│   │   ├── layout.tsx            # 根布局（Provider 树 + 全局样式）
│   │   ├── page.tsx              # S0 根首页；业务入口从 S1 开始
│   │   ├── globals.css           # Tailwind v4 + CSS 变量
│   │   └── <route>/               # 真实 URL 段，如 projects、studio/[episodeId]/script
│   │       ├── page.tsx           # 该 URL 段的页面入口
│   │       └── useXxxViewModel.ts # 仅服务该页面的 ViewModel/Controller
│   ├── api/                      # @umijs/openapi 生成并提交，禁止手改
│   ├── components/
│   │   ├── ui/                    # shadcn/ui/Radix 无业务基础件
│   │   └── <feature>/             # 按业务场景组织的可复用组件
│   ├── lib/
│   │   ├── request.ts            # axios 请求适配 + auth 拦截器 + 错误映射
│   │   ├── server-state.ts       # RTK Query 服务端状态与缓存失效
│   │   ├── redux-store.ts        # Redux store 与 middleware 配置
│   │   ├── auth-session.ts       # 浏览器访问令牌会话
│   │   └── class-names.ts        # 仅合并 Tailwind className
│   └── hooks/                    # 共享 hooks（Redux selector/action helpers）
└── tests/                        # 禁止把测试放进 src
    ├── architecture/
    ├── unit/
    ├── integration/
    └── e2e/
~~~

页面和组件均按用户任务而非后端表命名，例如 projects、studio、tasks、editing。路由页面直接进入 `app/<route>/`；禁止增加 `pages` 中间层，否则 Next.js 会把它暴露为 `/pages/...` URL。只有多个路由确实共享独立 layout 或访问边界时才建立语义明确的 Route Group，不使用 `(main)`、`(routes)` 等泛化分组。动态参数使用 `[projectId]`、`[episodeId]` 等 App Router 目录；只服务该页面的 ViewModel/Controller hook 与页面同目录。任务卡、镜头卡、资产选择器等可复用业务组件进入 `components/<feature>/`。`app` 可依赖 `components`，业务组件不得反向导入页面；`components/ui` 仅容纳无业务语义的通用 UI。不再设立同时混放页面、组件和状态的顶层 `features/`，也不因一次使用而提前创建 feature 目录或 barrel 文件。

RTK Query 保存服务端状态（缓存键、tag 失效、按需重新获取与必要轮询）；Redux Toolkit slice 只保存未提交编辑草稿、选择和布局。`src/api` 必须在 `frontend/` 执行 `npm run openapi2ts` 从 OpenAPI URL 更新并提交，CI 重新生成后检查 diff；业务代码不能手写平行 DTO/URL。

## 7. 容器与环境结构

~~~text
Lanverse/
├── docker-compose.yml            # PostgreSQL/Redis/RabbitMQ/MinIO/server/web
├── docker-compose.prod.yml       # 隐藏基础设施端口并改用已发布应用镜像
├── .env.example                  # development 示例
├── .env.production.example       # production 示例；必需 secret 留空
├── backend/Dockerfile            # API/Scheduler/Worker 共用镜像
└── frontend/Dockerfile           # Next.js standalone 镜像
~~~

Compose 参考 `StephenQiu30/code-ark` 的直接配置和本地开发优先方式，但承担完整环境快速启动与生产部署职责。`docker-compose.yml` 是六个服务、健康依赖、持久卷和重启策略的共享事实源：PostgreSQL、Redis、RabbitMQ、MinIO 提供依赖，`server` 先幂等初始化数据库，再使用一个后端镜像监督 API/Scheduler/Worker，`web` 运行 Next.js。`docker-compose.prod.yml` 只是生产差异层，不复制服务定义：它重置四项基础设施的宿主机端口、移除 server/web 的 `build`，并强制 `ENVIRONMENT=production`；生产命令使用 `--no-build --pull always --wait`。基础镜像统一使用 `latest`，不维护 tag、digest 或二进制版本守卫。

服务通过 Compose DNS 互联，不设置固定 `container_name`，从而允许 Compose project 隔离环境；也不维护宿主机 `CONTAINER_*` 转发地址。开发使用未提交的 `.env`，默认复用本机 Homebrew PostgreSQL、Redis、RabbitMQ 和 `127.0.0.1:9000` 的 MinIO，项目不管理这些本机服务。需要完整隔离环境时直接执行 `docker compose up -d --build --wait`；Compose 的 MinIO 在宿主机使用 `9100/9101`，容器内部仍通过 `minio:9000` 通信，因此可与本机 MinIO 并存。生产使用未提交的 `.env.production`，必需 secret 为空时 Compose 解析即失败，并通过 production 薄覆盖执行 `up -d --no-build --pull always --wait`。MVP 不复制完整 Compose，不创建 `deploy/`、Kubernetes、Helm、Terraform 或每模块 Dockerfile。

RabbitMQ topology 由应用幂等声明，不提交 definitions 快照。只有环境变量和 Compose command 无法表达且已有真实运行需求时，才在对应应用目录增加命名明确的配置文件。

## 8. 文档结构与命名

~~~text
docs/
├── requirement/                  # 已确认前的需求事实，中文文件名
├── design/                       # 架构与详细设计，中文文件名
├── prd/                          # Design 接受后按 MVP 切片创建

~~~

任一目录都不能作为空模板预建；Plan 可在 PRD 评审期写成 `proposed` 实施蓝图，但 PRD/Plan 未接受时不得据此创建代码脚手架。文档使用 `三位序号-中文功能主题.md`，目录索引使用中文名；文件主题不得使用 `S0/S1/S2` 等实施切片编号代替业务语义，切片与 `DEV-*` 只作为正文追踪字段。源码、配置、数据库表、API 字段和测试文件使用 ASCII 英文：Python 文件/包 snake_case，React 组件和页面 PascalCase.tsx，Hook/ViewModel 使用 `useXxx.ts`，Playwright 用例使用功能语义 kebab-case，shadcn 生成文件保持其原名。命名迁移和断链证据见[环境占位与语义化文件命名验收](../acceptance/arrived/009-环境占位与语义化文件命名验收.md)。

中文业务文档与英文源码命名职责不同：中文便于产品/设计评审；英文源码保证 Python import、Docker、CI、OpenAPI 生成和跨平台工具稳定。禁止拼音缩写和中英文混合源码路径。

## 9. 配置、secret 和生成物

- 仓库维护根目录 `.env.example` 与 `.env.production.example` 两个可提交模板，分别描述 development 默认值和 production 契约；两者变量集合必须完全一致，均覆盖应用连接串、隔离测试数据库、PostgreSQL 初始化、Redis/RabbitMQ、MinIO、认证、Provider、前端和 Compose 配置，只允许值与密钥策略不同。真实环境使用未提交的 `.env` 与 `.env.production`。后端 Pydantic Settings、前端运行命令、OpenAPI 生成和 Compose 共享变量名，禁止在 `backend/`、`frontend/` 重复维护环境文件。开发模板可提供仅限本机的默认凭据；生产模板中的数据库连接串、数据库密码、RabbitMQ 连接串/密码、MinIO、JWT 和 Provider secret 必须留空，由所选部署入口注入；Docker Compose 对实际消费的数据库、RabbitMQ、MinIO 和 JWT 离散 secret 缺失时快速失败。真实凭据、预签名 URL 和本地数据禁止提交；`NEXT_PUBLIC_*` 会进入浏览器包，只能保存公开配置。Compose 显式映射后端设置，并用服务 DNS 覆盖基础设施地址。
- 后端采用 PyCharm FastAPI Project venv 语义：开发者选择 Python 3.11.15，使用 `python3.11 -m venv backend/.venv` 创建标准虚拟环境，再通过该环境的 `python -m pip` 安装依赖；不使用 uv 创建、同步或运行环境。PyCharm 将 `backend/.venv/bin/python` 配为项目解释器，FastAPI Application file 指向 `backend/app/main.py`、Application name 为 `app`、Working directory 为 `backend/`；Pyright 通过 `venvPath = "."` 与 `venv = ".venv"` 使用同一解释器。
- `backend/pyproject.toml` 是依赖声明和质量配置的唯一手写来源；项目固定 pip 26.1.2 与 pip-tools 7.6.0，避免未经验证的安装器升级破坏锁生成。`requirements.txt` 与 `requirements-dev.txt` 由当前 `.venv` 从 pyproject 生成并提交。普通安装使用 `python -m pip install -r backend/requirements-dev.txt`；依赖变更后在 `backend/` 直接执行 `.venv/bin/python -m piptools compile pyproject.toml --output-file requirements.txt --strip-extras` 及带 `--extra dev` 的开发锁命令，并审查生成差异，不使用全局 pip。
- PyCharm 的 FastAPI 模板只提供项目解释器、`main.py`、`test_main.http` 和 Run/Debug 支持；Lanverse 保留已接受的模块化 `app/` 结构，并提交适配真实 `/healthz`、`/readyz` 的 `test_main.http`，不提交个人 `.idea/`、绝对解释器路径或 workspace 设置。
- 前端基线必须由 Vercel/Next.js 官方 `create-next-app` CLI 生成：`npx --yes create-next-app@16.2.12 frontend --typescript --tailwind --eslint --app --src-dir --empty --use-npm --disable-git --no-agents-md --yes`。生成后只在同一结构上加入业务依赖、测试、shadcn 与项目配置，不手写第二套脚手架。
- 必须提交 requirements 锁、package-lock.json、OpenAPI 生成的 src/api 和可审查配置；必须忽略 `.venv`、`.idea`、node_modules、dist、coverage、测试报告、临时媒体、基础设施数据和日志。测试样本只进入 tests/fixtures，保持最小且无真实个人数据。
- 数据库测试必须使用显式 `TEST_DATABASE_URL`，数据库名以 `_test` 结尾且不得等于 `DATABASE_URL`；默认复用本机专用测试库，单测事务回滚，并行时按 worker 隔离 schema。Testcontainers 仅在调用者显式设置 `LANVERSE_TEST_DATABASE_MODE=testcontainers` 时启动；默认 `.venv/bin/python -m pytest` 不得隐式启动容器，缺少测试库时应快速失败并提示前置条件。CI 使用显式 PostgreSQL service 或显式 Testcontainers 模式，不能与本地规则形成第二套测试语义。

## 10. 工程门禁

| 门禁 | 必须验证 |
| --- | --- |
| tree | 顶层只出现允许目录；不存在 backend/src/lanverse、apps、packages、独立 worker、源码内测试 |
| backend architecture | 模块导入单向、跨模块不导 ORM/Repository、core 不含业务、Model 属主唯一 |
| frontend architecture | src/api 无手改漂移、app 向 components 单向依赖、服务端状态不复制到 Redux |
| quality | Ruff、Pyright、Pytest、前端 lint/type/Vitest/Playwright、真实基础设施集成按切片通过 |
| delivery | 当前切片已有角色可 Docker build、compose config、健康检查和空库初始化；S2 创建 Scheduler/Worker 后验证三者使用同一 backend 镜像 |
| hygiene | requirements/package lock 已提交，secret/缓存/报告/本地数据未跟踪，git diff 无无关文件 |

architecture 测试属于正常测试，不编写自定义脚手架框架。只有命令包含无法由单个 Python/npm/Compose 调用表达的稳定领域流程，并且至少被本地与 CI 共同使用时，才在所属 backend/frontend 下增加命名明确的脚本；普通命令组合不得再引入 task runner。

质量配置保持少而硬：Python 3.11 源码与测试使用 Pyright strict，Ruff 至少启用 E/F/I/UP/B/ASYNC；`type: ignore`/`noqa` 必须限定具体规则并写原因。前端 authored TS/TSX 使用 TypeScript strict 和 ESLint，`frontend/src/api` 只接受生成器输出；业务代码不得通过 `any`、重复 DTO 或禁用检查适配生成 client。覆盖率只用于发现未执行分支，不设置脱离风险的全局百分比；事务、并发、权限、幂等和失败恢复必须由对应场景测试证明。

### 10.1 CI 执行边界

`.github/workflows/ci.yml` 保持为唯一主工作流，但按失败责任拆成并行 job；不为消除少量重复安装引入共享脚本、复合 Action 或第二套命令入口。

| Job | 负责证明 | 不负责证明 |
| --- | --- | --- |
| `Backend / Quality` | 后端锁安装、Ruff、Pyright、默认 Pytest、pip 完整性；使用显式 PostgreSQL 测试库 | 需要环境变量开启的真实 Redis/RabbitMQ/MinIO/ffprobe 契约 |
| `Frontend / Quality` | npm 10.9.8 可从 lockfile 清洁安装，ESLint、TypeScript、Vitest、Next.js build | 后端接口可达性与浏览器系统流程 |
| `API / OpenAPI Drift` | FastAPI OpenAPI 可生成前端 client，提交的 `src/api` 无漂移 | 页面交互正确性 |
| `Infrastructure / Contracts` | 真实 Redis、RabbitMQ、MinIO、ffprobe、Scheduler 和媒体栈 | 第三方付费 Provider；其测试继续由显式密钥门禁控制 |
| `System / Browser E2E` | PostgreSQL、Redis、RabbitMQ、MinIO、API 与 Web 共同运行时的无密钥 Playwright 主流程 | 生产部署与真实 Provider 调用 |
| `Delivery / Compose and Images` | 仓库卫生、开发/生产 Compose 可解析、server/web 镜像可构建 | 镜像发布和生产迁移 |
| `Required / CI` | 汇总以上所有 job 的真实 `success`，提供稳定的 required check 名称 | 替代任一上游测试 |

工作流在 `pull_request`、`merge_group` 和 `main` push 上完整运行，不使用 path filter，也不把失败 job 设为 `continue-on-error`。每个 job 必须设置与其正常耗时匹配的超时，`GITHUB_TOKEN` 只授予 `contents: read`。`Required / CI` 使用 `needs`、`always()` 和每个上游的 `result` 显式拒绝 failure、cancelled 或 skipped；这样内部 job 调整时，分支规则仍只依赖一个稳定名称。

CI 只能验证已推送的 main commit、PR head 或 merge queue commit，不能证明尚未推送的本地 commit。要做到“失败不得进入 main”，GitHub 仓库规则必须禁止直接绕过 main，并把 `Required / CI` 配为严格 required status check；工作流文件本身不能替代该远端规则。提交前仍运行 README 中与改动相符的直接命令，远端 runner 成功才形成最终 CI 证据。

## 11. 初始化顺序

1. 接受本 Design 后创建根 README、EditorConfig、GitIgnore 和最小 CI，命令直接使用 Python、npm 与 Docker Compose。
2. 创建 backend/frontend、根 Compose 配置与空库/健康检查最小闭环，不创建九模块空壳。
3. 按 identity + projects 第一个纵向切片创建实际模块、测试和 OpenAPI client。
4. 后续切片按依赖加入 media/governance/scripts/assets/storyboards/production/editing。
5. 每次新增目录都必须能追踪到已接受的 Design/PRD/Plan 和同次测试；目录图本身不构成创建理由。

## 12. 明确禁止的结构

- 禁止 `backend/src/lanverse/`、`backend/app/app/`、顶层 `src/`、全局 controllers/services/repositories，以及顶层 `apps/`、`packages/`、`shared/`、`common/`、`utils/`、`workers/`、`storage/`、`logs/`、`data/`。
- 每个业务模块复制完整 Clean Architecture 五层、每张表一套 CRUD、单独 Worker 项目或 Dockerfile。
- 在 backend/app 或 frontend/src 放测试、fixture、mock server、报告和构建产物。
- 禁止手写修改 pip-compile 生成的 requirements 锁、提交 uv.lock/个人 `.idea`、维护多个前端 lockfile，或为未来 Kubernetes、微服务、插件市场和多租户分库预建目录。
