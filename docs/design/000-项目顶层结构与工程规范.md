# DES-000 项目顶层结构与工程规范

- 状态：proposed
- 日期：2026-07-27
- 输入：SYS-NFR-008/009、已确认技术方向、`AGENTS.md` 长期协作规则
- 输出：仓库根目录、前后端与部署结构、命名、依赖、配置、命令和工程门禁
- 下游：所有架构/模块 Design、MVP PRD、初始化 Plan 与实现

## 1. 设计结论

Lanverse 使用一个仓库、三个可运行边界：FastAPI API、同代码库 Worker、React 工作台。仓库顶层只保留 `backend/`、`frontend/`、`deploy/`、`docs/` 四个项目目录，以及必要的 Git/Codex/CI 配置；不增加 `apps/`、`packages/`、`services/`、顶层 `src/` 或独立 Worker 仓库。

本文件是目录和命名的唯一事实源。当前仍处于 Design 阶段，只维护文档，不按目录图创建空代码；进入已接受的纵向实施切片时，才创建该切片实际使用的文件。

## 2. 目标仓库顶层

~~~text
Lanverse/
├── .codex/                       # Codex agent/skill 配置，不放业务事实
├── .github/
│   └── workflows/
│       └── ci.yml                # 唯一主 CI 工作流；需要时再按职责拆分
├── backend/                      # FastAPI API + RabbitMQ Worker，同一 Python 项目
├── frontend/                     # React/Vite 登录后工作台
├── deploy/                       # Docker/Compose 与部署配置，不放业务代码
├── docs/                         # 中文需求、设计、PRD、Plan、Acceptance
├── .editorconfig                 # 跨语言基础格式
├── .gitignore                    # 缓存、secret、构建和本地数据排除
├── AGENTS.md                     # 长期稳定协作规则，不写产品/架构事实
├── AGENTS.local.md               # 本仓库阶段性协作边界，不复制正式设计
├── LICENSE
├── Makefile                      # 人和 CI 的统一命令入口
└── README.md                     # 项目目标、前置条件、最短启动/验证路径
~~~

个人 IDE 文件和本地 `.env` 可以存在但不得提交。根目录不放 `requirements.txt`、`package.json`、数据库脚本、媒体样本、日志、对象存储数据或生成成片。

## 3. 根文件职责

| 文件 | 唯一职责 | 禁止内容 |
| --- | --- | --- |
| README.md | 项目入口、架构链接、依赖条件、启动和验证命令 | 重复完整需求、密钥、过期实现细节 |
| Makefile | 对 uv、npm、Docker Compose 和生成命令做薄封装 | 隐藏业务逻辑、长 Bash 程序、环境特判 |
| AGENTS.local.md | 当前仓库协作边界与设计阶段限制 | 目录/表数量、供应商和业务需求副本 |

根 Makefile 只转发命令，建议目标固定为 `setup`、`dev-api`、`dev-frontend`、`worker-io`、`worker-media`、`db-init`、`generate-api`、`lint`、`typecheck`、`test`、`check`、`compose-up`、`compose-down`。具体命令在初始化 Plan 中落实并由 CI 调用同一入口。

## 4. 后端结构

~~~text
backend/
├── .env.example                  # 仅变量名、安全示例和说明
├── pyproject.toml                # 依赖、Ruff、Pyright、Pytest 配置
├── uv.lock                       # 必须提交；CI 使用 frozen 安装
├── app/
│   ├── __init__.py               # 无导入副作用
│   ├── main.py                   # FastAPI composition root
│   ├── worker.py                 # 同一入口按 io/media kind 启动 Worker
│   ├── core/                     # 全局技术能力，不含业务规则
│   │   ├── config.py             # Pydantic Settings
│   │   ├── database.py           # engine/session/空库初始化
│   │   ├── auth.py               # OIDC 验证与 ActorContext 装配
│   │   ├── errors.py             # ApiError/TaskError 基础契约
│   │   ├── logging.py            # JSON logging
│   │   └── observability.py      # OpenTelemetry/Prometheus
│   ├── modules/
│   │   └── <module>/             # identity/projects/media/governance/scripts/
│   │       ├── __init__.py       # 只导出模块公开用例/DTO
│   │       ├── api.py            # Router/HTTP 映射
│   │       ├── schemas.py        # Pydantic HTTP/Application DTO
│   │       ├── service.py        # 用例、权限和事务编排
│   │       ├── models.py         # 本模块 SQLAlchemy Model
│   │       ├── repository.py     # 本模块参数化查询/锁
│   │       └── domain.py         # 仅在存在独立业务规则时创建
│   └── integrations/
│       ├── rabbitmq.py           # topology、publisher/consumer adapter
│       ├── minio.py              # 私有对象存储 adapter
│       ├── ffmpeg.py             # argv 构造、探测和子进程 adapter
│       └── providers/            # 第一个真实供应商接入时创建
└── tests/                        # 与 app 完全分离
    ├── architecture/             # 目录、导入、ORM 和测试边界
    ├── unit/                     # 纯规则，无外部基础设施
    ├── integration/              # PostgreSQL/RabbitMQ/MinIO/FFmpeg
    ├── contract/                 # OpenAPI、provider、message schema
    └── conftest.py               # 仅跨测试类别确实共享的 fixture
~~~

`<module>` 只允许九个业务名：identity、projects、media、governance、scripts、assets、storyboards、production、editing。目录按纵向切片逐步出现，不一次创建九套空文件。

API 与 Worker 共用 `backend/app`、Model 和 use case；Compose 通过不同 command 启动同一 backend 镜像，不创建 `backend-worker/`、第二份 pyproject 或 worker Dockerfile。

## 5. 后端模块文件规则

- Router 只依赖 schemas/service；service 可依赖本模块 domain/repository 和其他模块公开接口；repository 只访问本模块 Model。
- 禁止跨模块导入 `models.py`、`repository.py` 或内部异常；跨模块只传稳定 ID、版本 ID 和公开 DTO。
- `service.py`、`repository.py` 等从单文件开始；只有出现两个独立变化职责时才拆子包，不按行数或模板预拆。
- `__init__.py` 无启动、注册、数据库和网络副作用；组合只发生在 main.py/worker.py。
- core 只容纳 config、database、auth、errors、logging、observability、clock、ID 等技术原语；禁止 `common/`、`shared/`、`utils/` 成为业务垃圾桶。
- SQL/SQLAlchemy 查询留在所属 repository；复杂查询可拆语义明确的文件，例如 `snapshot_query.py`，不建立全局 queries 目录。

## 6. 前端结构

~~~text
frontend/
├── .env.example                  # 只含 VITE_* 公共配置示例
├── package.json
├── package-lock.json             # npm 唯一 lockfile；CI 使用 npm ci
├── components.json              # shadcn/ui，固定 Radix base
├── openapi2ts.config.ts          # OpenAPI URL → src/api
├── tsconfig.json
├── vite.config.ts
├── vitest.config.ts
├── playwright.config.ts
├── index.html
├── src/
│   ├── main.tsx
│   ├── app/                      # Router、Provider、全局布局和错误边界
│   ├── api/                      # @umijs/openapi 生成并提交，禁止手改
│   ├── components/ui/            # shadcn/ui/Radix 无业务基础组件
│   ├── features/<feature>/       # 页面、局部组件、ViewModel，按用户场景组织
│   ├── lib/
│   │   ├── request.ts            # 生成 client 的唯一请求适配
│   │   └── cn.ts                 # 允许的机械样式辅助
│   └── styles/index.css          # Tailwind v4 和设计令牌入口
└── tests/                        # 禁止把测试放进 src
    ├── architecture/
    ├── unit/
    ├── integration/
    └── e2e/
~~~

features 按用户任务而非后端表命名，例如 projects、studio、tasks、editing；一个 feature 从页面/组件/ViewModel 实际文件开始，不强制创建 pages/components/hooks/store 四层。跨 feature 编排留在 app，禁止互相导入内部文件。

TanStack Query 保存服务端状态；Zustand 只保存未提交编辑草稿、选择和布局。`src/api` 必须通过 `make generate-api` 从 OpenAPI URL 更新并提交，CI 重新生成后检查 diff；业务代码不能手写平行 DTO/URL。

## 7. 部署结构

~~~text
deploy/
├── .env.example                  # Compose 服务变量，无真实凭据
├── compose.yaml                  # API、I/O Worker、Media Worker、Web、PG、MQ、MinIO
├── docker/
│   ├── backend.Dockerfile        # API/Worker 共用镜像
│   └── frontend.Dockerfile       # Vite build 与静态运行时
└── config/                       # 只有环境变量/命令无法表达时才创建具体配置
~~~

Compose 服务名固定为 api、worker-io、worker-media、web、postgres、rabbitmq、minio。持久数据使用命名 volume，不映射到仓库的 `data/`；运行日志走 stdout/stderr，不写 `logs/`。MVP 不创建 `k8s/`、Helm、Terraform 或每模块 Dockerfile。

RabbitMQ topology 由应用幂等声明，不提交 definitions 快照；OpenTelemetry Collector、Prometheus 抓取和静态 Web Server 配置只有在部署 Plan 选定后才进入 `deploy/config/<component>/`。

## 8. 文档结构与命名

~~~text
docs/
├── requirement/                  # 已确认前的需求事实，中文文件名
├── design/                       # 架构与详细设计，中文文件名
├── prd/                          # Design 接受后按 MVP 切片创建
├── plan/                         # PRD 接受后创建实施计划
└── acceptance/                   # 实现完成后记录真实证据
~~~

当前只创建 requirement/design；后三个目录不能作为空模板预建。文档使用 `三位序号-中文主题.md`，目录索引使用中文名。源码、配置、数据库表、API 字段和测试文件使用 ASCII 英文：Python 文件/包 snake_case，React 组件和页面 PascalCase.tsx，Hook/ViewModel 使用 `useXxx.ts`，shadcn 生成文件保持其原名。

中文业务文档与英文源码命名职责不同：中文便于产品/设计评审；英文源码保证 Python import、Docker、CI、OpenAPI 生成和跨平台工具稳定。禁止拼音缩写和中英文混合源码路径。

## 9. 配置、secret 和生成物

- `.env`、真实凭据、OIDC/Provider secret、预签名 URL 和本地数据禁止提交；每个运行边界只维护自己的 `.env.example`。
- 后端配置只由环境变量进入 Pydantic Settings；前端只有明确公开的 VITE_* 值，不把服务端 secret 注入构建。
- 必须提交 uv.lock、package-lock.json、OpenAPI 生成的 src/api 和可审查配置；CI 用 frozen/ci 安装。
- 必须忽略 `.venv`、缓存、node_modules、dist、coverage、测试报告、临时媒体、基础设施数据和日志；测试样本只进入 tests/fixtures，保持最小、无真实个人数据，大型二进制不进入 Git。

## 10. 工程门禁

| 门禁 | 必须验证 |
| --- | --- |
| tree | 顶层只出现允许目录；不存在 backend/src/lanverse、apps、packages、独立 worker、源码内测试 |
| backend architecture | 模块导入单向、跨模块不导 ORM/Repository、core 不含业务、Model 属主唯一 |
| frontend architecture | src/api 无手改漂移、feature 不越界、服务端状态不复制到 Zustand |
| quality | Ruff、Pyright、Pytest、前端 lint/type/Vitest/Playwright、真实基础设施集成按切片通过 |
| delivery | Docker build、compose config、健康检查、空库初始化、API/Worker 使用同镜像 |
| hygiene | lockfile 已提交，secret/缓存/报告/本地数据未跟踪，git diff 无无关文件 |

architecture 测试属于正常测试，不编写自定义脚手架框架。只有命令超过 Makefile 薄封装能力且至少被本地与 CI 共同使用时，才在所属 backend/frontend 下增加命名明确的脚本。

## 11. 初始化顺序

1. 接受本 Design 后创建根 README、Makefile、EditorConfig、GitIgnore 和最小 CI。
2. 创建 backend/frontend/deploy 的配置文件与空库/健康检查最小闭环，不创建九模块空壳。
3. 按 identity + projects 第一个纵向切片创建实际模块、测试和 OpenAPI client。
4. 后续切片按依赖加入 media/governance/scripts/assets/storyboards/production/editing。
5. 每次新增目录都必须能追踪到已接受的 Design/PRD/Plan 和同次测试；目录图本身不构成创建理由。

## 12. 明确禁止的结构

- 禁止 `backend/src/lanverse/`、`backend/app/app/`、顶层 `src/`、全局 controllers/services/repositories，以及顶层 `apps/`、`packages/`、`shared/`、`common/`、`utils/`、`workers/`、`storage/`、`logs/`、`data/`。
- 每个业务模块复制完整 Clean Architecture 五层、每张表一套 CRUD、单独 Worker 项目或 Dockerfile。
- 在 backend/app 或 frontend/src 放测试、fixture、mock server、报告和构建产物。
- 禁止同时维护 requirements.txt 与 pyproject/uv.lock、多个前端 lockfile，或为未来 Kubernetes、微服务、插件市场和多租户分库预建目录。
