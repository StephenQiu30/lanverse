# DES-MOD-012 消息队列详细设计

- 状态：proposed
- 日期：2026-07-27
- 覆盖需求：MQ-ENT-001 至 004、MQ-FR-001 至 009、MQ-IF-001 至 005、MQ-NFR-001 至 009
- 输入：[消息队列与异步投递需求](../../requirement/011-消息队列与异步投递需求.md)、[生产模块详细设计](./009-生产模块详细设计.md)
- 输出：RabbitMQ topology、Outbox/Inbox、发布消费、重试、并发和运维设计

## 1. 设计结论

MVP 使用 RabbitMQ + aio-pika robust connection，只承担“某个持久任务现在可以执行”的至少一次通知。PostgreSQL 的 Task/Attempt、Schedule/Fire、业务请求、Outbox 和 Inbox 是事实源；RabbitMQ 队列深度、redelivery 标志和管理页面都不能决定业务状态。

只建立两个主队列，不增加业务队列、延迟队列或 DLQ。延迟重试和毒消息处置落在 PostgreSQL，避免 RabbitMQ TTL/DLX 与 Task 再形成一套互相漂移的状态机。

## 2. RabbitMQ topology

| 资源 | 名称/属性 | 用途 |
| --- | --- | --- |
| Exchange | lanverse.tasks.v1，topic、durable、非 auto-delete | 所有 Worker 通知的唯一交换机 |
| I/O Queue | lanverse.io，durable、非 exclusive、manual ack | 模型提交/查询、下载、内容检查等网络 I/O |
| Media Queue | lanverse.media，durable、非 exclusive、manual ack | 探测、转码、预览、FFmpeg 渲染和标识处理 |
| Bindings | io.# → lanverse.io；media.# → lanverse.media | 未登记 routing key 发布前即拒绝 |

消息使用 application/json、UTF-8、delivery_mode=2，并设置 message_id=event_id、type=event_type、correlation_id=trace_id。业务超时不依赖 RabbitMQ message expiration；payload 大小设部署上限，超限在发布前拒绝。

路由白名单：io.script.extract、io.provider.submit/query/cancel/download、io.moderation.check、media.probe/transcode/preview/render/label。`io.script.extract` 的 v1 payload 只包含 task_id，Worker 从 PostgreSQL 读取固定输入。新增 routing key 必须同时增加版本化 payload、handler、幂等键和契约测试。

## 3. Envelope 与 handler

Envelope 字段为 event_id、event_type、schema_version、aggregate_id、workspace_id、occurred_at、trace_id、可选 causation_event_id、payload。payload 只含 task_id、request_id、input_version_id/hash 等执行定位信息；Worker 必须从 PostgreSQL重新读取完整事实和当前状态。

Handler 通过显式字典以 event_type + schema_version 注册，返回 completed、retry_scheduled、rejected 或 manual_attention。禁止 pickle、Python import path、任意函数名和反射执行。未知版本写 Inbox rejected 和稳定 TaskError 后 ack，并产生告警。

DeliveryAttempt 不单独建表：发布尝试由 Outbox 的 attempt_count/last_error/available_at 表达，消费尝试由 Inbox 的 attempt_count/last_error 表达；供应商实际执行尝试仍使用 production Attempt。三者含义不同，不合并成万能 attempt 表。

## 4. Outbox 写入与发布

顶层业务命令在同一 session.begin 中写 Request/Task/Reservation 等事实和 sys_outbox_events(pending)。任何一项失败都回滚；事务中不连接 RabbitMQ。

Outbox Publisher 作为 Scheduler 运行角色中的独立受监督 loop 运行，与 Schedule dispatcher 不共享状态机；容器部署时该角色由 `app.server` 与 API、I/O Worker 统一监督。Publisher 循环流程：

1. 以 available_at 到期、status=pending 为条件，FOR UPDATE SKIP LOCKED 小批量领取，写 claimed_at/by 后提交短事务。
2. 逐条发布相同 event_id 的持久消息，并等待 publisher confirm；不得先标记 published。
3. confirm 成功后比较状态更新 published_at；confirm 超时/连接断开则递增 attempt_count、计算带 jitter 的有上限退避并回到 pending。
4. Publisher 崩溃造成 claim 过期时，由下一实例回收；重复发布仍使用原 event_id。
5. 超过发布策略上限进入 manual_attention 并告警，不删除 Outbox；人工重放仍使用原 event_id 或显式新事件记录原因。

多个 Publisher 通过 SKIP LOCKED 并行，不需要全局分布式锁。批量、轮询间隔、claim lease 和退避上下限属于部署配置，性能目标在 PRD/压测量化。

## 5. Consumer 事务与 ack 矩阵

正常消费流程：解析/限大小 → 建立 trace span → 读取 Inbox → 锁定 Task/聚合 → 校验状态和 input_hash → 执行一个可恢复阶段 → 写业务结果与 Inbox → 提交 → ack。

| 场景 | 数据库处置 | RabbitMQ 处置 |
| --- | --- | --- |
| 首次且成功 | Inbox completed，业务事实提交 | ack |
| 已 completed/rejected | 回读既有结果，不再调用外部系统 | ack |
| 可重试业务失败 | Inbox retry_scheduled、Task error、新 Outbox available_at | 当前消息 ack；到期由新 event_id 通知唤醒，并引用 causation_event_id |
| 不可重试/毒消息 | Inbox rejected/manual_attention、Task 稳定错误 | ack 并告警 |
| 提交前 Worker 崩溃 | 无完成事实 | channel 关闭后 broker 重投 |
| 提交后 ack 前崩溃 | Inbox 已完成 | 重投后回读并 ack |
| PostgreSQL 暂不可用 | 无法持久处置 | nack requeue，连接级退避，避免忙循环 |

外部供应商调用不能被数据库事务包围。Consumer 在发送前先提交 Attempt 和 provider_request_key；发送结果未知时写 unknown，并通过后续 reconcile 事件查询，不能 nack 原消息触发重新 submit。

## 6. 重试、取消和顺序

重试策略由 TaskError.code 映射：可重试基础设施错误使用有上限指数退避；参数、权限、状态冲突直接 rejected；供应商 unknown 只允许 reconcile；达到上限进入 manual_attention。发布 confirm 不确定时重用原 event_id；已消费阶段的计划重试创建新 event_id 并保存 causation_event_id，不能与 broker 重投混为一类。具体次数和时间不是代码散落常量，而是按 task_type 的受控配置。

取消请求只写 Task.cancel_status。Worker 在外部调用前、轮询前和媒体阶段边界重新读取；可取消时调用 provider cancel 或终止 FFmpeg，不能取消时保存 rejected/result_completed。清空队列不等于取消。

系统不依赖消息顺序。每次处理比较 Task revision、目标状态、input_version_id/hash；晚到消息发现事实已前进时安全 ack。单 Shot 批量生成仍是独立 Task，避免队头任务阻塞整批。

## 7. 连接、并发与容量

API、Scheduler/Publisher、I/O Worker、Media Worker 各自维护 aio-pika robust connection/channel，不因部署在同一 `server` 服务中共享 channel。连接恢复后重新声明完全相同的 durable topology；声明参数不一致视为启动失败。

lanverse.io 的 prefetch_count 不高于有界 ThreadPoolExecutor.max_workers。异步 SDK 调用优先留在 event loop；仅阻塞 SDK 进入线程池。lanverse.media 使用更小 prefetch，FFmpeg 每任务独立子进程并由 semaphore 限制；线程池不执行 CPU 密集编解码。

API 在 RabbitMQ 短时不可用时仍可提交 Outbox，`/readyz` 返回 HTTP 200 + `status=degraded`，并在依赖明细中标记 RabbitMQ 非硬依赖故障。若 pending Outbox 数/年龄超过容量门槛，新的高成本任务返回 DEPENDENCY_UNAVAILABLE 或容量错误，普通读写仍可用。Scheduler/Worker 因当前职责把 RabbitMQ 视为硬依赖时可返回 503；各进程必须独立计算，禁止用一份全局依赖布尔值。

## 8. 安全与运维

RabbitMQ 使用独立 vhost、非默认账号和最小 configure/write/read 权限；凭据只从 secret 注入。部署网络限制管理端口，生产连接使用 TLS。消息和 last_error 在写日志/数据库前脱敏，不保存预签名 URL、token、密钥或完整正文。

必要指标：outbox_pending_total/oldest_age、publish_confirm_failures、queue_ready/unacked、consumer_inflight、handler_duration、redeliveries、retry_scheduled、manual_attention。labels 仅 queue、event_type、result，不使用 workspace/task ID。

内部运维查询按 event_id/task_id/causation_event_id 展示 Outbox/Inbox/Attempt 链。未确认发布重放保持原 event_id；已经成功消费的业务不能靠重发消息再次执行，确需新动作必须走业务命令生成新 event_id。所有运维重放仅限 operator 并写 AuditEvent，Workspace owner 只查看脱敏 Task 状态。RabbitMQ Management 仅用于基础设施诊断，不面向业务用户。

## 9. 测试与验收

- PostgreSQL：业务 + Outbox 原子性、SKIP LOCKED 多 Publisher、claim 超时回收、Inbox 唯一和清理窗口。
- RabbitMQ：durable topology、persistent message、confirm 超时、重复投递、ack 前后进程退出、连接恢复。
- Worker：未知 schema、毒消息、状态乱序、取消竞态、unknown 对账和重试上限。
- 资源：prefetch 不超过执行容量，媒体任务不挤占 API，积压超过门槛后提交降级。
- 安全：payload 大小/字段白名单、凭据和敏感数据不进入消息/错误/日志。

不声称 exactly-once；验收目标是在重复、乱序和故障下实现一次业务效果，事实可恢复且运维可解释。
