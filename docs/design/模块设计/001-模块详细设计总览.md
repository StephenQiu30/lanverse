# DES-MOD-001 模块详细设计总览

- 状态：proposed
- 日期：2026-07-27
- 输入：DES-000、REQ-001 至 REQ-013、DES-001 至 DES-004
- 输出：九个模块共同遵循的实现约束和需求追踪规则
- 下游：各模块详细设计、MVP PRD、API 契约和实施 Plan

## 1. 设计结论

Lanverse 采用领域模块化单体：FastAPI API、Scheduler 和 Worker 共用 Python 代码库，PostgreSQL 保存事实，Redis 仅做缓存，RabbitMQ 投递工作，MinIO/已选 OSS 保存私有媒体。先以单集纵向闭环验证边界，不拆微服务，不建立万能 CRUD、通用审批引擎或第二套任务系统。

每个模块只有四类必要代码职责：HTTP 输入输出、用例与事务、业务规则、持久化或外部适配。简单模块允许合并文件，只有规则复杂时才拆 domain、repository 或 provider；目录图不是必须预建的空壳。

## 2. 需求到设计的追踪

| 需求范围 | 设计落点 | 必须验证的系统性质 |
| --- | --- | --- |
| SYS-ENT、各模块 ENT | 聚合、字段、唯一约束、不可变和引用 | 事实只有一个所有者，版本不可覆盖 |
| SYS-FR、各模块 FR | 显式应用用例和业务命令 | 角色、状态、成功结果和失败结果可观察 |
| SYS-IF、各模块 IF | HTTP/OpenAPI 或模块公开 DTO | 前后端不重复状态机，跨模块不读内部表 |
| SYS-NFR、各模块 NFR | 事务、锁、幂等、恢复、观测和测试 | 故障下不丢事实、不重复副作用、不越权 |

详细设计覆盖整个对应需求前缀；PRD 只量化仍待确认的规模、性能、供应商、合规和交互指标，不重新发明业务边界。

## 3. 运行时与模块依赖

~~~mermaid
flowchart LR
    WEB["React 工作台"] --> API["FastAPI API"]
    API --> PG[(PostgreSQL)]
    API --> REDIS[(Redis Cache)]
    API --> STORE[(MinIO / OSS)]
    PG --> SCH["Scheduler / Outbox Publisher"] --> MQ["RabbitMQ"]
    MQ --> WRK["I/O 与媒体 Worker"]
    WRK --> EXT["模型供应商与 FFmpeg"]
    WRK --> PG
    WRK --> STORE
~~~

模块事实依赖保持 identity → projects → scripts/assets → storyboards → production → editing；media 和 governance 提供横向受控能力。后置模块通过公开查询或命令使用前置事实；不得导入其他模块的 SQLAlchemy Model、Repository 或内部异常。

## 4. 后端分层与调用规则

| 层 | 允许职责 | 禁止职责 |
| --- | --- | --- |
| Router/Controller | 鉴权入口、Pydantic 校验、调用一个用例、映射 HTTP | 事务、SQL、状态判断、供应商调用 |
| Application Service | 用例编排、权限、事务边界、跨模块公开调用、事件 | 返回 ORM 对象、实现 HTTP 细节、持久轮询 |
| Domain | 状态转换、不变量、值对象、确定性计算 | 依赖 FastAPI、SQLAlchemy、RabbitMQ 或 SDK |
| Repository/Adapter | 参数化读写、锁、MinIO/供应商/FFmpeg 适配 | 决定角色、业务状态或跨聚合流程 |

跨模块同步查询只用于同一请求内的轻量校验和快照；长操作一律创建 Task 与 Outbox。模块内可以共享 SQLAlchemy Session 以完成同库事务，模块间只能传稳定 ID、版本 ID 和明确 DTO。

每个 HTTP/Worker 顶层命令只开启一次 SQLAlchemy async session.begin；被调用模块接收同一 Session 并只 flush，不自行 commit。Repository 永不提交事务。这样候选决议与下游对象、Render 与 Task 等同库事实可以原子落库，同时避免嵌套事务和半提交。

### 4.1 前端的 MVVC 对应

前端不机械复制后端九个包。路由页面在 `frontend/src/app/pages/<feature>/` 下按用户可完成的业务场景组织，页面专属 ViewModel/Controller hook 与页面同目录；可复用业务组件进入 `frontend/src/components/<feature>/`。View 只组合 shadcn/ui + Radix UI 组件并渲染状态；ViewModel 使用 TanStack Query 调用生成的 OpenAPI client、解释服务端 next_action，并把命令结果写回查询缓存。Zustand 仅保存尚未提交的剧本/分镜/时间线草稿、当前选择和布局，不复制 Task、readiness、审核或费用状态。

页面事件处理器承担 Controller 语义：把用户意图转换为一个明确命令，携带 expected_revision/version 和 idempotency_key。它不拼 URL、不构造供应商参数、不在刷新后自行决定重试。无业务语义的通用 UI 基础件进入 `components/ui`；任务卡、镜头卡、资产选择器等业务组件进入所属 `components/<feature>`，且不得反向导入 `app` 中的页面。

### 4.2 中间件管道

FastAPI 中间件按固定顺序注册到 `backend/app/main.py`，处理每个 HTTP 请求的横切关注点。顺序决定处理语义——鉴权必须在租户解析之前，日志必须在所有业务逻辑外侧。

```text
Client Request
  ↓
1. CORSMiddleware          ← 浏览器预检和跨域头；允许 origin 来自环境变量白名单
  ↓
2. RequestIDMiddleware      ← 从 X-Request-ID header 读取或生成 UUIDv7，注入 contextvars
  ↓
3. TraceMiddleware          ← 校验/创建 W3C traceparent，创建 root span
  ↓
4. LoggingMiddleware        ← 记录 access log（路由模板 + status + duration_ms + error_code）
  ↓
5. OIDCAuthMiddleware       ← 验证 Authorization: Bearer <token>；未认证路由白名单跳过
  ↓
6. WorkspaceMiddleware      ← 从 X-Workspace-Id header 解析 workspace_id，校验 Membership
  ↓
7. FastAPI Router           ← 业务路由处理
  ↓
Exception Handler           ← 所有异常在此转为统一错误信封
  ↓
Client Response
```

| 中间件 | 源文件 | 失败行为 | S0 最小实现 |
| --- | --- | --- | --- |
| CORS | Starlette 内置 | 非白名单 origin 返回 400 | 环境变量 `CORS_ORIGINS` 配置 |
| Request ID | `core/logging.py` | 从不失败；非法 UUID 格式替换为新 UUID | 必须（所有日志依赖） |
| Trace | `core/observability.py` | 非法 traceparent 创建新 trace | 必须（trace 关联依赖） |
| Logging | `core/logging.py` | 从不失败；序列化异常降级到 stderr | 必须（审计依赖） |
| OIDC Auth | `core/auth.py` | 401 → `UNAUTHENTICATED` | S1 前返回 mock actor |
| Workspace | `core/auth.py` | 403 → `FORBIDDEN`；无 header 时对 S0 健康路由跳过 | S1 启用真实校验 |

**关键规则**：
- 中间件不访问数据库（避免每个请求额外连接）；鉴权令牌在 OIDC 层验证，Workspace 层只读缓存的 claims。
- ActorContext 由 OIDC + Workspace 中间件共同装配到 `contextvars`，Router 通过 `Depends(get_actor_context)` 获取。
- 健康检查路由 `/healthz` 和 `/readyz` 注册在中间件栈之外（Starlette Router 挂载），不触发鉴权和 Workspace 解析。

### 4.3 组合根与依赖注入

`backend/app/main.py` 是 FastAPI 的组合根，负责创建连接池、注册中间件、挂载模块 Router 和注册异常处理器。各模块只暴露 `router: APIRouter` 和 `init_module()`（如需），不自行创建连接或注册全局状态。

**依赖注入链**（FastAPI `Depends`）：

```text
get_settings()        → Settings (Pydantic Settings, 单例)
get_async_session()   → AsyncSession (每个请求一个会话)
get_actor_context()   → ActorContext (从 contextvars 读取)
get_current_user()    → UserAccount (依赖 actor_context)
get_current_workspace() → Workspace (依赖 actor_context)
```

| 依赖 | 提供者 | 生命周期 | 说明 |
| --- | --- | --- | --- |
| `Settings` | `core/config.py` | 应用单例 | 环境变量解析，使用 `lru_cache` 缓存 |
| `AsyncSession` | `core/database.py` | 请求 scoped | `async with session.begin()` 管理事务 |
| `ActorContext` | `core/auth.py` | 请求 scoped | 从 contextvars 读取，Router 层注入 |
| `RedisClient` | `integrations/redis.py` | 应用单例 | 连接池在 startup 事件创建 |
| `RabbitMQChannel` | `integrations/rabbitmq.py` | 应用单例 | Publisher 共享 channel；Worker 独立连接 |
| `ObjectStoragePort` | `integrations/minio.py` | 应用单例 | MinIO/OSS adapter 在 startup 选择 |

**main.py 组装顺序**：

1. 创建 FastAPI app
2. 加载 `Settings()`
3. 按 §4.2 顺序注册中间件
4. 注册全局 `exception_handler`（`core/errors.py`）
5. 注册 startup/shutdown 事件（创建/销毁连接池）
6. 挂载 `/healthz`、`/readyz`（Starlette Route，无鉴权）
7. 挂载 `core/logging.py` 的 observability router（`/metrics` 等）
8. 按依赖顺序挂载业务模块 Router（identity 先于 projects，assets 先于 storyboards 等）
9. 注册 OpenAPI schema（`openapi_url="/openapi.json"`）

**禁止模式**：
- 模块 `__init__.py` 中注册 Router、创建连接或启动后台任务
- 模块内创建自己的 SQLAlchemy engine/session factory
- 使用 `global` 或模块级可变单例传递状态
- 业务模块直接导入 `Settings` 之外的 core 具体实现（如直接调 Redis client 而非通过公开 port）

## 5. 统一接口契约

- HTTP 前缀为 /api/v1；资源查询返回资源本身，列表返回 items、page、page_size、total。
- 普通资源使用 GET、POST、PATCH；归档、恢复、重排、发布、选择、审核、取消等使用有业务名称的 POST 命令。
- 写命令携带期望状态、expected_revision 或 expected_version_id；冲突返回服务端最新引用，不静默覆盖。
- 会触发外部副作用或可安全重试的命令必须携带 idempotency_key；键的作用域由 Workspace、用例和业务目标共同组成。
- 长操作快速返回 Task。前端刷新后读取 Task 或聚合快照，不用本地计时器猜测真实状态。
- OpenAPI 是前端契约事实源，由 @umijs/openapi 从 URL 生成到 frontend/src/api；生成文件不得手改。

统一错误对象包含 code、summary、retryable、next_action、trace_id，可选 detail 和 fields。稳定错误至少覆盖 UNAUTHENTICATED、FORBIDDEN、NOT_FOUND、VALIDATION_FAILED、STATE_CONFLICT、VERSION_CONFLICT、QUOTA_INSUFFICIENT、IDEMPOTENCY_IN_PROGRESS、EXTERNAL_STATE_UNKNOWN、DEPENDENCY_UNAVAILABLE 和 INTERNAL_ERROR。跨 Workspace 资源按 NOT_FOUND 处理，避免资源探测。

### 5.1 成功响应信封

所有成功响应使用统一信封，不裸返业务对象。单个资源与列表使用不同顶层形状；命令和长操作返回稳定结构。

| 场景 | HTTP 状态 | 响应体 | 说明 |
| --- | --- | --- | --- |
| 查询单个资源 | 200 | `{ "data": <resource> }` | data 是模块公开 DTO，不含 ORM 内部字段 |
| 分页列表 | 200 | `{ "data": [<resource>, ...], "meta": { "page": int, "page_size": int, "total": int } }` | total 为当前筛选条件的总数；空列表返回 items: [] 和 total: 0 |
| 创建资源 | 201 | `{ "data": <resource> }` | 同时返回 Location header |
| 命令（无返回资源） | 200 | `{ "data": { "revision": int, ... } }` | 至少返回最新 revision 或版本引用 |
| 命令（长操作） | 202 | `{ "data": { "task_id": "<uuid>", "status": "queued", "next_action": "poll_task" } }` | 前端按 task_id 轮询 Task 状态 |
| 异步操作已幂等 | 200 | `{ "data": <existing_result> }` | 同键返回既存结果，与 201 区分 |

信封类型由 `backend/app/core/schemas.py` 提供 `ApiResponse[T]` 和 `PaginatedResponse[T]` 泛型 Pydantic Model；Router 只使用这些信封包装业务 DTO，不自行构造 dict。

### 5.2 全局异常处理

FastAPI 通过 `backend/app/core/errors.py` 注册全局 `exception_handler`，把所有已知和未知异常映射为统一错误信封。业务代码只抛 `ApiError` 或其子类，永不直接构造 JSONResponse。

```text
Request → Router → Service → Domain/Repository
                ↓ 异常
        exception_handler
                ↓
        { "error": { code, summary, retryable, next_action, trace_id, detail?, fields? } }
```

| 异常基类 | HTTP 状态 | 使用场景 |
| --- | --- | --- |
| `ApiError` | 由子类决定 | 所有业务异常的基类，定义 code/summary/retryable/next_action |
| `AuthenticationError` | 401 | 令牌缺失、无效或过期 |
| `AuthorizationError` | 403 | 角色能力不足（不暴露资源存在性） |
| `NotFoundError` | 404 | 资源不存在或跨 Workspace 访问 |
| `ValidationError` | 422 | 输入格式、字段或业务规则校验失败 |
| `StateConflictError` | 409 | 状态不允许当前操作 |
| `VersionConflictError` | 409 | expected_revision/expected_version_id 冲突 |
| `QuotaError` | 422 | 额度、预算或并发上限不足 |
| `IdempotencyInProgressError` | 409 | 同键命令正在处理 |
| `ExternalStateUnknownError` | 502 | 供应商状态未知（不视为 500） |
| `DependencyUnavailableError` | 503 | Redis、MQ、存储或外部服务不可用 |
| `InternalError` | 500 | 意外错误；detail 不暴露堆栈 |

`exception_handler` 同时处理 Pydantic `ValidationError`（请求体/参数校验失败）和 Starlette 标准异常，转换为 ApiError 格式。未捕获异常记录完整 traceback 后返回 `INTERNAL_ERROR`，仅对外显示稳定 summary。

**前端消费**：TanStack Query 的 `onError` 读取 `error.code` 和 `error.next_action`；401 触发重新登录，404/403 显示统一无权提示，409 读取服务端最新 revision 并提示用户刷新，503 显示降级横幅。

### 5.3 全局状态枚举目录

以下枚举是跨模块共享的基础设施，定义在 `backend/app/core/statusses.py`（或按职责拆入 `core/` 下对应模块）。业务模块只能导入，不能重复定义相同语义的枚举。

**任务与异步**

| 枚举 | 值 | 拥有模块 | 说明 |
| --- | --- | --- | --- |
| `TaskStatus` | `queued \| running \| waiting_provider \| succeeded \| failed \| cancelled \| unknown` | production | API/Worker/Scheduler 共享的任务生命周期 |
| `AttemptStatus` | `prepared \| submitting \| accepted \| polling \| succeeded \| failed \| cancelled \| unknown` | production | 单次外部调用的阶段 |
| `CancelStatus` | `none \| requested \| acknowledged \| completed` | production | 取消的异步传播状态 |
| `ProgressStage` | `preflight \| submitting \| waiting \| downloading \| registering \| done` | production | 前端展示的可验证阶段 |

**媒体与存储**

| 枚举 | 值 | 拥有模块 | 说明 |
| --- | --- | --- | --- |
| `UploadSessionStatus` | `pending \| completed \| expired \| failed` | media | 直传会话生命周期 |
| `MediaLocationStatus` | `verified \| active \| retiring \| retired \| quarantined` | media | 存储位置状态机 |
| `ProbeStatus` | `pending \| ready \| failed \| quarantined` | media | 媒体探测结果 |

**治理与审核**

| 枚举 | 值 | 拥有模块 | 说明 |
| --- | --- | --- | --- |
| `ReviewStatus` | `draft \| submitted \| approved \| changes_requested` | governance | 版本审核生命周期 |
| `IssueStatus` | `open \| resolved` | governance | 审核问题的开闭状态 |
| `DecisionType` | `approve \| request_changes \| revoke` | governance | 只追加的审核决定 |
| `ModerationStatus` | `pending \| passed \| flagged \| blocked \| unknown` | governance | 内容检查结果 |

**资产与就绪度**

| 枚举 | 值 | 拥有模块 | 说明 |
| --- | --- | --- | --- |
| `AssetKind` | `character \| location \| prop \| costume \| visual_style \| voice` | assets | 资产类型，不可变 |
| `ReadinessStatus` | `draft \| ready \| blocked` | assets/storyboards | 资产和镜头的就绪状态 |

**通用生命周期**

| 枚举 | 值 | 拥有模块 | 说明 |
| --- | --- | --- | --- |
| `ArchiveStatus` | `active \| archived` | identity | Workspace/Project/Episode 的归档状态 |
| `MembershipRole` | `owner \| editor \| viewer` | identity | 固定角色，P1 邀请完成后不增加新角色枚举 |
| `ScheduleKind` | `one_off \| interval \| cron` | 基础设施 | 调度类型 |
| `MisfirePolicy` | `skip \| run_once \| catch_up` | 基础设施 | 错过触发时的策略 |
| `ConsentStatus` | `active \| revoked \| expired` | governance | 授权生命周期 |

**前端枚举**：前端不重复定义这些枚举。OpenAPI 生成时将 Python 枚举转为 TypeScript union type，前端直接使用生成类型。需要展示中文标签时，使用 `frontend/src/lib/labels.ts` 集中维护单一映射表。

**规则**：新增状态枚举必须先更新本表（DES-MOD-001 §5.3），再实现。Status 字段统一使用 `varchar(32)` + `CheckConstraint`，不使用 PostgreSQL native enum（避免 ALTER TYPE 的运维成本）。

## 6. 数据与一致性规则

- 所有业务查询先限定 workspace_id，再解析资源；外键不能替代租户校验。
- 业务主键使用 UUIDv7，时间统一存储 UTC；对外不暴露可推断租户数据量的顺序 ID。
- 可变聚合使用 revision 做乐观并发；排序、最后 owner、当前版本切换等竞争路径使用事务和行锁。
- ScriptVersion、AssetVersion、ShotSpecVersion、MediaVersion、TimelineVersion 只追加；内容 hash 和创建快照写入后不可修改。
- Task、Attempt、Candidate、CostEntry、Decision、ModerationResult、Label、AuditEvent 等证据记录只追加或受控转态，不开放删除。
- 跨模块关系保存稳定 ID；同库可用外键保证存在性，但 ORM 不建立跨模块级联删除和双向对象图。
- JSONB 只用于已由 Pydantic 判别联合校验、需要整体快照的规格；可筛选、唯一、排序和引用字段保持关系化列。
- MVP 以 SQLAlchemy Model 为结构来源，仅对空库 create_all；初始化必须拒绝非空且结构不符的数据库。

逐表字段、约束、索引和分类软删除规则见 [数据库表与数据生命周期详细设计](./011-数据库表与数据生命周期详细设计.md)。模块文档中的实体是业务模型，DES-MOD-011 才是 SQLAlchemy/PostgreSQL 结构基线。

## 7. 事务、消息与外部副作用

创建异步工作时，在一个数据库事务内写业务请求、Task、费用预占和 Outbox。Publisher 使用持久消息与 confirm，成功后标记 Outbox；失败保留重放。消费者手动 ack，在数据库提交结果之后确认；重复消息根据 Task/Attempt 和幂等键读取既有事实。

消息 envelope 固定包含 event_id、event_type、schema_version、aggregate_id、workspace_id、occurred_at、trace_id 和类型化 payload。消费者按 schema_version 显式解析，未知版本拒绝并告警；不得把 ORM 对象或供应商原始响应直接序列化进消息。

供应商调用前持久化稳定 provider_request_key。若发送结果未知，Task 进入 unknown，先按 provider_request_key 查询或人工对账；禁止用新键盲目重发。数据库事务不包围网络调用，使用短事务分阶段推进状态。

RabbitMQ 只使用 lanverse.io 与 lanverse.media 两类队列。prefetch 不高于有界 ThreadPoolExecutor 的工作数；FFmpeg 使用独立子进程和更小并发，不占 FastAPI 请求线程。

Exchange、routing key、Outbox/Inbox、ack、重试和容量降级见 [消息队列详细设计](./012-消息队列详细设计.md)；Redis、MinIO/OSS 和持久调度见 [缓存、对象存储与任务调度详细设计](./014-缓存对象存储与任务调度详细设计.md)。

## 8. 删除、归档与隐私

硬删除只允许未引用、未产生费用、未审核的空草稿；检查结果返回 blockers 数组。已有历史的聚合归档，历史引用仍可读。对象存储字节只有在数据库确认无任何活跃引用、血缘、审核、交付或留存约束后进入清理任务。

日志只记录稳定 ID、状态、耗时和错误摘要，不记录令牌、供应商密钥、完整剧本、提示正文或授权证明。下载通过短期受控 URL，数据库和 API 不持久化公开 URL。

日志字段、trace 传播、Prometheus 指标、脱敏、告警和 exporter 降级见 [日志与可观测性详细设计](./013-日志与可观测性详细设计.md)。

## 9. 可观测与恢复

每个请求建立 trace_id；异步链路关联 workspace_id、task_id、attempt_id、provider_request_key、outbox_id 和 media_version_id。进度只表达可验证阶段，不伪造百分比。错误由服务端给出 retryable 与 next_action。

恢复顺序固定为：读取持久 Task → 检查 Attempt 与 Outbox → 对账外部状态 → 完成媒体/费用收敛 → 决定重试、人工处理或终态。客户端断线不会创建新请求，也不能把 unknown 当作 failed。

## 10. 测试与架构门禁

测试只进入 backend/tests 和 frontend/tests。后端分为 unit、integration、contract；关键链路再由端到端测试覆盖。核心规则实施时遵循 Red → Green → Refactor。

必须自动验证：模块导入方向、测试目录边界、Workspace 越权、版本不可变、唯一约束、乐观并发、删除阻塞、Outbox 重放、消息重复、未知发送对账、费用不变量、Redis 故障回源、MinIO/OSS 存储契约、Schedule 并发防重、FFmpeg 样片和 OpenAPI 客户端无漂移。数据库集成使用真实 PostgreSQL，不以 SQLite 替代锁和 JSONB 语义。

## 11. 最小纵向实施顺序

1. identity + projects：登录、个人空间、项目、单集和隔离。
2. scripts + media + assets + 最小 governance：输入、版本、授权、候选决议和资产准备。
3. storyboards：规格版本、重排、readiness 和影响预检。
4. production：单镜头预检、任务、恢复、候选和费用。
5. editing + governance：时间线、审核、渲染和交付清单。

每个切片在 Plan 中绑定需求编号、API、数据约束、失败用例和可执行测试；未被当前切片使用的目录、表和抽象不提前创建。
