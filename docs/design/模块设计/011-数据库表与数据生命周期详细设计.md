- 状态：部分 accepted（当前已实现表及租户约束增量；未来 S5 表与最终留存策略仍 proposed）

- 输出：PostgreSQL 表、字段、约束、索引、跨模块引用和删除策略

## 1. 设计结论

MVP 使用本机 PostgreSQL 18.4 数据库和一套 SQLAlchemy 2 async Metadata。表按模块前缀命名，不创建 PostgreSQL 多 schema，不让模块直接查询其他模块 Model。数据库负责类型、非空、唯一、外键和检查约束；应用层负责角色、状态机、跨聚合规则和阻塞清单。

从 2026-08-13 起，SQLAlchemy Metadata 继续作为模型设计和 Alembic autogenerate 输入，`backend/alembic/versions/` 的已审阅 revision 是部署升级事实源。部署前独立执行 upgrade；运行角色只核对 revision head。首次 baseline 固定当时已实现的 42 张业务表；自动生成结果必须人工补齐 `use_alter` 循环外键并通过 `alembic check`、空库 upgrade/downgrade 和旧库零差异接管测试。已有无 revision 数据库不得直接 stamp，必须先取得可恢复备份并验证表、列、类型、默认值、约束和索引无差异。

本文件的表目录描述 MVP 最终结构，不代表 S0 一次性建表。S0 最初只实现单 Metadata 和空库初始化；该历史路径已由 Alembic baseline 接管。从现在开始每个纵向切片只注册当前已接受且真实用到的 Model，并在同一 DEV 中增加可逆 revision，用 PostgreSQL 集成测试核对对应表、约束和索引。PT-DAT-003 从 S1 首个租户表开始累计证据，在 S6 汇总接受。

“软删除”使用已有业务生命周期表达：可恢复资源保存 status、archived_at、archived_by、archive_reason，默认查询排除 archived。不会给所有表继承 deleted_at；不可变版本和证据表禁止删除，空白且无引用草稿才允许硬删除。

## 2. 类型、命名与公共列

| 规则 | 设计 |
| --- | --- |
| 主键 | Python 3.11 应用统一通过 `uuid6.uuid7()` 生成 UUIDv7，PostgreSQL 类型 uuid；不手写位运算生成器，不使用可枚举自增业务 ID |
| 时间 | timestamptz，UTC；created_at 默认数据库当前时间，updated_at 仅可变表使用 |
| 状态 | varchar(32) + CheckConstraint；避免 PostgreSQL 原生 enum 带来的结构变更耦合 |
| 金额 | numeric(20,6) + char(3) currency；禁止 float，业务再限制非负和账本平衡 |
| 文本 | 名称 varchar(200)，短代码 varchar(100)，正文 text；长度上限仍由 Pydantic/PRD 约束 |
| JSONB | 仅保存已由 Pydantic extra=forbid 校验的不可变规格、快照或低频 metadata；不默认建 GIN |
| 租户 | 所有租户业务表带 workspace_id not null；查询先限定 workspace_id，再使用资源 id |
| 版本 | 聚合 revision 为 bigint 从 1 递增；内容版本使用父 ID + version_no 唯一和 content_hash |

可变聚合通常包含 id、workspace_id、created_at、updated_at、revision；追加证据通常只含 id、workspace_id、created_at。字段只按真实需要声明，不建立通用 BaseEntity ORM 继承层。

每个租户聚合根声明 unique(workspace_id,id)，子表使用 ForeignKeyConstraint(workspace_id,parent_id) 引用父表的(workspace_id,id)，从数据库层阻止“子记录 workspace_id 正确但 parent_id 指向其他空间”。全局 UserAccount、ModelCapability 及 Workspace 自身除外。

## 7. 外键、级联和并发

- 聚合根之间及跨模块外键统一 ON DELETE RESTRICT；ORM 不配置 delete cascade。
- 租户子表优先使用 workspace_id + parent_id 复合外键；单独的 parent_id 外键不足以证明租户一致性。
- 只有纯组成表可 ON DELETE CASCADE，且父级本身必须先通过硬删除规则，例如未发布 ScriptVersion 的 Scene/Dialogue。
- current_version_id 循环引用使用 DEFERRABLE INITIALLY DEFERRED，或在创建聚合后以第二条语句设置；事务提交时必须有效。
- 排序、最后 owner、版本号、当前指针和预算并发使用 SELECT FOR UPDATE 或比较 revision；不把全库事务提升为 SERIALIZABLE。
- 幂等唯一约束是最后防线；捕获冲突后按同一输入回读既有结果，不把 IntegrityError 直接暴露为 500。

当前实现中的追加证据也必须具有明确租户父级：`sbd_shot_transforms` 以 `episode_id + workspace_id` 复合引用 Episode；`sys_schedule_fires` 分别以 `schedule_id + workspace_id`、`task_id + workspace_id` 和 `outbox_event_id + workspace_id` 引用 Schedule、Task 与 OutboxEvent。服务层已校验不能替代这些数据库约束，任何跨 Workspace 拼接都必须在 PostgreSQL 事务内失败。

当前 Attempt 增量把 `prod_attempts` 作为已实现表纳入同一 Metadata：Attempt 以 `(task_id,workspace_id)` 复合引用 Task，CostEntry 的非空 attempt_id 以 `(attempt_id,workspace_id)` 复合引用 Attempt；真实 PostgreSQL 测试必须拒绝跨 Workspace Attempt、同 Task 重复 sequence 和重复 provider_request_key。该结构只接受当前 `prepared → failed` 路径，不代表 Provider 其余状态已经实现。

DEV-AIP-01 把 Provider 四类数据库事实纳入同一 Metadata：CredentialVersion 以 `(connection_id,workspace_id)` 引用 Connection；Binding 与 HealthCheck 以 `(credential_version_id,workspace_id,connection_id)` 同时固定租户和连接，不允许只替换其中一个 ID；Binding 另以 `(capability_id,config_version)` 固定已验收模型契约。部分唯一索引分别保证同 Connection 只有一个 current CredentialVersion、同 `(workspace_id,usage_type)` 只有一个 active Binding。数据库只保存 AES-256-GCM 的 nonce/ciphertext/auth_tag、部署 key_id 和独立 HMAC-SHA256 fingerprint；AAD 由应用固定 Workspace、Connection、CredentialVersion 和 version，主密钥/fingerprint key 只从部署 Secret 注入且默认缺失时 fail closed。

该表结构增量的真实 PostgreSQL 与恢复证据见[生成 Attempt 预持久化与无 Provider 失败收敛验收](../../acceptance/arrived/025-生成Attempt预持久化与无Provider失败收敛验收.md)。

Provider 表、AES-GCM AAD/篡改拒绝、随机明文 sentinel 扫描与真实 PostgreSQL 约束证据见 [Provider 数据与凭据安全底座验收](../../acceptance/arrived/027-Provider数据与凭据安全底座验收.md)。

## 8. 软删除、归档和清理矩阵

| 分类 | 适用表 | 默认查询 | 恢复/清理 |
| --- | --- | --- | --- |
| 可恢复业务软删除 | workspaces、projects、episodes、media_objects、script_sources、assets、shots、provider_connections | status=active 或 archived_at IS NULL；include_archived 需显式权限 | archive/restore 命令；保留稳定 ID 和历史版本 |
| 状态停用 | user_accounts、memberships、consents、capabilities、provider_bindings | 只允许符合状态的业务动作 | 通过专用恢复/续期流程，不清行 |
| 可变草稿 | timeline 草稿、空 Project/Episode/Asset/Shot/Source | 正常读取 | 无引用、无费用、无审核时可事务硬删 |
| 不可变版本 | 所有 Version、ProviderCredentialVersion、Lineage、Manifest | 始终按权限可追溯 | 禁止普通删除；受法定清理需独立审批设计 |
| 证据与账本 | Task/Attempt/Candidate/Decision/Audit/Cost/Review/ProviderHealthCheck | 可筛选但不可修改历史 | 用户不可删；仅按已确认留存政策受控清理 |
| 临时技术数据 | UploadSession 隔离对象、已发布 Outbox/Inbox、过期 ScheduleFire | 仅运维查询 | 满足过期、去重/运维窗口和无引用条件后批量硬清理 |

归档命令在同一事务中写状态、archived_at/by/reason 和 AuditEvent。恢复清空当前归档字段但不删除历史 AuditEvent。任何默认 Repository 查询都必须显式选择 active 或 include_archived，禁止全局魔法过滤器隐藏后台/审计查询。

## 9. 初始化、验证和未决项

SQLAlchemy Model/单一 Metadata 是已实现切片的结构设计与 autogenerate 输入，人工审阅的 Alembic revision 是部署升级事实源。`app.initialize_database` 独立执行 `upgrade head`；API、Scheduler 和 Worker 组合根在任何业务数据库操作前比较 database heads 与 script heads，过期或无 revision 时 fail closed，禁止 Web 启动自动改表。组合根必须显式导入当前已实现模块的 Model，禁止扫描未来模块或建立自动注册框架。`metadata.create_all()` 只保留在隔离测试 fixture；旧 `create_all` 数据库需先取得可恢复备份，再通过 Metadata 零差异校验后采用 baseline，任何未知表、缺列、缺约束或缺索引都拒绝 stamp。

验证至少覆盖：空库 upgrade/current/check/downgrade、旧库带数据接管、未知表/缺索引/缺外键拒绝、运行入口 revision fail-closed，以及 workspace_id 隔离、外键 RESTRICT、组成级联、部分唯一索引、归档/恢复、硬删除 blockers、版本不可变、Provider 密文篡改/AAD 互换/主密钥缺失、Outbox/Inbox 去重、MediaLocation 唯一/active 切换、Schedule/Fire 并发防重、金额精度和真实 PostgreSQL 锁。当前已实现表的租户引用可以持续形成 PT-DAT-003 增量证据，但 Provider owner/RBAC、Repository 只追加、并发 revision 与 Audit 原子性仍由 DEV-AIP-02～05 实现，不能从 DEV-AIP-01 的表结构外推；未来 S4/S5 表、金额账本与交付清单尚未实现时也不得提前接受 PT-DAT-003。Outbox/Inbox/ScheduleFire 与 Provider 健康证据的具体运维留存窗口未确认前，不得以任意默认天数接受 PT-DAT-002。正式接管仍需在团队自有旧库副本完成真实备份、恢复演练并保存操作证据；测试库接管通过不能外推为生产恢复已验收。
