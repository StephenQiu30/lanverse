- 状态：accepted（S2/S3；PT-AST-001～005 对应范围已完成验收）
- 覆盖需求：SYS-FR-003、SYS-ENT-003；AST-ENT-001 至 006、AST-FR-001 至 008、AST-IF-001 至 007、AST-NFR-001 至 007
- 输入：[资产模块需求](../../../requirement/arrived/007-资产模块需求.md)

## 1. 聚合与类型边界

assets 提供项目级稳定资产身份与不可变版本。共享流程仅覆盖创建身份、追加版本、当前指针、归档和查询；不同 kind 的业务字段由显式类型负责，不建立接受任意 JSON 的万能 Asset。

| 实体/组成 | 关键字段 | 不变量 |
| --- | --- | --- |
| Asset | id、workspace_id、project_id、kind、name、aliases、tags、status、current_version_id、revision | kind 创建后不可变；当前版本只由命令切换 |
| AssetVersion | id、asset_id、version_no、schema_version、spec、prompt_description、source_type/id、created_by、content_hash | 只追加；spec 先经对应判别模型校验 |
| MediaReference | asset_version_id、media_version_id、purpose、position | 引用固定媒体版本；purpose 受 kind 限制 |
| RightsEvidence | subject AssetVersion、usage、consent_ids、evaluated_at | 由 governance 实时派生，不在 assets 复制可撤销授权状态 |
| AssetReadiness | status、blocking_reasons、warnings、next_actions、dependency_snapshot | 派生 DTO，不持久化可编辑布尔值 |

支持 kind 固定为 character、location、prop、costume、visual_style、voice。数据库中的 spec 使用 JSONB 保存整体不可变快照，但写入只能来自以下 Pydantic 判别联合，extra=forbid：CharacterSpec、LocationSpec、PropSpec、CostumeSpec、StyleSpec、VoiceSpec。schema_version 只用于显式解析已存在版本，不允许静默接受未知字段。

## 2. 类型化规格

| 类型 | MVP 结构核心 | 专属校验 |
| --- | --- | --- |
| CharacterSpec | kind=`character`；identity、appearance、age_impression 可空字符串；temperament 列表 | ready 时四项完整；默认服装/声音引用留到 S3 显式 AssetVersion 引用，不塞入自由 JSON |
| LocationSpec | kind=`location`；spatial_description、time_weather、visual_elements、lighting | ready 时四项完整且 visual_elements 非空 |
| PropSpec | kind=`prop`；appearance、material、usage_context、holder_character_id | holder 可空，存在时属于同 Project 且 kind=character |
| CostumeSpec | kind=`costume`；appearance、material、usage_context、wearer_character_id | wearer 必须属于同 Project且 kind=character |
| StyleSpec | kind=`visual_style`；visual_language、palette、lighting_language、negative_constraints | 前三项完整；不要求直接媒体 slot |
| VoiceSpec | kind=`voice`；source_kind=`synthetic_recording|human_recording|voice_clone`、language、performance_traits、allowed_usage | 列表非空；真人/克隆仍执行同一授权门禁 |

写入模型允许字段缺失形成 draft，但字段存在时必须满足长度、枚举、UUID 和列表上限；`extra=forbid`。ready 的固定媒体门槛为 character/image `portrait`、location/image `environment`、prop/image `object`、costume/image `outfit`、voice/audio `voice_sample`；visual_style 的 image `style_reference` 可选。一个 purpose 可有多个 position，`asset_version_id + purpose + position` 唯一。

所有 ready 版本必须通过以当前 AssetVersion 为 subject 的 RightsGate。版本先创建为 draft，再由治理模块登记 Consent；readiness 返回匹配的 consent_ids，但 assets 不持久化 `ConsentReference`，从而避免授权撤销后出现第二份陈旧状态。

## 4. 追加版本事务

1. 读取并锁定 Asset，校验 active、Project active、expected_current_version_id 和 kind。
2. 用对应 Spec 模型校验并规范化，拒绝未知字段和跨类型引用。
3. 通过 media 公开契约批量解析 MediaVersionRef，校验 Workspace、对象状态、probe 状态、媒体 kind 和 purpose；不在版本创建事务中猜测未来授权。
4. 计算规范化 content_hash，写 AssetVersion 及关系化引用行。
5. 若请求 set_as_current，比较更新 Asset.current_version_id 与 revision；写审计并提交。首次版本允许 expected current 为 null，后续冲突返回最新指针。

版本号由锁定聚合后分配，asset_id + content_hash 可用于提示内容重复，但不自动合并用户有意创建的版本。外部媒体或授权校验在短事务前完成，事务内再次核对稳定 ID 和关键状态，避免检查后失效。

## 5. 准备度和引用升级

readiness 顺序为：Asset/Version 可用 → kind 必填字段 → 关系化类型引用 → 固定媒体 ready → RightsGate 对 AssetVersion 与目标 usage 有效。缺少用户可补充的字段/媒体时为 draft；媒体失败/隔离、归档、授权缺失/撤销/过期或依赖 unavailable 时为 blocked；全部满足才为 ready。blocker 包含 code、field_path、dependency_type/id、summary、next_action；dependency_snapshot 固定返回已评估 AssetVersion、MediaVersion、Consent ID 和时间。`review_asset_consent` 下一动作必须交接该固定 AssetVersion 及可用的证明 MediaVersion，由 governance 预填后重新校验并登记；授权建立或撤销后重新读取 readiness 即得到新结果，不修改 AssetVersion。相同版本与依赖状态得到相同结果。

反向使用由 storyboards 的公开查询按 asset_version_id 分页返回，不建立双方都写的 AssetUsage 表。升级预检确认新旧版本同 Asset、新版本 ready、目标 Shot current Spec、类型兼容、授权、下游影响和预计 input_hash；返回每个目标的 expected_spec_version_id 与整批 preflight_hash。实际升级由 storyboards 在一个事务锁定全部目标 Shot，任一 expected Spec/preflight hash 变化则整批零写入；成功时每个 Shot 只创建一个新 ShotSpecVersion。Asset.current_version_id 切换永不触发批量升级。

## 6. 生命周期、持久化与失败

Asset 为 active ↔ archived。归档后禁止新 ShotSpec 引用和新版本，但已存在 AssetVersion 仍可用于历史重现与交付追踪。只有没有任何 AssetVersion、媒体/授权和候选决议关联的空 Asset 可硬删；AssetVersion 不提供 DELETE。

Asset 删除预检同时读取自身不可变版本数、Prop/Costume 历史版本中的 `holder_character_id`/`wearer_character_id` 引用数，以及 scripts 的候选决议引用数，分别返回 `asset_has_versions`、`asset_has_related_versions` 和 `asset_has_candidate_decisions`，并以 `version_count`/`related_version_count`/`decision_count` 提供稳定结构化事实。关联版本计数直接查询不可变 JSONB 快照，active/archived 持有方与非 current 历史版本均不能遗漏。assets 定义 `AssetCandidateDecisionCountReader`，API 组合层注入 scripts 公共批量查询；assets 不读取 CandidateDecision ORM。

所有既有 Asset 写命令统一按 Project → Asset 重读并加锁，锁定重读必须强制刷新 SQLAlchemy identity map，保持 append/current CAS 单 winner。追加 Prop/Costume 版本在锁定所属 Project 与自身 Asset 后，再锁被引用 Character；Asset DELETE 使用同一 Project → 目标 Asset 顺序并在锁内复查三类 blocker。scripts 的 `link_existing` 只锁目标 Asset 后追加决议且不再申请 Project 锁，所以不会形成反向等待。并发只允许“追加引用版本 201/删除 409”或“删除 200/追加 422”，以及“候选关联 201/删除 409”或“删除 200/候选关联 404”；任何 winner 都不会产生悬空 UUID/downstream_id。有自身版本、候选决议或被道具/服装历史版本引用时界面只允许归档。

assets 对 projects 公开 Project 维度的批量删除影响摘要，统计 active/archived Asset 和所有 AssetVersion，不因 current 为空或资产已归档而遗漏历史。Project 预检逐项展示身份数和版本数，实际 DELETE 持有 Project 行锁后重新读取；Asset 创建使用同一 Project 锁，保证并发创建/删除只产生可解释且无孤立事实的结果。该项目级摘要不改变 Asset 自身“有版本只能归档”的规则。

唯一约束覆盖 asset_versions(asset_id, version_no) 和 media_refs(asset_version_id, purpose, position)。assets(project_id, kind, normalized_name) 只建立查询索引并用于重复提示；名称允许业务确认的同名，故不以数据库唯一约束阻止创建。

跨类型/跨空间引用返回 VALIDATION_FAILED 或 NOT_FOUND；依赖失效返回 readiness blocked，不修改版本；current 指针冲突返回 VERSION_CONFLICT 与最新版本；批量升级存在一个冲突时默认不执行。

## 7. 测试设计

- 单元：六类 Spec 的必填/未知字段、kind 不可变、readiness 证据、版本不可变。
- PostgreSQL 集成：并发追加版本与切换、候选决议幂等、无版本但有决议时删除阻塞，以及 link/delete 双向 winner 无悬空事实。
- 模块契约：媒体/授权类型与租户校验、反向使用只读、升级预检不产生写入。
- 端到端：剧本候选 → 资产版本 → ShotSpec 固定引用 → 新版本切换后旧镜头不漂移。

公共素材市场、LoRA 训练、跨 Workspace 共享、无限资产树和自动身份合并不进入 MVP。
