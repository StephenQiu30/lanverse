# DES-MOD-006 剧本模块详细设计

- 状态：proposed
- 覆盖需求：SYS-FR-002、SYS-ENT-003；SCR-ENT-001 至 006、SCR-FR-001 至 009、SCR-IF-001 至 007、SCR-NFR-001 至 007
- 输入：[剧本模块需求](../../requirement/006-剧本模块需求.md)

## 1. 聚合边界

scripts 把原始输入变成不可变的单集剧本版本，并保存 AI 提取候选和人工决议证据。Asset 和 Shot 由下游模块拥有；scripts 只通过公开命令创建或关联它们。

| 聚合/实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| ScriptSource | id、workspace_id、episode_id、input_type、title、source_media_version_id、rights_declaration、status | 归属一个 Episode；原始来源可追溯 |
| ScriptVersion | id、source_id、version_no、body、content_hash、created_by、created_at | source + version_no 唯一；发布后不可变 |
| Scene | id、script_version_id、position、heading、location、time_of_day、summary、source_range | ID 仅在本版本稳定；position 唯一连续 |
| Dialogue | id、scene_id、position、speaker_candidate、kind、text、performance_note、source_range | 允许未解析 speaker；正文不可变 |
| ExtractionBatch | id、script_version_id、scope、extractor_snapshot、task_id、status、confirmed_script_version_id、idempotency_key | 固定输入；执行状态跟随 Task；确认结果指向新版本 |
| ExtractionCandidate | id、batch_id、kind、source_range、proposal、confidence_note、status、revision | proposal 为按类型校验的判别联合 |
| CandidateDecision | candidate_id、sequence、action、payload、downstream_type/id、actor、created_at | 只追加；相同决议键返回同一结果 |

Scene/Dialogue 是 ScriptVersion 内的组成实体，保留关系化顺序和文本位置，便于差异、定位和引用；不分别开放任意 CRUD。

## 2. 剧本版本用例

| 用例 | HTTP 形态 | 关键规则 | 需求 |
| --- | --- | --- | --- |
| create_source | POST /api/v1/episodes/{id}/script-sources | 文本或 MediaVersion、权利声明、Episode active | SCR-FR-001、IF-001 |
| publish_version | POST /api/v1/script-sources/{id}/versions | 完整正文、expected_current_version_id | SCR-FR-002/003、IF-002 |
| list/get/diff_versions | GET /api/v1/script-sources/{id}/versions 等 | 历史只读；差异是派生结果 | SCR-FR-002 |
| set_current_version | POST /api/v1/episodes/{id}/current-script-version | 固定版本与期望旧 ID | SCR-FR-002、IF-003 |
| start_extraction | POST /api/v1/script-versions/{id}/extractions | 固定输入与幂等键，快速返回 Batch/Task | SCR-FR-004、IF-004/005 |
| get_extraction | GET /api/v1/extraction-batches/{id}、/api/v1/extraction-batches/{id}/candidates | 批次状态、分页候选和 next_actions | SCR-IF-005 |
| decide_candidate | POST /api/v1/extraction-candidates/{id}/decisions | 类型化人工决议与下游结果 | SCR-FR-005/008、IF-006 |
| confirm_structure | POST /api/v1/extraction-batches/{id}/confirm-structure | 由已决议 Scene/Dialogue 产生新 ScriptVersion | SCR-FR-005/007、IF-006 |
| check_continuity | GET /api/v1/script-versions/{id}/continuity | 证据位置与建议，不修改正文 | SCR-FR-006、IF-007 |
| delete_draft_version | DELETE /api/v1/script-versions/{id} | 仅未引用、未提取的明确草稿 | SCR-FR-009 |

publish_version 在事务前完成大小与结构校验，在事务中锁定 Source、比较期望版本、写 Version/Scene/Dialogue 并更新项目模块的当前版本引用。结构化内容可以由用户输入或已确认提取结果产生，但一经发布整体不可变。

MVP 不持久化第二套自动保存草稿；编辑器本地草稿发布时创建新版本。若 PRD 需要跨设备草稿，再为真实用例增加 ScriptDraft，而不是让 ScriptVersion 可变。

## 3. 提取任务

start_extraction 对固定 ScriptVersion、scope、extractor_version 和 idempotency_key 创建 ExtractionBatch，并通过 production 的内部 Task 命令创建 task_type=script_extraction；同事务写 Task 和 Outbox，接口快速返回 Batch/Task。

Worker 读取不可变文本快照，通过 `langchain-deepseek==1.1.0` 的 `ChatDeepSeek` 调用官方 `deepseek-v4-pro` 非思考模式，并以 `ScriptExtractionResult` 执行结构化输出。系统提示固定 JSON schema、候选类型、source_range 和“只提取、不改写正文”规则；结果再次通过 Pydantic 判别联合、候选引用和正文边界校验。原始供应商响应不进入业务表、消息或普通日志；无效结果记录结构化错误，不伪造候选或已确认事实。

提取器快照固定模型 ID、thinking 模式、`langchain-deepseek` 版本、prompt 版本和 schema 版本；相同 Batch 永不因依赖升级漂移。`DEEPSEEK_API_KEY` 是唯一新增 secret，Base URL 与模型不接受前端或任意环境覆盖。网络结果不明或 Worker 在外部响应落库前中断时不得自动再次付费调用，Task/Batch 进入 unknown 或明确阻断，由用户创建新 Batch；重复 RabbitMQ 投递只读取既有执行事实。

Batch 状态 queued → running → succeeded/failed/cancelled/unknown，由 Task 投影更新。重试产生新 Attempt；重新提取使用新 Batch，不覆盖旧候选和决议。

Scene/Dialogue 候选先在 Batch 内完成 accept、edit 或 ignore；confirm_structure 锁定 Batch，要求这两类必需候选均已决议，以原正文和决议结果创建新的不可变 ScriptVersion/Scene/Dialogue，并记录 confirmed_script_version_id。这样 AI 结构不会原地写进被提取版本，Shot 的 source_scene_id 也能引用真正稳定的新版本实体。

## 4. 候选决议

支持 accept_new、link_existing、merge_into、accept_with_changes、ignore。每个命令携带 candidate_id、expected_revision、decision_key 和类型化 payload。Scene/Dialogue 决议只形成待确认结构；Asset/Shot 决议要求 Batch 已有 confirmed_script_version_id，再在共享数据库事务中调用 assets 或 storyboards 的公开创建/关联命令，追加 CandidateDecision，更新候选状态并提交。

唯一约束 candidate_id + decision_key 防止重复创建。相同命令返回既有 downstream ID；改变已完成决议必须走 revise-decision 命令，先查询下游 blockers 和影响，不允许 PATCH status。批量决议默认全有或全无；逐项模式只有 PRD 明确需要时再增加。

必需候选全部离开 pending、存在 confirmed_script_version_id 且没有未处理的 blocking continuity issue 时，结构确认查询才返回 completed。连续性问题包含 source_range、规则/模型依据和严重度，只作提示，不自动修改正文。

## 5. 当前版本切换与影响

切换前校验版本属于同一 Episode，通过 projects 的比较更新命令改变 current_script_version_id。切换后调用 storyboards 的影响查询返回仍引用旧 ScriptVersion 的 Shot；不自动重建 Scene ID、不改 ShotSpec、不撤销已发生的任务或费用。

删除检查通过 storyboards、ExtractionBatch 和当前指针的公开 blocker 查询。已被引用的 ScriptVersion 永不硬删；ScriptSource 归档仍允许读取历史。

## 6. 持久化与安全

约束覆盖 script_sources(episode_id, id)、script_versions(source_id, version_no)、scenes(script_version_id, position)、dialogues(scene_id, position)、extraction_batches(script_version_id, idempotency_key)。content_hash 对规范化正文计算；source_range 使用字符偏移并校验边界。

正文、导入文件和提示不进入普通日志或跨租户缓存。文件导入先经 media 校验，再在 Worker 中解析；API 不同步处理大文件和模型调用。

## 7. 失败与测试

解析失败保留 Source/Version；未配置 DeepSeek、供应商明确拒绝或结构校验失败保留 Batch 与 TaskError；限流/服务故障按结构化错误给出安全重试动作，网络结果不明进入 unknown 且不盲重发；候选下游冲突回滚整个决议事务并返回 next_action；版本并发返回最新 current_version_id。

- 单元：版本不可变、source_range、候选类型、决议状态机、结构完成判定。
- PostgreSQL 集成：并发 publish 版本号、批量决议原子性、重复 decision_key、引用删除阻塞。
- Worker：无效 AI 输出、重复消息、unknown 恢复不覆盖人工决议。
- 端到端：导入 → 发布 → 提取 → 确认结构版本 → 人工决议 → 资产/Shot 创建及完整追踪。

实时协作文档、自动改写已确认剧本、通用知识图谱和无人工门禁的一键提取不进入 MVP。
