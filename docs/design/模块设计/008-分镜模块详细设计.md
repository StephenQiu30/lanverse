## 1. 聚合、来源与模块边界

storyboards 拥有 Episode 内 Shot 身份、顺序、不可变规格版本、固定资产引用、变换证据和 readiness。scripts 只提供已确认的 ScriptVersion/Scene/Dialogue 与 `kind=shot` Candidate 引用；assets/media/governance 提供固定版本和当前门禁；production/editing 只消费快照并拥有候选、任务、媒体、费用、审核和时间线事实。任何交接都走公开 contract，不跨模块导入 ORM Model。

| 实体/读模型 | 关键字段 | 不变量 |
| --- | --- | --- |
| Shot | id、workspace_id、episode_id、position、title、source_script_version_id、source_scene_id、source_candidate_id、creation_key、status、current_spec_version_id、revision | active Shot 的 position 连续唯一；结构来源必须来自同 Episode 的 confirmed ScriptVersion；`source_candidate_id` 仅允许 `kind=shot` |
| ShotSpecVersion | id、workspace_id、shot_id、version_no、schema_version、spec、content_hash、input_hash、created_by、created_at | 完整规格只追加；固定 Script/Scene/Dialogue 与资产引用随版本保存 |
| AssetReference | shot_spec_version_id、slot_key、role、asset_version_id、subject_key | slot_key 在规格内唯一；role 与 Asset kind 匹配；不读取 current AssetVersion 猜测 |
| ShotTransform | operation、source_shot_ids、source_spec_version_ids、result_shot_ids、impact_hash、idempotency_key、actor_id、created_at | copy/split/merge 一次业务效果一条只追加证据；来源和结果均不可重写 |
| Readiness | status、ready、blocking_reasons、warnings、next_actions、evaluated_dependencies、evaluation_hash | `ready = (status == ready)`；确定性派生，不持久化可编辑状态 |

结构化创建只接受 Batch 已确认后的 `kind=shot` Candidate。scripts 把 Candidate 的 `scene_candidate_key` 解析为 confirmed ScriptVersion 中稳定的 Scene ID，再调用 `create_from_confirmed_candidate`；唯一 `(workspace_id, source_candidate_id)` 保证重复决议只得一个 Shot。手工创建使用 `(workspace_id, creation_key)` 幂等；一个 Scene 可通过不同 creation_key 创建多个镜头。未确认候选、Scene/Dialogue 候选和跨 Episode 来源全部拒绝。

## 2. ShotSpec v1

`spec` 是 `extra=forbid` 的 Pydantic 判别模型并以 JSONB 保存；API 不接受自由 JSON、供应商模型名、供应商参数或费用字段。v1 固定结构如下：

| 字段 | 类型与约束 | 语义 |
| --- | --- | --- |
| script_reference | confirmed_script_version_id、scene_id、0～8 个 dialogue_id | 均由 scripts 公开 contract 验证为同一已确认版本和 Scene |
| narrative | purpose 1～500 字、可选 continuity_note 0～500 字 | 镜头叙事目标，不复制整段剧本文本 |
| visual | shot_size、camera_angle、camera_movement、composition、environment、subject_placements、mood_lighting | 枚举与受限文本；至少 composition/environment/mood_lighting 非空 |
| action_beats | 1～8 个 `{beat_key, order, description}` | beat_key 在规格内唯一，order 从 1 连续 |
| dialogue_or_narration | 0～8 个 `{source_dialogue_id, beat_key, speaker_subject_key, render_as_audio, performance_note}` | source_dialogue_id 必须在 script_reference；有声项必须可解析 voice slot |
| duration_ms | 500～15,000，默认草稿值 3,000 | 大于 8,000 产生 warning，不绕过硬范围 |
| audio_intent | 可选 ambient、0～8 个 sound_effect | 只描述意图，不引用生成结果 |
| generation_intent | mode、可选 first_frame/last_frame/keyframe_notes | mode 仅为 keyframe_then_video/reference_to_video/text_to_video |

Shot size 固定为 `extreme_wide/wide/full/medium/medium_close_up/close_up/extreme_close_up`；机位固定为 `eye_level/high/low/bird_eye/dutch`；运镜固定为 `static/pan/tilt/dolly/truck/pedestal/zoom/handheld/orbit`。扩展枚举必须升级 schema_version，不得让前端夹带未知字符串。

AssetReference role 固定为 `location/character/prop/costume/visual_style/voice`。一个可保存的 blocked 草稿可以缺少资产；ready 时必须恰有一个 location，subject_placements 引用的主体必须有 character slot，有声 dialogue/narration 的 speaker_subject_key 必须有 voice slot，所有引用必须属于同 Workspace/Project 且 AssetVersion 未归档。slot_key 和 subject_key 是规格内稳定键，不使用展示名称关联。

`content_hash` 由规范化 spec 与按 slot_key 排序的 AssetReference 计算；`input_hash` 再加入 schema_version、confirmed ScriptVersion/Scene/Dialogue ID。production 只接收固定 ShotSpecVersion、input_hash 和 evaluation_hash，不从当前指针重新拼装输入。

## 3. HTTP 与公开 contract

| 用例 | HTTP 形态 | 输入/输出关键规则 | 需求 |
| --- | --- | --- | --- |
| create/list/get/update_shot | `/api/v1/episodes/{id}/shots`、`/api/v1/shots/{id}` | editor/owner 写；PATCH 仅 title；active 列表返回 order_hash | SBD-FR-001/002、IF-001 |
| archive/restore/delete | GET `/api/v1/episodes/{id}/archived-shots`、`/archive`、`/restore`、`/delete-preflight`、DELETE Shot | 归档列表按更新时间稳定排序；archive/restore 原子重编号；仅无 Spec/变换/下游证据的空 Shot 可删 | SBD-FR-009、IF-001 |
| save_spec_version | POST `/api/v1/shots/{id}/spec-versions` | 完整 spec/references、expected_current_spec_version_id；返回新版本与 readiness | SBD-FR-003、IF-002 |
| list/get/set_current_spec | 版本查询、POST `/api/v1/shots/{id}/current-spec-version` | 历史只读；expected old ID；跨 Shot 版本拒绝 | SBD-FR-003、IF-003 |
| reorder_shots | POST `/api/v1/episodes/{id}/shots/reorder` | 完整 active Shot ID 列表、expected_order_hash；返回新 order_hash | SBD-FR-004、IF-004 |
| copy_shot | POST `/api/v1/shots/{id}/copy` | expected spec/order hash、idempotency_key；来源保持 active | SBD-FR-005、IF-005 |
| split/merge preflight | POST `/api/v1/shots/{id}/split-preflight`、`/api/v1/shots/merge-preflight` | 返回固定 source specs、下游影响摘要和 impact_hash；无写副作用 | SBD-FR-005、IF-005 |
| split/merge apply | POST `/api/v1/shots/{id}/split`、`/api/v1/shots/merge` | 完整目标 Spec、expected source specs/order hash、impact_hash、idempotency_key | SBD-FR-005、IF-005 |
| get_readiness | GET `/api/v1/shots/{id}/readiness`、Episode 批量查询 | status/blockers/warnings/next_actions/evaluated_dependencies/evaluation_hash | SBD-FR-007/008、IF-006 |
| asset usage/upgrade | AssetVersion usage 查询、preflight/apply | 新旧版本同 Asset；expected specs；默认整批原子 | SBD-FR-006/010、IF-007 |

storyboards 对 scripts 暴露 `create_from_confirmed_candidate`；对 assets 暴露 usage、upgrade preflight/apply；对 production 暴露 `ShotSpecRef` 与 readiness snapshot；对 projects 暴露 Episode 分镜摘要和受影响 Shot ID。公开 DTO 使用 dataclass/Pydantic，不返回 SQLAlchemy 对象。

## 4. 保存、切换与顺序并发

保存规格前验证 Episode/Shot active、expected 当前版本、confirmed Script/Scene/Dialogue 范围、AssetVersion 类型/范围和 v1 结构。授权失效或可选资产缺失允许把编辑结果保存为 blocked 版本，但响应必须给出 readiness；生产预检不能绕过 blocker。事务锁定 Shot，计算 version_no/hash，写 ShotSpecVersion/AssetReference，比较更新 current_spec_version_id 和 Shot revision。失败不写版本、不改变 current。

Shot 列表返回 `order_hash = sha256(canonical_json(ordered_active_shot_ids))`。创建、归档、恢复、copy、split、merge 和重排都锁定 Episode 的 active Shot 集合，比较 expected_order_hash，使用临时负 position 避开唯一约束，再写 1..N 连续 position。完整 ID 集合校验防增删漂移，order_hash 防同集合陈旧顺序覆盖；冲突返回 `version_conflict`、最新 order_hash 和服务端顺序。单集 active Shot 硬上限 120，任何会超限的事务整体 `state_conflict`。

归档 Shot 不参与 active 顺序或 `order_hash`，但必须能在刷新后按 Episode 查询并恢复。归档列表只返回生命周期事实，按 `updated_at DESC, id DESC` 稳定排序；恢复仍提交当前 active `expected_order_hash`，成功后插入 active 列表末尾。

## 5. copy、split 与 merge

- copy：要求来源有 current Spec；在来源后创建一个 Shot 和 Spec v1，复制规范化 spec/AssetReference，保留稳定 Script 来源；不复制 Candidate、Media、Task、Cost、Review、Timeline 或 selected 状态，来源不归档。
- split：preflight 固定一个 active 来源 Shot/current Spec 和下游影响。apply 接收两个完整目标 Spec；两个 Spec 的 ScriptVersion/Scene 必须与来源一致，引用 Dialogue 必须是来源集合子集且不能同时分配到两边，两个 duration_ms 之和必须等于来源时长。成功在来源位置创建两个 Shot、归档来源并连续重排。
- merge：preflight 仅接受同 Episode、相邻、active 且各有 current Spec 的两个 Shot。apply 接收一个完整目标 Spec；若来源 ScriptVersion 不同则拒绝，目标 Scene/Dialogue/AssetReference 必须显式给出且通过完整校验，duration_ms 等于两来源之和并仍满足 15,000 ms 上限。成功在较小 position 创建一个 Shot、归档两来源并连续重排。

preflight 的 impact snapshot 至少包含 source Shot/Spec/revision、GenerationRequest/Candidate/selected Media、Review/Issue、TimelineSource 的稳定 ID 与计数。apply 必须提交完全匹配的 impact_hash；变化返回 `version_conflict` 并要求重新预检。确认表示用户理解新 Shot 不继承旧证据，不会删除或迁移原历史。每个成功变换与顺序更新同事务写 ShotTransform；相同 idempotency_key + 相同 input hash 回读原结果，不同输入返回 `resource_conflict`。

## 6. Readiness 与警告

计算顺序固定，blocker code 固定如下：

1. `CURRENT_SPEC_MISSING`、`SPEC_FIELD_MISSING`、`DURATION_OUT_OF_RANGE`。
2. `SCRIPT_VERSION_UNAVAILABLE`、`SOURCE_SCENE_INVALID`、`SOURCE_DIALOGUE_INVALID`。
3. `LOCATION_REFERENCE_MISSING`、`CHARACTER_REFERENCE_MISSING`、`VOICE_REFERENCE_MISSING`、`ASSET_KIND_MISMATCH`。
4. `ASSET_VERSION_UNAVAILABLE`、`ASSET_NOT_READY`、`MEDIA_REFERENCE_UNAVAILABLE`、`RIGHTS_BLOCKED`。
5. 任一 scripts/assets/media/governance 公开依赖调用失败时返回 status=`unavailable`、`DEPENDENCY_UNAVAILABLE`，禁止生产。

warning code 仅允许 `DURATION_ABOVE_RECOMMENDED`（>8,000 ms）、`ACTION_DENSITY_HIGH`（>4 beats 或 >1 beat/s）和 `STYLE_REFERENCE_MISSING`。S3 只返回 warning；production 提交时必须按当前 evaluation_hash 保存 acknowledged_warning_codes，依赖变化后旧确认失效。模型能力、供应商参数、预算和额度属于 S4 production preflight，不混入 S3 readiness。

Episode 批量 readiness 先批量取得 Script 引用、AssetVersion/readiness、MediaVersion 和 RightsGate 所需 ID，再按内存映射逐 Shot 评估；禁止循环调用单 Shot service。目标 36 Shot 的 SQL 语句和模块 contract 调用数必须为常数阶，测试记录查询上限；按 PLAN-000 §7.5.1 固定环境验证 36 Shot ≤800 ms、120 Shot ≤2 s。

## 7. 资产升级、影响与删除

AssetVersion usage 由 storyboards 按关系化 AssetReference 分页返回。升级 preflight 要求新旧版本属于同 Asset、新版本 ready，固定每个目标 Shot 的 current Spec/revision、授权变化、下游证据和预计 input_hash。apply 锁定全部目标 Shot；任一 expected spec 或 preflight hash 冲突则整批零写入。成功为每个 Shot 创建且只创建一个新 SpecVersion，不修改旧引用、任务或时间线。

ScriptVersion current 切换、Asset current 切换、AssetVersion 归档或授权撤销只使影响/readiness 查询变化，不自动修改 Shot 或 current Spec。Shot active ↔ archived；restore 默认插入末尾并受 120 上限约束。仅没有 Spec、ShotTransform 和 production/governance/editing 公开 blocker 的空手工 Shot 可硬删；结构候选创建的 Shot 至少保留来源证据，因此只能归档。

## 8. 持久化、错误与验证

数据库约束至少包含：active `(episode_id, position)` 部分唯一、`(workspace_id, creation_key)`、非空 source_candidate 的 `(workspace_id, source_candidate_id)` 部分唯一、`(shot_id, version_no)`、`(shot_spec_version_id, slot_key)`、`(workspace_id, idempotency_key)` ShotTransform 唯一。索引覆盖 source_script_version_id/source_scene_id/source_candidate_id、asset_version_id、input_hash 和 transform source/result 查询。

跨空间资源统一 `not_found`；类型/范围/完整集合错误为 `validation_failed`；current spec/order/impact 变化为 `version_conflict` 并返回最新事实；同幂等键异输入为 `resource_conflict`；状态/上限不允许为 `state_conflict`。所有错误携带稳定 next_action 和字段级 details，不返回正文、URL、供应商响应或内部路径。

- 单元：ShotSpec v1 判别模型、枚举/extra 拒绝、hash 稳定性、readiness code、copy/split/merge 纯规则。
- PostgreSQL 集成：并发创建/保存、order_hash 冲突、连续位置、硬上限、变换/升级原子性、幂等、历史和删除 blocker。
- 模块契约：confirmed Candidate/Scene、Asset/Media/RightsGate 批量读取、依赖 unavailable、production snapshot 无供应商参数。
- 性能：12/36/120 Shot fixture 的查询计数与 PLAN-000 §7.5.1 固定环境 P95。
- 端到端：确认结构 → 候选/手工 Shot → Spec → 重排/变换 → readiness → 资产升级影响；刷新和服务重启后结果只由服务端事实恢复。

无限画布、逐子项全套 CRUD、自动不可审阅拆镜、供应商参数编辑器、专业动画曲线和生成事实回填不进入 MVP。
