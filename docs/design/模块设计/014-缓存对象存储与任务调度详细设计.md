## 1. 设计结论

Redis 使用 cache-aside，只保存有限 TTL、可从 PostgreSQL 重建的副本和限流计数。开发/MVP 对象存储使用 MinIO；生产如选阿里云 OSS，在同一 ObjectStoragePort 后使用独立适配器。任务调度以 PostgreSQL Schedule/ScheduleFire 为事实，由独立 Scheduler 运行角色生成 Task + Outbox；RabbitMQ 只通知到期工作。

不引入 Redis 队列、Celery Beat、RabbitMQ 延迟插件、APScheduler 持久 JobStore 或 Temporal。这些方案会与现有 Task/Outbox 再建第二事实或额外运维边界。

当前已落地的首个 Schedule handler 为 `expire_upload_session`：媒体上传初始化与 Schedule 同事务，成功完成上传时同事务结束该计划；未完成且到期时，dispatcher 用数据库 lease 和唯一 Fire 创建 `upload_expiration` Task + Outbox，Media Worker 删除临时 MinIO 对象并把 UploadSession 收敛为 expired。立即触发若早于真实 UploadSession.expires_at 只安全完成检查，不提前删除；暂停只阻止新的计划触发。

第二个真实 handler 固定为 `cleanup_expired_uploads` 补偿计划：每个 Workspace 首次初始化上传时同事务幂等确保一份，按有界配置周期创建 `upload_cleanup` Task，Media Worker 只扫描该 Workspace 内仍 pending、已过期且未形成 MediaVersion 的小批 UploadSession。它用于收敛 one-off 计划缺失、暂停或历史异常留下的临时对象，不取代 one-off 精确到期主路径，也不删除 completed/failed session、MediaVersion 或 MediaLocation。owner 可通过 handler 专用配置命令在 interval 与数字五段 cron/IANA timezone 间切换，并明确选择 skip/run_once/catch_up；不提供通用 Schedule 创建、任意 handler、函数路径或 payload。

第三个真实 handler 固定为 `retire_media_location` one-off 退役计划。迁移/回滚 Worker 在同一业务事务设置 retiring Location 的 `retire_after` 并幂等创建或重排计划；dispatcher 到期后创建 `media_location_retirement` Task。退役 Worker 再次锁定 Location 并检查到期、唯一 verified active 和当前 storage profile/bucket，任何门禁不满足均不删除。它只服务 PT-MED-005，不开放用户自定义 handler；完整 Scheduler 的接受由三个白名单 handler、时间规则、并发故障矩阵和真实消息栈联合证明，不从单一 handler 外推。

## 2. Redis 缓存设计

后端使用 `redis-py` 的 `redis.asyncio`，应用 lifespan 创建连接池并在关闭时 `aclose`。Redis 使用独立用户、TLS/受控网络和最小 key pattern 权限；不在 key/value 放 token、预签名 URL、原始剧本或密钥。

key 格式为 `lanverse:<env>:<namespace>:v<schema>:<scope>:<identity>:<revision>`。scope 必须能表达 Workspace/全局边界，identity 只使用不可猜测 ID 或 hash。namespace 仅允许登记项；TTL 带小幅 jitter，防止同时过期。

cache-aside 流程：

1. 先建立 ActorContext 和访问 scope，再读取对应 key；缓存不能跳过授权。
2. miss 时读 PostgreSQL，转成显式 schema 的 JSON 并以有限 TTL 写回；空结果使用更短 TTL。
3. 业务写事务提交后再删除稳定 key/推进 revision；失效失败记指标和告警，不回滚已提交业务。
4. Redis 超时使用毫秒级客户端上限和小次数重试；普通读立即回源，不让缓存故障耗尽 API 连接。

高成本生成的令牌桶/固定窗口限流可用 Redis 原子脚本；Redis 不可用时失去安全/成本保护的命令 fail closed。幂等键、Task、Schedule lease、所有者权限和账本仍留在 PostgreSQL，不用 Redis 分布式锁保护关键业务。

### 2.2 高成本生成保护

`PT-CCH-002` 只保护服务端价格快照判定为 `high_cost_required` 的生成提交，低于阈值的命令不因 Redis 故障被阻断。顺序固定为：鉴权 → PostgreSQL 幂等请求回读 → 锁内重算预检/价格与确认项 → Redis 高成本保护 → PostgreSQL Request/Task/Reservation/CostEntry/Outbox 原子事务。已有成功请求的同键同输入直接从 PostgreSQL 回读，不再次消耗窗口额度；Redis 不是幂等或费用事实源。

高成本保护使用单个 Lua 脚本原子处理全局窗口、Workspace 窗口和请求去抖。窗口 key 只含环境、固定 `high_cost_guard` schema、scope 与 Workspace UUID；请求 key 使用原始 `idempotency_key` 的 SHA-256，不保存原文，并把 GenerationRequest input hash 作为 value。相同请求摘要在去抖 TTL 内返回 duplicate 并允许原事务重试，不重复计数；同一幂等摘要绑定不同 input hash 返回冲突。新请求只有在全局和 Workspace 计数均低于上限时才同时增加两个计数并写去抖记录，脚本内任一拒绝都不产生部分计数。

默认策略由有界环境配置提供：60 秒窗口、每 Workspace 3 个、全局 20 个、去抖记录 900 秒；全局上限不得小于 Workspace 上限，去抖 TTL 不得短于窗口。错误只返回稳定 scope 与 `retry_after_seconds`，不返回 Redis key、请求摘要或内部计数。Redis 超时、协议异常或连接失败映射为 `DEPENDENCY_UNAVAILABLE` 并零业务写入；窗口不足映射为 `QUOTA_INSUFFICIENT`；去抖摘要冲突映射为 `STATE_CONFLICT`。Redis 许可已写而数据库事务随后失败时，相同幂等键和相同 input hash 可在去抖 TTL 内安全重试且不增加计数。

### 2.1 首个真实 namespace：Workspace 详情

`workspace_detail` 是首个且当前唯一登记 namespace。API 读取顺序固定为 `JWT/账号校验 → PostgreSQL Membership 查询 → Redis revision 指针/投影 → miss 时 PostgreSQL Workspace 查询 → 最佳努力回填`，因此缓存命中不能绕过账号停用、token version、成员关系或跨 Workspace 隐藏。缓存值只保存 `workspace_id/name/status/revision`，响应中的 role 永远来自本次 PostgreSQL Membership；不缓存邮箱、token、头像、审计、预签名 URL 或业务正文。

该 namespace 使用两个同 TTL 的 key：`...:<workspace_id>:revision:current` 保存当前 revision，`...:<workspace_id>:workspace:r<revision>` 保存对应投影。更新、归档和恢复提交后只需删除 `revision:current`；旧 revision 投影无法再被发现并由 TTL 自然回收。创建和成功读取可最佳努力写入新 revision/投影；任一步缓存错误都按 miss 处理，不回滚已提交事务。TTL 和 jitter 来自有界环境配置；namespace/operation/result 指标仅使用固定低基数 label。

`CachePort` 只暴露类型化 get/set/monotonic-revision/delete/namespace invalidate/close，业务模块不导入 `redis`。revision 指针通过 Redis 原子脚本只接受不旧于当前值的 revision，防止并发 miss 回填或连续更新的提交后动作把新投影倒退成旧投影。Redis adapter 只能接受登记 namespace，并对 key 片段做格式校验；运维在 `backend/` 执行 `.venv/bin/python -m app.cache_admin workspace_detail` 按前缀扫描删除，容器内使用同一 CLI，不执行 `FLUSHDB`，避免影响同一 Redis 中其他环境或应用。

## 3. 对象存储端口与适配器

`backend/app/modules/media/storage.py` 定义 media 可见的 `ObjectStoragePort`，只提供 ensure_bucket、presign_upload、presign_download、stat、put、copy、stream、delete 八项受控操作。`stat` 返回 `StorageObjectMetadata(size_bytes, content_type, etag)`；ETag 只用于诊断与契约验证，业务不得把它持久为平台内容 hash。端口统一抛出 `StorageObjectNotFound`、`StorageAccessDenied`、`StorageIntegrityMismatch`、`StorageUnavailable`，不泄漏 SDK 异常。MinIO/OSS 适配器分别在 integrations 中按真实选型创建。

对象 key 和预签名 TTL 必须在网络调用前验证：key 非空、至多 1024 字符、不以 `/` 开头、不含空段、`.`/`..` 段或控制字符；TTL 限制在 1～604800 秒。同步 MinIO SDK 调用使用同一有界 `CapacityLimiter` 离开事件循环，每次操作有独立超时并允许取消后的线程结果被放弃；超时、连接失败或无有效响应统一为 `StorageUnavailable`。S3 `InvalidAccessKeyId`、`AccessDenied`、`SignatureDoesNotMatch`、`InvalidToken`、`ExpiredToken` 映射为 `StorageAccessDenied`，缺对象映射为 `StorageObjectNotFound`。任何错误响应、endpoint、access key、secret 或预签名 URL 都不得进入异常消息、日志和持久事实。

`ensure_bucket` 是幂等的 MinIO bootstrap/readiness 操作：不存在时创建 bucket，随后验证 bucket 没有允许匿名读取的策略；已经存在的私有 bucket 不改变策略。`put` 接受内存字节并由 SDK 在超过分片阈值时自动 multipart，业务不暴露 upload-id/part API；直传仍使用短期预签名 PUT。`delete` 对不存在对象幂等成功，`copy` 必须使用服务端复制且缺源对象返回 NOT_FOUND，`stream` 必须在正常、异常和取消路径关闭并释放连接。

完整性由 media 域的单一 `verify_object_integrity` 实现：先 HEAD 比对声明大小和可选 MIME，再分块流读计算 SHA-256；任何不一致抛出 `StorageIntegrityMismatch`。上传完成只有校验通过才创建可用 MediaVersion；位置迁移只有目标对象通过同一校验才切 active。未知写入结果不得重试制造第二对象，应先 HEAD/流式 hash 对账。端口的 multipart 证据必须使用大于 5 MiB 的真实对象并证明 multipart ETag 含分段标记且不等于平台 SHA-256。

| 环境 | 适配器 | 约束 |
| --- | --- | --- |
| 开发/测试/MVP | MinIO Python SDK → MinIO | 私有 bucket，本地 Compose；使用支持的 S3 操作子集 |
| 阿里云生产（选定后） | Alibaba Cloud OSS Python SDK V2 → OSS | RAM 最小权限、私有 bucket、地域 endpoint、虚拟主机风格 |

不用“同一 SDK 只改 endpoint”作为验收假设。OSS 只兼容 S3 API 子集，请求风格、ACL 和分片 ETag 与 MinIO/S3 存在差异。两适配器必须共用一套 port 契约测试；平台自己计算 sha256，不把 ETag 当内容 hash。

MediaVersion 只持久不可变内容元数据；`med_media_locations` 追加 storage_profile、bucket、object_key、migration_task_id、retire_after 和 verified/active/retiring/retired 状态。profile 配置从 secret/环境注入，表中不放 endpoint 凭据。迁移 Task 使用服务端复制写入稳定目标 key，验证 size/sha256 后才事务切换每版本唯一 active location；旧位置的 one-off 退役计划和 `retire_after` 共同构成独立删除门禁。MVP 先在同一 MinIO profile/bucket 证明私有匿名拒绝、真实预签名 PUT/GET、HEAD、服务端 copy、自动 multipart、分块流读、类型化错误、临时删除、上传半失败以及迁移/回滚/退役算法；切换 OSS 后新对象使用新 profile，并须另行通过真实 OSS 契约，不能复用本地证据冒充上线验收。PT-STO-002 在目标 OSS、地域和 RAM 权限未选定时保持 `conditional/not-applicable`，不得由 MinIO 结果推定接受。

2026-08-04 PT-STO-001 已按上述边界完成真实 MinIO 收口：端口严格保持八项操作，`StorageObjectMetadata` 与四类稳定错误已落地，上传完成和位置迁移共用流式完整性校验；真实私有访问、预签名 PUT/GET、HEAD、copy、>5 MiB multipart、ETag/SHA-256 差异、删除幂等、错误凭据、不可达 endpoint、上传半失败和完整媒体栈均通过。业务模块不再读取 SDK、endpoint 或凭据，证据见[MinIO 对象存储端口验收](../../acceptance/arrived/022-MinIO对象存储端口验收.md)。该接受不包含任何 OSS 适配或生产地域证明。

## 4. 调度数据与算法

`sys_schedules` 必须归属 workspace_id，并保存 schedule_key、handler_name、scope/payload JSONB、kind(one_off/interval/cron)、rule、timezone、status、next_fire_at、next_attempt_at、misfire_policy/max_catch_up、failure_count/last_error、revision、lease_until/by。handler_name 来自显式登记表，payload 使用 Pydantic `extra=forbid`，不存 Python 函数路径或 pickle。

`sys_schedule_fires` 保存 workspace_id、schedule_id、fire_key、scheduled_for、trigger_kind、status、task_id、outbox_event_id、trace_id、error_summary 和 created_at，并唯一 `(schedule_id, fire_key)`。Fire 分别以 `(schedule_id,workspace_id)`、`(task_id,workspace_id)` 和 `(outbox_event_id,workspace_id)` 复合引用 Schedule、Task 与 OutboxEvent；OutboxEvent 为此声明 `(id,workspace_id)` 唯一键，数据库必须拒绝任何跨 Workspace 拼接。计划触发的 fire_key 由计划 UTC 时刻规范化得到；手动触发使用 `manual:<request_id>`，不伪造计划时间。

Scheduler 循环：

1. 按 status=active、next_fire_at<=now、next_attempt_at 已到期且 lease 为空/过期，用 `FOR UPDATE SKIP LOCKED` 小批量领取，写有期 lease 后快速提交。
2. 对每个到期时刻开启短事务；写唯一 ScheduleFire、调用已登记的 task factory 创建业务 Task + Outbox，计算 next_fire_at 并释放 lease。
3. 唯一冲突时回读已有 Fire，不创建第二 Task。Fire/Task/Outbox 事务失败时全部回滚，随后以独立短事务增加 failure_count、保存脱敏 last_error 并指数退避 next_attempt_at；达上限后进入 manual_attention 并告警。
4. 进程中断后其他实例只回收过期 lease；不依赖 Redis 锁、本地时钟内存或 RabbitMQ 中的未来消息。

时间一律以 UTC 持久，生产 Scheduler 的到期与 lease 判定使用 PostgreSQL `CURRENT_TIMESTAMP`，不使用多实例各自的进程时钟作权威。测试可显式注入 UTC `now` 重放边界。

rule 仅允许三种受控 schema：one-off 保存 `at/misfire_grace_seconds`，interval 保存 `seconds/misfire_grace_seconds`，cron 保存 `expression/misfire_grace_seconds`。cron 只接受数字五段 `minute hour day-of-month month day-of-week`，支持星号、列表、范围和步长；拒绝秒字段、宏、月/星期名、函数路径或未登记扩展。IANA timezone 用锁定 `tzdata` 解析；春季 DST 不存在的 wall-clock 分钟跳过，秋季重复分钟只选 `fold=0`，因此同一本地计划点不会产生两个 Fire。

misfire 以 rule 内的有界宽限判定，MVP 默认 30 秒：`skip` 不为超出宽限的历史点创建 Fire/Task；`run_once` 只为最接近当前的到期点创建一份；`catch_up` 为最接近当前的最多 `max_catch_up` 个点各创建一份，范围 1～20。三种策略均在同一调度事务中把 `next_fire_at` 推到严格晚于本次数据库时钟，超出 catch-up 上限的更旧计划点明确丢弃，不在后续 loop 继续无界补发。one-off 的 skip 超宽限后直接 completed，不伪造 Task。

`cleanup_expired_uploads` 是唯一允许在 interval 与 cron 之间配置的已登记业务 handler。owner 只能对已存在的该 Schedule 调用专用 configuration 命令，提交 expected revision、effective_from、rule、timezone、misfire policy 与 max catch-up；不提供通用 Schedule create、handler 名称、payload 或函数路径输入。暂停不取消已有 Task；恢复必须明确 resume_from 和三种策略，skip 在恢复时直接跳过旧点，run_once/catch_up 保留应补偿的旧 `next_fire_at`。手动触发使用独立幂等 Fire，不改变下一计划时刻，也不重复写审计。

## 5. 运行与依赖边界

`backend/app/scheduler.py` 在 S2 第一个真实 Outbox 发布用例中创建，并保留独立组合函数；容器部署由 `backend/app/server.py` 将其与 API、I/O Worker、Media Worker 作为同级受监督任务启动。Schedule dispatcher 与 Outbox Publisher 两个 loop 相互独立：前者使用数据库时钟产生到期 Task/Outbox，后者将已提交 Outbox 发布 RabbitMQ。每个独立入口都通过组合根模型注册表加载完整 SQLAlchemy Metadata，避免后台事务只导入局部模型而无法解析跨模块外键。任一受监督角色退出时 `server` 取消其他角色并交由容器重启；恢复仍依赖持久事实、连接重试和 lease，不把进程重启当数据恢复机制，也不在 FastAPI lifespan 中偷启后台线程。

Scheduler 的租约、SKIP LOCKED 和唯一约束仍保证重复执行安全，但当前固定容器名的本地拓扑只运行一个 `server` 实例。它只引用公开 task factory，不导入业务 Repository 或直接调用外部系统。API 只提供经授权的运维 Schedule 列表/暂停/恢复/立即触发；MVP 不提供任意 handler 或 cron 创建接口。

每个 Schedule/Fire/Task/Outbox 使用同一 workspace_id，从数据库外键到 handler 均拒绝跨空间执行。需要处理租户数据的周期维护按 Workspace 创建 Schedule；容器日志轮转、telemetry 清理等平台运行时工作不伪装为业务 Task。

## 6. 失败、可观测与安全

| 故障 | 处置 |
| --- | --- |
| Redis 超时/清空 | 普通读回源，限流保护失效的高成本命令拒绝；不做数据恢复 |
| 对象写超时 | 以 locator + size + sha256 先 HEAD/对账，再重试登记或清理；不盲目改 key |
| Schedule handler 未知或 payload 不合法 | 第一次调度即进入 manual_attention、保留类型化错误摘要并告警，不反射执行 payload |
| Scheduler 中断 | 回收过期 lease，按 misfire 收敛；唯一 Fire 防重 |
| RabbitMQ 不可用 | Task/Outbox/Fire 仍持久，Publisher 恢复后继续发布 |

普通 dispatcher 失败使用 2/4/8/16 秒有界退避；第 5 次失败进入 `manual_attention`、清除下次自动尝试并产生低基数告警指标与结构化错误日志。未登记 handler/payload 不做五次无意义重试，第一次直接人工处置。`last_error` 只保存稳定错误类别，不保存 payload、对象 key、URL 或依赖原文。

指标仅使用 namespace/operation/result/handler 等低基数 label：cache_requests/hit/error/duration、storage_operations/bytes/error/orphan_age、schedule_due/lag/misfire/fire_result/lease_recovered。日志携 trace_id、schedule_id/fire_id 但不把它们作指标 label，也不记 Redis value、预签名 URL 或存储凭据。

## 7. 测试与验收

- Redis 集成：hit/miss、TTL、revision key、提交后失效、原子全局/Workspace 高成本窗口、同摘要去抖/异摘要冲突、故障 fail-closed 和连接关闭。
- 同一 ObjectStoragePort 契约必须在 MinIO 通过；选定 OSS 上线时，再以真实 OSS 验证私有直传、HEAD、分片、预签名、ETag 差异、hash 和迁移。
- PostgreSQL 并发：多 Scheduler 同时领取只产生一个 Fire/Task，事务回滚、lease 回收、暂停/恢复、手动触发和三种 misfire 策略。
- 故障注入：Scheduler 在 Fire/Task/Outbox 各边界退出、Redis 不可用、存储写结果未知、RabbitMQ 恢复后最终收敛。
