# AI生成媒体与候选采用模块设计

## 1. 模块边界

- `generation` 拥有 GenerationCandidate 和 Adoption，负责“某个版本化使用位置有哪些候选、当前采用哪一个”。
- `media_library` 拥有 MediaObject/MediaVersion，负责 MinIO 对象定位、字节哈希、探测、技术状态和派生谱系。
- `integrations/ai` 和 `integrations/minio` 是 Adapter，不拥有业务事实。
- `production_jobs` 拥有执行记录；Worker 必须经上述两模块公开用例登记结果。

## 2. AI 能力端口与 Registry

| 能力 | 输入 | 输出 | 必要校验 |
| --- | --- | --- | --- |
| `text` | 快照、Prompt、严格 Schema | 结构化内容 | Pydantic strict 契约 |
| `image` | asset/shot usage 与版本哈希 | 图片位置或字节 | MIME、字节上限、可解码、尺寸 |
| `video` | shot + 必需图片 Adoption | 视频位置或字节 | 9:16、时长±90,000 ticks、可解码 |
| `tts` | SpeechLine、文本哈希、逻辑 voice_id | 音频位置或字节 | 音色映射、非空时长、可解码 |

`AiModelRegistry` 按 capability/profile ID 解析已批准的不可变 profile，包含 Provider/model/route/schema/parameters 约束与 Adapter factory。每类能力可登记多个 Provider/模型和确定性 Mock；Task 受理时冻结一个 profile，失败后不自动 fallback。文本使用 `langchain-core` Runnable/模型接口，图片、视频、TTS 可用对应 LangChain Provider 集成或直接 Python SDK Adapter；业务层不感知 SDK。

## 3. Usage slot 与输入兼容性

| usage_type | usage_id / input_version | 受理前置 |
| --- | --- | --- |
| `asset_image` | character/scene asset_id / CreativeAssetVersion | confirmed 资产；style 不产生 slot |
| `shot_image` | shot_id / ShotSpecVersion | confirmed Shot 及所有关联资产/风格版本 |
| `shot_video` | shot_id / ShotSpecVersion | 当前 input_hash 下所需 asset/shot image 的 active Adoption |
| `speech_audio` | speech_line_id / ScriptVersion | confirmed SpeechLine 的文本哈希和 voice_id |

`input_hash` 使用 DESIGN-04 的 canonical wrapper，绑定内容版本和所需 Adoption。新版本、新文本哈希或新输入 Adoption 会形成新 slot，旧 Adoption 不能冒充新生产输入。

## 4. 媒体下载、登记与候选

1. Adapter 只返回批准域名的远端引用或受控字节流；Worker 限制超时、跳转、MIME 和最大字节。
2. 下载到受控临时目录，计算 SHA-256，用 ffprobe/图片解码器探测；先按稳定 object key 写 MinIO，再幂等登记 MediaObject/Version。
3. 技术校验通过才创建 `ready` Candidate；超尺寸、无法解码、时长超差或取消后迟到结果为 `invalid/blocked`。
4. Candidate/MediaVersion 的身份、输入、哈希、谱系不可变；不保存 Provider 私有原始响应。
5. MinIO URL 不是事实；PostgreSQL 只保存 bucket/object_key/version/hash/probe，前端按需获得 900 秒预览授权。

## 5. 采用事务与并发

`adoptCandidate` 验证 Candidate ready、同 Episode、usage slot 完全匹配且输入仍兼容；然后锁 Episode 和当前 Adoption，supersede 旧 active 并插入新 active。partial UQ 保证每个 `usage_type+usage_id+input_version_id+input_hash` 最多一个 active。不删除旧 Candidate/MediaVersion/Adoption；采用不改变 Task 状态。

## 6. 失败、安全与回滚

| 场景 | 结果 | 恢复 |
| --- | --- | --- |
| profile 缺失/不支持能力 | 受理前明确失败 | 批准配置后创建新 Task |
| Provider 限流/超时 | Attempt 可重试或 unknown | 遵循 DESIGN-09 对账，不换 Provider |
| 媒体技术无效 | Candidate invalid/blocked，不可采用 | 为该 slot 创建新 Task |
| 并发采用 | 唯一约束只保留一个 active | 返回稳定冲突并刷新 |
| 预览授权过期 | 媒体事实不变 | 重新申请授权 |

凭据只在服务端环境，LangSmith tracing 强制关闭，网络只许可批准 Provider/MinIO。回滚不删除已登记对象；新代码异常时停止领取新 Job，保留对账信息。

## 7. Design 验收标准

- AC-MOD-GEN-001：四类能力均可通过同一 Registry 解析确定性 Mock 和多个已批准 profile，Task 内 profile 不变且无自动 fallback。
- AC-MOD-GEN-002：缺少必需图片 Adoption 或风格版本/哈希的视频命令在受理前被拒绝。
- AC-MOD-GEN-003：每个 ready Candidate 可追溯到 Task/Attempt/快照/profile/Provider/model/input hash 和 MediaVersion SHA-256。
- AC-MOD-GEN-004：媒体在 ready 前完成 MIME、字节、解码、尺寸/时长探测，无效或迟到结果不可采用。
- AC-MOD-GEN-005：并发采用中每个版本化 slot 最多一个 active Adoption，旧候选、媒体和历史采用不变。
- AC-MOD-GEN-006：局部失败/重试只新增目标 slot 的 Task/Candidate，其他 slot 的 Attempt、Adoption 和媒体哈希不变。
