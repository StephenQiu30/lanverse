## 结论

Production Bible 不再是 Scene 分析前先锁死的一份大 JSON。正确顺序是先从每个 Scene 提取不带风格的原文事实，再用全剧事实调和身份；Gate 1 只确认结构与身份，随后才构建完整状态、场景出现、人物—道具交互和连续性，并在 Gate 2 由三个正式 Owner 协同提交。

```text
DocumentRevision + SourceSpanIndexVersion
→ source_revision_accepted
→ EpisodeSpanCandidate + SceneSpanCandidate
→ SceneFactCandidate（style-blind，使用 RawMentionRef）
→ 全剧 IdentityResolutionCandidate
→ Gate 1: Structure & Identity
→ production/project: project_episode_lifecycle_confirmed
→ production/bible: StructureIdentitySetVersion
→ ProductionWorldCandidate
   ├─ Specification / WorldRule / 跨集 Claim
   ├─ 完整 Character/Location/Prop AssetState
   ├─ Scene / Dialogue / NarrativeBeat / Occurrence
   ├─ ContinuityClaim（含 InteractionClaim）
   └─ DesignGap / ContinuityLedgerView / ReviewIssue
→ 跨 Scene、跨 Episode 调和，直至固定点或显式 blocker
→ Gate 2: Bible & Continuity
→ production/bible + production/planning + asset 协同 Owner Apply
→ Confirmed Production World
→ Preset / Visual Foundation / Reference Plan（Gate 3 以后）
→ storygraph-production 下游编译
```

剧本事实抽取和前两个 Gate 对 Preset、Style、视觉 Recipe 与图片 Provider 隔离。用户即使已选择世界观预设，也只能冻结该选择，不能让它进入 Scene Fact、Identity、Specification、AssetState、Scene、Occurrence 或 Interaction 的事实判断。剧本未写明的视觉信息形成 `DesignGapCandidate`；它不能被模型常识或预设静默补写成 Evidence。

Agent/Python Harness 只产出不可变 Candidate 或有界 Repair Patch。Go Backend 持久化执行事实、校验证据与覆盖、管理人工决议，并调用唯一 Owner。StoryGraph 只在 Owner Apply 完成后投影正式事实，不能作为本流程输入、身份库或调和记忆。

## 1. 问题、范围与非目标

按集或按场孤立解析会产生四类直接伤害：同一人物被别名拆成多个身份，同名人物被错误合并，换装/伤势被建成新角色，人物拿取或交接道具被塞进人物形象。旧设计又要求完整 Bible 先确认、Episode/Scene 只能引用既有身份和状态，使 Scene 级证据无法反向纠正全局判断。

本文固定：

- 从原文固定、拆集、拆场到 Gate 1 的结构与身份算法；
- 从 Gate 1 到 Gate 2 的制作世界候选、调和循环与局部收敛规则；
- Character、Location、Prop 的 Identity、Specification、完整 AssetState、Occurrence、Interaction 和连续性边界；
- Evidence、创作者决定、Design Gap、Candidate Revision、覆盖证明、人工审核和多 Owner Apply 语义；
- 分片、重试、恢复、局部失效和 P0 Text Production Bible 完成门。

本文不固定 Agent Stage 名、Wire Schema、Skill Bundle 路径、WorkflowDefinition Node 或 HumanTask Record；这些由 `VP-D07` 和 `VP-D11` 定义。本文也不定义 Preset 解析、Visual Brief、三视图/地点板/道具板生成、图片 Provider、Reference Binding 或 Storyboard；它们分别从 Gate 3、`VP-D07`、`VP-D08` 和后续设计开始。

## 2. 两个正式快照，而不是一份过早 Bible

### 2.1 StructureIdentitySetVersion

`StructureIdentitySetVersion` 是 Gate 1 后由 `production/bible` 发布的窄快照，只保存结构与身份决议的内容身份：

- 精确 `DocumentRevision`、`SourceSpanIndexVersion` 和候选根修订；
- 已接受的 EpisodeSpan/SceneSpan 引用、每个 span 冻结的 `scene_owner_logical_id` 与由其逐字节派生的 Scene scope keys；
- 版本内稳定的 Character/Location/Prop identity keys；
- 每个 `RawMentionRef` 到某个 identity key 或 `unresolved` 的完整映射；
- alias、同名拆分、显式 merge/split/reuse 决议及 ReviewDecision 引用；
- coverage manifest、内容 Hash、父版本和 supersession 谱系。

它不复制原文或 Candidate payload，不包含正式 Asset、Specification、AssetState、Scene、Occurrence、Interaction、Preset 或 StoryGraph Node。identity key 是 Gate 1 后稳定的生产身份键，但只有 Gate 2 的 `asset` Owner Apply 才创建或复用正式 AssetIdentity。临时 key → 稳定 identity key 的映射必须进入该版本的内容 Hash，不能只藏在 Receipt 或日志中。

### 2.2 ProductionBibleVersion

`ProductionBibleVersion` 是 Gate 2 后由 `production/bible` 发布的项目级制作世界根。它必须内嵌精确 `StructureIdentitySetVersion` Ref，并完整声明同一 Root 下的：

- Evidence；
- Character/Location/Prop SpecificationVersion；
- WorldRule、StoryArc、PlotThread 与跨集 Narrative Claim；
- Specification、AssetIdentity、AssetState 的 `ProductionBinding`；
- Gate 2 ReviewDecision 输入、覆盖身份与内容 Hash。

Receipt 在提交后单向引用 Owner Version/Collection Root，不能反向进入 ProductionBibleVersion 的 content hash，否则会形成哈希环。ProductionBibleVersion 不复制 `production/planning` 的 Scene/Dialogue/Beat/Occurrence/Continuity/Causal Claim，也不复制 `asset` 的 AssetIdentity/AssetState。`Confirmed Production World` 是 Backend 从同一次 Gate 2 已提交的 Bible、Planning、Asset roots 和 receipts 组成的 typed Query 结果，不建立第四个 Owner 或万能 JSON 表。

### 2.3 废止的顺序

以下旧行为不再是目标合同：

- 先构造包含全部身份/状态的 ProductionBibleVersion，再让 Scene 分析只能引用它；
- Bible Confirm 后另起 `MaterializeConfirmedBible` 才创建 Asset/State；
- Episode 分析遇到未知实体就只报错、不能反向参与全局调和；
- 用 `current/latest Bible`、名称相似度或 StoryGraph 搜索补齐正式引用；
- 将 Human Gate、Candidate JSON 或 Agent checkpoint 当作 Owner 事实。

## 3. 唯一 Owner 与写入边界

| 对象 | 唯一 Owner | 本流程中的写入时点 |
|---|---|---|
| DocumentRevision、SourceSpanIndexVersion | `production/script` | 原稿固定与 `source_revision_accepted` |
| Project/Episode 身份、顺序和生命周期 | `production/project` | Gate 1 同一用户决议内、Bible Apply 之前 |
| StructureIdentitySetVersion | `production/bible` | Gate 1 |
| Evidence、SpecificationVersion、WorldRule、跨集 Claim、ProductionBinding、ProductionBibleVersion | `production/bible` | Gate 2 |
| Scene、Dialogue、NarrativeBeat、Occurrence、Causal/Continuity Claim | `production/planning` | Gate 2 |
| Character/Location/Prop AssetIdentity 与完整 AssetState | `asset` | Gate 2 |
| Candidate/Revision/Invocation/Shard/Result | Backend `agent` | 每次分析或修复 |
| HumanTask/ReviewDecision | `review` | Gate 决议 |
| StoryGraphVersion | `production/storygraph` | Gate 2 Owner 事实提交后的独立编译 |

任何模块只能通过 typed Query 读取其他 Owner 的精确 version/ref/hash。Gate 2 的协同 Apply 可以在当前单 Go Backend、单 PostgreSQL/GORM 事务中执行，但每个模块仍独立校验、写自己的聚合与 receipt；Gate 1 保持后文定义的两个有序独立 checkpoint。不得引入第二数据库、跨服务分布式事务或绕过 Owner 的共享 Repository 写入。

## 4. P0 Checkpoint 与 Owner Collection 路由

P0 只允许以下四个决策 checkpoint；Gate 1 和 Gate 2 之外的两个 checkpoint 是原稿与 Project 生命周期事实，不增加用户 Gate：

| checkpoint | Owner | version family | 语义 |
|---|---|---|---|
| `source_revision_accepted` | `production/script` | `script_source_set` | 一个已接受 DocumentRevision 与匹配 SourceSpanIndexVersion |
| `project_episode_lifecycle_confirmed` | `production/project` | `project_episode_set` | 完整 active Episode 身份、顺序与生命周期 |
| `gate_1_structure_identity` | `production/bible` | `bible_structure_identity_set` | 一个精确 StructureIdentitySetVersion 根 |
| `gate_2_bible_continuity` | `production/bible` | `bible_production_world_set` | ProductionBibleVersion 及其 Evidence/Specification/Binding/Rule/跨集 Claim 完整根 |
| `gate_2_bible_continuity` | `production/planning` | `planning_scene_set` | 每个 active Episode 的完整 Scene/Dialogue/Beat/Occurrence/Continuity/Causal Claim 根 |
| `gate_2_bible_continuity` | `production/planning` | `planning_structure_rebase_set` | 仅结构重切分时一个 rebase/supersession 根；正常为空且无 Receipt |
| `gate_2_bible_continuity` | `asset` | `asset_identity_state_set` | 完整 AssetIdentity 与每个身份至少一个 AssetState 根 |

表外 checkpoint/Owner/family 组合全部拒绝。七个 family 的 collection scope、成员基数、空集和排序规则直接采用 [0010 的 Owner Input Manifest](0010-StoryGraph内容图与DAG创作画布设计.md#storygraph-production-schema-scoped-owner-input-manifest)，本文不建立另一份同名 Schema。

每个实际 Collection Root 必须形成自己唯一的幂等 Receipt，唯一性维度为 `(checkpoint, owner, family, scope_kind, scope_key, collection_root_hash)`；不能用一个 Owner 级 Receipt 证明多个 Collection。Receipt 至少绑定 checkpoint、receipt scope、covered Scene scopes、committed collection root hash、committed Owner version ref、idempotency identity 和 receipt content hash。`planning_scene_set` 因而对每个 active Episode 各有一份 Receipt；条件式 rebase 另算一份，正常空 rebase 既无 committed ref 也无 Receipt。

`gate_1_structure_identity`、`gate_2_bible_continuity` 以及与 Gate 1 共用用户决议的 `project_episode_lifecycle_confirmed` Receipt 必须绑定精确 ReviewDecision；`source_revision_accepted` 绑定 source acceptance audit/command identity，不伪造 ReviewDecision。Receipt 不能替代业务内容：identity key 映射属于 StructureIdentitySetVersion，Specification/State 映射属于 ProductionBinding，Scene 集合属于 Planning root。

Owner read adapter 在同一数据库读事务中按精确 scope 重算 Collection 的 scope revision/hash、完整 members、members hash 与 collection root hash；调用方不能自行声明 Collection 完整，也不能在两个查询时点拼出 roots。`source_revision_accepted` 与 `project_episode_lifecycle_confirmed` 的 `covered_scope_keys[]` 为空；Gate 1 和 Gate 2 receipts 的 scope 并集分别必须精确等于将进入 p0 的 scope keys。

## 5. 规范原文、Evidence 与覆盖

Backend 先把上传文档规范化为不可变 `DocumentRevision`，再发布 `SourceSpanIndexVersion`。所有文本区间使用规范化原文的 Unicode code-point 半开区间 `[absolute_start, absolute_end)`；不得混用 UTF-8 byte、UTF-16 code unit、页码或模型自行计数。

来源经过三个层次，不能混为一个对象：

1. `SourceSpanIndexVersion` 的 slice 是 Backend 计算输入；
2. Candidate Evidence 是 Agent 对一个 slice 的引用/观察，只能留在 Candidate Revision；
3. Gate 2 由 `production/bible` 发布正式 `source_evidence` fragment，其他正式 Owner 对象通过 `EvidenceRef` 引用它。

正式 `EvidenceRef` 唯一业务四元组固定为：

```text
document_revision_id
absolute_start
absolute_end
text_hash
```

Candidate 可以额外携带 `source_span_index_version_ref` 和 `exact_text` 供校验，但它们不改变 `storygraph-production` 的 EvidenceRef 合同。`text_hash` 对 code-point slice 重新编码为 UTF-8 后计算小写 SHA-256。Backend 必须从已接受的 SourceSpanIndexVersion 重建区间、逐字校验 Candidate exact text，并保证同一四元组只物化一个规范 Evidence fragment；Agent 自报坐标不能直接成为正式 Evidence。

Episode/Scene 分片使用不可变 coverage manifest：

- active leaf 对目标原文范围无缺口、无越界；
- 为理解上下文产生的 overlap 明确标为 context，不重复计入 coverage；
- 每个叶片冻结 scope、输入 Hash、前后邻接和排序键；
- 聚合按稳定键和 Canonical JSON 排序，不依赖 Worker 返回顺序；
- 超过输入预算时发布新的 manifest/tree，不截断原文，也不把漏读当作空结果。

分析覆盖完整不等于所有 Scene 已可生产。未决问题进入显式 blocked scopes；已闭合 scopes 可继续，二者必须可机械证明互斥且与 active Scene scope 集合对账。

## 6. 三层 Candidate 合同

所有 Candidate 都是不可变 `StageCandidateRevision` 所承载的严格 payload。共同 Envelope 至少包含 schema identity、精确输入 refs/hashes、scope/coverage manifest、stable candidate keys、parent/origin、content hash 和有序 issue refs；具体 Wire 字段名留给 `VP-D07`。

### 6.1 EpisodeSpanCandidate 与 SceneSpanCandidate

边界候选只表达原文结构：

- Episode/Scene 临时 key、Backend 预留的稳定 logical identity、绝对区间、顺序和标题/slug line evidence；
- 场头、时空/内外景线索和边界置信度；
- overlap、gap、跨集场、空场和无法判定 issue；
- split/merge 的候选操作及其影响区间。

Scene 边界必须形成每个 Episode 内有序、可覆盖证明的集合。Agent 不分配正式 Episode/Scene UUID；Backend 通过 `production/planning` 所拥有的逻辑 ID 命名空间为候选 Scene 确定性预留 `scene_owner_logical_id`，但预留本身不发布 Scene、Owner Version 或 Receipt。正式 Episode 生命周期由 `production/project` 在 Gate 1 决议内提交，正式 Scene 在 Gate 2 由 `production/planning` 提交。

### 6.2 SceneFactCandidate

`SceneFactCandidate` 只从精确 SceneSpan 与原文提取：

- Dialogue/说话者 mention/台词区间；
- NarrativeBeat、动作、事件和因果线索；
- Character/Location/Prop 的 `RawMentionRef` 与类型线索；
- source-explicit visual assertion 与 `StateClue`；
- `InteractionFact`：使用 raw mention keys 表达动作、道具、人物角色和不确定性；
- Scene 时间、地点、进入/离开、前后状态与连续性线索；
- Evidence refs、置信度、互斥备选和 ReviewIssue。

它禁止输入或输出 ProductionBibleVersion、Preset/Style、Specification、AssetState、正式 Identity/Asset ID、creative fill 或 StoryGraph。首次全剧分析的所有身份引用必须是 raw mention keys，不能用“模型已经知道这个人是谁”绕过 Identity Resolution。

### 6.3 IdentityResolutionCandidate

Identity Resolution 对精确 SceneFact root revision set 的全部 `RawMentionRef` 做全剧调和：

- 每个 mention 必须且只能进入一个同 kind cluster 或 `unresolved`；
- cluster 给出 canonical display name、aliases、kind、支持与反对证据；
- 同名默认不合并，跨名默认不拆分；合并/拆分需可解释约束；
- `new` 只产生临时 identity key；Agent 不创建 UUID；
- `reuse` 只能引用输入中显式允许的旧 StructureIdentitySetVersion 身份索引；
- 每个 merge/split/rebind 保留 supersession lineage 和影响 scopes；
- 完整映射、unresolved 集与 coverage root 必须可重算。

姓名相似、人物常识、图像相似或 Preset 不是身份合并证据。共享身份跨越多个 Scene 时，任何会改变该身份的未决项都把这些 Scene 纳入同一影响闭包。

### 6.4 ProductionWorldCandidate

Production World 的权威身份输入只能是 Gate 1 的精确 StructureIdentitySetVersion；事实输入是该版本内容定址引用的 SceneFact roots 与 Evidence。它可以读取 RawMentionRef 追溯来源，但所有身份解析必须经过版本内的 mention mapping，不能把 raw mention 直接当正式 Identity ref。Candidate 根必须分成三个目标 Owner partition，任何对象只出现一次：

| partition | Candidate 内容 | Gate 2 目标 |
|---|---|---|
| `bible` | Evidence、Specification、WorldRule、StoryArc/PlotThread、Relationship/Foreshadowing/Payoff Claim、ProductionBinding 提案 | `production/bible` |
| `planning` | Scene、Dialogue、NarrativeBeat、Occurrence、Causal/Continuity Claim，InteractionClaim 是其严格分支 | `production/planning` |
| `asset` | Character/Location/Prop AssetIdentity 映射与完整 AssetState 时间线 | `asset` |

根还包含三个 partition 的 expected business keys、scope coverage、cross-partition ref table、DesignGapCandidate、派生 ContinuityLedgerView 和 ReviewIssue。相同 temporary/stable key 的交叉引用必须在 Candidate 内可解析且在 Owner Apply 后映射到精确 Owner refs；Receipt 不能成为唯一映射来源。

Candidate 可以为多个 Owner 提出一致的提交集合，但它本身不拥有业务写权，也不能把三个 Owner 的正式对象折叠为一份 JSON Record。

## 7. 事实、推断、创作者决定与 Design Gap

每个候选字段必须声明来源：

```text
source_explicit  # 原文直接支持
inferred         # 从已列明事实推导，仍可被否决
user_supplied    # 用户明确输入
creative_fill    # 只允许在后续视觉基底阶段或显式用户决议中产生
```

正式可审计事实遵守 `evidence XOR creator decision`：允许创作者决定的对象必须在非空 Evidence 与非空 `creator_decision_ref` 中恰选一；不得同时填写，也不得两者皆空。普通上游 Ref 不能替代来源。Creator decision 必须由目标业务 Owner 内容定址、被该 Owner version content hash 覆盖，并可反查精确 ReviewDecision。Scene、Dialogue、Beat 等必须来自原文的结构事实仍要求 Evidence，不能用创作者决定伪造原文。

`DesignGapCandidate` 至少包含稳定 gap key、subject/field、缺失原因、原文约束、互斥备选、影响 scopes/visual targets 和允许的解决来源。Gate 2 可以让用户：

- 以明确输入形成有审计的 creator decision；
- 保持视觉设计空白，由 Gate 3 的 Preset/Visual Foundation 提案；
- 拒绝错误推断并重跑影响闭包。

“完整 AssetState”指语义槽位完整的独立快照，而不是保证视觉细节已经全部设计：每个受控槽位都必须是已知值、明确 `unspecified_design_gap` 或 `not_applicable`，不能因未填写而继承未知旧值。Gate 2 只有在身份、状态边界、来源约束和连续性确定时才能通过；纯视觉空白可作为 typed gap 交给 Gate 3，但不得把该 Scene 标记为已有可生成视觉输入。

DesignGap 不建立新 Owner 表或 StoryGraph Node。Gate 2 保留的 gap 必须以稳定 key 和原文约束嵌入对应 Specification/AssetState 的显式 `unspecified_design_gap` 槽位并进入 Owner content hash；VisualProductionPackageView 再从这些精确 Owner refs 派生待设计项。Gate 3 产生的是 Visual Foundation/Brief 决议，不反向改写 source-backed Specification/AssetState。

## 8. Identity、Specification 与完整 State

同一现实叙事对象只有一个 AssetIdentity：

- 角色别名、称谓、隐瞒身份属于 Identity 映射；
- 换装、妆容、伤势、污损、年龄阶段、伪装、阵营阶段或形态变化属于同一 Character 下的多个完整 AssetState；
- 地点的季节、损毁、陈设阶段属于 LocationState；
- 道具的开闭、完整度、内容物、污染或关键外观阶段属于 PropState；
- 瞬时表情、姿势和一次性动作默认是 Beat/Interaction，不新建 State。

每个 State 必须有稳定 key、同一 Identity ref、完整槽位快照、故事时间有效范围、适用 Scene/Beat、进入原因、离开原因、前后 State refs 以及 Evidence 或 creator decision。范围重叠只能在业务允许的并行层存在；互斥外观或物理状态重叠必须成为 blocker。

同一已确认制作世界内，每个 Identity 通过唯一 active `ProductionBinding` 解析到恰一个同 kind Specification 和该 Identity 的完整 State 集；每个 Specification/State 也必须被恰一个 Binding 覆盖。Occurrence 使用 Identity/State 后必须机械得到唯一 Specification，零个或多个都以 `ambiguous_production_binding` 拒绝。

## 9. Scene、Occurrence、Interaction 与连续性

### 9.1 Scene 与 Occurrence

正式 Scene 必须绑定一个已确认 Episode、精确 Source spans、故事时间/顺序和完整 Dialogue/Beat 集。每个实际出现在画面或剧情动作中的 Character/Location/Prop 使用独立 Occurrence，并精确引用：

- 一个 Scene，零或一个 Beat；
- 一个 AssetIdentity 和一个属于它的 AssetState；
- Evidence 或允许的 creator decision；
- occurrence role、story time 和稳定 business key。

纯提及、回忆中未呈现、画外谈论等保留为 `mentioned_only`，默认不创建视觉 Occurrence。若用户要求把它制作成实际视觉出现，必须在 Gate 2 生成由 `production/planning` 审计并纳入 Owner root hash 的 creator decision；Gate 3 不得无上游事实直接加 Reference Target。

### 9.2 InteractionClaim

人物拿、穿、使用、传递或改变道具是 `InteractionClaim`，不是 Character AssetState、组合 Identity 或自由文本备注。它是 `production/planning` 拥有的 `ContinuityClaim(claim_type=interaction)`，严格遵循 [0010 的 Interaction 分支](0010-StoryGraph内容图与DAG创作画布设计.md#continuity_claim-的-interaction-分支)：

- predicate 只允许 `hold|carry|wear|use|give|receive|place|drop|open|break`；
- 恰一个 Prop Occurrence、至少一个 actor Character Occurrence；`give|receive` 还需恰一个 counterparty；
- 恰一个 Scene，可选一个 Beat，并锚定全部 participant Occurrence；
- `holder_before/after` 必须存在且只能为 `null` 或 participant Character；
- `prop_state_before/after` 必须属于同一 Prop；
- 手别、握法、接触点、方向、比例只有 Evidence 或用户决定时才填写；
- `give` 与 `receive` 的同一事件只发布一个规范 Claim，不重复应用转换；
- Claim revision/supersedes 形成逐次加一的单链，旧 Claim 不原地修改。

### 9.3 ContinuityLedgerView

Ledger 是按 story time 从 State、Occurrence 和 ContinuityClaim 确定性派生的只读视图，不新建第二套可写状态表。它至少检查：

- 同一物理 Prop 在任一时点最多一个 holder，复制品必须先有独立 Identity；
- `give/receive/place/drop` 的 holder 前后连续；
- `open/break` 等 PropState delta 与相邻 Scene 一致；
- Character/Location/Prop 的 State 变化有原因和有效边界；
- Scene 入场状态等于上一相关事件的出场状态，或存在明确 Continuity delta；
- 播放/编辑顺序不能冒充故事时间顺序。

双 holder、道具瞬移、无因状态恢复、缺 participant、缺 before/after 或相邻账本不一致只阻塞影响闭包，不能由 StoryGraph Compiler 或下游图片生成补猜。

普通 `ContinuityClaim(claim_type=continuity)` 只允许 `state_persists|state_changes`，必须精确绑定一个 subject Identity、同一 Identity 的 before/after State、起止 anchor、非逆序 story time、Evidence 或 creator decision，以及逐次加一的 revision/supersedes 单链。`state_persists` 前后 State 相同；`state_changes` 前后 State 不同且必须说明 delta。正式 Owner Claim 不允许 `uncertain`，不确定项留在 Candidate/Review Issue。

## 10. 全局调和循环

调和不是单次 fan-in，而是有界、可审计的固定点过程：

```text
Scene facts
→ global identity clusters
→ specifications + state timelines
→ formal scene bindings + occurrences
→ interactions + ordinary continuity
→ continuity ledger + cross-scene claims
→ conflict/design-gap detection
→ repair impacted closure
→ repeat until canonical root is unchanged or blockers remain
```

每轮必须冻结输入 root、输出 revision、变更 key 集、影响 scopes、问题集和 canonical content hash。Backend 只允许 Repair 修改已授权 keys；修改后重跑其依赖闭包的 Schema、Evidence、Reference、Coverage、State、Interaction、Continuity 与 Hash Gate。

收敛规则：

- 相同输入、Schema 和决议必须产生相同规范 Root；
- 聚合与比较使用稳定 key，不使用数组到达顺序或显示名；
- 已接受 identity key 不得静默 merge/split；变化必须发布新 StructureIdentitySetVersion；
- 状态边界变化只重算引用该 Identity/State 的 Scene、Occurrence、Interaction 和邻接 Ledger；
- 跨范围 Claim 或共享身份使闭包扩大时必须显式展示扩大结果；
- 达到配置的最大轮次仍不稳定时产生 `non_convergent_reconciliation` blocker，不取最后一次结果冒充完成；
- 模型意见冲突进入 Human Gate，Backend 不按置信度静默胜出。

轮数、单次技术 deadline、调用与 token 预算是运行策略，由 `VP-D07` 冻结；本文只要求预算耗尽不会截断为“成功”，而是保留可恢复状态和未解决问题。

## 11. Gate 1：Structure & Identity

用户看到原文覆盖、Episode/Scene 边界、Scene 风险、raw mention clusters、aliases、同名拆分和 unresolved。用户可以 split/merge Scene、merge/split Identity、重绑 mention、复用明确旧身份或保留未决。

Gate 1 通过条件：

- 目标 scopes 的 Episode/Scene 原文覆盖完整且边界无 blocker；
- 每个目标 scope 的全部 RawMentionRef 恰映射到一个 identity key 或显式 unresolved；
- 需进入后续制作的身份在其依赖闭包内没有 unresolved；
- alias/type/reuse/merge/split 约束通过；
- Candidate revision/hash、DocumentRevision 和 coverage manifest 未漂移。

Gate 1 ReviewDecision 必须把每个接受的 SceneSpan 临时 key 映射到预留的 `scene_owner_logical_id`，并将完整映射写入 StructureIdentitySetVersion content hash。Gate 1 Receipt 的 `covered_scope_keys[]` 逐字节等于这些 ID 派生的 `scene:<scene_owner_logical_id>`；不得用数组序号、标题或临时 key 生成 scope。

一次 Guided Studio 决议在 Backend 内按固定顺序执行两个 Owner Apply：

1. `production/project` 先发布或幂等复用 `project_episode_lifecycle_confirmed`，正式确定 Episode 身份与顺序；
2. `production/bible` 再发布 `StructureIdentitySetVersion`，引用前一步的精确 project/episode refs，并产生 `gate_1_structure_identity` Receipt。

二者是有先后依赖的独立 Owner command/checkpoint/receipt，不是第六个用户 Gate。Project checkpoint 先独立提交；若随后 Bible Apply 失败，已确认且输入未漂移的 Project receipt 继续有效，重试 Gate 1 只幂等复用它并重做第二步。Bible Apply 没有精确 Project receipt 就失败关闭。Bible Owner 不得代写 Episode，Project Owner 不得代写 StructureIdentitySetVersion。

边界编辑会先产生新的 span/SceneFact/Identity candidates，再重新展示决议，不能在 Apply 时直接改 Candidate。Gate 1 后的结构或身份变化必须发布新不可变版本，并使受影响 Gate 2 及下游结果 stale。

## 12. Gate 2：Bible & Continuity

用户看到每个身份的 Specification、完整 State 时间线、Scene/Occurrence、Interaction、Continuity Ledger、世界规则、跨集 Claim、Design Gap 和影响闭包。用户可以调整 State 边界/快照、重绑 Occurrence、修改 Interaction、裁决冲突、把 `mentioned_only` 显式提升为视觉出现，或补充带审计的创作者决定。

Gate 2 通过条件：

- 每个目标 Scene 的三个 Owner partition 满足 expected business key coverage；
- 每个实际 Occurrence 绑定精确 Identity、唯一 Specification 和精确完整 State；
- 所有必需 Interaction 的 participant、anchor、predicate、holder 与 PropState 转换完整；
- Ledger 无双 holder、无因状态跳变和未裁决 blocker；
- 每个正式事实满足 Evidence 或 creator decision 合同；
- 纯视觉 Design Gap 已显式保留或由用户决定，不冒充 source fact；
- Gate 1 精确版本、Candidate head、Owner expected revisions 与 scope closure 未漂移。

正向决议调用一个幂等 `ConfirmProductionWorld` 协调命令。它在同一 PostgreSQL/GORM 事务中按 Owner 规则：

1. `asset` 为 Gate 1 identity key 创建或显式复用唯一 Character/Location/Prop AssetIdentity，并发布完整 AssetState；
2. `production/bible` 发布 SpecificationVersion、Evidence、WorldRule、跨集 Claim、ProductionBinding 和不可变 ProductionBibleVersion；
3. `production/planning` 发布 Scene、Dialogue、NarrativeBeat、Occurrence、Causal/Continuity Claim；存在已接受结构 rebase 时同时发布唯一 planning rebase fact，否则该 Collection 必须显式为空且无伪造 receipt；
4. 为每个实际 Collection Root 分别写精确 committed refs/hash、covered scopes、decision 和 idempotency identity 的 Receipt；Planning 对每个 Episode 各写一份，三 Owner 共同写一次事务 outbox。

实现可以按外键依赖调整事务内 SQL 顺序，但不能改变逻辑 Owner、先验校验或最终原子性。任一 Owner 校验失败整体回滚；重试相同命令返回相同 refs/receipts；输入或 expected head 漂移返回 conflict。精确 Command/Record/Receipt 字段由 `VP-D09` 固定。

Gate 2 不创建 AssetVersion、图片 Candidate、Preset Snapshot、Reference Plan、StoryGraphVersion、Shot 或 WorkflowDefinition，也不再存在 Confirm 后的第二次身份物化。正式 AssetVersion 只能在 Gate 3 以后消费精确 Specification/State/Style，经生成、QC 与人工选择发布。

## 13. Typed Query 与下游读取

Guided Studio 不等待 StoryGraph。Backend 至少提供以下内容定址、只读 Query View；View 不成为 Owner Record，也不读取 current/latest：

| View | 精确输入 | 完整性与 stale 规则 |
|---|---|---|
| Gate 1 Review View | Document/Span refs、SceneFact root、IdentityResolution revision、scope manifest、ReviewTask revision | 任一 Candidate Head、source hash 或 scope closure 变化即 stale |
| Gate 2 Production World Review View | 精确 StructureIdentitySetVersion、ProductionWorldCandidate 三分区 roots、Gate 2 issue/decision revision | 任一 partition root、Gate 1 ancestry 或 expected business key 集变化即 stale |
| ContinuityLedgerView | 精确 Planning Candidate/Owner refs、AssetState refs、story-time ordering contract | participant/state/claim supersession 或顺序变化即重算；不保存可写 ledger row |
| P0 VisualProductionPackageView | 同一次 Gate 2 的 Bible/Planning/Asset roots、receipts、ready/blocked/stale scopes、Design Gaps | roots 与 receipts 必须同一闭包；任何缺 family、漂移或非法 scope 都拒绝构建 |
| Compiler Owner Collection Query | schema id、精确 scope sets、七个 P0 family 的全部 OwnerCollection 实例与 receipts | 同一读事务重算 collections 和 VerifiedCoverageProof；不命中即 stale/conflict |

P0 Compiler Query 的输入必须包含 `script_source_set`、`project_episode_set`、`bible_structure_identity_set`、`bible_production_world_set`、每个 active Episode 各一份 `planning_scene_set`、条件式 `planning_structure_rebase_set` 与 `asset_identity_state_set`。这是七个 family，不是固定七个 root；正常无 rebase 时仍有空 rebase Collection，因此 Collection 实例总数为 `6 + active_episode_count`，但该空 Collection 没有 Receipt。它按 [0010 的 VerifiedCoverageProof](0010-StoryGraph内容图与DAG创作画布设计.md#storygraph-production-schema-scoped-owner-input-manifest) 计算 p0 scope 集；Candidate、HumanTask、ReviewDecision、ContinuityLedgerView 和 VisualProductionPackageView 都不是 Compiler 输入。

StoryGraph p0 是 Owner Apply 后的可选下游投影，不反向阻塞 Guided Studio 或 VisualProductionPackageView。Storyboard 不能直接读取 Bible/Scene/State 后用 `needs_asset` 补救；它只能在 Gate 4 后消费绑定精确 production StoryGraph 与 Reference bindings 的 `SceneProductionPacket`。

## 14. Scope、局部通过与完整性

完整剧本始终有一个全量分析 coverage root，但用户审核和后续制作可以按闭合 Scene scope 推进：

- `ready_scope_keys`、`blocked_scope_keys` 与 `stale_scope_keys` 显式保存，不能用缺省数组表达；
- 一个 scope 只有在其身份、State、Occurrence、Interaction、跨场连续性和共享 Claim 依赖闭合后才可通过；
- blocker 只阻塞影响闭包；无依赖的 Scene 可以继续到下一 Gate；
- 若共享身份或跨场道具账本连接 ready 与 blocked scopes，闭包必须扩大，不能人为截断；
- 后续不可变版本可以扩大 ready 集，但不能原地改写旧版本；
- StoryGraph p0 编译只取同时拥有 Gate 1、Gate 2 精确 receipts 的 scope，并按 `0010` 的 Coverage Proof 验证其并集；Candidate 自报“完整”不算证明。

`StructureIdentitySetVersion` 可以记录全剧候选覆盖及未决映射，但任何用于 p0 的 scope 都必须在对应 Gate 1 receipt 中已通过。Gate 2 创建的每个正式 Planning Scene 必须逐字节复用 Gate 1 冻结的 `scene_owner_logical_id`，其 Receipt 不得重新派生 scope；不一致以 `scene_scope_identity_mismatch` 拒绝。split/merge/delete 只能通过新 StructureIdentitySetVersion 和 `planning_structure_rebase_set` 显式提供旧 scope → 新 scope 映射。`ProductionBibleVersion` 和 Planning/Asset roots 可以覆盖一个闭合集；未进入该集的 Scene 继续保持可追溯候选，不产生半正式 Owner 对象。

局部通过不放宽 `0010` 的 P0 Collection 激活规则：首次发布 p0 StoryGraph 前，每个 active Episode 都必须已有一份非空且完整的 `planning_scene_set` Collection 及其 Receipt，其他六个 family 也必须满足对应基数。若某个 active Episode 的全部 Scene 都仍被阻断，其他 Scene 仍可完成 Candidate、Gate 2 Owner Apply 和后续 Guided Studio 工作；VisualProductionPackageView 只能明确显示 `package_completeness=partial`，当前项目不能声称 P0 完成或已发布合法 p0 StoryGraph。待该 Episode 形成合法非空 Planning Collection 后，View 才可标记 P0 complete 并允许编译。本文不通过“局部”自行修改 `planning_scene_set` 的 forbidden-empty 策略。

## 15. Candidate Revision、校验与 Repair

Agent Result 一经保存不可修改；Backend 从 Result 创建不可变 Candidate Revision，聚合和 Repair 继续产生新 Revision：

```text
AgentResult
→ CandidateRevision(origin=invocation)
→ aggregate CandidateRevision(origin=aggregate, sorted leaf refs)
→ optional CandidateRevision(origin=repair, parent + allowed key set)
```

确定性校验按依赖顺序至少包括：Schema → Source/Evidence → Coverage → stable key/reference → identity/alias/type → Specification/State → Scene/Occurrence → Interaction/Continuity → Owner target completeness → Canonical Hash。后层不能掩盖前层失败。

Repair Patch 必须绑定 base revision/hash、issue refs、允许修改 keys、只读邻接和预期输出 schema。Backend 拒绝越权字段、未知 key、删除必需对象、伪造 Evidence、跨 scope 偷改和基于旧 Head 的迟到 Patch。应用后只移动 expected Candidate Head，并重跑影响闭包；不允许 Patch 已确认 Owner Version 或已发布 StoryGraphVersion。

## 16. 执行、分片与恢复边界

本文只定义领域 pass，不把它们提前命名为 Stage。`VP-D07` 必须把以下能力映射到一个版本化 `storygraph-stage-wire-production` 和固定 Skill Release：

- source span / scene fact extraction；
- global identity resolution；
- specification/state/scene binding；
- occurrence/interaction/continuity reconciliation；
- deterministic review 与 scoped repair。

运行时边界必须满足：

- Temporal 只驱动 Backend Activity/Command；不直连 Python Harness；
- WorkflowRun/NodeRun 先存在，随后才在精确节点下创建 shard/invocation/result/candidate；
- 一个稳定输入身份只允许一个逻辑 Invocation，重试沿用同一身份；
- 进程中断或调用结果 unknown 时先按 invocation/result 对账，不从头重跑全剧；
- Agent 不保存跨请求 checkpoint，不写 Owner 表，不安装远程 Skill，不从网络 Prompt 获得业务写权；
- Kafka 不作为 Bible Workflow 调度器；Owner outbox 只在事务提交后发布；
- Schema、Skill、Recipe 或模型升级不改历史 Candidate，只有显式新运行产生新 revision lineage。

## 17. 变更、失效与失败路径

| 变化或失败 | 必须处理 | 不应扩大到 |
|---|---|---|
| DocumentRevision 改变 | 重建受影响 SourceSpan、SceneFact、身份/连续性闭包；旧 Gate task stale | 未引用改变区间的已确认历史版本 |
| Scene split/merge | 重算该场、邻接场、mention、Occurrence、Interaction 和跨界 Claim | 无共享依赖的其他 Episode |
| Identity merge/split/rebind | 新 StructureIdentitySetVersion；重算该身份所有 State/Occurrence/Interaction/Binding | 不相关身份 |
| Character/Location/Prop State 改变 | 相关 Occurrence、Ledger、Interaction 和后续视觉目标 stale | 其他身份的基础事实 |
| Interaction 改变 | 对应 Ledger、Scene 和后续组合/Shot stale | 基础 Character/Prop Identity |
| Preset 改变 | Gate 3 以后 Visual Brief/Reference/Storyboard stale | Scene Fact、Identity、Specification、State、Occurrence、Interaction |
| Agent result unknown | 保留 invocation 并对账或同身份恢复 | 新建重复 Owner 事实 |
| 协同 Apply 中任一校验失败 | 单事务回滚，返回 owner-scoped issue | 留下半份 Bible/Planning/Asset |
| receipt 已提交但 Workflow signal unknown | 重放同一 receipt | 再次执行 Owner Apply |
| 调和不收敛 | 保留全部 revisions，进入人工 blocker | 选最后一轮冒充通过 |

所有 stale 都保留旧版本和可追溯输入；“重跑”创建新 Candidate/Owner Version，不原地覆盖。用户在 UI 执行会扩大影响闭包的修改前必须看到预计 stale 范围。

执行状态必须分层：WorkflowRun/NodeRun 只表达运行推进，Candidate Head 只表达当前候选，HumanTask/Decision 只表达审核，Owner Version/Receipt 只表达已提交业务事实，typed View 只表达查询时的 ready/blocked/stale。不得再用一个 `BibleStatus` 同时冒充五类状态。

## 18. P0 完成门与验收场景

P0 Text Production Bible 不生成图片，但必须用一份完整多集剧本和最小反例集证明：

1. Episode/Scene spans 覆盖规范全文，Evidence 可由 Go/Python 按 code point 逐条重建；
2. 每个 RawMentionRef 恰归入一个 identity cluster 或 unresolved，同一角色跨 alias、称谓、换装、伤势和身份揭示仍只有一个 Identity，两个同名角色不会自动合并；
3. Character/Location/Prop State 是完整快照，边界、原因、前后关系和 Design Gap 可审核；
4. 每个正式 Scene 有完整 Dialogue/Beat/Occurrence，实际出现与 mentioned_only 可机械区分；
5. `A 将道具交给 B` 形成一个规范 Interaction、单 holder 账本和正确 PropState 转换；
6. 无因换装、道具瞬移、双 holder、开闭/损坏恢复等只阻塞影响 scopes；
7. Scene/Identity/State/Interaction 的一次修改只重算影响闭包，迟到 shard/patch 不能覆盖新 Head；
8. 四个 P0 checkpoints 和七个 Owner families 的 roots/receipts 可独立对账，重复命令不重复创建；
9. Gate 2 后每个 Occurrence 通过唯一 ProductionBinding 解析到恰一个 Specification 和精确 State；
10. storygraph-production p0 可从 Owner roots/receipts 编译并反查 StructureIdentitySetVersion、ProductionBibleVersion、Scene、Occurrence、Claim、AssetState 与 Evidence；
11. Preset/Style 不出现在 SceneFact 或 Identity Resolution 输入 Hash 中，切换预设不使前两个 Gate 事实 stale；
12. 至少一个无原文视觉细节的对象保留 typed Design Gap，未被模型伪造成 source fact；
13. VisualProductionPackageView 可在不读取 StoryGraph 的情况下展示同一精确生产世界与 scope readiness。

样本长度、集数和具体角色名只作为测试 fixture 的机器统计，不写成产品真理；fixture 改版后必须由测试读取实际 DocumentRevision/coverage root，而不是把旧的 `60 集/139,723 字符` 常量当合同。

Backend 业务测试继续位于 `backend/tests`，Agent Schema/golden/fixture 测试位于 `agent/tests`。本设计接受只证明合同完成，不表示 Wire、数据库或功能已经实现。
