## 结论

Production Bible 是完整剧本的项目级、带证据、可审核的正式叙事上游。它拥有 Evidence、Specification、世界规则和跨集 Claim；它不拥有 Asset 身份/状态/版本，不直接创建 Episode/Scene/Shot，也不等同于 StoryGraphVersion。

```text
DocumentRevision
  → Backend deterministic slices
  → Evidence Candidate Revisions
  → Story Analysis / Reconcile Candidate Revisions
  → deterministic gates + review_storygraph
  → Human Gate
  → Production Bible Owner Confirm
  → immutable ProductionBibleVersion
  → separate MaterializeConfirmedBible Coordinator
      ├── Production Bible: SpecificationVersion / ProductionBinding
      └── Asset: Asset / AssetState
  → Planning Owner / StoryGraph Compiler
```

Agent 只返回 Candidate/Patch；Backend 保存 Stage/Shard/Invocation/Candidate Revision、执行 Gate、确认 BibleVersion 并协调正式 Owner。Kafka 不调度 Bible Workflow；Temporal 是唯一跨步骤持久执行引擎。

## 1. 问题、范围与完成边界

按集独立理解剧本会把别名、阶段形象和跨集关系拆成重复人物或地点，导致后续角色卡、参考资产和 Shot 绑定漂移。完整原稿必须先形成一个项目级 Bible Snapshot，逐集分析只能引用该 Snapshot 中已确认的身份 Key、Specification、AssetState Candidate 和 Claim。

本文定义：

- 全文 Evidence、全局实体/Specification/State/Claim Candidate 的输入输出边界；
- Backend 分片、Candidate Revision、确定性 Gate、Human Gate 和确认语义；
- ProductionBibleVersion 与 Asset/Specification/State 物化的两步 Owner 边界；
- Planning、Storyboard 和 StoryGraph 如何消费已确认 Bible。

本文不定义图片生成、三视图 Provider、Canvas UI、Kafka 通用任务队列、Agent 内 Checkpoint、通用知识图谱或完整媒体生产链。Bible 完成只证明项目级叙事上游已确认，不代表分集、分镜或成片完成。

## 2. 当前事实与演进缺口

| 能力 | 当前代码事实 | 目标缺口 |
|---|---|---|
| Backend Owner | `ProductionBible` GORM Record、Application Service、HTTP、Command Receipt 已存在 | 新增不可变 BibleVersion 与 StoryGraph 所需严格 Fragment Ref |
| Candidate | 当前 JSON 已有 Entity、EntityState、WorldEntry、Evidence、ReviewIssue | 扩展为 Specification、严格 Claim、EvidenceRef 和 StageCandidateRevision |
| Agent | 私有 Runtime 已能受 Grant 调用本地 Codex CLI | 从旧三 Skill 调用迁移到 `build-storygraph` Bundle 的 Stage/Reference |
| Workflow | `activity.production_bible`、Human Gate、Owner Receipt、Temporal 等待/恢复已存在 | 先 Definition/Run/NodeRun，再挂 Stage/Shard/Invocation/Candidate Revision |
| Confirm | 当前 `production_bible.confirm` 只确认 Bible 并返回持久 Receipt | 固定为创建/返回不可变 ProductionBibleVersion，不顺带物化 Asset |
| Asset 物化 | 尚无 Asset Identity/State/Version 与 Bible ProductionBinding 完整实现 | 在确认后的独立 Coordinator 中按需实现 |

现有 `CheckpointStage/CheckpointRevision` 只记录旧执行事实，不能成为新 Harness 的目标模型。新链路的恢复事实是 Workflow NodeRun、ShardManifest、AgentInvocation、StageCandidateRevision/Head 与 Owner Receipt；不建立 Agent 自己的持久流程状态。

## 3. 唯一 Owner 与数据对象

| 对象 | 唯一 Owner | 说明 |
|---|---|---|
| DocumentRevision/Normalized Text | `production/script` | 不可变全文与规范 Hash |
| Evidence Fragment | `production/bible` | 精确指向 DocumentRevision 绝对区间 |
| ProductionBibleVersion | `production/bible` | 已确认的不可变项目级叙事 Snapshot |
| Character/Location/Prop SpecificationVersion | `production/bible` | 稳定叙事规格与证据，不是资产身份 |
| WorldRule/StoryArc/PlotThread/RelationshipClaim/ForeshadowingClaim/PayoffClaim | `production/bible` | 全局与跨集 Claim |
| Asset / AssetState | `asset` | 稳定身份与剧情阶段状态 |
| ProductionBinding | `production/bible` | Bible 物化时 Specification/State 与 Asset 的正式关系 |
| Stage/Shard/Invocation/Result/CandidateRevision | Backend `agent` | 执行与候选谱系，不是正式 Bible 事实 |
| HumanTask/ReviewDecision | `review` | 审核事实，不替代 Bible Owner Apply |
| StoryGraphVersion | `production/storygraph` | 编译已确认 Owner 事实，不拥有 Bible 内容 |

“角色卡”“地点卡”是 Asset、Specification、AssetState、AssetVersion、Claim 与 Evidence 的组合 Query View，不由 Bible 新建第二身份表。

## 4. Evidence 契约

Backend 先 Normalize 原稿并确定性生成不可变 Slice；模型不得自报无法重建的全文坐标。

每个 Evidence Ref 至少冻结：

```text
document_revision_id
normalized_hash
start_code_point / end_code_point   # half-open [start,end)
exact_text
text_hash
episode_marker_hint?
```

门禁必须证明：

1. 区间位于同一 DocumentRevision，使用 Unicode code point，不混用 UTF-8 byte 或 UTF-16 unit；
2. `exact_text` 逐字等于规范全文对应区间，Hash 可由 Go/Python 产生相同结果；
3. Slice 的 active leaf coverage 无缺口、无越界；显式 overlap 被记录且可去重；
4. Entity、Specification、AssetState Candidate 与 Claim 至少有一条直接 Evidence 或一条已确认上游引用；
5. 模型不得用常见套路补写原稿中不存在的动机、关系、伏笔、外貌或场景。

全文很大时，Backend 以 Episode marker、段落/场景边界和技术输入预算生成 ShardManifest。超过预算必须产生新的 Manifest/Tree，不截断 Evidence，也不临时提高上限掩盖失败。

## 5. Bible Candidate Schema

聚合后的 Bible Candidate 只包含下列严格类型：

- `IdentityCandidate`：temporary key、kind、canonical name、aliases、稳定证据；
- `SpecificationCandidate`：character/location/prop 严格联合类型、稳定锚点、功能/约束、Evidence；
- `AssetStateCandidate`：同一 Identity 的完整剧情阶段状态、有效范围、Evidence；
- `WorldRuleCandidate`：规则、作用域、Evidence；
- `StoryArcCandidate` / `PlotThreadCandidate`：跨集范围、关键锚点、Evidence；
- `RelationshipClaimCandidate` / `ForeshadowingClaimCandidate` / `PayoffClaimCandidate`：participant、anchor、valid scope、polarity、status、Evidence；
- `ReviewIssue`：稳定 issue key、severity、scope、subject ref、证据和修复建议。

稳定身份与剧情状态必须分离：同一人物的服装、伤势、伪装、年龄或阵营阶段是 AssetState Candidate，不是第二 Identity。别名只可指向同类型的一个 Identity；冲突必须保留 Issue，不能用字符串相似度自动合并。

人物关系等天然可能成环的语义只产生 Claim Candidate。subject/object/anchor 必须同时存在于严格 Payload 与可校验引用中；Agent 不返回 `character_a → character_b` 的任意 StoryGraph Edge。

## 6. Harness Stage 与恢复边界

Bible 只使用 [3003](3003-StoryGraph剧本解析Harness与内置Skill设计.md) 定义的统一 Bundle Stage：

| Stage | 输入 | 输出 |
|---|---|---|
| `extract_source_evidence` | 一个绝对区间 Slice 与 marker hints | Evidence Observation Fragment |
| `analyze_story` | 有界剧情区间/实体簇与已校验 Evidence | Identity/Specification/State/World/Claim Fragment |
| `reconcile_story` | 同层 Candidate Ref/Hash 的确定性 fan-in | 规范临时 Key 与聚合 Bible Candidate |
| `review_storygraph(scope=bible)` | Candidate Lens/影响闭包与 Gate 结果 | Evidence-scoped Review Issues |
| `repair_candidate` | 当前 Candidate Revision、Issue 与允许修改集 | CandidateRepairPatch |

`extract-bible-evidence`、`reconcile-bible`、`review-bible` 是当前过渡代码事实，不再作为目标 Skill 名或新增入口。实施 SG-I05 时按 `3003` 的原子切换规则迁移到 `agent/skills/build-storygraph`，运行时不能双读旧路径。

WorkflowDefinition 必须先发布并创建 WorkflowRun/NodeRun，之后 Backend 才能在精确 NodeRun 下创建 ShardManifest、Invocation 和 Candidate Revision。每个 `stage_instance_key + shard_key + input_hash` 对应一个稳定 Invocation；Temporal 用 Activity/Timer/Signal 推进宏观节点，Agent 不保存跨请求 Checkpoint。

单个 Invocation 有技术 deadline、调用次数和 Token/费用预算；完整 Bible Workflow 没有用来截断正常任务的固定业务墙钟。进程中断或结果不确定时按原 Invocation/Result 对账，不能从头重跑全部剧本或把 unknown 当作空成功。

## 7. Candidate Revision、Gate 与 Repair

Agent Result 一经保存不可修改。Backend 以它创建不可变 `StageCandidateRevision`；Shard 聚合与 Repair 也创建带完整 origin 的新 Revision，并以 expected Candidate Head Hash 做 CAS。

```text
AgentResult
  → StageCandidateRevision(origin=invocation)
  → aggregate Revision(origin=aggregate, sorted leaf refs)
  → optional Repair Revision(origin=repair, parent hash)
```

确定性 Gate 顺序固定为：Schema → Evidence → temporary key/reference → alias/type → state scope → Claim payload/anchor → coverage → Canonical Hash。存在 blocker 时只能继续有界 Repair 或进入 Human Gate 的“拒绝/要求修改”路径，不能直接确认。

Repair Patch 必须冻结目标 Candidate Revision、允许修改的 Key、Base Fragment Hash 和只读邻接；Backend 应用 Patch 后重跑受影响闭包的全部确定性 Gate 与 review。模型不能 Patch 已确认 ProductionBibleVersion 或已发布 StoryGraphVersion。

## 8. Human Gate 与 Bible Confirm

HumanTask 绑定精确 Candidate Revision ID/Hash、Review Issue 集合和冻结 Rubric。ReviewDecision 只记录审核结论；正向决议必须调用 `production_bible.confirm`。

Confirm 命令至少携带：

- Bible/Candidate Revision ID 与 Hash；
- DocumentRevision ID/Hash；
- expected Bible revision；
- ReviewDecision ID；
- idempotency key。

Backend 重新校验身份、Workspace/Project、Candidate Head、全部 blocker、Evidence 与 expected revision，在一个 GORM 事务中创建不可变 `ProductionBibleVersion`、更新当前 Bible 状态并写 Command Receipt。重复命令返回同一 BibleVersion/Receipt；输入漂移返回冲突。

Confirm **不创建** Asset、AssetState、AssetVersion、Episode、Scene、Shot 或 StoryGraphVersion。Workflow Human Gate 只在 Owner Receipt 已提交后输出精确 `production_bible_version` Ref；Signal 丢失时重放同一 Receipt，不再次确认。

## 9. 确认后的物化

`MaterializeConfirmedBible` 是 Confirm 之后的独立 Backend Coordinator Command。它读取精确 ProductionBibleVersion，并在一个共享 PostgreSQL/GORM 事务中：

1. 为每个确认 Identity 创建或复用唯一 `Asset(kind)`；
2. 由 `production/bible` 发布对应不可变 SpecificationVersion；
3. 由 `asset` 发布一个或多个 AssetState；
4. 写 `ProductionBinding` 与 Command Receipt 中的 temporary key → Owner Ref 映射；
5. 写正式 Owner Outbox，整体提交或整体回滚。

已存在 Identity 只能通过精确 Owner Ref 或已确认人工链接复用；不能按名称近似合并。该步骤不创建视觉 AssetVersion：AssetVersion 需要后续冻结 Specification、AssetState、EffectiveStyleSnapshot，经真实 Generation、Artifact READY、QC 和 CandidateSelection 后发布。

同一 Materialization Command 重试返回同一 Owner Ref 映射；BibleVersion、Identity、Specification、State 或映射漂移时失败关闭。不创建第二数据库、Migration、手写 SQL 或跨 Owner 补偿流程。

## 10. 下游消费与 StoryGraph

Episode 分析与 Storyboard 不能读取“当前最新 Bible”，必须冻结精确 ProductionBibleVersion Ref/Hash：

- `segment_episodes` 只产生边界 Candidate，不创建 Episode；
- `analyze_episode/reconcile_episode` 只引用已物化 Identity/State 与确认的 Bible Snapshot，未知实体进入 Review Issue；
- Planning Owner Apply 后创建 Scene/Dialogue/Beat/Occurrence/集内 Claim；
- Storyboard Draft 只消费相关 Scene/Beat/Occurrence、非空 Specification/AssetState 与 EffectiveStyleSnapshot；
- 缺视觉 AssetVersion 时输出 `needs_asset`，不得用自由文本或“最新资产”继续 Detail；
- StoryGraph Compiler 只在 Bible Confirm 与必要物化/Planning Owner Apply 完成后读取正式 Owner Ref。

ProductionBibleVersion、Specification 和 Claim 通过 Owner Ref 成为 StoryGraph Node；Evidence 通过 `derived_from/supports` 输入边连接。StoryGraph 只投影这些事实，不更新 Bible JSON。

MVP 不为 Bible 单独创建 Kafka Topic 或 Elasticsearch Index；首个真实消费者只监听 `ScriptVersionPublished` 与 `StoryGraphVersionPublished`。Bible 内容在编入 StoryGraph 后通过 StoryGraph 业务索引检索，避免无消费者事件和重复索引事实。

## 11. 状态与失败路径

现有 Bible 运行状态继续使用：

```text
queued → running → needs_review → confirmed
       ↘ failed / unknown / cancelled
confirmed → superseded（新 DocumentRevision 的 BibleVersion 被确认）
```

- Evidence 区间/文本/Hash 不一致：Shard 失败，不产生 Candidate Revision；
- Alias、Identity 或 State 范围冲突：保留 blocker，要求有界 Repair 或人工决议；
- Claim 缺 participant/anchor/evidence 或语义互相冲突：拒绝确认；
- Candidate Head/DocumentRevision 漂移：旧 HumanTask 变 stale，不确认旧 Candidate；
- Agent 结果 unknown：保留 Invocation 与预算事实，按同一 ID 对账；
- Confirm 已提交但 Signal unknown：只重放 Owner Receipt；
- Materialization 部分校验失败：单事务整体回滚，不留下半份 Asset/Specification/State；
- 分集遇到未知实体：创建 Planning/Bible Review Issue，不自动创建 Asset；
- 新 BibleVersion 发布：旧下游保持可追溯，但标记 stale，只有明确重跑才消费新版本。

## 12. MVP 验证

使用完整样本 `He Left Our Kids to Drown—He Didn’t Know I Was the Empress.docx` 验证：

- 60 集边界完整覆盖规范全文的 139,723 个字符；
- Evidence Unicode 绝对区间可由 Go/Python 逐条重建；
- Aurelia、Tristan、Valerie、Jace、Iris 等每个角色只有一个 Identity；
- Aurelia 的 Empress 身份、服装和剧情阶段形成同一 Identity 下的 Specification/AssetState，不产生重复角色；
- 世界规则、关系、伏笔/回收与 Story Arc 全部带 Evidence 和有效范围；
- Candidate 分片/归并/Repair 可恢复，迟到旧 Shard 不能覆盖 Candidate Head；
- Human Gate、Bible Confirm 和 Materialization 是三个可单独对账的 Receipt/状态边界；
- Bible Confirm 不产生 Asset，Materialization 不产生 AssetVersion；
- 代表集的 Occurrence 只能引用已确认并物化的 Identity/State；
- Core StoryGraphVersion 可反查 BibleVersion、Specification、Claim、Evidence 与 Owner Hash。

全部 Backend 测试只位于 `backend/tests`，Agent 契约/golden 测试只位于 `agent/tests`。本文只接受设计，不声明上述缺口已经实现；可执行任务仍以 [0010 的 `SG-Ixx`](0010-StoryGraph内容图与DAG创作画布设计.md#唯一实施任务队列)为唯一顺序。
