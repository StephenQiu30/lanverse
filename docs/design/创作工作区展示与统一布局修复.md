# 创作工作区展示与统一布局修复

## 范围与依据

2026-09-15 用户明确要求：保留注册页原配图，按根 `DESIGN.md` 修正样式；优先修复剧本解析页面内容展示与 ToC 体验；统一 BasicLayout、Header、Footer。此修复沿用已接受的文本创作、人工审阅与正式采纳接口，不改变 Go/Python 所有权、数据库、模型执行和媒体生成流程。

## 当前问题

- BasicLayout 已存在，但认证页重复品牌、主内容和页脚；首页自行覆盖为 1200px，其他页面使用 1440px；固定页眉页脚依赖人工计算高度，长内容与小屏容易挤占阅读空间。
- 阶段提案目录直接显示内部 episode/scene key，难以在多集内容中定位。
- 世界设定把角色、场景、道具、关系和状态平铺；原稿外观证据没有归入对应角色资料，状态没有按同一身份汇总。
- 场景级 issues 没有展示；分镜缺乏可快速定位的索引；数据未到达时缺少解释。
- 全局“任务通知”是无动作按钮；工程术语与多主按钮影响普通创作者判断下一步。
- 单集制作页独立输出 main，没有共享页眉页脚，导致从作品进入剧集后布局脱节；已接入既有 StudioShell，保留单一 main。

## 设计与实施边界

1. 复用现有 BasicLayout / BasicHeader / BasicFooter / LayoutContainer。正文、页眉页脚统一 1200px 容器与响应式边距；正文随文档滚动，不用固定高度补偿。认证作为同一个基础布局的配图变体，保留原图与展示处理；表单使用一致的宽度和控件。
2. 保持已有路由、权限、接口与缓存。创作入口突出导入/继续解析；作品信息与高级技术身份为辅助。移除没有行为的通知入口，不添加假搜索或假素材生成按钮。
3. 创作内容以四阶段目录组织，展示剧集标题、场景标题和待审/已采纳状态；内部 key 只作为确实无法解析时的可追踪降级，不猜名称。同一运行、同一源版本内解析引用，不能混入其他运行结果。
4. 角色、场景、道具分别分组。一个角色资料区汇总名称、出现位置、外观证据、关系、不同场次的状态和视觉参考需求；不把提及次数或状态数算作新角色，不将文本描述伪装成已生成三视图。
5. 保留完整剧集结构、节拍、对白、来源、导演意图、调度、镜头/声音/时间及审核。补齐场景问题、内容目录与明确空态。原文与未知信息不可被“友好文案”隐藏。
6. 审阅、批准、正式采纳仍是原契约，不合并命令、不跳过待确认问题，不自动重跑或调用付费模型。
