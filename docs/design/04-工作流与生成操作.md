## 1. 原则

| # | 原则 | 落地 |
| --- | --- | --- |
| W1 | 工作流只用 Go 编写；工作流代码确定性、无 I/O | 所有 I/O 在 Activity；时间用 `workflow.Now`，随机数不用 |
| W2 | 业务状态以 PostgreSQL 为准 | 每次状态迁移由 `flow` Activity 写库（带期望状态的条件更新）；Temporal 历史只用于恢复流程 |
| W3 | Workflow ID = 业务 ID | 重复启动被拒绝（`WorkflowIdReusePolicy = RejectDuplicate`），天然幂等 |
| W4 | Activity 幂等 | 写库 Activity 使用条件更新（`WHERE status = $expected`）；媒体 Activity 以目标对象键为幂等键；供应商提交用 `provider_request_key` |
| W5 | 付费提交不自动重试 | `provider.submit` 的 `MaximumAttempts = 1`；只有 Activity 明确返回 `not_submitted` 时，工作流才用**同一** `provider_request_key` 再次提交 |
| W6 | 人工决定走 Signal / Update | 用户命令先写库，再发信号；工作流收到后继续 |
| W7 | 任务只写结果字段 | `flow` Activity 只能调用 operation 模块的结果写入端口与 storyboard 的进度端口（REQ-25 R5） |

## 2. 任务队列与 Worker

| 队列 | Worker | 执行内容 | 并发（单实例默认） |
| --- | --- | --- | --- |
| `flow` | `backend-worker`（Go） | 工作流任务；写库、结算、状态迁移、发布 Outbox | 工作流 200 / Activity 100 |
| `media` | `backend-worker`（Go，含 FFmpeg） | 下载接管、探测、转码、缩略图 / 代理、抽帧、裁剪 | Activity 4（按 CPU 核数 / 2） |
| `agent` | `agent-worker`（Python） | LLM Skill、提示词、内容审核、凭据测试 | Activity 32 |
| `agent.<provider>` | `agent-worker`（Python） | 该供应商的 submit / query / cancel | 按 `catalog.provider.concurrency_limit` |

- 按供应商拆队列，使某家限流或故障不阻塞其他供应商（REQ-02 AVL-03）。
- 同一 Go 二进制以 `--role=worker --queues=flow,media` 启动；媒体处理压力大时单独扩 `media` Worker。
- Worker 优雅退出：收到 SIGTERM 后停止拉取新任务，等待进行中的 Activity 最多 5 分钟，长 Activity 依赖心跳超时由其他实例接手。

## 4. 生成操作生命周期

### 4.1 状态机（内部）

```text
draft → quoted ─确认─→ confirmed → submitting → submitted → succeeded → ingesting → completed
  │        └─过期 / 剔除─→ expired          │            │
  │                                          │            ├→ failed
  │                                          └→ unknown → reconciling → submitted | failed | manual
  └ 复用：confirmed ─→ completed（不经过供应商）
任意非终态 ─cancel─→ cancelling → cancelled
manual ─resolve─→ ingesting | failed
```

终态：`completed`、`failed`、`cancelled`、`expired`。进入终态的同一事务内完成结算（§7），`finished_at` 置位，写 `operation_event` 与 Outbox。

### 4.2 状态迁移写库

所有迁移经 `flow.Transition(op_id, from[], to, patch)`：

```sql
UPDATE operation.operation
   SET status = $to, update_time = now(), … patch …
 WHERE id = $id AND status = ANY($from)
RETURNING status;
```

影响 0 行时读取当前状态：若已是 `$to`（重放）则视为成功；否则返回不可重试错误 `illegal_transition`，工作流进入失败分支并告警（说明存在逻辑缺陷）。同一事务写 `operation_event` 与 Outbox `operation.status_changed.v1`。

## 5. 报价（命令层，同步）

报价不在工作流中执行：它是只读计算 + 创建 `quoted` 记录，需要毫秒级响应（REQ-02 PERF-10）。

### 5.1 步骤

```text
Quote(item):
  1. 解析目标：按 target_type 取目标对象当前版本（shot → shot_version；reference_slot → 槽位 + 所属条目；dialogue_audio → 台词当前内容 + 音色 …）
  2. 选模型：item.model_key > 目标版本上的模型 > 项目 default_models[capability]
     校验：模型 active、凭据 active、region 与项目 allow_overseas_models、capability / mode 匹配
  3. 展开输入：InputExpander[target_type](目标版本) → []OperationInput{seq, role, ref_type, ref_id, ref_version, media_asset_id, text}
  4. 校验：InputValidator(model_version.limits, inputs) + ParamValidator(model_version.param_schema, params)
     + 就绪（media ready、moderation passed、授权）+ 前置条件（如 image2video 需选定关键帧）
  5. 组装提示词：PromptComposer（规则模板；用户 prompt_override 优先）→ 作为 role = prompt 的输入
  6. input_hash = sha256(canonical_json({capability, mode, model_profile_version_id, provider_model_id, params_normalized, inputs[], prompt}))
     模型参数表声明了 seed 且本次未指定 → 视为随机，不参与复用（REQ-25 R2）；不支持 seed 的能力（如 TTS）正常复用
  7. 复用：非 force_regenerate 且存在同项目 completed 且 hash 相同 → reused_from_id，quote = 0
  8. 计价：Pricer(price_rule_version 生效版本, mode, params, output_count, 估算用量) → quote_micros、quote_detail
  9. INSERT operation(status = quoted, quote_expires_at = now + 15min, target_version_no, model_profile_version_id, price_rule_version_id)
     + operation_input[]
```

### 5.2 输入展开规则

| target_type | 能力 / 模式 | 展开的输入 |
| --- | --- | --- |
| `reference_slot` | image.generate | prompt（条目描述 + 槽位类型模板 + 风格预设）；style（风格预设参考图）；subject（同造型其他已锁定槽位，可选） |
| `shot_frame` | image.generate | prompt；subject / scene / prop / style（镜头参考组合中的图片项） |
| `shot_take` | video.generate · image2video | first_frame（选定关键帧）；prompt |
| `shot_take` | video.generate · omni_reference | 参考组合全部项（按 seq）；prompt（带指代编号，REQ-28 R4） |
| `shot_take` | video.generate · frames2video | first_frame、last_frame；prompt |
| `dialogue_audio` | audio.tts | prompt（台词文本或发音修正文本）；参数：voice_id、speed、emotion（REQ-29） |
| `voice_preview` | audio.tts | prompt（示例文本）；voice 参数 |
| `episode_split` / `episode_parse` / `bible_extract` / `scene_storyboard` | text.structured | 按 Skill 输入 schema 冻结的结构化输入（原文片段带偏移、设定摘要等），以对象存储快照保存，输入项 `ref_type = text` 指向快照 |
| `free`（画布） | 任意 | 画布节点 `input` 连线的来源 |
| `agent_session` | text.chat | 无输入展开；报价 = 会话 LLM 费用上限（REQ-37 R7），`input_hash` 含会话 ID，不参与复用 |

### 5.3 计价

```text
quantity =
  per_second : clamp_duration(target.duration_ms, model.durations) / 1000 × output_count
  per_image  : output_count
  per_request: 1
  per_1k_chars: ceil(chars / 1000)
unit_price = rule.base_micros × Π multipliers(resolution, mode, 参数命中的系数)

per_1k_tokens 以外的单位：amount = quantity × unit_price
per_1k_tokens（不使用 base_micros 与系数）：
  amount = est_input_tokens / 1000 × rule.input_micros_per_1k + max_output_tokens / 1000 × rule.output_micros_per_1k
  # 报价与预留取输出上限；结算按实际 input / output tokens 用同一公式计算，再按 §7 封顶

quote_micros = ceil(amount × fx_rate_to_cny)   # 境内币种 fx = 1；汇率与取整各只执行一次
```

`clamp_duration`：取模型允许时长中不小于镜头时长的最小值（REQ-27 R3）；无可用值则报价失败。

## 6. 确认（命令层事务 + 启动工作流）

```text
事务 A（失效判定，独立提交）：
BEGIN
  SELECT … FROM operation WHERE id IN (…) AND status = 'quoted' FOR UPDATE
  逐项校验：未过期；目标版本号 = target_version_no；模型版本、价格版本仍为当前生效；冻结输入关联素材的授权未作废（REQ-17，否则原因 consent_revoked）
    （agent_session 额度例外：报价是用户确认的费用上限，不绑定单一模型与价格版本，两字段为空，不做此两项校验；逐次调用的模型与价格版本记在 provider_call，§8.7）
    → 不满足的项：UPDATE status = 'expired'（记录原因）（REQ-21 R4）
COMMIT
  单项确认（/operations/{id}:confirm）时该项失效 → 返回 quote_expired
  批量确认时仍有效的项组成“确认集合”；集合为空 → 返回 quote_expired（附逐项原因）

事务 B（预留与确认，全有或全无）：
BEGIN
  SELECT … FROM operation WHERE id IN (确认集合) AND status = 'quoted' FOR UPDATE
  在锁内按 REQ-21 R4 再次逐项核对：未过期、目标版本号、模型版本、价格版本、关联素材授权未作废（防止事务 A 与 B 之间发生变化；agent_session 额度同事务 A 的例外）
    → 新发现的失效项：UPDATE status = 'expired'（记录原因）并移出确认集合；集合为空 → COMMIT 后返回 quote_expired
  SELECT … FROM billing.budget WHERE project_id = $p FOR UPDATE
  校验：is_overrun = false 且 limit − settled − reserved ≥ Σ 确认集合 quote_micros
    → 否则 ROLLBACK，返回 budget_insufficient（附差额与逐项结果；事务 A 标记的失效项保持 expired；事务 B 中新发现的失效项在回滚后立即以独立事务 C 置为 expired（记录原因），与 REQ-21 R4 一致；其余项仍为 quoted，可剔除后重试）
  INSERT reservation(held) ×n；UPDATE budget.reserved_micros += Σ
  INSERT ledger_entry(reserve) ×n
  UPDATE operation SET status = 'confirmed', confirmed_at, confirmed_by, reservation_id,
         provider_request_key = 'lv-' || id, workflow_id = 'operation/' || id
  单项确认：INSERT outbox(operation.confirmed.v1)；批量确认：UPDATE batch SET status = 'confirmed'，
    total_count = |确认集合|，quote_total_micros = Σ 确认集合 quote_micros（批次计数、进度与金额只按确认集合统计）；
    用户剔除的项与失效项保留 batch_id，status = expired（原因 excluded_by_user / 失效原因），不计入批次统计，仅在批次明细中以“未执行”列出；
    INSERT outbox(batch.confirmed.v1) 一次
    （批内各项不单独发 operation.confirmed.v1）；另 INSERT outbox(audit.recorded.v1)
COMMIT
→ 返回逐项结果（confirmed / expired + 原因）
→ StartWorkflow（单项：OperationWorkflow；批量：BatchWorkflow），失败不回滚
   例外：target_type = agent_session 不启动工作流，确认事务内直接置为 submitted（§8.7）
```

**启动补偿**：`WorkflowStarter` 消费者订阅 `operation.confirmed.v1`（只针对 `batch_id` 为空的单项）与 `batch.confirmed.v1`（针对批次），对“已确认且工作流不存在”的对象再次启动（Workflow ID 去重保证只启动一次）。**`batch_id` 非空的 Operation 永不被补偿器或扫描器单独启动**：其子工作流 `operation/{id}` 只由所属 `BatchWorkflow` 按并发与熔断规则启动；补偿对象是 `batch/{id}`，BatchWorkflow 启动（或 ContinueAsNew）时跳过已存在子工作流的项。因此 API 在提交事务后崩溃也不会丢任务，也不会绕过批次并发控制。

## 7. 结算

```text
Settle(op, actual_cost_micros):     # 在进入终态的同一事务中
  res = SELECT reservation WHERE operation_id = op FOR UPDATE（status = held）
  budget FOR UPDATE
  若按 token 计费（per_1k_tokens）且 actual > res.amount：charge = res.amount，超出部分 overage = actual − res.amount
      由平台承担：写 ledger(provider_overage, overage) 供对账，不计入项目预算（COST-02 以预留上限封顶）
  否则 charge = actual
  budget.reserved -= res.amount
  budget.settled  += charge
  若 settled + reserved > limit：budget.is_overrun = true（事实不可拒绝），发 billing.budget_overrun.v1
  ledger: settle(+charge)、release(res.amount − charge 或 0)
  reservation.status = settled（charge > 0）| released（charge = 0）
  operation.settled_micros = charge
  Outbox(billing.settled.v1 {operation_id, charge, overage, 归集维度})   # 所有终态（completed / failed / cancelled / manual 处理后）统一发出
```

实际费用来源：

| 终态 | actual |
| --- | --- |
| completed | Σ provider_call.cost_micros（按供应商返回用量 × 报价时价格规则计算） |
| failed（供应商明确未扣费） | 0 |
| failed（供应商已扣费，如审核拒绝仍计费） | 按供应商用量 |
| cancelled（未提交） | 0 |
| cancelled（已提交且供应商支持取消） | 供应商返回的已产生用量 |
| 复用 | 0 |
| manual → 人工判定 | 按管理员填写的依据（成功按用量，未执行为 0） |

## 8. OperationWorkflow

### 8.1 流程

```go
func OperationWorkflow(ctx workflow.Context, in OperationInput) error {
    op := exec(flow.LoadOperation, in.OperationID)                    // 状态、模型版本、supports_*、队列
    if op.Status.IsTerminal() { return nil }                           // 重放保护

    if err := exec(flow.CheckConsent, op.ID); err != nil {             // 冻结输入关联素材的授权仍有效（REQ-17）
        return exec(flow.Fail, op.ID, "consent_revoked", false)        // 未提交供应商：actual = 0，释放预留，operation.failed.v1 通知确认人
    }
    if op.ReusedFromID != nil {                                        // 复用分支（REQ-25）
        return exec(flow.CompleteFromReuse, op.ID)
    }
    if op.Capability.IsSynchronous() {                                 // LLM / TTS / 审核等同步型
        return runSynchronous(ctx, op)
    }
    return runAsyncProvider(ctx, op)                                   // 图片 / 视频等异步型
}
```

### 8.2 异步型分支

```text
1. flow.Transition(confirmed → submitting)：同一事务内以 SELECT consent_record … FOR SHARE 复核冻结输入关联素材的授权（与作废事务互斥），
   已作废 → failed(consent_revoked)，未提交、actual = 0、释放预留、通知确认人；同步型分支在调用供应商前执行同一复核；flow.LoadCredential(provider) → 凭据密文（DES-07 §5.2，停用则 credential_disabled）
2. r = agent.<provider>.provider.submit(op, request_key, credential 密文)          MaximumAttempts = 1，StartToClose = 60s
     accepted     → flow.Transition(submitting → submitted, provider_task_id)
     rejected     → flow.Fail(op, code, retryable=false)（参数 / 内容 / 余额类）
     not_submitted→ 等待退避后用同一 request_key 重提，最多 3 次（连接建立前失败、429 且明确未受理）
     unknown      → flow.Transition(submitting → unknown) → 进入对账（§8.4）
3. 轮询循环：
     sleep(backoff)：5s, 5s, 10s, 15s, 30s, 30s …（上限 60s）；收到 provider_callback 信号立即查询
     q = provider.query(provider_task_id)                           Retry：指数退避，最多 10 次，非重试错误：not_found
       pending / running → 继续；更新进度（节流：进度变化 ≥ 10% 或 30s 才写库）
       succeeded         → flow.Transition(submitted → succeeded, usage, result_urls)
       failed            → flow.Fail(op, provider_error)
       not_found         → 进入对账
     总时长超过 expected_max_ms × 2 → 进入对账（REL-10）
4. flow.Transition(succeeded → ingesting)
5. 对每个 result_url 并行：media.Ingest(op, seq, url)                StartToClose = 10min，心跳 15s，重试 ≥ 5 次（只重试下载，不重提）
     下载 → 类型识别 → ffprobe → 按需转码到项目规格 → sha256 → 写对象存储 → 派生版本（缩略图 / 代理）
     → 登记 media_asset(origin = generated, provider, model, region) 与 operation_output(moderation = pending)
6. 审核（按模型 moderation 配置）：agent.moderation.check(output)   失败重试 3 次；仍失败 → 输出保持 pending 并告警，
     Operation 停留在 ingesting，工作流用持久计时器每 10 分钟重试审核；全部输出得到 passed / rejected 后才进入第 7 步；
     24 小时仍无法审核 → 输出置为 rejected（原因 moderation_unavailable），Operation 以 failed（failure_code =
     moderation_unavailable，retryable = true）结束，按供应商实际费用结算（§7），发 operation.failed.v1 通知确认人；
     批次计为失败，可在审核恢复后对该项重新报价。pending 输出不可选定（REQ-22），批次只在 Operation 终态后计数
7. 至少一个输出审核通过（或全部因内容被拒绝）→ flow.Complete(op)：status = completed + 结算（§7）+ Outbox(operation.completed.v1)；
   全部输出因内容被拒绝时 completed 但无可选候选，界面显示拒绝原因
```

### 8.3 同步型分支

```text
1. flow.Transition(confirmed → submitting)
2. r = agent.llm.run_skill / agent.provider.tts / …                 StartToClose = 按 Skill 声明（默认 10min），心跳 30s
     Harness 内部完成调用 → 校验 → 修复（≤ 2 轮）；返回结构化结果、trace、usage
     Activity 重试策略：仅对“确定未计费”的错误重试（网络在请求发出前失败、供应商 5xx 且声明不计费）；最多 2 次
3. 媒体结果（TTS 音频）→ media.Ingest；结构化结果 → flow.ApplyStructuredResult（写候选：episode_structure / bible 候选 / 分镜候选 …）
4. flow.Complete(op)
```

LLM 调用在超时后的状态也可能是“已计费但无结果”：按 token 计费的请求不做对账（供应商无查询接口），按实际计费结算为“预留上限”并标记 `failed(unknown_charge)`，由每日与供应商账单对账修正（REQ-32 R2 `adjust`）。

### 8.4 对账（unknown / not_found / 超时）

```text
flow.Transition(→ reconciling)
if model.supports_query:
    for attempt in 1..6（间隔 1m, 5m, 10m, 20m, 30m, 50m，累计约 2 小时）:
        q = provider.query(by request_key 或 provider_task_id)
        found → 回到轮询（§8.2 第 3 步）
        confirmed_not_exist（供应商明确“无此任务”且已超过其受理窗口）→ flow.Fail(retryable=true, charge=0)
    仍无法确定 → manual
else:
    flow.Transition(→ manual)；Outbox(operation.manual.v1) → 通知管理员
    等待 resolve_manual 信号（无超时；24h 未处理告警）
      succeeded(provider_task_id) → 以该 ID 查询 / 下载 → 接管 → completed
      not_executed → failed，actual = 0
```

### 8.5 取消

```text
收到 cancel 信号：
  状态 confirmed / submitting 前 → flow.Cancel(actual = 0)
  已 submitted：
    supports_cancel → provider.cancel → 成功：flow.Cancel(actual = 供应商用量)；失败：记录“取消未生效”，继续轮询
    不支持 → 标记 cancel_requested，继续执行到结束；结果照常入库（已付费）
  ingesting 之后 → 不取消（结果已付费），完成后照常入库
```

取消使用 Temporal Update（`cancel`）以便同步返回“已取消 / 取消请求中”。

### 8.7 对话式 Agent 会话费用（REQ-37 R7）

会话费用的 Operation（`target_type = agent_session`，下称“额度”）不走 OperationWorkflow。规则：**一个会话同一时刻只有一个当前额度；每次运行只属于一个额度；额度各自结算，不做跨额度分摊。**

```text
开启会话：创建 agent.session(status = active) 与额度 Operation(quote = 会话上限) → quoted
确认（§6）：预留 = 上限；Operation confirmed → submitted（不启动工作流）；session.current_operation_id = 该额度

每次运行（Go 在调用 agent-api 前，一个事务）：
  SELECT session FOR UPDATE（status 必须为 active）；SELECT 当前额度 Operation FOR UPDATE
  剩余 = quote − Σ agent.run.cost_micros（finished）− Σ agent.run.run_cap_micros（running 与 abandoned，作为占用）
  run_cap = min(剩余, 单次运行上限)；run_cap ≤ 0 → 拒绝运行，提示对新额度报价确认
  INSERT agent.run(session_id, operation_id = 当前额度, run_cap_micros, status = running, started_at)
  把 run_id 与 run_cap 传给 agent-api；Harness 在每次模型调用前把最大可计费用限制在剩余 run_cap 内（DES-05 §3.6）
逐次调用记账（运行过程中，先登记后调用；每一次模型调用含工具结果返回后的续写，DES-05 §3.6）：
  ① 调用前：agent-api POST /internal/agent/runs/{run_id}/calls {call_seq, model_profile_version_id}
     Go 一个事务：SELECT agent.run FOR UPDATE（status 须为 running，行锁使同一 run 的登记串行）
       call_seq ≤ run.last_call_seq → 返回已有登记（重试幂等）；call_seq ≠ last_call_seq + 1 → 拒绝
       request_key = "{run_id}:{call_seq}"；INSERT provider_call(action = llm, operation_id = 该额度, run_id, call_seq, request_key,
         model_profile_version_id, price_rule_version_id = 当前生效版本, outcome = unknown, cost_micros = NULL)；last_call_seq = call_seq
     返回 request_key 与剩余可计费用；登记成功后 agent-api 才发起模型调用，并把 request_key 作为供应商请求的客户端请求标识传递
     （供应商支持的请求元数据 / 用户标识字段，出现在其用量账单明细中）
  ② 调用返回后：PUT /internal/agent/runs/{run_id}/calls/{call_seq} {usage}（重试至成功）→ 按 (run_id, call_seq) 更新该行
     usage、cost_micros = 用量 × 登记时价格版本、outcome = ok（已为 ok 则幂等返回）
  已登记的调用明细不受后续进程崩溃影响；任何已发出的调用都至少有一条 unknown 登记
运行结束（agent-api 报告结束，一个事务，按 run_id 幂等）：
  agent.run.cost_micros = Σ 该 run 的 provider_call.cost_micros（全部为 ok 时；仍有 unknown 的调用则按中断处理），status = finished
运行中断（agent-api 超时、进程崩溃、结束写库失败）：
  agent-session-settle 每小时（及关闭时）扫描 running 超过 15 分钟的 run → status = abandoned，cost_micros 为空；
  已为 ok 的调用明细保留；仍为 unknown 的调用即未知费用；其 run_cap 继续作为该额度的占用，直到费用确定；
  迟到的 ② 回调仍按 (run_id, call_seq) 幂等写入；全部调用确定后 run → finished
  每日对账按 request_key 与供应商账单明细匹配，补写未知调用的用量与费用；
  供应商账单不含请求标识或 30 天内仍无法匹配 → 保留暂估，进入对账差异（billing.reconciliation_diff.v1），
  由管理员人工核对后以 ledger:adjust 处理（只退不补）
追加额度：对新上限创建新的额度 Operation（target_id = 同一会话）→ 用户确认后，同一事务：
  旧额度标记为“待结算”（不再接受新运行），session.current_operation_id = 新额度
  旧额度在其 running 运行全部 finished / abandoned 后结算（见下方“额度结算”）
会话结束（用户关闭，或闲置 24 小时）：session.status = closing（拒绝新运行）→ 当前额度的运行全部结束或被判为 abandoned
  → 额度结算 → session.status = closed
额度结算：actual = Σ 该额度 finished 运行的 cost_micros + Σ abandoned 运行的 max(run_cap_micros, 该 run 已确定调用费用之和)
  （未知调用按用户已确认的单次占用暂估，Operation 标记 cost_estimated）→ Settle(额度, actual)（§7：按 token 计费，结算金额 = min(actual, 预留)，
  超出部分记 provider_overage 并由 billing.settled.v1 一并发出）→ completed
暂估修正（每日与供应商账单对账，该额度全部 run 的费用均已确定后，一个事务，按 operation_id 幂等）：
  SELECT operation FOR UPDATE（cost_estimated = true）；budget FOR UPDATE
  actual' = Σ provider_call.cost_micros（按 operation_id，已全部确定）
  charge' = min(actual', 首次结算金额 operation.settled_micros)     # 以整个额度重算；只退不补，不向用户多收
  overage' = actual' − charge'
  Δcharge = charge' − settled_micros（≤ 0）；Δoverage = overage' − 已记 provider_overage 合计
  ledger: adjust(amount = Δcharge，有符号，退款为负)、provider_overage(amount = Δoverage，有符号，可为负以冲回)
  budget.settled += Δcharge；重新判定 is_overrun；operation.settled_micros = charge'；cost_estimated = false
  Outbox(billing.ledger_adjusted.v1 {operation_id, Δcharge, Δoverage, 归集维度})，billing-report 据此重算 cost_summary
  例：预留 100，已知 90，中断暂估 30 → 首次结算 用户 100、平台 20；中断实际为 0 → actual' 90，charge' 90，overage' 0：退用户 10，冲回平台 20
对账等式：每个额度 Operation 的供应商实际费用 = Σ provider_call.cost_micros（按 operation_id，全部确定后）= settled_micros + Σ provider_overage
```

## 9. BatchWorkflow

```text
输入：batch_id、operation_ids[]
并发：semaphore = min(项目并发上限 20, 供应商剩余配额)；每项启动子工作流 operation/{id}
      ParentClosePolicy = ABANDON；子工作流完成后回调父工作流（ChildWorkflowFuture）
熔断：连续 5 个子项以同类错误（规范化后的相同供应商错误码，REQ-23）失败 → 暂停启动新子项，flow.PauseBatch(reason) → 通知；等待 resume / cancel 信号
cancel：未启动项 → flow.Cancel(actual = 0)；已启动项 → 向子工作流发 cancel
结束：flow.FinishBatch(汇总计数) → Outbox(batch.finished.v1)
事件历史：每启动 100 个子项执行一次 ContinueAsNew（单批上限 300 项，REQ-23 R1），状态携带未完成子项列表
```

## 12. 供应商并发与限流

- **并发**：`agent.<provider>` 队列的 Worker 设置 `MaxConcurrentActivityExecutionSize = provider.concurrency_limit / worker 实例数`。
- **速率**：`agent-worker` 在 submit 前向 Redis 令牌桶申请（`quota:{provider}`，速率 = `rate_limit_per_min`）；拿不到令牌时 Activity 返回可重试错误 `rate_limited_local`（不计入 submit 的“1 次”，因为请求尚未发出）。
- **项目公平性**：BatchWorkflow 的并发上限避免单个项目占满供应商配额。
- **429**：供应商返回 429 且明确未受理 → `not_submitted`，工作流退避重提（§8.2）。

## 14. 版本演进与测试

- **工作流代码变更**：使用 `workflow.GetVersion` 标记分支；删除旧分支前确认无在途工作流（Temporal 可见性查询）。
- **回放测试**：CI 保存各工作流的典型历史（成功、unknown→对账、取消、manual、批量熔断），每次变更执行 `worker.ReplayWorkflowHistory`。
- **单元测试**：Temporal Go testsuite 模拟 Activity，覆盖 §4.1 全部迁移。
- **集成测试**：testcontainers（PostgreSQL、Redis）+ Temporal dev server + 模拟供应商（REQ-02 DEP-06）。
- **故障注入矩阵**：

| 注入 | 期望 |
| --- | --- |
| submit 超时但供应商已受理 | unknown → 对账找到 → completed；账本 1 次 |
| submit 超时且未受理 | 对账确认不存在 → failed(retryable)，费用 0 |
| 供应商不支持查询 + 超时 | manual → 管理员处理 → 正确结算 |
| 轮询期间 Worker 崩溃 | 其他实例继续，无重复提交 |
| 接管下载失败 3 次 | 仅重试下载，最终 completed |
| 确认事务提交后 API 崩溃 | workflow-starter 补偿启动一次 |
| 重复回调 / 乱序回调 | 状态单调，结果只入库一次 |
| 批量中连续 5 项同错 | 熔断暂停并通知 |
