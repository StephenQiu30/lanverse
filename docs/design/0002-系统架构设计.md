# 0002 系统架构设计

- 状态：草案，待评审
- 日期：2026-09-25
- 依赖：[0001 产品定义与需求分析](0001-产品定义与需求分析.md)
- 范围：领域模型、系统组成、模块边界、关键流程、数据存储、失败路径、画布架构、安全与可观测
- 非范围：具体库与版本（见 0003）、排期（见 0004）

## 1. 结论

1. **一个业务后端（Go，模块化单体）掌握全部正式事实**；AI 执行层（Python）和媒体处理层只做计算，不写业务数据库。
2. **Temporal 是唯一的流程编排者，工作流用 Go 编写**。Python AI Worker 和媒体 Worker 作为 Temporal Activity Worker，监听各自的任务队列。这样一个流程只有一个状态机 Owner，不需要在服务之间来回回调。
3. **所有产物都有版本和来源**：AI 结果先是候选，人工选定后才被正式对象引用；每个产物记录由哪些上游版本生成，用于影响分析和依赖传播。
4. **画布是视图，不是事实源**：画布只保存布局，节点通过 ID 引用业务对象；所有修改表达为命令，服务端用 revision 做乐观锁。
5. **MVP 不引入 Kafka、Elasticsearch、微服务和图数据库**；需要时通过已定义的边界平滑加入。

## 2. 领域模型

### 2.1 限界上下文

| 上下文 | 职责 | 核心对象 |
| --- | --- | --- |
| identity | 账号、登录、会话 | User、Session |
| workspace | 组织、项目、成员、权限、项目设置 | Organization、Project、Member、StylePreset |
| script | 剧本导入与结构 | ScriptVersion、Episode、Scene、DialogueLine |
| bible | 设定集与参考资产 | Character、Look（造型）、Location、Prop、ReferenceSlot |
| storyboard | 分镜 | Shot、ShotReference |
| media | 媒体文件登记、上传、探测、缩略图 | MediaAsset、MediaRendition |
| generation | 生成任务、供应商调用、候选 | GenerationJob、ProviderCall、Candidate |
| review | 阶段确认、选定、打回、批注 | Gate、Decision、Comment |
| edit | 时间线与渲染 | EditPlan、TimelineClip、Render |
| delivery | 成片版本与导出 | Delivery |
| billing | 价格、预算、预留、账本 | PriceBook、Budget、Reservation、LedgerEntry |
| canvas | 画布布局与命令 | CanvasDocument、CanvasNode、CanvasEdge |
| lineage | 产物依赖与过期传播 | ArtifactRef、Dependency、StaleMark |

`lineage` 是横切能力：各上下文在产生新版本时登记依赖，lineage 负责计算影响范围，不拥有任何业务对象。

### 2.2 核心关系

```text
Organization ─< Project ─┬─< ScriptVersion
                         ├─< Episode ─< Scene ─┬─< DialogueLine
                         │                     └─< Shot ─┬─ selected_frame  → Candidate
                         │                               ├─ selected_take   → Candidate
                         │                               └─< ShotReference  → Look / Location / Prop 的锁定版本
                         ├─< Character ─< Look ─< ReferenceSlot ─ selected → Candidate
                         ├─< Location / Prop ─< ReferenceSlot
                         ├─< GenerationJob ─< ProviderCall
                         │                 └─< Candidate → MediaAsset
                         ├─< EditPlan ─< TimelineClip ─ → Shot.selected_take / 音轨 / 字幕
                         ├─< Delivery → Render → MediaAsset
                         ├── Budget ─< Reservation / LedgerEntry
                         └── CanvasDocument ─< CanvasNode(ref_type, ref_id) / CanvasEdge
```

### 2.3 建模规则

1. **版本不可变。** ScriptVersion、Look、Shot、EditPlan 等以“对象 + 版本号”存储；修改产生新版本，旧版本保留。引用一律指向具体版本。
2. **候选与正式分离。** Candidate 是 AI 或上传产生的结果；正式对象通过 `selected_*_candidate_id` 引用它。选定是一次显式命令，带 `expected_version`，防止旧页面覆盖新选择。
3. **输入快照。** 每个 GenerationJob 冻结输入：所引用的版本 ID 列表、提示词、参数、模型，以及它们的内容 hash。相同 hash 的已成功任务可以复用（缓存命中不重复付费）。
4. **依赖显式登记。** 产生新版本时写入 `lineage.dependency(downstream, upstream)`。上游出新版本时，lineage 递归查找下游并标记 `stale`，只标记，不触发生成。
5. **单一 Owner。** 每个字段只由一个上下文写入。例如“镜头用哪个片段”只由 storyboard 写入，画布和工作流都不能另存一份。

## 3. 系统组成

```text
┌──────────────────────────────── 浏览器 ────────────────────────────────┐
│ Web 应用：流水线视图 / 画布 / 审阅 / 时间线                                │
└────────────┬──────────────────────────────────────────▲─────────────────┘
             │ HTTPS REST（OpenAPI）                     │ SSE（项目事件流）
             │ 直传：预签名 URL ──────────────────────┐   │
┌────────────▼──────────────────────────────────────┐ │   │
│ Go API 进程（模块化单体）                           │ │   │
│  鉴权 · 租户上下文 · 各上下文 HTTP Adapter           │ │   │
│  应用用例 · 事务 · Outbox · SSE 推送                 │─┼───┘
└───────┬───────────────────┬─────────────────────────┘ │
        │ 启动/信号/查询       │ SQL                       │
┌───────▼────────┐   ┌───────▼────────┐        ┌────────▼────────┐
│ Temporal        │   │ PostgreSQL      │        │ 对象存储 + CDN    │
│ (流程状态)       │   │ (全部业务事实)    │        │ (媒体字节)        │
└───┬───────┬────┘   └────────────────┘        └─────────────────┘
    │任务队列 │                                           ▲
┌───▼───┐ ┌─▼─────────────┐ ┌──────────────────┐          │
│Go 编排 │ │Python AI Worker│ │Go 媒体 Worker     │──────────┘
│Worker  │ │ 队列: ai        │ │ 队列: media        │
│队列:    │ │ LLM / 生图 /     │ │ 下载接管 / ffprobe │
│flow    │ │ 生视频 / TTS     │ │ 转码 / 合成 / 标识  │
└────────┘ └───────┬────────┘ └──────────────────┘
                   │ HTTPS
            外部模型供应商 · 内容审核服务
            Redis：限流、SSE 跨实例广播、短期缓存
```

### 3.1 进程与职责

| 进程 | 语言 | 职责 | 不负责 |
| --- | --- | --- | --- |
| api | Go | 公共 REST API、鉴权、业务命令与查询、事务、Outbox、SSE | 长时间计算、调用模型 |
| flow-worker | Go | Temporal 工作流定义（业务流程）；写库的 Activity（登记候选、结算费用等） | 调用模型、处理媒体字节 |
| ai-worker | Python | Activity：LLM 结构化解析与校验修复、生图 / 生视频 / TTS 供应商调用、内容审核调用 | 写业务数据库、决定业务状态 |
| media-worker | Go | Activity：下载供应商结果、ffprobe 探测、缩略图、转码、合成、写入 AIGC 标识 | 业务决策 |

api 与 flow-worker 是同一个 Go 代码库、同一个二进制，用启动参数区分角色；MVP 可以在一个进程内同时运行。ai-worker 与 media-worker 按队列长度独立扩容。

### 3.2 为什么这样划分

- **单一流程 Owner**：Go 工作流决定“下一步做什么”；Python 只接收冻结输入、返回结构化结果。避免两个服务各自维护同一任务的状态机。
- **Python 只做 Python 擅长的**：模型 SDK、结构化输出、评估工具生态都在 Python。
- **媒体处理用 Go + FFmpeg 子进程**：CPU 密集、需要独立扩容和资源隔离，与 AI 调用的扩缩容节奏不同。
- **不拆微服务**：一个小团队维护一个事务边界清晰的单体最快；模块边界靠代码结构和依赖检查保证，将来按需拆分。

## 4. Go 后端内部结构

```text
backend/
  cmd/lanverse/                 # 单一入口：--role=api|flow|media|all
  internal/
    app/                        # 组合根：装配依赖、生命周期
    <上下文>/                   # identity、workspace、script、bible、storyboard、media、
      domain/                   #   generation、review、edit、delivery、billing、canvas、lineage
      application/              # 用例、事务边界、消费方接口
      adapter/
        http/                   # Handler（由 OpenAPI 生成的接口实现）
        postgres/               # 仓储实现（sqlc 生成的查询）
        temporal/               # 工作流与 Activity（仅 generation、script 等需要编排的上下文）
    platform/                   # 数据库连接、事务、Outbox、SSE Hub、对象存储客户端、鉴权中间件
  api/openapi.yaml              # 公共接口契约（唯一事实源）
  db/migrations/                # 版本化 Schema 迁移
  db/queries/                   # sqlc 查询
```

规则：

1. 依赖方向 `adapter → application → domain`，内层不引用外层。
2. 上下文之间只通过对方 application 层公开的接口协作，不读取对方的表。
3. `platform` 只放基础设施，不放业务逻辑；不设 `utils`、`common`。
4. 事务在 application 层开启；一个用例一个事务；跨上下文的后续动作通过 Outbox 事件或工作流步骤完成。

## 5. 关键流程

### 5.1 剧本解析（阶段 1–3）

```text
用户上传 → api: 登记 ScriptVersion（hash）→ 启动工作流 ParseScript(scriptVersionId)
  ① ai: 分集分场（LLM，结构化输出 + 原文位置校验，失败有限次修复）
  ② flow: 写入候选解析结果 → 创建 Gate(解析确认) → 等待人工决定（Signal）
  ③ 用户审阅/修改 → api: 提交 Decision → Signal 工作流
  ④ flow: 将确认后的结果写为正式 Episode/Scene/DialogueLine
  ⑤ ai: 资产抽取 → flow: 候选设定集 → Gate(资产确认) → 等待 → 正式 Character/Look/Location/Prop
```

- LLM 输出必须带原文位置（段落 / 字符偏移），程序校验“引用的原文确实存在”；校验失败走修复，超过次数则明确失败，不静默截断。
- 长剧本按集分块处理，每块独立重试；全局身份合并（别名）作为单独一步在分块结果之上执行。

### 5.2 生成任务（阶段 4、6、7、8 共用）

**状态机：**

```text
draft → quoted → confirmed(已预留费用) → submitted → running → succeeded → ingested → candidates_ready
                                          │            │
                                          │            ├→ failed(retryable | final) → 释放 / 结算
                                          └→ unknown(提交超时 / 响应丢失) → reconcile → running | succeeded | failed
任意非终态 → cancelling → cancelled
```

**时序：**

1. **报价**：api 根据目标（如 Shot v3 的关键帧）、引用的锁定参考版本、模型单价计算报价；冻结输入快照并计算 `input_hash`。若同一 `input_hash` 已有成功任务，直接返回已有候选（不收费）。
2. **确认**：用户确认后，api 在**同一事务**内：预留费用（Reservation）、创建 GenerationJob、写 Outbox；随后以 `job_id` 作为 Temporal WorkflowID 启动工作流（天然幂等，重复启动会被拒绝）。
3. **提交**：ai-worker 调用供应商。请求前先生成 `provider_request_key` 并由 flow 持久化；供应商返回的任务 ID 同样持久化。
4. **等待**：优先使用供应商回调（经 api 验签后 Signal 工作流），同时以轮询兜底；工作流用 Temporal 定时器等待，不占用 Worker。
5. **接管**：media-worker 下载结果到自有对象存储，ffprobe 核验格式、尺寸、时长，生成缩略图，登记 MediaAsset；只有接管成功才算 `ingested`。
6. **候选**：flow 写入 Candidate，推送 SSE；按实际用量结算费用、释放多余预留。
7. **选定**：用户选定后，storyboard 等 Owner 更新正式引用（带 `expected_version`），lineage 将下游标为 stale。

**关键约束：**

- **`unknown` 状态不允许直接重试**：先用 `provider_request_key` 或供应商任务 ID 查询；供应商不支持查询时，标记人工处理，不自动重买。
- 下载失败只重试下载；供应商结果链接过期则标记失败并说明，不自动重新生成。
- 批量生成（整场 / 整集）是父工作流按镜头启动子工作流，单镜失败不影响其他镜头。

### 5.3 依赖传播与局部重做

1. 用户选定 Look v4 → lineage 查询所有引用 Look v3 的 ShotReference → 相关 Shot 的关键帧、片段、所属 EditPlan 标为 `stale`。
2. 前端展示影响清单：受影响镜头数、每镜当前状态、重做预估费用。
3. 用户勾选要重做的镜头 → 批量报价 → 确认 → 按 5.2 执行。
4. 未重做的镜头保留旧结果并持续显示“过期”，导出时提示但不阻止（由用户决定）。

### 5.4 剪辑与渲染（阶段 9–10）

1. **自动粗剪**：按分镜顺序排列各镜 `selected_take`，按台词音频时长对齐，生成 EditPlan v1。
2. **编辑**：用户调整顺序、入出点、字幕后产生新 EditPlan 版本。
3. **渲染前校验**：所有片段已选定且 ingested、音轨与字幕时码不越界、输入版本未漂移；否则阻止渲染并列出原因。
4. **渲染**：media-worker 统一转码到项目输出规格（分辨率、帧率、编码、响度）后合成；写入显式标识（角标 / 片尾）与隐式标识（元数据）。
5. **质检**：对成片完整解码，核对时长、音画流、分辨率；通过后登记 Delivery，并附清单（引用的全部版本与 hash、渲染器版本）。
6. 修改后重新渲染产生新 Delivery，旧成片保留。

### 5.5 实时推送

- 业务事务写 Outbox → api 内的发布器读取 Outbox → 发布到 Redis 频道 `project:{id}` → 各 api 实例的 SSE Hub 推送给订阅该项目的浏览器。
- 事件只携带“什么对象变了、新版本号”，前端据此让对应查询失效并重新拉取；不通过事件传递完整业务数据。
- SSE 断线重连使用 `Last-Event-ID`；超出保留窗口则前端全量刷新。

## 6. 画布架构

### 6.1 两种视图，一份数据

| 视图 | 用途 | 数据 |
| --- | --- | --- |
| 流水线视图 | 按阶段推进、批量生产（MVP） | 直接读写业务对象 |
| 画布视图 | 自由布局、可视化依赖、局部实验（V1） | 业务对象 + CanvasDocument 布局 |

### 6.2 四种数据权威

| 数据 | Owner | 存储 |
| --- | --- | --- |
| 业务事实（镜头、角色、候选、选定） | 各业务上下文 | PostgreSQL |
| 画布布局（坐标、尺寸、分组、注释连线、便签） | canvas 上下文 | PostgreSQL |
| 执行状态（排队、运行、失败、未知） | generation + Temporal | PostgreSQL（投影） |
| 临时交互（选中、拖拽、视口） | 浏览器 | 内存 |

### 6.3 节点与连线

- **节点**：`{id, kind, ref_type, ref_id, x, y, w, h, group_id, style}`。`kind` 分为数据节点（引用 Shot / Character / Look / MediaAsset）、生成节点（引用 GenerationJob 或生成配置草稿）、注释节点（便签、分组框）。
- **连线**：分两类。`dependency` 连线表示真实数据依赖，由业务关系派生（如 Shot → Look），用户在画布上连线等价于调用业务命令（如“为该镜头添加参考”）；`annotation` 连线只是视觉注释，不参与计算。
- **端口有类型**（text、image、video、audio、character_ref、location_ref），连线时前后端都校验兼容性。

### 6.4 命令与同步

- 所有画布修改都是命令：`AddNodes`、`MoveNodes`、`ResizeNode`、`DeleteNodes`、`Group`、`Ungroup`、`Connect`、`Disconnect`、`UpdateStyle`。
- 前端乐观应用命令，并写入本地撤销栈；批量提交到 `POST /projects/{id}/canvas/commands`，带 `expected_revision` 和幂等键。
- 服务端校验权限与引用合法性，按序应用，revision + 1；冲突返回 409 和最新文档，前端基于最新文档重放本地未确认命令，无法重放的提示用户。
- 拖拽过程只更新本地，松手时提交一条 `MoveNodes`。
- 涉及业务的命令（如 dependency 连线、删除镜头）不由画布上下文直接执行，而是调用对应业务上下文的用例；画布只记录布局结果。

### 6.5 画布上的生成与 AI 助手

- 生成节点点击“运行”→ 走 5.2 的报价 → 确认 → 执行流程；节点状态由 SSE 驱动。
- AI 助手（V2）只产出**提案**（一组画布命令 + 可能的生成意图），前端展示差异，用户确认后由服务端应用；助手不能直接发起付费生成。

## 7. 数据存储

| 数据 | 存储 | 说明 |
| --- | --- | --- |
| 业务实体、版本、依赖、画布、执行投影、账本 | PostgreSQL | 一个库，按上下文分 schema；依赖图用关系表 + 递归 CTE |
| 模型调用明细 | PostgreSQL 分区表 | 量大后归档到对象存储或列式库 |
| 工作流历史 | Temporal 自身存储 | 不作为业务事实源；业务状态以 PostgreSQL 为准 |
| 媒体字节 | S3 兼容对象存储 + CDN | 数据库只存 key、hash、元数据；按项目前缀隔离 |
| 限流、SSE 广播、短期缓存 | Redis | 丢失可恢复，不存事实 |
| 全文检索 | PostgreSQL 全文检索 | 规模上来后再评估独立搜索引擎 |
| 语义检索（V1 以后） | pgvector | 不预先引入独立向量库 |

**媒体上传：** 前端向 api 申请预签名 URL → 直传对象存储 → 通知 api 完成 → media-worker 探测并生成缩略图 → MediaAsset 变为 ready。未 ready 的媒体不能被引用。

**媒体访问：** 缩略图与预览通过 CDN 短期签名 URL；多个尺寸（如 256 / 1024 / 原图）由 media-worker 预生成，画布按缩放级别选择。

## 8. 失败路径

| 场景 | 行为 |
| --- | --- |
| 供应商提交超时 / 响应丢失 | 进入 `unknown`，用请求键 / 任务 ID 对账；不支持查询则转人工，不自动重买 |
| 供应商限流 | 按供应商配额排队（Temporal 重试 + 退避）；前端显示排队中 |
| 供应商成功但下载失败 | 只重试下载；链接过期则失败并说明 |
| 结果格式不符（非视频、时长为 0） | 接管失败，不产生候选，按供应商策略结算并提示 |
| LLM 输出不合法 | 有限次修复；仍失败则该步骤失败，保留原始输出供排查 |
| 用户在旧页面选定候选 | `expected_version` 不匹配返回 409，前端刷新 |
| 服务重启 / Worker 崩溃 | Temporal 从历史恢复；Activity 幂等（先查已有结果再执行） |
| 预算不足 | 报价阶段拒绝，提示预算与差额 |
| 用户取消 | 支持取消的供应商同步取消；已发生费用按实际结算 |
| 内容审核不通过 | 输入侧阻止提交；输出侧候选标记为不可用，不计入可选 |
| 画布并发编辑冲突 | 409 + 最新文档，前端重放本地命令 |

## 9. 安全

- **鉴权**：会话 Cookie（HttpOnly、SameSite）；每个请求解析组织与项目权限，application 层做授权判断。
- **租户隔离**：所有表带 `project_id` / `org_id`，仓储查询强制带租户条件；对象存储按项目前缀并用短期签名。
- **密钥**：供应商密钥存于 KMS / 加密配置，只注入 ai-worker；前端与 api 日志不出现密钥。
- **内部通信**：Worker 只连 Temporal，不暴露 HTTP；供应商回调端点验签并限源。
- **审计**：选定、确认、预算变更、成员权限变更写审计记录。

## 10. 可观测

- 结构化日志（Go `slog`、Python 结构化日志），统一字段：`trace_id`、`org_id`、`project_id`、`job_id`，不记录剧本正文、密钥与个人信息。
- OpenTelemetry 贯穿 api → Temporal → Worker → 供应商调用。
- 模型调用明细入库：模型、版本、参数 hash、耗时、token / 秒数、费用、结果状态，用于成本报表与质量回溯。
- LLM 提示词、输入输出采样与评估接入 LLM 观测平台（见 0003）。
- 核心告警：任务失败率、`unknown` 堆积、供应商错误率、预算预留未释放、队列积压。
