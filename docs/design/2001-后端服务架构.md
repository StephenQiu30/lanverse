## 结论

Backend 只有一个 Go Module 和一个业务 Writer。`lanverse-api`、`workflow-worker` 与有真实 Kafka 消费职责时创建的 `event-worker` 共享同一套 Domain/Application/Port 和 GORM Model Catalog，不共享全局可写 Repository。Python `agent-runtime` 是 Backend 私有的 Candidate 生成运行时，不是第二 Backend。

```text
Browser
  ↓ REST / SSE
lanverse-api (Go, only business writer)
  ├── PostgreSQL + GORM Model Catalog
  ├── MinIO / ObjectStore
  ├── Temporal ↔ workflow-worker
  ├── private HTTP → agent-runtime → controlled Codex CLI
  └── Transactional Outbox → Kafka ↔ event-worker
                                       └──▶ Elasticsearch business indices

JSON logs → Filebeat → Kafka log topics → Logstash
                                               └──▶ Elasticsearch log indices → Kibana
```

Kafka 与 Elasticsearch/ELK 不是第二事实源。Kafka 只运输已提交业务事件和独立日志流，Elasticsearch 业务索引可从 PostgreSQL 全量重建，日志索引不承担业务状态。

## 当前事实与目标缺口

| 能力 | 当前事实 | StoryGraph 目标 |
|---|---|---|
| 公共 Backend | `backend/cmd/api`、OpenAPI、GORM、PostgreSQL、MinIO 已有实现和测试 | 继续作为唯一公共 API/业务 Writer |
| Workflow | `backend/cmd/workflow-worker` 与 Temporal SDK/工作流已存在 | 添加 StoryGraph 宏观 Node、Stage/Shard 挂载、Human Gate 和精确恢复 |
| Agent | 私有 FastAPI/Pydantic Candidate Runtime 与旧 Skill/Harness 已存在 | 迁移并收口为 `agent/skills/build-storygraph`，只返回 Candidate |
| Kafka/Event | 已有 `franz-go`、事务 Outbox、Inbox/Checkpoint、DLQ/Replay 与 `event-worker` | 保持 Script/StoryGraph 业务 Topic 与日志 Topic 隔离 |
| Search | 已有 Script/StoryGraph Elasticsearch Alias、事件投影、PostgreSQL Reindex 和授权 Query | 保持可重建投影、Owner 深链和 degraded/stale 边界 |
| ELK 日志 | 已有统一脱敏 JSON Logger、Filebeat、独立 Kafka Log/DLQ Topic、Logstash、严格 Elasticsearch Log Template/ILM、Kibana Data View 和真实故障验收 | 保持日志与业务事实、业务事件、业务索引隔离 |

当前存在不等于目标已验收，目标缺口也不允许用内存假实现、兼容分支或模型桩冒充。每个缺口只在对应 `SG-Ixx` 任务经 Red 契约、实现、真实 CI 和独立提交后转为已完成证据。

## 模块与依赖

```text
HTTP / Temporal / Kafka Inbound Adapter
                 ↓
Owner Application (authorization / transaction / idempotency / Owner Apply)
                 ↓
Owner Domain + deterministic Compiler
                 ↑
Owned Port ← GORM / MinIO / Agent / Provider / Kafka / Search Adapter
```

规范业务模块是 `access/production/preset/authoring/workflow/review/generation/agent/asset/media/cost/quota/eventing/search`，`bootstrap/config/database/cache/telemetry` 是装配/基础设施。当前 `platform` 只保留已有数据库、Command Receipt、HTTP 和对象存储基础设施，不接管 StoryGraph、Eventing 或 Search 业务 Owner。

- `production` 拥有 Project、ScriptVersion、ProductionBibleVersion、Episode/Scene/Beat/Shot 与 StoryGraph Compiler/Version/Head；
- `authoring` 拥有 `AuthoringDraft/AuthoringRevision.Graph`，不拥有 StoryGraph；
- `workflow` 拥有 Compiler、Definition Version、Run/NodeRun、Temporal 协调和 Cache；
- `agent` 拥有 Invocation、Grant、Stage/Shard/Policy、Candidate Client 和 Result Receipt，不拥有 Production 事实；
- `asset` 拥有 Asset/AssetState/AssetVersion/Artifact/Lineage/Storage Location；
- `eventing` 拥有 Kafka Envelope、Outbox Publisher、Inbox、DLQ、Replay 和 Checkpoint；
- `search` 拥有业务索引文档、Alias/Template、Indexer 和 Reindex，不拥有原始业务事实。

Domain/Compiler/Application/HTTP Handler 不直接导入 GORM；仅 GORM Adapter 和数据库组合根使用它。跨模块调用只依赖对方显式 Application Interface 或由调用方定义的窄 Port，不直接查询对方 Model/Repository。

## 公共与私有契约

| 契约 | 唯一事实源 | 规则 |
|---|---|---|
| Browser REST/JSON | `backend/api/openapi/lanverse-v1.json` | Go 路由实现；Frontend 只从该文件生成/校验类型 |
| 公共错误包络 | OpenAPI + `backend/internal/platform/httpapi` | `{error:{code,message,request_id,next_action,details}}` |
| Backend → Agent Invocation | `backend/internal/agent/contract` | Backend 拥有 Envelope、Stage、Policy、签名 Grant 和 wire version |
| Agent → Backend Result | Backend contract + `agent/app/candidate_runtime` 严格消费模型 | 只返回 succeeded/failed/unknown 与严格 Candidate/Result Hash；Backend 二次校验 |
| Kafka Event | 对应 Domain Owner 事件语义 + `eventing` Envelope | 必须有生产者、消费者、幂等键、失败去向和重放契约 |
| Search Document | `search` 模块中的版本化投影 Schema | 必须保留 Owner ID/Version/Source Event，可从 PostgreSQL Reindex |

Backend 与 Agent 当前使用最小 JSON/HTTP 私有契约，不为两个本地运行进程引入 Protobuf/gRPC 生成链。契约变更顺序为 `Design → Red Contract Fixture → Owner Schema → Implement → Cross-language Contract → E2E`。

## 数据库工具与唯一 Schema 源

Backend 已使用的成熟工具链继续以 `backend/go.mod` 为代码事实：

| 能力 | 选型 | 当前版本 | 使用边界 |
|---|---|---:|---|
| ORM 与事务 | `gorm.io/gorm` | `v1.31.2` | GORM Adapter、事务与唯一 Catalog |
| PostgreSQL Driver | `gorm.io/driver/postgres` | `v1.6.2` | 唯一 `DATABASE_URL` |
| JSONB | `gorm.io/datatypes` | `v1.2.7` | 不可变 Snapshot/Version、Receipt、Candidate Payload |
| 精确金额 | `github.com/shopspring/decimal` | `v1.4.0` | Budget/Cost 的 `NUMERIC` 映射 |
| UUID | `github.com/google/uuid` | `v1.6.0` | ID 与 GORM Record |
| 请求校验 | `github.com/go-playground/validator/v10` | `v10.30.3` | HTTP 基础格式；领域规则仍属于 Application/Domain |
| 对象存储 | `github.com/minio/minio-go/v7` | `v7.3.0` | 预签名、完整性读取与对象操作 |

Event/Search 已锁定 `github.com/twmb/franz-go v1.21.6`、官方 `github.com/elastic/go-elasticsearch/v9 v9.4.3`、Kafka `4.3.1` 与 Elasticsearch `9.4.4`；Filebeat、Logstash、Kibana 同步锁定为 `9.4.4`。Kafka 客户端只由 `eventing/adapter/kafka` 导入，Elastic 客户端只由 `search/adapter/elasticsearch` 导入；不建第二客户端、兼容分支或可回写 Owner 的索引接口。

数据库结构唯一来源是 `backend/internal/platform/database/model` 的 GORM Record Catalog：

1. `schema.Sync` 对 Catalog 执行 GORM `AutoMigrate` 的非破坏性空库同步。
2. 仓库不保留手写 SQL Schema/Migration、迁移元数据表、迁移 Binary、第二 DSN、`sqlc` 或第二 ORM/DAO。
3. CRUD、关联、计数、事务、行锁、JSONB、索引和约束全部使用 GORM API/Clause/Tag，不在业务 Adapter 手写 SQL。
4. 当前没有历史生产数据搬迁需求，开发和 CI 从独立空库启动并验证重复 Sync；不预建迁移框架。
5. 每个新 StoryGraph Model 只在对应 `SG-Ixx` 的首个 Red 契约需要时加入 Catalog，不一次性预建未来表。

## Temporal、Agent 与 Candidate 边界

Temporal 是唯一跨步骤持久 Workflow Engine。WorkflowDefinition 只编排稳定宏观节点和 Human Gate；Stage/Shard、AgentInvocation、Candidate Revision、Owner Receipt 与业务恢复状态由 Backend 保存在 PostgreSQL 并挂到精确 NodeRun。Agent 不保存跨请求 Checkpoint，不使用 LangGraph 管理宏观流程。

- `agent-runtime` 不接收 `DATABASE_URL`、MinIO、Kafka、Elasticsearch、Temporal、JWT 或 Browser Session 凭据；
- Backend 以签名 Grant 冻结 Invocation/Stage/Shard/Input Hash/Bundle Hash/Schema/Model Policy/Budget/Deadline；
- `StoryGraphHarness` 只加载 `agent/skills/build-storygraph` 指定 Reference，本地可启动受控 Codex CLI；
- Codex 不读取用户级/项目级配置或仓库文件，不获得 Shell、Web、浏览器、文件写入或业务工具；
- Agent 只返回 `succeeded/failed/unknown` 与不可变 Candidate Result；Backend 重算 Hash、执行确定性 Gate/Human Gate/Owner Apply 后才能创建正式事实。

未知结果按稳定 Invocation/Intent/Provider Job ID 对账，不当作确定失败盲目重提。高成本操作在执行前经 Cost/Quota 预留与 ExecutionAuthorization，Candidate 未被选中前不覆盖当前生产版本。

## Kafka、Search 与 ELK 边界

```text
Owner Transaction
├── Aggregate / Version / Head
└── Outbox Event
      ↓ GORM publisher, at-least-once
Kafka Business Topic
      ↓ idempotent event-worker + Inbox/business key
Elasticsearch Business Index
```

当前不引入 Debezium/CDC。Outbox Publisher 和 Consumer 都使用 GORM，超时、批量、Claim/Fencing、Broker ACK、退避、DLQ 和 Replay 在首个真实 Topic 契约中固定。不为没有消费者的 Domain Event 创建 Topic。

Search Indexer 只消费已发布 `ScriptVersion/StoryGraphVersion` 事件，索引文档保留 `project_id/owner_kind/owner_id/owner_version/source_event_id`，支持幂等更新、Alias 切换和从 PostgreSQL 全量 Reindex。Backend Query 只返回投影结果和可追溯 Owner Ref，不把 Elasticsearch 文档当作聚合回写。

日志链路只接收应用输出的脱敏 JSON Log：`Filebeat → Kafka Log Topic → Logstash → Elasticsearch Log Index → Kibana`。日志 Topic/Index 与业务 Topic/Index 使用独立 Schema、ACL、Retention、Consumer Group 和 Index Template；Logstash 不消费业务事件。

## 对象存储

- Bucket 保持私有，Browser 使用短时 Presigned URL 直传/下载；
- Backend 完成声明大小、MIME、SHA-256 和可用性校验后才登记不可变 `AssetVersion/ArtifactLocation`；
- 对象字节不进入 PostgreSQL，业务元数据、权利/同意、Lineage 和精确绑定仍只由 Backend 写入；
- MVP 只实现当前 MinIO Adapter，不预建 TOS/S3/OSS/COS 代码或 Storage Router。

## 运行、CI 与安全门禁

- `healthz` 只证明进程存活；`readyz` 只检查当前 Binary 的真实必需依赖，不伪装尚未实施的 Kafka/Elasticsearch/Agent 能力已就绪；
- 实施 Event/Search 后，`event-worker` readiness 必须验证 Kafka Metadata/Consumer Group 和 Elasticsearch 连通性，Reindex 与日志链路有独立可执行验收；
- 日志不记录 JWT、Refresh Token、Execution Grant、数据库/对象存储密钥、完整预签名 URL、未脱敏剧本或生成内容；
- 架构、单元、契约和集成测试只位于 `backend/tests`，Agent 测试只位于 `agent/tests`；
- CI 必须使用空 PostgreSQL、真实 Temporal、MinIO，并在对应能力实施后加入真实 Kafka、Elasticsearch 和 ELK 管道；缺少依赖时不报告通过；
- 只有全部实施切片和真实 CI 通过后，才使用 `agent-browser` 完成最终 Web Journey。

## 非目标

- 不预建微服务、空 Binary、兼容代理、Migration/CDC 平台、第二 ORM/DAO、手写业务 SQL、第二 Agent 流程引擎、通用 Tool Registry 或第二 UI 状态库。
- 不让 Agent、Temporal、Kafka、Elasticsearch、Logstash 或 Frontend 承担任何 Production/StoryGraph/Asset/Storyboard 正式事实写入。
- 不以当前目录、模型桩、过时验收记录或未执行的 CI 证明 StoryGraph/Kafka/ELK 目标已完成。
