# BeefTV 能力引入设计

日期：2026-09-30。当前方向：**遵循用户指定的“完整前端 → 对应服务 → PoC 验证 → 消费者能力”顺序**。本轮实施前端页面与交互 PoC，复用已接受的 REQ-05、DES-05、DES-06、DES-27、DES-38 及 DESIGN.md；后续公共 API 的待决项仍需单独收敛，不因页面完成而视为已接受。

依据：[调研与代码证据](../prd/BeefTV能力调研与借鉴评估.md)、[前端需求](../requirement/05-界面与交互需求.md)。用户先要求调整原媒体生命周期切片，随后明确前端优先；本设计据此调整，B1 不作为当前交付主线。

## 1. 问题与目标

当前前端仅有项目占位页、参数 / 报价展示组件和固定样本性能画布，不能完整演示创作工作台。内部服务虽已有部分实现，公开业务 API、真实供应商和产品闭环尚未联通。

先把页面、导航和关键决策操作摆到可运行的界面里，用统一样例明确素材、镜头、候选、任务与成本的关系。前端 PoC 通过后，再以页面暴露的实际需要补齐服务，避免把未连接的内部实现误报为产品可用。

## 2. 阶段与非目标

| 阶段                     | 交付                                                                                                                     | 放行条件                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| F1：完整前端 PoC（本轮） | 项目 / 剧本 / 设定集 / 单集 / 分镜 / 故事板 / 配音 / 画布 / 素材 / 任务 / 成本影响 / 设置 / 内部管理；报价与变更提案预览 | 路由可直达，核心交互可演示，空 / 错误 / 只读等状态可检查，自动检查与浏览器证据通过；用户确认页面方向 |
| F2：补齐对应服务         | 鉴权、项目、素材、模型能力、报价确认、任务与候选、草稿和画布命令；复用既有业务模块和契约生成链                           | 受控联调证明接口 / 失败 / 幂等 / 恢复；真实服务单独记录                                              |
| F3：端到端 PoC           | 真实模型、对象存储、Temporal、SSE、刷新恢复、费用核对、候选选定                                                          | 有真实来源和实际费用证据；用户验收创作链路                                                           |
| F4：消费者功能           | 注册 / 套餐 / 支付 / 运营 / 分享 / 面向消费者的服务                                                                      | F3 已通过，再接受相应设计                                                                            |

本轮不接真实登录、不执行付费生成、不构建开放注册 / 支付 / 营销、不新增后端架构、不以浏览器草稿替代服务端保存、不移植 Wails / SQLite / FFmpeg.wasm。管理页是内部界面演示，权限依赖后续服务，不能当作授权实现。

## 4. 模块与数据

继续使用 Next.js App Router、React、现有 Tailwind / shadcn Radix、TanStack Query 及 React Flow。页面路由只解析参数并验证样例对象；领域页面按项目、剧本、资产、分镜、任务、管理职责划分在 `features/workbench`，公共展示组件只限工作台本身。复用已有 BudgetCard 与 QuoteConfirmDialog。

样例项目、单集、镜头、素材与任务是一套显式关联的固定数据，所有界面持续显示“前端 PoC · 样例数据”。样例金额只用于布局 / 报价决策预览，不映射为真实模型价格或费用。页面中不增加伪 HTTP 服务或手写生成客户端。

| 状态                                      | 所有者 / 生命周期                                         |
| ----------------------------------------- | --------------------------------------------------------- |
| 搜索、列表视图、候选 / 类别选择、状态演示 | URL 查询参数；深链接与刷新恢复                            |
| 编辑草稿、预览对话框、拟选定候选          | 当前页面 React 状态；明确“仅本页，刷新丢弃”，不声称已保存 |
| 项目 / 素材 / 任务事实                    | F1 固定样例；F2 后由服务端和 TanStack Query 提供          |
| 画布位置和视口                            | F1 页面内预览；F2 使用 DES-06 的 revision 与命令接口      |
| 真正选定 / 删除 / 取消 / 生成             | F1 阻断或只显示影响提案；F2 由服务端复核                  |

## 5. 关键交互与失败路径

1. 生成入口复用报价对话框，在新增 `previewOnly` 模式明确“样例报价”；确认按钮持续禁用，即使剔除错误项或刷新报价也不能放行。默认真实调用行为保持兼容。
2. 镜头页候选比较可以切换并在 URL 恢复；拟选定先打开影响预览，确认后只标记本页预览状态。不会修改候选的服务端事实。
3. 表单显式标签、错误文本和禁用状态。登录不收集或发送真实账号密码；演示者直接进入样例。
4. 页面可选择正常、加载、空、错误、无权限和只读状态；重试恢复到正常样例。只读仍可查看、筛选和预览，写入预览入口禁用。
5. 任务读取失败与任务失败分开；示例“提交结果未知”只允许查看核对说明，不显示安全重提或零费用承诺。失败下一步区分改参数、重新报价、取回已有产物和人工核对。
6. 不存在的项目 / 单集 / 镜头 / 任务 / 管理页面返回 404。刷新保留筛选与候选；没有服务端草稿恢复时明确提示。
7. 保留键盘焦点、跳过导航、对话框标题和语义表格。内容 Card 无闭合边框 / ring / 阴影，表单控件和浮层保留识别与焦点。

## 6. BeefTV 借鉴的落点

- 工作台把素材、引用、候选、任务和画布串联，便于继续创作，先在前端显示真实结构关系。
- 候选选择与生成结果接管分开，迟到结果和版本保护由 F2 / F3 服务实现。
- 任务给出明确失败原因与下一步；读失败不覆盖执行状态，提交不确定不盲目重试。
- 页面 / 媒体生命周期与播放额度后续在实际媒体接入时衡量。当前不修改独立性能画布的样本统计，不宣称性能指标通过。
- 3D、深度视频、自动布局、诊断包和时间线是后续建议，不扩大 F1。

## 7. 服务阶段必须解决的决定

公开鉴权 / Cookie / CSRF / SSE、DES-03 IF4～IF6 的幂等与浏览器部署方案、Swagger 在线文档 → `@umijs/openapi` → 统一 `request.ts` 的请求链，需在 F2 的具体 Design 中收敛。当前前端路由不是公共 API 合同。

真实模型来源、能力、价格和预算来自 P0 决策。先按界面顺序补接口，不能依赖 BeefTV 某条网关就推定 Lanverse 账号可调用。用户补充允许必要时取消 Agent 服务、由 Go 统一实现。F2 优先评估 Go 统一承接 API、Temporal Workflow / Activity 与模型适配；迁移前必须核对现有 Python worker 的职责、进行中工作流兼容与验收成本，更新正式架构事实来源后再实施。此方向不要求把前端改成 Go，也不在 F1 删除现有 worker。服务模块继续遵守 `adapter → application → domain`。

### Go 统一服务的具体评估边界

本次核对 `backend/internal/operation/adapter/workflow/provider_calls.go`：持久化工作流、供应商调用身份、提交不确定和取消编排已在 Go；无需另迁移一套 Python Workflow。`agent/app/main_worker.py:90` 使用 MockStructuredClient，`:117` 注册 MockProvider，实际独立进程还承接 Skill 与凭据测试 Activity。因此最小生成链可优先评估迁入 Go，独立 Harness 不作为 F2 前置。

后续收敛设计应具体覆盖：

1. 在现有业务模块的 Go Activity / 显式供应商适配器中实现 submit / query / cancel / download 与结构化模型输出验证；不是把网络调用放进确定性 Workflow。
2. 保持稳定的 Operation ID、provider_request_key、Activity 名称 / 队列合同和账本去重。付费提交不自动重试，超时保留 unknown；下载恢复只取已有产物。
3. 将 Python 的凭据解封、限流、取消、错误分类、授权与审核职责逐项映射。没有真实供应商证据时不能把 mock 的迁移测试当作完整替代证明。
4. 核对已启动工作流的回放 / 队列兼容，先用 Go 的受控供应商 Activity 证明同一合同，再做真实供应商联调；完成后才删除 Python / Compose / CI 依赖并更新 PROJECT、DES-03 / DES-04 / Agent 设计。
5. 剧本解析、提示词构造、模型选择先做明确用例与模板；消费者阶段确有需要再考虑自治 Agent。前端仍使用现有 Next.js，不增加新框架。

以上是针对用户补充的评估方案，尚未实施迁移，不构成已删除 Agent 或已统一运行服务的完成声明。
