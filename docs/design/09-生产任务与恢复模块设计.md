# 生产任务与恢复模块设计

## 1. 范围与事实所有权

`production_jobs` 是异步命令与恢复的唯一业务事实模块，拥有 SubmissionSnapshot、ProductionTask、ProductionAttempt、TaskEvent、TaskJob 和 TaskOutput。它不拥有 AI 业务结果、MediaVersion、Adoption 或 Delivery，也不把 TaskEvent 作为对外消息总线。

## 2. 命令受理契约

非 Render 异步命令在同一个 PostgreSQL 事务中写入：

```text
SubmissionSnapshot
  → ProductionTask(queued)
  → ProductionAttempt(initial)
  → TaskEvent(accepted)
  → TaskJob(pending)
  → IdempotencyRecord(completed)
```

返回 `202 task_id/status/status_url/poll_after_ms=2000`。事务内失败时不留半套事实。Render 使用 DESIGN-06 的 Tx1/Tx2/Tx3 协调，但 Task 始终引用 SubmissionSnapshot。

Task type 仅允许 `generate_script/generate_storyboard/generate_media/render_episode`；每个媒体命令只对应一个 usage slot。多项生成是 API/UI 聚合视图，不新建 Batch 事实。

## 3. 状态机与进度

| 对象 | 状态 | 关键规则 |
| --- | --- | --- |
| ProductionTask | `queued/running/cancelling/cancelled/succeeded/failed/unknown` | 只允许显式单向迁移；终态不可改写 |
| ProductionAttempt | `pending/submitting/waiting_provider/downloading/postprocessing/succeeded/failed/unknown/cancelled` | 外部执行阶段和错误只存 Attempt |
| TaskJob | `pending/leased/completed/failed` | 租约过期允许重新领取；failed 只显式 replay |

Task 的 `progress.phase/percent/next_action/error_code/resource_version` 和对应 TaskEvent 在同事务 CAS 更新。前端不直接读取 Attempt/TaskJob，只查询 Task 权威投影。

## 4. Worker 租约与 Handler

1. Runner 在短事务中按 `(next_attempt_at,created_at,id)` 使用 `FOR UPDATE SKIP LOCKED` 领取并写 `lease_owner/lease_until`。
2. 外部 Provider/MinIO/FFmpeg 调用期间不持有数据库锁；独立心跳按固定间隔续租。
3. Runner 仅根据 Task type 调用具名 Handler；Handler 通过 owning module `public.py` 执行业务步骤。
4. payload 含 `release_version/task_id/snapshot_id/handler_version`；非终态任务排空前保留兼容 Handler。
5. 并发容量和超时使用 REQ-06 上限；容量不足时停止领取，不丢弃已受理任务。

## 5. 幂等、重试与对账

- 输入快照固定所有版本、Prompt、参数、model profile、Provider/model 和哈希；Task 受理后不切换。
- 每次外部提交前，先以短事务持久化稳定 `provider_request_key`。
- 系统自动重试在原 Task 下创建带 parent 的新 Attempt；用户重试终态失败则创建 `retry_of_task_id` 新 Task。
- 继任 Worker 先根据 Attempt、Provider key/ID、MinIO object key/hash 对账；无法证明是否受理时收敛为 `unknown`，不盲目重发。
- 输出使用 `(task_id,output_type,output_slot)` 唯一键，Handler 重入先读 TaskOutput 再执行。

## 6. 取消、迟到结果与失败恢复

| 场景 | 收敛结果 | 禁止 |
| --- | --- | --- |
| queued 取消 | Task 可直接 cancelled，Job 不执行 | 伪造 Provider 取消 |
| running 取消 | `cancelling`，Adapter 尽力取消并继续对账 | 立即删除 Attempt/Job |
| Provider 迟到成功 | 登记为 blocked 对账输出 | 改写 cancelled/failed Task 或自动采用 |
| lease 过期 | 新 Worker 对账后续执行或 unknown | 不对账重复付费提交 |
| 单位置失败 | 只改变该 Task/Attempt | 回滚其他 Task 的成功事实 |

日志用 `request_id/task_id/job_id/attempt_id/release_version/error_code` 关联，不记录凭据、Prompt 或 Provider 原始响应。部署回滚保留任务事实，由 lease 过期与兼容 Handler 恢复。

## 7. Design 验收标准

- AC-MOD-TASK-001：任一异步受理成功后，快照、Task、初始 Attempt/Event/TaskJob 和幂等回执同时存在并返回同一 `task_id`。
- AC-MOD-TASK-002：同命令并发重放 20 次只有一个逻辑 Task、初始 Attempt、TaskJob 和初始外部副作用。
- AC-MOD-TASK-003：双 Worker 竞争同一 Job 时只有一方获得未过期租约，心跳不延长非当前 owner 的租约。
- AC-MOD-TASK-004：在领取、Provider 提交、下载、登记和渲染故障点重启后，120 秒内进入终态或明确 `unknown`，不增加外部副作用。
- AC-MOD-TASK-005：自动重试和用户重试的 Task/Attempt 关系正确，同重试命令重放不重复创建。
- AC-MOD-TASK-006：取消、迟到结果和单位置失败均保留历史，不改写其他位置的 Task/输出。
