# 后端领域模块功能设计

- 目标状态：已接受
- 落地状态：阶段 1 运行契约与 Event Envelope v2 部分实现，目标业务模块尚未接管 Writer
- 来源：[后端服务架构](../architecture/后端服务架构.md) · [领域语言与模块命名规范](../architecture/领域语言与模块命名规范.md) · [完整设计基线](AI短剧制作平台完整设计基线.md)

## 结论

Backend 按 14 个业务能力模块、1 个组合根和 4 个基础设施 package 组织。模块不是“表的文件夹”，而是拥有明确业务事实、状态机和用例的边界。跨模块只使用公开 Application Interface、不可变 Snapshot 或 Domain Event；同一业务事实只能有一个 Owner。

`lanverse-api`、`workflow-worker`、`model-gateway`、`media-worker`、`event-worker` 是同一 Go Module 的不同组合，不是五套重复领域实现。

## 全局应用契约

Command Envelope 按调用主体区分，不能假设所有命令已经登录或属于 Workspace：

| Command 类型 | 必需上下文 |
|---|---|
| 已认证业务命令 | `actor_context`、`workspace_id`、`idempotency_key`；并发修改再带 `expected_revision` |
| 已认证账户级命令 | 不含 Workspace 的 `account_actor_context`、`idempotency_key` 和 Account Entitlement；用于创建首个/新 Workspace 等尚无 Membership 的用例 |
| 匿名认证命令 | `client_context`、`idempotency_key`；注册完成前没有 actor/workspace |
| Provider Callback | `provider_principal`、`provider_event_id`、签名时间和重放窗口 |
| 内部服务命令 | `service_principal`、`correlation_id`、`causation_id`、调用授权 |
| 运维命令 | `operator_principal`、变更单/原因、幂等键和审计上下文 |

所有模块遵守：

1. 修改权威业务事实的 Command 在一个 PostgreSQL 事务中修改本模块事实并写 Outbox；登录、只读校验、Projection/Reindex 等非业务事实操作按自身协议处理。
2. Query 无业务副作用；Redis、Search 和投影不能参与 Command 正确性判断。
3. 同 Binary 内通过 Go Interface；跨 Binary 才使用 gRPC/Protobuf。
4. 远程调用必须区分 `known_failure` 与 `outcome_unknown`，未知结果不能自动当作失败重试。
5. 每次运行冻结 Authoring Revision、Workflow Definition、Preset/Effective Policy、Skill/Prompt、Access Capability Catalog Revision、Generation Capability/Model Catalog、Price 版本和允许的 Model 集合；每次 Provider Attempt 再记录实际 Provider、Model 与 Adapter 版本，以允许受控 Fallback。
6. 跨模块引用使用 ID + Version 或不可变 Snapshot，不读取对方 Repository/表。

统一错误族见 [领域语言与模块命名规范](../architecture/领域语言与模块命名规范.md#状态与失败语义)。

跨模块原子用例由最外层 Application Coordinator 发起，同一 Binary 内通过共享 Unit of Work 调用各模块公开接口；Coordinator 不拥有表，也不能直接调用 Repository。当前设计明确必须使用该模式的用例是：注册/创建 Workspace 与 Owner Membership、发布 Production Bible 并物化 Asset/Version Binding、同时创建 Cost/Quota Reservation。跨 Binary 不使用分布式事务，改用持久 Intent、幂等 Receipt、Outbox 和可补偿 Saga。

所有会触发付费 Provider、Agent 模型调用或高成本 Media Job 的入口都必须先取得 `ExecutionClaim`。业务提交事务只持久化 Intent、Cost/Quota Reservation 与 Outbox，不生成也不在 Event 中携带短时 Token；Worker/Gateway 真正开始处理 Intent 时，调用 `lanverse-api` 内部 `AcquireExecutionClaim`。API 在一个事务内锁定 Intent 与两类 Reservation，验证 revision/scope/expiry 后将三者推进为 `EXECUTION_CLAIMED`，持久化 `claim_id/claim_version/claim_digest` 到 Intent，再返回由这些事实派生签名、但不独立持久化的 `ExecutionAuthorization`。因此队列延迟不消耗 Token 有效期，签名只证明已原子领取的 Claim，取消也不能在 Claim 后释放 Reservation 形成 TOCTOU。

授权引用两类 Reservation ID/Revision、Workspace、Generation Capability/操作类型、预计用量、最高金额、Intent、Claim Version、调用范围和到期时间。Worker/Gateway 验证签名并绑定稳定 Provider/Job Request Key；Token 过期不释放 Claim。只有 Provider 明确支持幂等 Request Key，且按原 Key 对账确认可安全续接时，API 才可为同一 Claim Version 重签；否则进入 `OUTCOME_UNKNOWN/RECONCILING`。任何模块都不能自行创建预留、绕过 Claim 或先执行后补账。

## 依赖方向

```text
access ─────────────────────────────────────────────┐
production ─┐                                      │
preset ─────┼→ authoring → workflow ───────────────┼→ review
asset ──────┘                 ├→ agent ─→ generation│
                             ├→ generation ─→ asset│
                             ├→ media ──────→ asset│
                             └→ cost + quota       │
                                                   │
所有事实事务 → eventing/outbox → Kafka → event-worker → search/audit/cost projection
```

箭头表示用例级依赖，不表示共享数据库。为避免环：

- Review 完成只写 Decision + Outbox；Workflow Adapter 消费后发送 Temporal Signal。
- Generation/Media 成功只产出幂等结果引用；Workflow Activity 调用 Asset 接口登记 Artifact。
- Cost/Quota 不回调 Generation；Workflow 使用 Usage Report 结算 Cost Reservation 并确认 Quota Usage。
- Search 只消费事件/重建快照，不被业务 Command 查询。

### Workspace 首次创建协议

`RegisterUserAndCreateWorkspace` 是 `lanverse-api` 的跨模块 Application 用例。Redis Verification Ticket 与 Auth Session 无法加入 PostgreSQL 事务，因此使用可对账协议：

1. 注册请求体在兼容期继续只发送现有 `registration_ticket/password/display_name`，避免旧 `extra=forbid` Schema 因新增字段拒绝；新版 SDK 先增加 `Idempotency-Key` Header，旧服务会安全忽略。Access 用服务端 HMAC 对 Ticket 派生不可逆 `challenge_ref`，不要求当前随机 Ticket 携带 `challenge_id`；若 Header 缺失，兼容期以该 HMAC 派生稳定注册幂等键。
2. Access 以 `challenge_ref + registration_idempotency_key` 原子把 Verification Ticket 从 `AVAILABLE` 置为带短租约的 `CLAIMED`，不在数据库提交前直接删除；同一幂等键可读取原 Claim，其他请求不能复用。Redis Adapter 在一个旧 Ticket TTL 窗口内同时识别当前原始值与目标 Claim Envelope，且任何日志/表都不保存原始 Ticket。
3. 在同一个 PostgreSQL Unit of Work 中创建 `UserAccount`、`Workspace`、Owner `WorkspaceMembership`、Access 拥有的 `RegistrationReceipt(COMMITTED_SESSION_PENDING)` 和三类领域事件/Outbox。`access` 与 `production` 分别执行不变量并写自己的 Repository；Coordinator 不直接写表。
4. PostgreSQL 已知失败时释放 Ticket Claim；结果未知时先按幂等键查询 `RegistrationReceipt`，查到即视为已提交，禁止重新创建账户。提交成功后再把 Ticket 标为 `CONSUMED`，不能让 Ticket 删除承担提交事实。
5. 事务提交后以 Receipt 中稳定的 Session ID 幂等创建 Redis `AuthSession`；成功后把 Receipt 推进为 `SESSION_ISSUED`。Redis 失败时账户与 Workspace 仍是已提交事实，API 返回明确的 `registration_committed_session_pending`，重试同一注册请求或普通 Login 只补发 Session，不重放数据库写入。
6. 部署顺序是“SDK 先发 Header → 服务端兼容旧 Body/Ticket → 等待一个旧 Ticket TTL → 切注册 Endpoint”；故障注入必须覆盖“Ticket 已 Claim/数据库失败”和“数据库成功/Session 写入失败”。

后续 `CreateWorkspace` 同样通过 Coordinator 原子创建 Workspace + Owner Membership；邀请普通成员只调用 `access`。

### Production Bible 发布与 Asset 物化协议

`PublishProductionBibleVersion` 由 `lanverse-api` 的跨模块 Coordinator 执行：

1. Production 校验 Bible/Entity/World Version、Project/Episode Scope 和 expected revision；Asset 校验名称、State、Version、Rights 与幂等不变量。
2. 同一 PostgreSQL Unit of Work 发布不可变 `ProductionBibleVersion`，创建或绑定对应 Asset/AssetState/AssetVersion，并写 `BibleAssetMaterializationReceipt` 与双方 Outbox。
3. Coordinator 只调用 Production/Asset 公开 Application Interface，不直接写双方 Repository；任一步失败整体回滚。
4. 重试以 Bible Version + materialization key 返回同一 Receipt；已发布 Bible 的资产绑定只通过显式新版本变更，不能原地重物化。

迁移时当前 DB-08/DB-14A 与 Confirm Endpoint 是一个不可拆切片；旧 Bible Agent Run/Lease 可以继续排空，但目标发布命令不能把一半事实写入旧模块。

### PostgreSQL 与 Temporal 一致性协议

Temporal 是 History、Timer、Retry、Signal 的权威源；PostgreSQL 只保存业务 Run ID、持久 Intent/Receipt 和查询投影：

1. `RequestWorkflowStart` 事务创建 `WorkflowStartIntent(PENDING)`、`WorkflowRun(DRAFT)` 和 `workflow.start_requested.v1`。稳定 Temporal Workflow ID 为 `lanverse/{workspace_id}/{workflow_run_id}`，输入同时保存 definition/revision hash。
2. `workflow-worker` 的专用 `workflow-command-dispatcher` Consumer Group 接收 Intent，使用稳定 ID 调用 Temporal Start。遇到 Already Started 时必须比较 memo/input hash；相同即复用，不同进入人工处置。
3. 远程返回前后崩溃时将 Intent 标记 `UNKNOWN`；Dispatcher 通过 Describe Workflow 对账，再写 `WorkflowStartReceipt(CONFIRMED|FAILED)`。API 不能在收到请求时把投影提前标为 RUNNING。
4. Pause/Resume/Cancel/Human Signal 创建带稳定 `control_id` 的 `WorkflowControlIntent`。Temporal Workflow 在确定性状态中记录已应用 ID，重复 Update/Signal 返回同一结果。
5. `workflow-worker` 写 `WorkflowControlReceipt` 和 PostgreSQL Query Projection；Run/Node 业务事件只能在 Temporal 已确认对应状态后发布。
6. Projection 可丢弃并从 Temporal Visibility/History + 业务绑定重建；不得反向驱动 Temporal。

Event Worker 不发送 Workflow Control。Review/Control Intent 由 `workflow-worker` 专用消费组处理；`event-worker` 只建设 Search、通知、审计和成本分析等下游 Read Model。

### Candidate、Artifact、QC 与选择 Saga

候选必须可预览、可做 QC、可追踪，因此先登记为 Candidate Artifact，再产生选择绑定：

1. Provider Job 成功后返回受控 Staging Object Ref；Workflow Activity 用 `provider_job_id + candidate_index` 作为幂等键调用 Asset `RegisterArtifact`。
2. Asset 完成 Hash/Integrity 后返回 `artifact_id`；Generation 创建 `GenerationCandidate(artifact_id, readiness=READY)`。崩溃重试复用同一 Artifact/Candidate。
3. 技术 QC 由 Media、语义 QC 由受限 Agent 产生结构化 `QCReport`，两者都登记为 Artifact。Workflow 根据冻结的 QC Policy 写唯一 `QualityGateResult`。
4. 需要人工选择时 Review 创建绑定 Candidate/Artifact/对象版本的 `HumanTask`。`ReviewDecision(SELECT)` 是人工事实，不是 selected binding。
5. `workflow-worker` 以 `review_decision_id` 为 causation/idempotency key 调用 Generation `ApplyCandidateSelection`；Generation 对同一 selection slot 建唯一约束并写 `CandidateSelection`。
6. Workflow 再调用 Production/Asset 公开接口更新 Shot Result 或 Asset Version Binding，最终继续下游节点。

Staging 对象在 Artifact 登记前失败由 Retention Job 清理；未选择的 Candidate Artifact 按 Preset Retention Policy 保留或 Tombstone。任何模块都不能另存第二个“当前候选”字段。

### Review、Production Apply 与 Temporal Signal 协议

普通 Human Gate 由 Review 在一个事务写 `ReviewDecision` 与 Outbox；`workflow-worker` 以 `review_decision_id` 写 Inbox Receipt，并向绑定 Workflow 发送同 ID Signal。

会修改 Production 事实的 Bible/Storyboard Decision 走 `lanverse-api` 同 Binary Coordinator：同一 Unit of Work 先由 Review 写不可变 Decision，再调用 Production 公开接口校验对象版本、应用变更并写 `BibleReviewApplicationReceipt` 或 `StoryboardApplyIntent/Receipt` 及 Outbox；Coordinator 不直接访问双方 Repository。`workflow-worker` 只消费 `production.*.applied` Receipt Event 后发送 Temporal Signal，不再消费该类原始 Decision 触发第二次应用。Temporal 确认后写 `WorkflowSignalReceipt`；重复 Event、进程崩溃或 Signal 返回未知时先按 Decision/Apply Receipt 查询对账，保证一条 Decision 最多产生一次生产效果。

## 1. Access & Membership (`access`)

### 职责与边界

拥有用户身份、注册验证、登录会话、Access Token、Workspace Membership、角色能力、账号停用和全局 Session 撤销，并向其他模块提供不可变 `ActorContext`。

不拥有 Workspace 的名称、生命周期或项目资源；不决定 Shot/Artifact 等领域状态；不保存 Provider 密钥。

### 核心模型

- `UserAccount`、`RegistrationChallenge`、`RegistrationReceipt`、`AuthSession`、`TokenVersion`。
- `WorkspaceMembership`、`RoleDefinition`、`AccessCapabilityDefinition`、`AccessCapabilityGrant`、`AccountEntitlement`。
- `ActorContext`：actor、workspace、membership revision、capabilities、session/token version。

Session 生命周期：`ACTIVE → ROTATED / REVOKED / EXPIRED`。同一 Refresh Token 只能成功轮换一次；检测到重放时撤销该 Session Family。

Registration Receipt 状态：`COMMITTED_SESSION_PENDING → SESSION_ISSUED`；已提交账户不能回退为“未注册”，只能通过幂等补发 Session 或普通 Login 恢复。

### 用例

Commands：`RegisterUser`、`ConfirmRegistration`、`Login`、`RefreshSession`、`Logout`、`ChangePassword`、`DeactivateAccount`、`RevokeAllSessions`、`GrantWorkspaceMembership`、`ChangeWorkspaceRole`、`RevokeWorkspaceMembership`。

Queries：`GetCurrentActor`、`ListWorkspaceMemberships`、`GetWorkspaceMembership`、`ResolveAccessCapabilities`、`ListAccessCapabilityDefinitions`、`GetSessionStatus`。

V1 Access Capability Catalog 由 Access 唯一发布。`workspace:create` 是账户级 Entitlement：V1 默认授予已验证且未停用的账户，并受平台 Workspace 数量策略限制，不依赖一个尚不存在的 Membership。其余首批 Workspace Access Capability 为：`production:create`、`production:edit`、`authoring:edit`、`authoring:publish`、`workflow:start`、`workflow:retry`、`workflow:cancel`、`review:claim`、`review:decide`、`asset:upload`、`asset:publish`、`asset:manage_readiness`、`asset:manage_rights`、`copilot:invoke`、`copilot:apply_tool`、`workspace:manage_members`、`workspace:manage_policy`、`workspace:view_audit`。前端只能消费这些机器标识控制可见性；Backend 仍须在每个 Command 上重新授权。

Events：`access.user.registered.v1`、`access.user.password_changed.v1`、`access.user.deactivated.v1`、`access.membership.granted.v1`、`access.membership.role_changed.v1`、`access.membership.revoked.v1`、`access.sessions.revoked.v1`。

### 失败与验收

- 验证码过期、密码错误、Session 重放、Token Version 失效和并发角色变更返回不同机器错误码。
- Redis/Session 依赖故障时认证失败关闭，不能降级成匿名放行。
- `CreateWorkspace` 在没有 Workspace Context 时验证 `workspace:create` Account Entitlement；创建成功后原子产生 Workspace 与 Owner Membership，此后所有 Workspace Capability 都从 Membership 解析。
- 修改密码、停用账户和全局撤销后，旧 Access/Refresh 材料均失效。
- 跨 Workspace 访问不能泄漏资源是否存在；日志/Event/Trace 不包含密码、验证码、JWT 或 Cookie。

当前映射：`agent/app/modules/identity`、`agent/app/core/auth.py`、Redis Session Adapter 和 Workspace Member 语义。

## 2. Production Management (`production`)

### 职责与边界

拥有生产层级 `Workspace → Project → Episode → Scene → Shot`，以及 Script、Production Bible、Character/Location 剧情规格版本和这些规格到可复用 Asset Version 的生产绑定。

不执行 Workflow/Agent/模型/媒体任务，不保存文件字节，不解析 Effective Policy，不管理审核队列。

### 核心模型

- `Workspace`、`Project`、`Episode`、`Scene`、`Shot`。
- `ScriptVersion`、`ProductionBibleVersion`、`CharacterSpecificationVersion`、`LocationSpecificationVersion`。
- `ProductionAssetBinding`、`ProductionAssetOccurrenceBinding`、`CurrentVersionBinding`、`ProductionSnapshot`、`ShotOrder`。
- `BibleReviewApplicationReceipt`、`StoryboardApplyIntent`、`StoryboardApplyReceipt`。

Project 生命周期固定为 `ACTIVE / ARCHIVED`；Episode 为 `DRAFT / IN_PRODUCTION / IN_REVIEW / COMPLETED / CANCELLED`。归档父级使子级只读但不删除历史 Revision/Run 引用；已完成/取消 Episode 只能通过显式新版本或恢复用例继续修改。

### 用例

### 失败与验收

- 拒绝跨 Workspace 引用、父级已归档写入、非法 Shot 顺序和预期版本冲突。
- 已发布内容版本不可原地修改；当前版本指针改变不影响历史 Run。
- Split/Merge/Reorder 必须保持顺序、叙事引用、资产引用和审计守恒。
- 任一 Workflow Run 都能通过绑定版本还原启动时的完整 Production Snapshot。

当前映射：`projects`、`scripts`、`storyboards` 以及 Production Bible 的角色/地点规格可复用；当前 Bible Entity → Asset 的显式绑定迁移为 `ProductionAssetBinding`，Asset 的身份/状态/版本仍归 `asset`。

## 3. Production Preset (`preset`)

### 职责与边界

以版本化声明组合 Style、Skill、Model Policy、QC Policy、Motion Strategy 和 Render Policy，并解析不可变 `EffectivePolicySnapshot`。

不执行模型、Agent、QC 或 Render；不保存 Provider Credential；不按“真人/漫剧”在 Workflow 中写硬编码分支。

### 核心模型

- `Preset`、`PresetVersion`、`StyleProfile`、`StyleVersion`。
- `ModelPolicyRef`、`SkillVersionRef`、`QCPolicyRef`、`MotionPolicy`、`RenderPolicyRef`。
- `ProjectPolicyOverride`、`ShotPolicyOverride`、`EffectivePolicySnapshot`、`PolicyReferenceValidationReceipt`。

解析优先级固定为 `Shot Override > Project Override > Preset > System Default`。相同输入版本必须得到相同 `effective_policy_hash`。

### 用例

Commands：`CreatePresetDraft`、`PublishPresetVersion`、`RetirePresetVersion`、`PublishStyleVersion`、`BindProjectPresetVersion`、`SetProjectPolicyOverride`、`SetShotPolicyOverride`。

Queries：`ListPresetVersions`、`GetPresetVersion`、`ResolveEffectivePolicy`、`ExplainPolicyResolution`。

Events：`preset.version.published.v1`、`preset.binding.changed.v1`、`preset.style.version_published.v1`、`preset.override.changed.v1`。

### 失败与验收

- 引用不存在/已退役、Generation Capability 不满足、Skill 输出 Schema 不兼容和非法 Override 必须阻止发布。
- `PublishPresetVersion` 同步调用 Generation 的版本化 Generation Capability/Model Policy Catalog 和 Agent 的签名 Definition Manifest 做强校验，保存双方返回的版本/Hash Receipt；任一 Catalog 不可用时发布 fail closed，不能改用异步投影猜测合法性。
- Workflow 只消费已冻结 Snapshot，不在运行中重新解析可变 Preset。
- 扩展新内容类型优先新增 Preset/Policy，不复制 Workflow 或 Agent。

当前映射：已有 Skill、Generation Capability、Storyboard/Production Bible Harness 版本可复用；正式 Preset/Style 聚合尚未实现。

## 4. Authoring (`authoring`)

### 职责与边界

统一 Guided 与 Canvas 的可变 Draft 和不可变 Revision，拥有 Node Definition Catalog、Graph/Port Validation、GraphPatch、版本 Diff、Publish 和协作 Snapshot 提交。

不启动 Temporal、不调用 Provider/Agent、不写 Production 内部表；Yjs update log 是恢复投影，不是 Authoring 业务事实。

### 核心模型

- `AuthoringDraft`、`AuthoringRevision`、`AuthoringGraph`。
- `NodeDefinitionVersion`、`AuthoringNode`、`AuthoringEdge`、`VariableBinding`。
- `GraphPatch`、`GraphPatchApplicationIntent`、`GraphPatchApplicationReceipt`、`GraphValidationReport`、`GraphDiff`、`DocumentEpoch`。

`authoring_mode=GUIDED|CANVAS` 仅是来源元数据。Revision 冻结 Graph、Preset/Policy/Prompt/Skill/Node Catalog 版本和输入 Artifact 引用。

### 用例

Commands：`CreateAuthoringDraft`、`CommitDraftSnapshot`、`ApplyGraphPatch`、`RebaseAuthoringDraft`、`PublishAuthoringRevision`、`DuplicateAuthoringRevision`、`PublishNodeDefinitionVersion`、`RetireNodeDefinitionVersion`。

Queries：`GetAuthoringDraft`、`GetAuthoringRevision`、`DiffAuthoringRevisions`、`ListNodeDefinitions`、`ValidateGraphPatch`、`ValidateAuthoringGraph`、`GetGraphPatchApplication`、`ExplainGraphChanges`。

Events：`authoring.graph_patch.application_requested.v1`、`authoring.graph_patch.applied.v1`、`authoring.graph_patch.rejected.v1`、`authoring.draft.snapshot_committed.v1`、`authoring.revision.published.v1`、`authoring.node_definition.version_published.v1`。

### Copilot/Agent GraphPatch 应用协议

1. Agent 只返回绑定 `draft_id`、base revision、Document Epoch、Yjs State Vector、Patch Hash 和目标节点版本的不可变 `GraphPatch` Proposal，不直接修改 Yjs。
2. Frontend 调用无副作用的 `ValidateGraphPatch` 生成 Preview。用户确认后调用 `ApplyGraphPatch`；普通 Canvas Agent 至少需要 `authoring:edit`，Copilot Tool 同时需要 `copilot:apply_tool ∧ authoring:edit`。
3. Backend 在修改协作态前完成权限、对象版本、Graph/Port、预算与 Patch Hash 校验，创建幂等 `GraphPatchApplicationIntent`，并给 Collab Runtime 签发只可使用一次、绑定 Application ID/Epoch/State Vector 的 Apply Grant。
4. Collab Runtime 只在 Epoch/State Vector 仍匹配时以 `application_id` 执行一次 Yjs Transaction，并返回新 State Vector/Graph Hash Receipt；Frontend 不自行先改 Yjs。
5. Backend 验证 Receipt 后执行 `CommitDraftSnapshot` 并将 Application 标为 `APPLIED`。若远程结果未知，则按 `application_id` 查询 Yjs Transaction Marker 对账，不能生成第二个 Patch；只有持久 Snapshot 成功后 UI 才显示完成。

该协议是一个带 Intent/Receipt 的可补偿协调，不把 Yjs update 变成业务事实。Backend 校验失败发生在 Yjs 修改前；Collab 已应用但 Snapshot 尚未提交时进入 `outcome_unknown` 对账，不能由前端静默回滚或伪报成功。

### 失败与验收

- base revision/document epoch 过期、GraphPatch 冲突、未知 Node 版本、端口不兼容、非法环和权限节点必须分别报告精确 path。
- 一般环禁止发布；Loop 必须声明最大迭代、预算和终止条件。
- 坐标、颜色、Frame、Comment、Viewport 不改变执行语义；Prompt、连接、输入 Artifact、Policy/Skill 变化进入 Graph Diff。
- Guided 和 Canvas 必须发布同一 Revision Schema。

当前映射：Script/Storyboard Version 与现有 Guided 页面可作为基线；Node Catalog、统一 Authoring、Canvas/Yjs 尚未实现。

## 5. Workflow Execution (`workflow`)

### 职责与边界

拥有 Workflow Compiler、不可变 Definition Version、Workflow/Node Run 业务投影、Temporal Workflow/Activity、Human Gate、Retry/Cancellation、Execution Dirty Set 和 Node Cache。

不保存活动 Canvas，不修改 Production 内容，不把 Kafka/LangGraph 当成 Episode 编排器。

### 核心模型

- `WorkflowDefinitionVersion`、`CompilationReceipt`、`WorkflowRun`、`NodeRun`。
- `WorkflowStartIntent/Receipt`、`WorkflowControlIntent/Receipt`、`WorkflowSignalReceipt`。
- `RunInputSnapshot`、`ActivityAttempt`、`HumanWaitBinding`。
- `ExecutionDirtySet`、`NodeCacheKey`、`NodeCacheEntry`、`FailureRecord`。
- `QCReportRef`、`QualityGateResult`、`RepairAttempt`。

Run 状态使用 V1 统一枚举；等待原因另存为 `HUMAN_SIGNAL / PROVIDER_RESULT / CHILD_WORKFLOW / RETRY_BACKOFF / EXTERNAL_SIGNAL`。

### 用例

Commands：`CompileAuthoringRevision`、`StartWorkflowRun`、`PauseWorkflowRun`、`ResumeWorkflowRun`、`CancelWorkflowRun`、`RetryNodeRun`、`RetryShotWorkflow`、`RunWorkflowSelection`、`SignalHumanDecision`、`RecordQCReport`、`EvaluateQualityGate`、`RequestQualityRepair`、`ReconcileWorkflowIntent`、`ReconcileUnknownActivity`、`InvalidateNodeCache`。

Queries：`GetWorkflowDefinitionVersion`、`GetWorkflowRun`、`ListNodeRuns`、`GetRunTimeline`、`GetQualityGateResult`、`ExplainWorkflowFailure`、`ExplainCacheDecision`。

Events：`workflow.definition.compiled.v1`、`workflow.run.start_requested.v1`、`workflow.run.started.v1`、`workflow.run.human_wait_started.v1`、`workflow.node_run.succeeded.v1`、`workflow.node_run.failed.v1`、`workflow.quality_gate.passed.v1`、`workflow.quality_gate.failed.v1`、`workflow.quality_gate.repair_requested.v1`、`workflow.quality_gate.review_required.v1`、`workflow.run.succeeded.v1`、`workflow.run.failed.v1`。

### Quality Gate 契约

- Media 负责分辨率、时长、Codec、静帧等确定性技术检测；Agent 通过版本化 Skill 负责图像/视频语义、一致性和剧本符合度 QC。
- 每份结构化 `QCReport` 都登记为 Artifact，冻结 detector/agent/skill/model/schema/policy 版本和被测 Artifact ID。
- Workflow 是 `QualityGateResult` 的唯一 Owner，按 `QCPolicyVersion` 汇总报告为 `PASS / REPAIR / HUMAN_REVIEW / FAIL`。
- `REPAIR` 只能启动 Policy 允许次数与预算内的 Repair Activity；超限进入 Human Task 或 FAIL，禁止无限循环。
- 人工 Override 只能通过绑定同一报告/对象版本的 ReviewDecision；Workflow 记录 override causation 后继续，不能改写原 QCReport。

### 失败与验收

- Temporal 不可用、Workflow 非确定性、Activity timeout/retry exhaustion、取消竞态、失效 Human Task 和未知远程结果必须有独立恢复路径。
- Worker/服务重启后 Run 可恢复；Activity 重试不能重复费用、Candidate 或 Artifact。
- 单 Shot 失败只重跑当前 Shot；Human Gate 可跨天等待且不占 Worker。
- 旧 Workflow 版本继续完成，新 Run 使用显式新版本；同一 Run 不被旧 Kafka 与 Temporal 双驱动。

当前映射：现有 Task、Lease、Checkpoint、Scheduler/Kafka Consumer 提供行为基线，但最终编排所有权必须转移到 Temporal。

## 6. Review (`review`)

### 职责与边界

拥有统一人工任务队列、审核对象快照、领取/指派、不可变决议、理由和历史。自动 QC 只作为审核证据。

不直接修改被审核对象，不执行 QC Agent，不维护 Workflow 状态机。

### 核心模型

- `HumanTask`、`ReviewSubjectRef`、`ReviewSubjectSnapshot`。
- `ReviewDecision`、`ReviewDecisionType`、`QCReportRef`、`Assignee`。

Task 状态：`WAITING / CLAIMED / RESOLVED / CANCELLED / STALE`；Decision：`APPROVE / REJECT / SELECT / REGENERATE / EDIT / SKIP`。

### 用例

Commands：`OpenHumanTask`、`ClaimHumanTask`、`RenewHumanTaskClaim`、`ReleaseHumanTaskClaim`、`AssignHumanTask`、`ExpireHumanTaskClaim`、`RecordReviewDecision`、`CancelHumanTask`、`MarkHumanTaskStale`。

Queries：`ListHumanTasks`、`GetHumanTask`、`GetReviewSubjectPreview`、`ListReviewHistory`、`ListPendingHumanTasksForRun`。

Events：`review.human_task.opened.v1`、`review.human_task.claimed.v1`、`review.human_task.claim_released.v1`、`review.human_task.claim_expired.v1`、`review.decision.recorded.v1`、`review.human_task.cancelled.v1`、`review.human_task.marked_stale.v1`。

### 失败与验收

- 决议必须绑定精确对象版本；对象变化时旧 Task 转为 `STALE`。
- Claim Lease 到期只执行 `CLAIMED → WAITING` 并记录 `claim_expired`，不把 Human Task 变成不存在的 `EXPIRED` 终态，也不产生 Review Decision。
- 同一 Task 只能有一个终态决议；重复提交幂等并只触发一次 Workflow Signal。
- 决议保留 actor、能力、理由、时间、对象版本、trace 和幂等键。
- Signal 结果未知时进入对账，不能再次写第二条 Decision。

当前映射：Extraction/Storyboard/Coverage Decision 等分散决议可迁移；统一 Review Queue 尚未实现。

## 7. Generation Gateway (`generation`)

### 职责与边界

统一 LLM、Vision、Embedding、Moderation、Image、Video、TTS 等 Provider 调用，拥有 Generation Capability Registry、Model Policy 路由、Provider 报价、Fallback、Rate Limit、短时 Inference Invocation、异步 Provider Job、Callback Receipt、Candidate 和 Usage Report。

不控制 Episode Workflow，不拥有最终 Cost Ledger，不执行人工选择，不把 Provider URL 写到 Shot。

### 核心模型

- `ProviderConnection`、`ProviderCredentialVersion`、`GenerationCapabilityDefinition`、`ModelPolicyVersion`、`ProviderPriceQuoteVersion`。
- `InferenceInvocation`、`InferenceResult`、`StructuredOutputSchemaRef`。
- `GenerationSubmissionIntent`、`GenerationSubmissionReceipt`、`GenerationRequest`、`ProviderJob`、`GenerationCandidate`、`CandidateSelection`。
- `ProviderCallbackReceipt`、`ProviderUsageReport`、`ProviderHealth`。

Provider Job 状态：`CREATED / SUBMITTED / WAITING_CALLBACK / SUCCEEDED / FAILED / CANCELLED / UNKNOWN`。

`GenerationSubmissionIntent` 是 Generation 拥有的跨 Binary 持久提交意图，不是 Workflow Run，也不复制 Provider Job。Generation 的 Submission Intent ingress 以公开 Application Interface 装配在 `lanverse-api`，且只有该 ingress 写 Intent；Cost/Quota Coordinator 在同一 PostgreSQL Unit of Work 中创建两类 Reservation、调用 ingress 创建 Intent 并写 Outbox。Outbox 只含 Intent/Request Hash/Reservation Ref，不含尚未领取的 Authorization。

`model-gateway` 的 Intent Consumer 收到事件后先调用 API `AcquireExecutionClaim`，成功才按 Intent ID、Claim Version 和 Request Hash 幂等创建 `GenerationRequest`/Provider Job，并写 `GenerationSubmissionReceipt`。Intent 状态为 `PENDING / EXECUTION_CLAIMED / CANCEL_REQUESTED / ACCEPTED / REJECTED / CANCELLED / OUTCOME_UNKNOWN`：`PENDING` 可取消并原子释放 Reservation；Claim 后取消只进入 `CANCEL_REQUESTED`，不得释放，直到 Provider 取消/拒绝 Receipt 明确；未知结果进入 `OUTCOME_UNKNOWN` 并把两类 Reservation 置为 `RECONCILING`。

Gateway 在同一事务写 Receipt 与 `generation.submission_receipt.*.v1` Outbox；`lanverse-api` 的专用 Consumer Group `generation-submission-intent-updater.v1` 消费 `lanverse.generation.v1`，以 Inbox Receipt 和 `intent_id + claim_id + claim_version + request_hash` 栅栏调用 ingress 推进 Intent/Reservation。迟到或旧 Claim Receipt 进入隔离，不覆盖当前状态。提交后签名前崩溃由 Outbox 重投恢复；Claim 后崩溃必须先按稳定 Provider Request Key 对账，禁止新建 Intent 或无条件重签。

### 用例

Commands：`RecordGenerationSubmissionIntent`、`AcquireExecutionClaim`、`AcceptGenerationSubmissionIntent`、`RejectGenerationSubmissionIntent`、`RequestGenerationSubmissionCancellation`、`CancelGenerationSubmissionIntent`、`MarkGenerationSubmissionOutcomeUnknown`、`ReconcileGenerationSubmissionIntent`、`SubmitGenerationRequest`、`CancelProviderJob`、`AcceptProviderCallback`、`PollProviderJob`、`ReconcileProviderJob`、`RegisterGenerationCandidate`、`ApplyCandidateSelection`、`PublishModelPolicyVersion`、`PublishProviderPriceQuoteVersion`、`ActivateGenerationCapability`、`DeactivateGenerationCapability`。`SubmitGenerationRequest` 必须绑定覆盖目标 Generation Capability 和最大尝试成本的 `ExecutionAuthorization` 与当前 Claim Version；Fallback 只能在同一 Claim 范围内发生。

Queries：`ListGenerationCapabilities`、`GetModelPolicyVersion`、`ValidateGenerationPolicyReferences`、`ExplainGenerationRoute`、`GetGenerationSubmissionIntent`、`GetGenerationRequest`、`GetInferenceInvocation`、`GetProviderJob`、`ListGenerationCandidates`、`GetProviderHealth`。

Events：`generation.inference.succeeded.v1`、`generation.inference.failed.v1`、`generation.submission_intent.recorded.v1`、`generation.submission_intent.execution_claimed.v1`、`generation.submission_intent.cancellation_requested.v1`、`generation.submission_intent.accepted.v1`、`generation.submission_intent.rejected.v1`、`generation.submission_intent.cancelled.v1`、`generation.submission_intent.outcome_marked_unknown.v1`、`generation.submission_receipt.accepted.v1`、`generation.submission_receipt.rejected.v1`、`generation.submission_receipt.outcome_marked_unknown.v1`、`generation.request.submitted.v1`、`generation.provider_job.submitted.v1`、`generation.candidate.created.v1`、`generation.request.succeeded.v1`、`generation.request.failed.v1`、`generation.provider_job.outcome_marked_unknown.v1`、`generation.candidate.selected.v1`。

Agent 使用独立的短时推理 gRPC：`GenerateText`、`GenerateStructured`、`Embed`、`Moderate`，可选 server stream 但必须以一个持久 `InferenceResult` 收口。每次请求只携带 `ExecutionGrant`、Generation Submission Intent Ref、idempotency key、deadline、Generation Capability/Model Policy 版本和结构化 Schema Hash；Gateway 必须按 Intent Ref 向 API 在线领取当前 Claim 对应的 Cost/Quota `ExecutionAuthorization`，再持久化 Invocation、最终 Usage 与实际 Provider/Model/Adapter。deadline 前结果未知时返回 `outcome_unknown`，调用方先按 invocation ID 对账，不能直接重提。

### 失败与验收

- 无匹配 Generation Capability、Provider 限流/超时、回调验签失败、重复回调、提交结果未知、价格未知和 Fallback 超预算必须可区分。
- Provider Request Key 重试稳定；未知昂贵请求不自动重提，先 Reconcile。
- Provider 成功输出先登记为可校验的 Candidate Artifact；Artifact 达到 `READY` 后才创建 `GenerationCandidate`，选择后才进入下游生产绑定。
- Routing 冻结允许集合和 Catalog/Price 版本，每次 Attempt 记录实际 Provider/Model；Fallback 不得超出冻结集合、预算或 Generation Capability。
- Provider Credential 不出现在 API、Agent、日志、Trace 或 Event。

当前映射：`agent/app/modules/production` 已有 Generation Request、Reservation、Attempt 以及 Generation Capability/Provider Credential 的 Schema 语义；Generation Capability 和四张 Provider 配置表只有读取或测试夹具引导，没有生产管理 Writer，不能视为已接入 Catalog。目标图片/视频能力仍需真实 Provider 验证。

## 8. Agent Orchestration (`agent`)

### 职责与边界

Agent 不连接 PostgreSQL、ObjectStore、Yjs，不掌控 Episode Workflow，不直连 Provider，不拥有任意 Shell 或网络权限。

### 核心模型

- `AgentInvocation`、`ExecutionGrant`、`ExecutionBudget`、`AgentRun`、`AgentResult`、`EvaluationResult`。
- `CopilotConversation`、`CopilotTurn`、`ConversationContextRef`；Conversation 属于精确 Workspace/Project，可选绑定 Episode/Draft。

### 用例

Commands：`RegisterAgentDefinitionBundle`、`ActivateAgentDefinitionVersion`、`InvokeAgent`、`CancelAgentRun`、`EvaluateAgentResult`、`CreateCopilotConversation`、`SubmitCopilotTurn`、`ArchiveCopilotConversation`。需要模型的 `InvokeAgent` 和 `SubmitCopilotTurn` 必须绑定限定 Agent/Tool/Generation Capability/预算的 Expensive Operation Intent Ref，并在准备事务中创建 Reservation；Agent/Gateway 开始执行时凭 Intent Ref 调用 `AcquireExecutionClaim`，只在当前执行进程中持有派生的 `ExecutionAuthorization`。纯规则执行可显式声明 `NO_PROVIDER_COST`，但仍受 `ExecutionGrant` 约束。

Queries：`ListAgentDefinitions`、`GetAgentDefinitionVersion`、`ValidateAgentDefinitionReferences`、`GetAgentRun`、`ListSkillVersions`、`ExplainAgentBudgetUsage`、`GetCopilotConversation`、`ListCopilotConversations`。

### 失败与验收

- 输出 Schema 无效、Tool 拒绝、预算耗尽、step/call 上限、checkpoint 不兼容和 Runtime 不可用分别可诊断。
- 每次 Run 有 `max_steps/model_calls/tool_calls/tokens/cost/deadline`；Structured 用例默认不用 LangGraph。
- Tool Allowlist、参数 Schema 和资源归属均在 Backend 验证。
- 每个结果可追踪 Agent/Skill/Prompt/Model/Schema 版本，并通过现有 Golden/Contract Fixture。
- Copilot 只持久化已接受的 User Turn、Tool Receipt 和最终 Assistant Turn；in-flight token buffer 不进入 Conversation。所有读取/提交重新检查 Workspace Access Capability，对象 Stale 时禁止应用 Tool/GraphPatch。

当前映射：`modules/skills`、Storyboard/Production Bible Harness、Codex Local Adapter 及相应 Golden/Contract Test。

## 9. Asset Registry (`asset`)

### 职责与边界

统一逻辑 Asset 与不可变 Artifact，拥有上传会话、版本、哈希、血缘、引用、访问授权、Storage Profile、对象位置，以及内容/主体使用权的 Consent Version 与 Proof Binding。

不做模型推理或媒体解码/渲染；业务层不直接依赖 MinIO SDK。

### 核心模型

- `Asset`、`AssetState`、`AssetVersion`、`AssetBinding`。
- `Artifact`、`ArtifactLineage`、`ArtifactUsage`、`ArtifactLocation`。
- `UploadSession`、`StorageProfile`、`IntegrityRecord`、`ArtifactReadinessRecord`、`RetentionPolicy`、`AccessGrant`。
- `RightsSubject`、`Consent`、`ConsentVersion`、`ConsentProofBinding`、`ContentUsageScope`。

Artifact 内容和 Hash 创建后不可变；`ArtifactReadiness` 是与内容身份分离的 Asset 事实，状态为 `PENDING_VALIDATION / READY / QUARANTINED / UNAVAILABLE / TOMBSTONED`。正常注册从 `PENDING_VALIDATION` 经完整性校验进入 `READY`；安全隔离进入 `QUARANTINED`，全部有效位置丢失进入 `UNAVAILABLE`，保留期结束进入终态 `TOMBSTONED`。恢复只改变 Readiness/Location，不改变 Artifact ID 或 Hash；清理对象字节后仍保留 Tombstone、血缘与审计身份。

### 用例

Commands：`CreateUploadSession`、`CompleteUploadSession`、`RegisterArtifact`、`VerifyArtifactIntegrity`、`QuarantineArtifact`、`RestoreArtifactReadiness`、`TombstoneArtifact`、`PurgeExpiredArtifactContent`、`CreateAsset`、`PublishAssetVersion`、`SetCurrentAssetVersion`、`ArchiveAsset`、`CreateArtifactDownloadGrant`、`MigrateArtifactLocation`、`RollbackArtifactLocation`、`CreateConsent`、`PublishConsentVersion`、`AttachConsentProof`、`RevokeConsent`。

Queries：`GetArtifact`、`GetAsset`、`ListAssetVersions`、`GetArtifactLineage`、`ListArtifactUsages`、`GetArtifactReadiness`、`ListArtifactLocations`、`GetConsent`、`ListConsents`、`ValidateArtifactUsageRights`。

Events：`asset.artifact.registered.v1`、`asset.artifact.integrity_verified.v1`、`asset.artifact.quarantined.v1`、`asset.artifact.readiness_restored.v1`、`asset.artifact.marked_unavailable.v1`、`asset.artifact.tombstoned.v1`、`asset.artifact.content_purged.v1`、`asset.location.migrated.v1`、`asset.version.published.v1`、`asset.current_version.changed.v1`、`asset.consent.version_published.v1`、`asset.consent.revoked.v1`。

### 失败与验收

- 上传过期、大小/Hash 不符、对象缺失、Primary Location 不唯一、迁移 Checksum 不符和版本被使用分别阻止提交。
- Browser 通过 Presigned URL 直传；失败重试不产生重复 Artifact；只有 `READY` Artifact 可进入 Candidate 选择、Asset Version 发布或 Render 输入。
- Download Grant 对 `QUARANTINED / UNAVAILABLE / TOMBSTONED` 默认拒绝；恢复需要完整性校验 Receipt，Tombstone 不可恢复。
- Consent 必须绑定权利主体、精确内容/Asset/Artifact 范围、用途、地域、期限与不可变 Proof Artifact；过期、撤销或范围不匹配时发布/生成/导出 fail closed。
- Storage 切换不改变 Artifact ID；历史 Revision 永远引用原固定版本。
- ObjectStore SDK/Credential 只存在 Adapter。

当前映射：`modules/assets`、`modules/media` 的对象、版本、位置、血缘、上传与 MinIO Port 可复用，`modules/governance` 的 Consent/Revision/Proof 迁入 Rights & Consent 子域。当前 `ast_asset_occurrences` 是 Narrative Unit Version ↔ Asset State 的生产绑定，迁入 `production`；当前 `med_media_versions` 同行混存不可变内容元数据与可变 Probe 字段，迁移时必须拆成 Asset Artifact 事实和 Media Probe Receipt，不能让两个模块按列共写旧表。

## 10. Media Processing (`media`)

### 职责与边界

负责媒体探测、缩略图、Proxy、转码、字幕、音频混合、Motion、Render 和 Export。

不调用生成模型，不选择 Candidate，不拥有 Workflow 或 Artifact 元数据事实。

### 核心模型

- `MediaProbeResult`、`MediaDerivativeReceipt`、`MotionPlan`。
- `RenderManifest`、`MediaJob`、`RenderReceipt`、`ExportReceipt`。

`RenderManifestVersion` 是不可变的目标合成规格，固定画布、帧率、时基、轨道、字幕/音频策略、全部输入 Artifact Version 和输出 Profile；它不同于当前 Storyboard 导出包使用的 `StoryboardExportManifest`，迁移时不能把二者视为同一事实。

### 用例

Queries：`GetMediaJob`、`GetMediaProbeResult`、`GetRenderManifest`、`ListMediaDerivatives`、`GetMediaCapabilities`。

Events：`media.render_manifest.published.v1`、`media.probe.succeeded.v1`、`media.derivative.created.v1`、`media.job.outcome_marked_unknown.v1`、`media.job.reconciled.v1`、`media.render.started.v1`、`media.render.succeeded.v1`、`media.render.failed.v1`、`media.export.succeeded.v1`。

### 失败与验收

- 损坏文件、Codec 不支持、Manifest 引用缺失、FFmpeg timeout、磁盘不足、Worker 丢失和输出 Hash 不符可独立诊断。
- 相同 Manifest Version + Idempotency Key 重试不产生重复最终 Artifact。
- Preview/Final 都注册新 Artifact，不覆盖输入；Manifest 精确绑定全部输入版本。
- Worker 重启后可恢复或安全重试；`UNKNOWN` Job 未完成对账前不得新建等价 Job。

当前映射：现有 ffprobe、存储清理、位置迁移和 Storyboard Export 可复用；`med_media_versions` 的 `probe_*`、width/height/duration/codec/container 字段迁为 `MediaProbeResult`，Asset 只接收结果 Receipt 推进 Readiness。完整 FFmpeg Render 尚未实现。

## 11. Cost Control (`cost`)

### 职责与边界

拥有价格快照、估价、预算预留、结算、释放、调整和 Budget。Quota 是独立事实 Owner；高成本授权由 Application Coordinator 在同一事务协调 Cost 与 Quota。

不执行模型/媒体任务，不用 Redis 余额替代账本，不决定 Provider 质量路由。

### 核心模型

- `PriceSnapshot`、`CostEstimate`、`CostReservation`、`CostLedgerEntry`。
- `BudgetPolicy`、`CurrencyAmount`、`UsageCostDimension`。

Reservation 状态：`RESERVED / EXECUTION_CLAIMED / SETTLED / RELEASED / EXPIRED / RECONCILING`。

### 用例

Commands：`EstimateCost`、`ReserveCostBudget`、`ClaimCostReservationForExecution`、`SettleCostReservation`、`ReleaseCostReservation`、`ExpireCostReservation`、`BeginCostReconciliation`、`ReconcileCostReservation`、`AdjustCostLedger`、`ConfigureBudgetPolicy`。

Queries：`GetCostBreakdown`、`GetCostReservation`、`GetRemainingBudget`、`ListCostLedgerEntries`、`GetProviderCostReconciliation`。

Events：`cost.reservation.created.v1`、`cost.reservation.execution_claimed.v1`、`cost.reservation.settled.v1`、`cost.reservation.released.v1`、`cost.reservation.expired.v1`、`cost.reservation.reconciliation_started.v1`、`cost.reservation.reconciled.v1`、`cost.ledger.adjusted.v1`、`cost.budget.threshold_reached.v1`。

### 失败与验收

- 价格未知、并发超预算、重复结算、币种不一致和 Unknown Outcome 长期占用预留可对账。到期且确认未执行的 Reservation 进入 `EXPIRED`；执行结果未知的 Reservation 进入 `RECONCILING`，只能凭 Provider/Media Usage Receipt 结算或释放。
- 金额使用定点 Decimal + Currency；Reserve/Settle/Release 全幂等。
- 高成本操作前必须持有有效 Cost Reservation；Redis 故障时 fail closed，PostgreSQL Ledger 仍是事实源。
- 可按 Workspace/Project/Episode/Shot/Node/Agent/Provider/Model 聚合。

当前映射：现有生产预留、费用条目、Generation Preflight 的金额与预算语义可复用。

## 12. Quota Control (`quota`)

### 职责与边界

拥有 Workspace/Project/Generation Capability/操作类型维度的 Quota Policy、Usage Window、Quota Reservation、Counter 和授权决议。Quota 表达“允许使用多少次/多少单位”，不保存金额、不替代 Cost Ledger。

### 核心模型

- `QuotaPolicy`、`QuotaLimit`、`QuotaUsageWindow`、`QuotaCounter`。
- `QuotaReservation`、`QuotaDecision`、`UsageDimension`。

Quota Reservation 状态：`RESERVED / EXECUTION_CLAIMED / CONSUMED / RELEASED / EXPIRED / RECONCILING`。

### 用例

Commands：`ConfigureQuotaPolicy`、`ReserveQuotaUsage`、`ClaimQuotaReservationForExecution`、`ConsumeQuotaReservation`、`ReleaseQuotaReservation`、`ExpireQuotaReservation`、`BeginQuotaReconciliation`、`ReconcileQuotaUsage`、`ResetQuotaWindow`。

Queries：`GetQuotaPolicy`、`GetQuotaUsage`、`GetQuotaReservation`、`ExplainQuotaDecision`、`ListQuotaWindows`。

Events：`quota.policy.configured.v1`、`quota.usage.reserved.v1`、`quota.usage.execution_claimed.v1`、`quota.usage.consumed.v1`、`quota.usage.released.v1`、`quota.usage.expired.v1`、`quota.usage.reconciliation_started.v1`、`quota.usage.reconciled.v1`、`quota.limit.exceeded.v1`。

### 高成本授权协调

高成本授权由 `PrepareExpensiveOperation` 与 `AcquireExecutionClaim` 两个 Application Coordinator 用例完成，不属于 Cost 或 Quota 聚合：

1. 读取固定 `CostEstimate` 和预计 Usage Dimension。
2. `PrepareExpensiveOperation` 在同一 PostgreSQL Unit of Work 中创建 `CostReservation(RESERVED)`、`QuotaReservation(RESERVED)`、对应业务 Intent 与 Outbox；任一事实创建失败整体回滚，Event 只传引用与 Hash。
3. Worker/Gateway 消费 Intent 后调用 `AcquireExecutionClaim`；API 按固定锁顺序锁 Intent、Cost、Quota，验证仍为 `PENDING/RESERVED` 后原子写同一 `claim_id/claim_version`，并将三者置为 `EXECUTION_CLAIMED`。这一步与取消/释放互斥。
4. API 返回该 Claim 派生的短时签名 `ExecutionAuthorization`；Token 不落表、不过 Kafka。提交后签名前崩溃靠原 Outbox 重投重新领取，Kafka 延迟不会让 Token 预先过期。
5. Receipt 为已知成功时结算 Cost/消费 Quota；已知未执行时释放；未知或 Claim 后进程丢失且无法证明 Provider 未调用时，将 Intent 与两类 Reservation 置为 `OUTCOME_UNKNOWN/RECONCILING` 并按稳定 Request Key 对账。

### 失败与验收

- 并发请求不能越过同一窗口限额；Policy Revision 变化不影响已签发 Authorization。
- Quota Reserve/Consume/Release 全幂等，Counter 不允许负数或重复消费。
- Claim 后的取消只能记录 `CANCEL_REQUESTED`，不能释放 Cost/Quota；迟到 Receipt 必须匹配 Claim Version，旧 Claim 结果隔离。
- Redis 可用于快速拒绝与窗口缓存，但故障时高成本操作 fail closed，PostgreSQL Counter 是事实源。
- Cost 金额不足与 Quota 次数不足返回不同错误和可解释剩余额度。

当前映射：Redis High-Cost Guard、当前限流和生产用量字段可作为行为基线；正式 Quota 聚合尚未实现。

### 失败与验收

- 阶段 1 的 Audit v2 Publisher 必须按 Topic allowlist 领取 Outbox；在该 Filter、Topic 注册与 v2 Consumer 就绪前禁止插入 Audit v2 Outbox。v2 Producer 的稳定 idempotency key 防止命令重试重复建事件；同一 Aggregate 可在不同 revision 重复产生同类型事件。

当前映射：现有 `messaging` Outbox/Inbox/Envelope/幂等和 Scheduler Publisher 可作为迁移基线；`backend/api/event/event-envelope-v2.schema.json` 与 `internal/eventing/domain` 已固定严格 v2 包络及 JSON payload，旧 Publisher 已强制使用 IO/Media Topic allowlist。`lanverse.audit.v2`、Consumer Group、独立 Inbox/AuditRecord/Checkpoint、Backfill 与 Query 切换仍未实现，`gov_audit_events` 继续是当前唯一审计资源。

## 15. Platform Runtime (`bootstrap` + `config/database/cache/telemetry`)

### 职责与边界

`bootstrap` 负责五个 Binary 的依赖装配、启动、Drain 和关闭；`config/database/cache/telemetry` 分别提供配置与 Secret、DB/Migration、Cache、HTTP/gRPC 运行支撑、Telemetry 与 Health Adapter。它们逻辑上属于 Platform Runtime，但不合并成新的物理 `platform` package。

这些边界不拥有业务状态机、权限规则或 Provider 策略，不创建全局 `utils/service/repository`。

### 运行结构

- `RuntimeConfig`、`ServiceIdentity`、`DependencyStatus`、`SchemaVersion`、`BuildInfo`。
- 运维入口：`migrate`、`config-check`、`serve`、`drain`。
- HTTP：`/healthz`、`/readyz`、`/metrics`、`/version`。

### 失败与验收

- 配置缺失、Schema 不兼容、关键依赖不可用、Migration Lock、优雅关闭超时和 Telemetry 背压必须影响正确的 Readiness/Degraded 状态。
- 一个 `go.mod` 构建五个真实 Binary；每个 Binary 只装配所需模块和最小权限凭据。
- Migration 是唯一生产 Schema Owner；SIGTERM 先停止接流量，再 Drain Activity/Consumer，最后关闭连接。
- Secret 不进入命令行、日志、Metric Label 或 Trace Attribute；Trace 贯穿 HTTP→Temporal→Agent/Generation/Media→Kafka。

当前映射：Go `cmd/api` 已实现 `/healthz`、包含兼容运行时探测的 `/readyz`、有界标签 `/metrics` 与构建身份 `/version`；`agent/app/core`、`agent/app/integrations`、`agent/app/runtime` 的配置、日志、Telemetry 和 Schema Guard 仍作为迁移基线。Baseline Migration、统一错误/认证 Context 与其余 Binary Runtime 尚未实现。

## 最小完整闭环验收

```text
注册/登录
→ 创建 Workspace/Project/Episode
→ 绑定不可变 PresetVersion
→ 发布 ScriptVersion 与 AuthoringRevision
→ Compiler 生成 WorkflowDefinitionVersion
→ Temporal 启动 WorkflowRun
→ Agent 生成结构化 Storyboard
→ Cost/Quota 准备 Reservation，Gateway 在线领取 Execution Claim/Authorization
→ Generation Gateway 提交 Provider Job
→ Asset Registry 登记并校验 Candidate Artifact
→ Generation Gateway 登记 GenerationCandidate
→ Media/Agent 产出 QC Report，Workflow 写 QualityGateResult
→ Review 记录选择决议，Generation 固化 CandidateSelection 并恢复 Workflow
→ Media Worker 按 RenderManifest 输出最终 MP4
→ Cost 结算、Quota 消费
→ Outbox/Kafka 投影
→ Search 可检索
```

验收必须重复注入 HTTP Command、Temporal Activity、Provider Callback 和 Kafka Delivery，并重启各 Worker，确认不会产生重复业务事实、重复费用、重复 Candidate 或重复 Artifact。
