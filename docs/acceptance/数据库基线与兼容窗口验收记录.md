## 结论

数据库已经从 Python 生产期 `create_all` 切换到唯一 Go Migration 流。第 1 号静态 Baseline 冻结当前 74 张兼容业务表；空库由 `lanverse-migrate` 初始化，已有旧库只能在严格 ORM 一致性审计通过后登记基线。Agent Runtime 随后只校验自身必需资源和允许的 Migration 版本窗口，不会因 Go 新增目标表或列而拒绝启动。

本切片没有新增目标业务表、修改业务列或切换任何 Writer；所有业务资源仍由 Python 兼容实现拥有。

## 实现边界

- `backend/migrations/000001_compatibility_runtime_baseline.sql` 是不可变静态快照，共 178 条 DDL，创建 74 张 `public` 业务表及其约束/索引。
- `backend/cmd/migrate` 在同一事务内取得 `lanverse.schema-migration` Advisory Lock、校验连续版本与已执行 Checksum、应用 Migration 并登记 Receipt；DDL 或 Receipt 任一失败都会整体回滚。
- Migration Receipt 位于 `lanverse_migration.schema_migrations`，不污染业务 `public` Schema；旧版严格 Guard 回滚时不会把它识别为未知业务表。
- 未版本化且已有业务表的数据库会被 Go 迁移器拒绝。只有显式 `adopt-baseline` 命令可以在完整旧 Schema 严格相等后登记 `source=adopted`；该路径不执行或修改业务 DDL。
- Agent 生产启动、API、Scheduler、IO Worker 和 Media Worker 共用只读 Guard：要求版本连续且位于 `1..2`，并逐版本校验允许的 Migration 名称与来源；第 2 号只预批准 `audit_projection_foundation`，为 Consumer-first 发布预留回滚窗口。Guard 同时要求 74 张运行时必需表、列、类型、空值规则和主键完整，允许额外目标表、列、约束和索引。
- Python `create_all` 已从通用数据库命令移除，只保留在隔离开发库和测试 Fixture 的显式初始化函数中。
- Compose 顺序固定为 `database-migrate → agent-init schema-check → API/Workers`；生产 Override 使用已发布 Go Backend 镜像运行同一迁移 Binary。

## Compose、容器与回滚

```bash
docker compose --env-file .env.example \
  -f docker-compose.yml -f docker-compose-env.yml config --quiet
docker compose --env-file .env.example \
  -f docker-compose.yml -f docker-compose-env.yml -f docker-compose-prod.yml \
  config --quiet
docker build --tag lanverse/backend:baseline-migration-verification backend
```

结果：开发/生产 Compose 解析通过；Go 镜像同时包含 `lanverse-api` 与 `lanverse-migrate` 并构建成功。迁移元数据独立于 `public`，因此切流失败时可回滚到仍只认识 74 张业务表的旧运行时；第 1 号 Baseline 不提供破坏性 Down Migration。若 DDL 尚未提交，事务自动回滚；若已成功创建空库，回滚应用版本不删除业务表。

使用 `./scripts/run-local-development.sh` 复用本机服务后，隔离开发库成功登记基线，Agent API、Go API 与 Frontend 均启动；Health、Readiness、Version、Metrics 和 Frontend 分别返回预期结果，验收后已统一停止进程。本机 MinIO 仍因既有凭据不一致报告 `access_denied`，不属于本数据库切片。
