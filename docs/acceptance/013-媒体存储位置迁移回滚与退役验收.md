## 1. 验收结论

1. owner 可对固定 MediaVersion 幂等创建 `media_location_migration` Task；API 只返回 Task 和脱敏 Location 状态，不返回 bucket、object key、永久 URL 或凭据。文件字节不经过 FastAPI。
2. Media Worker 使用 ObjectStoragePort 的服务端 copy 写入由 Task ID 派生的稳定目标 key，并以 HEAD size 与分块 SHA-256 对照不可变 MediaVersion。校验失败删除目标临时副本、保留原 active，不创建第二 MediaVersion。
3. 校验通过后先形成 verified Location，再在同一 PostgreSQL 事务把原 active 改为 retiring、目标改为 active；部分唯一索引和竞争任务测试共同证明同一版本最多一个 active。MediaVersion ID、sha256、size 和业务引用不变。
4. 原位置保存显式 `retire_after`，同时创建唯一 one-off `retire_media_location` Schedule。窗口内可异步回滚；Worker 再次校验目标字节后切回 active，并让原 active 重新获得完整保护窗口。
5. 退役 Worker 只有在位置仍为 retiring、`retire_after <= now`、同版本存在另一个 verified active 且 storage profile/bucket 与当前配置一致时才删除。提前触发只产生可解释失败 Task，不删除；对象已不存在可幂等收敛为 retired。
6. Storage 不可用时事务回滚、RabbitMQ 消息 requeue，Task、Inbox 和 Location 不伪造完成；重复消息由 Inbox 去重，不重复 copy/delete。Task、ScheduleFire、Outbox/Inbox 和脱敏 AuditEvent 保留全链路证据。
7. Studio 媒体库复用现有 Card、Badge、Button、Dialog 展示位置状态、保护截止时间、迁移和回滚动作；任务中心识别位置迁移/回滚、退役 Task 与 one-off 计划，没有创建平行状态机或自定义视觉体系。

## 3. 真实基础设施证据

`make contract-media-stack` 为 4/4。新增契约通过预签名 URL 把固定 PNG 写入本机 MinIO，经真实测试 PostgreSQL Task/Outbox、隔离 RabbitMQ、Media Worker 执行服务端 copy；随后从 Studio 同一 API 语义提交回滚，让 one-off Schedule 到期并经 dispatcher 产生 Fire/退役 Task，再由真实 RabbitMQ 和 Worker 删除旧对象。MinIO HEAD 证明当前对象存在、到期对象不存在；数据库同时证明原 MediaVersion ID、sha256、size 不变，Location 为唯一 active + retired。

完整 `make check` 通过 Ruff、Pyright、ESLint、TypeScript、后端 196 passed/11 个显式外部或性能开关 skipped、前端 17 文件/53 tests、pip check、Next.js 生产构建与 development/production Compose config。显式打开真实媒体栈开关后的 4 个契约不计入默认 skipped，已单独全部执行通过。

## 4. 环境、模型与供应商边界

本能力只复用本机已运行的 MinIO、PostgreSQL 与 RabbitMQ；没有启动第二套 MinIO，也不安装或调用 Ark SDK。`.env.example` 与 `.env.production.example` 保留 `DEEPSEEK_API_KEY=`、`ARK_API_KEY=` 空占位，并增加有界 `MEDIA_LOCATION_ROLLBACK_SECONDS`；未配置 Provider Key 时生产能力继续 fail-closed，不生成 mock 结果。

同 profile/bucket 的 MinIO 迁移证明供应商无关的状态机、完整性校验和退役门禁，但不证明 OSS adapter、RAM 权限、目标地域或跨 profile 网络迁移。PT-STO-002 必须等目标 OSS/地域确定后使用真实 OSS SDK 与同一端口契约另行验收。

## 5. 产品接受与剩余风险

PT-MED-005 的临时对象清理由 Acceptance 010/012 覆盖，当前位置迁移、回滚窗口和已形成版本的受控物理退役由本文件覆盖，因此 PT-MED-005 可标记 accepted。该产品任务提前完成不等于 DEV-S6-01、WP-11、S6、PT-SCH-001/002/003 或发布门禁完成。

剩余风险是当前开发基线仍只允许空库 `metadata.create_all()`；本次新增 MediaLocation 字段不提供存量数据库在线升级。进入保留存量数据的部署前，必须先按既有 Design 决策引入正式 schema migration，不能对已有生产库直接运行 create_all 冒充升级。

后续状态：完整 Scheduler 的本地 MVP 已在[持久调度、故障恢复与受控运维验收](./014-持久调度故障恢复与受控运维验收.md)独立接受；本文件产品边界仍只针对 PT-MED-005 的位置迁移、回滚和退役，不以单一退役 handler 代替该后续联合证据。
