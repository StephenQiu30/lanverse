## 1. 验收结论

1. PostgreSQL 的 Schedule、ScheduleFire、Task 和 Outbox 是唯一调度事实。生产 dispatcher 以数据库 `CURRENT_TIMESTAMP` 领取到期项，不依赖 API 进程时钟、Redis 锁、RabbitMQ 延迟消息或内存定时器。
2. 支持 one-off、interval 和数字五段 cron；cron 只接受数字、星号、列表、范围与步长，拒绝秒字段、宏、名称和函数路径。IANA timezone 来自锁定的 `tzdata==2026.3`；DST spring gap 跳过，fall fold 只取第一次。
3. `skip` 丢弃超宽限历史点，`run_once` 合并为最新到期点，`catch_up` 只创建最近 1～20 个点。每次事务后 `next_fire_at` 严格晚于本次数据库时钟，超限历史点不会跨 loop 无界补发。
4. 多 dispatcher 使用 `FOR UPDATE SKIP LOCKED` 和有期限 lease；同一计划点以唯一 fire_key 约束只产生一份 Fire/Task/Outbox。Task/Outbox 创建后注入崩溃会整笔回滚，lease 到期后其他进程恢复仍只产生一次。
5. 普通失败按 2/4/8/16 秒退避，第五次进入 `manual_attention`；未登记 handler、非法 payload 或规则第一次即停止。`last_error`、结构化日志和 Prometheus 指标只保存稳定类别及低基数 handler/result/policy/reason，不保存 payload、对象 key、URL、凭据或依赖原文。
6. owner 只能在 Studio 配置已存在的 `cleanup_expired_uploads`，在 interval/cron 间切换并显式选择 timezone、宽限和 misfire；暂停不取消既有 Task，恢复必须选择策略，手动触发使用幂等 Fire 且不移动下次计划时刻。跨 Workspace 始终返回 404，重复手动幂等键只写一份 Fire、Task、Outbox 和 AuditEvent。
7. 真实 RabbitMQ 不可用时 Fire/Task/Outbox 保留为可重试事实；恢复后 Publisher 发布原 event_id，Media Worker 完成 Task，重复消息由 Inbox 收敛为 duplicate。页面刷新继续读取 PostgreSQL Task/Schedule，不从队列猜测状态。

## 3. 真实基础设施与恢复证据

`make contract-scheduler-stack` 为 1/1：在真实测试 PostgreSQL 创建 cron Schedule，先由模拟崩溃的 Scheduler 持有 lease，过期前重启实例无法领取，过期后新实例只创建一个 Fire/Task/Outbox；模拟 RabbitMQ 不可用后 Outbox 保存 `RabbitUnavailable` 类型并退避，真实隔离 RabbitMQ 恢复后发布成功，Media Worker 首次完成、同 event_id 重投返回 duplicate，最终 Inbox 一行、Task 一份、Fire 一份。

同轮显式执行 `make contract-minio contract-redis contract-rabbitmq contract-ffprobe contract-media-stack contract-scheduler-stack`，结果依次为 2/2、1/1、2/2、1/1、4/4、1/1，均使用本机已启动的 PostgreSQL、Redis、RabbitMQ、MinIO 和 ffprobe。默认测试中的 skipped 仅用于隔离外部条件，所有相关契约均已通过显式开关真实执行。

完整 `make check` 通过 Ruff、Pyright、ESLint、TypeScript、后端 213 passed/12 skipped、前端 54/54、pip check、Next.js 生产构建与 development/production Compose config。标准 `make e2e` 首次因本机 3000 端口已被未知进程占用而在测试前拒绝启动；未结束未知进程，改用 `LANVERSE_E2E_BACKEND_PORT=8002 LANVERSE_E2E_FRONTEND_PORT=3001 make e2e` 后 8/8 通过。

## 4. 环境、模型与安全边界

本验收不需要模型 API Key，不安装或调用 Ollama、Ark SDK，也不伪造 DeepSeek、Seedream 或 Seedance 成功。`.env.example` 与 `.env.production.example` 继续保留 `DEEPSEEK_API_KEY=`、`ARK_API_KEY=` 空占位；浏览器仍验证 DeepSeek 未配置时 fail-closed。真实基础设施只复用本机已启动服务，没有启动第二套 MinIO。

公开 API 不接受 handler 名称、函数路径、pickle 或任意 payload；前端复用现有 Card、Badge、Button、Dialog、Input、Label 和 Select，没有建立第二套视觉系统或客户端调度状态机。生成类型是唯一前端 API 契约。

## 5. 产品接受与剩余风险

PT-SCH-001/002/003 和只承载其余恢复矩阵的 DEV-S6-02 可标记 accepted/completed。DEV-S4-02 仍因 ArkMediaAdapter、Attempt、取消/unknown 对账和真实火山账号证据保持 in_progress；调度平台接受不替代这些 Provider 工作，也不提前接受 PT-MQ-003/004、PT-CCH-002、WP-07、WP-11、S4 或 S6。

当前开发基线仍只允许空库 `metadata.create_all()`，没有存量库在线 schema migration；进入保留数据的部署前必须引入正式 migration。当前 cron 是刻意受限的数字五段 MVP，不支持秒级、名称、宏或用户工作流；如未来扩展，必须先更新 Requirement/Design 并重新做 DST、容量和安全验收。
