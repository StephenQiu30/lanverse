## 1. 交付结果

1. Shot 支持 confirmed Scene/shot Candidate 或手工 creation key 建立、120 上限、完整集合重排、复制、拆分、合并、归档、恢复和受保护删除；position/order hash、revision、impact hash 与幂等键共同阻止并发覆盖。
2. ShotSpec v1 以不可变版本保存剧本、场次、对白和固定 AssetVersion 引用；current 只能显式切换，未知字段、供应商参数、跨 Episode 结构和非法资产类型在写入前被拒绝。
3. readiness 返回稳定 blocker/warning/next action 与 evaluation hash；scripts、assets、media 或 governance 依赖不可用时 fail-closed，不把草稿、过期授权或故障误报为 ready。
4. 资产版本 usage 按页区分当前与历史规格。升级必须选择当前引用并先执行服务端 preflight；apply 锁定全部目标，任一 expected Spec、Shot revision 或 preflight hash 变化时整批零写入，成功后每个 Shot 只追加一个新规格版本。
5. Next.js 分镜工作台使用生成的 OpenAPI client 和 RTK Query，提供已确认 shot 候选/手工建镜、revision 保护的标题修改、完整规格编辑、历史版本切换、拖拽重排及键盘上移/下移、复制、归档恢复、拆分/合并预检、安全删除、批量 blocker，以及资产引用/升级复核；主体站位、对白声音/表演提示、首尾帧意图和 readiness warning 均进入用户界面，没有 API Key、模型参数、供应商费用或伪造生成结果。
6. 12/36/120 镜头固定性能样本使用虚构主体和 ready 的 location、2 character、voice、visual style 固定引用；production 配置单进程通过本机 loopback PostgreSQL 运行 10 次预热、50 次采样和 120 镜头 30 次重排。
7. current ScriptVersion 切换通过 storyboards 公开读取契约返回仍固定旧版本的 active Shot ID；切换只更新剧本 current 指针，不重建 Scene，也不改写既有 ShotSpec。资产工作台则允许显式切换历史 current，并明确提示既有镜头固定引用保持不变。
8. 无密钥 Playwright 用例在独立测试库中建立与生产确认结果同构的 published v1 → confirmed v2 → current v2 关系，以及明确标记为本地测试事实、不得解释为模型输出的 accepted Scene/Shot Candidate；浏览器从候选建立并归档 Shot，再完成手工建镜、标题修改、规格 v1/v2/v3 与 current 切换、HTML5 原生拖拽、键盘重排、复制、合并、归档恢复、空镜头安全删除、拆分和刷新恢复。该用例通过本机唯一 MinIO、RabbitMQ、Media Worker 与授权治理建立真实 ready 角色、声音和场景资产，填写叙事、时长、连续性、受控镜头语言、构图环境、动作对白、固定角色站位、声音表演、环境声/音效与生成意图，并验证合并/拆分后仍恢复这些规格；场景 v1→v2 usage、升级预检/apply、归档引用历史化与来源选择失效均成立。最后切换 ScriptVersion current，2 个 active Shot 影响可持续显示且不会改写既有镜头，再恢复 v2 并得到 0 个影响。
9. ShotSpec 手工保存、资产升级、复制、拆分、合并与显式 current 切换均在原业务事务中追加 owner 可查的 AuditEvent；metadata 只记录稳定 ID、版本号、revision 和来源枚举，不复制规格正文、提示词或 hash。幂等重放、陈旧 preflight 与并发 loser 不产生重复事件，治理页可按两个分镜动作筛选。
10. storyboards 对 projects 公开 Episode 维度的批量影响摘要，同时计数 active/archived Shot 与全部 ShotSpecVersion。Episode/Project 删除预检逐项显示真实镜头/规格数，Episode DELETE 在锁内重查；建镜与删除并发时不留孤立分镜事实。真实 S3 浏览器显示“单集已有 6 个分镜镜头（7 个规格版本）”与项目级同量 blocker。
11. assets 对 projects 公开 Project 维度的批量影响摘要，同时计数 active/archived Asset 与全部 AssetVersion。Project 删除预检以 `HAS_ASSETS` 展示真实身份/版本数，DELETE 持有 Project 锁后重查；首个资产/项目删除的两种 winner 均无孤立数据。真实 S3 浏览器显示“项目已有 5 个资产（5 个版本）”。
12. Asset 自身删除预检通过 assets 自有 Protocol 读取 scripts 公共 CandidateDecision 计数；无版本但已有决议的 Asset 返回结构化 `asset_has_candidate_decisions`，DELETE 在 Asset 锁内复查。`link_existing` 与删除的真实并发只允许 201/409 或 404/200，数据库没有悬空 downstream_id；真实资产页显示“资产已被 1 条剧本候选决议关联，只能归档。”且不提供硬删除动作。
13. Asset 自身删除预检还读取 Prop/Costume 历史版本 JSONB 中的 holder/wearer 引用；无自身版本的 Character 被引用后返回 `asset_has_related_versions`。全部 Asset 写命令统一 Project → Asset 锁顺序并强制刷新锁定实体；追加引用版本/删除并发连续 3 轮只产生 201/409 或 422/200，append/current 并发仍保持单 winner。真实页面创建道具版本并选择角色后显示“资产已被 1 个道具或服装版本引用，只能归档。”。
14. PT-PRJ-005 的 S3 增量新增跨 Episode `EpisodeStoryboardSummary`：与 shot-readiness 使用同一套真实结构、资产、媒体和授权规则，ProductionSnapshot 返回 Ready/blocked/unavailable 分镜数。依赖故障显式进入 `STORYBOARD_SUMMARY_UNAVAILABLE`，全 ready 时进度为 90% 且不生成 S4 任务或费用。12 集列表查询保持固定上限，36/120 镜头的 ProductionSnapshot 均返回全量 ready 且查询数不随镜头数增长。

## 4. Red → Green 记录

1. 先以 ShotSpec 判别模型测试固定字段集合、枚举、时长、action beat 和禁止供应商字段，再实现 v1 领域模型。
2. 先固定建镜、重排、生命周期和并发失败路径，再实现事务、连续位置和 order hash；有来源或规格证据的 Shot 只能归档。
3. 先固定 copy/split/merge 的 preflight、幂等、陈旧 impact 和证据保留，再实现变换事务；下游 Task、Candidate、Media、费用和时间线不复制也不迁移。
4. 先固定 readiness code、授权变化、依赖 unavailable 和 36 镜头查询上限，再实现批量读取；随后扩展到 120 镜头并执行冻结环境 P95。
5. 先固定资产升级全或无测试，再实现 usage、preflight/apply；前端同样先定义引用选择、预检和追加式确认测试，再接入现有资产工作台。
