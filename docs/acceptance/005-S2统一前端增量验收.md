## 4. Red → Green 记录

1. 真实 Scheduler 刷新 Outbox 时首先暴露 `NoReferencedTableError`：后台入口只导入局部模型，`sys_outbox_events.workspace_id` 无法解析 identity 表。
2. 新增运行时模型注册架构测试，证明所有已实现外键目标都进入同一 Metadata，并约束数据库初始化、Scheduler、I/O Worker、Media Worker 四个入口执行注册。
3. 引入唯一 `app/model_registry.py` 组合根并把 Media Worker 加入 `server` 监督列表；目标测试与完整 `make check` 全绿后，再重新运行真实后台角色完成媒体探测。
4. 资产页虽给出“前往授权治理”，但最初没有传递被阻断 AssetVersion；治理表单也只支持媒体/剧本版本，用户无法从当前动作完成资产授权。
5. 新增前端 Red 测试固定 `ASSET_VERSION` subject、证明 MediaVersion 和表单预填，再以已有组件扩展治理工作台；创建授权后重新读取 readiness，角色/场景/声线均变为 ready。
6. 对三个后台角色执行逐个替换与停止旧进程后，通过认证 ProductionSnapshot 再次确认 3/3 ready 和现有失败 Task 均从服务端事实恢复，没有重复资产版本或授权副作用。
7. DeepSeek 增量先以缺失适配器、失败批次无重试入口、候选无修改/合并控件形成 Red，再分别以 LangChain 适配和 shadcn/ui 交互转 Green。
8. Worker 在首个事务中只固定输入并将 Task/Batch 转 running，事务外调用 DeepSeek，第二事务落候选和终态；故障注入证明响应后落库失败的重投不会第二次调用模型。
9. 首次真实 RabbitMQ 契约与开发 Worker 共用 `/` 后被实时消费，无法作为可重复契约；先增加“默认 vhost 必须拒绝”的 Red 测试，再统一本地与 CI 的 `lanverse_contract` 配置，结果 4/4 安全单测和 RabbitMQ 2/2 真实契约通过。
10. Playwright 复用 8000 服务且只启 API 时无法验证 Worker，冷启动 Turbopack 还出现真实 chunk 加载竞态；加入可配置 API 绑定的 Red 测试后，改用独立组合根和 standalone 生产产物，完整 E2E 稳定通过。
11. 媒体/资产/授权原只有单模块测试与人工记录，首个 Playwright 用例先串联角色链路，并暴露和消除了构建时字体外网依赖；commit `9d670f5` 再把场景与非 AI 的普通 PCM WAV 声线纳入同一真实后台组合根，自动断言 3/3 ready 与撤销后 2/3，`make e2e` 6/6 与 `make check` 通过。
12. 原 `make contract-deepseek` 只直接调用适配器，无法证明业务队列、Worker、浏览器决议和确认结构。新增真实 Provider E2E 后，默认模式仍只收集 6 条本地用例并强制空密钥；显式模式缺密钥会在启动前失败，使用非密钥占位值执行 `--list` 时只收集 1 条联合验收，确保真实运行只产生一次模型提取调用。
13. PT-SCR-005 审计先证明切换 current 时 `affected_shot_ids` 恒为空、版本历史缺少影响与清理动作；Red 测试固定真实 active Shot 影响后，通过 storyboards 公开契约补齐查询，并以现有 Dialog/Button/Badge 完成版本差异、影响确认、draft 删除和来源归档。
14. 资产生命周期审计先以页面测试证明身份编辑、历史 current 切换和删除预检控件缺失，再复用生成 client、RTK Query 与现有组件转 Green；删除只有服务端 preflight 明确允许时才出现确认动作。
15. 浏览器扩展测试先暴露两版本资产的英文删除详情；后端补充必填 `version_count`，前端按稳定 blocker code 和结构化数量生成中文文案，再由集成测试、单测、定向 Playwright 与全量 E2E 转 Green。

## 5. 接受边界与下一步

1. 本文接受统一前端、后台组合根、本地媒体链路、资产授权交接和三类 ready 资产的工程增量，不接受 DEV-S2-06、任一 S2 PT 或 S2 产品切片完成。
2. 本轮验收时项目未配置真实 AI 服务；明确失败是正确的 fail-closed 结果，不等于提取成功。LangChain DeepSeek + `deepseek-v4-pro` 适配、新 Batch 重试、修改与合并及联合验收入口已实现；按用户当前“不配置 API Key”的决定，真实 `make contract-deepseek` 保留为未来 Provider 门禁，本轮不运行也不记为通过。
3. 角色、场景、声线 ready 门禁已经完成；S2 联合接受现在只受真实 AI 提取→候选决议→结构确认及对应 PT 联合证据约束，不得用未配置服务的失败 Task 代替。
4. 默认 `make check` 仍不会隐式启动外部服务；当前 6 项基础设施契约 skipped 不能解释为通过，本轮已分别显式通过 MinIO、RabbitMQ、ffprobe 和媒体联合栈契约。DeepSeek Provider E2E 不进入默认收集，仍必须在明确配置密钥后单独执行且以该真实结果为准。
5. 本机历史容器的创建标签仍可能显示 `latest`，但运行二进制已被精确发行版守卫核验；仓库不得回退浮动标签，也不得因为标签名重复拉起第二容器。
6. Next.js 开发服务曾因内存阈值自动重启并让已打开页面短暂出现 chunk 失配；HTTP 随后恢复且生产构建通过。该现象不改变本轮服务端验收事实，但开发态内存仍需在后续长时间联调中观察。
7. 资产生命周期对话框已通过真实 Playwright 浏览器交互、类型检查和 production 构建；该证据接受功能可用性和可见反馈，不替代逐像素截图复核。剧本版本及 S3 分镜新增对话框仍保留单独的视觉复查边界。
8. 当前本机唯一原有 MinIO 已恢复到 9000/9001，精确版本守卫和 2/2 真实契约通过；没有重装、升级、创建新容器或启动第二实例。该显式结果不改变默认 `make check` 不启动外部服务、相关用例仍 skip 的规则。
