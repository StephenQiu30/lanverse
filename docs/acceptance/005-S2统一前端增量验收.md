## 4. Red → Green 记录

1. 真实 Scheduler 刷新 Outbox 时首先暴露 `NoReferencedTableError`：后台入口只导入局部模型，`sys_outbox_events.workspace_id` 无法解析 identity 表。
2. 新增运行时模型注册架构测试，证明所有已实现外键目标都进入同一 Metadata，并约束数据库初始化、Scheduler、I/O Worker、Media Worker 四个入口执行注册。
3. 引入唯一 `app/model_registry.py` 组合根并把 Media Worker 加入 `server` 监督列表；目标测试与完整 `make check` 全绿后，再重新运行真实后台角色完成媒体探测。
4. 资产页虽给出“前往授权治理”，但最初没有传递被阻断 AssetVersion；治理表单也只支持媒体/剧本版本，用户无法从当前动作完成资产授权。
5. 新增前端 Red 测试固定 `ASSET_VERSION` subject、证明 MediaVersion 和表单预填，再以已有组件扩展治理工作台；创建授权后重新读取 readiness，角色/场景/声线均变为 ready。
6. 对三个后台角色执行逐个替换与停止旧进程后，通过认证 ProductionSnapshot 再次确认 3/3 ready 和现有失败 Task 均从服务端事实恢复，没有重复资产版本或授权副作用。
7. DeepSeek 增量先以缺失适配器、失败批次无重试入口、候选无修改/合并控件形成 Red，再分别以 LangChain 适配和 shadcn/ui 交互转 Green。
8. Worker 在首个事务中只固定输入并将 Task/Batch 转 running，事务外调用 DeepSeek，第二事务落候选和终态；故障注入证明响应后落库失败的重投不会第二次调用模型。

## 5. 接受边界与下一步

1. 本文接受统一前端、后台组合根、本地媒体链路、资产授权交接和三类 ready 资产的工程增量，不接受 DEV-S2-06、任一 S2 PT 或 S2 产品切片完成。
2. 本轮验收时项目未配置真实 AI 服务；当时的明确失败是正确的 fail-closed 结果，不等于提取成功。2026-07-30 后续的 LangChain DeepSeek + `deepseek-v4-pro` 适配、新 Batch 重试、修改与合并已实现；下一步只能在提供 `DEEPSEEK_API_KEY` 后跑通真实提取候选、人工决议和结构确认。
3. 角色、场景、声线 ready 门禁已经完成；S2 联合接受现在只受真实 AI 提取→候选决议→结构确认及对应 PT 联合证据约束，不得用未配置服务的失败 Task 代替。
4. 默认 `make check` 仍不会隐式启动外部服务；当前 7 项 skipped 不能解释为通过，其中 DeepSeek 真实契约必须在明确配置密钥后单独执行。已单独通过的外部证据仍是当时明确使用的真实 MinIO 契约和浏览器媒体链路。
5. 本机历史容器的创建标签仍可能显示 `latest`，但运行二进制已被精确发行版守卫核验；仓库不得回退浮动标签，也不得因为标签名重复拉起第二容器。
6. Next.js 开发服务曾因内存阈值自动重启并让已打开页面短暂出现 chunk 失配；HTTP 随后恢复且生产构建通过。该现象不改变本轮服务端验收事实，但开发态内存仍需在后续长时间联调中观察。
