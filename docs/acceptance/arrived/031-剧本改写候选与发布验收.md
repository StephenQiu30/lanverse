## 1. 验收结论

1. 单集工作台已经形成“固定当前已发布原稿 → 填写改写约束 → 异步生成一个 AI 候选 → 人工编辑独立工作稿 → 查看服务端权威 diff → 显式发布新版本”的最小闭环。AI 候选不会覆盖原稿或自动修改 Episode current。
2. `AdaptationRun` 固定输入 ScriptVersion、正文 hash、目标时长、核心剧情点、节奏、口语化要求、Provider、模型、Prompt 和 Schema 版本；模型候选与人工工作稿分离，候选生成后仍可审阅和修改。
3. 运行复用 Task、Outbox、RabbitMQ 和 I/O Worker。消息只携 `task_id`，Worker 从 PostgreSQL 读取输入和约束；剧本正文、Prompt、正文 hash 和幂等键不进入 Task、Outbox 或 Audit 的公开载荷。
4. 服务端独立校验结构化输出、字符长度和目标时长范围。无 Provider、输入漂移、非法输出、未知中断、排队取消和并发发布均 fail closed；未知结果不会盲目再次请求模型。
5. 发布使用 Run 行锁、expected revision 和 Episode current CAS，只追加新的 published ScriptVersion；同一发布命令可幂等回读，并发命令不能产生双重 current。
6. 页面支持运行状态轮询、刷新后从最近 Task 恢复、候选/工作稿对比、人工编辑、显式发布和取消；新建 Run 会清空旧 Run 视图，不会被迟到查询结果回填。
7. 无 Provider 的真实前后端、PostgreSQL、RabbitMQ 和 Worker 闭环证明失败时原稿/current 不变，刷新后仍能重建失败 Run 并显示可操作原因。

## 2. 交付事实

| 交付面 | 当前事实 |
| --- | --- |
| 数据模型 | `scr_adaptation_runs` 单表保存不可变输入快照、约束、候选、工作稿、执行状态、Task、版本和发布结果；关键状态/长度/版本关系由 PostgreSQL 约束 |
| API | 创建/读取 Run；编辑工作稿；获取服务端 diff；发布；取消 |
| AI 路径 | `script_adaptation.requested` → `io.script.adaptation`；DeepSeek 结构化输出；服务端再次执行 schema、长度和目标时长硬校验 |
| 人工门禁 | 候选只进入 reviewable Run；人工工作稿和 AI candidate 分列；只有显式 publish 才追加 ScriptVersion 并尝试切换 current |
| 并发与幂等 | 创建、编辑、发布和取消均使用 expected revision/幂等命令；发布另校验 Episode current 仍等于输入版本 |
| 前端 | Episode script 工作台包含目标时长、核心剧情点、节奏和口语化约束、状态、候选编辑、diff、发布、取消与刷新恢复 |
| 审计 | 记录类型化运行、失败、取消和发布事件，不记录原文、候选全文、Prompt 或正文 hash |

## 3. 成熟方案约束如何落地

- Jellyfish（Apache-2.0）用于验证结构化 AI 中间产物与正式剧本版本分离；没有复制其工作流代码。
- LocalMiniDrama（MIT）用于复核分集后逐集制作的最小边界；没有沿用直接覆盖脚本或一次性生成整剧的路径。
- ai-fusion-video（MIT）用于复核模型调用、资源与镜头生产应由显式阶段承接；本次只实现剧本候选，不提前创建分镜目录或空抽象。
- DramaClaw、ArcReel 仅作为候选账本、输入指纹和失败恢复的行为证据；由于许可证或产品边界不同，没有复制其 Agent、账本或代码。
- LangChain 的结构化输出契约和 CPython 的不可变数据对象实践用于校验 Provider 端口与纯数据契约；领域状态转换仍由 Lanverse 服务承担。

这些证据只决定本次边界和失败语义。第三方方案没有稳定解决“剧本修订后分镜如何保留叙事血缘”，因此该问题不会以兼容补丁塞入 AdaptationRun，而由下一阶段稳定 NarrativeUnit/Version 和显式下游失效传播解决。

## 4. 真实 DeepSeek 证据

第一次真实 DeepSeek 合同返回合法结构，但对 45 秒目标只给出 15 秒自估，服务端拒绝结果且没有创建可发布候选。随后补强 Provider 输入中的可接受时长范围，并保留服务端独立的目标值 ±25% 硬门禁；第二次真实调用返回 45 秒、161 字候选并通过合同测试。

这证明当前 Provider 能完成至少一次受约束结构化改写，也证明提示词、模型自报和 JSON Schema 都不能代替领域硬校验。单条合同不代表题材泛化、戏剧质量、真实配音时长、成本、延迟或 SLA；这些需要用自有剧本评测集持续测量。

## 5. Alembic、命名与恢复证据

Alembic 是数据库 schema 的有序版本控制和可恢复执行器；revision ID 是已经部署数据库的稳定身份，迁移文件名只是仓库中的可读源码名称。本次不重写 revision 图，也不增加中文旧名别名、双路径或 allowlist，而是一次性把全部历史迁移源码改为短英文 snake_case 名称，并由架构测试持续阻断回归。

DES-000 同时固定：可执行源码和测试文件名最长 64 个 ASCII 字符，名称表达最小职责，禁止 `misc`、`common`、`helpers`、`manager`、`data` 等含混桶名；Python/TypeScript 按 POJO 等价的 Plain Data Contract 约束，纯数据对象只声明字段、类型和局部校验，不持有 ORM Session、FastAPI Request、HTTP Client、缓存、队列、Logger 或 I/O 行为。

## 7. 保留边界与下一步

- 本次只接受 PT-SCR-008，不接受 NarrativeUnit、AssetState、AI 分镜、覆盖率或分镜包。
- MVP 每次 Run 只生成一个候选；没有 Top-N 排名、逐块接受/拒绝、剧本文档版本树或任意历史回滚界面。
- 目标时长仍是文本估算与模型返回值，不是 TTS、演员表演、动作和镜头节奏的真实测量。
- 页面从最近 Task 恢复当前 Run，但还没有 Episode 级 Run 历史列表、对比矩阵或归档管理。
- 剧本文本变化后对已有分镜的影响尚不能精确到叙事单元；不得用整镜兼容更新或字符串 offset 补丁冒充稳定血缘。

在这些边界内，PT-SCR-008 和 DEV-MVPA-05 接受。下一任务是 DEV-MVPA-06：先完成成熟 GitHub 方案证据、本地 delta 和 Red，再实现稳定 NarrativeUnit/Version、人工修正、current 影响与下游 stale 传播。
