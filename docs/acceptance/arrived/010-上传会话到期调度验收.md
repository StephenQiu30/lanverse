## 1. 验收结论

1. 初始化 UploadSession 时，同一 PostgreSQL 事务创建唯一 `expire_upload_session` one-off Schedule；对象存储预签名失败会与上传事实一起回滚。
2. 成功完成上传时，同一事务把 Schedule 结束为 completed；未完成且到期时，独立 Scheduler 通过 lease、`FOR UPDATE SKIP LOCKED` 和唯一 fire_key 创建一份 ScheduleFire、Task 与 Outbox。
3. Outbox 经真实 RabbitMQ 投递给 Media Worker；Worker 按 Inbox 去重读取 Task 与 UploadSession，幂等删除本机 MinIO 临时对象并把上传、任务收敛为 expired/succeeded。
4. API 与生成 client 提供服务端 Schedule 查询、暂停、恢复和立即触发；仅 owner 可管理，跨 Workspace 返回 404。页面只展示服务端事实，不复制调度规则。
5. 本次 one-off 验收时唯一 handler 为 `expire_upload_session`，不接受任意函数路径、pickle、用户 cron 或未实现的 Provider 对账。提前手动触发不会在 UploadSession 真正到期前删除对象。后续新增的唯一 interval handler 另见[过期上传周期补偿清理验收](./012-过期上传周期补偿清理验收.md)。

## 3. 真实基础设施证据

`make contract-media-stack` 为 2/2 通过。新增用例在真实测试 PostgreSQL 中把 UploadSession/Schedule 推进到期，使用预签名 URL 把字节写入本机 MinIO，通过 dispatcher 创建 Fire/Task/Outbox，经真实隔离 RabbitMQ vhost 投递并由 Media Worker 删除对象；随后以 MinIO HEAD 证明对象不存在，并验证重复消息只回读同一 InboxDelivery、不重复业务副作用。

默认后端测试为 179 passed、8 个显式外部/性能开关 skipped；上述媒体联合栈已单独打开真实开关运行，不能把默认 skip 当作通过证据。`make check` 同时通过 Ruff、Pyright、ESLint、TypeScript、pip check、前端 17 个文件/51 项测试、Next.js 16.2.12 生产构建以及 development/production Compose 配置校验。
