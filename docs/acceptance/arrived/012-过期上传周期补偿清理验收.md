## 1. 验收结论

1. 每个 Workspace 在首次初始化上传的同一事务中幂等确保唯一 `cleanup_expired_uploads` interval Schedule；第二次上传复用同一计划，不创建按对象增长的周期任务。
2. interval 使用 UTC 固定秒数与 run_once：停机跨过多个周期时只产生一个唯一 ScheduleFire/`upload_cleanup` Task/Outbox，并把 `next_fire_at` 推进到严格晚于 dispatcher 当前时间的首个周期边界；手动触发不改变计划时刻。
3. Media Worker 只小批锁定同 Workspace 内 `status=pending`、`expires_at<=now`、`completed_version_id IS NULL` 的 UploadSession。对象删除成功或已经不存在后才改为 expired；未来、completed、已形成 MediaVersion 的对象及所有 MediaLocation 均不进入候选。
4. Storage 删除失败时整批数据库事务回滚，RabbitMQ 消息 requeue，Task 与 UploadSession 不伪造完成；重复消息由 Inbox 返回同一业务结果，不重复删除。
5. ScheduleFire、Task、Outbox/Inbox、UploadSession 和 `task.succeeded` AuditEvent 共同保留清理证据，审计只增加低敏 `cleaned_count`，不记录 object key、文件名、URL 或凭据。
6. OpenAPI client 和现有任务中心已支持 `upload_cleanup`、Workspace scope 与 interval 计划，复用 Card/Badge/Button 组件；未创建第二套前端调度状态或自定义组件体系。

## 3. 真实基础设施证据

`make contract-media-stack` 为 3/3。新增契约在真实测试 PostgreSQL 中创建一个已完成 MediaVersion 和一个未完成 UploadSession，通过预签名 URL 把两份字节写入本机 MinIO；随后让 Workspace interval 到期，经 dispatcher 写 Fire/Task/Outbox、真实隔离 RabbitMQ 投递和 Media Worker 消费。结果以 MinIO HEAD 同时证明临时对象不存在、版本化对象仍存在，并核对 completed UploadSession、MediaVersion hash 与唯一 active MediaLocation 保持不变。

完整 `make check` 通过 Ruff、Pyright、ESLint、TypeScript、后端/前端测试、pip check、生产构建和 development/production Compose config。OpenAPI client 连续生成目录哈希均为 `d0d16f55513b2270d9b698be6b7627f05ca6df84c2522f26b8803a2dfa090e32`，无漂移。

## 4. 环境与密钥边界

本增量只复用本机 PostgreSQL、RabbitMQ 和 MinIO，不安装或调用 Ark SDK，不需要 DeepSeek/Ark Key。`.env.example` 与 `.env.production.example` 继续保留 `DEEPSEEK_API_KEY=`、`ARK_API_KEY=` 空占位；空值按未配置处理，不产生 mock 模型结果。

## 5. 未接受范围

- 同一 MediaVersion 的新 Location 复制、size/hash 验证、active 原子切换、旧位置回滚窗口与 retiring/retired 物理清理。
- cron、IANA timezone/DST、skip、有限 catch_up、完整 lease 回收和 Fire/Task/Outbox 进程级故障注入。
- Scheduler 连续失败告警联动、Seedream/Seedance unknown 对账、费用、候选及任何 Ark 调用。

因此本文件只接受可独立验证的临时清理与 interval/run_once 子范围；PT-MED-005、PT-SCH-001/002/003、DEV-S6-01/02 与 S6 继续保持未完成。
