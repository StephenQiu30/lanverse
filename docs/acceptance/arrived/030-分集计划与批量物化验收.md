## 1. 验收结论

1. 项目页已经形成“整剧修订 → 分集计划 → 人工编辑 → 确认 → 全量建集 → 批量发布”的完整闭环。合法显式集标记跳过 LLM；《雾港倒计时》固定得到 5 个可审阅候选，确认前数据库中 Episode、ScriptSource 和 ScriptVersion 均为 0。
2. `EpisodePlan` 固定不可变 `DocumentRevision`、输入 hash、策略、目标时长、引擎/模型/提示/schema 版本和 plan revision；`EpisodeProposal` 固定结构块、Unicode code-point 原文范围、内容 hash、预计时长、理由、置信度和边界证据。移动边界、拆集、合集和改标题只改变 Plan，不提前改变正式 Episode。
3. 无显式标记时复用现有 Task/Outbox/I/O Worker 和 DeepSeek runtime。消息只携带 `task_id`，Worker 从 PostgreSQL 读取原文；`episode-plan-prompt-v2` 把原文包装成带稳定 position 的只读 `source_blocks`。AI 只产候选，服务端仍独立验证锚点逐字存在且唯一、锚点落在声明块末尾、边界严格递增和全文并集守恒。
4. confirm 使用 Plan 行锁、expected revision 和幂等 receipt。物化由 projects 模块持 Project/活动 Episode 行锁，比较 Project revision 与活动顺序 hash 后一次事务追加全部 Episode；scripts 通过公开批量契约写 Source、draft Version 和 `EpisodeSegmentOrigin`，没有跨模块导入 Project ORM。
5. 首次物化只建立草稿，不偷改 current。显式发布再一次事务为每集追加 published ScriptVersion，并对全部 Episode current 执行 CAS；5 集最终得到 5 Episode、5 Source、5 draft、5 published，来源切片按序拼接严格等于整剧原文。
6. 同键同输入回读同一结果，同键异输入、陈旧 Plan/Project revision 和活动顺序变化均拒绝。并发 confirm 只产生一个状态迁移；注入第 3 段异常会回滚全部 Episode/Source/Version/Origin，只保留 failed ImportCommit 作为可解释证据。
7. Worker 对未配置模型、非法 AI 锚点和“准备事务已提交但 Provider 结果未知”的中断重投分别收敛为 `ai_service_unavailable`、`ai_output_invalid` 和 `ai_result_unknown`；三种路径都 ack 且不创建 Episode，unknown 不会盲目再次请求模型。

## 2. 交付事实

| 交付面 | 当前事实 |
| --- | --- |
| 数据模型 | `scr_episode_plans`、`scr_episode_proposals`、`scr_import_commits`、`scr_episode_segment_origins` 四表；Workspace 复合外键、范围/状态 check、Plan/Commit 幂等和来源唯一约束由 PostgreSQL 承担 |
| API | 创建/读取 Plan；`move-boundary`、`split`、`merge`、`rename`、`confirm`；`materializations`；ImportCommit `publish` |
| 确定性路径 | 独占一行的连续集标记直接生成 review-ready Plan；标题、原文范围、预计时长、理由和 1.0 置信度可读；不调用模型 |
| AI 路径 | `episode_planning.requested` → `io.script.plan`；DeepSeek 结构化候选；服务端锚点/顺序/全集覆盖硬校验；失败不重试风暴 |
| 人工编辑 | 只允许 NarrativeBlock 边界；移动、拆、合、重命名均使用 expected revision 和幂等 receipt；确认后不可继续编辑 |
| 批量写入 | `append_new` 是当前唯一模式；Project revision + 活动顺序 hash 双 CAS；draft 物化与 published/current 设置分为两个显式原子步骤 |
| 前端 | 项目页展示完整原文、逐集切片、块范围、预计时长、理由、置信度和项目影响；支持边界选择、拆合、改名、确认、物化和发布 |
| 审计 | Plan 创建/生成/编辑/确认、批量建集、失败、发布和 current 变化均写类型化事件；不写正文、提示词或正文 hash |

## 3. 成熟方案约束如何落地

- ArcReel（AGPL-3.0）只作为“原稿指纹 + 唯一锚点 + validator + 并发变化拒绝”的行为与失败测试证据；没有复制代码、`project.json` 账本或物理 episode 文件。
- LocalMiniDrama（MIT）证明显式集标记应走确定性路径；没有沿用其解析后直接写 Episode 的方式。
- Jellyfish（Apache-2.0）证明结构化 AI 候选与正式写入应分离；Lanverse 另补齐了范围守恒、Plan revision 和 ImportCommit 原子性。
- OpenTimelineIO（Apache-2.0、跨年度维护）用于校验稳定身份与顺序分离；本次没有引入 OTIO 依赖或把 Episode 错当编辑 Clip。
- DramaClaw 只作结构化分集字段参考；因 ELv2 托管限制和缺少同构 CAS/原子测试，没有复制其 Agent 或代码。

## 4. 真实 DeepSeek 证据

第一次真实 DeepSeek 合同返回了合法 JSON，但把候选序号当作 `end_block_position`，最后边界没有覆盖原文；该结果被硬契约识别为失败，没有写入 Plan proposals 或 Episode。随后只调整 Provider 输入契约：每个原文行块带明确 position，提示中强调位置不是候选序号、最后位置必须等于原文末块；服务端校验没有放宽。相同真实合同随后通过：返回位置严格递增、最后覆盖末块、所有锚点逐字来自原文且在全文唯一。

这证明当前 runtime 能产生至少一条合规候选，也证明提示词本身不能替代服务端校验。它不是边界质量、题材泛化、成本、延迟或 SLA 评测；这些仍需在真实自有剧本评测集上持续测量。

## 7. 保留边界与下一步

- 本次只接受 PT-SCR-007，不接受 PT-SCR-008 及后续改写、NarrativeUnit、AssetState、AI 分镜或分镜包。
- MVP 只给一个确定性或 AI 推荐方案，不实现 DES-011 完整 Top-3/评分器；AI 推荐没有唯一正确答案，人工确认仍是硬门禁。
- 当前只支持 `append_new`，不映射或重排已有 Episode；项目已有集数加计划超过 10 时阻断。
- 单集预计时长仍是字符速率/模型建议，不是配音、动作和镜头节奏的真实测量；每集 20,000 code points、整剧 100,000 code points、总计 10 集仍是 MVP 上限。
- Plan 有 `superseded` 状态但尚无重规划/历史对比命令；项目页刷新后可回读已物化 Episode，但未提供未完成 Plan 的项目级历史列表。
- published Version 是 draft 正文的不可变复制；剧本改写、逐段 diff、接受/拒绝和回滚属于 DEV-MVPA-05，不能由本次批量发布外推。

在这些边界内，PT-SCR-007 和 DEV-MVPA-04 接受。下一任务是 DEV-MVPA-05：先完成成熟开源方案证据 Gate，再实现受约束改写候选、diff/人工编辑、追加 ScriptVersion 与 current CAS。
