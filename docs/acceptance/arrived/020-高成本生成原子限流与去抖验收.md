## 1. 验收结论

1. `HighCostGuardPort` 是与普通 `CachePort` 分离的类型化业务保护契约；FastAPI 组合根让两者复用同一个 `redis-py` 连接池，production 不导入 Redis SDK，也不增加第二套队列、锁或幂等事实。
2. 一个 Lua 脚本原子读取并更新全局窗口、Workspace 窗口和请求去抖记录。默认 60 秒内每 Workspace 3 个、全局 20 个，去抖 TTL 900 秒；配置有上下界并强制全局不少于 Workspace、去抖 TTL 不短于窗口。
3. Redis key 不保存原始 idempotency key，只使用 SHA-256；value 只保存 GenerationRequest input hash。相同摘要返回 duplicate 且不重复计数，相同幂等摘要绑定不同 input hash 返回冲突。指标只使用固定 result，不含 Workspace、摘要、Redis key 或错误正文。
4. 生成提交顺序为鉴权 → PostgreSQL 幂等回读 → 锁内重算预检/价格/确认 → Redis guard → 五类 PostgreSQL 事实原子写入。已有成功请求直接回放且 Redis 计数保持 1；Redis 已许可但数据库失败时，同键同 input hash 可安全重试而不再次计数。
5. `DEPENDENCY_UNAVAILABLE`、`QUOTA_INSUFFICIENT` 和 Redis 去抖冲突均发生在业务写入前；真实联合契约证明断连时 GenerationRequest、Task、Reservation、CostEntry、Outbox 数量均不增加。低成本提交完全不调用 guard，Redis 断连仍可形成正常数据库事实。

## 3. 真实依赖与契约证据

- `make contract-redis` 显式运行本机 Redis：普通 cache-aside、Lua 并发/TTL/去抖/冲突/断连和 Redis + FastAPI + PostgreSQL 联合契约共 3 passed（2.85 秒）。
- 联合契约真实写入一组 GenerationRequest/Task/Reservation/CostEntry/Outbox，验证 Redis 全局/Workspace 计数均为 1、请求 value 等于数据库 input hash；同请求 PostgreSQL 回放后计数仍为 1；重新预检的新请求在真实断连客户端上返回 503 且数据库计数不变。
- 从显式空 `DEEPSEEK_API_KEY`/`ARK_API_KEY` 的运行中 FastAPI `/openapi.json` 重新生成前端 client 成功；高成本 guard 是服务端依赖，公开生成请求与成功响应 DTO 没有手写分叉。
- `make check` 通过 Ruff、Pyright、ESLint、TypeScript、后端 233 passed/14 个显式外部或性能开关 skipped、前端 17 文件/55 tests、pip check、Next.js 16.2.12 生产构建与 development/production Compose config；其中本增量的 3 个 Redis skip 已由上述真实契约显式补证。
- 显式 `DEEPSEEK_API_KEY='' ARK_API_KEY=''` 的完整 Playwright 顺序回归为 9/9（1.2 分钟），任务中心继续把 Seedream/Seedance 显示为不可用且费用为零，没有因 guard 接入制造伪能力或伪费用。

## 4. 环境、命名与安全边界

`.env.example` 与 `.env.production.example` 增加四项具名且有注释的高成本策略配置，同时继续精确保留 `DEEPSEEK_API_KEY=`、`ARK_API_KEY=` 空占位。Compose 只透传相同配置并沿用现有 Redis；没有新增容器、固定额外软件版本、Ollama、Ark SDK、API Key 或模拟 Provider 成功。

新增文件 `test_generation_high_cost_guard.py` 与现有 `contracts.py`、`redis.py` 均按职责命名；没有 `s1/s2` 阶段代号、通用 utils、原始幂等键日志或高基数指标。

## 5. 未接受项与残余风险

默认 Seedream/Seedance 仍为 `provider_contract_unverified`。本增量使用隔离 active Capability 只触发提交前保护和真实 PostgreSQL 事实，不进入 Worker、Attempt 或 Provider，因此不能证明真实额度消耗，也不能接受 PT-CCH-002 产品任务、PT-PROD-004 或 S4。

当前 Lua 契约针对 MVP 单实例 Redis；若未来切换 Redis Cluster，三个 key 必须通过受控 hash tag 保证同 slot，并重新运行真实集群契约，不能直接复用本次 standalone 证据。Redis permit 是短期安全保护而非账本；真实费用、并发和最终额度仍以 PostgreSQL Reservation/CostEntry、Provider 账单和后续 D-004 验收为准。
