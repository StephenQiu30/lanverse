## 验收范围

本记录验收 `BE-MOD-011` 的第三个前置边界：Cost 从不可变 Estimate 原子创建唯一费用 Reservation，以 PostgreSQL 中 Reservation 的 `Reserved + Settled` 事实执行 Project Budget 门禁，并用追加式 Ledger Entry 记录创建、结算或释放的金额变化。

本增量只实现当前图片生成链路所需的 `RESERVED → SETTLED/RELEASED` 最小状态机。它不包含 GenerationIntent Coordinator、Cost/Quota 共享准备事务、Execution Claim/Authorization、Provider Job/Callback、未知结果对账、自动释放、通用会计科目或公开 Reservation REST，因此不代表 `BE-MOD-011`、`BE-JRN-004` 或阶段 6 已完成。

## 实现事实

1. `CostReservation` 只接受 Cost 已冻结的 `generation.image` Estimate ID，复制 Estimate、BudgetPolicy 和 PriceQuote 的必要快照；调用方不能自报金额、币种、单价、Budget/Quote Revision 或 Provider 用量。
2. 创建 Reservation 时锁定当前 Project BudgetPolicy，并通过 GORM 读取该 Project 全部 Reservation 计算 `Reserved + Settled`。实现没有第二余额表、缓存计数器、手写聚合 SQL 或补偿兼容字段，PostgreSQL Reservation 是当前预算占用的唯一事实源。
3. 同一 Estimate 只有一个 Reservation。相同命令并发、相同幂等键重试和新幂等键的同 Estimate 请求复用同一事实；Estimate、Receipt、Reservation 或 Ledger 内容漂移均失败关闭。
4. `SettleReservation` 只接受稳定 Usage Receipt ID 和实际 Units；Cost 使用 Estimate 冻结单价计算实际金额，实际 Units 必须在 `1..EstimatedUnits`。`ReleaseReservation` 只释放仍为 Reserved 的金额，已结算与已释放终态不能互换。
5. 每次创建、结算或释放均追加不可变 `CostLedgerEntry`。每个 Reservation 只有 Sequence 1 的 Created 和至多一个 Sequence 2 的 Settled/Released；Delta、Currency、Usage Receipt、Actor、时间与 Content Hash 必须能精确重建 Reservation 生命周期。
6. Budget 下调复用同一事务锁和派生用量，不能低于当前 Reserved + Settled；当前 Budget Revision 可以晚于 Estimate Revision，但不能早于 Estimate 冻结的 Revision。
7. `CostReservation` 与 `CostLedgerEntry` 进入唯一 GORM Model Catalog，约束、唯一索引和外键由成熟 ORM 模型声明。实现没有 Migration 文件、DDL/Raw SQL、第二数据库、预算账户镜像或 Agent 侧业务事实。

## 真实验收证据

- Red 阶段先执行 `go test ./tests/cost`，明确因 `ReserveEstimateCommand`、Reservation Result 和对应 Service 方法不存在而编译失败；完成最小实现后同一目标包转绿。
- 最终目标测试第一次误把旧容器端口 `55439` 与新容器凭据组合，PostgreSQL 在 SASL 认证阶段拒绝连接，未进入业务测试；改用已核验的新 PostgreSQL `16.15-alpine` 容器 `55440` 后，`go test -count=3 -run TestCostReservationAndLedgerPreserveBudget ./tests/cost` 连续三次通过，累计 11.384 秒。
- 数据库目录查询确认只新增 `cst_reservations` 与 `cst_ledger_entries`，不存在 `cst_budget_accounts`；Estimate 唯一预留、Ledger Sequence/Type 唯一索引以及 GORM Check/FK 约束均真实创建。
- 两个各需 `60.000000 USD` 的 Estimate 在 `100.000000 USD` Budget 下并发预留，只有一个成功；8 路相同预留重放收敛到同一 Reservation/Receipt，Budget 不能下调到占用额以下。
- 成功 Reservation 以 5/6 Units 结算为 `50.000000 USD`，Ledger 写入 `Reserved -60.000000 / Settled +50.000000`；相同 Receipt 重放成功，Units 漂移和结算后释放被拒绝。
- 第二个 `50.000000 USD` Reservation 正好占满余额后释放，Ledger 写入 `Reserved -50.000000 / Settled +0`；释放后不能结算。Budget 可下调到已结算的 `50.000000`，但 `49.999999` 被拒绝。
- 独立 Project 的 Settle/Release 并发竞态只有一个终态成功，另一个得到状态冲突且最终恰有两条 Ledger；另一条 Reserved 事实在时钟推进 72 小时后仍保持 Reserved，没有未经对账的自动释放。
- Viewer 可读但不可写，撤销 Token 后访问失败，跨 Workspace 读取返回不泄漏存在性的 `not_found`；篡改 Ledger Hash 后读取返回事实冲突。
- 全新 PostgreSQL + Temporal + MinIO 下执行 Backend `gofmt`、`go vet ./...`、`go test -count=1 -p 1 ./...` 全绿；Cost 套件 15.116 秒，Workflow 真实集成套件 124.529 秒，未跳过外部服务旅程。
- Agent 使用真实 Python 3.11 临时虚拟环境执行依赖安装、Ruff check/format、Pyright 与 12 个 Pytest 全绿；Frontend 执行 `npm ci`、OpenAPI 重生成、ESLint、TypeScript、45 个 Vitest 与 Next.js 生产构建全绿，生成客户端无漂移。
- 仓库卫生、开发/生产 Compose 配置、Frontend/Backend/Agent 三类部署镜像构建以及 API、Workflow Worker、Frontend standalone、私有 Agent Candidate Runtime 容器内入口断言全部通过。
- `rg` 审计 Cost/Application/GORM Model/Catalog/目标测试没有 `Raw`、`Exec`、Migration 或 Budget Account 实现，符合单一 SQL 事实源和成熟 ORM 约束。

## 边界与残余风险

- Reservation 当前只有内部 Cost Application Interface，尚无真实 GenerationIntent 调用者；在后续共享准备事务完成前，不能宣称昂贵生成已经被 Cost/Quota 联合门禁。
- Provider 执行和 Usage Receipt 来源尚未实现；未知结果必须保持 Reserved。后续需要显式 Claim/Authorization、回调去重和对账流程，不能用超时自动释放掩盖费用事实。
- 当前 Ledger 是该 Reservation 生命周期的预算事实，不是通用会计复式账本；没有真实业务需求前不扩展账户、科目、汇率或跨币种抽象。
- 远端 `origin/main` 仍停留在已通过 GitHub Actions 的 `2f6e066`；本地提交只有在获得推送并实际运行后才能报告远端绿色。
- `agent-browser` 按约定只在全部开发完成后执行；当前仍有 GenerationIntent、Execution Claim、Provider、CandidateSet/Workflow 和单 Shot Workflow 后续任务，因此本切片不提前调用。
