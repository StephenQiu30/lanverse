# 软件生命周期与需求管理

本文件定义浮光从原始需要到运行、维护和退役的工作方法。当前交付是需求整理稿；流程说明不代表设计已经获接受、功能已经实现，或部署操作已经得到授权。

采用按业务模块迭代交付的方法：整体需求保持完整，每次选一个可验证闭环，完成需求确认、方案评审、实施与验收，再进入下一轮。风险和依赖可调整实现顺序；不按文档编号机械地等到最后才补权限、审计和可靠性。

## 方法依据与裁剪

[ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)的公开说明涉及需求过程及其信息内容；[ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html)的公开说明覆盖开发、运行、维护和退役等生命周期过程，且不强制一种开发模型。这里仅据公开范围建立项目工作方法，未购买全文或进行标准符合性审计，不宣称符合认证要求。

本项目结合 `pm-execution` 的 PRD 方法（问题、使用者、价值、目标、范围、假设、交付）、用户故事的 Card/Conversation/Confirmation 与 INVEST 检查，以及测试场景方法。用户故事用于解释用户需要，需求规格用于定义系统必须做什么；实施前才拆当次工作项，不把每个动作变成独立文档，也不承诺每份完整模块一个Sprint完成。

下面的格式、状态和阶段门是本项目的待评审方法提案。表格数量服从实际问题；简单修改可在同一份模块文档记录方案、测试与交付，复杂方案才单独形成Design。

## 原始需求的层次与唯一来源

| 层次           | 回答的问题                               | 本项目事实来源                                                                                    |
| -------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 产品意图       | 为什么做、为谁做、带来什么价值           | [PRD-浮光](prd/00-浮光.md)                                                                        |
| 用户需求       | 使用者在什么场景需要什么结果             | 各模块“需求概述”的角色与价值、[业务流程](requirement/03-业务流程与用例模型.md)                    |
| 功能性需求     | 什么条件下系统执行什么行为、产出什么结果 | [06～19业务模块](requirement/01-需求总览.md#建议执行顺序)的功能性需求                             |
| 非功能性需求   | 行为需达到什么安全、可靠、性能和可用条件 | 对应业务模块内的非功能性需求、质量缺口与验证方法                                                  |
| 数据与业务约束 | 数据含义、权限、版本、格式和保留规则     | 模块业务规则/原始字段、[术语](requirement/04-术语表.md)和[交互](requirement/05-界面与交互需求.md) |
| 设计           | 如何实现已确认需求，有哪些技术取舍       | 获接受的当次Design，不能把旧表、mock或删除的设计写成新需求                                        |
| 测试与交付     | 哪项需求已被验证，哪些外部条件仍缺失     | 模块验收场景及当次测试/发布记录；当前没有新功能验收结果                                           |

文件按业务职责组织，功能与非功能是模块内部章节，不是目录或文件分类。原始页面字段和按钮是获取需求的证据，不是全部需求。还须询问正常流程、替代流程、失败恢复、权限、数据生命周期和运行条件。缺失部分登记为问题，不直接臆造产品规则。

## 模块需求统一格式

06～19各一份业务需求，保持已有顺序。每份包含以下八部分：

1. **需求概述**：问题、目标、使用者/价值、来源、文档状态与完成依据。
2. **范围与边界**：包含/排除内容、跨模块职责，区分用户需要与技术方案。
3. **功能性需求**：内部编号、功能、前置/输入、系统行为/业务规则、结果/异常及验收。
4. **非功能性需求**：直接给出本模块适用的完整质量条件与验证方法，不引用独立类别文件。
5. **验收场景**：关联需求、角色/初始条件、操作顺序、预期结果；执行时另填实际证据。
6. **依赖、假设与待确认**：必要依赖、政策空白、冲突、外部条件和影响范围。
7. **原始字段、动作与来源约束**：保留旧规格内容供追踪，建议值与存储名不默认成为合同。
8. **页面与实现来源**：现有路由/代码/Figma，用于定位，不能证明真实功能已经完成。

文档号表达阅读/建议执行顺序；`FR-USER-01`等内部需求号、`MNFR-USER-01`模块内质量号、`AC-USER-01`场景号用于追踪。保留既有号；新增条目追加，不因排序变化复用旧号。原`REQ-F`仅是来源标识。

一条功能需求的表达是：“在【前置条件/输入】下，系统应【行为及业务规则】，得到【可观察结果】；若【失败/边界】，则【可见反馈和状态保留】。”一条质量需求应明确“对象/场景、指标或限制、阈值、测试环境/测量方法”。没确定的阈值写“待确认”，不能以“快速、稳定、友好”代替指标。

## 获取、分析、评审与基线

1. 从用户原始目标、模块文档、现有代码/界面及实际使用反馈获取需要，记录来源和差异。源码常量属于现状证据，不能自动压过用户决定。
2. 分析角色、场景、业务实体、正常/替代/异常流程及依赖；明确产品行为、质量目标、数据约束和方案建议的区别。
3. 用统一格式整理，检查是否必要、清楚、不矛盾、可验证，并确保原始内容有去向。用户故事检查价值/独立性/可讨论/可估算/适度大小/可测试；整体模块允许跨多轮实现。
4. 对照[缺口登记](requirement/01-需求总览.md#需求缺口与确认)逐项确认；未知不能用样例值补齐。相应业务负责人决定产品政策，工程/测试负责人确认可实施、可测条件。
5. 产品负责人明确接受相应范围后，以Git提交标识需求基线；Design接受单独记录。本轮各文件仍为`unreviewed`，已有Git提交只证明保存，不证明需求批准。

| 质量检查   | 可审阅证据                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------- |
| 完整与必要 | 原始功能/字段逐项有去向；无效、失败、越权、重试/冲突、空数据可解释；新增需要有来源或提案标记 |
| 清楚与一致 | 同一术语/业务规则只维护一份；来源冲突登记，不让两组风格/排序/指标同时成为合同                |
| 可验证     | 需求可映射场景，质量有测量条件；待确认事项标记受影响能力，不假称可验收                       |
| 可追踪     | 产品目标→功能/质量编号→方案→变更→场景与证据的链路可定位                                      |
| 可实施     | 用户结果与模块职责明确，关键技术/供应商风险先验证；不预建无消费者的平台                      |

## 生命周期阶段与交付条件

| 阶段               | 工作内容                                                       | 最小产物                                       | 进入下一阶段的条件                                        | 决策/验证角色          |
| ------------------ | -------------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------- | ---------------------- |
| 问题与可行性       | 明确用户问题、价值、范围，检查真实供应商、运行和费用等关键约束 | PRD目标、假设与风险；必要的有限验证记录        | 价值与范围明确，关键风险有处理路径；不拿POC替代生产能力   | 产品负责人、工程负责人 |
| 需求获取与分析     | 访谈/材料/页面核对、流程与字段分析、功能/质量区分              | 同一模块的功能/质量/验收、缺口登记             | 来源齐全；该轮受影响政策/阈值已确认，未完成范围明确       | 产品负责人、测试负责人 |
| 需求确认与方案设计 | 评审原始需要；形成模块边界、数据/接口、状态/失败和取舍         | 接受的需求范围与Design                         | 需求与Design均明确获接受；迁移/真实收费等执行条件另行满足 | 产品负责人、工程负责人 |
| 实施规划           | 按当次闭环拆实现/测试步骤，安排依赖与责任                      | 当次计划、测试场景和完成定义                   | 工作项能交付可验证结果；不提前分解未来所有模块            | 工程负责人、测试负责人 |
| 开发与配置管理     | 核心逻辑Red→Green→Refactor，保持依赖边界，审查差异与秘密       | 代码、必要Schema/生成规范与测试；可审阅Git变更 | 适用质量门禁和审查通过，需求偏差已处理                    | 开发者、审阅者         |
| 集成与系统验证     | 联通认证/数据库/文件/真实供应商，测冲突、重启、失败与质量指标  | 可执行测试及环境、原始结果                     | 该轮功能和质量验证有实际结果；外部限制明确                | 开发者、测试负责人     |
| 用户验收           | 用真实用户流程确认解决原始问题，核缺口与剩余范围               | 需求号对应的验收结果/缺陷/接受范围             | 产品负责人明确接受；未测内容不能标完成                    | 产品负责人、测试负责人 |
| 发布与迁移         | 说明部署范围、数据影响、配置、回退和验证；确认外部执行授权     | 发布/迁移步骤、版本及回退办法                  | 适用授权已具备，数据风险可恢复；发布后烟测通过才报成功    | 发布负责人、产品负责人 |
| 运行与维护         | 查真实故障、用户反馈、数据恢复、费用与性能；修复回归           | 运行记录、缺陷、需求变更与验证                 | 变更重新走影响分析、设计/测试/发布；定期核实恢复能力      | 运行负责人、工程负责人 |
| 退役与处置         | 确认停用范围、用户通知、依赖、数据保留/导出/销毁和撤销凭据     | 经授权的退役与数据处理记录                     | 用户明确接受精确目标及数据策略，执行结果可核对            | 产品负责人、运行负责人 |

以上是项目拟采用的职责，不是已经分配的人员；由实际承担者落实，少量成员可兼任。阶段可迭代、并行处理独立内容；开发发现新需求要回到分析与评审，不能直接隐藏在代码中。产品规则先确认，复杂Design接受后再细化当次技术需求、实施计划与测试，不预先堆满未来设计目录。

## 测试与证据

需求验证确认“文档表达是否清楚、完整、可测”；实现验证确认“实现是否符合规格”；用户验收确认“结果是否解决用户需要”。三个结果分别记录。

每次测试使用现有工具和当次场景，在记录中写：需求/场景号、目标、环境/版本、角色、起始数据、操作及逐步预期、实际结果、原始输出或截图、缺陷和重测。自动化断言、真实存储读回、浏览器操作、供应商/实际费用、容量与恢复实验分别报告，不互相替代。核心逻辑按AGENTS执行TDD，跨边界风险补集成测试，变更后选择相关回归。

追踪可留在该模块当次验收记录的一张表，不另建每按钮文件或复制整份需求：

| 需求/质量号               | Design位置与版本 | 实现变更/提交    | 场景/测试                 | 证据与结果         | 缺陷/剩余条件                    |
| ------------------------- | ---------------- | ---------------- | ------------------------- | ------------------ | -------------------------------- |
| FR-USER-03 / MNFR-USER-01 | 实施时填实际位置 | 实施时填实际提交 | AC-USER-03及会话/越权测试 | 尚未执行，不填通过 | 撤销后服务端失效与用户隔离须验证 |

## 变更、风险与文档维护

需求状态与实现状态分开：原始整理→待确认/待评审→已接受基线→变更中；实现则记录未实施、实施中、验证中、已验收及外部条件未满足。`unreviewed`只表示文档未完成评审。

新增/删除/变更需求时，在同一模块或当次记录写明原因、来源、受影响需求/数据/接口/测试/部署、决定与证据，更新唯一事实来源和相关链接。已接受基线发生变化要再次确认相应范围；不靠重排编号或改完成标签隐藏范围缩小。保留必要决策历史在Git，不恢复已经删除的历史目录为新基线。

每轮选择关键风险：权限隔离、数据覆盖、丢响应重复收费、失败恢复、供应商能力、性能/容量、运行与退役。记录“风险、验证/处置、责任角色、剩余条件”，按风险补证据，文档数量服从实际问题。正式方法和工程工具有冲突时先指出并更新拥有该决定的正式文档；AGENTS仅维护稳定协作规则。
