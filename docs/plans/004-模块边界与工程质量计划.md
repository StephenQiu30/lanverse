# 模块边界与工程质量执行计划

## 1. 范围与基线

本计划只重排已经存在的 identity、catalog、API、Worker、Scheduler 和 migration；
HTTP、领域规则、数据库字段和前端行为保持不变。开始实现前创建 annotated tag，
记录 `main` SHA，并确认开发数据库各业务表计数。

## 2. 工作包

| ID | 输入 | 最小产出 | 验证 |
| --- | --- | --- | --- |
| M-R01 | DESIGN/PRD v3/v2、当前树 | 目标结构与 migration Red 门禁 | architecture tests 必须针对旧树失败 |
| M-R02 | M-R01 | `backend/src/thief` 单包，移动 identity/catalog/API/runtime | unit、API 契约、lint、mypy |
| M-R03 | M-R02、确认无保留数据 | `migrations/versions/0001_initial.py` 单 head，显式重建开发 DB | 空库 upgrade、heads、downgrade/restore、integration |
| M-R04 | M-R03 | Make/CI/runtime 使用单 source root，删除旧目录 | `make verify`、`make test-runtime`、路径扫描 |
| M-R05 | M-R04 | Acceptance 与 Web/登录回归证据 | agent-browser 健康页/登录页、CI、干净 main |

## 3. Test-first 顺序

1. `test:` 固定唯一 source root、允许模块集合、禁止空占位、单 migration head、统一入口。
2. 证明 Red 来自旧 `apps/packages/migrations/{module}` 结构，而非测试环境问题。
3. `refactor:` 一次移动所有 Python 调用方，不保留旧包 re-export 或双轨 PYTHONPATH。
4. `refactor:` 压缩 migration 并删除空 schema；只在显式确认后重建命名卷。
5. 运行目标与完整验证，回填 Acceptance 后 `docs:` 提交。

从新包导入；禁止在旧路径留下兼容文件。

## 5. Migration 重建步骤

1. 启动 PostgreSQL，只读查询 identity/catalog 表计数和当前 revision。
2. 如果存在非测试数据，停止删卷并记录阻塞；否则停止 Compose。
3. 删除且只删除 Compose 命名卷 `thief_postgres_data`，RabbitMQ/MinIO 卷不受影响。
4. 从空卷运行 `make infra-up && make migrate`，断言一个 head 和预期六张业务表。
5. 运行 `make migrate-down`，断言业务 schema/revision 清空；再次 migrate 并跑 integration。

普通 `make migrate` 不执行删库；重建只发生在本次明确的 pre-release 结构切换。

## 7. 验证命令

```text
make test-unit
make test-architecture
make migrate
make test-integration
make migrate-down && make migrate
make verify
make test-runtime
```

浏览器使用 production standalone 验证 `/health`、`/login`、错误凭据提示与无
console/page error。前端无视觉改动，不重新设计页面。

## 8. 风险与回滚

- import 漏改：禁止旧路径并运行完整 discovery/mypy/compileall。
- migration 基线不一致：只对已确认空的开发卷重建，CI 从空库复核。
- 历史恢复：重构前 tag 保存源码；旧 PostgreSQL 卷仅在计数为 0 时删除。
- 范围膨胀：目录导入、搜索 API、生成和管理继续留在原计划，不进入本任务。
