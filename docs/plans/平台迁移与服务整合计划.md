## 结论

当前兼容运行时与 Next.js 系统不能通过“新增几个目标目录”变成目标架构，也不应一次性重写。迁移采用按业务聚合切换写入所有权的 Strangler 方式：先冻结契约与数据，再建立可运行的目标 Runtime；每个 Endpoint、表、事件和 Workflow 只由一个实现写入，经过兼容、对账、恢复和回滚验收后再退役旧代码。

目标目录树只描述终态。任何 `backend/cmd/*`、`agent/`、Frontend Package 或 Compose Service 都必须随真实可运行能力和测试一起创建，不预建空骨架。

## 当前基线

当前仓库事实：

- Backend：`backend/` 已是单一 Go Module；`cmd/api` 拥有公共健康/就绪入口，并转发尚未迁移的路由。
- Python 兼容运行时：原 FastAPI + SQLAlchemy Async 模块化单体已迁入 `agent/`，暂时继续拥有全部业务写入。
- 运行进程：Go API、Python `agent-api`、Schedule Dispatcher、Outbox Publisher、IO Worker 和 Media Worker 已有独立入口；后四者仍是待迁出的旧执行链。
- Workflow：PostgreSQL 持久任务、Lease/Checkpoint、Kafka IO/Media Topic；没有 Temporal。
- Agent：目录已建立但仍处于兼容期；进程内 Skill/领域 Harness 与旧 API/Worker 共存，部分 Checkpoint 仍直接落业务数据库，尚未达到终态安全边界。
- Frontend：单 npm Next.js App Router 应用，RTK Query + 生成 OpenAPI Client。
- Infrastructure：PostgreSQL、Redis、MinIO、Kafka 已接入；Temporal、Debezium、Elasticsearch、Yjs/Hocuspocus 和完整 Model Gateway 未接入。
- 本机开发：优先复用根目录 `.env` 指向的已安装基础设施，只启动 Python 兼容 API、Go API 与 Frontend；默认不消费共享 Kafka Topic，Compose 全栈用于 Worker 执行、隔离验收和生产拓扑验证。
- 阶段 1 运行契约：Go API 已提供 Health、Readiness、Prometheus Metrics 与 Build Version；Event Envelope v2 JSON Schema/Go 严格解码已建立；Python 旧 Publisher 已显式限定 IO/Media v1 Topic。Audit v2 Consumer/Projection、Baseline Migration 与生产者尚未启用。
- 当前代码已经形成 Production Bible、剧本结构、Asset/State/Version、Storyboard、人工决议、媒体上传/探测/导出等可复用业务语义。

## 可复用资产

迁移不得丢弃以下已验证资产：

- Workspace、Project、Episode、Script、Scene、Shot、Asset、Media、Storyboard 的领域语义与状态机。
- 现有数据库中的版本、候选、人工决议、审计、费用、幂等、Lease 和 Checkpoint 语义。
- `/api/v1` OpenAPI、稳定错误包络、认证流程、前端生成 SDK 与 OpenAPI Drift Gate。
- ObjectStorage Port、Presigned Upload/Download、Storage Profile、Checksum、位置迁移与回滚。
- Outbox/Inbox、Kafka Envelope、Traceparent、重复投递与消费幂等。
- Production Bible/Storyboard 的 Pydantic Schema、Skill、Prompt、Rubric、Golden/Contract Test。
- Guided Studio 页面、Radix/shadcn/Tailwind 组件、Vitest/Playwright 业务旅程。
- JSON 日志脱敏、Prometheus 指标和 Trace 传播。

物理表和 API 名称是否保留由兼容性与数据字典决定，不能按新设计概念表清单直接重建生产数据。

## 迁移总门禁

每个切片在切换前必须回答并验证：

1. 当前和目标写入所有者分别是谁？
2. 哪些 Endpoint、表、Topic、Workflow Type、Index 和 Bucket Prefix 在本切片内？
3. 输入/输出、错误、认证、幂等和版本冲突契约是否兼容？
4. 数据基线、增量追平、Checksum/Count/Invariant 对账如何完成？
5. 旧运行如何 drain，新运行从哪个版本进入新引擎？
6. 切流信号、观测指标、成功阈值和回滚操作是什么？
7. 回滚后是否会出现旧实现不认识的新数据？

双读可用于 Shadow 对账；双写默认禁止。若确有一次性迁移写入，必须由单个迁移程序在维护窗口执行，并记录可验证 Receipt。

## 阶段 1：运行基础设施与契约源

交付：

- 建立 `docker-compose.yml`、`docker-compose-env.yml`、`docker-compose-prod.yml` 的可运行闭环。
- 将 Python/FastAPI 物理迁入 `agent/`，建立唯一 `backend/go.mod` 和 Go 公共 API 入口；未迁移路由只做代理，不改变 Writer。
- 接入 PostgreSQL、Redis、MinIO、Kafka、Temporal、Elasticsearch/Kibana、Kafka Connect/Debezium、OTel Collector、Prometheus/Grafana。
- 固化健康检查、私有网络、Volume、初始化、Secret 注入、资源限制和生产 Override。
- 建立 `backend/api/openapi|proto|event|gen` 的单一契约源和兼容性流水线。
- 建立数据库 Baseline Migration；先把 Python Schema Guard 从“全库必须与本 ORM 完全相等”改为“本 Runtime 必需资源完整 + Migration 版本处于允许范围”，并关闭生产 `create_all`，随后才允许新增目标 Owner 表。
- 将 Schedule Dispatcher 与 Outbox Publisher 拆成独立生命周期、启动入口和显式开关；默认监督进程可分别 Drain，确保后续 Debezium 切换时不误停 Timer 或形成双 Publisher。
- 在首个 Go Command 前，以真实 Audit Projection 用例建立唯一 `backend/go.mod`、最小 `event-worker` 和 Eventing/Audit 闭环。阶段 1 新建 `lanverse.audit.v2` 与 Consumer Group `lanverse.audit-projector.v2`，不在旧 IO/Media Topic 原位升级协议；先部署 v2 Consumer，再部署按 Topic allowlist 领取的 Python Publisher lane，最后才允许写入 Audit v2 Outbox。旧 lane 只领取 `lanverse.io.v1`/`lanverse.media.v1`，Audit lane 只领取 `lanverse.audit.v2`，避免现有 Publisher 抢到未注册 Topic 后反复失败。Baseline Migration 为 Outbox 增加 envelope version、aggregate version、partition key、correlation id、producer idempotency key，移除错误的 `(event_type, aggregate_id, schema_version)` 唯一约束并对 v2 idempotency key 建唯一约束；旧 v1 行允许兼容空值。Event Envelope v2 保留严格字段校验但允许 JSON payload，不复用旧 `dict[str,string]` Contract。为当前全部同步审计动作补等价 Domain Event/Outbox；向独立 AuditRecord 资源 Shadow/Backfill，以 Outbox `(occurred_at,event_id)` high-watermark、Kafka partition offset 和 Projection Checkpoint 完成 100% 字段/数量/顺序对账；原子切 Audit Query 后停旧 `gov_audit_events` 同步 Writer。此后 Python/Go Command 都只写各自业务事实 + Outbox，Eventing 是唯一 AuditRecord Writer；阶段 6 再以 PostgreSQL LSN/Watermark 将各 lane 统一切到 Debezium。

实施约束：Compose 只在服务可启动且 Health Check/持久化验证同时存在时创建；真实 Secret 不进入仓库。Schema Guard 兼容切片必须先在旧 API、Scheduler、IO Worker、Media Worker 全部验证，再应用任何目标表 Migration。Audit v2 必须按“建 Topic/Group → Consumer-first → 带 Topic Filter 的 Publisher lane → Producer/Outbox”部署，任一旧 Consumer 不得接收 v2；Audit Shadow 只能写独立目标资源，旧/新 Writer 不得同时写同一 Audit 表。

完成门：从空 Volume 能初始化，从已有 Volume 能重启恢复；Python/Go Schema 兼容窗口与回滚演练通过；Publisher/Dispatcher 可独立启停和 Drain；Event Envelope v2 兼容、Audit 事件覆盖率/对账均为 100%、旧同步 Audit Writer 已关闭；关键服务故障有可观测降级；契约生成无漂移。

## 阶段 2：Frontend 机械 Monorepo 化

顺序：

1. 用 `git mv` 将当前应用原样迁入 `frontend/apps/web`，先保持路由、行为和测试不变。
2. npm 切换为 pnpm Workspace + Turborepo，恢复 lint/typecheck/unit/build/E2E 门禁。
3. 抽取生成 API Client 到 `packages/sdk`，抽认证到 `packages/auth`，抽现有基础组件到 `packages/ui`。

完成门：迁移前后关键页面视觉/交互、URL、认证、API 请求和 E2E 等价；Package Dependency Test 通过。

## 阶段 3：Go Core 纵向切片

在阶段 1 已建立的唯一 `backend/go.mod` 和 Go API 入口中增加首个真实 Core 业务切片。阶段 1 的代理与健康接口不代表任何业务聚合已经迁移；迁移期不允许同一聚合双写。

顺序：

1. 复用阶段 1 的 Baseline Migration 与兼容 Guard，建立配置、日志、Telemetry、错误、认证 Context、sqlc 和 Health/Readiness。
2. 先实现只读 Shadow API，与 FastAPI 响应做 Contract/Differential Test。
3. Go 接管首张业务表前再次验证阶段 1 的 Guard/Migration 版本窗口、Audit Projector 和旧 Writer 关闭证据，再应用首张业务表 Migration；不得建立第二份 Baseline。
4. 首个写入切片整组迁移注册与 Workspace：DB-01 User、DB-02 Workspace/Owner Membership、DB-02C Registration Receipt、同事务 DB-21 Outbox，以及 Redis Verification Ticket Claim 与 Auth Session；DB-20 Audit Projector 已成为唯一 Writer只是切流前置，不加入注册事务。先让 SDK 发送旧服务可忽略的 `Idempotency-Key` Header，目标服务保持现有注册 Body并由 Ticket HMAC 派生 Challenge Ref；等一个旧 Ticket TTL 后才按完整 Endpoint 族切流，不能先切纯 Workspace Writer。
5. Project Writer 切换前，先把 `prj_projects` 的预算列一次性回填到 Cost 拥有的 `BudgetPolicy` 资源，切换 Budget Command，并把旧列冻结为只读兼容投影；随后才迁移 Project → Episode，禁止 Python Cost 与 Go Production 按列共写同一行。
6. 阶段 3 只切 Script Document/Version 等不受运行同行写影响的 Production 事实；Production Bible、Asset Registry/Rights 与 Storyboard 均只做 Shadow Read。旧 Bible/Extraction/Draft Run 会同时写 Bible、Asset、Occurrence、Shot 等行，故 DB-06A/08/10/11/12/14A/14B/19 的 Writer 统一留到阶段 5，不能按列或按 Endpoint 提前切。`scr_script_documents/revisions` 对 `med_media_versions` 的 FK 暂作 Legacy Media Ref，不写 Media 表、不伪装成 Artifact ID；阶段 6 再与其他入向 FK 一次转换。

完成门：OpenAPI compatibility、权限、幂等、数据库不变量、事件、E2E 和回滚演练通过；Shadow 差异为零或有已接受解释。

## 阶段 4：Model Gateway 与独立 Agent

先实现一个经过真实 Provider Contract 验证的结构化文本能力，再扩多模态：

1. 先核验 DB-16A/B/D 真实数据；因 GenerationRequest 与 ProviderBinding 都强 FK 到 `prod_model_capabilities`，使用同一 Catalog/Schema Migration 建立 Capability 管理/Seed、版本审计、引用回填和兼容读，不能独立切表。
2. 建立 DB-16C Submission Intent/Receipt 与 DB-17B Quota；将 DB-17A 从 `request_id NOT NULL` 的旧模型分解为按通用 `operation_intent_id` 预留的新 CostReservation。旧 request-linked Reservation 随旧 Engine 排空，目标准备事务不能等待尚未创建的 GenerationRequest。
3. 部署 `lanverse.generation.v1`、`model-gateway-submission.v1` 与 `generation-submission-intent-updater.v1`，两个 Consumer/Inbox 和 API internal `AcquireExecutionClaim` 先于 Producer 启用。Intent Event 不携带短时 Token；Gateway 消费时由 API 原子锁定 Intent/Cost/Quota 并签发 Claim Authorization，Receipt 再按 Claim Fence 回写 API 收敛状态。
4. Model Gateway 建立 Generation Capability、Model Policy、Provider Job、Callback、Rate Limit、Provider 报价与 Usage Report；它不拥有 Cost/Quota Reservation。Claim 后取消、Gateway 崩溃、Token 到期和迟到 Receipt 必须按原 Provider Request Key/Claim Version 对账，禁止新 Intent 重提。
5. 完成上述闭环并通过 Consumer-first、故障注入与 Reservation/Intent/Receipt 对账后，才允许第一次真实付费 Provider 调用。
6. Agent 建立 gRPC API、Run Context、StructuredExecutor 和受限 Tool/Model Client。
7. 首先迁移 Script Agent，再迁移 Production Bible、Storyboard 和确需 LangGraph 的有限 Repair Harness；复用当前 Schema/Prompt/Skill/Golden Test 做新旧等价验证。
8. 将 Checkpoint 所有权交给 Workflow/Backend Tool API，移除 Agent 的 PostgreSQL、MinIO、任意 Shell 和任意网络凭据。

当前本地 Codex Harness 的“业务长流程不设总墙钟截止”转换为：单次模型/Graph Activity 有有限预算，Episode 生命周期由 Temporal 续接多个 Activity；不得简单删除恢复语义。

完成门：结构化输出、预算、取消、Tool Allowlist、安全扫描、Golden/Regression 与真实 Provider 对账通过。

## 阶段 5：Temporal 接管新运行

交付：

- 先停止创建新的 Bible/Extraction/Draft 旧 Engine Task，排空 DB-06A/08/12 的 Task/Lease/Checkpoint；旧 Bible 行尚未稳定前禁止目标 Writer。随后同一 Schema 切片把 DB-08 Bible 内容/Revision、Review Receipt 与 Run 字段分解，并同步转换 DB-06A/DB-12 对 Bible 的强 FK Anchor。
- 在上述排空后整体切换 Production Bible、Asset Registry/Rights、Review Apply、Storyboard DB-10/11/12 与 Occurrence DB-14B；Bible 发布 + Asset 物化、Bible Review Apply、Storyboard Draft Apply 都由 `lanverse-api` Coordinator 在各自共享 Unit of Work 收口。
- Guided 所需的最小 `AuthoringDraft/AuthoringRevision`、系统 Node Catalog、Graph Validation 与 Workflow Compiler；Guided 模板也必须先发布 Revision，不能直接启动 Temporal。
- `workflow-worker`、ShortDramaEpisodeWorkflow、ShotWorkflow、Human Gate、Node Cache 与 Workflow Definition Version。
- Agent、Model、Media Activity 的 deadline、retry、idempotency、heartbeat 与 cancellation。
- Workflow Start/Control Intent、稳定 Temporal Workflow ID、幂等 Signal Receipt、Unknown Outcome 对账、Workflow/Node 业务投影、SSE 状态与 Trace 关联。

切换规则：旧 Task/Run 继续由旧 Kafka/Lease 链按 lane drain；切换版本之后创建的新 Run 只进入 Temporal，禁止迁移进行中的 Run 或让同一 Run 被两个引擎处理。`prod_tasks` 仍被阶段 4 Generation、阶段 5 Planning/Extraction/Adaptation/Bible/Draft 和阶段 6 Export/Media 等资源强 FK 引用，因此不在本阶段整表删除；各 lane 随所属资源移除 FK，旧表保留只读/排空到阶段 9。

完成门：Guided Draft→Revision→Definition→Temporal 链路、Worker/服务重启、Provider timeout、Human Wait、单 Shot 重跑、取消、补偿和 Temporal Replay 测试通过。

## 阶段 6：Media 与 Event 能力扩展

本阶段以同一个物理 Schema 分解 Migration 和 Writer 切换，同时完成 DB-15A 与 DB-15B：Asset 接管 Upload/Artifact/Location/Lineage/ObjectStorage，Media 接管从 `med_media_versions` 拆出的 `MediaProbeResult`。切片必须同时处理所有入向 FK：阶段 3 保留的 `scr_script_documents/revisions`、阶段 5 切换后仍保留 Legacy Ref 的 `ast_media_references` 与 `gov_consent_proofs`，以及本阶段的 `sbd_export_manifests`；先建立 Artifact ID 映射与新 Ref 列、单迁移程序全量+增量回填，维护窗口冻结相关 Writer 后原子切为 Artifact/Proof Ref，再移除旧 FK，禁止业务代码按列双写。新 Media Probe 只持久化 Probe Receipt，再通过 Asset Command 推进 Artifact Readiness。随后迁移 ffprobe、Storyboard Export 及其旧 Task lane，再补 FFmpeg 转码、字幕、混音、GENERATE/COMPOSE/HYBRID Motion 与 `RenderManifestVersion`。

Event Worker 在阶段 1 最小 Event Envelope v2/Audit Projector 基线上接管其余 Kafka Consumer、Search/Cost Analytics Projection、通知、DLQ、Replay 与 Reindex；Workflow Control/Signal 仍由 `workflow-worker` 专用 Consumer Group 处理。以 LSN/Watermark、Outbox、Offset、Inbox 做 Debezium 对账；使用阶段 1 的独立开关在同一切换窗口停用旧 Python Outbox Publisher，不能两个 Publisher 同时发布。

完成门：媒体 Hash/时长/格式、对象迁移回滚、事件重复/乱序、DLQ Replay、全量 Reindex 和 Cost 对账通过。

## 阶段 9：退役旧 Backend

只有以下条件全部满足才删除 FastAPI 业务实现：

- 所有 Endpoint/聚合 Owner 已切换并完成回滚窗口。
- 旧 Workflow 全部 drain、终止或有可审计处置。
- 数据对账、事件回放、Search Reindex、媒体 Hash 和 Cost 账本一致。
- Go/Agent/Frontend/Deployment 的 CI、Integration、E2E、Performance 和恢复演练通过。
- Python 最终只保留独立 Agent Runtime；不存在 Backend 兼容层或双 ORM。
- `prod_tasks` 全部 13 类 lane 的 pending/claimed/Lease/Inbox/Schedule 归零，所有入向 FK 已按阶段 4–6 分解，历史 Task/Fire Receipt 已归档可查后才删除旧表。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 双写导致事实分叉 | Owner 清单、按 Endpoint/聚合切流、默认禁止双写 |
| Schema 被 Python/Go 同时管理 | Baseline Migration；Go 接管前关闭 Python Schema 管理 |
| 旧任务被重复执行 | Workflow Definition 版本路由；旧 Run drain，新 Run 只进 Temporal |
| Outbox 重复发布 | Debezium 切换窗口停旧 Publisher；Event ID 幂等和对账 |
| Agent 跨进程后权限扩大 | 先建立 Tool/Model RPC 与执行令牌，再移除 DB/Storage/Shell 权限 |
| Frontend 同时换目录、状态和 UI | 机械移动、包管理器、Package 抽取、状态迁移分步完成 |
| 目标目录变成空脚手架 | 每个目录随首个真实用例、测试和运行入口一起创建 |
| 绿地重写丢失业务语义 | 复用当前 OpenAPI、Schema、不变量、Golden Test 和真实 60 集验收 |
